## 1. Claude Haiku 5.5 {#story-1}
*#1 on HN · [anthropic.com](https://www.anthropic.com/claude-haiku-5-5) · 240 points · 102 comments · [HN discussion](https://news.ycombinator.com/item?id=49996437)*

Anthropic announced Claude Haiku 5.5, its cheapest, fastest and most capable small model yet, aimed at high-volume work like summaries, compaction, classification and subagent tasks. Pricing is tiered: $0.10/$0.50 per Mtok input/output for prompts up to 100k tokens, jumping to $0.50/$2.50 above that — Anthropic says this is about 75% cheaper on average and 90% cheaper than Haiku 4.5 under 100k tokens, where it claims 90% of Haiku 4.5 requests fell. The post also halved Sonnet 5.5 cache reads to $0.10 per Mtok and introduced monthly API credits for Max 5x ($100), Max 20x ($200) and Team (up to $500 pooled) subscribers, plus new computer-use/browser-use support in the Python and TypeScript SDKs.

**Discussion**: The dominant thread is pricing: many call the 100k-token threshold absurdly low for agentic use, while others point out Anthropic's own claim that 90% of Haiku 4.5 traffic sat under it and note GPT-6 Luna has a similar, higher 272k threshold (commenters add that tokenizer differences make Claude's 100k roughly 60-65k GPT tokens). Several users say Haiku 5.5 looks smarter than Luna at matching $0.10/$0.50 sub-100k pricing, with OpenRouter showing 131 tok/s P50, though skeptics argue cheap Chinese models (GLM, MiMo) still win on cost per completed task only if you ignore token-hungry output. A recurring criticism, raised twice, is that the monthly API credits quietly coincide with the Claude Agent SDK moving off Claude subscriptions to API billing — a change Anthropic had backed away from in June. On the practical side, commenters welcome the credits, report Haiku's sweet spot as low-reasoning grunt work and document parsing, and note it knows its limits: in one image-to-HTML test it immediately delegated the job to Opus.

**Worth reading**
- [minimaxir](https://news.ycombinator.com/item?id=49996502): Breaks down the tiered pricing as oddly aggressive — a 100k cutoff unique to Haiku that agent workloads will blow past, but still far cheaper than Haiku 4.5 and competitive with GPT-6 Luna.
- [thepasch](https://news.ycombinator.com/item?id=49997143): Argues the API credits are a back-door way of re-introducing the June change that takes the Claude Agent SDK off subscription plans, with a link to Anthropic's support article.
- [jjcm](https://news.ycombinator.com/item?id=49996898): Ran image-to-HTML UI tests with links to outputs: Haiku 5.5 produced something entirely different from the design while Opus 5.5 matched near pixel-perfect, though Haiku knew to delegate.

## 2. GPT‑6 and Intelligent UI for everyone {#story-2}
*#2 on HN · [openai.com](https://openai.com/index/gpt-6-for-everyone/) · 135 points · 56 comments · [HN discussion](https://news.ycombinator.com/item?id=49996425)*

OpenAI's launch post for GPT‑6 in ChatGPT, which ships Intelligent UI: the model composes responses from a library of native streamable components (charts, sliders, forms, tappable buttons) plus a compiler that renders the interface progressively as it generates. It also interleaves thinking with answering — OpenAI says GPT‑6 Instant starts answering 44% sooner on web-search questions than GPT‑5.6 Instant, and that GPT‑6 Extra High matches GPT‑5.6 Medium's time-to-first-answer while beating GPT‑5.6 Extra High on internal agentic evals. Rollout hits Plus, Pro, Business and Enterprise today and Free/Go tomorrow, powered by GPT‑6 Sol (paid) and GPT‑6 Luna (free); Work and Codex models are unchanged.

**Discussion**: The dominant reaction is aesthetic and product-level pushback: several users say the generated layouts — cards, checklists, whitespace, taglines — feel condescending or bloated, and some explicitly ask for text-only output so it can be exported and processed. A recurring complaint is that chat is powered by GPT‑6 Sol rather than the newer, more capable GPT‑6.1 Sol, with users speculating (without sources, and one explicitly asking for sources) that 6.1 is a rebranded, heavier model shipped to cover for GPT‑6's weaker agentic performance; others note they hit capacity limits on 6.1 Sol on both $200 Pro and enterprise Codex accounts. Practitioners point out this is not new: models in a GUI harness already render inline HTML/artifacts on request, and Codex/Astra already write full HTML documents for non-linear data, so this is mainly productizing an existing behavior — with the real question being latency and how the model decides when UI is warranted. A minority is enthusiastic about accessibility (elderly, disabled, ADHD users), while skeptics note there's no way for users to tell whether a generated visualization is accurate, and the article's own page/player drew complaints for a broken video player and for the bike-disassembly graphic looking anatomically fake. Best-received observations are that Bartosz Ciechanowski's hand-coded WebGL explainers remain unmatched (and that he now works at OpenAI), and that the GPT‑6 vs 6.1 choice is the story's most substantive question.

**Worth reading**
- [FLeXMurphy](https://news.ycombinator.com/item?id=49997098): Argues Ciechanowski's rise and the loss of hand-drafted explanations came from CAD and short-form video killing careful technical writing, so his style is already being consigned to history.
- [MikhailTal](https://news.ycombinator.com/item?id=49997112): Claims without citation that GPT‑6.1 is a heavier 'Astra minor' model rebranded as Sol in a panic after GPT‑6's disappointing launch, making them effectively two different models.
- [wincy](https://news.ycombinator.com/item?id=49996798): First-hand report that Codex work mode with Astra and Sol already writes full HTML documents for complex non-linear data, unprompted — evidence Intelligent UI productizes existing behavior.

## 3. Visa, Mastercard, Major Banks Facing New Litigation over 'Anticompetitive' Fees {#story-3}
*#3 on HN · [classaction.org](https://www.classaction.org/news/visa-mastercard-major-banks-facing-new-litigation-over-anticompetitive-merchant-credit-card-transaction-fees) · 297 points · 165 comments · [HN discussion](https://news.ycombinator.com/item?id=49993914)*

这是一篇 ClassAction.org 的报道，介绍 Pizza Standard LLC 诉 Visa 等公司一案（2026 年 9 月 30 日提起，加州南区法院，案号 1:26-cv-06087）。这份 134 页的诉状指控 Visa、Mastercard 以及美国银行、Capital One、Chase、花旗和富国银行数十年来合谋统一设定交换费（interchange），并称商户每年为此支付超过 1000 亿美元；案件代表自 2019 年 1 月 25 日起接受 Visa/Mastercard 信用卡的所有美国商户。诉状称此前和解（约 50 亿美元，2019 年 12 月获批）只覆盖 2019 年 1 月 24 日之前的『集体诉讼期』，因此 2019 年之后被收取的费用没有任何补偿。

**Discussion**: 讨论迅速从本案转向一个更广泛的争论：最高票评论认为支付、物流这类中间商已无多少附加价值，甚至应作为公共服务运营，随后大量回复则强调支付网络要承担欺诈、合规（PCI-DSS）和争议处理成本，不能只看「转发一个数据包」的成本；有加拿大从业者指出 Interac 借记每笔仅约 10 加分、欧洲和中国等地的替代系统证明低费率可行。另一场争论围绕费率构成：有人纠正说收单机构（而非卡组织）设定商户折扣率，但这些诉讼从不把收单机构列为被告，也有人贴出 Stripe 2.9% + 30 美分的拆解，指出固定费用在小额交易中占比极高，而 EU 对借记 0.2%、信用卡 0.3% 的费率上限以及美国 Durbin 修正案被反复引用。关于争议处理／拒付（chargeback）的体验也两极分化，多人抱怨 Amex Platinum 和 Chase 的拒付流程漫长、被反复要求提供同样材料，另一些人则说能为拒付多付 3% 完全值得。多处评论批评集体诉讼和解的结构：钱大多归律师和第三方机构，商户与消费者拿不到钱，还有人对反复抱怨『跑题』的元评论表示不满。

**Worth reading**
- [tiffanyh](https://news.ycombinator.com/item?id=49996621): 用 Stripe 的 2.9% + 30 美分举例说明固定费用常被忽视：30 美元的交易中这 30 美分相当于 1%，使实际费率接近 3.9%，而流向发卡行的交换费只有约 1.75%。
- [jijji](https://news.ycombinator.com/item?id=49996178): 第一手经验：FedNow 每笔收 0.045 美元、7×24 即时到账，Same Day ACH 约 0.30 美元／笔，并把 B2B 争议窗口从信用卡的 120 天缩短到 3 天，作者称其企业因此节省数百万美元手续费。
- [gadders](https://news.ycombinator.com/item?id=49996070): 引用 Oliver Bateman 的访谈与播客，用一个谷歌隐私诉讼和解的实例说明集体诉讼里律师拿走 1900 万美元、200 人的集体获得零赔偿、其余资金流向与原告律师有关联的机构。

## 4. Show HN: Bigwords.page – Turn any screen into a sign. The URL is the app {#story-4}
*#4 on HN · [bigwords.page](https://bigwords.page/) · 144 points · 46 comments · [HN discussion](https://news.ycombinator.com/item?id=49994443)*

Bigwords.page is a Show HN single-page web app that turns a URL into a full-screen sign, timer or message: everything after the # fragment encodes the message plus settings such as bg, fg, font, interval, timer and until, with markdown, || slide splitting, {countdown}, QR codes, and pulse/scroll/rainbow animations. The pitch is that the fragment is never sent to a server, so there is no backend, no account and no storage, and the whole thing is MIT-licensed and self-hostable. The author (SpeakingOfBrad) built it so a URL could configure a remotely managed display he had no physical access to.

**Discussion**: The thread is broadly positive: people call it a clean example of DOTADIW and like the idea of the URL as data or argv for a static app, and several say they already have a use for it (conference signs, a broken-car message from a phone, a Unix-timestamp countdown for cross-timezone game nights). The main disagreement is over the submission title 「The URL is the app」 — notpushkin and rpdillon call it LLM-speak and factually wrong, arguing the app lives on the server and only the content lives in the URL, while rendleflag pushes back that there is no evidence of AI authorship and it is just terse phrasing. In reply, the author (SpeakingOfBrad) confirms it uses the URL fragment precisely because browsers never send fragments to the server, and admits the title was compressed because he had only 80 characters. Suggested extensions include Google TV / Apple TV apps and letting one device control what another displays, with wiradikusuma plugging his own signagesync.app for multi-screen café video walls; other notes include nostalgia for bigassmessage.com, an unanswered complaint about the obtrusive Open Graph thumbnail in Apple Messages, and one report of an SSL warning on Firefox. A separate historical nod comes from okaleniuk, who built a teaching slide deck where the URL is the slide.

**Worth reading**
- [SpeakingOfBrad](https://news.ycombinator.com/item?id=49994461): The author explains the origin: he needed to push a message to a remotely managed tablet with no physical access, and solved it by making the message the URL fragment, which browsers never send to the server — no backend, no storage, MIT-licensed and self-hostable.
- [rpdillon](https://news.ycombinator.com/item?id=49997107): A pointed correction of the title: the URL is not the app, the app runs on the server, and the whole thing is essentially a differently-shaped version of the textarea project at github.com/antonmedv/textarea.
- [okaleniuk](https://news.ycombinator.com/item?id=49997241): okaleniuk links his own teaching deck built on the same principle (「URL is the slide」), noting the shared benefits: no backend, no storage, no data collection, no authorization.

A commenter comparing it to modal.com, e2b and Cloudflare questions why Docker Agent is needed when those already provide original Docker plus tooling and network-level isolation, and another dismisses the whole thing as vague.

**Worth reading**

## 7. Shipping JPEG XL in Chrome {#story-7}
*#7 on HN · [developer.chrome.com](https://developer.chrome.com/blog/jpeg-xl-in-chrome) · 390 points · 253 comments · [HN discussion](https://news.ycombinator.com/item?id=49991227)*

A Chrome developer blog post announcing that Chrome 155 ships decoding support for JPEG XL (.jxl). The post claims 30–50% better compression than JPEG, lossless JPEG transcoding, HDR, progressive decoding and lossless compression, and describes reimplementing the decoder in Rust as jxl-rs — with a SIMD abstraction layer (jxl_simd) inspired by the C++ Highway library used in libjxl — so that unsafe code is confined to a few vetted spots, claiming fuzzing and AI review found no memory-safety bugs. Google recommends trying both AVIF and JPEG XL, expecting JXL to be strongest for high-fidelity or lossless photographic use.

**Discussion**: The thread is broadly celebratory: the top commenter notes that during October JPEG XL goes from Safari-only to majority browser coverage, with Firefox (158) following Chrome. Sceptics argue the payoff is marginal — one says they will stick with properly optimised JPEG and PNG because any old browser handles them, others complain about yet another format and about compatibility with older software and cameras — while supporters reply that JXL is not only about compression: 32-bit float, layers, spot colours, depth maps, HDR and lossless recompression of existing JPEGs are things JPEG and PNG genuinely cannot do. The most concrete practical objection is server-side encode cost: an operator of a media-upload site says AVIF encoding raised processing time roughly 10–20x, forcing a switch to async jobs plus a hardware upgrade, and expects the same for JXL until encoders are baked into silicon. Much of the thread speculates about why Google reversed its 2022 removal; the most-cited explanations are the Rust rewrite removing the memory-safety objection, and Adobe/the PDF Association adopting JXL as a PDF image format, which forces every PDF renderer to bundle a decoder anyway. Side threads cover WebP's uneven support in apps and OSes, whether lossy versus lossless can be signalled in the file extension, and whether browsers should use system shared libraries (AmigaOS DataTypes, BeOS Translators, Windows WIC) instead of vendoring codecs.

**Worth reading**
- [jjcm](https://news.ycombinator.com/item?id=49996253): First-hand account: accepting user-uploaded AVIF images produced a 10–20x jump in processing time, forcing async pipelines and a hardware upgrade — the cost trade-off versus WebP was not worth it, and the same is likely for JXL without hardware encoding.
- [pwg](https://news.ycombinator.com/item?id=49991548): Argues the real turning point for Chrome was Adobe/PDF Association approving JPEG XL for the upcoming PDF spec, since browsers-as-PDF-renderers then have to ship a JXL decoder anyway and can expose it to img tags.
- [mort96](https://news.ycombinator.com/item?id=49994322): Links an ongoing jxl-rs (Rust) versus libjxl (C++) benchmark by Luca Versari, a JPEG XL standardisation participant and main jxl-rs developer, showing the Rust decoder faster on almost all tests since June 2026 at slightly higher RAM use.

**Worth reading**

## 9. A font recreated from photographs of classic Commodore 64 keycaps {#story-9}
*#9 on HN · [github.com](https://github.com/szabadkai/c64-keyboard-font/) · 334 points · 56 comments · [HN discussion](https://news.ycombinator.com/item?id=49990224)*

Levente Szabadkai's C64 Keyboard is a CC0-licensed typeface reconstructed from photos of classic Commodore 64 keycap lettering, with cleaned-up outlines rather than exact photo traces. Version 1.111 ships as TTF/OTF plus a webfont, covering uppercase letters, numbers, punctuation, arrows, £ and π, selected Hungarian accents, f1–f12 labels, and all 63 PETSCII graphic front legends, with editable glyphs and build scripts in the repo. Identities and key assignments come from the Ultimate Commodore 64 Reference; the private source photographs are not included, and lowercase input renders as uppercase to mimic printed legends.
