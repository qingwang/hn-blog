## 1. Lovable 应用泄露护照信息及逾 20 万条私密消息 {#story-1}
*HN 第 1 名 · [crissyfield.de](https://www.crissyfield.de/research/lovable-en/) · 273 分 · 84 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50499017)*
*原标题: Lovable apps expose passport details and more than 200K private messages*

一位安全研究员（HN 用户 neathack）与 Handelsblatt 记者 Lina Knees 合作，分析了从 Common Crawl 抓取的 159,041 个 Lovable 构建项目，时间跨度为 2025 年 12 月至 2026 年 9 月。这些项目中有 34,545 个使用了 Supabase，其中 24,664 个在页面加载时无需任何登录即返回 Supabase 记录；据作者称，通过进一步发出只读请求（从不越过分页的第一页），团队在 7,403 个站点（该子集的 30%）的 10,560 张表中发现了电子邮件地址。点名的案例包括：一个德国生活方式论坛泄露了 80,000 多份个人资料和 200,000 多条聊天消息；一家服务商暴露了 1,000 多条包含护照号码、有效期和国籍的记录、280,000 个客户邮箱，以及合同、发票、相册和内部 WhatsApp 聊天记录；作者指出 30% 这一数字并非经确认的泄露率，且 Common Crawl 样本并不具代表性。

**讨论**: 争论最激烈的焦点是研究伦理而非漏洞本身：jacquesm 认为作者从白帽跨越到了「很可能是犯罪」的地步，因为他为了评估严重程度而拉取了大量数据，而不是在证明可访问后就停手；作者则回应说，只抓取了第一页，完整数据集已披露给 Lovable，且这项工作是和一位数据保护与道德黑客领域的律师共同完成的（jacquesm 说这一细节应当写进文章里）。多位评论者把矛头指向 Supabase 历史上的默认设置以及行级安全策略的复杂性——有人链接了一个 Supabase 讨论帖，称修复已于 10 月 30 日落地，但已有项目可能仍保留旧的默认设置——一位从业者解释说，Lovable 架设在 Supabase Auth 之上并提供浏览器端数据库访问，因此把 RLS 弄错很容易，他还描述了自己只把 Lovable 用于原型开发，随后将其 eject 并在审查后重新部署到别处。其他人则认为 AI 只是偶然因素（糟糕的访问控制早于它存在），真正新鲜的是规模以及完全缺乏技术把关，最激烈的一串讨论要求追究责任和 GDPR 后果——作者对此反驳说，能被起诉的是客户，而不是 Lovable。一个长串子讨论嘲讽「无证驾驶客机」的类比是安全至上主义，另一串讨论则在争论在 LLM 出现之前工程界是否曾经在意过质量。

**值得一读的评论**
- [SOLAR_FIELDS](https://news.ycombinator.com/item?id=50499905): 认为 Supabase 也难辞其咎：它刻意选择了无摩擦的入门体验而非默认安全，而一个 GitHub 讨论表明 10 月 30 日的修复可能不适用于已有项目。
- [dudus](https://news.ycombinator.com/item?id=50500145): 从业者的解释：Lovable 把 Supabase Auth 和一个浏览器端 JS 客户端放在数据库前面，因此授权完全依赖手写的 RLS 策略——这与 Firebase 是同一种失败模式——该评论者所在的团队只用 Lovable 做原型，然后 eject 并重新部署到别处。
- [neathack](https://news.ycombinator.com/item?id=50499661): 作者补充了一个文章中没有的数字：一个置信度为 85% 的分类模型判定约 4,000 个站点（约占使用 Supabase 的 Lovable 项目的 15.9%，约占总分析量 159k 的 2.5%）在泄露隐私敏感数据。

## 2. 美国国税局（IRS）免费在线报税开源代码仓库 {#story-2}
*HN 第 2 名 · [github.com](https://github.com/IRS-Public/direct-file) · 62 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50499083)*
*原标题: US IRS free online tax filing open source repo*

GitHub 仓库 IRS-Public/direct-file 是 Direct File 的源码发布版本；Direct File 是 IRS 提供的免费、以访谈问答方式完成联邦电子报税的服务。该仓库依据 2024 年《SHARE IT Act》（Public Law 118-187）和 OMB M-16-21，按 Tax Year 2024 公开发布。仓库文档描述了基于 Scala 的 Fact Graph（一种 XML 知识图谱，可对尚未填完的申报表进行推理，运行于 JVM，并通过 Scala.js 转译到浏览器中运行）、向 IRS Modernized e-File（MeF）API 的传输，以及一个 State API：该 API 会把 MeF XML 连同经过增强的 JSON 一起传给第三方州级报税工具。该项目由 IRS 内部团队与 USDS、GSA 以及供应商 TrussWorks、Coforma、ATI 共同构建。README 声明该仓库已归档、无人维护，已移除与 PII/FTI/SBU/NSS 相关的代码，并且不应在生产环境中使用。

**讨论**: 这个讨论串在很大程度上是一场针对「它为何存在、它是否重要」的全民公投：一方质疑这个仓库是否合法，指出在 irs.gov 上搜索找不到任何指向它的链接，并指出 Direct File 项目已在 DOGE 之下被砍掉；另一方引用了最早的那个 pull request，其中一位评论者说开发已于 2025 年 1 月停止，代码之所以公开只是因为联邦法律要求如此。有几个人把那些被关闭的 PR 解读为业余的 Git 使用证据，另一些人则反驳说，政府开发者可能只是刚接触 Git，或者身处驱动力低的机构文化之中。在政策层面，一位评论者预计在最近的国会格局变化之后，Direct File 会回归并被永久化；另一位则认为，考虑到团队已被裁员、以及本届政府在《Impoundment Control Act》上的争议，2028 年之前不会有任何进展。一个反复出现的附带争论是国际比较：欧洲人指出，他们大多根本不需要申报，因为收入已被预先申报；一位长期居住在美国的人说，把美国对欧洲数字服务的嘲讽与 90 年代水平的美国行政工具放在一起看显得很奇怪；还有人预测，AI 编程会对 TurboTax 做出这个仓库所暗示的那种事。

**值得一读的评论**
- [ram1500natrluvr](https://news.ycombinator.com/item?id=50500103): 引述了 elijah-wright 提交的 PR #1 的原文，其中说他从一位前 IRS 项目经理处得知，Direct File 的开发已于 1 月停止，代码之所以公开只是因为联邦法律要求如此。
- [simonw](https://news.ycombinator.com/item?id=50500188): Simon Willison 指出，用 Google 搜索 site:irs.gov 找不到任何链接到该仓库的结果，并将其归因于 DOGE 砍掉了这个项目。
- [raverbashing](https://news.ycombinator.com/item?id=50500164): 提出了一个实际且尚未解决的问题：接收这些 JSON/XML 载荷的 IRS MeF 报税端点是否仍然开放、是否仍可免费使用。

## 3. PyPI 重新设计的项目页面已上线，安全信号更清晰 {#story-3}
*HN 第 3 名 · [blog.pypi.org](https://blog.pypi.org/posts/2026-11-06-ui-updates-complete/) · 148 分 · 52 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50497892)*
*原标题: PyPI's redesigned project pages with clearer security signals are now live*

PyPI 完成了从 7 月开始的界面改版，新增专门的 security 标签页，显示每个 release 的 provenance 状态（全部文件都有 attestation、完全没有、部分文件有、文件来自不同构建系统或仓库、以及「以前有 attestation 现在没有」的回退警告），并可逐文件查看 PyPI Publish 和 SLSA Build Provenance attestation 及透明度日志链接。项目页面把 provenance 警告置顶，release files 表支持搜索/过滤并标出 late files（首个 release 后超过 14 天上传的文件，2026 年 7 月起已禁止），release history 也显示文件数、provenance 状态和 quarantined/yanked/archived/pre-release 状态。工作由 OpenSSF 资助、Kabu Creative 实现，遵循 OpenSSF Attestations Style Guide。

**讨论**: 争论几乎全部集中在信任模型上：一批人认为这套机制把 Python 生态的安全押在 GitHub、GitLab、Google 等美国大型营利公司身上，是中心化与锁定，并对 PyPI 当年移除 PGP 支持耿耿于怀。PyPI 维护者 woodruffw 在帖中大量回帖澄清：微软没有为 Trusted Publishing 或 attestations 付钱，支持哪些平台是务实而非教条的选择；本地构建未来可能通过 email attestation 获得签名，而「一旦用了 Trusted Publishing 就永久不能回头」的说法是错的；Codeberg 之所以迟迟未接入，是底层 Forgejo 目前要把 OIDC 私钥落盘，达不到 PyPI 作为凭据代理所需的密钥管理标准，但他本人希望有非营利提供方加入。SQLAlchemy 作者 zzzeek 提供了最有分量的实战抱怨：只要有部分文件带 attestation，其余文件就会触发大红警告，而且上传这种文件时 PyPI 根本不发邮件通知。另有多人指出 attestation 只证明代码托管在大平台并用其 CI 构建，既不识别恶意项目，也不防仓库被入侵，因此有人呼吁把精力转向可复现构建和分布式审查；也有人调侃「根本没人会去看这些页面」。

**值得一读的评论**
- [zzzeek](https://news.ycombinator.com/item?id=50498790): zzzeek 以实际维护者身份说明：同一项目里只要部分文件走 Trusted Publishing、其余文件不走，就会挂上大红警告，PyPI 却不发任何邮件通知（当年弃用 GPG 时可是每个签名都发信），而且他以为这是不可逆的开关。
- [woodruffw](https://news.ycombinator.com/item?id=50498894): woodruffw 直接纠正上面两点：这不是永久开关，并给出讨论链接；同时表示 PyPI 一直欢迎更多 publisher provider，只要满足密钥管理与知名度要求。
- [woodruffw](https://news.ycombinator.com/item?id=50499442): woodruffw 强调如果把 attestation 当成「安全金牌」就搞错了前提——它只是对一组声明做密码学签名以便审计，并给出支持本地构建的 email attestation 讨论链接。

## 4. 软件职位名称的家族树 {#story-4}
*HN 第 4 名 · [zwischenzugs.com](https://zwischenzugs.com/2026/11/03/a-family-tree-of-software-job-titles/) · 70 分 · 21 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50499038)*
*原标题: A Family Tree of Software Job Titles*

Ian Miell（zwischenzugs）用 Graphviz 渲染了一棵包含 104 个软件职位名称的家族树，从「Computer」（1940 年代的一个人）一直到「AI Agent / Context Engineer」（约 2025 年），以五年为一行、七条彩色家族列排布，实线箭头表示血统，虚线箭头表示影响。其论点包括：编程最初是低地位的文书工作，从 Goldstine 与 von Neumann 1947 年论文中的「planning」分离出来；职位名称不断分裂又重新合并（webmaster → front-end/back-end → full-stack；prompt engineer 几乎刚一出现就被并入 AI engineer）；而「forward deployed engineer」本质上就是 IBM 1960 年代的售前系统工程师，或者换了名字的老式咨询。Miell 承认这些年代只是他自己的最佳猜测，并非有出处的引证，并欢迎向仓库提 PR。

**讨论**: 整个讨论串基本上都同意这些职位名称本身几乎不携带什么信息：一位评论者列出了自己职业生涯中用过的七个带运维色彩的职位，说只有「Cloud Infrastructure Engineer」算是有意义的，并认为大多数组织根本不知道真正的 DevOps 是什么，就算知道，他们也不会去雇一个「DevOps Engineer」。也有人温和地反驳，指出在规模足够大时，确实需要有专人负责工具链；而且开发者可以乐于学习新技能，同时并不想背上运维的 on-call 负担。Agile 和 Scrum 被普遍宣布已死或只剩残余——一位评论者已把相关认证从简历里删掉，把它们比作 1990 年代的 webmaster——而一位数据领域从业者则表示，即便 AI 让需求降温，analyst/engineer/scientist 这些职位依然存在。一个反复出现的实际抱怨是：图本身在页面上没法用（不能缩放），对此有人回复了独立 SVG、托管站点以及 ctrl+滚轮 的提示。还有人指出遗漏：operations/incident/problem manager 和「member of technical staff」都没有出现；一位评论者认为「编程只是文书那部分」这种说法，是在讨好做规划的人。

**值得一读的评论**
- [mikepurvis](https://news.ycombinator.com/item?id=50500081): 一位做了十年「robot devops」的从业者解释了为什么这件事格外难：机器人车队运维、面向开发者的仿真/测试硬件工具链、以及已部署单元的现场支持，是三门不同的学科，还要面对无法虚拟化的硬件「雪花服务器」，而且没有粗壮的数据管道。
- [stroebs](https://news.ycombinator.com/item?id=50499468): 列出了自己用过的七个基础设施类职位（从 DevOps Engineer 到 SRE Lead），并认为除了 Cloud Infrastructure Engineer 之外，其余都只是对一个被托付 AWS root 账号的通才的、毫无意义的委婉说法。
- [kristianc](https://news.ycombinator.com/item?id=50499710): 一句犀利的短评：所谓 1947 年编程只是文书部分、规划才是真正工作的说法，不过是一个恰好能讨好规划者的故事。
