## 1. Ggml v1.0.0 {#story-1}
*HN 第 1 名 · [github.com](https://github.com/ggml-org/ggml/releases/tag/v1.0.0) · 205 分 · 33 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50493062)*

这是 ggml-org 在 GitHub 上发布的 ggml v1.0.0 release notes（发布页部分内容加载失败，但变更日志可读），该库是 llama.cpp 以及一大批本地推理工具底层的 C 张量/算子库。它清理了废弃的公共 API，移除了旧的 DIAG_MASK_INF/DIAG_MASK_ZERO 算子，把 RPC 协议升到 v9（加载更快，并能在连接不可达或握手失败时优雅退出），新增 OCP FP8 与 FP8 KV-cache 支持、可配置的 YaRN truncation，并在后端做了大量优化：CUDA/Metal 的少行量化 matmul 与 MoE 融合、Vulkan 的 Intel prefill FlashAttention、SYCL 设备端 MoE 调度器、OpenCL 上 Adreno 的分解式 FlashAttention、新的 WebGPU kernel、Hexagon/Qualcomm 覆盖，以及 ARM NEON 4x4 simd_gemm 与 SpacemiT RVV kernel。变更条目几乎逐条引用 llama.cpp 的 PR 编号。

**讨论**: 讨论以赞赏为主：多位长期用户说每次月度升级通常能白捡 5%–10% 的速度提升，并称 ggml/llama.cpp 是「AI 界的 Linux」，在只能跑 Vulkan 的老 AMD 卡和 RISC-V 上都可用。也有人泼冷水，说针对特定硬件手写 kernel 的专用推理引擎会快得多，但若不打算逐个评估引擎，llama.cpp 依然是最稳的通用选择。话题随后偏离到 ggml.ai 官网的极简设计上，一方嫌它毫无设计感、连项目做什么都不说，另一方认为极简正是其哲学、比又一个「Claude 味」的落地页清爽得多。还有人调侃「以自己名字命名库」（GG 即 Georgi Gerganov），评论区搬出 Linux、djgpp、MZ 文件头等先例；另有一条指控把 CLI 到 server 的 HTTP 路由说成「遥测/监视用户」，基本无人接茬。

**值得一读的评论**
- [jacquesm](https://news.ycombinator.com/item?id=50494080): 实测一次月度升级：5 万 token 的提示跑完从 4:22 降到 3:59，prefill 是主要受益部分。
- [dust42](https://news.ycombinator.com/item?id=50494982): 给出反面视角——针对自己硬件定制 kernel 的专用推理引擎要快得多，llama.cpp 的价值在于「一个引擎通吃且稳定」。
- [nvme0n1p1](https://news.ycombinator.com/item?id=50494518): 引述项目「保持代码库尽可能小和简单」的原则，认为官网的极简风格正是这种哲学的延伸，难得地让人耳目一新。

## 3. 不占用单元格的终端边框 {#story-3}
*HN 第 3 名 · [joshka.net](https://www.joshka.net/cell-borders/) · 213 分 · 88 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50491423)*
*原标题: Terminal borders that don't cost a cell*

Josh McKinney（joshka）是 Ratatui 的维护者，他提出了一种终端协议：在单元格的边缘绘制细线，而不是使用 Unicode 制表符字形，这样窗格、标签页标签、带下划线的文本输入框和图表网格线就不再需要占用一行或一列。边框成为一种逐单元格属性（最多十二条线段，每条线段各自带有颜色、宽度和样式），通过单一的 DCS 命令命名空间传递，并配合能力查询和 DA1，使应用在不支持的终端上回退到制表符。他已经把它做成了一个约 1,650 行的 Ghostty 补丁（用 Zig 0.17 构建，目前仅支持 macOS），外加一个 Ratatui 演示分支；每个单元格使用一个 16 位边框 ID，存放在已有的 padding 中，指向一个共享的边框集表，每个边框集约 100 字节，如果全部 65,535 个 ID 都被使用，最坏情况约为 10-25 MB。他列举了先例，包括 DECterm 的 ruled lines、SGR 51-65、Win32 控制台的网格标志和 IBM 3270 的字段轮廓，并指出它们都没有提供逐边的颜色和宽度。

**讨论**: 被提及最多的替代方案是 overstrike 模式（DECSET 20），让应用在已有的文本单元格上绘制边框字形；评论者指出 mintty 基本上是唯一支持它的模拟器，而作者回应说 overstrike 无法给出圆角且内部正确填充的边框，也无法给出逐边着色的线条。随后围绕野心爆发了一场更大的争论：一位知名评论者问道，既然你同时要改协议和终端，为什么不干脆构建一个专为界面而设计的、信息密集的完整 UI 框架；其他人则反驳说，终端的约束正是人们使用 TUI 的原因，而扩展协议的高成本恰恰是让廉价的多实现保持可行的原因。tmux 是最大的技术反对意见，一位评论者坚持认为逐单元格属性应该像其他 CSI 序列一样穿过复用器；作者回答说 tmux 会丢弃未知的 DCS，真正的支持意味着要存储并重绘额外的逐单元格状态，可能需要一千行代码，而不支持该特性的复用器应该自己回答 DA1，让应用回退。一位前 Alacritty 维护者说，他很可能宁愿禁用这个特性，也不愿发布一个在不同终端上渲染效果不同的 UI；作者强调 Ratatui 那部分工作只是一个孤立的可行性验证，绝不会作为默认功能发布，他预计 Ghostty、Rio 和 Kitty 会采用，但 Terminal.app 永远不会，还开玩笑说他主要想要的是这项能力，而不是这个具体的规范。少数读者干脆更喜欢回退版本的截图，说原生边框去掉了他们喜欢的留白；还有一位提出 CJK 用户的 Unicode 宽度问题，并询问边框是附着于单元格还是字素簇（grapheme cluster）。

**值得一读的评论**
- [favori995749721](https://news.ycombinator.com/item?id=50493340): 指出制表符字符属于东亚「Ambiguous」宽度，因此在配置为 CJK 的终端里边框本来就已错位；并要求规范明确定义：考虑到续接单元格和 ZWJ emoji，边框是附着于单元格还是字素簇。
- [joshka](https://news.ycombinator.com/item?id=50492475): 直接回应 tmux 的反对意见：tmux 会丢弃它不认识的 DCS 序列，而完整支持意味着要在所有边界情况下跟踪、渲染并重绘逐单元格的边框状态。
- [nixpulvis](https://news.ycombinator.com/item?id=50494092): 一位前 Alacritty 维护者预测在那里采用这项特性会阻力重重，并解释了原因：作为应用作者，他宁愿禁用它，也不愿接受各终端之间渲染不一致。

## 4. FAA 发布全国性地面停飞令 —— 4.5 小时后解除 {#story-4}
*HN 第 4 名 · [nbcnews.com](https://www.nbcnews.com/news/us-news/faa-orders-nationwide-ground-stop-departing-flights-reasons-safety-rcna609247) · 1,506 分 · 1,154 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50489641)*
*原标题: FAA issues national ground stop – lifted 4.5 hours later*

NBC News 报道了 FAA 对全部离港航班实施的全国性停飞：该命令于 2026 年 11 月 13 日周五美东时间下午 3:54 发布，并于美东时间晚上 8:15 解除；此前已有超过 7,000 个航班被取消，Reagan National 和 O'Hare 机场的登机口空间也已用尽。交通部长 Sean Duffy 表示，这套已有数十年历史的空中交通管制系统中的路由器「被数据压垮」，导致航路中心和 TRACON 的雷达与通信数据出现不稳定；DHS 的 Markwayne Mullin 表示没有证据表明存在网络攻击。Duffy 借此事推动为 ATC 全面改造争取 500 亿美元，而国会此前批准的五年拨款为 125 亿美元；文章还指出，这只是 9/11 以来第三次全国性停飞（另外两次分别是 2001 年和 2023 年 1 月的 NOTAM 故障）。

**讨论**: 讨论帖先是被早期猜测主导，随后有评论者贴出报道，指出是 L3Harris 运营的私人通信网络的一次软件更新导致系统重启并崩溃，讨论由此变得尖锐。几位工程师抓住时间点——周五、大约下午 3 点——认为这是生产环境部署搞砸的证据；一位评论者引用 Mullin 的话说新设备「正在压垮旧系统」，其他人则指出 Duffy 在新闻发布会上一直在指责国会、要钱，而不是解释故障原因。另一种说法把矛头指向 FAA 新近扩展的 AI 工具 SMART，它来自承包商 Air Space Intelligence（合同金额最高 875.9 百万美元，几天前刚部署到全部 22 个中心）；不过评论者指出 FAA 和 ASI 都声明 SMART 只负责建议航路，与出故障的设备「完全无关」。懂航空的评论者则在给恐慌降温：有人贴出 2009 年 DOT 监察长关于 FTI 网络中断的报告，另一个人描述 2004 年美国西南部 ATC 雷达/无线电故障时自己正在空中，还有人主张这套 40 年历史的老系统久经考验，真正出问题的恰恰是升级。关于根本原因并无共识，但主流看法是粗心的升级而非攻击；同时有一小撮声音很大的人在传播阴谋论，把它与前一天的 Microsoft 故障、NOAA 雷达故障以及 13 号星期五联系起来。零散有评论者贴出实时航班追踪观察，以及停飞解除时 ATCSCC 通告的实际文本。

**值得一读的评论**
- [fooey](https://news.ycombinator.com/item?id=50491855): 引用《华尔街日报》和 CBS 的报道：故障出在 L3Harris 运营的、承载管制员无线电频率的电信网络上，一次更新导致系统重启并崩溃——这是帖中最具体的成因说法。
- [amluto](https://news.ycombinator.com/item?id=50490420): 一位乘客的第一手叙述：2004 年 9 月美国西南部 ATC 故障时他正在飞行；细节是这次失败属于应用错误，而非著名的 Windows GetTickCount() 溢出。
- [hysan](https://news.ycombinator.com/item?id=50492744): 一位滞留者的实时反应：白宫新闻发布会晚了十分钟才开始，前十五分钟都在指责国会，而不是给旅客提供可据以行动的更新信息。

## 19. 骗过 Zed，让它的远程服务器在 FreeBSD 上跑起来 {#story-19}
*HN 第 39 名 · [hayzam.com](https://hayzam.com/blog/03-lying-to-zeds-remote-editor/) · 24 分 · 5 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50491295)*
*原标题: Lying to Zed to get its remote server running on FreeBSD*

一位 FreeBSD 开发者记录了他如何让 Zed 的远程编辑功能连上一台 FreeBSD 主机：先安装 linux_base-rl9，然后在 ~/.local/bin 里放一个假的 uname 包装脚本，让它回答「Linux x86_64」，这样 Zed 就会把它的 Linux 服务器下载到 ~/.zed_server/ 里。随后连接虽然建立起来了，项目树却是空的，原因是一个 FreeBSD Linuxulator 的回归问题：2026 年 2 月为修复 NFS 的伪 dirent（110f2567cb51，PR 292282）而做的改动，使 linux_getdents/linux_getdents64 把请求的缓冲区向上取整到 512 字节的块，于是 Zed 使用的 768 字节缓冲区会让原生批量请求超出它，转换在 kern_getdirentries 已经推进了目录偏移之后返回 EINVAL——在较安静的情况下，这悄无声息地丢掉了 1,002 个文件中的 112 个。他的修复 ec6629628cb（评审编号 D60760）已经进入 main、stable/15 和 releng/15.2，所以 15.2-RELEASE 会带上它。

**讨论**: 这个帖子很短，而且以赞赏为主。一位评论者认为整个折腾完全没必要，说纯 ssh 就能正常做远程编辑，不需要什么专门的服务器二进制文件，性能上的收益不值得为此做这些配置。另一位问他为什么不能干脆把远程服务器编译到 FreeBSD 上，还指出了 Zed 自己的 FreeBSD 开发文档，随后又编辑自己的评论承认它「doesn't really build on freebsd」。这段对话引出了唯一一段真正的跑题：有人对文章中括号里提到音频通话在 FreeBSD 上无法工作感到意外，解释是这属于 Zed 在转型 AI 之前专注于人与人协作时期留下的东西，还有一位评论者说自己完全不知道 Zed 竟然有音频通话和屏幕共享。技术内容上没有分歧；剩下的一条评论只是开玩笑说「using VS Code since I was 16」让人觉得自己老了。

**值得一读的评论**
- [eddythompson80](https://news.ycombinator.com/item?id=50492384): 询问是否只需要一个 FreeBSD 构建，贴出 Zed 的 FreeBSD 开发文档，然后更正自己：它其实在 FreeBSD 上构建不起来。
- [disposedtrolley](https://news.ycombinator.com/item?id=50492531): 解释了 Zed 为什么会有音频通话：它在转向 AI 之前，本来就是一个人与人协作的工具。
- [kodoman](https://news.ycombinator.com/item?id=50493796): 反方观点：纯 ssh 远程编辑已经能满足大部分需求，为此专门弄一个服务器并不值得，性能上也划不来。
