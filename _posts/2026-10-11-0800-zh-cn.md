## 1. 构建你自己的决策模型 {#story-1}
*HN 第 1 名 · [nishtahir.com](https://nishtahir.com/build-your-own-decision-model/) · 230 分 · 57 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50037949)*
*原标题: Build your own decision model*

Nish Tahir 的博客文章讲解了如何把一个现成的 LLM 变成单次前向的「系统一」决策模型：运行 Qwen/Qwen3-1.7B，将词表掩码到仅保留选项 A–E 对应的 token id，并只在这些 token 上对 softmax 取 argmax，而不是一个 token 一个 token 地生成文本（在他的示例中用了 11 次前向）。他在 CommonsenseQA 的随机留出集上对 1.7B 模型做了基准测试，通过一次快速微调获得了小幅提升，随后指出该模型校准严重失准——在 0.9–1.0 置信度区间内正确率约 70%，而在 0.8–0.9 区间内只有约 40%——并用拟合于 T≈3.797 的温度缩放（temperature scaling）修正了这一问题。配套的 GitHub 仓库完整覆盖了数据集构建、评估、微调与校准。

**讨论**: 讨论串中很大一部分在争论术语：mastazi、make3 以及一位 MLE（「howunfortunate」）指出「决策模型」其实就是零样本分类器，而 Laya 不过是一个微调过的 ModernBERT；另一些人则反驳说差异是真实存在的——灵活/开放式的标签集合、文本与图像输入，以及一个用起来像 switch 语句而非聊天调用的 API。多位评论者对架构层面的说法提出质疑，2bitencryption 和 kombinatori 指出 token 掩码不过是一种受限生成，它给计算量设了上限（因而也限制了准确率），并追问 Jev 是否做了本质上不同的东西。实践者报告了具体的收益：Jev 用于 Claude Code hooks 中标记危险命令、对研究论文的章节进行分类，以及一个测验游戏流水线用它预筛文本块，把 LLM token 用量削减了大约 10 倍；一位 Jeffy 作者补充说，一旦分类任务确定下来，在 CPU 上本地训练的小型分类器（banking77 上 94%+，用 50–100 个样本训练的邮件分类器 F1 达 95%）通常能打败通用决策模型。围绕校准问题存在尖锐分歧——demibabs 称事后温度缩放「有点像 p-hacking」，JMKH42 耸耸肩说「行就行」，shawntan 则长篇论证：任何针对所报告测试集去调优系统组件的行为都是过拟合，并质疑 Jev 的校准主张究竟是什么意思。支线讨论涉及速度（一位评论者声称浏览器端决策模型能在 200ms 以内完成，另一位则说 Qwen 1.7B 本来就该有这么快）以及一个 iOS Safari 重载 bug，有回复将其追溯到浏览器约 400MB 的内存上限。

**值得一读的评论**
- [shawntan](https://news.ycombinator.com/item?id=50040410): 一段详细的论证，认为针对测试集调优校准就是过拟合，援引了老派的训练/验证/测试划分纪律——「Jev 究竟凭什么能声称自己的概率是校准过的，我实在想不通。校准到哪儿了？」
- [howunfortunate](https://news.ycombinator.com/item?id=50038233): 一位多年来一直推销分类器的 MLE 认为，普通 LLM 早就已经是廉价、够用的零样本分类器，所以 Jev 的热度主要来自易用性和时机，而非什么新东西。
- [xavortm](https://news.ycombinator.com/item?id=50040366): 第一手使用体验：一位测验游戏开发者用 Jev 对文本块能否构成问题进行分类，只把预筛过的内容升级处理，从而把 LLM token 用量至少削减了 10 倍。

## 2. 2D Vehicles {#story-2}
*HN 第 2 名 · [patkerr.co.uk](https://patkerr.co.uk/2d-vehicles/) · 435 分 · 94 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49991852)*

这是 Pat Kerr 的博文与可玩 demo：1996 年 8 月的一个周末，他在 Atari ST 上用 GFA BASIC 写了一个 2D 刚体物理演示（后来移植到 C），成为《Grand Theft Auto》车辆系统的雏形。为纪念 30 周年，他把这个原型用 JavaScript 重制成「remastered」版本，浏览器里可直接玩，并提供 Car、Ship（致敬 1986 年游戏 Thrust）和 Brick 三种模式，以及碰撞墙（B 键）、重力（G 键）、相机死区和速度变焦（Z/X）等开关。技术核心是一套标准 2D 刚体动力学（含力矩），叠加一层刻意近似的轮胎模型——轮胎在自身朝向方向阻力很小、侧向阻力很大，作者承认这更像粘性阻尼而非真实摩擦，是为了「好玩」而做的有意 hack。

**讨论**: 讨论分成两条主线。第一条是对文章「AI 味」的质疑：不少人（如 tsukikage、carlos256、m00x、frou_dh）指认图表和部分文字是机器生成，whateveracct 称 Pangram 判定前半人类、后半生成式 AI。作者 Pat Kerr 本人下场回应，坦承图表确实由 AI 依据代码生成、只有串联文字是机器写的，正文与代码还原的是 30 年前手工原型的逻辑，并自嘲是「ChatGPT 轻度协助的 PatSlop」；也有人（fxtentacle、forrestthewoods）力挺，认为其中有真正的架构洞见，值得鼓励更多人分享作品。第二条是技术与怀旧讨论：zeroq、Hydraulix989、tonyarkles 补上 Marco Monster 2003 的 Car Physics 和 Brian Beckman 的 The Physics of Racing 等经典资料；许多人对 GTA 1/2 的俯视驾驶手感和电台念念不忘，认为 3D 化后反而失去了那种感觉。也有玩家实测反馈：撞墙判定、开车后切到 Brick 不会减速等细节被作者确认为有意为之。

**值得一读的评论**
- [PatKerr](https://news.ycombinator.com/item?id=50037891): 作者本人承认图表是机器生成、只有串联文字手写，澄清了整篇文章的 AI 使用范围。
- [baw-bag](https://news.ycombinator.com/item?id=50037988): 一位开发者描述多年未能解决的实操难题：低速倒车入库时车辆会朝轮胎方向侧向滑动，并提到 Multibody Systems Approach to Vehicle Dynamics 一书。
- [Hydraulix989](https://news.ycombinator.com/item?id=50037241): 补充了 Brian Beckman 的 The Physics of Racing Series 这一经典车辆物理资料。

## 4. 站会中的 AI agent {#story-4}
*HN 第 4 名 · [atoll92.github.io](https://atoll92.github.io/agent-standup/) · 29 分 · 31 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50039630)*
*原标题: AI agents in a stand-up call*

链接的页面是 Agent Standup 的落地页，这是一个玩具性质的开发项目，把一次 Claude Code 会话变成一场实时的团队会议：一个 lead agent 发号施令，sub-agent 加入、「共享屏幕」并回报，还配有上下文计量表、token 计数、回放/回顾/树状视图、语音、自定义角色和 8 种语言。它以 macOS 应用（Apple Silicon 和 Intel，未签名）、VS Code 面板和侧边栏的形式发布，也可以从命令行启动；它要求这台机器上至少运行过一次 Claude Code，并且它不是原生插件。作者坦承它「主要是为了好玩」，是「由一个无聊的开发者和他的一群机器人做的」，不过又称它「莫名地有用」。

**讨论**: 这个讨论串分成两派：一派觉得这个梗很讨喜，另一派则质疑整个前提是否讲得通。最有分量的批评认为，站会的存在是为了修复人类信息流动的瓶颈——agent 随时都能拉取自己需要的任何上下文，所以定期同步没有必要，人们应该直接写一个 harness，让一个 manager agent 持续读取 sub-agent 的文件并纠正它们的方向。另一些人则为这样一种想法辩护：agent 确实会卡住或陷入循环，并且持有各自分歧的上下文，所以定期同步（也许是每 1M 个 token 一次，而不是每天一次）可以帮助它们互相帮助。一个反复出现的务实反驳是：agent 交付的代码仍然需要审查——一位评论者说 agent 的产出中有 25–30% 需要修复，另一位在发现计划中存在细微的误解之后，不再委派未经审查的代码，还有第三位则兴致勃勃地报告说，自己运营着由 5–10 个角色明确的 agent 组成的常驻办公室，代码质量比以往任何时候都好。少数人直接将其斥为噱头或泡沫时代的滑稽表演，但也有少数人指出，工具生态在五年间发生了多大的变化。

**值得一读的评论**
- [Olscore](https://news.ycombinator.com/item?id=50040211): 一位使用开源的 Pullboard 工作流开发正确性至关重要软件的评论者认为，agent 写代码比大多数人更好，但看不到改动会如何在代码库中产生连锁影响，所以真正的工作在于流程——测试驱动开发，外加一个对抗性的「证明给我看」审查环节。
- [necovek](https://news.ycombinator.com/item?id=50040461): 对该概念最有力的辩护：站会之所以存在，是因为孤立工作的人意识不到自己卡住了，而 agent 也会卡住或陷入循环，因此一种按 token 预算而非按天数来调整的同步节奏，可能真的会带来回报。
- [Olscore](https://news.ycombinator.com/item?id=50040281): 一个来自实践的具体数字：agent 交付的东西大约有 25–30% 需要修复。

## 5. 灯泡计算机 {#story-5}
*HN 第 6 名 · [lightbulbcomputer.com](https://lightbulbcomputer.com/) · 360 分 · 58 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50029487)*
*原标题: The Lightbulb Computer*

Guillaume Ardaud（Héliographe）的一个设计原型项目。他曾是驻东京的 Apple 原型设计师，提出了「Lightbulb Computer」构想：一个形似大灯泡的投影仪加计算机视觉模块，可拧入 Edison 灯座或便携灯具底座。演示（厨房菜谱叠加、读一页纸问答、共享地图、智能家居指点、家庭氛围信息板）在一台 Mac 上运行，配有定制的投影映射软件、一台约 1100 ISO 流明的小型消费级 4K 激光投影仪和一个普通网络摄像头；Ardaud 表示视频都是真实拍摄，没有任何 AI 生成，并将这一概念定位为智能眼镜/头显的替代方案。
