## 1. 为什么业界没有对 DeepSeek 4.1 Flash 感到惊慌？ {#story-1}
*HN 第 1 名 · [dgt.is](https://www.dgt.is/blog/2026-10-07-deepseek-freek-out/) · 611 分 · 480 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50000488)*
*原标题: Why isn't the industry freaking out about DeepSeek 4.1 Flash?*

一篇由开发者撰写的博客文章，他在一个月内于十几个项目中大量使用 DeepSeek 4.1 Flash。核心论点是：该模型在日常工作中实际上已达前沿水平——作者表示，在会话进行到一半时，他无法分辨自己用的是 DeepSeek 还是 Opus——而成本却低了好几个数量级，这得益于比 DeepSeek V1 小约 437 倍的 KV 缓存，以及每月 10 美元的 OpenCode Go 订阅，使使用几乎不受限制（小任务只需 0.003 美元而非 1 美元，单个会话很少超过 1 美元）。作者认为，各大实验室理应感到惊慌，因为中国的蒸馏模型已足以胜任无人值守的复杂工作，而如今对大多数任务而言，追逐前沿已显得愚蠢。

**讨论**: 讨论线程分歧鲜明。主流反驳观点认为，没人感到有迫切需要换用，因为 OpenAI 和 Anthropic 的订阅补贴力度极大，20–200 美元的计划已经优于开放模型的 API 价格；几位评论者指出，他们几天就能烧掉 50 美元的 API token，而订阅却覆盖了远远更多的用量。第二个阵营坚称文章夸大了该模型：批评者说，与 Luna、Haiku 5.5 和 GPT-6.1 Sol 相比，DeepSeek 4.1 Flash 不在成本/智能的帕累托前沿上，它是一个「幻觉工厂」，而且「像被提拔成 CEO 的实习生一样过度思考」，并且与 Opus 5.5 的真实差距是 6–12 个月，而非作者所称的「一两个月」。支持者则用第一手数据反驳：一位用户报告说，他全天把它当作编排器运行、由 Opus 做最终审查，每天花费 1–2 美元；另一位说 30 天用了 400 亿 token 和约 800 美元；还有几位描述在 Pi/OpenCode 框架中把它当作主代理使用，速度为 250–350 tok/s。几个值得注意的子话题纠正了文章自身的数字——评论者指出该模型出厂即预量化为原生 NVFP4/MXFP8，约 200GB 的 n-gram 表存放在主机内存中，而且它大约能在 300GB 显存上运行，而非某位评论者引用的 1.6TB FP16 数字。一个反复出现的支线辩论涉及供应商（OpenRouter 被指相比直接从 DeepSeek 购买最高多收 100 倍的费用）以及将工作发送到中国托管的模型所带来的数据/隐私风险。

**值得一读的评论**
- [wren6991](https://news.ycombinator.com/item?id=50012676): 对模型的内存占用做了实际计算：LM 主干为 307.2 GB（286.1 GiB），203.1 GB 的 n-gram 表放在主机内存中，因此「FP16 需要 1,664 GB」的说法是错的，而且发布版本根本不存在全精度/INT8 版本。
- [user43928](https://news.ycombinator.com/item?id=50012504): 对文章前提的有力反驳：认为开放模型落后 6–12 个月，至今仍无法超越 2 月的 Mythos/Fable 5，并且如果进展持续，领先的实验室就没什么可担心的。
- [try-working](https://news.ycombinator.com/item?id=50013174): 第一手实践者数据点：30 天内在 DeepSeek API 上用了超过 400 亿 token、花费 800 美元，结论是它能完成大部分工作，但需要分阶段运行、验证和子代理，这点与前沿模型不同。

## 2. Show HN：Quake 被移植到 safe Rust，可在浏览器中游玩 {#story-2}
*HN 第 2 名 · [quake-srp.pages.dev](https://quake-srp.pages.dev/) · 110 分 · 86 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50016312)*
*原标题: Show HN: Quake ported to safe Rust, playable in browser*

链接的页面是 quake-srp（「slop rust port」），这是用 safe Rust 重写的 id Software 1996 年作品 Quake 的浏览器可游玩移植版，通过 WebAssembly 软件渲染，无需 GPU、无任何依赖，并打包了共享软件章节（id 原始的 quake106.zip，9.1 MB）。页面记录了完整的键盘/鼠标/手柄操作、控制台命令、任务包支持（Scourge of Armagon、Dissolution of Eternity），以及放入你自己的 Quake .pak 文件和 CD 音乐的选项，全部存储在浏览器中。该仓库还附带一个「oracle」视觉差异比对工具，将画面与原始游戏逐帧对比，试图像素级复刻原作。

**讨论**: 讨论区在「LLM 辅助的移植是否有价值」上严重分裂：一派认为这对 LLM 来说轻而易举、也毫无意义，因为 Quake 的 C 代码本就扎实，而且 C2Rust 早就存在（一位评论者指出每一次提交都来自 Claude）；另一派则为其辩护，认为这是个有趣的副项目，并指出真正的成就是数十年积累的浏览器/WASM/Rust 基础设施，而非翻译本身。评论者还争论「safe Rust」（仅仅是没有 `unsafe`）究竟意义几何，以及 Rust 的内存安全是否真能消除那些赋予老游戏魅力的怪癖与漏洞利用——对于发布版构建是否检查整数溢出也存在分歧。若干纠正浮出水面：Quake 是用 C 而非 C++ 写的（id 的第一款 C++ 游戏是 2004 年的 Doom 3），而著名的快速平方根倒数出自 Quake 3，而非 Quake 1。一个反复出现的更阴暗的话题担心，同样的技术会让人能以低廉成本克隆/冒充受信任系统（银行后端、Amazon 物流、二维码停车缴费诈骗）。大家普遍认同该移植确实流畅可玩，还有一位评论者指出，代码频率图显示它其实是「human assisted」，尽管打着 LLM 的旗号。

**值得一读的评论**
- [flohofwoe](https://news.ycombinator.com/item?id=50016844): 纠正：Quake 是用 C 而非 C++ 写的——id 的第一款 C++ 游戏是大约 2004 年的 Doom 3。
- [aroman](https://news.ycombinator.com/item?id=50016508): 称赞该仓库附带的「oracle」视觉差异比对工具（附链接），认为正是它让移植能够向原作的像素级一致推进。
- [parasti](https://news.ycombinator.com/item?id=50016723): 第一手反例：该评论者花了五年时间手工将 Neverball 移植到 Web 并附上成果链接，以此说明这些 LLM 移植绕过了哪些工作。

## 3. 减少 C 语言中的未定义行为 {#story-3}
*HN 第 4 名 · [lwn.net](https://lwn.net/Articles/1095811/) · 91 分 · 62 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50015074)*
*原标题: Reducing undefined behavior in the C language*

一篇关于 Kernel Recipes 演讲的整理，讲者是 Martin Uecker，一位为 MRI 扫描仪编写自由软件的生物医学工程教授，他认为 C 仍然值得修补，而非放弃。他梳理了 C89 的抽象机模型及其约 100 种未定义行为如何让编译器为所欲为（包括时间旅行），指出正在制定中的 C2y 草案删除了其中 45 种，而 C23 已经移除了 K&R 函数、三字符组（trigraphs）和符号-数值表示（sign-magnitude）支持，同时新增了位精确整数和带检查的整数运算。他的结论是，完整的内存安全只能通过昂贵的运行时检查或形式化验证实现，而 C2y 将新增 case 范围、具名 for 循环和 _Countof()，但不包括内存安全。

**讨论**: 最大的分歧在于由 UB 驱动的优化是否应当可见：一派希望在因 UB 而折叠分支时给出醒目的编译器警告，另一派（包括一位自称为编译器作者的人）则认为这不可行——UB 通常是运行时条件，因此检查要么拖慢 C，要么用用户无法满足的警告淹没他们。第二条讨论线索中，Fil-C 的作者主张 Fil-C 和 CHERI 在 ABI 层面堵住了内存安全漏洞，比 Rust 更全面；一位评论者反驳说，两者都只为分配附加来源信息（provenance），因此缓冲区溢出仍可能覆写相邻的结构体字段，不过据说 CHERI 支持子对象能力（sub-object capabilities）。有几个人反驳将 C 描述为「高级汇编」的说法，指出真正的高级汇编没有 UB，而 C 之所以有 UB 恰恰是因为激进的优化。评论者还争论有符号整数溢出（将其定义为回绕、捕获它，还是保留为 UB 以维持运行时 sanitizer 的意义），以及 C2y 能否在不破坏每一个实现的前提下，让读取未初始化的 malloc 内存变为已定义行为。

**值得一读的评论**
- [pizlonator](https://news.ycombinator.com/item?id=50016256): Fil-C 的作者主张 Fil-C 和 CHERI 在 ABI 层面攻克内存安全，比 Rust 更全面，因为 Rust 的保证只覆盖真正用安全 Rust 重写的代码。
- [afdbcreid](https://news.ycombinator.com/item?id=50016413): 给出一个 Godbolt 示例：读取未初始化的 malloc 内存，随后用 v<0 || v==0 || v>0 进行守卫，在 Clang -O3 下被编译成一个光秃秃的 exit(1)。
- [strenholme](https://news.ycombinator.com/item?id=50016207): 第一手报告，在 GCC 和 Clang（直至 Clang 23）以及 TCC 上测试了将未初始化的 malloc 内存当作熵源的旧技巧，发现加密例程总是会运行，而不是被优化掉。

## 4. Windows 与 Mac 之间的键盘差异 {#story-4}
*HN 第 5 名 · [unsung.aresluna.org](https://unsung.aresluna.org/deeper-dive-keyboard-differences-between-windows-and-macs/) · 73 分 · 69 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50015515)*
*原标题: Keyboard differences between Windows and Macs*

Marcin Wichary（unsung.aresluna.org）撰写的一篇参考文章，盘点了那些会坑到跨平台 Web 应用的各平台键盘差异。文章指出：Windows 的 Backspace 对应 Mac 的 Delete，Windows 的 Delete 对应 Mac 的 Forward Delete；Windows 的 Enter 对应 Mac 的 Return（macOS 还有一个独立的数字小键盘 ⌤ Enter，可通过 Fn+Return 触发）；Windows 上几乎所有的 Ctrl 快捷键在 Mac 上都会变成 ⌘ Command，并多出一个 ⌥ Option 修饰键。文章还涵盖了 macOS 的 Emacs 风格文本框按键 ⌃A/E/K、⌥ 以及 Windows 的 AltGr/Ctrl+Alt 字符层、符号图例差异（⎋ ⇥ ⌫）、相互冲突的「重做」（⌘⇧Z 对 Ctrl+Y）和「刷新」（⌘R 对 F5）惯例，并提醒 Web 应用避免在文本框中使用 ⌥ / Ctrl+Alt 快捷键，同时要预期某些组合键（⌘Q/⌘W/⌘T）已被浏览器占用。

**讨论**: 这个讨论帖大多把这篇文章当作一份有用的参考，随后扩展成关于哪个平台的方案设计得更好的争论。一个反复出现的说法是，Apple 把 Command 键做对了——一个专用于 GUI 操作的修饰键让以终端为中心的 Ctrl 得以保持自由——而 Windows 把专用的 Home/End/PgUp/PgDn 键做对了；好几位评论者希望同一套系统上两者兼有。从 Linux 桌面转过来的人（spankalee、zdw、wpm）把 Ctrl 的处境形容为所有世界中最糟的，Ctrl-C 视语境不同既表示复制又表示中止，不过其他人反驳说这可以通过重新映射解决，而且 Ctrl-C 在表示复制之前已经表示中断几十年了。与此并行的还有几条分支讨论：文章的模拟键盘、外接键盘上 Command/Alt 的互换（Logitech、Karabiner、macOS 的「修饰键」设置），以及用英国 PC 布局来修复坏掉的反引号键。少数人补充了更正和历史，而 Enter 与 Return 的命名引发了 Apple 内部的小争论：这两个键是否应该是不同的功能。

**值得一读的评论**
- [disillusioned](https://news.ycombinator.com/item?id=50016662): 一位用了 35 年 Windows 的用户描述了转用 Mac 后每天都在经历的肌肉记忆之痛——例如他习惯的 Ctrl+Shift+Left 选词，在 macOS 上是 Shift+Option+Left，他说重新学这个简直是地狱。
- [miki123211](https://news.ycombinator.com/item?id=50016586): 补充技术性更正：在 AltGr 布局上，右侧 Alt 实际上被映射为 Ctrl+Alt；波兰语布局的 shift+反引号是一个死键，会破坏像 cFooManager 这样的 C++ 标识符；应用应该依赖 macOS 的菜单选择器，而不是自己处理复制/粘贴快捷键。
- [m3galinux](https://news.ycombinator.com/item?id=50016276): 一段历史叙述：Ctrl+Del / Ctrl+Ins / Shift+Ins 才是最初的剪切/复制/粘贴，Ctrl+X/C/V 来自 Macintosh，并在 Windows 3.1 时代为对齐 Word for Mac 而被采用，而这与 Ctrl+C 更早的中断含义发生了冲突。

## 5. 男子发现父母的咖啡机 10 天内用了 1TB 流量 {#story-5}
*HN 第 6 名 · [dexerto.com](https://www.dexerto.com/entertainment/man-discovers-his-parents-coffee-machine-used-1tb-of-data-in-10-days-3416399/) · 607 分 · 363 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49995495)*
*原标题: Man discovers his parents' coffee machine used 1TB of data in 10 days*

这是一篇简短的 Dexerto 聚合报道，源自用户 Nomad 在 X 上发布的一条爆火帖子。Nomad 远程帮忙管理父母的家庭网络，在 UniFi 仪表盘上发现他们的智能 Keurig 咖啡机在 10 天内跑了大约 1TB 的流量。Nomad 自称从事 IT 工作超过 10 年，他澄清其中几乎全部流量都留在本地网络内，并没有流向互联网，但它占满了他的接入点，他怀疑是那台特定设备有 bug；他的结论是，当 IoT 设备会这样行为异常时，不值得让它一直联网。这篇文章几乎没有补充技术细节，原始证据只是一张 UniFi 客户端流量的截图。

## 17. DuckDB Ducklake {#story-17}
*HN 第 19 名 · [github.com](https://github.com/duckdb/ducklake) · 164 分 · 21 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49996149)*

链接的页面是 DuckLake 的 GitHub 仓库/README。DuckLake 是 DuckDB 团队推出的开放 lakehouse 表格式，构建在 SQL 和 Parquet 之上：元数据存放在 catalog 数据库中，而实际数据则存放在 Parquet 文件里。一个 DuckDB 扩展让 DuckDB 能够挂载（attach）DuckLake 数据库，并用标准 SQL 创建、查询、更新表以及对表进行时间旅行（例如 ATTACH 'ducklake:metadata.ducklake' ... 和 FROM table AT (VERSION => 2)）。它支持将 Postgres、SQLite 和 DuckDB 作为 catalog 存储，目前正在 main 分支上针对一个固定版本的 DuckDB 进行开发。

**讨论**: 这个讨论串中最有价值的纠正是：DuckLake 并不需要 DuckDB——多位评论者强调它只是一个格式/规范，并指向一个 Rust/DataFusion 实现（datafusion-ducklake）。其作者 eddietejeda 表示，他的团队放弃了自研 catalog，因为「仅作为规范的 DuckLake」性能与他们自己定制的工作相当：他们用 Postgres 作为 catalog 存储来承载事务性数据，在高并发下仍能达到亚秒级延迟，他还称赞该规范对时间旅行和快照的支持。其他人则纠正了「catalog 总是 DuckDB 文件或 Postgres」这一假设——网站的标签页界面只是默认选中 Postgres，而 SQLite/DuckDB 同样受支持。反复出现的告诫是它尚不成熟：在 v1.5.4 上按 catalog 过滤的计数是坏的，main/v2 的 SQL 解析器慢得多，还有一位评论者指出规范已经到 1.0 但软件还没有，所以你可能需要自己 fork。人们对 DuckDB 普遍赞誉有加（有人链接了它那篇「小数据的失去的十年」文章），也有人抱怨新项目仍然选择 C++ 而不是 Rust。

**值得一读的评论**
- [eddietejeda](https://news.ycombinator.com/item?id=50013044): datafusion-ducklake 的作者解释了为何放弃自研 catalog：作为规范的 DuckLake 性能与他们定制方案相当，同时由 Postgres 处理事务性元数据，而且它为时间旅行、快照等复杂功能提供了清晰的规范。
- [engineeringwoke](https://news.ycombinator.com/item?id=50011781): 一则第一手警告：DuckLake 仍大致处于 alpha 阶段——在 v1.5.4 上按 catalog 过滤的计数是坏的，而迁到 main/v2 带来了慢 10 倍的 SQL 解析器，所以目前可能得自己 fork。
- [Lucasoato](https://news.ycombinator.com/item?id=50013413): 一则澄清性纠正，说明 DuckLake 与 Delta/Iceberg 的区别所在：它的 validity log 直接存储在数据库中，而不是 JSON/Parquet，这更快，但也增加了对数据库的依赖。

## 20. ADHD 作为一种昼夜节律紊乱：证据及对时间疗法的启示（2025） {#story-20}
*HN 第 24 名 · [frontiersin.org](https://www.frontiersin.org/journals/psychiatry/articles/10.3389/fpsyt.2025.1697900/full) · 270 分 · 160 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50011928)*
*原标题: ADHD as a circadian rhythm disorder: evidence and implications for chronotherapy (2025)*

2025 年 12 月发表在 Frontiers in Psychiatry 上的一篇观点文章主张，昼夜节律紊乱是相当一部分 ADHD 人群中普遍且具有临床重要性的表型，而非普遍特征。文章引用：ADHD 成人中高达 80%、儿童中高达 82% 存在失眠；高达 78% 存在睡眠-觉醒时相延迟；DLMO（暗光褪黑素起始）在儿童中约延迟 45 分钟、成人中约延迟 90 分钟；此外还有皮质醇反应迟钝/延迟、松果体体积减小以及 BMAL1/PER2 时钟基因节律减弱。所评述的试验显示：每晚 0.5 mg 褪黑素可使成人 DLMO 提前约 88 分钟，症状减轻 14%；10,000 lux 晨光可使 DLMO 提前约 31 分钟；一项为期 3 周的多模式夜猫子方案使 DLMO 位移约 2 小时，抑郁评分下降约 58%；作者提出一套以行为干预为先的路径：固定起床时间、晨间强光、晚间限制光照，以及选择性地使用低剂量褪黑素。
