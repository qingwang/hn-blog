## 1. Asahi Linux 进展：Linux 7.3 {#story-1}
*HN 第 1 名 · [asahilinux.org](https://asahilinux.org/2026/11/progress-report-7-3/) · 106 分 · 55 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50401867)*
*原标题: Asahi Linux Progress Linux 7.3*

这是 Asahi Linux 团队针对 Linux 7.3 周期的例行进展报告，核心是上游化开始见效：约 3100 行的 macaudio 驱动和约 13000 行的 AVD 驱动已提交上游，音频子系统还连带需要多项 ALSA 核心改动；M4 Pro/Max 与 M5 的初始 Devicetree 也已出现（仅够启动到 TTY）。M3 支持摘掉了 EXPERT 标志并启用 DCP（带来休眠和刘海区域可用），m1n1 现在能在 EL1 下起三个 VM，从而在 M4 和 M5 上虚拟化并逆向带 SPTM/Exclaves 的 macOS。Thunderbolt 补丁终于进了上游和下游内核，但目前只支持 USB3、XDomain 和 Thunderbolt Networking，PCIe 与 DisplayPort 隧道（ docks 必需）还没有；游戏方面借助 Android 的 P3S（Per Process Page Size）补丁可以绕开 muvm 约 20% 的性能损失，跑起 Battlefront、Wolfenstein: The New Order（M2 上 144+ FPS）乃至 Bethesda 的游戏。报告还提到项目因有人滥用 MIT 许可而转向 copyleft。

**讨论**: 线程很快从技术进展转向两场争论。一是 Omarchy：多人指出 Asahi 报告中「有人利用宽松许可劫持成果并变现」一段指的是 Omarchy Mac，有人翻出其 readme 自述为「Asahi + Omarchy」，讽刺「骑在 Asahi 肩上扣篮」；也有人反驳 Omarchy 并未售卖任何东西，其赞助收入与 Asahi 接受捐赠并无本质区别，并把 DigitalOcean 削减 OSS 支持转投 Omarchy 当作「吸血」证据，随即被纠正为 DO 的 OSS  credits 项目本身难以持续。二是许可与 LLM 立场：一派认为既然选了 MIT 就别在别人真用的时候喊「不是这样用」，另一派认为 Asahi 当初选 MIT 是为了吸引 BSD  contributor，改成 copyleft 是迟来的正确决定；也有人担心 Asahi 拒绝 LLM 会在与「vibecoder」团队的竞争中吃亏。此外还有若干实践反馈：有人用 Omarchy 的内核在 Fedora Asahi 上跑通了 Thunderbolt 和 Touch ID，另有一个自称 GravityLinux 的项目宣称已支持 Vulkan 1.4、M4 与大部分 M5、以及 Asahi 尚不支持的 suspend-to-RAM。最少数的声音是质疑「为何非要在 Mac 上装 Linux」，被多人以「MacBook 是最好硬件之一」「旧机器再利用」「这是 Hacker News」反驳。

**值得一读的评论**
- [cornedor](https://news.ycombinator.com/item?id=50402169): 第一手经验：把 Omarchy 的内核编译进 Fedora Asahi 并给 m1n1 打上其补丁后，Thunderbolt 和 Touch ID 都能用，终于省掉了外接 USB hub 和 HDMI 线，并称对方正在推进 M4/M5。
- [favorited](https://news.ycombinator.com/item?id=50402566): 关键纠正：所谓「Omarchy 追上了 Asahi」站不住脚，Omarchy Mac 的 readme 自己写着它是「Asahi + Omarchy」，相当于坐在 Asahi 肩上扣篮。
- [ADevWithAnIdea](https://news.ycombinator.com/item?id=50402197): 另一个自称 GravityLinux 的项目来打广告，声称已有 Vulkan 1.4、M4 全支持和大部分 M5，并在做 Asahi 尚不具备的 suspend-to-RAM——等于是对报告结论的直接挑战。

## 2. Libghostty 1.0 {#story-2}
*HN 第 2 名 · [mitchellh.com](https://mitchellh.com/writing/libghostty-1-0) · 529 分 · 86 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50399933)*

Mitchell Hashimoto 的文章宣布了 libghostty-vt 1.0，这是一个从 Ghostty 核心中提取出来的可移植 C 终端仿真库，现在具备稳定的 C ABI 和语义化版本管理。该 ABI 在设计上支持扩展：不透明句柄、以枚举为键的 getter/setter、带大小标记的结构体、用于未知值的 GHOSTTY_UNSUPPORTED，以及通过 libabigail 实现的 CI 强制检查和带版本号的 ELF 符号。采用情况是文章的重点主张：JetBrains IDE 终端现在运行在它之上（超过 1250 万活跃用户），一个 Neovim PR 用它替换了 libvterm，文中还点名了 Turborepo、devenv、OrbStack、Antithesis、Emacs 的 ghostel 以及一个提供 Xterm.js 兼容 API 的 WASM 构建；该库采用 MIT 许可，仅依赖 libc（不使用 SIMD 时可在无操作系统环境下独立运行），并在一台 4 核/8 GB 的机器上用 10,000 个活跃终端做了压力测试。

**讨论**: 讨论串几乎是一边倒的好评，人们称赞其发布工程质量（tarball、SONAME、pkg-config、CMake 配置、离线依赖打包、没有 copyleft 依赖），还有几位用户表示 Emacs 的 ghostel 和新的 JetBrains 终端相比 vterm/EAT 和 JediTerm 是质的飞跃。一个分支话题调侃 Hashimoto 没有宣传他自己的终端 Rex，随后演变成 beta 用户的证言，说 Rex 已经取代了他们使用的 Ghostty 或 Herdr，同时也有人对 Rex 和 Ghostty 之间的关系感到困惑。反复出现的实际争论是 Ghostty 与 iTerm2 的对比：支持者提到速度、简洁性以及新标签页会在当前目录打开，另一些人则说 iTerm2 仍在 tmux 集成、搜索打磨、配置文件、字体渲染和窗口布局上更胜一筹。有两个较冷清的话题，一个问 Zig 库如何呈现 C API（答案是它就是 Zig，通过 C ABI 暴露），一个问为什么 Windows 仍没有官方 Ghostty（存在 Noctty 和 wintty.io 等社区移植版本），还有一个问这项工作的资金来源（HashiCorp、赞助者、一家初创公司）。一位持异议的实践者报告说，把它用作 Mudlet 的 ANSI 解码器并没有带来可测量的速度提升。

**值得一读的评论**
- [spacechild1](https://news.ycombinator.com/item?id=50402503): 以 libopus 作为 C 库的范本，并解释了带大小前缀的版本化结构体技巧，还附上 ARA API 作为具体示例的链接——直接回答了前面提出的 API 设计问题。
- [VadimPR](https://news.ycombinator.com/item?id=50401419): 第一手负面结果：尝试把 libghostty-vt 1.0 用作 Mudlet 的 ANSI 解码器，没有发现可测量的速度提升，而且它的网格模型（仅支持 UTF-8、滚动缓冲不可变）不适合 MUD 客户端。
- [isomorphic](https://news.ycombinator.com/item?id=50401805): 详细列出了仍让一位用户留在 iTerm2 上的因素：字体渲染和单元格尺寸、带细标题栏标签页的紧凑主题、配置文件、窗口布局以及终端内 API——同时承认 Ghostty 的纯文本配置更好。

## 4. 能向 Opus 求助的 Jev 以四分之一成本达到 Opus 的准确率 {#story-4}
*HN 第 4 名 · [hightouch.com](https://hightouch.com/blog/llm-judges-identity-resolution) · 441 分 · 99 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50397429)*
*原标题: A Jev that can ask Opus for help gives Opus accuracy at 4x lower cost*

Hightouch 工程师 Albert Jin、Neil Desai 和 Delaney Mackenzie 对廉价的“决策模型” Jev 和 GPT-6 Luna 进行了基准测试，让它们承担一项困难任务：审计身份解析中的过度合并（over-merging）。他们使用 IHME 的 pseudopeople 工具生成了 1,000 个合成身份，其中一半是单个人的带噪记录，另一半是过度合并；此外还用更难、更具对抗性的用例进行了测试。Claude Opus 5.5 的准确率为 99.0%，每个身份耗时 2.2 秒，成本为每 1,000 个身份 $3.86；Jev 为 95.7%，成本为 $0.05；Luna 为 97.3%，成本为 $0.10。Jev 的置信度校准得更好，因此只把落在 30%–90% 置信度区间的案例升级给 Opus 处理，准确率就达到 98.8%，成本为每 1,000 个身份 $0.88；相比之下，Luna 的过度自信使相同的混合方法在困难测试集上只得到 91.6%。

**讨论**: 大多数评论者跳过了身份解析的具体细节，转而讨论如何用昂贵模型编排廉价模型；多位工程师描述了自己采用相反方向的配置（例如以 Opus 5.5 作为编排者和规划者，把实现工作交给本地 Qwen3.8-27B 子代理，或使用更便宜的层级，如 GPT-6.1 Sol 和 Muse Spark）。有几个人问，智能体是先大后小还是先小后大，是否有过任何测量依据，还是仅仅出于直觉；也有人提出这取决于任务，并指出 Anthropic 的 /advisor 功能和模型路由是同一思路更简便的版本。最主要的反对意见是有争议的校准结论：一位评论者根据作者自己的图表估算，Luna 的预期校准误差实际上比 Jev 低 2–3%，并认为在总体通过率很高时，高置信度的错误本身并不算问题；还有一位评论者指出，整个结果都锁定在确切的模型版本和参数下。还有评论者提出了伦理层面的异议，认为这项工作让把数据映射到真实人物变得更便宜、更快速，本质上属于 AI 辅助的隐私侵犯；也有人纠正了分类：GPT-6 Luna 是一个小型 LLM，带有一个 “decisions API” 变体，而非原生的决策模型。实际经验大多证实了这种模式：决策模型作为判断器、用于剔除提示词、在并行智能体之间路由，以及在工具调用前拦截；不过也有人报告说，一旦 Haiku 5.5 发布，这种成本优势就消失了。

**值得一读的评论**
- [pcwelder](https://news.ycombinator.com/item?id=50401734): 认为校准分析有误：根据提供的图表估算，Luna 的预期校准误差在两项任务上都比 Jev 低 2–3%，而且高置信度的错误如果通过率也高，本身并不一定有害，并呼吁报告实际的 ECE。
- [netshade](https://news.ycombinator.com/item?id=50399491): 第一手经验：在 Jev+Opus 这样的组合中，只要给 Jev 一份其他模型能力的清单，它在升级时通常能做出正确判断，但在 Haiku 5.5 发布后，这种决策层不再划算，因为 Jev 的毫秒级延迟已被链中其他环节（例如网页浏览）掩盖。
- [ezotony](https://news.ycombinator.com/item?id=50400499): 根据文章中的成本数据推算出隐藏的升级率：困难集大约送给 Opus 处理 53%（在相同阈值下），而简单集约 22%，这对于任何想复用这种混合方法的人都有用。

## 10. 「GROUP BY 这么多年了，还能再优化吗？」 {#story-10}
*HN 第 16 名 · [pivotlake.io](https://pivotlake.io/blog/know-your-limit-faster-top-k-aggregation/) · 76 分 · 9 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50354097)*
*原标题: Can GROUP BY still be optimized after all these years?*

这是 Pivot（pivotlake.io）的工程博客，讲他们在 top-K 聚合查询（例如「订单最多的 10 件商品」）上做的一项新优化。常规分析型 GROUP BY 会按分组键把数据切成很多分区（ClickHouse 用 256 个，Pivot 在这类查询里会用到 4,096 个），并对每个分区都做合并，但最终结果只用到少数分组。他们的做法是给每个分区固定数量的「槽位」，用哈希把分组映射到槽位，并按槽位累计聚合值；只要一个分区里所有槽位的总数都低于当前 TopK 的最小值，就整个跳过这个分区。文中举例说，ClickBench 有 63% 的查询含这种 GROUP BY 加聚合排序的模式，最简单的 Q16 从 35.6 ms 降到 22.2 ms（1.6 倍），执行中剪掉了 70% 以上的分区。

**讨论**: 评论不多，整体偏技术欣赏。有人贴出 ClickBench 上 Pivot 的成绩单，认为结果相当亮眼；另一位读者指出，这套结构其实就是 count-min sketch，用来给能进入 group-by 的元素设上界、从而跳过大量工作。讨论的主要分歧在分布式 GROUP BY 本身是否值得：一位评论者主张单机顺序内存加 NVMe 才是最快的，跨网络传数据比传聚合结果昂贵得多，超大集合就该上大型机；有人反驳说这个优化对 sum、max 等其他聚合同样适用，而另一位从业者详细列举了横向扩展的实际好处——按需增减、分离存储与计算带来更高聚合带宽、单机故障影响小因而能用便宜的 spot 实例、运维和容灾更容易。另有几条评论跑题到 Rust 做数据库的 arena 分配是否顺手，以及 Parquet、对象存储的性能问题，还有人借机吐槽 MySQL 的 GROUP BY 默认行为。

**值得一读的评论**
- [malisper](https://news.ycombinator.com/item?id=50402082): 指出文中的槽位结构本质上是 count-min sketch，用途是给能进入 group-by 的元素设上界并据此剪枝。
- [toddbandrowsky](https://news.ycombinator.com/item?id=50401087): 提出反论点：单机顺序内存读 NVMe 才是最快的 GROUP BY，跨网络搬数据远不如直接传聚合结果划算。

## 18. Show HN：Waymark —— 一个编译任务而非重放的工作流引擎 {#story-18}
*HN 第 28 名 · [github.com](https://github.com/piercefreeman/waymark) · 62 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50379221)*
*原标题: Show HN: Waymark – A workflow engine that compiles jobs instead of replaying*

Waymark 是 Pierce Freeman（icyfox）和 mozgiii 开发的一个 MIT 许可的开源持久化执行（durable execution）库，定位介于 Temporal/DBOS 与普通 Postgres 任务队列之间。它不像重放式方案那样从头重放工作流代码，而是把 Python 工作流的 AST 解析成 IR，再下降到字节码，交给一个无栈虚拟机运行；由 Rust 核心负责执行并快照到 Postgres —— 因此任何能通过编译的代码都能运行，而像 time 或 uuid 这类非确定性调用会在编译期而不是运行期报错。Postgres 是唯一的 broker（基准测试约为每秒 1,500 个工作流），action 通过 FastAPI 风格的依赖注入接入，内置一个跑在 24119 端口的 webapp，以及 cron/间隔调度；作者明确提醒在 1.0.0 之前不要用于生产环境，并表示 SQLite 支持和 JavaScript 是后续的候选方向。

**讨论**: 整个讨论帖基本是赞赏的态度。一位前 Pachyderm 工程师认为真正的洞见在于把 Bazel/Nix 的模式 —— 用一门纯协调语言去编排沙箱化的命令式组件 —— 应用到了分布式工作流上，并说一个由编译器驱动的编排器本可以解决他团队遇到的局部缓存失效问题（作者回复说他自己已经有一个内部的 map-reduce，并询问缓存是在哪里出问题的）。有几个人询问 SQLite 或 .NET CIL 支持；作者表示数据库层本来就是插件式的，很容易替换。唯一真正的争议在于 async：一位评论者称这种重度依赖 async 的 API 令人反感，并预言会因 Python 版本和第三方依赖耦合而出问题；当作者说后台任务更适合用 async 建模时，他反驳说协程跑在单线程上，而线程/进程队列已经用了几十年。其他人则反驳说，在 Temporal、Hatchet 和 Dagster 中，asyncio 已是 IO 密集的分布式工作的惯例，并指出同步代码可以用 asyncio.to_thread 和 aiomultiprocess；作者也指出 action 本身可以是同步的。

**值得一读的评论**
- [msteffen](https://news.ycombinator.com/item?id=50398960): 一位前 Pachyderm 工程师说，Waymark 把 Bazel/Nix 那套「在沙箱化的命令式代码之上加一层纯协调层」的模式用上了，而这种架构本可以解决他团队的流水线缓存难题。
- [icyfox](https://news.ycombinator.com/item?id=50400223): 作者解释了持久化对 agent 为何重要：每次 LLM 调用和工具调用都成为一个检查点，sleep 可以持续数小时，而每次调用都获得干净的输入/输出契约以便追踪。
- [whilenot-dev](https://news.ycombinator.com/item?id=50402289): 一位评论者具体回应了关于同步代码的抱怨 —— 用 asyncio.to_thread，如果想要进程就用 aiomultiprocess —— 并反问同步工作流究竟能换来什么样的底层并发控制能力。

## 20. Show HN：Tmux-restore 可在重启后保留 tmux 窗口与 agent 会话 {#story-20}
*HN 第 30 名 · [github.com](https://github.com/andrewboldi/tmux-restore) · 28 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50355009)*
*原标题: Show HN: Tmux-restore saves tmux windows and agent sessions across reboots*

tmux-restore 是 andrewboldi 开发的一款 MIT 许可工具，它封装在 tmux-resurrect 和 tmux-continuum 两个插件之上：它每分钟保存一次全部 tmux 状态，并在系统关机时再保存一次（Linux 上通过 systemd，macOS 上通过 launchd），恢复时会带回各个会话、窗口、分屏、工作目录和滚动缓冲区。它最大的价值在于让 agent 会话可以接续：一个小型适配器会到 Claude Code、Codex、Gemini CLI、opencode 和 pi 各自的会话文件里找出对应的 conversation id，然后保存一组命令，用相同的命令行参数恢复该对话。出于安全考虑，它只重新启动编辑器和监控程序；部署脚本、dev server 等则被重新输入到提示符处，等待用户按 Enter 确认，不会自动执行。安装方式是通过 curl 执行 install.sh，脚本会自动安装 tmux、TPM 以及所需插件。

**讨论**: 最主要的疑问是，它比原版插件多做了什么：几位评论者已经在跑 tmux-resurrect/tmux-continuum（另一个人甚至为每个面板专门 fork 了 Zed），作者回应说，新增的部分是 agent 会话恢复，以及关机时保存这一层。一位评论者建议提供手动安装操作步骤，而不是只给出 curl | bash 一行命令。有人提出，用带休眠的 VM 是更简单也更完整的方案，但反驳意见指出，VM 仍然会为了升级内核而重启，而且升级库之后无论如何都要重启依赖程序。最实质的提醒是安全性问题：该工具会把屏幕缓冲区持久化到磁盘，因此任何留在某个 pane 里的敏感内容（例如密码）都会被捕获，并且每 10 分钟覆盖一次。

**值得一读的评论**
