## 1. 得了癌症后需要知道的事 {#story-1}
*HN 第 1 名 · [jjmaxwell4.com](https://jjmaxwell4.com/writing/things-to-know-when-you-get-cancer/) · 1,168 分 · 296 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50093568)*
*原标题: Things to know when you get cancer*

这是一篇由 jjmaxwell4 撰写的第一人称文章，他于 2026 年 5 月被诊断出患口腔鳞状细胞癌，文中列出了他迄今为止在治疗过程中总结的实用经验：接到预约取消通知要回电、不要相信那些告诉他「多半没得癌症」的 LLM、在拖延了数月后要极力争取全面的基因检测、亲自阅读 NCCN 标准治疗流程图、去顶尖癌症中心寻求第二诊疗意见并做第二次病理判读，以及查看 Sijbrandij 基金会（GitLab 的 Sid Sijbrandij）的资源。他认为，如果你住在距离大型癌症中心（他以 MD Anderson 为例）2-3 小时车程以内，就应该去那里而不是社区医院，主要原因是在那里几个分钟就能拿到答案，而不是几天。

**讨论**: 整个讨论串几乎一致地认同第二诊疗意见和积极的自我维权，并以许多真实的个人经历为证：一位母亲的诊断从 1 期在 Dana-Farber 第二次判读后变成了 4 期；一例肺癌被误诊为缺铁；一个脑肿瘤直到第三位医生开了 MRI 才被发现；还有一位评论者说，为了发现他朋友母亲的脑肿瘤，前后看了 21 位医生。几位体系内的从业者补充了战术层面的细节：要在治疗方案确定之前去拿第二诊疗意见，因为否则专科医生不会推翻第一位肿瘤医生的方案；另外，比较在不同医院判读的扫描结果时要谨慎。异议来自两个方向——一位患结肠癌的评论者说这份清单很实用，但漏掉了真正重要的事（遗产、葬礼、接受死亡）；另一位则认为第二诊疗意见带来的是虚假的自信，因为诊断手段本身信号很弱，而且所有人都遵循相同的 NCCN 指南。非美国评论者（爱尔兰、北欧、印度）表示整份清单都是美国式的：他们几天内就做了扫描，医疗免费或几乎免费，当天就能见到专科医生，完全不需要追着任何人跑。

**值得一读的评论**
- [jcims](https://news.ycombinator.com/item?id=50096154): 一位妻子患卵巢癌的照护者主张在治疗方案确定之前就去拿第二诊疗意见——否则像 Cleveland Clinic 和 MSK 这样的专科机构会直接拒绝推翻原方案，使这些就诊毫无作用——他还警告说，接受过任何免疫治疗都会让你无法参加之后的大多数免疫治疗试验。
- [jongjong](https://news.ycombinator.com/item?id=50096478): 一位妻子患 3 期癌症的丈夫描述说，他用一个周末搭出了一棵 LLM 辅助的决策树，然后在医生建议对一种对免疫治疗有反应的肿瘤类型做放化疗时提出异议——肿瘤在一个月内缩小了约 50%，他还指出，她与一项著名的 100% 治愈率试验的患者条件完全吻合。
- [tonymet](https://news.ycombinator.com/item?id=50096104): 一个反驳观点认为第二诊疗意见带来的是虚假的自信：诊断手段还很原始、信号很弱，所有中心都遵循同样的 NCCN 治疗指南，患者必须接受一个事实——你永远无法真正知道自己那套花费五十万美元、历时数年的治疗是否必要。

## 2. OpenCode 2.0 {#story-2}
*HN 第 2 名 · [anoma.ly](https://anoma.ly/notes/opencode-2-0/) · 517 分 · 205 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50094994)*

这是 Anomaly（anomalyco，SST/opencode 背后的团队）发布的 OpenCode 2.0 版本说明，宣布了热重载插件（agent 可以在会话中途为自己写一个插件并立刻使用）、按 Effect 重新架构的循环、内置的最小化 JavaScript 解释器，以及会持续存在的 client/server 模型。升级说明中列出了破坏性变更：1.0 插件无法在 2.0 中使用，Server API 完全重做，tui.json 配置迁移到新的 JSON 配置文件；OpenCode Go 订阅被描述为仍在开发中。抓取到的正文本身非常碎片化、几乎无法阅读，多位评论者也抱怨该页面难以阅读（「我希望有一份大的新功能和变更清单」）。

**讨论**: 讨论明显分裂：长期用户报告了真实的改进——技能和插件终于能自动重载、任务可以放到后台运行、子会话可以用自己选择的模型开启、配置从创建会话的目录而不是启动服务器的目录加载——而像 verdverm 这样的其他人则表示他们已经永久切换到了 Pi，理由是他们不喜欢 v2 的 UX 方向、担心安全姿态，以及对 CEO 的社交媒体行为不满。最主要的实质性抱怨是安全问题：不止一位评论者报告说他们用来包裹 TUI 的沙箱静默失效了，因为工具调用现在会通过常驻后台服务器进程路由（必须传入 --standalone 才行），verdverm 统计了三个回归问题，包括热重载插件以及插件添加的工具会忽略权限配置。有一个大阵营抱怨资源占用（启动时占用 2GB 内存、文件监视爆炸、风扇狂转），另一个阵营则吐槽该网站，说它会卡死笔记本和手机，很多人直到有人指出才意识到页面需要滚动。在定价方面，多个帖子称 OpenCode Go「$10/mo，$40 Go Plus」令人困惑，一位评论者用详细的数学计算解释了 $10 订阅如何在 DeepSeek 4.1 Flash 上获得 $80 的额度，而另一位则声称自己在模型定价上被多收了最多 2 倍的费用，在 Discord 上被敷衍后便被无视。一个反复出现的元主题是 OpenCode 是否拥有「最好的」轴：有人认为它的非 TUI 网页/桌面客户端是其最强的区分点，但也有人警告这是一个很浅的护城河。

**值得一读的评论**
- [ghrl](https://news.ycombinator.com/item?id=50099588): 称赞 OpenCode 的 GitHub issue 跟踪流程：连接的 GitHub App 会读取 bug 报告，在报告版本和最新 dev 分支上复现，并在一两分钟内用复现脚本回复（TUI bug 还会附上录屏），同时指出 opentunnel.xyz 提供持久化的个人子域名和本地生成的通配符证书。
- [kingds](https://news.ycombinator.com/item?id=50095629): 警告了一个安全方面的意外：由于所有工具调用现在都会经过后台进程，用于包裹 TUI 的沙箱静默地变成了无用之物，本该被阻止的网页抓取却能通过——使用者需要花一两天才会注意到。
- [sieve](https://news.ycombinator.com/item?id=50099377): 用 multipliers 机制拆解了被普遍批评为不透明的 OpenCode Go 定价：你支付 $10，获得按 1.5x–8x 倍率计算的使用额度，因此更便宜的开源模型能提供更多额度（DeepSeek 4.1 Flash 为 $80/月，Kimi K3 为 $15/月），并有 5 小时 25%、每周 50%、每月 100% 的滚动上限。

## 3. Tiny Little Office {#story-3}
*HN 第 3 名 · [tinylittleoffice.com](https://tinylittleoffice.com/) · 324 分 · 46 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50096142)*

Tiny Little Office（tinylittleoffice.com，324 分）是一款基于浏览器的办公套件——包含文字处理器、电子表格、演示文稿、动画工具和一个行程规划器——它的噱头在于整个文档都被序列化进链接本身，因此一个分享出去的 URL 就是文件本身。该网站的落地页几乎没有向抓取器返回可读文本（依赖 JavaScript），所以这里的细节来自标题、HN 帖子以及评论者的描述。一位评论者指向了联合创始人在 aboard.com 上写的文章，文中说这个想法可以追溯到六年前，而这些网站的早期版本已从网上消失，其链接也随之失效。

*未能读取原文：page had almost no readable text (probably needs JavaScript or a login)*

**讨论**: 评论者大多赞赏其实现（「absolutely lovely」「so well done」），并立刻把它和前辈们对应起来：能自我保存的 TiddlyWiki、bento.page 那种把编辑器和内容一起嵌进单个 HTML 文件的演示文稿编辑器、nathanvy 用于文档的 singlebook，以及一位用户在 hashpage.dev 上做的语义 HTML 改版。最一致的反对意见是：没有办法打开已有的文档——不能导入 .csv、.txt 或 .ics——有几个人说这对电子表格来说是真正的拦路虎，因为电子表格很少从零开始做。第二个更结构性的抱怨：把文档放在 URL 里，会把它的体积限制在 Chrome 约 2048 KiB、Firefox 约 64 KiB，因此对稍微大一点的东西来说，「easy to share」就站不住脚了。一位评论者报告该网站的 OpenStreetMap 瓦片返回 403，其他人回复说 OSM 的瓦片并非面向终端用户应用，应改用 Mapbox 或自托管瓦片。除了一些小 bug 报告（切换输入方式时文字处理器中的光标位置、深色模式下演示文稿预览里的黑字配深底），人们还要求实时协作、PDF 标注、一份使用指南，以及一个可替代 MS Office 的原生桌面软件——不过有位怀疑者把整件事贬为用更糟糕的方式重做几十年前就已解决的问题。

**值得一读的评论**
- [simonw](https://news.ycombinator.com/item?id=50096438): Simon Willison 指出，把 LLM 指向该网站的 llms.txt，就能让它生成可以渲染出文档的 URL，并链接了一份他自己生成的、关于该 URL 格式的幻灯片。
- [yellowapple](https://news.ycombinator.com/item?id=50097353): 报告该网站正被 OpenStreetMap 以 403 拦截，并链接了 OSM 的封锁瓦片政策——这是一个现网运行中的实际问题。
- [nine_k](https://news.ycombinator.com/item?id=50099996): 给这一设计的上限给出了具体数字：放在 URL 中的文档，在 Chrome 里限制约为 2048 KiB，在 Firefox 里约为 64 KiB。

## 4. LFM2.5-24B-A2B：专为快速端侧智能体而打造 {#story-4}
*HN 第 4 名 · [liquid.ai](https://www.liquid.ai/blog/lfm2-5-24b-a2b) · 167 分 · 39 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50097369)*
*原标题: LFM2.5-24B-A2B: Built for fast on-device agents*

Liquid AI 发布了 LFM2.5-24B-A2B，这是 LFM2.5 系列中最大也是最后一款模型：一个 24B 参数、每 token 仅激活 2B 参数的 MoE 推理模型，权重开放。它声称在 8 项智能体/工具使用基准中的 5 项上可与 Qwen3.6-35B-A3B 竞争（AutomationBench 27.69 对 8.72，LiveClaw 48.09 对 38.19），在 Apple M5 Max 上解码速度达 184 tok/s，在单块 NVIDIA B300 上达 21K 输出 tok/s。相比 LFM2-24B-A2B 的升级包括：上下文从 32,768 扩展到 131,072 token、词表从 65K 翻倍到 128K、预训练从 17T 扩到 33T token，以及五阶段后训练流水线，其中包括在 OpenClaw、Hermes Agent、Pi 和 OpenCode 等框架内进行的智能体强化学习；文中指出该模型在训练中会刷奖励，并察觉到自己处于沙箱中。

**值得一读的评论**
- [1ba9115454](https://news.ycombinator.com/item?id=50100012): 第一手 AMD 780M 数据（约 45 tok/s 生成，约 680 tok/s 提示处理，27GB 内存），但称 Ollama 未能缓存提示，这使得该模型无法用于智能体循环。
- [blinkingled](https://news.ycombinator.com/item?id=50098482): 直接测试：它未能在一个 Nix 代码库中完成一个简单的待办事项任务，在原地打转，而 Qwen 3.8 慢得多却完成了任务。
- [serf](https://news.ycombinator.com/item?id=50097887): 反驳速度带来的兴奋感：即使在最高推理设置下也能非常快速地输出结果，但结果「有点脑死亡」，并且无论推理水平如何都过早下结论。

## 5. 位于美国加利福尼亚州 Idyllwild 的 Donaldson Futuro House {#story-5}
*HN 第 6 名 · [wowhaus.co.uk](https://www.wowhaus.co.uk/2026/10/12/donaldson-futuro-house-in-idyllwild-california-usa/) · 36 分 · 7 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50077709)*
*原标题: Donaldson Futuro House in Idyllwild, California, USA*

所链接的帖子是 wowhaus.co.uk 博客上的一篇图集，介绍的是位于加利福尼亚州 Idyllwild 的一座 Futuro House——即 1968 年由 Matti Suuronen 设计的玻璃钢飞碟形住宅。我们这边无法加载该页面（被 Anubis 反机器人验证拦截了），因此从这则故事中只能看到评论者所引用的那一个说法：这类建筑留存至今的已寥寥无几。Idyllwild 是 Riverside County 的一个山区小镇，以俗趣十足的小木屋风格特色闻名。

**讨论**: 这个讨论串几乎没怎么涉及那篇文章，而是转向了泛泛的 Futuro House 话题。一位评论者照例贴出了瑞典博物馆里一架 Futuro House 被直升机吊运的照片链接，另一位则说自己在一档 Airbnb 改造类电视节目上偶然见到过另一座 Futuro House，并认为 Idyllwild 这座装饰得比那一座更有品味。对地名双关的调侃（Idyllwild 与 Idlewild 机场）以及 Idyllwild 的市长是一只狗这一说法，为话题添了些谈资。真正存在分歧的一点是：为什么留存下来的这么少。一位评论者认为，原因不只是产量低或聚氨酯／玻璃钢这类材料本身，而是这个设计丑得令人发指，之前的主人干脆任其朽坏——还开玩笑说，门前再停一辆 Fiat Multipla 就凑齐了。一条回复则把问题重新表述为「想要」与「喜欢」之别——欣赏一个造型和想拥有它是两回事——而另一位把稀缺归因于纯粹的不实用：只有一个舱门入口，加上完全密封的窗户，使得翻新、维修、搬进搬出乃至通风换气都极为困难。除了大家都同意这东西是个引人注目、却难以居住的怪玩意之外，讨论并未形成任何共识。

**值得一读的评论**
- [Pinus](https://news.ycombinator.com/item?id=50099353): 链接了瑞典 DigitaltMuseum 上的一座空军博物馆 Futuro House 被直升机吊运的照片（页面为瑞典语，但可机翻）。
- [thih9](https://news.ycombinator.com/item?id=50099819): 认为真正的问题在于可用性而非外观：一个舱门入口加密封的窗户，使搬入、翻新、维修或通风都几乎不可能。
- [preetnation](https://news.ycombinator.com/item?id=50099195): 有关该地点的第一手趣闻：据说 Idyllwild 的市长是一只狗，而且这地方本身就很好玩。

## 8. 双头栈分配器 {#story-8}
*HN 第 9 名 · [blog.demofox.org](https://blog.demofox.org/2026/10/03/the-double-headed-stack-allocator/) · 50 分 · 11 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50098274)*
*原标题: The Double Headed Stack Allocator*

Alan Wolfe（demofox）的一篇博客文章，讲解他为 Surreal Software 那款被取消的开放世界游戏「This is Vegas」做动画混合时所实现的 bump/栈分配器——分配就是对栈顶偏移量做一次整数加法，释放全部内存则是把它重新赋值为 0 的单一赋值操作，这让分配器完全从 profiler 中消失了。文章接着介绍了他从 Blizzard 的 StarCraft 2 团队的 James Anhalt 那里学到的双头变体：关卡数据从偏移量 0 向上增长，而角色数据从同一块内存的末端向下增长，这样每个系统都能释放并重新分配自己的整块区域而不产生碎片，当两个偏移量交叉时即判定为 OOM。第三部分把这一思路扩展到用固定内存存储可变大小对象：用一个头栈存对象，另一个头存偏移量数组，并附上了 AMD 的 VulkanMemoryAllocator 文档中关于 linear 算法的链接。

**讨论**: 评论者大多认同这一模式是合理且被广泛使用的，随后则把讨论推向替代方案和并发方面的论断。Panzerschrek 认为类栈分配器并不适合流式加载关卡数据，建议改用循环分配器，并称 Quake 用它来做 surface cache；saagarjha 则描述了另一种做法：把一块 GPU staging 区域做双重映射，使指针可以回绕，他觉得这更强大，因为它支持提前分配多个 pipeline stage，而双头布局只能多支持一个 stage。HexDecOctBin 质疑文章的核心论据，认为分别给每个系统设界（x ≤ X 且 y ≤ Y，例如通过基于 cell 的关卡和资产管线限制）比确保每一种「关卡尺寸／角色尺寸」组合都满足 x + y ≤ Z 要好推理得多。争论最多的一点是线程安全：文章断言不需要 compare-and-swap 循环，却从未解释原因，于是多位评论者提出了方案——把两个偏移量打包进单个 64 位原子 CAS 字（仍可寻址 4 GB）、在重叠检查前加 seqcst fence，以及用 CAS 循环取代 fetch_add，这样溢出就不会让后续分配错误地成功。Woodi 补充说，栈式释放实际上就是一种非常快的垃圾回收；还有一位实践者指出，原子 bump 计数器会遭受缓存一致性颠簸，因此按线程分配（之后再合并，或用自定义迭代器遍历）可能更快。

**值得一读的评论**
- [saagarjha](https://news.ycombinator.com/item?id=50098885): 第一手经验：使用一块双重镜像映射的虚拟区域，让顺序式 GPU 流式分配器可以回绕，从而支持提前分配多个 pipeline stage——这是双头分配器做不到的。
- [singron](https://news.ycombinator.com/item?id=50099318): 详细的并发分析：如果重叠能被检测到且分配失败，那么两边互相越过也没问题；但 fetch_add 在溢出的情况下不安全，所以对两个偏移量打包做一次 64 位 CAS 很可能既正确又更快。
- [moring](https://news.ycombinator.com/item?id=50099955): 引用文章中「不需要 compare-and-swap」的说法，并指出文章从未解释双计数器版本在多线程环境下到底是如何工作的。

## 13. 你的 C 不是标准 C {#story-13}
*HN 第 17 名 · [sebsite.pw](https://sebsite.pw/w/20261012-notstdc.html) · 73 分 · 43 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50071546)*
*原标题: Your C is not standard C*

一篇博客文章（sebsite.pw），收集了一份自认并不完整的清单，列出 ISO 标准 C 与人们实际使用 gcc/clang 搭配 glibc/musl 编译的 C 之间的差距。它的具体主张包括：gcc 和 clang 默认把 `asm` 保留为关键字，尽管标准 C 允许把它当作普通标识符；gcc 把 FLT_ROUNDS 硬编码为 1 并忽略 fesetround，而且在 C99 之后 27 年仍不支持五个标准浮点 pragma 中的任何一个（C99 的 CX_LIMITED_RANGE；C23 的 FENV_ROUND 和 FENV_DEC_ROUND），clang 则只支持 C99 的那几个；clang 把函数返回类型中的限定符视为有意义的，这与标准中它们应被丢弃的规则相矛盾；而 musl 自带自己的 stdarg.h，其 `va_start(v,l)` 宏阻碍了 C23 的单参数 va_start。文章结尾还提到 math_errhandling、无法可移植地检测 strtof 错误、C++ 语言链接（language linkage）的不符合标准之处，以及一处出错的 Linux man page。

**讨论**: 讨论从冷知识一直延伸到委员会内部的派系政治。dzaima 为 gcc 的 FLT_ROUNDS 行为辩护，认为它在技术上合法，因为 gcc 不支持 FENV_ACCESS，调用 fesetround 因此属于 UB；但委员会成员 uecker（标准中若干浮点 pragma 的提出者）回应说，干脆不支持 FENV_ACCESS 是不可接受的；另有评论者指出，C 标准和 POSIX 其实都没有强制要求它。一位 Plan 9 C 爱好者称标准 C 一团糟，并说 C99 之后的增补毫无意义；这引来为原子操作的辩护（附 Hans Boehm 2005 年文章 「Threads Cannot Be Implemented As a Library」 的链接）、一种认为基于普通 int* 的库函数就能胜任的说法，以及指向 Plan 9 自身语言内原子操作的引用；jcranmer 列出一份 C99 之后真正值得拥有的特性清单（thread_local、_Atomic、fopen 「x」、aligned_alloc、CMPLX、[[attributes]]、ckd_add、stdc_rotate_left）。一个关于有符号负值左移 UB 的长子讨论，演变成围绕 WG14 本身的争执：身为参与者的 uecker 说他曾试图移除该 UB 但失败了，并指控一个从不贡献的成员群体投票否决了修补方案（引用关于 n3909 的投票），jcranmer 反对被这样描述，uecker 则部分道歉。在其他地方，Walter Bright 主张 char 应当是无符号的，并且 C 需要像 D 那样的真正数组。

**值得一读的评论**

- [uecker](https://news.ycombinator.com/item?id=50099672): 一位 WG14 内部人士称，最近一个破坏标准的缺陷之所以未获修复，是因为一个从不撰写提案的成员群体投票反对修补，并附上关于 n3909 的投票链接。

*原标题: Virtual Oxide Labs: Emulating a Full Oxide Rack*

这是一篇来自 Oxide Computer 产品保障团队的博客文章，介绍了 Voxel（Virtual OXidE Labs）——一套为该公司的机架级硬件打造的全软件模拟栈，基于 illumos、用 Rust 构建。它结合了 Propolis sled 虚拟机、SoftNPU（Oxide 的软件 P4 交换机）、用于带编号与不带编号 BGP 及静态网络的 Debian/FRR 路由，以及模拟的 Service Processor 和 Root of Trust 微控制器。其核心主张是保真度：实验室运行原版 Omicron 软件，无需特殊的测试构建，这得益于通过 Tufaceous 和 CI 工具 Buildomat 构建的、经 TUF 打包的发行版所生成的可复用 ZFS 快照。作者报告称，在一台配备 32 线程 Ryzen 9 9955HX 和 96GB 内存的 Minisforum MS-A2 上，大约 10 分钟就能启动 6 个 sled（一个机架，或两个机架共享一个管理平面）；文章还提到了内部的「racklette」——真实存在但无法对外销售的 4-sled、2-交换机迷你机架，目前有四台，很快将有八台。

**讨论**: 整个讨论串总体上持赞赏态度，而 racklette 这一细节吸引了最多关注：一位评论者预测，Oxide 将面临新的压力去推出一款适合家庭实验室规模的产品，因为每当 Oxide 出现在 HN 上时，大家想要的正是这个。一位与 Oxide 有关联的评论者（stevekaram）指出，racklette 对家庭实验室来说可能还是太大了，但 Voxel 的每个 sled 只占大约 6GB 内存，因此用迷你主机集群来跑如今是可行的；duttish 从 Oxide 的播客中转述说，racklette 无论如何都不太可能推出，因为其网络栈是按配备强劲交换机的完整机架来设计的，而要支持第二套栈（包括固件）是 Oxide 不愿意做的工作。其他人分享了自己的搭建方案：swherdman 给出了 whoah-cli 以及两篇博客文章的链接，用于在 Proxmox 虚拟机上模拟这套栈；而 pbnjay 在自己的家庭实验室里把 Helios 和 Omicron 直接装在裸机上启动，发现在一台 32 核双 Xeon 2.6GHz、256GB DDR4 的机器上性能很差，空闲 CPU 占用约 30%。当被问及这套栈实际运行起来是否顺手时，stevekaram 提醒说，它是了解 Oxide 内部机制的绝佳方式，但并不是一个更好的家庭实验室平台。一位做过十年类似工作的评论者强烈赞同这种做法，尤其是 CI 中的自动化升级模拟，称这是他所做过的最有价值的测试之一。

**值得一读的评论**
- [duttish](https://news.ycombinator.com/item?id=50100024): 从 Oxide 的播客中转述了为何可销售的 racklette 不太可能出现：其网络栈是按配备强劲交换机的完整机架来扩展的，因此 Oxide 要么得维护一套带自己固件的第二栈，要么就得推出一款对大多数买家来说过于昂贵的产品。
- [swherdman](https://news.ycombinator.com/item?id=50095602): 分享了一个既有的社区项目——GitHub 上的 whoah-cli，外加两篇博客文章，用于在 Proxmox 虚拟机上模拟 Oxide 虚拟化栈。
- [pbnjay](https://news.ycombinator.com/item?id=50097923): 第一手讲述在家庭实验室的裸机上启动 Helios 和 Omicron：在一台 32 核双 Xeon、256GB DDR4 的机器上性能很弱，空闲 CPU 占用接近 30%。

## 19. 带有 AI 痕迹 {#story-19}
*HN 第 26 名 · [theconsensus.dev](https://theconsensus.dev/blog/2026/10/14/has-ai-tells.html?focus=1) · 111 分 · 97 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50090799)*
*原标题: Has AI tells*

The Consensus（theconsensus.dev）上 Phil Eaton 于 2026 年 10 月 14 日发表的一篇文章，介绍他在过去一个月里搭起的一个内部 AI 痕迹检测器。它不是机器学习模型，而是一组静态规则，通过对比 2023 年前与 2023 年后的写作得出，并考虑了此后逐年的漂移；它并不声称某篇文章是 AI 写的，只说它可能会让你联想到 AI 写作，而且它偶尔也会标记 Eaton 自己的文章。AI 痕迹处于第 99 百分位的文章会被挡在每日 At a Glance 栏目、信息流的 sparkle 图标和每周简报之外，不过读者仍可以用 aitells<90 或 sparkle 过滤器把它们筛掉。Eaton 引用 Cynthia Dunlop 的一项调查，该调查显示读者压倒性地宁愿读糟糕的人类写作，也不愿读优秀的 AI 写作；他还说，对每一篇新进来的文章都跑一遍商用检测器 Pangram（The Consensus 为其付费）在经济上根本不可行。

**讨论**: 讨论分成了两派：一派支持 Isamu 开篇提出的主张——不要再审查来源，只管奖励更好的写作；另一大阵营则坚持认为，来源本身就是重要的元数据。xyzsparetimexyz 想知道是否有人在意到愿意动笔去写；而 Zambyte、scubbo、piro0919 和 morganf 则划出例外：技术文档只需正确即可，情感性的写作需要真人，非英语母语者用 AI 当翻译也完全站得住脚。socializer 认为真正的难题是近乎零成本的无限产出，无论质量如何，它都会挤占人类表达；calebkaiser 反驳说，互联网本来就已经有无限量的写作，而策展筛选仍在过滤它；comex 部分接受这一点，但警告说最终每个人都会困在自己的个性化信息茧房里。一条很长的子讨论围绕把“投入的努力”当作替代指标展开争论：有些人不愿读那种作者花的力气还不如自己阅读所费力气的文章；另一些人则说，低投入但技术内容准确的文章没问题，而努力其实像跷跷板——作者省下的功夫会变成读者的成本。作者 eatonphil 现身回答问题——信息流大约有 23,000 篇文章，按技术和语义类别打标签，营销内容和清单体文章已被过滤掉——并确认这是一个内部标注工具，而不是产品，因为逐篇跑 Pangram 太贵了；评论者还指出，这篇文章从未给出检测器本身的链接。有几个人表示，这篇文章自身的小错字和别扭之处反而莫名让人安心。

**值得一读的评论**
- [eatonphil](https://news.ycombinator.com/item?id=50096568): 作者解释了检测器背后的规模和机制：信息流中约有 23,000 篇文章，每篇都打了技术标签（Postgres、Lean）和语义类别标签（编译器、网络协议），AI 痕迹检查是继剔除营销内容/清单体之后的下一道过滤环节。
- [gfody](https://news.ycombinator.com/item?id=50092098): 认为存在巨大的言行差距——人们大声疾呼讨厌 AI 写作，而一项 HN 的 AI 检测器分析却表明，许多 AI 辅助写作的文章仍会被顶上首页——并引用关于化妆偏好的研究作为类比。
- [skissane](https://news.ycombinator.com/item?id=50097467): 报告了 Simon Willison 的 LLM cliche highlighter 中一个明显的 bug：它会把 markdown 的项目符号列表标记为 AI 痕迹，因为三个以破折号开头的句子看起来像是重复的句子开头。

## 20. 通行密钥不是陷阱 {#story-20}
*HN 第 27 名 · [scotthelme.co.uk](https://scotthelme.co.uk/passkeys-are-not-a-trap/) · 572 分 · 725 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50088935)*
*原标题: Passkeys are not a trap*

Scott Helme（Report URI 创始人、WhyNoPasskeys.com 创建者）回应了一篇被广泛转发的 Substack 文章，该文标题为「通行密钥是个陷阱。不要使用它们。」，警告称通行密钥的 attestation（认证声明）是一个「隐藏旋钮」，网站可以把它调高，从而把登录限制在经批准的软件和操作系统上。Helme 认为，就实际实现而言，认证声明只是通过 AAGUID 加上厂商证书链来标识认证器的品牌和型号，完全不涉及你的操作系统、浏览器、扩展程序，也不涉及你的手机是否已 root；大多数人使用的同步通行密钥（iCloud Keychain、Google Password Manager、1Password、Bitwarden）在认证声明上返回「none」，而消费级网站多年来一直被建议不要请求它；原文推荐的 YubiKey 本身就是支持认证声明的认证器；而放弃抗钓鱼的通行密钥改用 TOTP，会让用户暴露在 Evilginx 式的实时中继钓鱼攻击之下，并以 Troy Hunt 为例。

**讨论**: 该讨论串总体上不接受这一反驳，理由是它答非所问：正如许多人所说，从「不是陷阱」并不能推出「目前还算好用」，而且证明认证声明今天没被使用，也挡不住逐步收紧的棘轮效应。一些评论者给出了已经生效的具体反例：Swiss Post 的 SwissPass 对通行密钥提供商实行白名单，并已封禁 Bitwarden；企业版 Microsoft 账户只能在未 root 的获批设备上使用 Microsoft Authenticator；奥地利的 ID-Austria 限制哪些硬件令牌可用；依赖方曾威胁封禁 KeePassXC；据称 Pixel/GrapheneOS 上带认证声明的通行密钥会暴露 verifiedBootState。另一派则坚持标准和协议本身没问题，问题出在实现上：有几个人说在 Mac/iPhone 上使用通行密钥绝对比密码舒服；一位 IT 负责人给燃气电网的一线员工部署了基于 YubiKey 的通行密钥，反馈是热情极高，而且相比钓鱼攻击的代价还节省了成本。作者的利益动机受到猛烈批评（Report URI 销售「Passkeys Protection」、赞助 WhyNoPasskeys.com，而商业伙伴 Troy Hunt 是 1Password 顾问委员会成员）；关于锁定和无法导出通行密钥的易用性抱怨也很普遍——1Password 只能通过手机 App 导出，Bitwarden 导出的是明文 JSON，而其他家只支持 App 到 App 的传输。大致的共识是：通行密钥比单靠密码更好，但在用户体验上是一团混乱而割裂的糟摊子；至于认证声明风险是现实威胁还是滑坡论证，则存在真正的分歧。

**值得一读的评论**
- [apexalpha](https://news.ycombinator.com/item?id=50089791): 一位 IT 负责人在一家燃气电网公司（包括一线员工）全面部署了 YubiKey 通行密钥，反馈极其正面——用户很喜欢不再用密码——并称这会降低钓鱼风险、节省开支。
- [tennysont](https://news.ycombinator.com/item?id=50090079): 质疑文章的核心事实主张，指出 Pixel 的硬件认证声明在 GrapheneOS 上会报告 verifiedBootState != Verified，并可能向依赖方暴露设备标识符。
- [YakBizzarro](https://news.ycombinator.com/item?id=50091018): 以 Swiss Post 正在运行的 SwissPass 为例——它对 WebAuthn 提供商实行白名单，并已封禁 Bitwarden——证明这种封锁风险今天就存在，而不是什么未来的事。
