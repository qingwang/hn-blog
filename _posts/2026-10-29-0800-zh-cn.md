## 1. 史上首次，Google Search 占 Alphabet 营收的比例不足 50% {#story-1}
*HN 第 1 名 · [kadoa.com](https://www.kadoa.com/companies/insights/google-search-below-half) · 224 分 · 151 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50291945)*
*原标题: For the first time ever, Google Search is less than 50% of Alphabet's revenue*

这是 Kadoa 的一篇数据文章，梳理了 Alphabet 的营收构成：在截至 2026 年 9 月的这一季度，Google Search 及其他业务在 1280 亿美元总营收中贡献了 634 亿美元，占 49.7%，这是 Alphabet 开始单独披露 Search 营收以来该占比首次低于一半。在此前的 31 个季度里，这一占比在 52.8% 到 62.0% 之间；同期 Google Cloud 的占比从 4.4% 升至 24.1%（307 亿美元）。文章强调，Search 营收仍在增长；占比下降只是因为其他所有业务增长得更快。

**讨论**: 讨论分成两派：一派读者认为这标志着搜索本身的衰落——AI 答案正在蚕食搜索查询，搜索结果越来越差，AI Overviews 把用户推向了 Kagi 和 DuckDuckGo；另一派则算了一笔账，指出 Search 营收同比增长约 12%，占比下降只是因为 Cloud 的份额几乎翻了一倍。有几个人指出，财报中真正坏的消息是每股收益（EPS）不及预期（2.12 美元，而预期约为 3.01 美元，股价下跌 13–15%），有人把这归因于 AI 资本开支，而不是主营业务疲软；一位评论者反驳说，营业收入并不比 EPS 更「真实」。一个很长的子讨论围绕一条 X 帖子展开，该帖子声称 Google 改动了广告拍卖机制以及完全匹配/近似变体匹配，以榨取更多营收；回复分成两派，一方称这是轶事式的无稽之谈，另一方则认为，调整 pCTR 预估的机制以及广告技术反垄断案的裁定（Project Bernanke）让这种说法可信；还有人反驳说，追踪 ROAS 和 CPA 的广告主只会直接转移预算。另有一场争论是 Google 究竟有没有自己做出过什么东西，还是只会收购 YouTube、Android 和 Maps，最后大多以这样一句反驳收尾：Google 把这些收购来的东西做成了它们如今的样子。还有几条评论纠正了关于分部归属的混淆，即什么算 Google Cloud（GCP、Workspace、Gemini Enterprise），什么算消费者订阅。

**值得一读的评论**
- [JumpCrisscross](https://news.ycombinator.com/item?id=50293123): 引用 Alphabet 的 10-Q 纠正前提：Search 及其他业务营收同比增长 12%，付费点击量增长 8%，每次点击成本增长 4%——Network 的下滑是一个独立的、仅限网页端的业务分部。
- [mlmonkey](https://news.ycombinator.com/item?id=50292787): 一位从业者解释了搜索拍卖如何抬高营收：竞价引擎自己按 bid_i+1 × pctr_i+1 / pctr_i 的公式计算 pCTR，因此调整预估点击率会直接提高成交价格。
- [happyopossum](https://news.ycombinator.com/item?id=50292243): 厘清了分部定义——Google Cloud 涵盖 GCP、Workspace 和企业服务，而 Google One 和 Gemini 消费者套餐这类消费者订阅则归在 Services 之下。

## 2. 我们正在发布 Mistral Large 4 的权重 {#story-2}
*HN 第 2 名 · [mistral.ai](https://mistral.ai/news/mistral-large-4-oss/) · 714 分 · 186 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50289418)*
*原标题: We're releasing the weights of Mistral Large 4*

Mistral 发布了 Mistral Large 4（「Le Chonk」）的开放权重。该模型是一个 1 万亿参数的原生多模态模型（总参数 1T，激活参数 A52B），在公开预览三周后，于欧洲基础设施上从零训练完成。文章称其为最佳开放权重编程模型：在 Cognition 私有的 FrontierCode 2.0 上得分 19.7%，在 Artificial Analysis Coding Agent Index 上得 48%（与 GLM-5.3 并列，且每任务 token 数少 47%），在 Terminal-Bench 4.0 上提升 13 个百分点至 41%；此外在 AA Cyber Index 上得 51%，对恶意网络请求的拒绝率为 96.6%。文中还提到三种推理模式，并引用了 Booz Allen、Cisco、Cloudflare、CrowdStrike、Elastic、ENISA、Fortinet、Orange Cyberdefense、Rubrik 和 Zscaler 的推荐语。

**讨论**: 讨论区大部分是在争论「open」这个词：许可证是修改版 MIT，要求任何经营 Model-as-a-Service 业务的人另行签订商业协议，许多评论者认为这属于「权重可用」，而不是开放权重，并援引 Redis、Elasticsearch、Terraform 的先例，以及 OSI 的开放源代码 AI 定义（该定义还要求提供训练代码和数据构成）。另一些人反驳说，Mistral 从未说过这是开源，内部使用和非托管类商业使用不受限制，只有做 token 转售的 neocloud 才需要许可证；一个子讨论认为这些条款可能根本无法执行，因为模型权重很可能不受著作权保护。另一场并行的辩论围绕价格与性能：一位评论者指出，价格较预览期大约减半至每百万输入 token $0.70、每百万输出 token $2.10（缓存 $0.07/M），值得重新评估；而其他人表示，在每任务成本和智能指数上，它仍然落后于 DeepSeek 和 GLM。一位缓存命中率高达 97% 的编程用户称其缓存定价是 DeepSeek 的 10 到 20 倍。从业者还谈到欧盟数据驻留的用途（有人指出 CLOUD Act 可能使这一点失效），被禁止使用中国模型的美国受监管企业将其视为主要的可自托管非中国选项；量化方面的算术也被提及：Unsloth 在发布当天就提供了 GGUF，但最小的量化版本仍需约 256GB 显存，而 4-bit NVFP4 权重约为 610GB。次要抱怨包括思考模式慢、harness/skills 工具链相比 Claude 较弱、欧盟区域推理加价 10%，以及令人困惑的控制台注册流程。

**值得一读的评论**
- [maxloh](https://news.ycombinator.com/item?id=50290476): 引用了许可证中要求 Model-as-a-Service 另行取得商业许可的条款，认为「权重可用」才是诚实的说法，并指出 Qwen、GLM、Kimi 和 MiniMax 同样被贴错了标签。
- [Topfi](https://news.ycombinator.com/item?id=50289701): 指出价格较预览期减半（从每百万 token $1.36/$4.18 降至 $0.70/$2.10），并称预览版在旧价格下缺乏竞争力，因此这次发布值得重新评估。
- [prophesi](https://news.ycombinator.com/item?id=50293101): 指出 Unsloth 在发布当天就获得了发布量化版本的权限，但即使是最低的量化版本也需要约 256GB 显存——这是对「开放」自托管的一次有用的现实检验。

## 3. H.264 就是魔法（2016） {#story-3}
*HN 第 4 名 · [sidbala.com](https://sidbala.com/h-264-is-magic/) · 136 分 · 58 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50291054)*
*原标题: H.264 Is Magic (2016)*

对 H.264 的一篇常被转发的讲解文章（最初发表于 2016 年，作者 sidbala），讲它如何在四个层面削减数据量：8-bit 4:2:0 之下的量化、离散余弦式的频域掩蔽、色度子采样，以及利用 I 帧／P 帧／B 帧和 16x16 宏块做时域运动补偿。它的核心演示是：苹果主页的一张 PNG 截图重 1015KB，而同一页面的 300 帧、5 秒、60fps 的 H.264 剪辑只有 175KB。文章用信息熵和「为一辆 3000 磅的赛车减重」的类比解释这一切，并强调低通频率掩蔽能在视觉上不明显的情况下把细节压到原图的 2%。

**讨论**: 大量讨论偏离了文章本身，转向现役编解码器的现状：有人说 AV1 已经「主流」，另一些人指出 Nvidia Shield（最后更新于 2019 年）没有 AV1 解码，而 Apple 硬件直到 2023 年才加入。反驳的一方列举了证据：Roku 约占 43% 的流媒体硬件、Amazon 约占 35%，且智能电视占了大多数观看时长；Tiger Lake 一代的 Intel NUC 以二手价几十美元就能硬解 AV1。另有一条独立线索说 AV1 值得用，甚至不一定需要硬件解码，因为它在 YouTube 上以更小的体积提供了更好的画质。还有个旁支关于图片格式：有人建议换掉 PNG，因为 WebP 和 JPEG XL 的体积都明显更小，但有人反驳说 WebP 解码比 JXL 快得多，且 lossy AVIF 两者都胜过。还有人对文章拿无损 PNG 去和有损视频比划提出异议，辩护者说那只是修辞引子，后面马上就解释了。其余评论讨论 H.264 专利（一条提示 High Profile 的专利几乎全部到期，另一条说「最后一项主要专利」还剩一年）、H.264 对 H.265 的取舍（1080p 选 H.264，4K 选 H.265，需要兼容性就选 H.264），以及有证据表明神经／学习型编解码器是未来方向，但目前速度太慢。

**值得一读的评论**
- [WhitneyLand](https://news.ycombinator.com/item?id=50291663): 认为文章拿无损 PNG 和有损 H.264 比大小的核心演示是苹果比橘子：「根本说不通」，尽管回复者辩称那只是文章刻意设置的引子（C55），而该对比本身就是衡量有损压缩的合理方式（C54）。
- [ksec](https://news.ycombinator.com/item?id=50292455): 指出 H.264 High Profile 已接近免专利，并链接到维基媒体关于 MPEG-4 AVC 专利到期的页面。
- [Dwedit](https://news.ycombinator.com/item?id=50292601): 给出各图片格式的实际分工：无损 WebP 解码比无损 JXL 快得多，有损 AVIF 则胜过有损 JXL 和 WebP，无损 AVIF 还不如 PNG。

## 4. LLM Voice {#story-4}
*HN 第 5 名 · [martinfowler.com](https://martinfowler.com/bliki/LLM-Voice.html) · 92 分 · 47 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50290177)*

Martin Fowler 的一篇 bliki 文章认为，读者会把「LLM Voice」当作一种本能的恐怖谷反应识别出来——不是破折号，而是「load-bearing tapestries」这类表达——而且远在任何检测工具能帮上忙之前就能察觉。他的建议是：绝不要让 LLM 起草，因为人工编辑无法把这种声音清除掉，并把大纲视为可接受的极限；他公开了自己的做法（只把 AI 当搜索工具，所有事实都在原始来源核实），并列出例外，包括 Jim Highsmith——后者依赖 LLM 在患帕金森病的情况下继续写作——以及翻译和官僚套话信函。他主张写作就是他思考的方式，因此把文字工作委托出去就等于把理解委托出去。

**讨论**: 讨论串总体上认同这一诊断，但在伦理问题上存在分歧。最常见的类比是食物：几位评论者把 LLM 生成的文字比作冷冻的 Sysco 墨西哥卷饼——作为私人的燃料没问题，但当作自家烹饪端给客人就是侮辱；其中一人指出，美国约 90% 的餐厅食物本来就来自 Sysco/US Foods，食客只是避开那些只做加热的地方。另一些人反驳说，这不是非此即彼，并认为「AI 会让人丧失思考能力」的说法是危言耸听；而一条反驳回复则认为，真正的风险在于消费 LLM 文字会训练人们用那种声音写作。一位发帖者称自己投给 HN 的帖子被从前页撤下，并怀疑评判依据是文风而非技术内容；尖锐的反驳是：LLM 腔调意味着价值可能很低，所以不能指望读者去筛出例外，原帖作者接受了这一分歧。另一个子讨论串争论这些破绽是否会消失——一些人预计几个月或两三年内就无法分辨，另一些人认为随着模型漂向过度复杂化，这个信号正在变差，而人类会改变风格以免被误认为机器。

**值得一读的评论**
- [martythemaniak](https://news.ycombinator.com/item?id=50293162): 描述了一套保留自己声音的具体工作流：录一段语音备忘，让 LLM 提出澄清问题并批评草稿，并反复指出它在哪些地方把你的想法抹平了——同时主张非个人化的文件完全可以安全地由 AI 全权撰写。
- [ctrlt](https://news.ycombinator.com/item?id=50292630): 第一手报告：一篇关于某个小众技术问题的 HN 帖子被从前页撤下，该评论者认为这说明评判依据是文风而非工程洞见。
- [dofm](https://news.ycombinator.com/item?id=50293028): 对「我们永远分辨不出来」这种悲观论调的反驳：破绽可能变得更糟而非更好，而且人类会改变写作方式以免被与 AI 混淆。

## 5. 僵尸统计数据：AI 引用的数字从何而来 {#story-5}
*HN 第 6 名 · [trakkr.ai](https://trakkr.ai/trakkr-research/zombie-stats) · 86 分 · 45 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50290283)*
*原标题: Zombie stats: Where the numbers AI quotes come from*

Trakkr Research Study 013 通过各家公司的 API 并开启联网搜索，向 ChatGPT、Perplexity、Gemini、Claude 和 Google AI Overviews 提出了 200 个数值型问题，随后对随机抽取的 1,285 条被引用的统计数据进行了人工和模型溯源，追溯深度最多五层。只有 40% 的溯源链最终抵达了说法一致的原始研究，8% 抵达了研究但数字或语境被改动，40% 在付费墙、已消失或不再作声的来源处中断，11% 则无疾而终；82% 的被引用页面确实包含该数字，但这些页面中只有 21% 是原始研究，超过一半是公司博客。ChatGPT 得分最高，为 57%，且每条答案引用的数字最少（1.3 个，Claude 为 6.8 个）；其余四家集中在 38–46%，而五个助手都引用过的四项统计数字，无一能找到可溯源的研究。文中展示的典型例子是广为流传的说法「44% 的销售人员在一次跟进后就放弃」，其溯源终点是一篇自由撰稿人的样本文章，该文章并未引用任何研究。

## 18. Qwenputer：在 Qwen3.5 内部运行的一台可用且确定性的 RISC-V CPU {#story-18}
*HN 第 22 名 · [divagr.com](https://divagr.com/blog/qwenputer) · 666 分 · 139 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50282838)*
*原标题: Qwenputer: A functioning, deterministic RISC-V CPU inside Qwen3.5*

divagr18 的一篇博客文章，介绍 Qwenputer：一个原版 Qwen 3.5 4B，在 Qwen 的 32 层前面额外编译了 11 层，其中包含一个 32 位 RISC-V 核心（RV32IM 加上 Zba 和一个小型大数单元），整个核心完全在模型的前向传播中运行。关键在于把 Gated DeltaNet 注意力头变成精确的 RAM：将门控强制设为 1，写入强度 beta 设为 1，并使用 one-hot 键，这样每次写入都恰好覆盖一行，每次查询都取回一个精确值。作者声称它通过了官方的 riscv-tests，与 qemu 一致，并且在自由运行中执行了 1800 万条指令，零错误；在 DeepMind 算术测试集上得分 97.5-100%（基础 Qwen 为 55-90%），另外还有一个实验性文件系统，在 DeltaNet 状态中容纳 512 个文件、约 5.3 万 token，把变更事实的召回率从 30% 提升到 90%。代价：18.8 GB 的检查点（大部分是零填充）、一个自定义的 RvChat 驱动，用于启动固件并让 trace token 不进入 Qwen 的层，以及每次大型计算大约需要数秒（在单块 24 GB GPU 的 L4 上约每秒 3,200 个 CPU token）。

**讨论**: 帖子的大部分内容都是愉快的不敢相信——DOOM 笑话、Qwen 套 Qwen 的笑话、把 LLM 变回 RAM 的笑话——但最尖锐的反驳集中在表述上：一位评论者认为「没有外部运行时、不是插件」的说法有误导性，因为宿主驱动仍然要加载固件、把 CPU 启动到初始状态，并手动跳过 Qwen 自己的层，这些都是对推理驱动的侵入性修改；另一位则直接问到底有没有发生工具调用。第二个争论点是确定性：一方把演示当作「LLM 天生非确定性」这一说法的有力反例，另一些人则回应说，这个 CPU 是硬编码权重，被固定在架构上，因此采样和生产环境中的非确定性并未被触及。有人问，一个在自己的基准测试中都拿不到 100% 的计算器有什么用；还有人报告了相反的实验——直接提示前沿模型去模拟 RISC-V——结果在几条指令内就失败了，而模型一直试图走捷径直接得出最终答案。不少人问它到底有什么用；同情的回答是，模型内部一个确定性的计算单元加上持久记忆，对算术和跨对话事实来说是低成本的收益，作者也出现在帖子里，说这是一个业余时间项目，并且他愿意接受工作机会。

**值得一读的评论**
- [gcr](https://news.ycombinator.com/item?id=50286992): 认为「没有外部运行时」的说法有些不够诚实：自定义的宿主运行时仍然要加载固件、启动 CPU 并跳过 Qwen 的层，而这些是对推理驱动的侵入性修改。
- [gspr](https://news.ycombinator.com/item?id=50285274): 对相反实验的第一手描述：要求 Qwen 和所有前沿模型去*成为*一个 RISC-V CPU，每次都在几条指令内失败，通常是在指令解码阶段，而且模型总是作弊，直接计算最终答案而不是单步执行。
- [gavinray](https://news.ycombinator.com/item?id=50287557): 指出若干基准测试显示准确率低于 100%，并问一个并非始终精确的计算器到底有什么用。

## 20. Java 的新 AOT 缓存功能目前状态不佳 {#story-20}
*HN 第 24 名 · [xpipe.io](https://xpipe.io/blog/java-aot-cache) · 71 分 · 23 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50242509)*
*原标题: Java's new AOT cache feature is in a rough state*

XPipe 开发者 Christopher Schnick 详细剖析了 JDK 的 AOT 缓存 —— 它由 JEP 483 在 JDK 24 中引入，经 JEP 514/515 在 JDK 25 中简化，又由 JEP 516 在 JDK 26 中扩展 —— 该缓存会记录一次训练运行的类加载、链接、方法剖析以及部分缓存对象，好让之后 JVM 启动时跳过这些工作。他的主要发现是：AOT 类链接会悄悄启用 adapter caching（JDK-8350209），从而把针对构建机器 CPU 特性调优过的机器码固化进缓存，并在 CPU 特性较少的机器上以 SIGILL 让 JVM 崩溃（例如在 13 代 Intel 上训练、在 12 代上运行）。规避手段是在生成缓存的那次运行中加上未公开文档的 -XX:+UnlockDiagnosticVMOptions -XX:-AOTAdapterCaching；JDK 27 将记录训练时的 CPU 特性并要求完全匹配，他认为这会让即将到来的 JEP 544 code cache 在没有兼容性开关的情况下，对分发给用户的软件几乎毫无用处。

**讨论**: 讨论中最大的一处更正来自作者本人：当一位评论者引用 JEP 544 时，他说明这篇博文讲的是更早、已经发布的 AOT 缓存（JEP 483），而不是 JDK 28 的 code cache。多位读者主张 JVM 应在启动时检测 CPU 特性不匹配并给出警告，或回退到 JIT，而不是直接段错误；其中一人指出，像「this is what I want AOT cache to mean」这样的期待，忽视了该功能是分阶段推进的。一位 OpenJDK 贡献者为这种分阶段做法辩护：在开发者能控制部署方式的生产环境中，该缓存已经体现出价值，机器码缓存会在 JDK 28 落地，对外分发则更晚 —— 另一位评论者说，相比 Java 此前遭遇的僵化，这种取舍更可取。还有人抱怨其易用性，以及某位评论者所称的 Java 社区面对此类批评时充满敌意、向内看的反应，另一些人则拿 Python 和 JavaScript 的打包来反驳；建议包括在安装时按用户的 CPU 做训练运行，也有人提到更成熟的替代方案（OpenJ9、Azul、CRaC、Android 自 Android 7 起的使用）。一个分支讨论发现，GraalVM Native Image 在 java.awt 缩略图生成这类普通场景下仍然别扭，而作者指出 AOT 缓存的独特之处在于允许在运行时向 classpath 添加模块和 jar，这一点不同于 Native Image 的封闭世界。

**值得一读的评论**
- [crschnick](https://news.ycombinator.com/item?id=50290250): 作者更正了一处误读：JEP 544 是另一项尚未发布的 JDK 28 AOT code cache；这篇博文讲的是 JEP 483 下的 JDK 24 AOT 缓存。
- [pron](https://news.ycombinator.com/item?id=50290362): 一位来自 OpenJDK 一方的评论者解释了这种刻意分步推进的做法 —— 该缓存对内部部署已经很有价值，机器码缓存将在 JDK 28 加入，对外部部署的更好支持则在其后。
- [crschnick](https://news.ycombinator.com/item?id=50292862): 作者详述了相对 GraalVM 的一项实际优势：使用 AOT 缓存时，只要 boot module path 与训练运行一致，你仍可以在运行时加载 jar 和模块。
