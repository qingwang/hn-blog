## 1. 我们在构建软件时应该更有野心 {#story-1}
*HN 第 1 名 · [danluu.com](https://danluu.com/ambitious/) · 360 分 · 307 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50225695)*
*原标题: We should be more ambitious with the software we build*

Dan Luu 认为，AI 编程工具已经让以前看似不合理的项目变得便宜到足以尝试，并以 Michael Malis 的 pgrust（用 Rust 重写 Postgres）为例——他说 pgrust 的测试已经暴露出 Postgres 的真实 bug（一个 SP-GiST 数值 bug、一个 JSONPath 格式缓存 bug、一个 pgcrypto bug、字典加载器的内存安全 bug、一个 money 溢出 bug）。Luu 列出了他自己那些省力的衍生项目——一个正则表达式引擎、一个 ripgrep 分支、一个让冷构建快约 50 倍、热构建快 2 倍的 Rust 解释器，以及一个约 5 小时就达到超人水平的 Azul 棋盘游戏 AI——并声称在 GPT-6 Astra 的帮助下，实现 zstd 通过已注册测试的比例超过 99%，成本约为 1 美元。他在开头就说明，他现在写文章只花半小时，且不做严格的基准测试，并承认自己没有亲自调查 pgrust，而是出于个人信任相信 Malis。

**讨论**: 讨论串分成两派。一派列举了真正大型的 AI 辅助构建项目（一个从零写起、击败 QuickJS 并在 test262 上超过 V8/JSC 的 JS 引擎，一个比 gcc 快 7 倍的 C++ 编译器，一个用 Rust 写的 Python 解释器，一个面向 ESP32 的复古 BASIC 操作系统，一个 1995 年游戏的重制版）；另一派是怀疑者，他们说更快的 ripgrep 或一个 Rust 解释器并不是「有野心」的含义——真正的瓶颈是想法、品味和 MVP 之后的产品工作，而不是代码量。几位实践者报告了一种典型的失败模式：一旦代码库复杂度越过某个阈值，模型就会原地打转、毫无进展，并且默认采用局部补丁和深层 if-else 嵌套，而不是简化；有人讲述 Opus 5.5 构建了一个脆弱的日志抓取 hack，另一位说它提议了一个 Python 负载均衡器，而在那里 haproxy 完胜。然而最主要的纠正是：pgrust 几天前被从 ClickBench 中移除，理由是它涉嫌为每个查询手写代码、缓存结果，并且无法运行基准测试集合之外的查询——评论者称 Luu 基于信任的辩护空泛无力，而 Malis 本人现身辩称，那些手写路径只用于测试，一个 PGRUST_GRAVITY_REPORT 标志证明使用的是通用查询路径，真正的局限是 SQL 支持范围狭窄。一个独立的子讨论串则嘲讽该网站近乎全宽的正文，并交换 CSS 单行技巧（max-width、书签脚本、阅读模式）。

**值得一读的评论**
- [anonymous908213](https://news.ycombinator.com/item?id=50226382): 详细阐述了 ClickBench 作弊指控——为每个查询手写代码、缓存、无法运行未经测试的查询——并认为 Luu 的脚注辩护是「我知道他绝不会作弊」，而不是证据。
- [malisper](https://news.ycombinator.com/item?id=50227869): Malis 本人反驳：发布的二进制文件通过 PGRUST_GRAVITY_REPORT 记录每个查询的代码路径，所有基准查询都走通用路径，没有使用结果缓存，真正的缺陷只是仅支持扫描、分组、排序和过滤。
- [malisper](https://news.ycombinator.com/item?id=50226514): Malis 描述了他实际的验证技术栈——一个从 C 和 Rust 到 Lean 的编译器，加上 LLM 编写的等价性证明，覆盖约 7 万行 C 代码——并说证明上下文正以超线性速度增长，因此他正在研究分片方案。

## 2. Cerebras 部署万亿参数级 AI 模型 {#story-2}
*HN 第 2 名 · [cerebras.ai](https://www.cerebras.ai/blog/how-we-deploy-trillion-parameter-frontier-models-on-cerebras) · 129 分 · 42 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50227356)*
*原标题: Cerebras Deploys Trillion-Parameter AI Models*

Cerebras 的工程博客详细介绍了如何在自家的 WSE-3T 晶圆级芯片上为一款约 3 万亿参数的开源模型 Kimi K3 提供推理服务。由于每片晶圆只有 44 GB 片上 SRAM，4-bit 权重按层分片：每片晶圆放两个线性注意力层，密层则每片晶圆放一个，以便为 KV cache 留出空间；整套系统共 59 片晶圆组成一条流水线，通过基于以太网的 RDMA 互联，每跳约 2 微秒。Cerebras 声称在处理 256k token 的请求时可达每秒 1,000–2,000+ token，并引用 Kimi K3 在 Terminal-Bench 2.1 上 88.3%、在 BrowseComp 上 91.2% 的成绩。

**讨论**: 讨论串分成两派：一派着迷于这套架构，另一派则怀疑大型企业之外的人是否用得上它。一位前订阅用户说，Cerebras 每秒 1,000 token 的速度曾经独一无二，但其托管的 Qwen 3.8 如今在成本和性能上都被 Mercury 3 超越，选择 Cerebras 的主要理由只剩企业定制合作；也有人指出，速度快的 GPT-5.6 Sol 端点并未向开发者普遍开放，或者需要付费。几位评论者批评其基准测试：文章引用的是全精度基准成绩，实际部署的却是 4-bit 权重；一位用户说，API 实际开放的那些小模型确实快，但经常答错。硬件方面的讨论涉及：芯片为何采用方形 2D 网格而非六边形排布、流水线并行与 GPU 批处理有何不同，以及 KV cache 能否放在片外 DRAM 或专用的注意力服务器上。能耗与可靠性也受到审视：有人估算这套 59 片晶圆的系统功耗接近 1.18 MW、约合每 token 4.1 焦耳；另一位评论者则问，一条横跨 59 片晶圆的流水线如何应对单片晶圆故障，毕竟模型实际上就是整个机架。

**值得一读的评论**
- [2001zhaozhao](https://news.ycombinator.com/item?id=50229280): 一位曾订阅 Cerebras 编程套餐的用户给出第一手市场看法：每秒 1,000 token 曾独一无二，但 Qwen 3.8 如今在成本和速度上都被 Mercury 3 超越，因此只有企业定制合作才说得通。
- [tgtweak](https://news.ycombinator.com/item?id=50229054): 指出 Cerebras 为 Kimi K3 引用的是全精度基准结果，实际部署的却是 4-bit 量化权重。
- [zhyblife99](https://news.ycombinator.com/item?id=50227547): 提出了文章回避的运维问题：模型作为一个流水线分布在 59 片晶圆上，Cerebras 如何容忍或摘除单片故障晶圆，而不让整个部署停摆？

## 3. Goose 编程语言 {#story-3}
*HN 第 4 名 · [aardappel.github.io](https://aardappel.github.io/goose/) · 361 分 · 237 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50224100)*
*原标题: The Goose Programming Language*

Goose 是 Wouter van Oortmerssen（Aardappel，也是 Lobster、Amiga E、Cube 2/Sauerbraten 和 TreeSheets 的作者）的新系统编程语言，其内存模型是一组由编译器决定的数据栈，这些数据栈在 64 位地址空间中大块预留的区域内通过 bump 分配（指针碰撞分配）来分配，因此数组增长时引用保持有效，而作用域退出就是释放。它声称没有分配器、GC、析构函数、借用检查器、unsafe 或未定义行为，支持内联的可变长度记录、兼作序列化格式的窄相对引用，以及彼此不共享任何东西的工作线程。最受关注的基准测试声明是：在十六个基准测试中，它的运行速度比惯用 C++ 快 3.3 倍，比手工优化的 C++ 快 1.16 倍，比最好的安全 Rust 快 1.12 倍，内存占用则分别少 1.9 倍、1.3 倍、1.2 倍；它编译成单个 C 文件，并带有用于快速开发构建的 libtcc JIT。作者表示，编译器和文档的很大一部分是由 LLM（Claude/Fable）在他的指导下编写的，这些工作建立在他的 Lobster 编译器和一份提炼出的风格指南之上。

**讨论**: 争论最激烈的两点是 AI 撰写的文字和基准测试。一大批人认为文档读起来像是机器生成的，他们无法信任、甚至无法享受阅读；另一些人则回应说教程清晰，想法应当按本身价值来评判，而且作者公开记录了 AI 的使用情况——作者说他已对其进行了编辑，并更希望人们去试用这门语言，而不是去打磨 Claude 腔。在性能方面，有评论者指出 C++ 基准测试文件缺少 reserve()/with_capacity()，并追问手工优化的版本在哪里；作者回答说真正手工优化的文件是私有的，仓库里的那些是幌子，这一说法立刻招致反驳。一篇尖锐的技术批评认为，这种不使用原子操作、通过队列做 memcpy 的线程模型，在大消息（双重写入、缓存未命中）以及受益于原子操作或锁的算法上必然明显落后，因此平均速度的声明只在程序做同样事情的地方成立。在内存布局方面，实践者追问到底有多少个栈、页粒度造成的浪费、碎片化，以及如何存放任意大小字符串的哈希表；得到的回答是使用池、只增不减的数组和按生命周期分组的数据，作者也承认这门语言要求你重新思考数据组织方式。支线讨论涉及先例（ML Kit 的区域推断、Dart isolates）、32 位/嵌入式/Wasm 的限制（没有惰性提交的 wasm64 行不通）、编译速度（受 C 后端限制，在 JIT 下约慢 3 倍），以及一场争论：帖子正文中 John Carmack 的推文究竟是对 Goose 的背书，还是只是对一个概念的回复——作者说 Carmack 显然读过仓库；其他人则认为这种表述具有误导性。

**值得一读的评论**
- [Aardappel](https://news.ycombinator.com/item?id=50225945): 作者确认，仓库中的 C++/Rust 基准测试文件并非手工优化的版本——真正手工优化的版本是私有的，因此「比优化过的 C++ 快 1.16 倍」这一说法无法核实。
- [nextaccountic](https://news.ycombinator.com/item?id=50229056): 详细论证指出：通过 memcpy 传递消息会强制双重写入，而使用原子操作或锁的 Rust 程序可以彻底击败 Goose，因此速度声明取决于基准测试场景。
- [groundzeros2015](https://news.ycombinator.com/item?id=50225854): 对提交内容表述的反驳：Carmack 是在回复一个概念，而不是在描述自己使用 Goose 的经历，因此这种暗示性的背书具有误导性。

## 4. SpeedCrunch 1.1 {#story-4}
*HN 第 5 名 · [speedcrunch.org](https://www.speedcrunch.org/) · 130 分 · 23 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50224210)*

SpeedCrunch 1.1 是这款免费、开源的高精度科学计算器的发布公告，适用于 Windows、macOS 和 Linux。它宣称支持最高 50 位精度、复数、140 多个函数、单位与常量、用户自定义变量、函数和单位、可编辑历史、标签页和分栏式的多会话、40 多种翻译和 40 多种配色方案。这是该项目大约十年来首次发布新版本，此前的版本是 0.12，社区将 1.0 和 1.1 视为长期沉寂后的重新启动。

**讨论**: 长期用户普遍为这次重新发布感到高兴，好几个人表示自己已经每天使用它多年，主要用于快速草稿纸式计算和位运算与进制转换。主要的批评意见是界面退步：一位十年老用户抱怨输入框被放大到两倍、多出边框和空白，并且出现明显的输入延迟，结果他回退到了 0.12；反驳意见则认为界面总有改进空间，不满意的人可以不升级，而支持者指出新版保留了经典视图选项。有评论者注意到一个长期存在的运算顺序缺陷已修复：1/2(-9.8) 现在得到 -4.9，而旧版本给出 -0.05102040816326530612。另一些人认为该表达式本身就有歧义，应该直接报错，而不是悄悄按新规则求值。其余讨论分散在替代方案上（numbat、Android 上的 Hiper Calc Pro、PARI/GP）、Homebrew 的 cask 被禁用后能否恢复，以及一位用户收到疑似 AI 撰写但很有帮助的 GitHub issue 回复。

**值得一读的评论**
- [unanimous](https://news.ycombinator.com/item?id=50226148): 指出一个长期未发布的运算顺序修复：1/2(-9.8) 现在得到 -4.9，而旧版本得到 -0.05102040816326530612，并且该表达式现在会渲染出明确的乘号。
- [Gormo](https://news.ycombinator.com/item?id=50227880): 一位近十年来几乎每天使用的用户报告 1.1 有明显退步——输入框尺寸翻倍、多余边框和留白，以及前所未有的输入延迟——并称他已回退到 0.12。
- [jiehong](https://news.ycombinator.com/item?id=50225240): 附上变更日志链接，并提到 numbat（github.com/sharkdp/numbat）是他现在更倾向使用的替代计算器。

## 5. 小型程序与语言 {#story-5}
*HN 第 6 名 · [ratfactor.com](https://ratfactor.com/cards/pl-small) · 98 分 · 7 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50225674)*
*原标题: Small Programs and Languages*

ratfactor.com 上的一篇卡片式文章，主张微型程序与微型语言不只是消遣，它们还是某个概念最小复杂度的证据——即把 Kolmogorov 复杂度套用到软件上。文章收集了一批例子：Luke Jackson 用 25 行代码写成的 ijk DOM diff 库、Philippe Brochard 的 46 字节 Forth、Arthur Whitney 的 122 行 J 解释器（即「Incunabulum」）、一份 kOS 转录记录（描述 Whitney 的 k 在 90 Kb 可引导镜像里带有 GUI 和窗口管理器，约 60 行 C）、William Byrd 的 Lisp-in-Lisp、Justine Tunney 的 436 字节带 GC 的 Lisp、Frank Force 的 2 Kb 3D JS 游戏，以及 Fabien Sanglard 的名片射线追踪器。文章还综述了小型语言——Forth、Lisp、Tcl、Lua（参考手册仅 27 页）、C——并指出 Zig 的体量具有欺骗性，引用了 David Ungar 的话「简洁胜过表达力」，最后以微型造物与『微观世界』在心理上的吸引力作结。

PySR 是一个开源符号回归（symbolic regression）工具：它用 scikit-learn 风格的 Python 接口去驱动 Julia 编写的搜索引擎 SymbolicRegression.jl，从数据中搜索既拟合目标又可解释的解析表达式——README 的示例从 100 个点、5 个特征中恢复出 2.5382·cos(x₃) + x₀² − 0.5。它可以 pip/conda 安装（首次导入时装 Julia 依赖），输出 pandas/hall-of-fame 表格，并能导出可微的 JAX 与 PyTorch 版本，还支持「Symbolic Distillation」把神经网络压成解析方程。项目同时新增了一个供编码代理使用的 skill（npx skills add astroautomata/PySR），并附有 Dockerfile/Apptainer 构建方式。

**讨论**: 讨论的一条主线是「如何为复杂度做惩罚并做模型选择」：有人提到自己博士期间找不到合适方法，只好自己实现 MDL，统计学家朋友则建议干脆别对符号模型做选择、改成概率模型；回复指出 PySR 的做法是给每个算子、变量和常量分配代价，还有人推荐 NSGA-II 的帕累托前沿思路，并谈到表达式膨胀导致早熟收敛。另一条主线是「确定性符号回归算法」：两位评论者分别推广自己的 Rust 项目 keplearn 和 JAX 项目 pge-jax，认为遗传/进化类方法有固有缺陷，并对「系数 snapping」是否只适用于物理公式提出疑问。最有分量的是一条严厉批评：PySR 原有代码尚可，但质量控制已经崩坏，examples 目录里多是 AI 生成的「vibeslop」，并以「evolved PRNG」示例为例，指出其周期证书只对最大周期 LFSR 有效、对搜索空间其余部分不成立，且把 360 个相关性取了平均值而非求和，导致完美相关只贡献 1/360 的损失，而文档里的运行结果恰好出现这种完美相关。也有人抱怨 Python 套 Julia 意味着两个解释器、两个 GC、约 200MB 内存开销以及由 JIT 带来的不确定性能。此外有评论问 Julia 部分是否用 JuliaC 编译（答：一条命令即可），以及是否有人拿它做过 n-body 问题。

**值得一读的评论**
- [saithound](https://news.ycombinator.com/item?id=50227137): 详细指控 PySR 的示例是 AI 生成的「vibeslop」，并逐行拆解 evolved PRNG 例子的损失函数为何在结构上只会返回 LFSR、且相关性惩罚被均值化而失效。
- [verdverm](https://news.ycombinator.com/item?id=50227406): 反驳说问题不在 AI，而在仍在用遗传/进化算法做符号回归的人本身，主张已有多个更优的确定性算法。
- [owls-on-wires](https://news.ycombinator.com/item?id=50226393): 介绍自己的 Rust 确定性符号回归引擎 keplearn（为 SRBench 而写），作为 PySR 之外的另一条路线。

## 19. 科技行业之外未见 AI 回报迹象 {#story-19}
*HN 第 49 名 · [apollo.com](https://www.apollo.com/wealth/insights-news/insights/daily-spark/no-signs-of-ai-payoff-outside-the-tech-sector) · 545 分 · 566 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50224463)*
*原标题: No signs of AI payoff outside the tech sector*

这是 Apollo Global Management 的 “Daily Spark” 系列文章，作者为首席经济学家 Torsten Slok，文章用几张图表论证：AI 带来的财务回报几乎全部集中在 Mag 7；Mag 7 的人均营收和利润率持续上升，而 S&P 493 的对应指标基本持平，整体生产率增长也未见起色。文章认为主流企业正把 token 支出从增长引擎重新归类为拖累利润率的成本项，并断言「AI 叙事将由 S&P 493 决定，而非 Mag 7」，理由是商业判断依赖语境、问责、信任与文化，而这些是模型无法承担的。

**讨论**: 最高票的观点借用历史类比：电气化用了几十年才体现在生产率统计中，引用 1987 年 Solow 的名言「你到处都能看到计算机时代，唯独在生产率统计里看不到」；结论是新工厂和新公司从零围绕 AI 设计，才会真正见效，而不是现有企业改造旧流程。另有一派把原因归到技术特性上：软件之所以先受益，是因为有编译器、测试套件这类自动验证关卡，而法律、医疗之外的领域缺乏「这个结果对不对」的判定器，再聪明的模型也无法闭环迭代。反方则质疑文章的数据与结论：有人说 Mag 7 的利润率上升始于 2020 年，可以用疫情红利和大规模裁员解释，不该全部归因于 AI；也有人指出 S&P 500 里近四成是科技或 IT 公司，把「S&P 493」当作非科技部门本身就有问题；还有人认为企业级工具才刚铺开，9 到 24 个月内不可能看到财务效果。几位从业者提供了正面的一手证据：一位小型上市公司的会计负责人说用工具做内部与公开报告，token 花费的 ROI 是最好的一项，审计问题还减少了；医院与医生端的环境记录与病历生成被反复提到已经常态化。还有一种更尖锐的经济学反驳：生产力收益被 AI 供应商以租金形式截留——他们希望你花掉接近全部人力预算去买 token，所以宏观统计上自然看不到增益。较有共识的一点是：无论乐观还是悲观，现在下结论都太早，而「科技行业自己是否真有回报」同样存疑。

## 20. Dream-1 {#story-20}

Dream Labs 的研究博客介绍了 Dream-1——一个以公开 API 形式提供的「World Action Model」操作策略：你把一台双臂、平行夹爪机器人对准它，公司声称无需微调、也不需要针对该机器人的演示数据即可工作，因为它预测的是末端执行器位姿与视频，而不是关节角度。该公司同时结束隐身状态，带着 9000 万美元种子轮融资亮相，模型定价为每小时 3 美元（Dream-1-flash 为每小时 2 美元，约合每 1.6 秒的动作块 0.0013 美元），并为效果不达标的机器人提供微调即服务——对相近本体只需 5 分钟数据，对 Dexmate 灵巧手这类差异较大的本体则需要 77–98 分钟。文中引用 Robocurve 的一项独立评测，称 Dream-1 处于新的帕累托前沿，在单次尝试成本比 Gemini 4 Argon 低 16 倍的情况下击败了 Opus 5.5 和 Gemini 4 Argon。
