## 1. Beam：Reflection 的 501B 开放权重模型 {#story-1}
*HN 第 1 名 · [reflection.ai](https://reflection.ai/blog/introducing-beam) · 406 分 · 124 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49969183)*
*原标题: Beam: Reflection's 501B open-weight model*

Reflection AI 为其首个开放权重模型 Beam 发布的发布帖：一个稀疏 Mixture-of-Experts（专家混合）LLM，总参数 501B、激活参数 23B，在 23.8T tokens 上预训练，并在 10.5K 张 NVIDIA GB300 GPU 上用四周时间、100M+ 次 rollout 进行了 RL 训练，使用了约 1.3B 个沙箱，并发沙箱数最高达 170K。该帖声称其编码/agentic 性能可与 GLM 5.2 竞争，并接近 Qwen 3.8-Max，同时相比同类推理模型使用的推理算力少 3–4 倍。目前尚无权重：模型正处于最后的 red-teaming（红队测试）阶段，权重、技术报告、模型卡和开发者工件都承诺「本月晚些时候」发布，并开放早期访问的报名。

**讨论**: 最主要的反应是「Talk is cheap, show me the weights（空谈无益，把权重拿出来）」——一篇没有权重、没有 API、也没有技术细节的公告被广泛认为为时过早，多位评论者将 Beam 与 DeepSeek V4.1 Flash 和 GLM 5.3 相比，认为它不如它们，指出它更大、运行成本更高，且几乎在每项基准上都更弱。最有力的证据来自一位评论者，他贴出了一份并排规格对比表（总参数 501B 对 552B，激活参数 23B 对 8–16B，预训练 tokens 28T 对 45T，Apache 2.0 对 MIT，不支持视觉，权重「本月」发布 对 发布当天即可用）。另一派则为其辩护，认为这是一次正当的西方入场——首个模型很少能击败现有领先者，而且对于合同中排除中国模型的买家来说，一家位于美国的实验室具有明确价值——而其他人反驳说，新入场者至少应在一个有意义的维度上胜出。两条支线讨论也引发了审视：一条纠正了文章的说法，即其 180×90 世界地图泛化演示只是几天前的成果（评论者将这一谜题追溯到 2025 年 8 月的一篇 LessWrong 帖子）；另一条讨论训练数据从何而来，有人声称真正的护城河是专有的 RL 环境和由承包商构建的合成任务，而非抓取的网络文本。评论者还指出，基准图表省略了 GLM 5.3 和 DeepSeek V4.1 Flash，它们只出现在表格中；并指出 Reflection 以约 $25B 估值筹集了超过 $4B（据称投资方包括 Nvidia、Eric Schmidt 和 Sequoia），却尚未发布过任何产品。

## 2. Example.com 刚刚推出了数十年来最大的一次改版 {#story-2}
*HN 第 2 名 · [debugbear.com](https://www.debugbear.com/blog/example-dot-com-redesign-history) · 181 分 · 103 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49971921)*
*原标题: Example.com just launched the biggest redesign in decades*

DebugBear 的一篇博客文章，梳理了 example.com 这个由 IANA 保留的文档域名的视觉与基础设施演变史，从 2002 年 1 月 20 日最早的 Wayback 存档一直讲到标注日期为 2026 年 9 月 28 日的一次改版。此次改动新增了多语言提示（阿拉伯语、中文、法语、俄语、西班牙语），以及一个由 JS 注入的 SVG 书本图标；每种语言的文案都说明它并非一项服务，不应被依赖用于测试或监控。文章逐一回顾了各个里程碑——2002 年运行在 Apache 1.3.22 上的表格布局、2003 年的 RFC 2606 链接、2010 年的 example.edu、2013 年迁往 EdgeCast CDN、2025 年 1 月 Server 响应头的消失（在 Edgio 破产、Akamai 接手合同之后）、2025 年 12 月的 Cloudflare 迁移，以及 2026 年 6 月用空的 `link rel=icon href=data:,` 来抑制 /favicon.ico 请求的小技巧——并引用了 IANA 的说法：拆分出 JS 主要是为了给那些从不抓取它的、以自动化为主的流量节省带宽。

**讨论**: 许多评论者抓住 Hyrum 定律不放：人们长期以来把 example.com 当作连通性和强制门户（captive portal）检测点，而这次改版会悄悄破坏测试、爬虫和手动敲出的 netcat 请求。一个反复出现的抱怨是：即便轮播式翻译已被撤下，本地化页面仍然依赖 JavaScript；thaumasiotes 认为，此举的目的就是尽可能把内容塞进一个外部 JS 文件，而不是真有哪里需要 JS。一位自称来自 IANA 的评论者（kijeda）表示，轮播翻译版本在某个周一上线，又在那个周五根据无障碍方面的反馈做了修改，所以现在所有译文会一次性渲染出来，浏览器首选语言被提到最前面——后来的评论通过观察证实了这一说法。还有一场关于 IANA 使用 Cloudflare 是否有什么不对的支线争论，kijeda 回应说 Cloudflare 只是多年来用过的若干 CDN 中最新的一家，并反问用它有什么问题；其他人则指出这只是个静态页面，缓存能省带宽。还有几个大帖子是跑题：neverssl.com 奇怪的 HTTPS/子域名配置以及其他不启用 HSTS 的端点，以及关于文章本身读起来是否像 AI 生成的争论——一位评论者称文章在 SVG 插入这一点上就是错的，另一位则贴出了实际的 `s.js` 源码，表明它确实同时注入了译文和 SVG。

**值得一读的评论**
- [kijeda](https://news.ycombinator.com/item?id=49973860): 一位自称来自 IANA 的评论者说，轮播翻译设计在某个周一上线，又在那个周五被替换掉，原因是无障碍方面的反馈，这解释了为什么现在所有语言会一起出现。
- [ajcp](https://news.ycombinator.com/item?id=49972312): 贴出完整的 `s.js` 源码，揭示页面究竟如何注入翻译后的 `<p>` 元素和 SVG 图标，直接反驳了文章凭空编造此事的说法。
- [creatonez](https://news.ycombinator.com/item?id=49974986): 量化了体积变化：页面为 2540 字节（是最初的 4.5 倍），但经 brotli 压缩后为 1713 字节，而纯 HTML 请求只有 334 字节，因此大多数自动化流量现在拿到的载荷约为过去的一半。

## 3. 在旧金山任意两点之间找到最平坦的路线 {#story-3}
*HN 第 3 名 · [flattensf.com](https://flattensf.com/) · 167 分 · 57 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49971230)*
*原标题: Find the flattest route between any two points in SF*

flattensf.com 是一个面向旧金山的浏览器端路线规划工具，它在约 16 万个街道段上计算最平坦路径，使用 USGS 的 1 米 lidar 高程数据以及 Overture/OpenStreetMap 街道图。一个滑块覆盖了距离与累计爬升之间的完整权衡，从最短路径到值得步行的最平坦路线（爬升 1 英尺按步行 200 英尺计价）。爬升指累计增益，而非两端点之间的净高程变化；楼梯允许步行通行、骑行时排除；地点搜索为离线运行，使用内嵌在页面中的数据。

**讨论**: 评论者大多称赞了实时高程剖面图和距离与爬升的滑块，但整个讨论串变成了一场找 bug 的围猎：多位骑行者报告，在滑块调到最平坦的设置时，该工具仍会把他们带上非常陡的街道。一位骑货运电动自行车的评论者给出了一个可复现的 Mission Bernal 到 Diamond Heights 的行程，工具为了节省约 1 英尺的爬升，选择了一条坡度 22.7% 的路线；作者承认目前的目标函数只在距离与总爬升之间做权衡，坡度虽有报告但未纳入优化。另一位骑行者关于 Outer Richmond 的 Cabrillo St 的报告，让作者发现了一个真正的解析器 bug：该街道的 Slow Streets「destination-only」标签被读取为禁止行人通行，导致这条街完全不可见，作者已修复并部署。作者还承认，在被告知该路由器会心安理得地把骑行者导向 Geary 和 Divisadero 之后，它目前还不了解自行车道。另一个子讨论串指责该项目是 LLM 生成的垃圾，理由是仓库中把 Claude Code 列为贡献者；一位资深路径引擎作者反驳说，这类解析器 bug 是把交通规则、杂乱的地图数据和用户偏好结合起来时固有的问题；还有几位评论者列出了替代方案：bikehopper.org（由一位 HN 评论者维护，覆盖旧金山的 1 米 DTM）、Valhalla，以及 OpenTripPlanner 的距离/时间/坡度三角形。

**值得一读的评论**
- [almstimplmntd](https://news.ycombinator.com/item?id=49971926): 作者诊断并修复了一个具体的解析器 bug：Cabrillo St 是一条 Slow Street，其「destination-only」标签被读取为禁止行人通行，因此路由器完全看不到这条街。
- [laurencerowe](https://news.ycombinator.com/item?id=49973119): 一位骑货运电动自行车的用户给出了一个可复现的路线：工具为了节省约 1 英尺的爬升，选择了 22.7% 的坡度而非 12% 的备选路线，并将其与 Google Maps 中出现的同一问题联系起来。
- [mschuster91](https://news.ycombinator.com/item?id=49975070): 认为该代码库看起来是 LLM 生成的，指出 README 的风格以及 Claude Code 被列为贡献者，同时认同批评的措辞过于严厉。

## 4. 复活 iChat 音频和视频会议 {#story-4}
*HN 第 4 名 · [blog.pipetogrep.org](https://blog.pipetogrep.org/2026/09/11/resurrecting-ichat-audio-and-video-conferencing/) · 33 分 · 6 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49973878)*
*原标题: Resurrecting iChat Audio and Video Conferencing*

Chris Jones 的一篇博文，描述他和一位朋友如何通过重新实现 Apple 已停止服务的 SNATMAP 服务器，让 iChat AV 音频／视频通话在 OS X Leopard 和 Snow Leopard 上重新可用。旧的配置之所以失效，是因为 iChat 会从 configuration.apple.com 的 snatmap.txt 获取自己的公网 IP，而该地址如今会重定向到旧版 OS X TLS 无法协商的 HTTPS，同时 Apple 的 snatmap.apple.com:5678 服务器也不再响应——于是两台 Mac 只能退回到交换私有 LAN IP。他利用抓包、iChat 的 -errorLogLevel 7 调试模式和 LLM 的帮助，逆向出了 UDP/5678 协议（16 字节的请求包和响应包，携带一个 nonce 以及主叫方的外部 IP 和端口），写了一个 Python 服务器，现在运行着一个公开的实例；用户只需把「157.230.2.213 configuration.apple.com」加入 /etc/hosts。他在一个 Proxmox/KVM 实验环境里用两台 OpenWrt NAT 虚拟机和一台 Logitech C920 摄像头做了测试。

**讨论**: 讨论串分成了怀旧派和一场关于 FaceTime 可用性的争论：一位评论者说现代的 FaceTime 版本是「先锋艺术实验」，最近通话／联系人界面的改版导致了误拨电话；另一位则坚称 FaceTime 几乎过于简单（预览、最近联系人、绿色的 New call 按钮），是为「奶奶打来的电话」而优化的——第三位接着指出，如果一个只会基本操作的用户连 16x16 的未接来电下拉菜单都找不到，那这本身就是令人困惑的设计。在技术方面，一位评论者把 SNATMAP 定位为 Apple 在 2003 年前后对 STUN（RFC 3489）的等价实现：从外部服务器得知自己的公网 IP 和端口，在聊天中交换它们，然后双方同时打洞穿透 NAT——这正是保留端口的 NAT 至关重要的原因。这位评论者警告说，运营商级 NAT（在移动网络和部分 ISP 中很常见）会为每个目的地分配一个新端口，因此即使做了 hosts 修复，通话仍会失败；他还指出，与现代 WebRTC 不同，iChat 没有 TURN 中继作为回退。原作作者的成果得到了热烈反响，一位评论者回忆起那台过度设计的 iSight 摄像头，通过转接器一直能用，直到 M1 取消了它的驱动。

**值得一读的评论**
- [mulanroo](https://news.ycombinator.com/item?id=49974410): 解释了 SNATMAP 是 Apple 在 2003 年对 STUN（RFC 3489）的前身，为什么需要保留端口的 NAT，并指出 CGNAT 很可能是剩余故障的原因，因为 iChat 没有 TURN 回退。
- [jd3](https://news.ycombinator.com/item?id=49974950): 第一手说明：iSight 摄像头在 Intel Mac 上通过多个转接器一直可用，直到 Apple 随 M1 移除了它的驱动。
- [penskymaterial](https://news.ycombinator.com/item?id=49974588): 认为这次复活是一次时间穿越，回到视频会议真正好用的年代，并与越来越令人困惑的 FaceTime 界面形成对比。

## 5. Opus 5.5 agent 发现两种室温磁性半导体候选材料 {#story-5}
*HN 第 5 名 · [vals.ai](https://www.vals.ai/blogs/room-temperature-magnetic-semiconductors) · 303 分 · 198 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49970667)*
*原标题: Opus 5.5 agents discover two room-temperature magnetic semiconductor candidates*

vals.ai 博客上的一篇文章（作者署名 spicylemonade）报告称，一队 Claude Opus 5.5 agent 使用密度泛函理论（PBE+U 与 HSE06）提出了两种 Luttinger 补偿反铁磁半导体的候选材料——净磁矩为零，但能带边缘按自旋分离。第一种是从未合成过的 YBaMnFeO₅，预计带隙为 2.35 eV，空穴自旋窗口为 1.0 eV，电子自旋窗口为 1.4 eV，但所需的 Mn/Fe 棋盘式有序在约 950 K 时瓦解，因此标准的 900–1300 °C 合成很可能会将其打乱。第二种是 KV[Cr(CN)₆]（普鲁士蓝的近亲，1999 年首次制得），预计带隙约为 2.1 eV，自旋窗口为 2.6/1.6 eV，1999 年粉末样品中测得的有序温度为 376 K——但唯一的样品含结合水并表现出 0.125 μB 的残余磁矩，而且两种模拟方法对空穴窗口在含水后是否仍然存在存在分歧。完整的输入、输出与注意事项都在 GitHub 上（compensated-magnet-ledger）。

## 6. Dust：无需反向传播的 Transformer 预训练 {#story-6}
*HN 第 6 名 · [qlabs.sh](https://qlabs.sh/research/dust) · 153 分 · 36 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49970871)*
*原标题: Dust: Pretraining Transformers Without Backpropagation*

这是一篇来自 qlabs.sh 的研究文章，介绍了 Dust——一种用于预训练 Transformer 语言模型的零阶（无导数）训练方法。Dust 不扰动权重，而是在每个 token 上对每个线性层的输出独立加入高斯噪声——即节点扰动——因此每个 token 都相当于一个独立的虚拟种群成员，在一次前向传播中完成评估，并用奖励加权的噪声构成梯度估计。作者声称，随着种群规模增大，Dust 的效果接近甚至超过反向传播；从 100 万 token 起（通过外推），它比权重空间 ES 方法 EGGROLL 的 Transformer 实现大约高效 10^3–10^4 倍；并且更大的模型在种群效率上更高而非更低——一个 2.43 亿参数的模型在大多数种群规模下都优于一个比它小 120 倍的模型，这种优势在多达 10 亿 token 时依然成立。他们承认，它目前的计算效率还不足以取代反向传播。

**讨论**: 主流反应是怀疑无导数方法究竟能否派上用场：得票最高的评论者认为，神经网络的目标函数是平滑的，梯度计算成本低，而且随着参数数量增长越来越有用，梯度法与无导数 Lipschitz 优化之间的复杂度差距最近已被证明，而像 Muon 这样基于梯度的结构优化器才是更值得押注的方向。另一些人则攻击其「苦涩的教训」式论述框架，指出论文从未讨论凸性，而 Dust 的平滑化加上一阶方法很可能会抹掉它的优势，不过他们也承认它确实比此前的零阶工作扩展性更好。一个并行的讨论串在辩论并行性：一位评论者说反向传播本身就已经只是矩阵乘法，并指出异步神经预测编码——它在某种条件下会收敛到反向传播，且无需全局协调；另一位则反驳说，在 GPU 上协调几乎是免费的，而大脑缺乏反向传播是其布线约束的结果，而不是一个值得模仿的目标。有几个人提出了混合方案——用 Dust 生成教学目标，或微调一个已经过反向传播的检查点——还有人指出 Dust 在持续学习上内存占用更小，尽管它并不能解决灾难性遗忘。除少数人之外（包括一位直接将其斥为毫无新意的蒙特卡洛梯度估计的评论者），整个讨论串并不相信 Dust 在效率上能胜过反向传播，但对虚拟种群这一技巧以及「模型越大种群效率越高」这一结果颇有兴趣。

**值得一读的评论**
- [blt](https://news.ycombinator.com/item?id=49974026): 论证无导数方法在结构上注定失败：目标函数是平滑的，随着参数量增长梯度更有价值，而已被证明的复杂度差距有利于一阶方法——Muon 是更好的方向。
- [vatsachak](https://news.ycombinator.com/item?id=49971640): 指出反向传播本身就是高度并行的，并指出神经预测编码是一种真正异步的替代方案，其梯度在某种范围内可证明收敛到反向传播，同时怀疑任何替代方案在没有专用硬件的情况下能否胜出。

## 16. 临时测试 {#story-16}

**值得一读的评论**
- [simonw](https://news.ycombinator.com/item?id=49973136): simonw 说他近期常用这一模式做 API 设计：agent 让「在其上构建多种东西」的原型成本几乎归零，可以在定稿前用五种不同方式试炼一个 API 设计。
