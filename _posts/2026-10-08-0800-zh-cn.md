## 1. 「Math 2.0」需要更全面地衡量数学进步 {#story-1}
*HN 第 1 名 · [mathstodon.xyz](https://mathstodon.xyz/@tao/117395269325940185) · 175 分 · 102 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50002008)*
*原标题: “Math 2.0” will need to value mathematical progress more holistically*

## 2. 离网生活：Hundred Rabbits {#story-2}
*HN 第 3 名 · [100r.ca](https://100r.ca/site/home.html) · 144 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49970767)*
*原标题: Living off-grid: Hundred Rabbits*

链接页面是 Hundred Rabbits 的项目日志，这对离网生活二人组 Devine Lu Linvega 和 Rekka Bellum（又称 Rek）居住在加拿大不列颠哥伦比亚省沿海的帆船 Pino 上，并在船上生活和工作。日志条目混合了船只维护（重建厨房橱柜、安装 100L 水箱、更换固定索具和船首三角帆、太阳能烹饪实验）、阅读书单以及软件发布：Uxn 16 位虚拟机及其汇编器 Uxntal、用于音乐的 Orca esolang、他们卡牌游戏 Donsol 十年后的重新发布、为摆脱 OpenOffice 而自写的 Nebu 电子表格、Rabbit Waves 漫画，以及《No Bears None》一书——一本大幅扩充的航海日志，记录他们从 Victoria 到 Sitka 的航行，包含 100 幅绘图、17 个章节和 13 份食谱。贯穿始终的主题是 permacomputing 与软件存档：极简、可修复、无依赖的工具，为在不可靠的电力和时断时续的网络下生存而打造。

**讨论**: 整个讨论串总体上是赞赏的——几位长期关注者描述自己在这个网站上一头扎进各种兔子洞，还有人称赞那篇把修补一顶旧帽子与开源软件相类比的日志。最尖锐的交锋在于离网生活是否是一种唯我论、是否是对改善所有人所处社会这一责任的放弃（kennywinker），有人回复反驳说，离网意味着抛弃电网，而不是抛弃社会，而且他们认识的大多数离网人士都以社区为导向（yawpitch）。一篇对某次长篇访谈的详细总结（contingencies）列出了诸如「在船上当穷人会教你为什么 SaaS 很糟糕」和「老旧硬件会教你，我们所有人都拥有远超自己所需的东西」这样的教训，这引来了反驳，认为云功能对另外 95% 的用户来说是合适的；又有反反驳说，挣扎中的用户占全世界的 50% 以上，而不是 5%。其他人则指出了一些具体的产物——自写的 Nebu 电子表格、Permacomputing 101（raptorraver）和 Orca（math_eaton）。一个关于该网站看起来像日语的子讨论被纠正：这两人是加拿大人，在日本相识，并以一个动漫角色的名字为他们的船命名。

## 3. 一个快 100 倍*的 homebrew 替代品 {#story-3}
*HN 第 4 名 · [github.com](https://github.com/zerobrewhq/zerobrew) · 58 分 · 31 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50001580)*
*原标题: A 100x faster* alternative to homebrew*

这是 zerobrewhq/zerobrew 的 GitHub 项目页/README,一个打算给 Homebrew 生态做「uv 风格」重写客户端的工具,支持 macOS 与 Linux,提供 zb install/bundle/upgrade 等命令。作者宣称同一个包和依赖,冷装中位数快 5.3 倍、热装快 56 倍,100 个包里 24 个热装快 100 倍以上(标题的星号即指此);测试环境为 2026-10-08、zerobrew 0.3.5 开发版对 Homebrew 7.0.8、macOS 26.6.2、M3 Pro 18GB、约 318 Mbit/s。作者强调它仍下载 Homebrew 构建农场里同样的 bottle,速度来自安装环节——in-process 重定位、内容寻址存储与 APFS clonefile——而非重新编译;并特别批评 nanobrew 的基准测的是「已安装后的提前退出」而非真正安装。项目自称实验性、双许可 Apache 2.0/MIT,建议与 Homebrew 并存。

**讨论**: 讨论最集中的是信任问题:有人主张包管理器是恶意软件进入系统的关键入口,Homebrew 维护者公开、有主见、多年积累的信任,而新项目「信任从零开始」,且看起来缺乏人类把关、像 LLM 产物;也有人回击 Homebrew 自身的问题(如淘汰旧系统版本、Intel Mac 支持不佳)。实测经验分歧明显:一位用户说用了一阵子后因 node 等基础包时常失败而退回 Homebrew,亦有人指出 README 是 LLM 写的、基准里混入了不相关的热装对比。争论的另一焦点是热装数字的意义——多数日常安装缓存是空的,冷装才更重要,而且瓶颈多在下载;作者一方则以内容寻址存储来解释安装阶段的开销才是差异所在。还有人问为何不直接给 brew 提 PR,回答是上游维护成本、架构整合与迁移回退方案门槛很高,且新项目更容易出名;有人补充 Homebrew 的 Rust 重写只是已被归档的实验。

**值得一读的评论**
- [meghanto](https://news.ycombinator.com/item?id=50002541): 第一手使用反馈:作者试用一段时间后因 node 等基础包时常失败,最终卸载并退回原版 Homebrew。
- [gavinsyancey](https://news.ycombinator.com/item?id=50002413): 解释为何不直接向 Homebrew 提 PR:上游要承担长期维护,需架构整合、完善文档与迁移回退方案,而新项目更容易博取 star。
- [BugsJustFindMe](https://news.ycombinator.com/item?id=50002153): 对热装基准意义的尖锐反驳:除非你反复在同机安装同一东西,否则热装加速基本没有意义。

## 4. Margaret Hamilton 逝世 {#story-4}
*HN 第 6 名 · [news.mit.edu](https://news.mit.edu/2026/margaret-hamilton-computing-pioneer-dies-1007) · 1,256 分 · 138 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49998895)*
*原标题: Margaret Hamilton has died*

MIT News 发布的 Margaret Hamilton 讣告，她于 9 月 30 日去世，享年 90 岁。她于 1965 年加入 MIT 的 Instrumentation Lab，是 Apollo 计划的第一位程序员，并逐步领导了 400 多人的团队，为指令舱和登月舱编写机载飞行软件，推广了「软件工程」这一术语，并于 2016 年获得总统自由勋章。文章将 Apollo 11 登月成功归功于她那种防御性、由优先级驱动的软件——当时制导计算机因过载触发了 1202 警报；文中还提到她后来创办的公司 Higher Order Software（1976）和 Hamilton Technologies（USL）。

**讨论**: 整个讨论串以悼念为主——1969 年她站在成堆打印清单旁的照片、她的乐高小人、呼吁网站挂黑条——此外还有 GitHub 上的 Apollo 代码链接和 Computer History Museum 的口述历史。少数人强烈反驳这种英雄叙事：他们引用 Don Eyles 的书，认为 Hamilton 直到 1970 年初、即 Apollo 11 之后才在登月舱软件中获得领导角色，异步软件和优先级调度是由 Hal Laning 首创的，而她却因此获得了荣誉；其他人则指责这些评论者（其中一些人被举报或被删号）是在以厌女方式贬低她的贡献，这场交锋最终演变成关于此类批评是否公正的争论。一个反复出现的辩护性技术论点是：AGC 只有 4KB RAM / 16KB ROM 和约 0.043 MIPS，因此优先级调度器确实非常难做。几个较小的子讨论串纠正了那张著名照片——它展示的是模拟器打印输出而非 AGC 源代码；还称赞她创造了「软件工程」一词，并就是否该词如今被过度套用到 Web 开发工作上展开争论。

**值得一读的评论**
- [Jach](https://news.ycombinator.com/item?id=50000913): 引用 Don Eyles 的 Apollo 回忆录中的一条脚注，声称 Hamilton 对登月舱软件的领导始于 1970 年初、即在主要目标达成之后，而异步软件和优先级调度是由 Hal Laning 首创的。
- [jshier](https://news.ycombinator.com/item?id=50000528): 纠正了那张标志性照片：她身旁的是 Apollo 模拟器运行后打印出来的输出，而非实际的 AGC 或登月舱源代码。
- [catskull](https://news.ycombinator.com/item?id=50000350): 一位评论者称，他找到并重新发布了那篇冷门教科书访谈——Hamilton 在其中首次使用了「软件工程」这一说法。

**讨论**: 讨论区分为不屑一顾和认真参与两派。几位评论者称这篇文章是把表层级的 FP 术语包装成了一篇长文——有人打趣说 LLM 很擅长把琐碎的想法变成晦涩的博客文章，不过也有人指出这篇文章明显是真人写的，拿 LLM 说事是在钓鱼；还有人表示用范畴论来包装恰好对应了函数式编程令人讨厌的那一面。实践者则从机制层面予以反驳：避免热循环中的分支才是真正的要点，这又引出一个子讨论——循环算不算一种分支（根据结构化编程定理和一个 godbolt 示例，循环包含一次比较并跳转）。一个反复出现的批评是：文章既没有给出基准测试也没有引用文献，而现代编译器/运行时早已自动完成这种变换——不过也有人指出这种变换很容易被破坏（JVM 复杂的 get() 调用；C/C++ 中 char* 的别名问题）。一位持异议者主张相反的立场：把条件判断往下沉，好让顶层控制流保持规整，并且把「分发」（循环/分桶）与「决策」分开。

## 17. 如果有人试图对已经被热补丁过的函数再进行热补丁 {#story-17}
*HN 第 27 名 · [devblogs.microsoft.com](https://devblogs.microsoft.com/oldnewthing/20261005-00/?p=112755/) · 55 分 · 25 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49978315)*
*原标题: If somebody tries to hot-patch an already-hot-patched function*

这是 Raymond Chen 在 Microsoft 的 Old New Thing 博客上发表的一篇文章，梳理了 Windows 的热补丁机制：更新代码会利用二进制文件中预留的空间，在内存中重写某个函数，从而让 Windows Update 无需重启即可应用安全修复。它的适用对象是 Windows Server，以及近来加入的 Windows 11 Enterprise；只有 Windows Update 有权使用这些预留空间。Chen 主张，出现第二个补丁程序就意味着哪里出了问题：如果热补丁代码发现有来路不明的补丁，它会把该文件标记为不可热补丁并强制重启；而如果某个函数在预扫描通过之后才被打上补丁，就会产生竞态，补丁程序可能在只应用了一半的状态下卡住，且没有可靠的 rollback。他把占用热补丁空间的应用比作把车停在消防通道上。

**讨论**: 最尖锐的分歧在于：Microsoft 自己就发布了 Detours 库，却把 hooking 称作「rogue」或未获授权。一方认为，代码的所有者最有资格判断安全性；另一方则回应说，只要你能保证没有线程正处在指令执行中途，hooking 就是安全的，或者说 Microsoft 自己在 Windows 内部也用 Detours。有评论者指出，用户态 hook 是按进程、写时复制（copy-on-write）的，这就引出一个悬而未决的问题：某个进程的 hook 是否会在系统范围内禁用热补丁。一个有力的反驳观点认为，一个称职的热补丁库会以原子方式打补丁——挂起线程或使用原子操作——因此 Chen 所描述的那种竞态本不应存在。实践者指出，层叠的 detour 是家常便饭（Steam 叠加层、OBS 游戏捕获可以同时作用于 Direct3D 之上），而 OBS 也展示了代价：在没有真正同步的情况下，最后打的 detour 往往胜出。还有几个人指出了那个未被回答的情形：连续两次 Windows Update 给同一个函数打补丁，而这纯粹是 Microsoft 自己的问题。

**值得一读的评论**
- [drdexebtjl](https://news.ycombinator.com/item?id=50000337): 质疑：既然 Microsoft 自己发布 Detours，把 hooking 定性为未获授权是否合理；并追问 Windows Update 修改的是共享的原始页面，还是各进程的写时复制页面，以及某个进程的 hook 是否会在系统范围内禁用热补丁。
- [ack_complete](https://news.ycombinator.com/item?id=50001645): 第一手证据表明 Microsoft 在 Windows 内部使用 Detours：AutoSR 功能让 dxgi.dll 在进程内 detour user32.dll 的调用，而且它在能处理启用了 PAC 的函数序言之前，会导致 Windows 11 ARM64 崩溃。
- [dataflow](https://news.ycombinator.com/item?id=50001934): 主张一个称职的热补丁库会以原子方式应用补丁，通过挂起线程或使用原子操作，因此并不存在文章所描述的那种竞态。

*原标题: Why were Victorian elites so effective?*

一篇 Works in Progress 的文章，作者主张：英国的维多利亚统治阶层治理着历史上最大的帝国，却起得晚、酗酒严重、热衷派对——而他们的精英学校出人意料地「进步」：Eton 位于公学等级体系的顶端（19 世纪约 30% 的内阁大臣和 40% 的首相出身于老伊顿人），拉丁语和希腊语占去 50–80% 的教学课时，体育运动每周占用 10–20 小时，学生主要通过级长（prefects）自行管理，男孩从八岁起就寄宿离家。其论点是：对软技能、团队建设和精英内部人脉网络的全心投入——而非 STEM、冷水浴和清晨五点起床——可能确实行之有效；同时也承认「正统观点」，即这种繁荣是以牺牲殖民地人民和工人阶级为代价的。

**值得一读的评论**

## 19. Google Playground：创建并游玩自定义游戏 {#story-19}
*HN 第 31 名 · [blog.google](https://blog.google/innovation-and-ai/technology/ai/playground-experimental-gaming-platform/) · 140 分 · 212 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49991823)*
