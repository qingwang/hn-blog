## 1. 我最喜欢的 PowerMac 是一台 Nintendo Wii {#story-1}
*HN 第 1 名 · [virtuallyfun.com](https://virtuallyfun.com/2026/10/29/my-favourite-powermac-is-a-nintendo-wii/) · 115 分 · 24 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50307190)*
*原标题: My favourite PowerMac is a Nintendo Wii*

这是 virtuallyfun.com 上的一篇客座文章，作者是 Rairii，讲的是把经典 Mac OS 移植到使用 ArtX 系列芯片的 PowerPC 主机上，也就是 GameCube，以及搭载 Vegas/Bollywood 芯片的 Wii，最终还会涉及 Wii U。项目于 2025-06-22 从 fork 上游 OpenBIOS 开始，作者明确表示没有使用任何 LLM 或编码代理；这是自 CHRP 克隆机时代之后，第一次有人在 Apple 之外让经典 Mac OS 在全新硬件上启动到桌面。文章详细记录了各种修补工作：Trampoline 启动加载器对物理地址布局的假设、把 0x0100_0000 映射到 0xE000_0000 的 MMIO 映射编造、伪造的 Mac99 电源管理节点、把 Flipper 中断控制器移植到内核驱动、SuperMario m68k 代码的修补（包括一个因复制粘贴错误导致的串口 2 无限循环），以及一个伪 SCSI 驱动和光驱所要求的 scatter-gather 读取支持。

**讨论**: 讨论帖很少谈移植本身，主要转向对 Wii 的怀念。大家普遍认为 Wii 是游戏主机的巅峰：游戏仍在光盘上发售，没有烦人的补丁和微交易，而且几乎人人都玩过它。几位评论者指出，就算不完全认同这种怀旧，也有客观理由支持。也有异见：一位评论者说自家就是没有 Wii 的那一户，另一位认为移动游戏才是真正把游戏带给了更多人。与文章相关的部分，有人问能不能反过来做，把 PowerMac 改成 Wii。回答是：由于 Wii 有两个处理器和一套自制 GPU，这条路很麻烦；更现实的路线是在 Dolphin 加上 KVM_PR 式的虚拟化上做。另有人提到原始 Xbox 360 开发套件本身就是一台 PowerMac G5。另有子讨论在争论现代 macOS 是否还留有经典 Mac OS 代码，多人指出，Carbon 菜单 API 一直用到 macOS 14 才移除。

**值得一读的评论**
- [my123](https://news.ycombinator.com/item?id=50309174): 菜单在 macOS 14 才从 Carbon 上移走，所以现在调用 Carbon 菜单 API 会返回一条 AppKit 报错，并附有 Apple 发布说明的链接。
- [spijdar](https://news.ycombinator.com/item?id=50308131): 解释了为什么把 PowerMac 变成 Wii 不现实：GPU 块并不对应任何 ATI/AMD 显卡，还建议结合 Dolphin 和 KVM_PR，以接近原生速度虚拟化 CPU。
- [RandallBrown](https://news.ycombinator.com/item?id=50309023): 指出与此相关的历史：原始 Xbox 360 开发套件（Alpha Xenon）就是一台 PowerMac G5。

## 2. Northflank 遭入侵 {#story-2}
*HN 第 2 名 · [status.northflank.com](https://status.northflank.com) · 243 分 · 155 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50305025)*
*原标题: Northflank Breached*

Northflank 对其状态页的实时更新，记录了 2026 年 10 月 30 日一起影响其托管 PaaS 平台的安全事件：11:44 UTC 工程师复盘告警，12:02 与 13:05 部署网络策略补丁，13:00 请 Wiz CIRT 支援，13:40 发出第一条“立即轮换环境变量”的告警。到 13:58 公司称认定“所有环境变量都已被解密”，15:12 为所有用户启用 Postgres 与 MongoDB 密钥轮换，并称有多名用户确认其 AI key 已被盗用；19:28 的最新更新仍建议用户假设 workloads、secret group 与 global secret 中的全部凭据均已泄露，立即轮换并关闭 addon 的公网暴露。文末只剩一行“日志与指标——重大故障”。

**讨论**: 讨论很快从这一起事件扩展到一个月内的连环事故：PingCAP/TiDB、Fireworks AI、Zeabur、OpenCode Console、Railway 和 Northflank，有人据此断言 AI 加速的攻击者时代已经到来，基础设施创业公司将被迫回流到 AWS/Azure/GCP。反驳的一方追问超大规模云是否真的更安全——Azure 近期才刚出过跨租户问题——但多数人承认，这些大厂有数十亿美元营收带来的责任压力、专职安全团队，更重要的是“出事时不止你一家”的背锅效应；有评论者讲述自家产品在 AWS 故障时零客户投诉的经历。技术侧最尖锐的一条解释来自一名评论者：PaaS 的卖点就是让用户和 agent 能在控制台里回显环境变量，这一产品需求本身就意味着管理面被攻破后可以冒充用户读取明文。另一条线索争论个人是否该自建：有人称现在有 AI 加持，把一台 VPS 加固比以往容易，也有人指出廉价 VPS 面板被攻破同样会连锅端，且海量未打补丁的自建实例反而是 LLM 自动化扫描的富矿。还有人讨论 BYOC 是否能隔离此类风险，以及对供应商做安全尽调时实际能问到什么。

**值得一读的评论**
- [btown](https://news.ycombinator.com/item?id=50305985): 指出 PaaS 的产品需求（用户和 agent 必须能在 UI/CLI 里回读环境变量）本身就让「管理面被攻破＝凭据泄露」几乎不可避免，静态加密和重新加密都挡不住冒读。
- [jonathaneunice](https://news.ycombinator.com/item?id=50309243): 列举自 9 月以来遭到快速攻击的多家多租户厂商——PingCAP/TiDB、Fireworks AI、Zeabur、OpenCode Console、Railway、Northflank——并主张团队应把凭据轮换、诱饵密钥、DFIR 待命、爆炸半径最小化当成战备。
- [macNchz](https://news.ycombinator.com/item?id=50306672): 给出风险对照：小团队用初创 PaaS 更可能栽在平台层入侵，而直接上超大规模云则要面对大量极易误配的「地雷」，尤其在有 AI 自信地给出错误建议的时候。

## 3. Cursor Marketplace 上 VS Code 版 Claude Code 扩展中的后门 {#story-3}
*HN 第 3 名 · [phorion.io](https://phorion.io/blog/offical-claude-code-vsx-compromise/) · 579 分 · 401 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50300683)*
*原标题: Backdoor in Claude Code for VS Code extension on the Cursor Marketplace*

Phorion 的文章分析了一个经过篡改的 VS Code 版 Claude Code 打包文件（版本 2.1.313），它通过 Cursor 的扩展市场分发。该文件在 extension.js 前面插入了一个 IIFE，在加载时执行，并植入一个持久化的 SSH 后门。它会向 ~/.ssh/authorized_keys 追加一个攻击者的 Ed25519 公钥，注释为 svc-telemetry，同时把对应的私钥写入临时目录下的 .stk_* 文件，并建立一条分离的反向隧道（-R *:0:localhost:22，使用 autossh，60 秒重试）连接到 134.209.82.225。它通过多种方式持久化：在 macOS 上伪装成 com.apple.sysmond.plist 的 LaunchAgent，在 Linux 上使用 cron @reboot，在 Windows 上使用名为 SysMon 的计划任务或启动文件夹脚本。它还会向 8099 端口上报主机名、git 邮箱、公网 IP，以及最多 40 个匹配 KEY|TOKEN|SECRET|PASS|AWS|GCP 的环境变量名——不过一个 bug 导致 macOS 上的启用步骤被跳过：对普通用户而言，systemsetup -getremotelogin 会以管理员权限提示失败（退出码为 0），因此代码永远匹配不到 /Off/i，也就永远不会执行 sudo -n systemsetup -setremotelogin on，结果是除非远程登录本来就已开启，否则 22 端口保持关闭。

**讨论**: 讨论主要围绕事件范围展开争论。两位 Anthropic 员工（felixrieseberg、ddworken）反复表示没有 Anthropic 系统被入侵，2.1.313 从未在 VS Code Marketplace、OpenVSX、npm 或他们自己的主机上发布过，并且他们发布 2.1.314 正是为了消除歧义——而多位评论者反驳称，2.1.313 并未出现在官方 VS Code 市场、npm 和 GitHub 的 changelog/tag 中，且 Kevin Beaumont 以及来自 Binance 的消息来源都描述了一起 OpenVSX 被入侵的事件，因此他们怀疑「仅限 Cursor」这一说法。其他人则深入讨论 Cursor 的架构：其市场是 OpenVSX 前面的一个代理，且没有扩展签名，评论者认为这才是真正的弱点；一条路透社链接称恶意构建的上线时间约为太平洋时间凌晨 2:27 至下午 1:35，受影响用户约 5,000 人。一个热门的分支讨论指出，VS Code 的扩展自动更新延迟明确不适用于 Microsoft、GitHub 和 OpenAI 这类「受信任发布者」，而且该延迟默认是 2 小时而非一周。其余大部分内容是实践者描述隔离手段：临时容器、不挂载主机共享目录也不转发 SSH agent 的 QEMU 虚拟机、独立用户账户，以及一场持续的争论：让编码 agent 拥有主目录访问权限到底是否说得过去。

**值得一读的评论**
- [jonas21](https://news.ycombinator.com/item?id=50306306): 引用了 Cursor 的公告，其中给出可直接复制粘贴的 macOS 和 PowerShell 命令，用于在 authorized_keys 中搜索 svc-telemetry 密钥。
- [orlp](https://news.ycombinator.com/item?id=50302955): 指出 VS Code 的扩展自动更新延迟对 Microsoft、GitHub 和 OpenAI 等「受信任发布者」不生效，而且无法按发布者单独配置。
- [ddworken](https://news.ycombinator.com/item?id=50304793): Anthropic 的 ddworken 表示 2.1.313 从未在 OpenVSX、VS Code 市场或官方主机上发布，2.1.314 是专门为消除歧义而发布的——这正是讨论中许多人质疑的说法。

## 4. Show HN：用约 1GB 的 Qwen 权重跑起一台能工作的任天堂 {#story-4}
*HN 第 4 名 · [github.com](https://github.com/dbreunig/nesformer) · 117 分 · 90 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50306442)*
*原标题: Show HN: A working Nintendo in ~1GB of Qwen weights*

GitHub 项目 nesformer 把 NES 的 6502 CPU（即 2A03 核心）、其 2 KB 工作 RAM，以及一张 NROM 卡带的 32 KB 程序 ROM，编译进一个现成 Qwen3.5 模型的权重里。这些权重没有任何人训练过：它们由一个编译器计算得出，模型则逐 token 预测 CPU 的执行轨迹，并用 Gated DeltaNet 的状态充当这台机器的内存。该检查点有 466.6M 个参数，以 bf16 存储（933 MB，其中仅 9.3M 个非零，压缩后 3.3 MB），在 nestest 和游戏轨迹上与参考 6502 一致，但运行速度比真实硬件慢 150–290 倍，每帧需要 1–6 秒，且只支持使用官方操作码的 mapper-0 NROM 游戏。

**讨论**: 讨论串里的反应大多是惊叹于这份胆量，以及 CPU、RAM 和 ROM 全都存在于模型内部而非宿主模拟器里这一点。作者说，Opus 5.5 仅凭两个提示就产出了可用的权重和代码，并把 Qwenputer 的编译器和包含 3000 多条黄金指令的 nestest 一致性测试套件列为主要助力。也有少数人高声唱反调：批评者称它在技术上毫无趣味、是垃圾产出，或者说是对神经图灵机的过度复杂化重造，并认为 AI 生成的版本不如它模仿的那些手工打造的 hack 令人印象深刻。另一些人用 150–290 倍的减速来论证，用 LLM 模拟的软件比普通代码低效数千倍；而辩护者则说，重点在于概念验证、趣味性，以及展示权重中的确定性计算。评论者还挑刺标题里把 NES 称作「Nintendo」，并询问随机解码和更广泛的卡带支持问题。

**值得一读的评论**
- [dbreunig](https://news.ycombinator.com/item?id=50307402): 作者解释说，Opus 5.5 仅凭两个提示就构建出了可用的权重和代码，其中 Qwenputer 和 nestest 一致性测试套件是必不可少的参考资料。
- [pbohun](https://news.ycombinator.com/item?id=50307246): 一位评论者用 150–290 倍的减速来论证，在 LLM 内部逐帧模拟一个操作系统所需的算力会是普通软件的数千倍。
- [rvz](https://news.ycombinator.com/item?id=50307455): 一位批评者认为该项目不过是神经图灵机的过度复杂化转世，并称 HN 上的反响是不加批判的垃圾吹捧。

## 5. 打破开放网络无法阻止恶意机器人 {#story-5}
*HN 第 5 名 · [techpolicy.press](https://www.techpolicy.press/breaking-the-open-web-wont-stop-the-bad-bots/) · 88 分 · 32 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50263837)*
*原标题: Breaking the open web won't stop the bad bots*

Tech Policy Press 发表的一篇评论文章，作者是 Lila Bailey（Internet Archive 高级政策顾问）和 Tess Vartanian（Center for Democracy & Technology 法律研究员），反对联邦《Stealth Bot Prohibition Act》和纽约州《Stealth Crawler Prohibition Act》。两项法案都把机器人定义为「检索、扫描、索引、抓取或以其他方式访问」网站的软件，并把机器人定为「隐蔽」——如果它未能披露自身身份以及其工作的「具体性质和目的」；联邦版本允许 FTC 在相关行为「有合理可能损害、削弱或加重」网站的技术或商业运营时，对每次违规寻求最高 53,000 美元罚款，却未对该标准作出定义；纽约州法案只覆盖新闻网站，并允许出版商在无需证明任何损害的情况下传唤爬虫的身份信息。作者认为，匿名往往正是爬取具有价值的原因——文中举了《华尔街日报》2022 年获得普利策奖的分析（基于 12,000 名官员的 31,000 份财务披露）、Wayback Machine 归档的一万亿个页面，以及无障碍与公共卫生研究；他们援引 Lamont v. Postmaster General 案中关于接收信息权利的判决，并提出改用 IETF 式的互操作协议与匿名认证，同时把责任与可证明的损害挂钩。

## 17. 编译期依赖类型 {#story-17}
*HN 第 21 名 · [thenumb.at](https://thenumb.at/Syl-Intro/) · 53 分 · 15 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50246538)*
*原标题: Compile-Time Dependent Types*

这是 Syl 作者的一篇文章。Syl 是一门研究性语言，它在模态类型系统中编码编译期计算，灵感来自 András Kovács 的两级类型论（two-level type theory）以及 OxCaml 的模态（modes）。Syl 的每个值在两个维度上都带有一个模态 —— static/dynamic（是否可在编译期得知）与 erased/unerased（是否可在运行时得知）—— 模态标注只能被弱化，此外还有诸如 `if erased`、`match erased`、`unreachable` 以及会被单态化的静态函数实参这类构造。其结果是一门在编译期具有依赖类型、在运行时为简单类型、且所有类型都被擦除的语言；由于它允许一般递归和 `type : type`，类型检查是不可判定的，需要依赖 fuel/递归上限，因此它是一门编程语言而非证明助手。文中示例走查了一个 GADT 风格的、以 sort 为索引的解释器，以及一个使用 Peano 的 `nat` 的长度索引向量 `append`。

**讨论**: 最尖锐的交锋在于什么才算依赖类型：一位评论者反驳说 C++ 模板、Rust const generics、Zig comptime 和 C 的 `_Generic` 根本不是依赖类型，作者承认它们只是在「类型可以提及编译期值」这个意义上算「依赖」—— 由此确认：用 2LTT 的术语来说，Syl 的元语言是依赖类型的，对象语言是简单类型的，运行时一切都被擦除。另一位有类型论背景的评论者认为，把类型限制为静态值是一种不必要的性能妥协，因为 dynamic-plus-erased 参数没有运行时开销；作者反驳说，Syl 用静态数据来决定运行时布局，所以动态类型会迫使采用统一表示，不过他也承认，OxCaml 风格的模态最终应当能让类型在动态模态下提及运行时值。一个大的分支讨论认为，讽刺的是 C 才是原列表里唯一拥有真正依赖类型的语言 —— 不是 `_Generic`，而是变长数组 —— 这又演变成一场关于 C99 VLA 究竟是错误、还是 Dennis Ritchie 与 D 的胖指针方案更好的辩论，其中还提到 variably-modified types 与 C2y 的 `countof` 如何改善了现状。此外，评论者们还岔开去讨论为什么依赖函数被称为积（products）、依赖对被称作和（sums），以及有人问 LTO 是否已经实现了同样的特化，有回复说编译器在这方面非常擅长。

**值得一读的评论**
- [TheNumbat](https://news.ycombinator.com/item?id=50308210): 作者反驳了动态类型参数是免费的这一说法：Syl 用静态值来描述运行时布局，因此允许动态值就需要统一表示 —— 不过他预计 OxCaml 风格的模态最终会允许类型中出现动态值。
- [wahern](https://news.ycombinator.com/item?id=50307171): 指出 C（而非 C++/Rust/Zig）才是文中列表里唯一拥有真正依赖类型的语言 —— 是变长数组，不是 `_Generic` —— 由此引发了一段关于 VLA 设计的长子讨论。
- [TheNumbat](https://news.ycombinator.com/item?id=50307927): 作者澄清了自己的意图：所列特性只是在「类型可以提及编译期值」这一宽泛意义上算依赖，并用 2LTT 的术语确认了完全擦除、没有字典传递。

## 20. 为什么程序从批处理文件运行时无法工作，而双击单击却能正常工作 {#story-20}
*HN 第 26 名 · [devblogs.microsoft.com](https://devblogs.microsoft.com/oldnewthing/20261026-00/?p=112797/) · 110 分 · 59 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50251070)*
*原标题: Why a program doesn't work when run from a batch file, but works when clicked*

Raymond Chen 的一篇 Old New Thing 博文，讲一位客户的程序在批处理文件启动时会报错，而在资源管理器中双击时却运行正常。Chen 的解释是：资源管理器会把新进程的当前目录设为所点击的可执行文件或文档所在的文件夹，而批处理文件是用完整路径调用程序的，当前目录仍留在别处；程序一直在相对于当前目录查找附属文件。客户用 pushd/popd 解决了问题，Chen 还指出 App Paths 条目是把目录加入 PATH 的另一种方式。

**讨论**: 评论者对当前工作目录究竟是有用的功能还是危险的隐藏状态意见不一：有人称 cmd.exe 的按驱动器分别记录当前目录的做法「非常糟糕」，另一些人则反驳说这是有文档记载的 MS-DOS 时代行为，在命令提示符里可见，并不比 PATH 或其他环境变量更糟。一个子讨论串解释说，cmd 为每个驱动器保留单独的当前目录，因此在 C: 下执行 `cd D:\foo` 不会改变可见的工作目录；需要使用 `cd /d`，几位偏 Unix 的用户称这是脚本编写中的坑。在别处，开发者们主张程序应通过自身可执行文件路径或 LocalAppData 而不是 CWD 来定位资源，其中一位指出 ASP.NET Core 至今仍会让人们踩坑，其他人则讨论 Windows DLL 搜索的限制和应用清单。一个较长的跑题讨论问，Raymond Chen 为什么会处理如此基础的支持案例，一位前 Visual Studio 工程师说资深工程师经常浏览支持队列并挑走有趣的工单，而其他人则认为这个故事可能来自他的博文积压。

**值得一读的评论**
- [andOlga](https://news.ycombinator.com/item?id=50304005): 澄清了按驱动器区分的困惑：`cd D:\foo` 只改变 D: 存储的工作目录，而 `cd /d D:\foo` 会同时改变驱动器和目录。
- [LatencyKills](https://news.ycombinator.com/item?id=50302646): 一位曾参与 Visual Studio 的工程师表示，微软的资深工程师经常浏览未处理的工单并挑走有趣的案例，因此 Chen 的参与是合理的。
- [pwdisswordfishq](https://news.ycombinator.com/item?id=50303498): 认为命令行本身设计糟糕：如果 CLI 接收的是已打开的文件句柄而不是路径字符串，大多数程序根本不需要当前目录。
