## 1. AI 正迫使我们偿还 40 年的技术债 {#story-1}
*HN 第 1 名 · [spectrum.ieee.org](https://spectrum.ieee.org/ai-in-cybersecurity-php2shell-vulnerability) · 859 分 · 507 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50364336)*
*原标题: AI is forcing us to pay off 40 years of technical debt*

Dina Genkina 在 IEEE Spectrum 上撰写的关于 PHP2Shell 漏洞的文章，该漏洞使基于 WordPress 和 Drupal 的网站——其中包括 NASA、Wikipedia 和白宫——面临远程代码执行风险。底层的内存耗尽 bug 于 2024 年被报告给 PHP Foundation，但当时只被当作普通的崩溃而未被重视；今年，安全公司 Calif 的一名研究员在 OpenAI 赞助、借助 AI 工具进行的审计中开展工作，在两周内就把它变成了任意代码执行，而四名工程师组成的团队在披露前花了两个月时间构建补丁。哥伦比亚大学的 Suman Jana 认为，AI 擅长漏洞利用所需的那种枯燥、高度具体的推理，并且在通过形式化验证进行修补方面进步飞快（并援引了 Anthropic 在 10 月 22 日发布的一项成果），而约翰斯·霍普金斯大学的 Matthew Green 则预测，在出现真正严重的事故之前——也许要到 2027 年初——不会有任何严肃的资金投入。

**讨论**: 讨论分成两派：一派把 AI 视为加速剂，另一派则视其为解药。几位评论者称这个标题是在无脑吹捧 AI，并指出这类漏洞已经存在了 40 年，还质问：为什么能发现 bug 的机器，在修复那些只有它们才能发现的 bug 之后还要被赞美？一个很长的子讨论重新翻出了 Linus 定律，其中最尖锐的一点是：这条定律是 ESR 提出的，而不是 Linus 提出的，而且关键在于「谁的眼睛」而非「多少双眼睛」——一个开源医疗项目的维护者证实，他们虽然例行做审计，但在过去六个月里仍被大量真实的漏洞报告所淹没。一个反复出现的反驳观点把问题归咎于激励机制而非工程文化：管理者和客户想要便宜、快速的交付，因此兼容性和重构从来没有得到预算；几位从业者表示，AI 现在把多年积压的修复一次性砸到了他们头上（其中一位说 Opus 5.5 的 9 月升级引发了长达两到三周的紧急清理）。另一些人则反驳文章把 PHP 定性为遗留语言的说法，指出 7.x/8.x 的改进，并认为它成为攻击目标是因为无处不在，而非因为老旧；一条被广泛阅读的回复则主张，真正更糟的情况是 Brotli/HTTP2Shell 漏洞，人类把它压了几个月。

**值得一读的评论**
- [adunsulag](https://news.ycombinator.com/item?id=50366063): 一个开源医疗项目的维护者描述了例行的第三方审计如何制造出一种虚假的安全感，以及最近大量涌来的 AI 辅助报告即使经过误报过滤，仍让人备受打击、疲于应对。
- [vanschelven](https://news.ycombinator.com/item?id=50364661): 认为 HTTP2Shell/Brotli2Shell 可以说比 PHP2Shell 更糟，并给出一条时间线：它在代码中存在了 8 年，修复后在 8 个月里未发布，而且由四名独立研究员各自发现——也就是说，压着它的是人类，而不是 AI。
- [0xfedcafe](https://news.ycombinator.com/item?id=50365317): 用链接梳理了政策层面的角度：据报道 Amazon 在游说限制模型能力，而 OpenAI（提供 10 亿美元的补贴 Daybreak 使用额度）和 Anthropic（提供 1 亿美元的 Mythos 额度、400 万美元捐款）则向防御方提供前沿安全模型。

## 2. Go 的新 JSON API {#story-2}
*HN 第 2 名 · [go.dev](https://go.dev/blog/jsonv2) · 88 分 · 22 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50369106)*
*原标题: A New Go API for JSON*

Go 团队在 go.dev 博客上宣布了新的 JSON API——从讨论看，即 `encoding/json/v2` 包，另有一个配套的 `encoding/json/jsontext` 层负责底层的 token／值处理。文章正文本身未能抓取（页面几乎没有可读内容），因此这里的细节来自标题和评论者的描述。最引人注目的反应是：这个设计花了大约六年才落地。

*未能读取原文：page had almost no readable text (probably needs JavaScript or a login)*

**讨论**: 评论者总体上对 `encoding/json/v2` 持肯定态度，但聚焦于迁移成本和 API 的人体工学。最响亮的抱怨是 `MarshalIndent` 没了，让快速美化输出变得别扭、迁移也不直观——直到其他人指出替代方案就是 `json.Marshal(v, jsontext.WithIndent("  "))` 或 `jsontext.Value.Indent()`，而最初抱怨的人漏掉了这一点。另有一场争论围绕 `json.Marshal` 为什么非要返回 error：一方认为不可序列化的类型属于代码 bug，应由更强的类型系统或 panic 来捕获；另一方则指出 `Marshal` 接受 `any`，`MarshalJSON` 方法可能在运行时失败（例如懒加载），而且非有限浮点数使得即便是静态已知的类型也部分不可序列化。被建议的惯用法是 `MustMarshal`／泛型 `Must[T]` 包装。还有几个人提到，他们现在的 Go 代码大多由 LLM 编写，因此更好的 API 主要影响的是模型生成出来的东西。

**值得一读的评论**
- [CamouflagedKiwi](https://news.ycombinator.com/item?id=50369853): 整体喜欢 v2，但认为去掉 `MarshalIndent` 让迁移和快速导出可读 JSON 都变得不必要地痛苦。
- [arccy](https://news.ycombinator.com/item?id=50370310): 更正：美化输出仍是一行即可，`json.Marshal(v, jsontext.WithIndent("  "))`（同一线程另有评论指向 `jsontext.Value.Indent`）。
- [duskwuff](https://news.ycombinator.com/item?id=50370539): 反驳「序列化只会对不可序列化类型失败」的说法：`MarshalJSON` 实现可能在运行时失败，例如懒加载的数据加载不出来，而且 `any` 可能出现在对象树的任何位置。

## 3. 大语言模型可证明推理的进展 {#story-3}
*HN 第 3 名 · [anthropic.com](https://www.anthropic.com/research/provable-inference) · 118 分 · 51 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50368626)*
*原标题: Progress on provable inference for large language models*

Anthropic 的一篇研究文章介绍了 FlashProve，这是一个开源（Apache 2.0）的原型，使用 zkSNARKs 来证明某条回复来自一组已承诺的模型权重，而不必泄露这些权重。对于 Llama 4 Maverick（400B 参数的 MoE，4-bit 量化），单张 H100 以约 110 tokens/秒 的速度生成证明，每个 1,024-token 请求的证明约 19 MB——大约是 vLLM 仅运行该模型所需 GPU 时间的 70-95 倍；客户端在 24 线程上用 17 秒验证一份证明（单线程 21 秒），前提是先下载约 6.5 MB 的权重承诺，该承诺可用于约 1600 万次请求。此次发布包括一份技术报告、一份由 Claude 撰写的协议规范、一个 C++ 验证器和一个 Lean 验证器，以及对顶层安全陈述的 Lean 证明；文中陈述的动机包括评估方、路由服务、篡改检测，以及监管机构对 AI 发展节奏的把控。

**讨论**: 讨论中最响的声音是一场归属之争：neuwirth 称这项工作建立在他作为 MARS 研究员时编写的原型 VerInf 之上，并且 Anthropic 把一切都拿走了，连选择 Llama 4 Maverick 都是如此，却几乎未给予署名——其他人指出文章确实引用了 VerInf，其速度约为 0.02 tok/s，而该子串随即演变成一场宿命论的争论，涉及 MIT 与 GPL 许可之争，以及 AI 改写是否让软件版权失去意义。第二个阵营认为这套密码学是杀鸡用牛刀：对于开放权重模型，你只需确定性地重新运行计算即可（比 70-95 倍的证明开销更便宜），而对于闭源模型，签名响应、比较多个独立提供商或 TEE 都更便宜——尽管如今的证明仅能覆盖单个 8-GPU 节点，机架级加密尚未广泛部署。几位评论者强调了当前的适用范围限制：仅整数权重、贪心解码、约 1k 上下文，因此一个在后台悄悄提供量化或采样解码变体的托管方，可能在某个 token 处偏离证明——而这正是人们怀疑 BaseTen、Fireworks 和 Together 所做的欺诈。在实用性上，讨论分成两派：一派说「谁在乎，你本来就得信任你的提供商」，另一派则给出具体案例：中国经销商把其他模型冒充成 Claude、OpenRouter 式的路由、独立的预发布评估方，以及黑盒审计（一位研究用于 AI 审计的 ZKP 的博士生表示，这印证了他们的结果）。怀疑者将其解读为保护 Anthropic 的定价免受更便宜的路由冲击，并且鉴于过去曾悄悄改路由到更弱的模型，这也是一种公关举动；最后一个串讨论监管中「只运行推理」的场景究竟是不是一个真问题。

**值得一读的评论**
- [neuwirth](https://news.ycombinator.com/item?id=50370121): 一位研究者声称 Anthropic 的系统源自他自己的 VerInf 原型，且署名极少——这是整个讨论中最大争论的起点。
- [gopalv](https://news.ycombinator.com/item?id=50368978): 指出证明/承诺机制看起来像昂贵的 proof-of-work，并链接了一项调查，探究为何 BaseTen、Fireworks 和 Together 以不同方式提供相同的权重，可能是针对长上下文做了量化。
- [FrasiertheLion](https://news.ycombinator.com/item?id=50370668): 解释了为何机密计算并非轻松的替代方案：证明需要安全硬件，在 Blackwell 上仅限单个 8-GPU 节点，而 Vera Rubin 上的机架级加密尚未广泛部署。

## 4. 教育不该被当作人质勒索 {#story-4}
*HN 第 4 名 · [blog.kagi.com](https://blog.kagi.com/education-should-not-be-held-for-ransom) · 69 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50369657)*
*原标题: Education Shouldn't Be Held for Ransom*

这是一封 Kagi 博客上的公开信，作者 Kevin Elgan 是 Kagi 的营销负责人、也曾是教育科技培训师。文章认为，Google 决定从 2027 年初起对 K-12 的 Google Workspace for Education 账户默认关闭 AI 工具是假胜利，因为 Google 搜索会随之一起被关掉——Google 教育副总裁 Chris Phillips 对《纽约时报》表示「搜索与 AI 已深度整合」。在遭到反弹后，Google 称学校可以只启用搜索，但搜索本身仍附带 AI Overviews，因此 Kagi 认为教育工作者没办法只让学生用纯粹的网页搜索。文章结尾变成了一段推销：Kagi 默认关闭 AI、可选的 Quick Answer、无广告且不被追踪的结果、站点屏蔽、自定义 Lenses 以及付费墙提示。

**讨论**: 讨论分裂为两派：一派认可文章的实质内容，另一派认为 Kagi 是在打误导性广告。最尖锐的反对意见是，Google 早已澄清管理员可以独立开关每一项功能，包括不带 AI 的搜索，这让「勒索」的说法显得像营销——另一些人反驳说，厂商博客本来就是做广告的合适地方，而且 Google 的捆绑销售仍是个真实的隐忧。一位从事家校沟通的教育科技从业者描述，学校要求关闭所有 AI 功能，随后又因基于 Google Translate 的翻译消失而惊慌，这说明学校自己都不清楚合同里的 AI 指什么。还有一个阵营认为学校几乎不需要 Google 搜索——有好老师和基础材料就够了——但有人反驳说，做独立研究的高中生需要开放的互联网，而且学校网络本来就封禁 Wikipedia，却又让孩子照样在 Google 上「做研究」。反复出现的主题是：公立与私立学校在技术政策上分歧明显，而真正的恐惧是一代人把自己的思考外包给一两家厂商。

**值得一读的评论**
- [ahmedfromtunis](https://news.ycombinator.com/item?id=50370561): 认为 Kagi 是在利用混乱做文章：Google 已澄清管理员可以独立开关每一项功能，包括不带 AI 的搜索，所以即便 Google 该受批评，这篇文章仍是欺骗性营销。
- [SeanAnderson](https://news.ycombinator.com/item?id=50370472): 来自教育科技家校沟通领域的第一手说法：学校下令关闭所有 AI 功能，随后又因 AI 驱动的 Google Translate 翻译消失而震惊。
- [lnkdinsuxs](https://news.ycombinator.com/item?id=50370611): 对比公立与私立学校，并论证责任风险的算术——在一个县级规模的公立学区，只要有一名学生因 LLM 受到伤害，就可能引来足以让学校破产的诉讼。

## 5. Ripple-65B Preview：美国开放权重模型在 agentic coding 上的 SOTA {#story-5}
*HN 第 5 名 · [ricursive.com](https://www.ricursive.com/ripple) · 30 分 · 15 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50369925)*

Ricursive Intelligence（一家同时做 AI 芯片设计的实验室）发布了 Ripple-65B Preview——一个从头训练的稠密 Transformer（d_model 5120、80 层、12T token 预训练、最高 1M 上下文），它声称这是美国开放权重模型在 agentic coding 上的 SOTA。它的核心数字是 TerminalBench 2.1 上 80.52，超过体积大得多的美国开放权重模型：Reflection Beam 501B（80.1）、Meta Muse Spark Open 816B（76.4）、Thinking Machines Inkling 975B（63.8）和 NVIDIA Nemotron 3 Ultra 550B（56.4）。Ricursive 表示，这个模型的完整 R&D 成本只有 3200 万美元，预训练中 MFU 保持在 40%，RL 阶段只用了 140 万次 rollout（比 Beam 少约 70 倍）；模型已在 Hugging Face、Together AI、GMI Cloud 和 OpenRouter 上线。

- [empath75](https://news.ycombinator.com/item?id=50368947): 一位已经用 Claude 造了一门类 Rust 语言、投入数月的评论者警告说，Claude 一直在走捷径；他说自己曾扔掉数月的工作，直到改用一种经过形式化证明的 Lean 演算重建——并建议别人先把已有论文形式化。

## 19. 为电子表格加入窗口函数 {#story-19}
*HN 第 23 名 · [getgrist.com](https://www.getgrist.com/blog/running-totals-you-dont-have-to-chase/) · 35 分 · 22 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50366860)*

这是 Grist 的一篇博客文章，作者是该公司的联合创始人兼产品负责人 Dmitry Sagalovskiy。文章说明传统电子表格的 running balance 会在插入或删除行时悄无声息地算错：因为单元格里的公式会把「上一行」调整成指的是原来那个单元格，而不是现在它上面的那一行。文章提出的做法是在电子表格里使用有序查找，具体包括 Grist 的 PREVIOUS()、NEXT() 和 RANK()，以及 lookupRecords(...).find.le()，把排序写进公式本身。文章称，在一张 2 万行的测试表上，用 PREVIOUS() 算完整列 running balance 只需几秒，而用 Python 逐行扫描的写法运行五分钟仍未结束。

**讨论**: 评论者从几个方向提出了意见。有几个人抱怨文章读起来像 AI 写的；一位评论者认为这种语法很别扭：UPPER_CASE 的函数名和 Python 的 dot 属性访问混在一起；而维护者的回复澄清说，这其实都是纯 Python，PREVIOUS() 返回的是一条完整的记录，.Running_Balance 只是取出其中一个字段，$A 也只是 rec.A 的语法糖，经典 Excel 函数本身就是用 Python 实现的，代码可在 GitHub 上找到。另一位评论者反驳说，返回记录并用点号访问是「clunky」的做法，主张返回一张表，再用列名做一次 index lookup，就像 Google Sheets 里 GOOGLEFINANCE 的工作方式。也有评论者认为，电子表格变得越来越像数据库是好事，但它有使简单任务复杂化的缺陷，而且很难避开近五十年的电子表格语法历史。旁支的讨论则提到了其他替代产品（IronCalc、treesum、omasheet、pyspread），并半开玩笑地说这等于在重新发明 BusinessObjects，或者幻想从小学开始教 SQL——其中有人设想，以后 SQL 对 LLM 来说会像中古英语一样显得过时。

**值得一读的评论**
- [dsagal](https://news.ycombinator.com/item?id=50369002): Grist 的开发者 dsagal 解释了实际实现：大小写敏感的 Excel 风格函数是 Python 的简单封装，链接到了 grist-core 的 sandbox 源码，并说明 PREVIOUS() 之所以特殊，只是因为它会自动创建索引，以便提升效率。

- [whizzter](https://news.ycombinator.com/item?id=50367357): 主张这种数据库化方向是一种误导：它想解决电子表格结果任意的问题，代价却是把「简单操作」变复杂，而且还要面对近五十年的电子表格语法；评论者说，这种语法和 Python 混用，是最大的设计约束。
