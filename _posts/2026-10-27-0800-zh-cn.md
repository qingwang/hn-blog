## 1. 数学、计算机科学与物理学中的三项新发现 {#story-1}
*HN 第 1 名 · [openai.com](https://openai.com/index/building-scientific-understanding-with-academic-communities/) · 815 分 · 356 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50251344)*
*原标题: Three new discoveries in mathematics, computer science, and physics*

OpenAI 的一篇文章公布了模型产出的三项成果，以及一套新的发布流程：由外部专家担任「牧羊人」（shepherd）。数学家直接拿到原始 AI 写作与 Lean 证明；由 Russell Impagliazzo、Ramamohan Paturi 和 Ryan Williams 领导的计算机科学组立即发布证明及 Lean 形式化；由 David Gross、Michael Douglas、Arthur Jaffe、Igor Klebanov 和 Nikita Nekrasov 领导的物理组则暂不公布 AI 产物，而是自行撰写论文。所宣称的成果包括：证明了任意维度下 Sogge 局部平滑猜想（因而经由一个新的辅助 PDE 得到所有维度下的 Kakeya 猜想与 Stein 限制猜想，于 2026 年 10 月 18 日获得，次日完成 Lean 形式化）；一个确定性算法，能在 2^(n/(log n)^(1/2+o(1))) 时间内精确计数 k-CNF 的满足赋值，从而反驳 ETH（自然语言反证于 10 月 16 日，Lean 于 10 月 17 日）；以及一个严格的四维存在性证明，涵盖包括 QCD 在内的相互作用规范场论，外加纯 Yang–Mills 理论——即千禧年难题中存在性那一半，但不涉及质量间隙。

**讨论**: 讨论串分成两派：一派认可流程的改变，另一派则质疑其动机。几位评论者表示，主动联系 Tao 以及该领域自身的作者，不过是学术礼节的最低要求，而「牧羊人」模式仍然把信息集中在一小群人手里，尤其是在物理学中，由五位具名人士决定压下产出；另一些人则认为，在上一次数学发布之后，整件事就是一场公关作秀。最有实质性的分歧在于反驳 ETH 意味着什么：实践者指出，这个界是次指数的但仍是超多项式的，因此它只是越过了某个多少有些随意的边界，并没有让指数层级崩塌；而且 ETH 曾是数百个困难性结果赖以成立的基础——一位评论者提到 Scott Aaronson 把自己对 P=NP 的置信度从 3% 调到了 5%，另一位则认为这一更新应当更大。在物理学方面，一线理论家意见不一：有人称严格的 QCD 存在性证明是终身量级的成果，也有人指出，拥有一个路径积分测度却对哪些函数可积只字不提，既得不到质量间隙也得不到禁闭；还有人猜测那个统一化的完成版本是实验上已死的 SU(5) Georgi–Glashow 模型，而非真正的标准模型。一个反复出现的元观点是：AI 正在碾压可形式验证的领域（Lean 提供了廉价的奖励信号），而在每轮迭代的验证都要花上数天的湿实验室或「邋遢」科学中，它会慢得多。

**值得一读的评论**
- [jltsiren](https://news.ycombinator.com/item?id=50252939): 一位复杂性理论家认为，2^(n/polylog n) 这个界是次指数的，因此多项式时间归约会放大实例规模，该结果对复杂性类的直觉判断几乎没有改变——这是个巨大的成果，但不是迈向 P=NP 的一步。
- [abetusk](https://news.ycombinator.com/item?id=50252781): 引用了已发布预印本中的实际定理：以 (n+m)^{O_k(1)}·2^{n/(log n)^{1/2+o(1)}} 时间，对 k-CNF 满足赋值进行多项式空间的确定性计数，即超多项式但次指数。
- [auntienomen](https://news.ycombinator.com/item?id=50253757): 一位理论家对 Yang–Mills 论断提出的保留意见：该证明给出了一个路径积分测度，但没有刻画可积函数，因此质量间隙与禁闭仍然原封未动——存在性只是让这些问题变得提法恰当。

## 2. AI 时代的《人月神话》 {#story-2}
*HN 第 2 名 · [j11g.com](https://j11g.com/the-mythical-man-month-in-the-age-of-ai) · 34 分 · 21 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50255298)*
*原标题: The Mythical Man-Month in the Age of AI*

j11g.com 的一篇短博客文章主张，Brooks 定律——向一个已经延迟的软件项目增加人手只会让它更晚——并没有被 AI agent 废除，只是发生了变异。作者提出的 2026 年改写版是：向一个需求不清晰的项目增加 agent，只会让你更快地得到错误答案。核心论点是，协调开销从管理人转移到了管理 agent——仍然需要有人来定义「完成」、审查代码、发现幻觉并把各个部分拼接起来——而且「九个女人一个月也生不出一个孩子」这一约束仍然适用于串行工作。

**讨论**: 最尖锐的分歧在于，快速给出错误答案究竟是缺陷还是特性：一派认为，花一小时、用价值 4 美元的 token 生成一个明显残缺的概念验证，是发现需求最便宜的方式；另一些人则反驳说，这只有在验证几乎免费、且失败的尝试确实能揭示正确答案时才成立——而事实并非总是如此。几位评论者对文章的核心比喻提出质疑，指出书中实际的表述是关于九个女人不能在一个月内生出孩子，并质疑「agent」到底能否对应「man」，因为现代 harness 中的子 agent 并不是独立的工作单元。实践者对生产力主张的看法分成两派：一位表示，九个 Claude Code 实例可以以前所未有的速度构建一个分解后的应用；另一些人则报告说，开放式、跨多个文件的改动会产生大量审查工作，把提速抵消掉，而且监督 agent 比亲自写代码更消耗认知精力。大致共识是，瓶颈已经转移到验证、设计一致性和人的理解上，而不是打字。

**值得一读的评论**
- [videotextly](https://news.ycombinator.com/item?id=50255548): 一位独立开发者认为，真正的成本在于协调和理解，而不是打字，因此带有测试的小型、边界清晰的任务能够奏效，而庞杂的跨文件改动会产生大量审查工作，把提速吃掉。
- [noduerme](https://news.ycombinator.com/item?id=50255819): 一种不同意见认为，把编码委托给 agent 既乏味又令人退化——感觉像是在和一个有智能的东西推理，却训练你接受答案而不去检查它们。
- [jurgenburgen](https://news.ycombinator.com/item?id=50255791): 对「让模型审查模型代码」这一想法的直率反驳：只要还有人承担责任，他们就必须理解代码，而「我让 LLM 把它做得安全」在发生泄露时是站不住脚的。

## 3. 指数时间假说为假 [pdf] {#story-3}
*HN 第 3 名 · [github.com](https://github.com/openai/math/blob/main/preprints/The-Exponential-Time-Hypothesis-is-False-October-25-2026/paper.pdf) · 576 分 · 207 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50251661)*
*原标题: The Exponential Time Hypothesis Is False [pdf]*

该链接是托管在 GitHub 上的 OpenAI 数学预印本（页面本身只返回了 GitHub 的登录样板文字），标题为 “The Exponential Time Hypothesis Is False”。其声称的结果是一个确定性算法，能够在时间 (n+m)^{O_k(1)}·2^{O_k(n log log n/√log n)} 内精确计算 n 个变量上的 k-CNF 公式的满足赋值数，且只使用多项式空间；这将使 3SAT 变为次指数复杂度，从而推翻 ETH。评论者称，随论文一起发布的还有一份 Lean 形式化证明，以及由 Impagliazzo、Paturi 和 Williams 主导的验证工作。

**讨论**: 评论者把这声称当作一项重大理论成果，但坚持认为它并不证明 P=NP，也没有近期实用价值；一位自称 SAT 求解专家的评论者称该算法是 “galactic” 级别的，多人都引用了论文的告诫：2^{o(n)} 界在一般多项式时间归约下不能保持，因此 NP 整体未必是次指数的。帖中很大一部分内容是在纠正这一误解（以及纠正该结果证明 NP ≠ EXP 的说法），有人耐心解释说，多项式归约可能把 n 放大到足以抹掉收益。关于 P 与 NP，意见分歧：有人引用 Scott Aaronson 的话，说他将 P=NP 的概率从 3% 上调到 5%，而另一些人说该结果对此没有提供任何真正的证据。有人提出了密码学方面的担忧——公钥系统、NSA 后门——但有人引用 Ryan Williams 的话说，OpenAI 检查了现有密码系统并发现它们是安全的，另一些人则指出该算法在真实密钥规模下太慢。一些评论者质疑查表构造、论文的篇幅，以及 Lean 证明是否经过了适当审查；其他人提到 Anthropic 有一篇声称类似界的预印本，并讨论了数学研究向 AI 实验室集中化的问题。

**值得一读的评论**
- [bsubs](https://news.ycombinator.com/item?id=50253117): 一位自认的 SAT 求解专家说目前没有直接应用，因为论文的结果是 “galactic” 级别的，不过其想法日后可能滚雪球般发展成实用方法。
- [mudita](https://news.ycombinator.com/item?id=50252719): 据报道，Scott Aaronson 回应这一消息时，将他个人对 P=NP 的概率从 3% 上调到 5%。
- [JonChesterfield](https://news.ycombinator.com/item?id=50253174): 一位持异议的评论者不接受该证明的框架，他反对说，其中一个构造把所有 SAT 答案枚举进一张状态数超过可观测宇宙的查找表，并表示他不接受这些公理。

## 5. 在 64 位 Windows 上运行 16 位 Windows（Windows 1.x、2.x、3.0、3.1 等） {#story-5}
*HN 第 9 名 · [github.com](https://github.com/otya128/winevdm) · 80 分 · 9 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50253529)*
*原标题: 16-bit Windows (Windows 1.x, 2.x, 3.0, 3.1, etc.) on 64-bit Windows*

这是一个名为 otya128/winevdm 的 GitHub 项目，是 winevdm 16 位 Windows 模拟器的改动版移植，目标是 64 位 Windows；你把 Win16 可执行文件拖到 otvdm.exe 上（或运行 otvdmw.exe），或者运行 install.inf 完成注册，这样 Win16 二进制文件就能直接被启动。由于 64 位 Windows 拒绝修改 LDT（用 NtSetInformationProcess 传 ProcessLdtInformation 总是报错），它改用源自 Wine 的 Win16 到 Win32 转换代码、自动生成的 convspec relay 例程、16 位到原生 HANDLE 的转换，并劫持 Windows 自身的 hook 来重定向 16 位安装程序。它还会把对旧式 INI 的写入从 %WINDIR% 引开，并且可以运行 DOS 可执行文件（通过 VDMDOSVER 变量），不过文中称 DOS 模拟并不完整，建议改用 DOSBox。

**讨论**: 这个讨论串主要是怀旧和实际使用报告，而非质疑：一位评论者通过它安装了 MS Office 2.0 并用了整整一周，觉得用来写日常邮件级别的文字完全够用，并确认它生成的文件在 Word 365、LibreOffice 和 Google Docs 中都能打开——只有词典文件无法被识别，另一位用户也认同这样的配置足以应付信件、简历和学校报告。同一位评论者随后提出一个安全担忧：旧的 16 位文件格式多半是可被利用的，对此无人反驳。其他人则冲着游戏而来：一位想在 Windows 11 上玩 Civilization 2，并指出 Linux 上较新的 WINE 已经能运行 16 位和 32 位应用；有人回复说 Civ2: Test of Time 有专门的补丁，无需借助外部工具。唯一真正的纠正是 winevdm 其实已经存在很久了，这削弱了把它说成全新 16 位支持的说法；一个关于某个 Windows 3.1 文字处理软件「从未崩溃」的子讨论串，得到的回应是一句干脆的「你那肯定是活在另一个现实里」。

## 19. Nginx 原生 Prometheus 集成 {#story-19}
*HN 第 40 名 · [categorica.io](https://categorica.io/blog/2026.10.16_nginx-stats-prometheus/) · 47 分 · 10 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50213502)*
*原标题: Native Prometheus Integration with Nginx*

这是一篇来自 Categorica 的博客文章，宣布了 nginx-stats-prometheus：一个采用 MIT 许可证的 NGINX 模块，它直接从 NGINX 内部暴露 Prometheus 指标，而不是像通常的做法那样借助 sidecar nginx-prometheus-exporter。它导出请求计数、响应类别、按方法和按 HTTP 版本的计数器、请求/响应字节数、一个耗时直方图以及连接计数器，还有按 server/upstream 的指标；硬性上限为 512 个 server/upstream 块、255 个字符的前缀和 1 MB 共享内存（可通过 prometheus_metrics_shm_size 提高），超出后采集会被静默跳过。作者明确表示它并非可直接替换的方案：指标更少、必须针对每个 NGINX 版本重新编译、久经考验的程度也远不如前者；构建时需要 --with-compat 和 --with_http_stub_status_module。

**讨论**: 讨论帖一开始有人声称 NGINX 的开放核心（open-core）模式正是第一方 Prometheus 支持始终未能推出的原因，但有评论者反驳说，NGINX 的指标导出模块早在 Prometheus 之前就已存在，而且 Prometheus 的拉取模型本来就不高效。更大的争论在于人们是否还该继续用 NGINX：几个人说他们所在的圈子里已经转向用 Rust 编写的反向代理（还拿 Lean 4 开玩笑），并认为写一个小型 Go 代理比部署 NGINX 更可取；另一些人则认为对大多数人来说那是糟糕的决定，因为手写的网关会积累缺陷、缺失功能和安全隐患，NGINX 或 Envoy 才应该是默认选择。一条回复承认 Go 的标准库提供了扎实的 HTTP 基础，但列出了真正的风险点——HTTP/2 和 3 到 1.1 的转换、安全地转发客户端 IP、请求头清理——在这些方面可配置的代理更胜一筹。一种不同意见认为 NGINX 已经停滞了 15 年（没有指标，没有 ACME），而 Traefik 才是出路。

**值得一读的评论**
- [lstodd](https://news.ycombinator.com/item?id=50252149): 自称在 2009 年和 2013 年亲手写过两个 NGINX 指标导出模块，并认为 Prometheus 式的拉取导出效率低下，任何严肃的人都不会用。
- [Thaxll](https://news.ycombinator.com/item?id=50252405): 对自行造轮子风气的有力反驳：自建网关会带来缺陷、缺失功能、安全问题和非标准集成，因此 NGINX 或 Envoy 才应该是默认选择。
- [photios](https://news.ycombinator.com/item?id=50254884): 认为 NGINX 大约 15 年来一直停滞不前，既没有指标支持也没有 ACME 证书支持，并表示自己转投 Traefik 后再没回头。
