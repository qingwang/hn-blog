## 1. Tell HN：Scribd 数据泄露 {#story-1}
*HN 第 2 名 · 文字帖 · 169 分 · 67 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50312756)*
*原标题: Tell HN: Scribd Breached*

这是一条 HN 文字帖，作者贴出了本周一（2026 年 10 月 26 日）收到的一封邮件：Scribd, Inc.（Scribd、SlideShare、Everand 和 Fable 的母公司）通过通知服务商 Epiq 告知用户发生了一起安全事件。邮件称入侵者可能获取了邮箱地址、信用卡后四位、持卡国家、发卡机构、有效期和支付历史（不含完整卡号），公司表示已封堵入侵、通知执法与数据保护机构，并聘请第三方安全公司。发帖人还指出，Scribd 本月早些时候已在其支持页面上发布过相关说明，且通知是按批次陆续发出的。

**讨论**: 讨论很快偏离了事件本身。一派认为这是 AI/LLM 让漏洞挖掘变得廉价的结果，另一派（包括有实战经验的人）反驳说漏洞本来就在那里，问题是这些工具普通人和攻击者是否都该拥有——有人主张红队已经存在，各国政府都有专门机构和承包商在打关键基础设施。parable 讲述了自己为关键国家基础设施做安全研究的经历：漏洞披露流程一团糟，有的 RCE 和批量 PII 泄露拖了数年才修，并指出只有美国 CFAA 的善意研究条款能提供保护，其他国家的白帽没有这种法律保障。另有人挖出 Scribd 2013 年就发生过同类泄露、当时的声明与今天几乎逐字相同，以及本次通知分批发送、从 10 月 1 日拖到 10 月 30 日才轮到部分用户，被批评为对自家事件毫无可用数据。技术侧较有价值的澄清是：静态加密只能防硬盘被拔走，应用服务器一旦被攻破，数据照样被读走。此外还有大段关于 HN 文字帖灰色低对比度、隐私虚拟卡、以及「没人再在乎泄露了」的疲惫感。

**值得一读的评论**
- [parable](https://news.ycombinator.com/item?id=50313707): 有从业者现身说法：为关键基础设施做安全研究时披露漏洞极其艰难，部分 RCE 和批量 PII 泄露拖了数年才修，且只有美国 CFAA 的善意研究条款能提供法律保护，其他国家的白帽缺乏动力。
- [x______________](https://news.ycombinator.com/item?id=50313857): 发帖人指出 Scribd 2013 年就因同类事件上过 HN，并贴出当年的声明原文——「未访问任何内容、支付数据」和「我们极其严肃对待用户数据安全」，与 2026 年的措辞几乎一致。
- [mirashii](https://news.ycombinator.com/item?id=50313350): 纠正「静态加密就能兜底」的直觉：加密只防物理拿走磁盘，在线数据库的应用服务器必须能读到明文，应用一旦被攻破数据即失守。

## 2. Cloudflare Turnstile 求解器库（无需无头浏览器） {#story-2}
*HN 第 3 名 · [github.com](https://github.com/chris124567/cfsolve) · 177 分 · 51 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50277379)*
*原标题: Cloudflare Turnstile solver library (no headless browser required)*

cfsolve 是一个 MIT 许可的 Rust 库兼 CLI，用纯 HTTP 请求逆向 Cloudflare 的 Turnstile 组件和插页式质询页面，返回 Turnstile token 或 cf_clearance cookie。它不驱动真实浏览器，而是通过一份 profile 文件冒充录制下来的浏览器（随附的是 iOS 上的 Safari，profiles/safari-26-ios.json），该文件重放抓取到的响应来应对 Cloudflare 的浏览器指纹检查；仅支持 Safari 和 Chrome/Chromium 两类 profile，且 profile 必须通过抓包代理录制真实浏览器的质询流量来生成。它以 CLI（--page、--solve、--sitekey/--action/--cdata、--blank-page、代理支持）和异步 Rust API（Browser::read、solve_turnstile、clear、clear_fetched、solve）的形式提供，从源码构建 BoringSSL/CMake/libclang，并警告 cf_clearance cookie 必须从与 profile 相同的 IP 和 user agent 重放。

**讨论**: 讨论的主流框架是军备竞赛：多位评论者把它比作 yt-dlp，认为从信誉良好的 IP 低频率使用仍能奏效，而高频抓取会被打上特征；一位曾写过求解器的作者说，单次绕过很容易，但要在 Cloudflare 整个网络上大规模模拟行为则不然。另一些人则在争论谁在赢——有人说 Cloudflare 早已落败，因为绕过是 bot 界的 hello world，它只能拦住业余玩家；也有人说它只需保持同步跟进即可。第二类讨论是普通用户被网站拒之门外（Letterboxd、Dell 的结账、被 Cloudflare 挡住的俄罗斯网站）的原则性抱怨，其中对小站遭受持续攻击表示同情，但对大公司则不然；此外还岔到 Anubis 的工作量证明，有人指出 node.crypto 不到一秒就能解出，而且它只对七层滥用有用，对流量型 DDoS 无效。可靠性与维护引发了最尖锐的交锋：一位评论者说价值在于能自动重新逆向 Cloudflare 混淆构建的流水线，另一些人反驳说，一个以现状免费共享的 MIT 库没有义务提供持续可用性。作者直接回答了提问，把大部分逆向工程归功于 Claude 和「Muse Spark」（他说服了它自己拥有该测试站点），并描述了每次 Cloudflare 出新构建时对 agent 说「他们改了东西，请修一下」，而等待时间大半花在 Rust 编译上。

**值得一读的评论**
- [costco](https://news.ycombinator.com/item?id=50311942): 作者报告说该求解器通过美国代理可用，但对一位使用欧洲代理的用户失败，他怀疑 Cloudflare 提供的是他仍需处理的地区特定构建。
- [manofmanysmiles](https://news.ycombinator.com/item?id=50312421): 一位一年前做过类似绕过的开发者认为，单个求解器很容易，但规模化是另一回事，因为 Cloudflare 会在整个网络范围内关联行为。
- [costco](https://news.ycombinator.com/item?id=50311867): 作者解释了他的维护循环：他告诉 agent Cloudflare 改了东西，然后等上几个小时，主要耗在 Rust 编译上，并承认代码库长期会变得凌乱。

## 6. Sanstun：一个用 Rust 编写的 sans-IO、对并行友好的 WireGuard 实现 {#story-6}
*HN 第 12 名 · [firezone.dev](https://www.firezone.dev/blog/introducing-sanstun) · 120 分 · 20 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50310398)*
*原标题: Sanstun: A sans-IO, parallel-friendly WireGuard implementation in Rust*

Firezone 宣布开源 sanstun，一个用 Rust 编写的 WireGuard 状态机实现，采用 sans-IO 设计——把 IO、时间和随机数与协议状态机彻底分离，以 Apache 2.0 发布并已上架 crates.io。它脱胎于团队两年多来对 Cloudflare boringtun 的 fork，累计合并了 70 多个补丁 PR，官方现已弃用该 fork。核心卖点是把每个数据包的记账（预留计数器、推进计时器）与 ChaCha20-Poly1305 加解密拆开：begin_encapsulate 约 20.8 纳秒，而 1280 字节包的 encrypt 约 933 纳秒，记账仅占 2%，因此可把 PendingEncapsulate 送到其他线程做 crypto，理论加速比 45 倍以上。

**讨论**: 最激烈的争论在 sans-IO 与 async 的关系上：一位评论者（Twey）指出 async 本身并非 IO，而是写纯确定性状态机的方式，去掉 async 反而让函数着色问题更糟；作者回应说 async 最终收敛到单一 poll 接口，而 Firezone 的核心需要同时处理入站 IP/UDP、WebSocket 控制消息、TURN 分配、计时器和用户命令，用一个大结构体的 &mut self 方法更易组合和测试，并解释了扩展为 Generator 并不能解决问题。另有人批评 Firezone 官网「硬件承担重任、电池更持久」的文案像 AI 生成的空话，质疑安全关键软件是否也在别处偷工减料；作者澄清那是指向量化加密指令与内核/网卡的校验和卸载、分段卸载，承认措辞可以更好，但不同意「面向技术人员的产品就该堆术语、不该用 AI 写文案」的反驳。有人提到 Mullvad 同样从 boringtun 分叉出自己的 gotatun，并有开发者在实际 VPN 管理器中使用了 gotatun，询问性能曲线、抖动与安全测试数据（未见答复）。还有人主张只该用 Jason Donenfeld 的参考实现（WireGuard 才约 2k 行，为何要三十个版本），作者反驳跨平台场景无法用 Linux 内核实现、官方用户态实现是 Go 不便从 Rust FFI，另一位则指出 sanstun 能在 ESP32 这类 no_std 环境运行，是参考实现做不到的。

**值得一读的评论**
- [Twey](https://news.ycombinator.com/item?id=50312268): 反驳「sans-IO 避免函数着色」的说法：async 不是 IO，而是把逻辑流聚在一起写纯状态机的方式，手动展开成状态转移反而使跨多转移的流程更难调用、着色问题更严重。
- [temp0826](https://news.ycombinator.com/item?id=50310928): 指出 Mullvad 也把 boringtun 分叉成了自己的实现 gotatun，说明这种分叉-重写路径并非 Firezone 独有。
- [lakeviewterrace](https://news.ycombinator.com/item?id=50311704): 直言非参考实现的 WireGuard 都是自找麻烦：协议只有约 2k 行，不需要三十个版本，审计现有的就好——引来作者与另一位评论者的反驳。
