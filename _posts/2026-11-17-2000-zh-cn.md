## 1. GPT‑6.2 Astra 与 Sol {#story-1}
*HN 第 1 名 · [openai.com](https://openai.com/index/introducing-gpt-6-2-astra-sol/) · 664 分 · 379 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50535230)*
*原标题: GPT‑6.2 Astra and Sol*

OpenAI 为两款新模型发布的上线公告：GPT‑6.2 Astra 被定位为处理高难度专业工作的前沿模型，GPT‑6.2 Sol 则是更便宜的日常模型。Astra 的 API 价格相比 GPT‑6 Astra 下降 20%，降至每百万 token 输入 $8、缓存输入 $0.40、输出 $40；OpenAI 声称它在 Agents' Last Exam 上以 5% 的成本领先 Claude Fable 5.2 五个半百分点，在 Harvey 的法律基准上通过率是 Fable 的两倍、成本约为其六分之一，并以 1,318 Elo 登顶 AA‑3D（Fable 5.2 为 1,271）。它也是首个在 OpenAI 的 Preparedness Framework 中达到 AI Self-improvement 的 High 阈值的对外发布模型，同时在网络安全方面达到 Critical、在生物/化学方面达到 High，并且网络相关拒答比以往更严格。

**讨论**: 讨论分成了两派：一派对其性价比印象深刻，另一派则表示基准测试始终对不上自己的日常体验。相当多的人报告说 GPT‑6.x 过度工程化——无意义的抽象、文件过多、diff 巨大——还有几人表示自己现在写代码默认用 Opus 5.5 或 Fable 5.2；一位评论者的 agent 对战数据表明 Sol 6.1 的 diff 大小是 Opus 5.5 的 1.42 倍。支持者则用按 effort 归一化的表格反驳，显示 Astra 在 medium、high 和 xhigh 推理档位下都领先 Opus 5.5，且每个任务成本低得多，但同时承认 Fable 在 max effort 下仍然胜出。帖子里很大一部分是元讨论：X 上的早期体验网红（danshipper、Shumer、Theo）对这次发布评价很差，评论者指责他们在蹭流量，或者没做真实测试就下判断；也有人指出时机明显卡在 Anthropic 的 IPO 之前，并认为 OpenAI 的策略显然是在每任务成本上压价，而非追求绝对能力。反复出现的支线话题包括嘲讽发布视频里「骗过老板、让 AI 替你干活」的前提、抱怨难以阅读的线性坐标轴图表，以及照例贴出 pelican SVG——如今许多人认为这个信号已经饱和或毫无用处。

**值得一读的评论**
- [scilro](https://news.ycombinator.com/item?id=50536704): 给出按 effort 归一化的表格，显示 GPT‑6.2 Astra 在 medium/high/xhigh 档位下于 AA Index、TerminalBench 和 FrontierCode 上胜过 Opus 5.5，每任务成本为 $1.62–$2.52，而后者为 $2.45–$6.05，并论证「落后于 Opus/Fable」的结论只在 max effort 下成立。
- [suddenlybananas](https://news.ycombinator.com/item?id=50536240): 引用 danshipper 的说法：在花费 30 万美元 token 之后，没有任何 OpenAI 模型在他的 ts-rust 重写上取得进展（而 7 天的 Astra 让编译器慢了 56%，Opus 则在不到两周内、约 2 万美元完成），随后质疑该任务是否过于含糊、缺乏管理，因而说明不了什么。
- [tedsanders](https://news.ycombinator.com/item?id=50535868): 一位制作了这些图表的 OpenAI 员工表示，Gemini 4 Carbon 只在其公开成本数据找不到的地方被省略，并非为了掩盖不利结果，并欢迎大家提出更正。

## 3. MAI Code 2 与 Code 2 Flash {#story-3}
*HN 第 3 名 · [microsoft.ai](https://microsoft.ai/news/introducing-mai-code-2-and-mai-code-2-flash/) · 107 分 · 39 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50535885)*
*原标题: MAI Code 2 and Code 2 Flash*

微软旗下的 Microsoft AI 部门发布了两款面向日常企业工作的编程模型：MAI Code 2 用于生产代码变更、调试、多文件及跨仓库编辑；MAI Code 2 Flash 用于解释说明、小型修复等高吞吐任务。微软称，在 DeepSWE 1.1、Terminal Bench 2.1、SWE-Atlas 与 FrontierCode v1.1 上取平均后，Code 2 以 GPT 6.1 Sol 40% 的成本达到其 98% 的性能，以 Claude Opus 5.5 5% 的成本达到其 96% 的性能；Flash 则可与 GPT-6 Luna 和 Claude Haiku 5.5 相比，成本分别为二者的 65% 和 20%。两款模型均已在 GitHub Copilot 中提供，其中 Code 2 Flash 在 Microsoft Foundry 中限量预览，并承诺将上线 OpenRouter、Vercel、Hermes、OpenCode 和 Kilo。文章也承认，这些模型并未针对高难度科学问题或超长周期的智能体任务进行调优，而且标题中的成本数字采用了 50% 的促销价格。

**讨论**: 评论者分为两派：一派认真看待这些数字，另一派则认为它们是精心挑选的结果，不予采信。最尖锐的方法论质疑是：微软给 Code 2 报的是临时 50% 折扣价，却让竞争对手以最大推理力度运行；而且测量所用的是微软自家的测试框架和内部评测平台（MSBench，以及不带子代理的 Copilot CLI）。有几位评论者把价格差距解读为这些是更小、专攻编程的模型而非通用模型，并认为「样样都要更大」的正统观念即将被打破；另一些人则认为更可能只是推理优化，或者微软就是在花钱买市场份额。关于来源问题，一位评论者引用了微软自己关于预训练的帖子，显示这些模型是自研而非微调而来，从而化解了针对中国实验室的蒸馏猜测。从业者反应平淡：有人希望把 DeepSeek、GLM 和 Qwen 加入对比，并指出这两款模型都不是开放权重；也有人说真正的目标客户是想削减成本的 CTO，而不是工程师，况且 GitHub Copilot 本来就已提供 Anthropic 和 OpenAI 的模型。另有一条支线讨论在争论：发布页用衬线体标题搭配无衬线正文，这种排版对于印刷风格的字体排印来说是不是反了。

**值得一读的评论**
- [user43928](https://news.ycombinator.com/item?id=50536992): 指出这项对比并不公平：MAI Code 2 的成本是其 50% 促销价，而 Opus 5.5 和 6.1 Sol 都是以最大推理力度运行的。
- [tomatoandbasil](https://news.ycombinator.com/item?id=50536518): 用微软自己关于前沿预训练的帖子回应了来源质疑，表明这些模型是自研训练的，而非对开源模型做强化学习。
- [VulgarExigency](https://news.ycombinator.com/item?id=50537111): 认为企业本来就能通过 GitHub Copilot 同时获得 Anthropic 和 OpenAI 的模型，所以实际的选择并不是 Anthropic API 对 MAI。

## 4. Solid 2.0 {#story-4}
*HN 第 6 名 · [solidjs.com](https://www.solidjs.com/blog/solid-2-0-the-long-hold/) · 57 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50536387)*

Solid 的创造者 Ryan Carniato 宣布 Solid 2.0 稳定版发布。此时距 1.0 已过去五年，期间在 14 周内经历了 23 个候选版本（合并了 971 个 pull request，关闭了 753 个 issue）。主要变化包括：异步原语被直接并入细粒度响应式图，因此 promise 和异步迭代器会自动回滚推测性状态；server functions 从 SolidStart 移入 Solid 核心；若干 API 被彻底移除（createResource、batch、startTransition、on、produce、createComputed、createMutable）。文章还论证说，不断缩小的 API 表面积以及运行时诊断能力（检测 waterfall、effect 循环、宽扇出，带有稳定的错误码和源码位置，外加一个 Sentry 插件）使 Solid 格外适合由 AI agent 来写代码，并让 SolidStart 元框架退役，转而采用与框架无关的 Vite 插件以及 TanStack Router、Query 等选项。

**讨论**: 该讨论帖以祝贺为主，缺少技术辩论；一位评论者感叹 Solid 的组件库生态薄弱，另一位则用一份清单予以纠正——Kobalte、Ark UI、Park UI、Shadcn Solid、Corvu 以及 Vercel 新的 UI SDK，后者现在已支持 Solid。更热烈的交锋围绕文章「为 agent 编写而生」的宣传：一位评论者认为 agent 恰恰消除了框架存在的理由，而其他人反驳说 LLM 能有效使用响应式框架，并且在框架强制规范模式时能产出更一致的代码。一位 Svelte 用户回顾了当年社区为何选择 Svelte 而非 Solid——模板看起来更简单、对 React 的疲劳——如今则好奇 Solid 的纯 JavaScript 模型是否会显得更自然。

**值得一读的评论**
- [pwmglenn](https://news.ycombinator.com/item?id=50537180): 反驳 Solid 缺少组件库的说法，列出 Kobalte、Ark UI、Park UI、Solid UI、Shadcn Solid、Corvu、Material Design Solid 以及 Vercel 新推出且支持 Solid 的 UI SDK。
- [rafram](https://news.ycombinator.com/item?id=50537093): 对「agent 让框架过时」的有力反驳：LLM 非常擅长使用响应式框架，用它们写出的代码比手写 DOM JavaScript 更易维护、更一致。
- [_nothing](https://news.ycombinator.com/item?id=50537109): 一位 Svelte 用户解释了历史上向 Svelte 的偏移（模板更简单、对 React 的疲劳），并表示 Solid 的纯 JavaScript 路线如今可能显得更自然，同时指出现在是尝试 2.0 的好时机，趁编码模型还没跟上。

## 5. 每个模型的最佳 harness 是什么？ {#story-5}
*HN 第 7 名 · [runta.com](https://runta.com/blog/introducing-frontierharness-eval-v1-1/) · 268 分 · 94 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50532191)*
*原标题: What is the best harness for each model?*

Runta（由 Baseten 提供模型服务）发布了 FrontierHarness Eval v1.1，这是一个覆盖 22 种 harness 配置、5 个开放权重模型（GLM-5.3、GLM-5.3-Flash、DeepSeek-V4.1-Flash-1017、Muse、Kimi-K3）、62 个终端任务且每个任务 4 次尝试的排行榜：27,280 次运行、83B token。其主张是：换模型后，性价比最高的 harness 也会改变——在 GLM-5.3 下 Codex CLI 的每次通过成本最低（$0.803），但在 Kimi-K3 下按每任务成本只排第 16，且同一模型内最好与最差 harness 的成本比在 1.8 倍到 5.0 倍之间。双因素方差分析（two-way ANOVA）把 92.8% 的成本差异归因于模型，仅 2.3% 归因于 harness 本身，4.9% 归因于二者组合；64.5% 的支出花在了未通过的试验上，另有 216 次试验被标记为 reward hacking（其中 163 次是联网查找答案，计 0 分）。

**讨论**: 评论区分成两派：一派对这些数据感兴趣，一派质疑其论述框架。最强烈的反驳来自一位自己跑了 927k 次运行实验的评论者，他发现 harness 与模型之间的交互效应很小，与文中核心主张相矛盾（OpenAI 的模型确实表现出一定偏好）；他还抱怨这 62 个任务（17 个来自 Terminal-Bench 4，45 个来自 TB 2.1）从未给出选取理由，看起来是精心挑选的。作者回应称用完整数据集太贵，任务清单已发布在 Harbor hub 上。有多人认为 64% 的失败成本并不意外——失败的尝试正是搜索发生的地方，就像人类做原型也会失败一样——并认为「每次通过的步数可预测成本」近乎同义反复，因为成本本来就与 token 成正比。实践者补充说，在各自的工作中，针对特定领域的定制 harness 胜过任何通用 harness；测试的二值通过/失败无法反映代码质量；而且结果只覆盖由单一提供商服务的开放模型，因此像 Claude 或 GPT 这样的闭源模型可能会重排榜单。Runta 的创始人现身总结结论，但因文字疑似 AI 生成而被版主标记。

## 13. Elephant-Goldfish Model {#story-13}
*HN 第 21 名 · [egm.dev](https://egm.dev/) · 40 分 · 16 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50515291)*

EGM 是一个面向 AI 助手的开源插件，以 egm.dev 上的一个落地页形式分发，附有面向 ChatGPT/Codex 桌面端以及若干 CLI 工具的安装说明。方法是这样：你先和一个了解背景的助手一起起草计划，然后让从未看过这段对话的「goldfish」评审去读这份计划，报告其中缺失或不清楚的地方——其理论依据是，作者的隐性知识会留下只有无上下文读者才能发现的空白。它改编自 Dave Rensin 的文章「Elephants, Goldfish, and the New Golden Age of Software Engineering」；页面本身内容单薄，大多是安装步骤和宣传说辞，没有任何基准测试或数据。

**值得一读的评论**
- [gopalv](https://news.ycombinator.com/item?id=50534950): gopalv 认为，自从分支预测失败成为瓶颈之后，位图就不再流行了；现代列式引擎改用紧凑选择向量，因此一次 1024 行、仅 1 个匹配的扫描只需几次分支判断，而不是 1024 次检查。

- [remywang](https://news.ycombinator.com/item?id=50532657): remywang 指出，PAX 的行组是页大小的，而 Parquet 的行组要大得多，并询问是否有人追溯过这一设计变化的起源。

## 19. 用 Turbo Pascal 编写的 Turbo Pascal 编译器 {#story-19}
*HN 第 31 名 · [turbo51.com](https://turbo51.com/compiler-design/tpc16-turbo-pascal-compiler-written-in-turbo-pascal) · 91 分 · 38 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50509456)*
*原标题: Turbo Pascal Compiler Written in Turbo Pascal*

Igor Funa 的 TPC16 是对 Borland 的 TPC.EXE 从零开始的重实现，声称与 Turbo Pascal 7.0 在源码级和二进制级兼容：语法相同，生成的 TPU 单元和 16 位 x86 输出也完全一致，只是明确排除了 map 文件和 exe 调试信息。这个编译器本身就用 Turbo Pascal 7 编写，目标是自举，不过在 DOS 上受内存限制，自举要靠保护模式编译器 BPC.EXE 完成。演示用的二进制是免费的，但 TPC16 的完整源码是收费出售的；用 Delphi 编译的 32 位版本 TPC32（符号表经过清理、支持长文件名，仍输出 16 位代码，也是作者那个 Turbo51 8051 编译器的基础）价格更高。

**讨论**: 整个讨论串基本上是温馨的怀旧：评论者回忆起 Turbo Pascal 在 8088/80286 机器上近乎瞬时的编译速度、集成调试器、Turbo Vision，以及一个让人觉得后来的 Web UI 开发像是少了一条胳膊的帮助系统。一个很长的子讨论串争论编译为什么变慢了——一方认为优化并不是真正的罪魁祸首，指出单遍、无宏的设计，并举出 D、Ada、OCaml、F# 和 FreePascal 这些编译很快的语言；另一方则反驳说现代类型系统和单态化让变慢成为内在特性，还有几个人指出 Turbo Pascal 确实有窥孔优化和其他优化，剩下的部分由内联汇编器补足。多人都指出这不是开源的：完整源码需要付费（一位评论者提到 TPC32 要 150 欧元，只能下载 24 小时）。其他人补充了相关项目和参考——Pasta80、berotinypascal、DRI Pascal MT/+，以及 turbopascal.org 上一个讲该编译器内部原理的页面。

**值得一读的评论**
- [joakleaf](https://news.ycombinator.com/item?id=50532147): 一位实践者的详细比较：Turbo Pascal 经过优化、不带检查的代码质量依然很好，相比之下，在 386/486 硬件上转向 Turbo C 以及后来的 DJGPP，感觉慢得令人痛苦。
- [plinkplonk](https://news.ycombinator.com/item?id=50532638): 一个有用的纠正埋在销售页面很靠下的地方：源码并非开源，TPC32 要 150 欧元，24 小时内可下载两次。
- [hnlmorg](https://news.ycombinator.com/item?id=50531667): 解释了实际的速度差异——Pascal 只需要单遍编译、没有宏，而现代编译器要处理宏、多遍和中间表示，换来的是可组合性和可移植性。

## 20. 我们不需要更多应用，我们需要更好的开源 {#story-20}
*HN 第 34 名 · [jordankrueger.com](https://jordankrueger.com/blog/better-open-source-not-more-apps/) · 325 分 · 212 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50532086)*
*原标题: We don't need more apps, we need better open source*

这是 Jordan Krueger 的博客文章。他是一名顾问，为进步派非营利组织运行自托管基础设施（Synapse/Element Matrix、Coolify、Hetzner、Paperless-ngx）。他主张，AI 辅助编程应该用在现有开源软件那些不起眼的日常维护上，而不是再做一个周末习惯打卡应用。他想要四件事：更快的工具（引用 Astral 基准测试中 uv 比 pip 快 8–10 倍的数据）、一条命令就能装好且默认配置合理、更友好的「第二天」运维体验（管理界面、安全升级、备份、有用的报错信息），以及更轻的资源占用，让软件能跑在一台 5 美元的 VPS 或树莓派上。他引用 2024 年的 xz 后门事件作为维护者脆弱的证据，并提到 curl 在 2026 年 1 月因大量伪造的 AI 生成安全报告而终止了漏洞赏金计划——而到 4 月，报告大多变成真实的 AI 辅助报告，新问题变成了数量本身——最后他给出几条礼仪规则：先和维护者沟通、带上测量数据、保持改动小、披露 AI 使用情况。

**讨论**: 讨论串在 AI 贡献是否真有帮助这一点上分裂了。一位维护者（joshdata）说，他的仓库现在收到的 PR 都是在处理假想出来的困扰和边缘情况，他根本没时间分诊，他可能会干脆关闭仓库的贡献入口；其他人也认同，写一个补丁的成本降到了零，但审查一个补丁的成本没有降，并提出给 PR 设置付费墙或托管押金、要求先开 issue 才能提 PR、把合并权限下放给可信贡献者，或者编写 AGENTS.md 指南。反方观点来自用 AI 做贡献的人：这些报告通常是他们亲自验证过的真实 bug，而且仓库的指南也被遵守了——其中一人说，在被告知「不要用 AI」之后他就把项目 fork 了。第二个争论围绕文章的前提：几位评论者说，用 LLM 定制生成一个工具，比跟现有工具较劲要好（其中一人在折腾 DAW 配置失败好几天后，大约 3 小时就做出了一个 8 通道 VST 播放器）；另一些人则说这是技能问题，或者警告说这类一次性软件互不兼容，而且没人维护。大家还普遍认同，作者是从非营利组织系统管理员的视角写作的，并对标题持怀疑态度——很多领域根本还没有足够好用的应用——此外还有反复出现的抱怨：「vibecoding」现在意味着粗制滥造、大多数维护者在 AI 出现之前很久就对补丁关门了，以及这些都没有解决资金问题。

**值得一读的评论**
- [joshdata](https://news.ycombinator.com/item?id=50532598): 一位维护多个项目的维护者说，AI 让他的入站 PR 从修复真正严重的 bug 变成了假想的边缘情况和小麻烦，他可能会关闭仓库的贡献入口，或者干脆彻底停止维护。
