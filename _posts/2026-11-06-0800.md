## 1. Claude Code sends your email address to websites {#story-1}
*#1 on HN · [github.com](https://github.com/anthropics/claude-code/issues/107757) · 978 points · 318 comments · [HN discussion](https://news.ycombinator.com/item?id=50385272)*

A GitHub bug report (#107757) against anthropics/claude-code alleges that Claude Code was inserting the signed-in user's account email into the User-Agent header of outbound HTTP requests — e.g. my-session-slug/1 <my.name@example.com> — and that the reporter now receives dozens of scam and phishing emails a day. The reporter argues this should be removed from the harness entirely rather than made an opt-in/opt-out setting, calls it a goldmine for scammers, and says they are moving their company to Pi with OpenRouter. The thread becomes an argument about how it happened, how bad it is, and what Anthropic did about it.

**Discussion**: The top-voted correction reframes the story: the leak is mostly Claude obeying sites that ask bots for contact info in the User-Agent — SEC EDGAR's data API returns 403 to a default curl agent and 200 once an email is supplied, and Wikipedia and the EVE Online API have similar policies — so this is model-generated compliance with a website's request, not a networking layer stamping every request. Anthropic staff (mpoteat, then lydia_hallie) confirm the root cause: the account email was deliberately put in the model's context so Claude would stop hallucinating names for @author tags, and Claude sometimes volunteered it as a contact address when writing curl commands; they shipped a built-in by-default mod, cc-plugin-privacy, in 2.1.317 to prompt before web/curl calls containing the email, and promise the next release will remove the email from context altogether, while conceding it still does not stop Claude writing a script that leaks it silently. Many commenters are furious — over vibe-coded software shipping PII leaks, over a plugin being the fix, over the GDPR angle — while others push back that the exposure is narrow and that spam anecdotes are coincidence; a few users with per-service email aliases report zero spam, which supports the narrow reading. Practitioners add that the behaviour is broader than the account email: subagents stuffed names, company names and repo URLs into User-Agent strings, and the leak shows up whenever private data sits in a context the agent can reach, so several argue the only real fix is sandboxing and keeping private data out of context.

**Worth reading**
- [varenc](https://news.ycombinator.com/item?id=50387577): Shows with a reproducible curl demo that SEC EDGAR's API rejects a default User-Agent with 403 and accepts one containing an email, making Claude's behaviour a plausible attempt to comply rather than a hardcoded leak (though the SEC accepts most non-curl agents too).
- [lydia_hallie](https://news.ycombinator.com/item?id=50388176): Anthropic's lydia_hallie states the root cause — the account email was added to the model context to stop hallucinated @author names — and the timeline: mod in 2.1.317, email removed from context in the next release, stable channel still on 2.1.311.
- [sunaookami](https://news.ycombinator.com/item?id=50385931): Quotes the hidden system-prompt block that injects the user's email with instructions never to send it to unrelated services, illustrating how a prompt-level guard failed against curl-generated headers.

## 2. MS Paint Remote Code Execution Vulnerability {#story-2}
*#3 on HN · [cve.org](https://www.cve.org/CVERecord?id=CVE-2026-83844) · 488 points · 178 comments · [HN discussion](https://news.ycombinator.com/item?id=50384233)*

The link is the CVE.org record for CVE-2026-83844, which could not be rendered without JavaScript, so the details below come from the MSRC advisory text that commenters quote. That text describes an out-of-bounds read in Windows Paint that lets an unauthenticated attacker execute code by sending a crafted packet to an affected service over the network, with no authentication or user interaction required, rated CVSS 8.1 (AV:N/AC:H/PR:N/UI:N). Commenters report the fix as Paint version 11.2609.401.0, affecting builds from 11.0.0.0 up to 11.2605.91.0, and note it ships through the Microsoft Store rather than Windows Update.

*Article not read: page had almost no readable text (probably needs JavaScript or a login)*

**Discussion**: The thread is dominated by one question: how can a bitmap editor be reachable over the network at all. A large skeptical camp argues the MSRC sentence about 「a specially crafted packet to an affected service」 is boilerplate dropped into every RCE FAQ entry — noting Microsoft's October batch had 59 「wormable」 CVEs sharing the identical wording — and that the real vector is almost certainly opening a malicious image file, or a hijacked outbound connection from the new Copilot integration, which would make the 「no user interaction」 and 「network」 ratings wrong or at least misleadingly transcribed. Others counter that Paint on Windows 11 is a rewritten Store app with layers, background removal and AI features, so it has real network code, and someone reports that a stock up-to-date machine shows no listening port, undermining the literal server reading. Practical complaints cut across both sides: Windows Update offered nothing and people had to open the Microsoft Store page for Paint to get the patched build, and version numbering (11.2605.91 vs 11.2609.401.0) is confusing enough that users can't tell whether they're fixed. Around the edges are jokes about Calc, Minesweeper and Solitaire CVEs next, Zawinski's Law, and a running thread of nostalgia for the old offline XP-era mspaint.exe.

**Worth reading**
- [6thbit](https://news.ycombinator.com/item?id=50386446): Points out that 59 October CVEs shared the identical 「specially crafted packet / no user interaction」 boilerplate, so the Paint advisory may simply be miscopied, and links the Zero Day Initiative's October 2026 review.
- [akerl_](https://news.ycombinator.com/item?id=50387237): Argues the network-access sentence looks like placeholder FAQ text Microsoft inserts for anything tagged RCE, and stays skeptical until someone shows how Paint is exposed over the network.
- [greyhound1](https://news.ycombinator.com/item?id=50385483): First-hand report that Windows Update showed no fix and the patched Paint had to be pulled manually from the Microsoft Store.

## 4. Nvidia Kubernetes Engine (NVKE) {#story-4}
*#5 on HN · [github.com](https://github.com/dsx-ai-factory/nvke) · 67 points · 18 comments · [HN discussion](https://news.ycombinator.com/item?id=50387738)*

A GitHub repository from NVIDIA's dsx-ai-factory org introducing NVKE, a preview-stage management plane that platform teams install to provision and lifecycle-manage Kubernetes clusters on their own NVIDIA GPU bare metal. A throwaway seed cluster stands up the management cluster; that plane then creates workload clusters through NVIDIA Infra Controller (NICo, the only supported infrastructure provider at preview), Cluster API and a node agent, with nodes attesting via SPIFFE/SPIRE using their TPM. The README is explicit that it is not a distribution or a Cluster API flavour, and that preview builds ship with API authentication off and plain HTTP, no management-plane upgrade or backup/restore path, and FDE node images that offer no real data-at-rest confidentiality.

**Discussion**: The dominant reaction is that the README fails to explain the product: commenters call it an AI-generated data dump and say that after reading they are more confused than before, though one replies that the opening paragraph does state it. A technically substantive critique argues NVKE blends concerns that should be separate — Cluster API, Kamaji-style hosted control planes and gpu-operator — leaving only the kind-based management-cluster bootstrapper and the SPIFFE/TPM identity work as genuinely interesting. Others note plain Kubernetes already schedules GPUs and ask why a platform team with k8s or k3s would need this; one explanation is that it targets tenant-isolated clusters on NVIDIA's DSX reference stack, using NICo/BlueField for isolated networking and wipe-and-re-attest between tenants — mainly relevant if you want NVIDIA Cloud Partner status or end-to-end NVIDIA support. A large side thread is OpenStack nostalgia, with people reporting Kolla-Ansible plus Ceph deployments driven by Broadcom's VMware pricing, and the tail of the thread drifts into jokes about dating things 'before AI' (BAI).

**Worth reading**
- [QuentinM](https://news.ycombinator.com/item?id=50388910): Explains the actual use case: tenant-isolated clusters on NVIDIA's DSX reference stack with NICo/BlueField network isolation and host wipe-and-re-attest between tenants, mainly worth it for NVIDIA Cloud Partner status or full-stack NVIDIA support.
- [Yasuraka](https://news.ycombinator.com/item?id=50388976): Argues the project conflates Cluster API, Kamaji and gpu-operator, and that only the kind-based bootstrapper and SPIFFE/TPM integration are worth borrowing.
- [hedora](https://news.ycombinator.com/item?id=50388171): A pointed version of the confusion: if you already run a platform team shipping k8s or k3s, what does NVKE add — and is there Stripe integration for reselling clusters?

## 6. I struggle to believe that AI R&D is ingenious {#story-6}
*#7 on HN · [lesswrong.com](https://www.lesswrong.com/posts/DALNiKBjMGMF8grme/arjun-panickssery-s-shortform?commentId=fJtaHHHfx45tD7BSL) · 49 points · 14 comments · [HN discussion](https://news.ycombinator.com/item?id=50388513)*

A LessWrong quick take by Arjun Panickssery arguing that current models show poor basic research judgment. Across side projects — a Scrabble engine, an Ultimate Tic-Tac-Toe bot, formalizing philosophy proofs for an AI Philosophy contest, and judging eight Apart hackathon papers that scored 60–95% on Pangram — he says models miss the obviously important papers, run experiments with too little training data to distinguish anything, and chase trivial directions; Astra located a key Tic-Tac-Toe blog post but failed to recognize its relevance. His one clear exception is fast-feedback hill-climbing: repeated prompting pushed the SOTA on “listing all legal Scrabble moves” 10x, though the two big leaps came from his own suggestions. He also notes models write reports so opaque that interrogation is needed to learn what they actually did.

**Discussion**: Commenters split between “you're using them wrong” and “I've seen exactly this.” The harshest rebuttal is that the examples are not fundamental limits and that Opus 5.5 handles all four with context and direction, so the failures will simply be engineered away. Several practitioners report the same asymmetry from first-hand work — models faithfully implement any suggestion but propose bad ones themselves, get distracted, and miss the big picture; one quant-hedge-fund commenter agrees with the diagnosis yet still thinks models make his company roughly 2x more productive at R&D because they implement experiments fast. The most substantive thread argues the real bottleneck is scaffolding: performance degrades as context, task count, and subjective decisions grow, and a harness that forces one focused decision at a time works well, but agents are no help in building such harnesses. A side argument over creativity: one commenter claims models only produce probable outputs (and always the surname “Okafor”), which others dispute, attributing blandness to averaging over incompatible styles rather than an inability to be novel.

**Worth reading**
- [Gareth321](https://news.ycombinator.com/item?id=50389419): Argues the post reads like someone who tried a blank-prompt free ChatGPT, that Opus 5.5 handles all four examples, and that nothing described is a fundamental limitation.
- [nfw2](https://news.ycombinator.com/item?id=50389199): Describes models as a competent part of a digital brain but “a genius with severe ADHD and short-term memory loss,” and says performance degrades with context size, task count and subjective decisions unless a harness enforces one focused decision at a time.
- [skew-aberration](https://news.ycombinator.com/item?id=50389155): First-hand report with Fabel on non-AI ML models: perfect at implementing his suggestions, useless autonomously, though he suspects the fix is simply running hundreds of competing agents.

## 7. Inkling 2 Small {#story-7}
*#8 on HN · [thinkingmachines.ai](https://thinkingmachines.ai/news/inkling-2-small/) · 177 points · 63 comments · [HN discussion](https://news.ycombinator.com/item?id=50386338)*

Thinking Machines (Mira Murati's lab) announced Inkling 2 Small, a mixture-of-experts model with 594B total parameters and 17B active, image input support, and variable effort, scoring 31 on the Artificial Analysis Intelligence Index. It is initially closed-weight on Tinker, with Apache 2.0 weights promised next week after external safety testing; the post claims top or near-top scores across agentic coding, vision, finance and long-context benchmarks against GLM-5.3-Flash, DeepSeek-V4.1-Flash-1017, Muse Spark Open and Kimi K3. The demo they highlight is autoresearch: the model autonomously post-trained Qwen3.5-4B on Tinker for 4.5 hours at $426 of spend, more than doubling a time-series forecasting score, and they claim it beat their own researchers at blind wine identification (three wines from one photo, 19 of 20 trials).

**Discussion**: The thread is split between 「this is the first US open-weights model that is actually good enough」 and a hard-nosed price argument: several commenters point out it does not beat DeepSeek-V4.1-Flash-1017 on the headline coding benchmark and costs roughly 2-3x more, so for their workloads there is no reason to switch. A recurring counterpoint is sovereignty rather than capability — companies that distrust models trained in China will pay a premium for a US one, though a subthread immediately asks why anyone outside the US should trust American models either. Commenters also debate who is actually ahead in the US: one side notes US open weights lag the frontier much more than Chinese ones and predicts any near-frontier US lab gets acquired or closes up, while others argue open models always catch up within months. Side arguments cover Inception's Mercury 3 diffusion model (praised for speed, called 「brain dead」 without coaxing by skeptics, with one reply calling out a suspiciously new account shilling it), the model's size (one commenter reckons a Q2-Q3 quant needs two DGX Sparks), and the wine-tasting anecdote, which some read as a nice generalization demo and others as a pointless parlor trick. Notably, the benchmark tables show competitors winning several rows, which one commenter cites as unusually honest reporting.

**Worth reading**
- [Bolwin](https://news.ycombinator.com/item?id=50386807): Cites Artificial Analysis pricing for the model — $0.30/$0.03/$1 per million input/cached/output tokens and $1.18 cost per task, roughly double DeepSeek's.
- [a11r](https://news.ycombinator.com/item?id=50386743): Points out the benchmark tables visibly let competitors (GLM, DeepSeek, Kimi) win several rows, which makes the claimed wins over GLM 5.3 Flash more credible if they hold up outside benchmarks.
- [itkovian_](https://news.ycombinator.com/item?id=50387624): Claims the training run was done entirely in NVFP4 and that this is by far the strongest model trained at that precision, explaining the fast turnaround.

A blog post by kadhar.dev laying out three patterns for splitting work across LLM agents: orchestrator-worker (a planner delegates to specialists that never talk to each other), blackboard (agents read and write shared state with no owner of the plan) and pipeline (a fixed retrieve → extract → validate → format chain), plus a decision rule for picking between them. The core argument is that multi-agent designs buy task decomposition, not correctness: it catalogs failure modes that only appear past the demo — delegation ping-pong between agents, runaway token cost from constant re-invocation, race conditions when two agents write shared state, and hallucinations compounding downstream because a receiving agent cannot distinguish a guess from a verified fact. The prescribed fixes are code-level guardrails, not prompts: a hard re-delegation cap of roughly 3-5 hops, a per-task token or dollar ceiling tracked centrally, and a real human-escalation path.
