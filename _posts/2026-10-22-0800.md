## 1. The recently proposed o(n log n) integer multiplication algorithm [pdf] {#story-1}
*#1 on HN · [web.maths.unsw.edu.au](https://web.maths.unsw.edu.au/~davidharvey/research/subnlogn.pdf) · 145 points · 84 comments · [HN discussion](https://news.ycombinator.com/item?id=50190455)*

A PDF by David Harvey (UNSW) assessing a newly claimed o(n log n)-time integer multiplication algorithm — apparently the result from OpenAI's recent mathematics release, which Harvey calls 「plausible」 even though he admits he has not actually read the underlying papers and finds their exposition hard going. The writeup situates the claim against prior art (the FFT-based O(n log n), Schönhage–Strassen's O(n log n log log n), and Harvey–van der Hoeven's 2019 result) and reflects on what an automated system doing research means for the field. The article itself was not fetchable as a web page, so this summary rests on the title and the thread's quotations.

*Article not read: not a web page (application/pdf)*

**Discussion**: The thread splits into technical nitpicking and a broader argument about AI in mathematics. Several commenters correct the headline's framing: big-O was already achieved via FFT, and the news is little-o — strictly slower growth than any constant multiple of n log n — a distinction explained at length and then itself corrected (limits and constants). On the AI question, one camp argues that if specialists cannot read the paper but a model can explain it, using the model is simply the new reality, and that Lean verification plus formal proof checking is the real safeguard; the other camp, led by several exasperated posters, insists that a validated proof nobody understands is only a proof of something, invoking the Mochizuki/IUT impasse, the possibility of a Lean soundness bug, and LLM error rates. A commenter with first-hand knowledge pushes back on the article's claim that no formalization exists, reporting a Lean development already done with Mathlib's TM2 machine. Rough consensus on the practical side: the result is theoretical only, irrelevant to any integer that fits in real hardware.

**Worth reading**
- [jdb1729](https://news.ycombinator.com/item?id=50191011): Reports that the o(n log n) result is already fully formalized in Lean (with platypii, on Mathlib's TM2 machine), currently at exponent 1-2^-14.38, contradicting the article's claim that no such proof exists.
- [krackers](https://news.ycombinator.com/item?id=50191565): Gives the clearest walkthrough of the algorithm's lineage — FFT convolution, Schönhage–Strassen's cheap root-of-unity ring, Gaussian resampling in the 2019 O(n log n) result, and OpenAI's trick of computing several butterfly layers simultaneously.
- [DannyBee](https://news.ycombinator.com/item?id=50192000): Argues the step Harvey says he cannot follow — why g < m is impossible — is not hard: each slice call can at most double the nonzero entries while 2^m are needed, with an Astra-generated variant of the argument linked.

## 2. There isn't an easy exploit for this PHP vulnerability {#story-2}
*#2 on HN · [eliastaylor.com](https://eliastaylor.com/noexploit/) · 445 points · 220 comments · [HN discussion](https://news.ycombinator.com/item?id=50188948)*

这是 Elias Taylor（论坛用户名 zkldi）发布的一篇博客文章，其中论证：近期被广泛报道的 PHP 核心内存破坏漏洞「php2shell」（CVE-2026-109618 / CVE-2026-109619，CVSS 10）确实存在，但并不像 Log4Shell、Heartbleed、Shellshock 或 RoR YAML 反序列化那样容易利用。作者称，GitHub 上有数千个「PoC」，但没有一个能针对未修改的 PHP 实例运行；许多 PoC 依赖预先存在的本地文件包含（LFI），或者干脆修改服务器，使其变得脆弱，而这通常是 LLM 生成的。他认为，恐慌部分源于一位 PHP 核心开发者的「补丁发布 15 分钟后就会出现漏洞利用」的评论、人们对 PHP 安全性的既有印象，以及一段带有动漫女孩的漏洞利用视频。

**Discussion**: 评论者严重分歧。怀疑者首先攻击文章本身：一位评论者指出 eliastaylor.com 三天前才注册，没有联系方式，并认为一位匿名博主无权做出这种绝对断言；另有评论者反驳说论点本身成立与否才是关键，并指出该域名/作者已通过另一篇博客文章和 zkldi 的 HN 账号得到验证。另一些人则反驳文章的核心主张：letmevoteplease 引用了 Wiz、Calif 和 PHP 基金会的说法，即该漏洞在默认配置下可被利用（包括 Apache mod_php 上的远程代码执行，以及 WordPress、Drupal、Joomla 上的预认证 RCE），而 Trail of Bits 的 CEO dguido 表示，他的两名员工分别在约 4 小时内针对未修改的 MediaWiki 写出了可用的漏洞利用程序。多位从业者报告了自己测试的结果：一人运行了两个 GitHub PoC，其中一个实际上只是借助 LFI 的间接利用，另一个需要修改才能触发过期的写入（stale write），但没有实现 RCE；另一人只有在把易受攻击的脚本放进 webroot 之后才复现出该行为。一场平行的、往往更激烈的争论则认为时间线才是真正的丑闻：管理员抱怨有 12 小时几乎没有人了解任何细节，而 Cloudflare 的 CTO 发帖称发生了漏洞利用尝试，这迫使一些人因风险而主动下线，而不是因为恐慌；还有一些人反驳说，在没有补丁的情况下为政府或医疗系统承担风险是不合理的，而且缺少公开 PoC 并不能证明不存在私有的、已被武器化的漏洞利用程序。相当一部分人同意打补丁是正确的，但认为 CVSS 10 的评分和营销式披露（php2shell.com、patchtheplanet.org）被夸大了。

**Worth reading**
- [dguido](https://news.ycombinator.com/item?id=50191174): Trail of Bits 的 CEO 表示，他的两名员工分别用约 4 小时各自写出了可用的漏洞利用程序，并针对未修改的 MediaWiki 验证通过——这直接反驳了「这是不可利用的」这一说法，不过他也同意编写漏洞利用程序仍然需要专业知识。
- [letmevoteplease](https://news.ycombinator.com/item?id=50190765): 直接引用 Wiz、Calif 和 PHP 基金会的话说，该漏洞在默认配置下可被利用，这表明该漏洞能在普通的 PHP 安装与 Hello World 脚本上生效，而不只是在预先被攻陷的服务器上。
- [Tadpole9181](https://news.ycombinator.com/item?id=50189461): 一名从业者指出，文章中「大家为什么害怕」这一节没有抓住重点：真正的失败在于 12 小时的几乎完全沉默、含糊的警告，以及一条关于漏洞利用流量的推文，这让管理员在毫无信息的情况下不得不决定是否让站点下线。

## 3. OpenAI CLI {#story-3}
*#3 on HN · [github.com](https://github.com/openai/openai-cli) · 30 points · 8 comments · [HN discussion](https://news.ycombinator.com/item?id=50191507)*

OpenAI 在 GitHub 上发布了 openai-cli，一个用 Go 编写的官方 REST API 命令行工具（要求 Go 1.26+，也可 brew install openai/tools/openai）。它围绕资源组织命令（openai files upload、openai images generate、openai admin organization usage 等），支持 JSON/JSONL/YAML/raw 输出，可借助 GJSON 的 --transform 做数据提取，并自带更新检查（最多每七天显示一次提示，可用 OPENAI_CLI_NO_UPDATE_CHECK=1 关闭）、命令补全、@file 文件读取和 OPENAI_UNTRUSTED_STDIN 安全模式；mTLS 认证仍处于 beta，图片生成默认使用名为 gpt-image-2.5-sunburst 的模型，并把结果保存到 ~/Downloads/gpt-images/。

**Discussion**: 讨论几乎没有落在工具本身的功能上，人们主要怀疑的是 OpenAI 长期维护自家工具的能力：一条高赞评论警告说，OpenAI 的几乎所有东西都在不到两年内被弃用，有时甚至没有正式通知，还称这些工具看起来像「vibecoded」，缺乏审查，并声称报告 bug 的用户曾被 GitHub 拉黑。有人反驳，认为有 bug 的软件并不能带来收入，公司成功也不代表不会犯错；另一位评论者则更悲观地认为，所有新软件现在都在走向由 agent 生成代码，而可读的代码库终将被这种潮流取代。几位评论者则试图搞清这款 CLI 的定位：Codex 是 agent harness，而这个 CLI 只是对 API 的一层包装，有人对此不以为然，说这基本上就是「curl？」。还有人猜测，真正的动机是让模型学会使用自家工具，以便进行强化学习训练。

**Worth reading**
- [throw20261022](https://news.ycombinator.com/item?id=50191829): 这位评论者警告说，OpenAI 过去会弃用大部分工具，MathJax 有时甚至没有通知；而且对于 GitHub 上的问题报告，它往往会拉黑报告者，而不是去修复问题。

## 4. WorldTUI: I trained a 360M model to pretend to be a terminal {#story-4}
*#4 on HN · [simedw.com](https://simedw.com/2026/10/21/world-model-terminal/) · 71 points · 33 comments · [HN discussion](https://news.ycombinator.com/item?id=50190363)*

A hobby project by simedw that fine-tunes Qwen2.5-Coder-0.5B to act as an entire terminal: there is no shell or filesystem, only a model that predicts how the character grid changes after each keypress, including vim, tmux, man pages and a game of snake. Training data was 336k synthetic sessions (~2B tokens) recorded from real programs in Docker, plus DAgger-style self-correction rounds; memory readbacks rose from 2/13 and 3/13 for prompted baselines to 9/13, and PresetBench went 24/47 to 38/47 at int4. Decoding rows in parallel with speculative verification cut large-frame p95 latency from 6.7s to 0.87s; trimming the 151,936-token vocabulary to 333 and quantizing to int4 shrank the model to 208 MB, running locally in the browser via WebGPU shaders in WGSL. Total cost: about 75 GPU-hours on an RTX 4090.

**Discussion**: The thread splits between people who think this is a preview of learned UIs (one commenter calls it regretfully the future, needing only fast local models) and skeptics who ask why you would burn a GPU on a non-deterministic process when a real program does it on the CPU in milliseconds — a counter-counter-argument notes we already accepted gigabytes of Chromium and JavaScript for developer convenience, not performance. Several commenters map it onto existing work: Microsoft's WHAM Quake II world model, DeepMind's Genie, a GPT-3-era hallucinated OS demo, and an older HN thread. Practical questions got answered by the author: the sleep/time behaviour comes from a WAIT or sleep token fed in when nothing is pressed (normal frames are only triggered by keypresses), and he says larger models are also better at memory, though he hasn't run extensive tests. One reoccurring theme is that this is a curiosity-driven exercise rather than a product — several people answer the blunt 「where is the point of this if I have a terminal?」 with 「because it was there」, and one notes it could be a cheap way to study systems traces without real accelerators. A question about whether the model is aware of window width went unanswered.

**Worth reading**
- [simedw](https://news.ycombinator.com/item?id=50191986): The author clarifies the mechanism behind `sleep`: only keypresses normally advance a frame, and a separate sleep token tells the runner that time is moving.
- [skohan](https://news.ycombinator.com/item?id=50191968): The sharpest counter-argument to the world-model-UI thesis: why run a non-deterministic GPU process with gigabytes of VRAM for something a CPU program does in milliseconds.
- [psandor](https://news.ycombinator.com/item?id=50191555): Points to Microsoft Research's WHAM, a Quake II world model where the whole game is generated by a model — the closest large-scale precedent for this project.

## 5. Security Disclosure {#story-5}
*#5 on HN · [blog.railway.com](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) · 416 points · 237 comments · [HN discussion](https://news.ycombinator.com/item?id=50188228)*

Railway's incident note says that on the morning of Wednesday, October 21, 2026 it detected anomalous activity in the systems that store customer environment variables, and that an unauthorized third party may have read encrypted variables and obtained the decrypted contents of some of them — API keys, database and registry credentials. Railway says it believes the campaign is part of a series of attacks on platform companies aimed at compromising AI inference providers, has told upstream providers to revoke keys proactively, recommends all customers roll every environment variable and registry credential, and has paused all deployments while it investigates, which means rotated credentials cannot be redeployed yet.

**Discussion**: The thread is dominated by rage at the sequencing: customers rotated keys at 5am and immediately broke their own running services, because changing environment variables requires a redeploy and deploys are frozen. Railway's Angelo (ndneighbor) showed up to defend the delay as 「aviate, navigate, then communicate」 — not wanting to tell people to roll keys before the breach was contained — and was met with a near-uniform rebuttal that disclosure should be immediate and uncertain scope means warn everyone; several said the choice between a leaked key and a downed product is no choice at all. Below that, the thread turned into a survey of a very bad week: the PHP RCE, the eMudhra certificate compromise, GitLab patches, LiteLLM, and especially the PingCAP/TiDB Cloud breach, which people called the worst of the lot. A side argument over whether environment variables are a bad place for secrets drew a correction from tptacek that env vars injected at launch are fine and that .env files, not env vars, are the problem — and that the likely target here was Railway's secrets database, not anyone's shell environment. Much of the rest is churn: people announcing migrations to Render, Cloud Run or bare VPSes, and a long tangent about a commenter taking his first vacation of the year.

**Worth reading**
- [ndneighbor](https://news.ycombinator.com/item?id=50189987): Railway's Angelo (ndneighbor) gives the company's side: they held the warning until mitigations were verified, call it a highly motivated attacker, promise a formal postmortem, and say he personally feels he let everyone down.
- [cowlby](https://news.ycombinator.com/item?id=50190145): A customer posts audit-log lines from Oct 21 showing Railway Staff regenerating their bucket instance credentials three times, plus the worry that env-var-stored database and bucket credentials mean the attackers saw data too.
- [tptacek](https://news.ycombinator.com/item?id=50189064): tptacek pushes back on the 「env vars are terrible for secrets」 consensus: env vars injected at launch are fine, .env and profile files are the real problem, and the breached database of variables is the plausible culprit here.

## 6. GitLab critical patch release {#story-6}
*#6 on HN · [docs.gitlab.com](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/) · 316 points · 74 comments · [HN discussion](https://news.ycombinator.com/item?id=50185869)*

GitLab 于 2026 年 10 月 21 日发布 19.5.1、19.4.3、19.3.6、19.2.9、19.1.9、19.0.10 和 18.11.13 等补丁版本，共修复 12 个漏洞。其中 CVE-2026-110264 最严重，CVSS 评分 10.0：由于正则表达式编译器中的整数溢出，未认证用户可以在 GitLab 服务器上执行任意代码；该漏洞影响从 7.0 起的所有版本，由 joaxcar 通过 HackerOne 报告，并特别回补到 18.11.13。其余漏洞包括 OmniAuth 与 LDAP 自动关联邮箱查询导致的账号接管（CVE-2026-15723，8.2）、OAuth/OIDC 发现端点的缓存投毒（CVE-2026-112212，7.5）等；GitLab.com 与 Dedicated 已完成修补。

**Discussion**: 讨论很快从补丁本身转向漏洞的可利用性：dvdkon 认为必须认证并上传恶意的 org-mode 文件才能触发，merb 则反驳说只要实例上存在一个公开项目、能存放 .org 载荷，攻击就无需认证，因此全部需要登录的自建实例相对安全。多人追问这到底是 Ruby、Rails 还是 GitLab 的 bug，wiml 指出 GitLab 自带一份 Ruby Onigmo 正则引擎的分支副本，而 bradly 猜测这是 ruby/ruby PR 16801 的回补。另一大主题是 AI 驱动的漏洞发现：一部分人认为我们正进入 IT 安全的至暗时刻，另一部分人则预期会进入「黄金时代」，即自动化扫描普及后系统反而更安全，也有人反驳说 AI 生成代码的速度会超过扫描能力。关于标题的争论中，tptacek 表示 CVSS 10.0 本身说明不了什么（Shellshock 就没拿到 10 分），提交者随后把标题从「CVSS 10.0」改成现有的措辞。此外有人报告升级到 19.5.1 后仪表盘仍提示需要升级，artooro 回应说更新检查器一向滞后数小时；muvlon 还指出同一天 musl libc 也披露了一个正则编译器整数溢出的 CVE。

**Worth reading**
- [merb](https://news.ycombinator.com/item?id=50188337): merb 指出触发路径无需认证，只要实例上有一个可存放 .org 载荷的公开项目即可，因此全站强制登录的自建实例风险较低。
- [wiml](https://news.ycombinator.com/item?id=50187490): wiml 查明了根因位置：GitLab 自带一份 Ruby Onigmo 正则引擎的 fork 副本，因此漏洞出在这份副本而不是上游 Ruby。
- [tptacek](https://news.ycombinator.com/item?id=50186783): tptacek 认为 CVSS 评分是「通灵板」：Citrix 目录遍历和 Cisco Broadworks SSO 绕过都拿过 10.0，Shellshock 却没有，所以分数本身不说明严重性。

## 7. Rust Style Guide {#story-7}
*#8 on HN · [google.github.io](https://google.github.io/styleguide/rustguide.html) · 275 points · 158 comments · [HN discussion](https://news.ycombinator.com/item?id=50186010)*

Google 公开发布的 Rust 风格指南，适用范围覆盖 Android、Chromium、ChromeOS 和 Fuchsia。它的“style”不只指格式化，还包括 API 与实现设计：禁止 glob 导入、公共 enum 与含公共字段的 struct 一律加 #[non_exhaustive]、优先借用而非深拷贝、Chromium 内禁止 async/.await 与 std 线程（改用 fuchsia_sync::Mutex）、use 语句按 imports_granularity = Module 拆成单模块导入、顶层函数需带模块名调用、Chromium 的 rust_library 用扁平单目录布局并倾向拆成小 crate。文档明确区分库代码（规则有约束力）与应用代码（强建议），并把方便大规模自动化改动（LSC）列为核心目标之一。

**Discussion**: 最大争议是公共 enum 强制 #[non_exhaustive]：多位评论者认为这废掉了 Rust 枚举最大的价值——新增变体时编译器强制逐处检查，把编译期错误变成运行期漏判；反方（包括为 Google 辩护者）指出不加则新增变体就是 semver 破坏性变更，在 google3 这种巨型 monorepo 里会造成下游大面积编译失败和无谓 churn，且与 protobuf 枚举语义一致。Chromium 的“小 crate、不嵌套目录”规则也遭质疑像 2010 年“函数越小越好”的教条，有 Chromium 相关经验的人解释这在内部构建系统下是成本很低的：crate 是并行编译与缓存的单位，且能强制依赖声明、杜绝模块循环依赖。另有关于类型是否该不加限定导入的往返争论（io::Error 这类歧义名称反而应保留限定），以及一条支线在吵“有了 LLM 还要不要风格指南”。整体没有共识，但多数人认可这份文档把散落各处的惯例集中成文很有价值。

这是 Ryan P. Burge 的 Substack 通讯 Graphs About Religion 的一篇文章，基于他与圣母大学本科生 Anna Bohlen 于 2025 年 8 月通过 Qualtrics 开展的一项调查，论文由圣母大学 de Nicola 伦理与文化中心的一项 Sorin Fellows 资助。在 557 名受访者中，最年轻的成年人有 38% 表示自己「非常」或「有些」远离自己道德上应当成为的那个人，而 55 岁及以上受访者中只有 6% 持相同看法；老年人称自己每天都在努力改善性格的比例还高出约 11 个百分点，但更少反复思虑（55 岁以上只有三分之一的人表示自己经常反思行为）。在宗教上活跃的人比不参加宗教活动的人或非宗教人士反思多得多（年轻成年人中为 53% 对 27%），但年龄最大的非宗教受访者最可能觉得自己已经「抵达」（近十分之六，而两个宗教群体约为 47%）；作者把这一点列为宗教可能灌输更高道德标准的可能解释，并提醒所有数据都是自我报告，且样本量小。

**Discussion**: 最高票评论把周日弥撒比作全员大会，会上员工被宣贯 CEO 的愿景，并被要求自查与这一愿景的一致程度；随后几条回复反驳说，天主教弥撒和东正教礼仪与此完全不是一回事，有些牧师才是心理变态。评论串的主体很快偏离原文，转向随年龄增长性欲下降是否带来内心安宁：几位中年男性表示，不再被二十多岁那股持续不断的驱动力支配是一种宽慰，其中一位还细致描述了这种转变，即现在看到有魅力的人只剩下审美感受；也有一个人反驳说自己的性欲仍远高于周同龄人，并认为随着年龄增长变得更平静与纯粹与性无关。其他分支争论自由意志（一方说没有任何证据支持自由意志，另一方回以「缺乏证据不等于证据不存在」），还纠正一条将一个自宫者归因于圣奥古斯丁的轶事：那其实是奥利金，而且割除生殖器一直被主流基督教传统视为罪。至少有一位评论者质疑文章的核心前提，即典型美国人总是在寻求自我提升，而另一些人只是开玩笑说，图表给出的答案是「我们根本不会变成那个人」。

**Worth reading**
- [ButlerianJihad](https://news.ycombinator.com/item?id=50190498): 纠正了那则自宫轶事：奥利金而非圣奥古斯丁，而且这种做法在整个基督教传统中一贯受到谴责。
- [avazhi](https://news.ycombinator.com/item?id=50191885): 用第一手经历反驳性欲衰退等于内心平静的说法：接近 40 岁，性欲仍高于年轻熟人，却更平静，并否认性欲是满足感的前提。
- [tasty_freeze](https://news.ycombinator.com/item?id=50190316): 一位 62 岁男性具体描述了这种变化：现在看到有魅力的人带来的感觉，与年轻时看到有魅力的人完全不同，纯粹是欣赏。

## 19. Claude Duet {#story-19}
*#40 on HN · [claude.com](https://claude.com/resources/articles/claude-duet) · 72 points · 8 comments · [HN discussion](https://news.ycombinator.com/item?id=50186455)*

Anthropic's launch post for Claude Duet, a research preview of a proactive agent app — standalone on iOS and Android plus claude.ai — built on Claude Opus 5.5 and initially limited to Pro and Max users in the US via a waitlist. Duet sends a morning brief across connected apps, messages only when something needs you, and runs long tasks on its own virtual machine with its own browser so your devices can be off; it uses the 6,000+ connectors in the Claude Marketplace (Gmail, Slack, QuickBooks, Stripe, Gusto, HubSpot, Docusign, Shopify, Canva) and can pay via Stripe's Link or Shop Pay with 1Password sign-in coming later. Anthropic says sends, payments, signatures and deletions require explicit approval, that trading securities and moving money between accounts are blocked even with approval, and that a new classifier plus safety prompt blocks sharing credit card numbers and government IDs; background checks count against normal plan usage limits.

**Discussion**: The thread is small and mostly sidesteps the announcement itself, turning into an argument about whether Anthropic's weakness is the model or the harness around it. One commenter worries the app will be buggy and says Meta's Muse beats Anthropic on non-model implementation; a reply calls Muse terrible outside web search and info aggregation, saying it remembers nothing, builds poor artifacts and is only good at shopping help. The original commenter concedes the distinction is getting hard to draw, and a third agrees Muse has a good harness but a lackluster model that makes mistakes and takes shortcuts, while another asks for concrete failure examples that were not supplied. The only other substantive thread argues these agents should run in trusted execution environments, citing Brave's browser-AI E2EE writeup, with a reply asking which specific part TEE attestation would actually improve. No consensus emerges, and nobody in the thread reports actually using Duet.

**Worth reading**
- [nh23423fefe](https://news.ycombinator.com/item?id=50187775): Pushes back hard on the Muse comparison, saying outside web search and info aggregation Muse remembers nothing, builds poor artifacts and mainly helps with shopping.
- [anderber](https://news.ycombinator.com/item?id=50190674): Draws the harness-versus-model distinction explicitly: Muse's harness is good but the model behind it is lackluster and prone to mistakes and shortcuts.
- [privacyishuman](https://news.ycombinator.com/item?id=50186583): Argues agent apps like this need trusted execution environments, linking Brave's post on browser AI end-to-end encryption — a point a reply immediately questions.

## 20. The bridge to agent-scale Git infrastructure {#story-20}
*#44 on HN · [github.blog](https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/) · 60 points · 17 comments · [HN discussion](https://news.ycombinator.com/item?id=50183344)*

GitHub 工程博客详细介绍了 Git 存储迁移的下一阶段：目前 99.99999% 的仓库已同时存在于自有数据中心和 Azure 中；第一个 Azure（美国中部）副本于 2025 年 8 月上线，如今大多数仓库的五个副本中有两个位于 Azure，Azure 承载约一半的 Git 流量。文章解释了一项变更，即把 Spokes 的写入法定人数（quorum）范围从整个仓库缩小到单个引用，这就消除了每次写入都要等待约 25ms 跨区域往返、而且写入还要经过仓库级锁的串行化瓶颈；GitHub 报告称，在内部测试中，不同引用的写入吞吐量提升了 3–4 倍。文章随后介绍了由 Azure Blob Storage 支持的「虚拟写副本」和瞬态虚拟读副本，作为最终状态的桥梁，用来与读取量解耦，也就是与写竞争的读操作约为每次写入的 100–1,000 倍。

**Discussion**: 最直接的反对意见是架构层面的：若干评论者认为，GitHub 从自有数据中心迁往 Azure 属于降级，有人甚至把近期稳定性问题与微软收购 GitHub 的时间线联系起来，尽管其他人指出，一些不稳定投诉早在微软收购之前就已经存在。相当一部分讨论集中在 GitHub Actions 的可靠性和计时上，人们开玩笑说故障是常态，这与存储文章几乎无关。几位评论者称赞该文章对内部架构的深度披露，认为它在技术上很有价值；另有一位评论者批评关于 PR 策略的评论质量低下。一个反复出现的主题是发布时间：评论者指出，这篇文章看起来是对 Anthropic 声称 GitHub 无法处理其合并量这一说法先发制人的回应，并且有评论者链接了该系列的前几篇以及其他系列文章。争点最尖锐的争论在于，Anthropic 所说的每日 30k 次合并是否是个真正的问题：有评论者认为，那是一个选择了单体仓库、而非拆分项目所造成的问题。

**Worth reading**
- [locknitpicker](https://news.ycombinator.com/item?id=50191732): 认为 Anthropic 所报告的合并限制是它自己造成的，因为它的单体仓库布局使得它成立；它没有把项目拆分成独立仓库，反而推行自建版本控制系统。
