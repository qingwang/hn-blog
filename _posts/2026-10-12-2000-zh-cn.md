## 1. Codex CLI 默认会安装一个常驻、自我更新的后台守护进程 {#story-1}
*HN 第 1 名 · [github.com](https://github.com/openai/codex/issues/48195) · 55 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50060694)*
*原标题: Codex CLI installs a persistent, self-updating background daemon by default*

这是一份发在 openai/codex 仓库的 GitHub issue（#48195），要求把 CLI 的 daemon_auto_start 改为可选、默认关闭。报告者称自 0.157.0（npm 全局安装、Linux/WSL2）起，仅打开一次交互式会话就会启动 codex app-server --managed-daemon，把约 374 MB 的平台包复制进 ~/.codex/packages/app-server-daemon/releases/<version>/，并拉起一个启动后 5 分钟、之后每小时的分离式更新器（会以 60 秒 drain 预算强杀进行中的回合）。问题还提到守护进程会锁定首个会话的环境变量（如 HTTPS_PROXY）、hooks 拿到错误的 cwd；关闭时 daemon stop 不会终止 pid-update-loop。临时解法是 codex features disable daemon_auto_start，issue 中已出现提交「codex: disable daemon auto-start by default」。

**讨论**: 评论区基本站在报告者一边，并补充了更多实害：有人称旧版本累积占了约 12 GB 磁盘，还有人说自己每天用一个 LLM 扫描磁盘删除各 harness 留下的垃圾。争议集中在自动更新是否有必要：一方认为浏览器等软件都会自动更新，2026 年这是常态；另一方反驳自己的浏览器更新需要用户确认，并且讨厌自动更新软件，还有人讽刺这等于让厂商往自己机器上装 rootkit，而对方回应自己是在容器里跑。有评论澄清 Codex 其实是 Rust 写的，但并未否认体积膨胀的抱怨；也有人问 brew 安装是否同样受影响，thread 中未见回答。总体共识是默认开启常驻守护进程与自更新不合理，至少应改为 opt-in。

**值得一读的评论**
- [icantevenhold](https://news.ycombinator.com/item?id=50060934): 实测旧版本累积占用约 12 GB 磁盘，并认为 Codex 在这方面比 Claude Code 更糟。
- [InsideOutSanta](https://news.ycombinator.com/item?id=50061105): 指出所有 harness 都不清理自身残留，自己已每天让一个 LLM 扫描磁盘删垃圾——「像雇个纵火犯来救火」。
- [icantevenhold](https://news.ycombinator.com/item?id=50060975): 反驳「自动更新是行业常态」：自己的浏览器更新需人工确认，且出于多种原因厌恶自动更新软件。

## 3. 一个用 C 编写的现代 Web 应用 {#story-3}
*HN 第 3 名 · [prophitt.me](https://prophitt.me/writing/a-modern-web-app-in-c) · 172 分 · 70 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50058528)*
*原标题: A Modern Web App in C*

Corey Prophitt 介绍了 marketyour.games：一个完全用 C 编写、通过 CGI 提供服务的商业 Web 产品（包含用户账号、创作者搜索仪表盘、文件夹、Stripe 支付、Postmark 事务性邮件，以及无需任何 JavaScript 的渐进增强）。技术栈是 BCHS —— OpenBSD、C、httpd 和 SQLite —— 没有框架、没有模板语言、没有数据库服务器、也没有容器：一个静态链接的二进制文件加一个 SQLite 文件，资源文件被编译进可执行文件并从内存中提供，沙箱则依靠 OpenBSD 的 pledge/unveil 以及 httpd 默认的 chroot。依赖项是 libcurl 和 libsodium（构建期）以及 libcjson 和 SQLite amalgamation（已内置）；作者认为 2004 年那套对 CGI 的批评如今已不再适用，因为 fork 成本很低、部署只需替换文件而无需重启，而且供应链极小。

**讨论**: 讨论串在赞赏与对 CGI 每请求 fork 模型的质疑之间分成了两派。几位评论者认为，一个单独的 Go 二进制文件（CGO_ENABLED=0、内嵌模板、scratch 容器）能在保证内存安全的同时提供同样的简洁性；有人称 CGI 是半吊子方案，仍然依赖一个独立的 Web 服务器，并付出巨大的每请求开销；作者反驳说它符合自己的思维方式，而且 FastCGI 是一条简单的升级路径。关于 SQLite 并发的一个务实讨论由作者本人作答（WAL 模式使读取不再阻塞，但写入仍是同步的，且必须设置 busy timeout）；也有人引用 SQLite 自己的文档指出，同一时间只能有一个写入者。评论者纠正了文中开头的说法，即 1994 年的 CGI 意味着 C，他们指出当年 cgi-bin 里是 Perl 的天下，并分享了更早的 CGI 往事（HP-UX 上的 FORTRAN 77、busybox 内置的 CGI 支持、lighttpd、nginx-cgi、通过社区插件实现的 Caddy、TurboLua）。有两个人索要源代码，并得出结论：这个项目并非开源；此外还有一场附带争论，关于这篇文章以及该产品低对比度的单色风格是否是 AI 生成的 —— 一位评论者称 Pangram 判定前半部分为 AI 生成，而作者表示该设计本意是达到 AAA 对比度标准，且 100% 由人类撰写。

**值得一读的评论**
- [prophittcorey](https://news.ycombinator.com/item?id=50059377): 作者直接回答了并发问题：SQLite 在 WAL 模式下允许非阻塞的并发读取，但写入仍然是同步的，因此必须设置 busy timeout，否则被阻塞的写入会立即失败。
- [EGreg](https://news.ycombinator.com/item?id=50059179): EGreg 从自己构建 PHP Web 服务器的经历出发，给出了 CGI 与 FastCGI 取舍的第一手细节，指出 fork 一个进程大约要花 8 毫秒，而他默认采用长驻的 FastCGI 式进程，并把每请求 fork 作为可选项。
- [xd1936](https://news.ycombinator.com/item?id=50059511): 为 AI 作者身份的争论补充了一个具体数据点：据说检测器 Pangram 恰好把文章前 50% 判为 AI 生成，后一半判为人类撰写。

## 4. Launch HN：Agent37（YC F26）——用于运行 agent 的低成本 agent 沙箱 {#story-4}
*HN 第 4 名 · 文字帖 · 44 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50059096)*
*原标题: Launch HN: Agent37 (YC F26) – Low-cost agent sandboxes for running agents*

这是一个 HN 上的发布帖（文本帖），Agent37（agent37.com）的创始人 Vishnu 介绍他们为运行 AI agent 提供的沙箱服务：号称成本不到大多数沙箱厂商的 10%，客户平均每个沙箱每月花 0.37 美元，而免费套餐的沙箱基础设施成本约每用户每月 0.05 到 0.10 美元。他把降本手段归结为四点：按 agent harness 的突发式 CPU/内存使用模式做调度、绕开 Amazon 等超大规模云厂商直接向 Hetzner 和 OVH 租服务器、用 gVisor 跨沙箱共享主机内存并加快启动（代价是不支持 Docker-in-Docker 和 Android 模拟器）、以及优先买内存更密的主机。他也提供略贵但仍便宜的全 VM 沙箱以支持 Docker 类负载，并称团队此前做 OpenClaw 套壳起家，Vishnu 本人曾在 Amazon 做内部 AI 聊天机器人 Diya 和内部编码 harness Ziya。

**讨论**: 评论区主线是「这个赛道太拥挤、纯拼价格没有护城河」：mparis 说自己所在的医疗行政机构已在 Firecracker microVM 上自建同类沙箱且永远不会外售，MikhailTal 认为超大规模云厂商一旦认真进场就能靠亏损把你挤死，bitlad 和 risyachka 也认为这是「逐底竞争」，bitlad 还反驳了创始人把沙箱比作 LLM token 价格战的类比，指出 LLM 是赢家通吃市场、终会价格回调。创始人 Vishnu 的回应是：价格只是获取份额的楔子，现有厂商一开始不会跟进降价（引用 Travis Kalanick 的播客观点），并承认光他所在的 YC 批次就有 5 家以上公司做类似的事，大家现在都还在快速增长、之后会分化出不同细分。价格对比上有明显分歧：alasano 和 colesantiago 拿 boat.dev、Fly.io Sprites 作参照，创始人称自家默认沙箱比 boat 便宜约 2.8–3 倍、比 Sprites 便宜约 94%，alasano 则说自己快速比对后觉得 boat 只是略贵但存储更多。另有早期用户 rajangdavis 反馈用起来很容易上手、但 Google 相关连接器的隐私问题让人不安，olalonde 试用免费层时发现模型不肯说出自己是什么、并遇到抓取网页的配额报错，还有评论者 C20 指出帖子下有朋友刷屏捧场、违反 HN 规则。

**值得一读的评论**
- [mparis](https://news.ycombinator.com/item?id=50060422): mparis 从医疗行政从业者角度说他们自建在 Firecracker microVM 上的沙箱不会外售、而是当作竞争优势，并警告纯卖沙箱会被愿意亏本卖来导流数据库等更高毛利产品的厂商碾过。
- [vishnukool](https://news.ycombinator.com/item?id=50060561): 创始人披露免费层的 agent37/default 模型实际用的是 OpenAI Luna，并说明他们顺带提供托管 MCP 和自建 LLM 网关。
- [vishnukool](https://news.ycombinator.com/item?id=50060979): 创始人解释架构：每个 harness 跑在自己的沙箱里（本质是预装 openclaw、hermes、claude code、opencode 等的 Docker 模板），并开源了统一各 harness 的 Gateway API，称之为「agent harness 界的 OpenRouter」。

## 5. AI 编程智能体生成了更多代码，但并没有造出更多软件 {#story-5}
*HN 第 5 名 · [arstechnica.com](https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/) · 101 分 · 79 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50059523)*
*原标题: AI coding agents generate more code, but not more software*

Ars Technica 的一篇报道（作者 Kyle Orland），介绍哈佛大学 Fiona Chen 与 James Stratton 的一项研究；该研究使用 Jellyfish 工程分析数据——来自 700 多家公司、逾 70 万名员工的 3 亿条工作事件，时间跨度为 2021 年至 2026 年 3 月——来检验 AI 编程工具是否提升了公司层面的产出。引入智能体后，代码行数增加 30%，提交数增加 20%，拉取请求（PR）增加 23%，但 Jira 问题与史诗（epic）的解决率没有显著变化；PR 审查时间上升 49%，需要修改的 PR 占比几乎翻倍，每个 PR 的评论数增加 35%，另有 14% 的更多员工最终参与做审查。作者没有发现统计上显著的就业效应，而且 AI 审查仍属边缘角色：到 2026 年 3 月，80% 的公司使用了某种 AI 代码审查，但智能体只撰写了 23.3% 的审查评论和 10.8% 的 PR。
