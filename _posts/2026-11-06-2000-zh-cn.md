## 2. Tesla 将逐步停产 Cybertruck {#story-2}
*HN 第 2 名 · [nbcnews.com](https://www.nbcnews.com/tech/tech-news/tesla-wind-cybertruck-production-years-poor-sales-markets-rcna607817) · 571 分 · 1,276 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50391456)*
*原标题: Tesla to wind down Cybertruck production*

路透社的一篇报道（经 NBC News 转载）称，Elon Musk 表示 Tesla 将于 2027 年年中前后在其奥斯汀超级工厂逐步停止 Cybertruck 的组装，从而为 Cybercab 自动驾驶出租车腾出产能。2025 年美国 Cybertruck 销量降至 20,237 辆，较 2024 年的 38,965 辆下降 48%，而 Musk 在上市前的预测是每年 25 万辆；Musk 称这款车是「Tesla 有史以来最好的车」，称停产是「一个时代的终结」。报道援引的分析师（Andy Palmer、Felipe Munoz）认为，电动皮卡在美国整体上都失败了，而且这款车的不锈钢楔形造型永远无法通过欧洲的行人碰撞法规；但 Cybertruck 首席工程师 Wes Morrill 表示，该平台「通过 Cybercab 延续下去」。

**讨论**: 最热门的讨论串完全与停产无关：一位车主相关的评论者描述，他的朋友在飓风 Helene 过后靠一辆 Cybertruck 给自家供电 14 天，方式是开车去 Supercharger 充电补能，这引发了一场漫长的争论。数十条回复指出这只是通用的 V2H/V2L 功能，并非 Cybertruck 独有——Ford 的 F-150 Lightning 早就做到了，Kia EV9、Ioniq 5、BYD 甚至 Jeep 4xe 也能做到——而另一些人则认为，在道路、充电桩和电网都瘫痪时，一台 500 至 8,000 美元的丙烷或柴油发电机更便宜也更可靠。就产品本身而言，评论者分为两派：一派「很高兴有人敢于尝试」（将其与 DeLorean 相比，称赞 48V、线控转向和不上漆的不锈钢），另一派则称它是丑陋、不实用的非卡车；一个反复出现的论点是，杀死它的是价格而非外观——40,000 至 50,000 美元的版本本会卖得很好——反驳者则指出，65,000 美元以上的 F 系列卡车销量要高得多。第二个反复出现的论点是，Cybertruck 实际上只是 Tesla 下一代电气架构的低产量试验平台，在产品市场契合之前就被放大了产量，许多人借这则新闻质疑 Tesla 的未来：只剩 Model 3/Y、Cybercab 仍在回答 NHTSA 的问题、而 BYD 在美国以外占据主导。Musk 的政治因素无处不在，一些评论者反感讨论串中「我不喜欢 Elon，但是……」这种框架本身就令人厌倦。

**值得一读的评论**
- [brightball](https://news.ycombinator.com/item?id=50394025): 第一手叙述：一辆 Cybertruck 在 Helene 过后长达 14 天的停电中为整栋房子供电，方式是往返 Supercharger 补电——正是这个故事引出了整个车辆到家庭（V2H）的子讨论串。
- [crawshaw](https://news.ycombinator.com/item?id=50396106): 认为被忽视的原因是价格：这款卡车是为卡车价格虚高、零利率的时代设计的，如果定价 40,000 美元，本会找到大得多的市场。

## 3. 使用 UEFI 迈出裸机编程的第一步 {#story-3}

*原标题: First steps in bare-metal programming using UEFI*

这是 Kevin Boone 撰写的一组系列文章的索引页，讲的是如何在 Linux 工作站上开发 UEFI 固件 PC 的裸机应用。目标读者是有经验的 Linux 开发者，但假定读者此前不熟悉 UEFI；系列内容包括所需工具、编译与链接、制作可启动的光盘或 U 盘，以及使用 Simple File System 协议做基本文件管理，其中已列出第 2 至第 5 部分。文章明确要求按顺序阅读，后篇依赖前篇。

**讨论**: 评论整体比较正面：一位用 Zig 写 bootloader 的开发者说这份指南是很好的起点，但提醒 EFI 环境里的 UTF-16 字符串和各类「尖锐边角」让它和普通 Linux 开发相差很远。有人为这些怪癖提供了背景和补丁：指出 edk2-libc 可以补上缺失的 C 标准库，并说明 UEFI 的「Windows 味」源自 Intel Boot Initiative → EFI → UEFI 的演进过程。另一位资深评论者则强烈反对这种「沿用」的说法，认为 UTF-16 和 VFAT 在 1998 年和 2005 年就已经是不合理的选择。同一位评论者还提出 Multiboot2 可作为自己构建 PE32+ 镜像的替代方案，并分享了一个只用 289 行头文件、借助 LLM 生成的 UEFI 输入监视示例程序。

**值得一读的评论**

## 4. 我们知道有 1.5 万个网站被感染。我们该怎么通知他们？ {#story-4}
*HN 第 6 名 · [scotthelme.co.uk](https://scotthelme.co.uk/we-know-15-579-websites-are-infected-how-do-we-tell-them/) · 72 分 · 48 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50396064)*
*原标题: We know 15k websites are infected. how do we tell them?*

Report URI 的 Scott Helme 表示，他的威胁情报爬虫已经识别出 15,579 个站点——保守估计每月 1.35 亿次访问——正在运行恶意 JavaScript：Magecart 信用卡窃取器、ClickFix 假验证码恶意软件诱饵、iOS 间谍软件漏洞利用（DarkSword、Coruna），以及跳转到钓鱼页面的重定向。他列出的感染途径包括 WordPress 式的直接入侵、被感染的第三方供应链脚本、XSS，以及「DeadTag」（一个专门购买过期域名的团伙，而网站仍在从这些域名加载脚本）。他没有公布站点列表，称 security.txt 的采用率很低，大多数外联邮件都无人回复，并请 CERT/NCSC 以及商业情报源的购买者发邮件至 intel@report-uri.com；他并没有可规模化的通知方案。

**讨论**: 最主要的建议是把名单交给浏览器厂商和 Google Safe Browsing，让用户看到拦截页——先保护访客，再通过流量下降或用户投诉迫使站长注意到问题；好几个人说这正是他们发现自己网站被黑的方式，还有人提出显而易见的追问：为什么这些站点还没有被标记？第二派意见希望直接公开名单（类似 haveibeenpwned 的查询服务，或一个按流量排序的纯文本文件），理由是这根本算不上「负责任披露」，因为危害已经在发生，保密只是在保护名声；也有人反对，认为公开已知存在漏洞的站点名单等于给攻击者提供目标清单，还有人警告说向站长收费才提供详情，读起来像是敲诈。最尖锐的反驳集中在「被感染」的定义上：一位评论者认为，如果第三方分析脚本也算，那黑名单会覆盖大半个网络；其他人则回应说，访客在输入银行卡信息时并不关心恶意 JS 是第一方还是第三方的。关于联系渠道的建议集中在 whois、abuse@、admin@、legal@ 和联系页面——并附带一场关于究竟是 GDPR 还是早已存在的隐私代理服务搞垮了 whois 的争论——而小站运营者怀疑这些渠道根本联系不到真人。有几个人问 Report URI 用的是什么检测工具，以及他们会怎么处理完全找不到联系方式的站点。

**值得一读的评论**
- [sublinear](https://news.ycombinator.com/item?id=50396805): 认为「被感染」的判定标准含糊得危险——如果被入侵的第三方分析脚本也算，那黑名单会干掉人们日常使用的大多数网站，因为几乎每个站点都至少加载一个第三方脚本。
- [athrowaway3z](https://news.ycombinator.com/item?id=50397247): 强有力的反驳：「负责任披露」被误用了——这些站点已经被感染，所以应该连同证据一起公布 URL，并在修复后自动更新，同时接受后果。
- [testplzignore](https://news.ycombinator.com/item?id=50396955): 用一个类比戳破了披露框架：负责任披露适用于一把能被撬开的锁，而不适用于站在街对面看着房子被洗劫——直接把一个文本文件放到博客上就行了。

## 5. Blender 的 UI 与运行时：比 GPUI 快得多 {#story-5}
*HN 第 7 名 · [github.com](https://github.com/ppmpreetham/BUI) · 600 分 · 244 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50389333)*
*原标题: Blender's UI and Runtime: Much Faster Than GPUI*

BUI 是一个把 Blender 界面层（控件绘制、交互规则、主题外观）抽出来做成独立 C 核心 UI 库的项目，提供 Python（tkinter 全量 API、Qt 风格、45 个 Blender 组件）、Rust、JavaScript/React/Svelte、C/C++ 和 Dear ImGui 绑定，无需安装 Blender，也不需要浏览器或 webview。README 声称按需重绘、空闲时 0% CPU，相比 gpui-fast 每帧少 2–4 倍 CPU、首帧约 5 ms，打包成单文件可执行程序为 6.3–6.9 MB，首次渲染约 70 ms、19 MB 内存。项目自述绘图代码是从 Blender 的 interface_widgets.cc 移植的 C 代码，仓库声明「完全由 LLM 编写，无人类手写代码」，并因源自 GPL 的 Blender 而只能以 GPL 发布；已知缺失无障碍支持、输入法和系统原生外观。

**讨论**: 讨论明显分成两派：一方（最上面的评论）夸 README 第一行就说清了是什么、为什么该关心；另一方则认为整篇 README 是典型的 LLM 文风——「super duper fast」「4. ## 10. Devvm.dev：每个项目一个 VM {#story-10}

devvm 是一个采用 MIT 许可证的开源工具，它为每个项目启动一个 Linux VM——通过 Lima 实现，在 macOS 上使用 Apple 的 Virtualization framework，在 Linux 上使用 QEMU——预装项目文件所暗示的工具链，并让编码代理（Claude Code、Codex 或 opencode）在虚拟机内运行，而不是在宿主机上。它的卖点是限制爆炸半径，以应对供应链攻击、密钥泄露、提示注入和失控代理：默认的允许列表网络层经由宿主机侧代理，用真实凭证替换占位符；在 macOS 上锁定 .git 钩子/配置；可选的 --clone 模式改为在仓库副本上工作；以及对基础镜像的 COW 副本，让后续 VM 在数秒内启动。它还支持 docker/nix/desktop 层、自定义层安装脚本、--from 容器基础镜像和 devcontainer.json，并可通过 Homebrew tap 或 curl|bash 脚本安装。

*原标题: Dutch 'idealist' bank ASN blocks non-Google Android, including GrapheneOS*

这不是一篇文章，而是 PrivSec-dev 的 banking-apps-compat-report 仓库里的一个 GitHub issue，用于追踪 ASN Bank（隶属 de Volksbank）的 Android 应用在去 Google 化／替代 Android 系统上的兼容情况。该 issue 于 2022 年开启，当时据称该应用无需 Google Play 服务即可运行，之后却在登录时改为要求 GMS；2026 年 11 月，该讨论串因 EPI/Wero 的书面答复而重新活跃：他们称需要 Google Play Integrity，而不是仅靠 Android 硬件密钥证明，因为他们希望对应用二进制、分发渠道和操作系统完整性获得保证。评论者翻出 Wero 自己的支持页面写明 LineageOS、Pixel Experience 等第三方 ROM 无法安装该应用，并且 Play Integrity 调用位于 ASN／de Volksbank 的代码中（nl.devolksbank.mobile.banking.security.data.wero.IntegrityRepository#requestIntegrityToken），令牌被发送到 de Volksbank 自己的服务器。

**值得一读的评论**
- [microtonal](https://news.ycombinator.com/item?id=50391298): microtonal 拒绝把 uattest.net 当作解决方案，称 Unified Attestation 是那些内核落后数年的厂商搞的项目，且一直在反对 GrapheneOS；他认为银行应当直接信任一份签名密钥列表，例如 grapheneos.org/attestation.json。
- [microtonal](https://news.ycombinator.com/item?id=50391093): 纠正了「荷兰警方破解了 GrapheneOS」的说法：那名转售商自己构建了带 MDM 的分支，缺少上游安全更新，且很可能泄露了签名密钥，所以手机是通过 ADB 解锁的。
- [skrebbel](https://news.ycombinator.com/item?id=50393189): 指出安全论据核心处的不一致：GrapheneOS 被拒，而缺少三年补丁的原生 Android 却被接受，所以银行自己其实并不相信这是真实风险。

## 20. 可编写脚本的 GeoDNS：离开 AWS 转向 Bunny {#story-20}
*HN 第 31 名 · [vincent.bernat.ch](https://vincent.bernat.ch/en/blog/2026-bunny-geodns) · 41 分 · 15 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50394292)*
*原标题: Scriptable GeoDNS: Leaving AWS for Bunny*

Vincent Bernat 讲述了他如何把博客的地理感知 DNS 从 AWS Route 53 迁移到 Bunny DNS。Bunny DNS 几乎免费（最多支持 500 个域名），并且会在每次查询时运行用户提供的 JavaScript。他运行着七台小型 NixOS 虚拟机（分别位于 Paris、Nuremberg、Ashburn、Singapore、San Jose、São Paulo、Sydney），脚本通过 Bunny 的 RoutingEngine.getClosestServer() 辅助函数返回距离最近的两台服务器，如果第一台宕机则回退到第二台。他记录了 HTTPS/SVCB 记录（RFC 9460）方案的失败：Chrome 会忽略目标不是「.」的记录，而 Bunny 不会为目标名称返回 glue，因此被迫进行第二次查询。他最终采用的做法是：当第二台服务器距离超过第一台两倍且超过 1000 英里时，只返回一台服务器并使用 2 分钟 TTL。仍有一些粗糙之处：Bunny 无法发布 DS 记录（因此 luffy.cx 区域托管在 deSEC，ACME 区域运行在用 Rust 编写的 Hickory DNS 上），CDN 不支持 HTTP/3，且最近服务器辅助函数仅支持 IPv4；账单从每月约 5 美元降到每月 1 美元。

**讨论**: 价格对比是最热闹的一条讨论线：一位评论者指出，NTP Pool 在每小时峰值时每秒大约处理一百万次 DNS 查询，靠的是一个名为 geodns 的小型老式 Go 程序，并称按云厂商约每百万次 0.70 美元的价格为每天约 110 亿次查询付费，对志愿项目来说是灾难性的。多人都称赞 Bunny 的可脚本化 DNS 被低估了，一个子讨论串纠正了文章中的 Terraform 配置：CDKTF 已于 2025 年 12 月弃用，不过 Bernat 指出有社区分叉 CDK Terrain（cdktn.io），其他人则表示如今 LLM 代理让手写 HCL 也没那么痛苦了。一个旁支辩论问为何不用 anycast；一位在 anycast CDN 工作十年的评论者解释了取舍：跳数不等于延迟，很难把一个网络的流量拆分到不同数据中心，而负载管理意味着要按站点撤回宣告的 IP 段；Bernat 则表示自建 anycast 很复杂，而且 BGP 上「近」的位置可能隔着一个大洲。一位怀疑者质疑这到底面向谁，因为把博客跑在全球七台服务器上并不是现实的默认做法；其他人则只是惊叹于这套配置以及文中的交互式地图和动画。

**值得一读的评论**
- [cortesoft](https://news.ycombinator.com/item?id=50396993): 十年 anycast CDN 运维经验：跳数并不反映真实延迟，流量工程需要持续监控和伪造路径填充，而把单个网络均衡到多个站点需要按数据中心撤回 IP 段。
- [askbjoernhansen](https://news.ycombinator.com/item?id=50395556): 针对定价的具体规模反例：志愿运营的 NTP Pool 在峰值时用一个小型 Go 程序每秒处理约一百万次 DNS 查询，而 Route 53 的按查询计费会让这变得无法负担。
- [vbernat](https://news.ycombinator.com/item?id=50396042): 指出 CDKTF 已于 2025 年 12 月弃用，并指向位于 cdktn.io 的社区分叉 CDK Terrain。
