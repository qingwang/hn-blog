## 1. Cloudflare 没有告诉你的那些事 {#story-1}
*HN 第 1 名 · [charlie.fish](https://charlie.fish/posts/2026/11/what-cloudflare-doesnt-tell-you/) · 63 分 · 28 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50632883)*
*原标题: What Cloudflare Doesn't Tell You*

Charlie Fish 的一篇文章认为，Cloudflare 向访客展示了对现代协议的支持——TLS、IPv6、抗量子密钥交换——但 Cloudflare 到源站这一段可能只是仅走 IPv4 的明文 HTTP，因此用户和网站所有者对整条链路形成了错误的印象。他引用 Cloudflare 自己的文档指出，对于同时有 A 记录和 AAAA 记录的被代理记录，Cloudflare 在连接源站时优先使用 IPv4 地址，并主张仪表盘应主动警告管理员，且 CDN 应当能够公开源站的 TLS 和 IP 版本元数据。

**讨论**: 讨论围绕透明化提议产生分歧：几位评论者认为，公开源站元数据与 Cloudflare 保护源站的职责相矛盾，其中一人描述了自己把服务器完全锁在 Cloudflare Tunnel 之后，并拒绝为了「某种舒心的透明感」而放弃这一做法，另一人则将这个想法比作让 SSH 向外界宣告管理员密码是一个众所周知的默认值。在技术主张方面，评论者反驳称 Cloudflare 已经在引导用户使用 Full (strict) 源站 TLS，你可以使用 Cloudflare 的源站证书，或者更好的做法是自己生成证书，这样 Cloudflare 永远不持有密钥；而且走隧道的方式让源站证书变得无关紧要。有几个人质疑 IPv4 偏好到底为什么重要，回答是 IPv4 每个数据包少 4 字节开销、某些 ISP 的 IPv6 路由历来更差，以及大多数运营者认为 IPv6 价值不大——同时有一人报告说自己在 Cloudflare 后面用 443 端口跑了整整一年仅 IPv6 的源站，没有出过问题。最常见的抱怨是针对标题：有几个人说真正的新闻不过是 Cloudflare 在源站连接上偏好 IPv4 而已。

**值得一读的评论**
- [Velocifyer](https://news.ycombinator.com/item?id=50633137): 从机制上解释了 IPv4 偏好——在 1500 字节的帧内每个数据包节省 4 字节开销——并指出可以通过保留被代理的 AAAA 记录、删除 A 记录来强制让源站连接走 IPv6。
- [bastawhiz](https://news.ycombinator.com/item?id=50633643): 对公开源站连接状态的有力反驳：这就像 SSH 向每一位访客宣告管理员密码是众所周知的默认值，而羞辱疏忽的管理员并不值得以这种泄露为代价。
- [dantillberg](https://news.ycombinator.com/item?id=50633363): 指出了文章混淆的那个区别：源站 TLS 为明文是真实的隐私问题，但 Cloudflare 用 IPv4 而非 IPv6 去连接源站为什么对任何人有影响，这一点并不清楚。

## 2. 针对 Check Point 安全管理服务器的活跃入侵行动 {#story-2}
*HN 第 2 名 · [greynoise.io](https://www.greynoise.io/blog/check-point-security-management-servers-intrusion-campaign) · 205 分 · 71 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50630594)*
*原标题: Active Intrusion Campaign Against Check Point Security Management Servers*

GreyNoise 发布的一份报告，涉及该机构追踪为 GreyNoise Threat 13（GT13）的一起针对 Check Point 安全管理服务器（Security Management Server）的攻击行动。报告确认的活动时间为 2026 年 10 月 17 日至 11 月 2 日，至少波及 22 家组织，涵盖金融、能源、政府、交通和制造业，分布在美国、英国、德国、印度、越南等 17 个国家。攻击者使用了 99 个 IP（ExpressVPN 出口节点和被劫持的 Check Point 设备）、1,400 多个会话和 30 多个 Python 脚本，此外还有 Nmap、Chisel、Impacket 和 Paramiko，并将 CVE-2026-16232（SmartConsole 认证绕过导致可执行 Run Script）与后续步骤串联起来，从 24 台服务器上复制防火墙数据库和内部 CA 材料，并签发了一张用于横向移动的证书。一个值得注意的细节是：他们先入侵了一台 Rejetto HFS 服务器，方法是收集登录 cookie 中 Math.random() 的输出，以重建 V8 PRNG 状态并伪造管理员会话；后来他们又使用 nftables 加固自己的跳板机，以防范 CVE-2026-98432。GreyNoise 认为，这些自动化操作很大一部分是由 LLM 和智能体工具驱动的。

**讨论**: 讨论分成三种观点。最强烈的反应是难以置信：由 Math.random() 生成的会话签名密钥竟然至今仍可被利用；一位评论者指出，他十年前就在 Burp Suite 里研究过同一攻击向量。另一些人则反驳说，这是语言设计上的陷阱（crypto.getRandomValues 需要安全上下文，不过 localhost 也算），而且任何合格的审计或静态分析规则都应该能发现它。一个很长的子讨论围绕报告所称的「由 LLM 驱动的自动化」展开争论：一位悲观论者预言会有大批犯罪分子把模型对准关键基础设施，但随即遭到反驳——反驳者的论点是，犯罪者看重的是风险和收益，而不是能力，并引用 FBI 的投诉数据和诈骗园区数据作为支持；还有一位安全行业老手表示，攻击率实际上并没有飙升，是 HN 过度炒作了网络安全。实践者则把重点放在那个平淡无奇的原因上：初始访问几乎可以肯定需要管理接口暴露在互联网上；共识建议是把管理平面放到公网之外、置于覆盖网络之后，并指出换用 pfSense 也没用，因为 Netgate 自己就发布了一个关键的 PHP 修复。还有几位评论者指出，攻击者反而给自己的中继节点打上了针对 Linux IPv4 释放后使用的补丁，而 Ubuntu 迟迟没有发布同样的修复；他们认为这说明如今的补丁节奏必须有多快。

**值得一读的评论**
- [omh](https://news.ycombinator.com/item?id=50633125): 提出了文章没有回答的问题：初始访问究竟是如何发生的？22 个受害者的 Check Point 管理服务器是否真的都能从互联网访问？
- [ba1afd89f34cb23](https://news.ycombinator.com/item?id=50633416): 认为仅仅让流量经过某个设备，通常并不能让你利用它；真正的解决办法是让管理平面远离互联网、把控制平面锁死——但也对动态 VPN 端点和 WAN BGP 对等连接提出了保留意见。
- [sigmar](https://news.ycombinator.com/item?id=50630972): 指出攻击者用 nftables 保护自己被攻陷的跳板机免受 CVE-2026-98432 影响时，Ubuntu 还在拖延同一个修复，相关情况记录在一个被链接的 HN 讨论帖中。

## 3. Grafana 12.4.16、13.0.14、13.1.11、13.2.7 和 13.3.2（多个 CVE） {#story-3}
*HN 第 3 名 · [grafana.com](https://grafana.com/grafana/download) · 30 分 · 5 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50633159)*
*原标题: Grafana 12.4.16, 13.0.14, 13.1.11, 13.2.7 and 13.3.2 (multiple CVEs)*

链接页面是 Grafana 的通用下载页，而不是安全公告：它提供 13.3.2 Grafana Enterprise 安装包（deb、tar.gz、rpm，附 SHA256 校验和），适用于 Ubuntu/Debian、RHEL/CentOS/Fedora 和 SUSE，另有 grafana.ini 配置说明以及 Grafana Cloud 试用（50GB 日志/追踪/性能分析数据，20 多个企业级数据源插件）。页面不含 CVE 编号、严重等级评级，也没有说明修复了什么，因此该页面本身除了暗示存在一个新补丁版本之外，并不能支持标题中的说法。

**讨论**: 该讨论帖规模很小，内容大多与主题本身无关。一位评论者询问该投稿为何被标记，得到的回答是：链接指向下载页，而非对 CVE 的说明——发帖人接受了这一批评，称他选择下载页是两害相权取其轻，因为他找不到博客文章，而且有些 CVE 当时还不太容易查到。随后发帖人贴出了从 GitHub 发布页收集到的 CVE 引用，按各分支列出了 CVE-2026-107561、CVE-2026-88943 和 CVE-2026-88960。其他评论者立刻纠正了他的转录：12.4.x 的修复版本是 12.4.16，而不是他写的 12.4.17；而他自己的列表写的是 13.0.4，标题却写 13.0.14，因此这个帖子最终的效果是让读者无法确定确切的版本号。帖中没有人讨论可利用性、严重程度或第一手的升级体验。

**值得一读的评论**
- [petecooper](https://news.ycombinator.com/item?id=50633196): 发帖人给出了从 GitHub 发布页摘取的真正 CVE 列表——CVE-2026-107561、CVE-2026-88943 和 CVE-2026-88960——并对应到各个发布分支，而链接的下载页对此只字未提。
- [debazel](https://news.ycombinator.com/item?id=50633691): 纠正了已发布的发布说明：12.4.x 的安全修复随 12.4.16 发布，而不是发帖人所写的 12.4.17。
- [petecooper](https://news.ycombinator.com/item?id=50633626): 投稿人解释了选择该链接的原因——当时没有博客文章，有些 CVE 也难以查证，所以下载页是最不坏的选择。

## 4. Jetty Pro {#story-4}
*HN 第 4 名 · [hypercritical.co](http://hypercritical.co/2026/11/23/jetty-pro) · 182 分 · 68 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50630462)*

Siracusa 的博客文章宣布推出 Jetty Pro：这是一款不经过沙盒、直接销售的 macOS 应用，可在屏幕边缘创建类似 Dock 的可自定义浮动面板，容纳文件、文件夹、宗卷、应用、快捷指令和废纸篓。他表示，原本计划推出的沙盒版 Mac App Store 应用「plain Jetty」在不到两周后就被放弃，原因是它继承了此前 SwitchGlass 的相同限制；Jetty Pro 则花了三个半月，向 250 名测试者发布了 160 多个 beta 版本，图标由 The Iconfactory 设计，并依赖私有 API 和大量系统权限。它的介绍价是每年 9.99 美元，持续到 2026 年底，并提供 14 天试用；他声称自己现在用它取代了 Dock，不过 Dock 仍有少数能力无法企及。

**讨论**: 最热闹的讨论串不是关于应用本身，而是关于价格模式：许多人表示愿意一次性支付 40–50 美元，但出于原则拒绝订阅制，并描述了订阅疲劳以及跟踪续费的心理负担；另一些人则认为每年 1 美元便宜到微不足道，并指出该应用依赖苹果随时可能破坏的私有 API。一个反复出现的提议是「荷兰模式」——支付一年费用，停止付费后继续保留当时拥有的版本——并以 Agenda、JetBrains、Forklift 和 Pagico 为例；怀疑者反驳说，永久回退许可会让用户留下未修补的安全漏洞，而且开发者最终要免费支持旧版本。一个大型子讨论串反驳了「这个应用只差一个 Claude/Gemini 提示词」的说法，评论者认为，明确并迭代数十种行为正是 Siracusa 所描述的工作；另一派则指出，个人使用的克隆版本制作成本低，自己修复也便宜。另有几组评论者进来时以为是 Java Jetty Web 服务器，得知无关后松了口气；还有少数 macOS 用户提供实用变通方法或竞品，而不是对定价发表意见。

**值得一读的评论**
- [Luc](https://news.ycombinator.com/item?id=50632330): 指出把别名拖进 Dock 后，点击文件夹已经会在 Finder 中打开，这削弱了 Siracusa 长期以来的 Dock 抱怨。
- [geraneum](https://news.ycombinator.com/item?id=50632294): 根据经验论证，这类应用并非「一个提示词就能搞定」——你无法预先指定每一个细节，而 LLM 纠正循环才是真正工作所在。
- [wlesieutre](https://news.ycombinator.com/item?id=50632767): 将 Jetty 每年 10 美元与 Ubar 的 40 美元许可加 20 美元升级相比，认为定价大致合理而非离谱，同时反对更广泛的订阅趋势。

## 5. Mechanical Pencil：喷雾瓶 {#story-5}
*HN 第 5 名 · [mechanical-pencil.com](https://mechanical-pencil.com/products/spray-bottle) · 196 分 · 56 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50598555)*
*原标题: Mechanical Pencil: Spray Bottle*

这是来自 mechanical-pencil.com 的交互式图解说明，该网站致力于「对我们身边工程学的图解式礼赞」，本页拆解了一个普通的扳机式喷雾瓶。文中指出，现代喷雾瓶出现于 1970 年代初，而几乎所有设计尽管在喷嘴和扳机上各有变化，都依赖同一个基本的单向阀机制；页面通过动画展示了扳机行程、回弹、剖面图和爆炸图，说明流体如何在一次次按压后持续被吸上来并喷出。该网站是出售这些图解拆解的商业产品页面，并给出 Instagram 账号指向未来的拆解内容。

**讨论**: 大多数评论者很喜欢它，视其为罕见的、手工制作且费心费力的网页设计范例，把它比作 Bartosz Ciechanowski 的 ciechanow.ski 以及德国儿童节目 Die Sendung mit der Maus，还有几人请求做后续选题（微波炉、塑料瓶设计、鸟类的肺）。真正的技术争论围绕球形止回阀：读者说动画从未解释为什么按下扳机时球会向下朝着吸管移动，而不是被更用力地压进上方阀座；jrflo 部分承认动画令人困惑，并提出球实际上靠在吸管顶端，在释放行程中因吸力而被抬起，再靠重力回落；其他人指出大多数真实泵都会加一根弹簧，而且若靠重力密封，喷雾器倒过来就会失效（确实会失效，不过主要是因为吸管吸进了空气）。一条次要的讨论串则因页面是否由 AI 制作而变得对立：the_af 和 sudobash1 引用作者 FAQ 中描述的实物拆解、CAD 建模和手工动画，而 0c3ca83 坚称这些图形看起来是 AI 生成的；另一场关于披露 AI 使用之激励机制的争论则演变成毫无成效的「人人都在作弊」之争。较小的实用观察：一些现代喷雾器如 Dawn Dish Spray 在松开扳机后还会短暂继续喷出，评论者猜测其中有加压腔；其他人抱怨喷头变得越来越不可靠，归咎于塑料弹簧、儿童安全锁以及吸管与腔体之间的接合处。

## 18. 机械表如何保持走时准确（交互式 3D） {#story-18}
*HN 第 22 名 · [martincmartin.github.io](https://martincmartin.github.io/slidev-stem/watches/article/1/) · 171 分 · 45 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50599458)*
*原标题: How a Mechanical Watch Keeps Time (Interactive 3D)*

这是 martincmartin 发布的一个交互式 Slidev 讲解页面，借助可拖动的 3D 图示逐个部件讲解现代机械表：惠更斯游丝（1675 年）和摆轮、擒纵机构及其红宝石叉瓦、把动力按 7½:1 再按 8:1 逐级减速到分针的轮系、Lépine 式条盒与主发条，以及把动力按 3:1 × 4:1 减速到时针的齿轮传动。其核心论点是：一块普通的 Seiko 或 Citizen 手表，约花 100 美元，就能达到约 99.99% 的准确度，也就是每天快慢约九秒。作者将其定位为一份更简单的「入门 101」读物，相比于 Bartosz Ciechanowski 那篇详尽得多的 Mechanical Watch 页面。

**讨论**: 批评主要集中两点。第一，钟表匠和爱好者指出，图中画出的擒纵机构根本无法工作：叉瓦既没有相应形状，也没有冲击面，无法让擒纵轮推动叉杆并为摆轮补充能量，因此摆轮会像无摩擦的摆一样逐渐停下来。jstanley 和 dust42 都提出了这一点，其中 jstanley 花了多年设计钟表机构，他要求至少写一句话说明这件事，因为文章不写的话会让摆轮显得很神奇。作者承认这是有意简化，但辩称这是「入门 101」的范围，好几位评论者对此并不买账。第二，许多读者的「AI 雷达」被这些文字触发了；作者承认 Claude 根据他的笔记写成了初稿，之后他才重写；评论者则剖析了具体句子，例如「the wheel provides mass and inertia」，以及「rest shape」那处分号，认为这些都是线索；而作者坚称短促朴素的句子是他本人的风格。还有一派声音更温和，包括 Luc 和 caseyf7，他们认为这个页面是一份有用的、不同层次的入门介绍，是通向 Ciechanowski 那篇的好跳板；不过也有人指出，Ciechanowski 现在在 OpenAI 工作，已经多年没有发帖了。少数较真的人指出，滴答跳动的秒针严格来说是停在每个刻度上的，因此转一圈大约需要 59–60 秒。

**值得一读的评论**
- [dust42](https://news.ycombinator.com/item?id=50632035): 认为这个动画在物理上是错误的：如果没有一块形状正确、带宝石的擒纵叉，在每个半周期给摆轮一次推动，那么这块表就是永动机，会停下来。
- [jstanley](https://news.ycombinator.com/item?id=50627737): 一位花了多年设计钟表机构的评论者解释了擒纵机构的第二项职责，即把能量送回摆轮，并附上了他自己的手表项目笔记和擒纵机构模型视频的链接。
- [plasticeagle](https://news.ycombinator.com/item?id=50633340): 一条直率的批评：AI 辅助写作产出的句子似乎讲得通，实际上并不成立（「齿轮不算数」），作者本可以自己写出好得多的文章。
