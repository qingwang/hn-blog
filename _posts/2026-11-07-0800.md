## 1. Asahi Linux Progress Linux 7.3 {#story-1}
*#1 on HN · [asahilinux.org](https://asahilinux.org/2026/11/progress-report-7-3/) · 106 points · 55 comments · [HN discussion](https://news.ycombinator.com/item?id=50401867)*

这是 Asahi Linux 团队针对 Linux 7.3 周期的例行进展报告，核心是上游化开始见效：约 3100 行的 macaudio 驱动和约 13000 行的 AVD 驱动已提交上游，音频子系统还连带需要多项 ALSA 核心改动；M4 Pro/Max 与 M5 的初始 Devicetree 也已出现（仅够启动到 TTY）。M3 支持摘掉了 EXPERT 标志并启用 DCP（带来休眠和刘海区域可用），m1n1 现在能在 EL1 下起三个 VM，从而在 M4 和 M5 上虚拟化并逆向带 SPTM/Exclaves 的 macOS。Thunderbolt 补丁终于进了上游和下游内核，但目前只支持 USB3、XDomain 和 Thunderbolt Networking，PCIe 与 DisplayPort 隧道（ docks 必需）还没有；游戏方面借助 Android 的 P3S（Per Process Page Size）补丁可以绕开 muvm 约 20% 的性能损失，跑起 Battlefront、Wolfenstein: The New Order（M2 上 144+ FPS）乃至 Bethesda 的游戏。报告还提到项目因有人滥用 MIT 许可而转向 copyleft。

**Discussion**: 线程很快从技术进展转向两场争论。一是 Omarchy：多人指出 Asahi 报告中「有人利用宽松许可劫持成果并变现」一段指的是 Omarchy Mac，有人翻出其 readme 自述为「Asahi + Omarchy」，讽刺「骑在 Asahi 肩上扣篮」；也有人反驳 Omarchy 并未售卖任何东西，其赞助收入与 Asahi 接受捐赠并无本质区别，并把 DigitalOcean 削减 OSS 支持转投 Omarchy 当作「吸血」证据，随即被纠正为 DO 的 OSS  credits 项目本身难以持续。二是许可与 LLM 立场：一派认为既然选了 MIT 就别在别人真用的时候喊「不是这样用」，另一派认为 Asahi 当初选 MIT 是为了吸引 BSD  contributor，改成 copyleft 是迟来的正确决定；也有人担心 Asahi 拒绝 LLM 会在与「vibecoder」团队的竞争中吃亏。此外还有若干实践反馈：有人用 Omarchy 的内核在 Fedora Asahi 上跑通了 Thunderbolt 和 Touch ID，另有一个自称 GravityLinux 的项目宣称已支持 Vulkan 1.4、M4 与大部分 M5、以及 Asahi 尚不支持的 suspend-to-RAM。最少数的声音是质疑「为何非要在 Mac 上装 Linux」，被多人以「MacBook 是最好硬件之一」「旧机器再利用」「这是 Hacker News」反驳。

## 2. Libghostty 1.0 {#story-2}
*#2 on HN · [mitchellh.com](https://mitchellh.com/writing/libghostty-1-0) · 529 points · 86 comments · [HN discussion](https://news.ycombinator.com/item?id=50399933)*

Mitchell Hashimoto's post announces libghostty-vt 1.0, a portable C terminal-emulation library extracted from Ghostty's core, now with a stable C ABI and semantic versioning. The ABI is designed for extension: opaque handles, enum-keyed getters/setters, size-tagged structs, GHOSTTY_UNSUPPORTED for unknown values, and CI enforcement via libabigail plus versioned ELF symbols. Adoption is the headline claim — the JetBrains IDE terminal now runs on it (over 12.5 million active users), a Neovim PR replaces libvterm, and Turborepo, devenv, OrbStack, Antithesis, Emacs's ghostel and a WASM build with an Xterm.js-compatible API are named; the library is MIT, needs only libc (freestanding without SIMD), and was stress-tested with 10,000 live terminals on a 4-core/8 GB box.

**Discussion**: The thread is overwhelmingly positive, with people praising the release engineering (tarballs, SONAME, pkg-config, CMake config, offline dependency bundles, no copyleft deps) and several users reporting that Emacs's ghostel and the new JetBrains terminal are a step change over vterm/EAT and JediTerm. A side thread teases Hashimoto for not plugging his own terminal Rex, then turns into testimony from beta users who say Rex has already replaced Ghostty or Herdr for them, with confusion over how Rex and Ghostty relate. The recurring practical debate is Ghostty versus iTerm2: fans cite speed, simplicity, and new tabs opening in the current directory, while others say iTerm2 still wins on tmux integration, search polish, profiles, font rendering and window arrangements. Two quieter threads ask how a Zig library presents a C API (answer: it is Zig with a C ABI), why Windows still lacks an official Ghostty (community ports like Noctty and wintty.io exist), and how the work is funded (HashiCorp, sponsors, a startup). One dissenting practitioner reports no measurable speedup from using it as Mudlet's ANSI decoder.

**Worth reading**
- [spacechild1](https://news.ycombinator.com/item?id=50402503): Points to libopus as a model C library and explains the size-prefixed versioned-struct trick, with a link to the ARA API as a concrete example — directly answering the API-design question raised upthread.
- [VadimPR](https://news.ycombinator.com/item?id=50401419): First-hand negative result: tried libghostty-vt 1.0 as Mudlet's ANSI decoder and found no measurable speed gain, and its grid model (UTF-8 only, immutable scrollback) does not fit a MUD client.
- [isomorphic](https://news.ycombinator.com/item?id=50401805): Detailed list of what still keeps a user on iTerm2: font rendering and cell sizing, compact theme with thin titlebar tabs, profiles, window arrangements, and the in-terminal API — while conceding Ghostty's plain-text config is nicer.

## 4. A Jev that can ask Opus for help gives Opus accuracy at 4x lower cost {#story-4}
*#4 on HN · [hightouch.com](https://hightouch.com/blog/llm-judges-identity-resolution) · 441 points · 99 comments · [HN discussion](https://news.ycombinator.com/item?id=50397429)*

Hightouch 工程师 Albert Jin、Neil Desai 和 Delaney Mackenzie 对廉价的“决策模型” Jev 和 GPT-6 Luna 进行了基准测试，让它们承担一项困难任务：审计身份解析中的过度合并（over-merging）。他们使用 IHME 的 pseudopeople 工具生成了 1,000 个合成身份，其中一半是单个人的带噪记录，另一半是过度合并；此外还用更难、更具对抗性的用例进行了测试。Claude Opus 5.5 的准确率为 99.0%，每个身份耗时 2.2 秒，成本为每 1,000 个身份 $3.86；Jev 为 95.7%，成本为 $0.05；Luna 为 97.3%，成本为 $0.10。Jev 的置信度校准得更好，因此只把落在 30%–90% 置信度区间的案例升级给 Opus 处理，准确率就达到 98.8%，成本为每 1,000 个身份 $0.88；相比之下，Luna 的过度自信使相同的混合方法在困难测试集上只得到 91.6%。

**Discussion**: 大多数评论者跳过了身份解析的具体细节，转而讨论如何用昂贵模型编排廉价模型；多位工程师描述了自己采用相反方向的配置（例如以 Opus 5.5 作为编排者和规划者，把实现工作交给本地 Qwen3.8-27B 子代理，或使用更便宜的层级，如 GPT-6.1 Sol 和 Muse Spark）。有几个人问，智能体是先大后小还是先小后大，是否有过任何测量依据，还是仅仅出于直觉；也有人提出这取决于任务，并指出 Anthropic 的 /advisor 功能和模型路由是同一思路更简便的版本。最主要的反对意见是有争议的校准结论：一位评论者根据作者自己的图表估算，Luna 的预期校准误差实际上比 Jev 低 2–3%，并认为在总体通过率很高时，高置信度的错误本身并不算问题；还有一位评论者指出，整个结果都锁定在确切的模型版本和参数下。还有评论者提出了伦理层面的异议，认为这项工作让把数据映射到真实人物变得更便宜、更快速，本质上属于 AI 辅助的隐私侵犯；也有人纠正了分类：GPT-6 Luna 是一个小型 LLM，带有一个 “decisions API” 变体，而非原生的决策模型。实际经验大多证实了这种模式：决策模型作为判断器、用于剔除提示词、在并行智能体之间路由，以及在工具调用前拦截；不过也有人报告说，一旦 Haiku 5.5 发布，这种成本优势就消失了。

**Worth reading**
- [pcwelder](https://news.ycombinator.com/item?id=50401734): 认为校准分析有误：根据提供的图表估算，Luna 的预期校准误差在两项任务上都比 Jev 低 2–3%，而且高置信度的错误如果通过率也高，本身并不一定有害，并呼吁报告实际的 ECE。
- [netshade](https://news.ycombinator.com/item?id=50399491): 第一手经验：在 Jev+Opus 这样的组合中，只要给 Jev 一份其他模型能力的清单，它在升级时通常能做出正确判断，但在 Haiku 5.5 发布后，这种决策层不再划算，因为 Jev 的毫秒级延迟已被链中其他环节（例如网页浏览）掩盖。
- [ezotony](https://news.ycombinator.com/item?id=50400499): 根据文章中的成本数据推算出隐藏的升级率：困难集大约送给 Opus 处理 53%（在相同阈值下），而简单集约 22%，这对于任何想复用这种混合方法的人都有用。

Per the settlement language quoted in the thread, none of the landlord companies admitted fault or liability, but they agreed to stop feeding nonpublic data into RealPage’s revenue management system and to stop using RealPage recommendations that rely on competitors’ private data. **Discussion**: The dominant reaction is that the settlement is a wrist slap: commenters note that RealPage keeps a decade of pricing history and that nothing in the deal prevents a repeat, with one pointing to 「tacit collusion」 theory and the Flash Boys 2.0 paper on bot coordination as evidence that prices can be lifted without any communication at all. ## 6. Greece has its own Pompeii: Thera buried Akrotiri in ash 17th-16th century BCE {#story-6}

A Smithsonian Magazine feature on Akrotiri, the Bronze Age Cycladic settlement on Santorini that was entombed under roughly 200 feet of ash and pumice when Thera erupted, dated by scholars to somewhere between 1620 and 1530 B.C.E. The eruption released about four times more material than Krakatau in 1883, and the collapsed caldera fuelled the later Atlantis legend, which the article says most scholars treat as Platonic allegory rather than history. Excavated since 1967 under Spyridon Marinatos and then Christos Doumas, the site has yielded 35 buildings, multistory houses with indoor plumbing, and frescoes such as those in Xeste 3 — but only about 10 percent of the settlement has been dug, and no human victims have been found, suggesting residents fled in time.

**Discussion**: Discussion is small and mostly first-hand travel enthusiasm rather than debate. One commenter recommends the Museum of Prehistoric Thera near the site for its well-preserved frescoes, and warns that Fira is miserably crowded, noting Akrotiri is roughly 1,500 years older than Pompeii and a very different experience. Another recalls being startled to find the original of a framed print — a life-size fresco of a man holding fish — in that museum. Someone links the Wikimedia Commons category for Xeste 3 photographs. The only substantive thread is about cultural influence: one commenter asks how much the Minoans shared with pre-Indo-European 「Old Europe」 farmers, and the reply argues for Ancient Near Eastern influence too, citing hybrid creatures, women flanked by big cats and serpent-holding priestly figures as Minoan iconography with parallels in Egypt and the Levant.

**Worth reading**
- [zetazzed](https://news.ycombinator.com/item?id=50401229): Practical visitor advice: the Museum of Prehistoric Thera is small but worth it for the frescoes, while Fira is miserably crowded, and Akrotiri predates Pompeii by about 1,500 years.

## 7. Firecracker VM Escape: PwnEscape Part 2 {#story-7}
*#11 on HN · [pwn.ai](https://pwn.ai/blog/firecracker-escape) · 218 points · 105 comments · [HN discussion](https://news.ycombinator.com/item?id=50397219)*

A follow-up post from PwnAI (Paulos Yibelo) showing the second half of a Firecracker escape chain: using a host read/write primitive obtained from inside the guest, the authors walk the EPT to find their own guest page's host physical address, reverse-map host page tables to recover the Firecracker process's PGD, locate the ELF image and its ASLR load bias, then find the live vCPU thread's pt_regs frame while it sits in KVM_RUN. They rewrite the saved registers so the thread returns into Firecracker's write(2) wrapper, printing an 8-byte marker (N8V23M2) to Firecracker's stderr, then restore eax to zero and resume at the original ioctl continuation, leaving the VM alive and SSH-reachable. Target was Firecracker v1.16.1 on x86-64 with host kernel 7.0.0-1011-aws, deliberately run without the jailer; the underlying bug is CVE-2026-99999 in the Linux networking stack, fixed upstream about a month before (commit 6785011f). The article is truncated before the root-execution section.

**Discussion**: The biggest thread is scope: the demo had no jailer, and Thomas Ptacek agrees that the escape only reaches the jailer boundary, so real host control would need a second LPE — though he and others insist it is still a serious Firecracker-stack bug, not just a kernel networking bug, because everyone running Firecracker also runs virtio-net. Skeptics argue the chain is really a Linux kernel flaw with Firecracker used as the vehicle; Ptacek counters that KVM is part of the Firecracker stack and code execution behind the jailer is effectively game over. Several commenters (monocasa, whiatp) criticise the write-up on technical grounds: the published PoC takes physical addresses as command-line arguments and opens /dev/mem, so it demonstrates none of the described memory primitives, and the 64-byte write primitive and page-boundary assumptions from Part 1 are never explained. Ptacek supplies the missing detail himself — the virtio-net checksum-offload metadata lets a guest tell the host to overwrite the IPv4 header length field instead of the checksum field, giving the kernel two conflicting notions of header length mid-packet — and notes cloud providers panic-rebooted fleets in response. Side threads cover the AWS bulletin saying AWS customers are not affected, the ClickBench playground operator offering to PoC the exploit, and a long tangent on Nova/seL4/Xen as alternatives. A sub-fight over whether the post is 'LLM slop' pits an insistence on better writing against the argument that there is no alternate source for this research.

**Worth reading**
- [tptacek](https://news.ycombinator.com/item?id=50398342): Ptacek explains the actual root cause: virtio-net checksum offload lets the guest direct the host to overwrite the IPv4 header length field rather than the checksum, so kernel code ends up with two different header lengths mid-processing.
- [monocasa](https://news.ycombinator.com/item?id=50401242): monocasa argues the published PoC is not a PoC: it assumes host physical memory is mapped at 2^39 and takes page addresses as command-line args while using /dev/mem, so the novel exploit link is never actually shown.
- [amluto](https://news.ycombinator.com/item?id=50401490): amluto notes that since the target is the host userspace pt_regs, one could equally corrupt it to return into a CPL0 kernel context — a trick he has used himself — and that Firecracker maps guest memory into its own address space, supplying easy gadgets.

## 8. Notes on San Marino {#story-8}
*#12 on HN · [mattlakeman.org](https://mattlakeman.org/2026/11/05/notes-on-san-marino/) · 52 points · 17 comments · [HN discussion](https://news.ycombinator.com/item?id=50395183)*

## 18. Show HN: Waymark – A workflow engine that compiles jobs instead of replaying {#story-18}
*#28 on HN · [github.com](https://github.com/piercefreeman/waymark) · 62 points · 18 comments · [HN discussion](https://news.ycombinator.com/item?id=50379221)*

Waymark is an MIT-licensed open-source durable execution library from Pierce Freeman (icyfox) and mozgiii, positioned between Temporal/DBOS and plain Postgres job queues. Instead of replaying workflow code from the start, it parses a Python workflow's AST into an IR and lowers it to bytecode for a stackless VM, which a Rust core executes and snapshots to Postgres — so any code that compiles will run, and non-deterministic calls like time or uuid fail at compile time rather than runtime. Postgres is the only broker (benchmarks around 1,500 workflows/second), actions plug into FastAPI-style dependency injection, there's a built-in webapp on port 24119 and cron/interval scheduling; the authors explicitly warn against production use before 1.0.0 and say SQLite support and JavaScript are candidates for later.

**Discussion**: The thread is largely admiring. An ex-Pachyderm engineer argues the real insight is applying the Bazel/Nix pattern — a pure coordination language over sandboxed imperative components — to distributed workflows, and says a compiler-driven orchestrator would have solved his team's partial-cache invalidation problems (the author replies he already has an internal map-reduce and asks where caching broke). Several people ask for SQLite or .NET CIL support; the author says the DB layer is already plugin-shaped and easy to swap. The one real dispute is over async: one commenter calls the async-heavy API off-putting and predicts breakage from Python version and third-party coupling, and when the author says background jobs are better modeled as async, he pushes back that coroutines run on a single thread and that thread/process queues have worked for decades. Others counter that asyncio is the norm across Temporal, Hatchet and Dagster for IO-heavy distributed work, and point to asyncio.to_thread and aiomultiprocess for sync code; the author notes actions themselves can be synchronous.

**Worth reading**
- [msteffen](https://news.ycombinator.com/item?id=50398960): A former Pachyderm engineer says Waymark applies the Bazel/Nix pattern of a pure coordination layer over sandboxed imperative code, and that this architecture would have fixed his team's pipeline caching headaches.
- [icyfox](https://news.ycombinator.com/item?id=50400223): The author explains why durability matters for agents: each LLM and tool call becomes a checkpoint, sleeps can last hours, and every call gets a clean input/output contract for tracing.
- [whilenot-dev](https://news.ycombinator.com/item?id=50402289): A commenter answers the sync-code complaint concretely — use asyncio.to_thread, or aiomultiprocess if you want processes — and asks what low-level concurrency control sync workflows would actually buy.

*#30 on HN · [github.com](https://github.com/andrewboldi/tmux-restore) · 28 points · 13 comments · [HN discussion](https://news.ycombinator.com/item?id=50355009)*

tmux-restore 是 andrewboldi 开发的一款 MIT 许可工具，它封装在 tmux-resurrect 和 tmux-continuum 两个插件之上：它每分钟保存一次全部 tmux 状态，并在系统关机时再保存一次（Linux 上通过 systemd，macOS 上通过 launchd），恢复时会带回各个会话、窗口、分屏、工作目录和滚动缓冲区。它最大的价值在于让 agent 会话可以接续：一个小型适配器会到 Claude Code、Codex、Gemini CLI、opencode 和 pi 各自的会话文件里找出对应的 conversation id，然后保存一组命令，用相同的命令行参数恢复该对话。出于安全考虑，它只重新启动编辑器和监控程序；部署脚本、dev server 等则被重新输入到提示符处，等待用户按 Enter 确认，不会自动执行。安装方式是通过 curl 执行 install.sh，脚本会自动安装 tmux、TPM 以及所需插件。
