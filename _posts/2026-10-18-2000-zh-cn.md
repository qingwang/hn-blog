## 1. RepRapMicron {#story-1}
*HN 第 1 名 · [github.com](https://github.com/VikOlliver/RepRapMicron/wiki) · 248 分 · 37 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50141076)*

这是 Vik Olliver 的 µRepRap 项目 wiki，目标是造出一台 RepRap（可自我复制的 3D 打印机），用常见易得的材料实现微米（1µm）和亚微米级制造，思路是用 OpenFlexure 项目的 3D 打印显微镜平台做精密定位，本质是一台极精确的小型 CNC。页面称 PIKA V0.02 硬件可在约 8mm 立方体积内实现约 1µm 的重复定位精度和 10µm 或更好的可靠精度，用自制蚀刻探针沉积出小至 4µm 的 UV 树脂液滴，并用 125/9 光纤探针固化了 9µm 宽的树脂线；已用 4µm 层高打印出 0.5mm 的 Benchy，另有一个 1.3mm 的「Hello World」是直接用探针在玻璃片上的 Sharpie 墨迹上刻出来的。硬件用 400 步 NEMA17 步进电机（200 步也接近 1µm）、GRBL 固件、0.5mm 针头或 0.25mm 针灸针作探针，树脂用的是 UV 美甲胶，加一个 3W UV LED 作打印头。

**讨论**: 讨论整体非常兴奋，但主要争议在「自我复制」和「小尺寸就等于更高精度」这两点。有评论者把这件事类比 1790 年代的精密机械浪潮（Ramsden 的分度、Maudslay 的螺纹车床、Wilkinson 的镗床），认为如今业余爱好者已能操纵单个原子；另一派则指出所有 RepRap 从来都不能完整自我复制，仍需要电机和控制器，而且把树脂打印缩小三个数量级不太可能，也许只能做成微型 CNC 或用来打印 MEMS 部件。有人用平方-立方定律和材料属性随尺度变化论证机械结构无法简单缩小，并强调「做得更小」并不等于「更精确」——真正的高精度机床通常反而更大。还有人给精度泼冷水：之所以能做到，是因为工作范围只有 8mm 立方，而廉价的蚀刻玻璃光栅编码器现在不到 50 美元就能给到 1µm 精度，直接用带内置编码器的直线电机更省事。支线讨论集中在家庭芯片制造：Sam Zeloof（AtomicSemi/fab2）、Jeri Ellsworth、Hacker Fab 以及那个「花园棚屋里的晶圆厂」——有人纠正说棚屋的主人本身是半导体公司创始人和 CTO，用家庭实验室跑业务，从车库一次性演示到可靠 mini-fab 的工作量差着好几个数量级。此外有人吐槽 USB 显微镜质量糟糕，回复澄清它们只用于回零和定位，观察成品要用 100x–200x 的台式显微镜。应用设想包括导电树脂打印 MEMS（加速度计、陀螺仪、微型扬声器）、磁芯存储器、黑胶唱片和 DIY 喷墨打印机。

**值得一读的评论**
- [generuso](https://news.ycombinator.com/item?id=50142402): 对「缩小即提升精度」的正面反驳：精密机械史是靠旧机器造出更精确的新机器逐级爬升的，而超高精度机床通常比低精度机床更大。
- [DannyBee](https://news.ycombinator.com/item?id=50142806): 指出这份精度来自仅 8mm 的立方工作体积，并提醒廉价的蚀刻玻璃光栅编码器如今不到 50 美元就能达到 1µm，带内置编码器的直线电机可能是更简单的路线。
- [generuso](https://news.ycombinator.com/item?id=50143443): 用 Sam Zeloof 从 CMU 电气工程学生、业余做半导体的爱好者到运营资金充裕的 mini-fab 设备团队的经历，说明车库一次性演示与可靠 mini-fab 之间的工作量差着好几个数量级。

## 2. 软件背后的人 {#story-2}
*HN 第 2 名 · [karrisaarinen.com](https://karrisaarinen.com/posts/someone-behind-the-software/) · 100 分 · 36 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50142573)*
*原标题: Someone behind the software*

Linear 联合创始人兼 CEO Karri Saarinen 的一篇文章，主张好的软件承载着制作者的口味、经验和判断力——他称之为产品的「灵魂」。他说 Linear 刻意把直觉置于流程和数据之上，而直觉指的是经过打磨形成的一种观点，而非个人偏好。他主要的抱怨是：许多产品，包括来自非常成功的公司的产品，如今感觉像是一堆堆叠起来的能力——「弗兰肯斯坦的怪物，而不是一件精心雕琢的雕塑」——他怀疑 AI agent（每个都像一家单人软件工厂）稀释了曾经赋予产品个性的那种共同视角。除了希望更轻松的软件开发能留出更多空间去培养并遵循一种观点之外，他并未给出任何解决办法。

**讨论**: 这个讨论帖大体上同意这一观点，并援引更早的框架来把它讲得更清楚：一位评论者通过 Fred Brooks 的《人月神话》引用了 Dorothy Sayers 的《The Mind of the Maker》，把创造描述为理念、实现和交互；另一位引用 Peter Naur 的《Programming as Theory Building》，警告说当你把工作委托给 AI 时，程序的理论就不再属于你了。最尖锐的分歧在于 AI 到底是不是元凶：一位评论者认为功能叠加的问题其实是经典的「创新者的窘境」——删掉东西会让用户不满，在公司内部政治上很难推行——而 AI 工厂只是在边缘让情况更糟；另一位同意 AI 只是强化了本已存在的力量，但认为 vibe coding 可能自下而上地带来颠覆。有几个人报告了具体的第一手观察，认为品味仍然跟随着提示者而不是工具：其中一位声称 Claude 产出的界面更宜人，因为它会从视觉上做验证，而 Codex 则「死板地照字面执行」，还像 1990 年代的 ERP 系统那样堆砌杂乱内容。还有两场次要辩论：独立开发者如今是否在交付有主见的软件上更有优势（大体上是的，只要他们不把太多决策交给 agent），以及直觉能否扩展到小团队之外，因为根本没有办法把 50 个人的直觉拿来相互权衡。爱好者们把类比延伸到软件之外——手工食物、服装，以及自工业革命以来被工厂夺走的物品——而一位评论者用一段讽刺的「手工打造、纯手工的代码行」戏仿，反驳了这种怀旧框架。

**值得一读的评论**
- [solatic](https://news.ycombinator.com/item?id=50143655): 认为这篇文章的核心抱怨根本与 AI 无关，而是「创新者的窘境」：删除或重做功能总会惹恼一部分用户，所以优秀的产品领导力需要「fuck with the user」的勇气，并接受用户流失。
- [jdw64](https://news.ycombinator.com/item?id=50143545): 引用 Peter Naur 的《Programming as Theory Building》——当一个程序所属的团队解散或知识传递失败时，这个程序就死掉了——并追问：当你把工作委托给 AI 时，这套理论是否还能存活。
- [kristianc](https://news.ycombinator.com/item?id=50143926): 来自实际使用的具体工具对比：Claude 会从视觉上验证自己的工作，界面直觉更好；而 Codex 对规格死板地照字面执行，却又堆上大量解释性文字和视觉杂乱；而 AI 所缺少的正是产品经理那种转译直觉。

## 3. Intel 8087 芯片：浮点加法与减法 {#story-3}
*HN 第 4 名 · [righto.com](https://www.righto.com/2026/10/8087-addition-subtraction-microcode.html) · 50 分 · 7 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50142449)*
*原标题: The Intel 8087 chip: floating-point addition and subtraction*

Ken Shirriff 在 righto.com 的文章拆解了 Intel 8087——这颗 1980 年的 x87 协处理器让 IBM PC 上的浮点运算在加法方面提速约 100 倍。他用凿子和显微镜给芯片开盖后，绘制了裸片的版图：一个含 1648 条微指令的微码 ROM，一种 80 位「temporary real」内部格式（符号位、偏置为 16383 的 15 位指数、64 位有效数字），一个 69 位整数加法器、一个桶形移位器、前导零检测与指数转换电路，以及八个带标签的栈寄存器。随后他从地址 #0232 开始逐步讲解实际的加/减微码——指数比较与操作数交换、用于对齐有效数字的 CREATE_DENORM 调用、符号锁存器的处理，以及针对溢出、零和非规格化（denormal）结果的规格化/舍入修正。

**讨论**: 该帖讨论规模不大，几乎清一色是赞赏，作者本人也几乎回复了每一条评论。有评论者指出一处笔误（二进制 1.1 × 2^8 等于 384，而不是 304），Shirriff 接受了这一纠正，因此全程并无实质性分歧。bonzini 询问 Shirriff 是否讲过 8087 的指令译码如何与 8086 共用，Shirriff 便给出了自己 2026 年 2 月关于 8087 指令译码那篇文章的链接。WalterBright 提供了最有力的亲历轶事：早期 Win32 在上下文切换时不会保存 8087 寄存器，他打电话给 Microsoft 要求他们别再破坏浮点状态，对方最终让步。其余评论则是怀念当年攒钱买 486DX 的往事，以及对 righto.com 的称赞。

**值得一读的评论**
- [WalterBright](https://news.ycombinator.com/item?id=50143956): WalterBright 说，早期 Win32 的上下文切换会丢弃 8087 的寄存器状态，直到他打电话向 Microsoft 提出异议才改变；他还说自己至今不明白为什么搞数值计算的人会忽视 8087。
- [n923263](https://news.ycombinator.com/item?id=50143070): 指出文章中的一处算术失误——二进制 1.1 × 2^8 是 384，不是 304——作者已承认。
- [bonzini](https://news.ycombinator.com/item?id=50143414): 询问 8087 的指令译码如何与 8086 共用，促使 Shirriff 给出了他早前那篇译码文章的链接。

## 4. Java 密封类与穷尽式模式匹配 {#story-4}
*HN 第 5 名 · [neilmadden.blog](https://neilmadden.blog/2026/04/24/java-sealed-classes-and-exhaustive-pattern-matching/) · 82 分 · 46 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50141579)*
*原标题: Java sealed classes and exhaustive pattern matching*

Neil Madden 的博文解释说，密封接口（Java 17）加上 switch 模式匹配让编译器能够检查穷尽性，因此不需要 default 分支——但仅限于同一个编译单元内。如果某个库新增了一个允许的子类型，而使用者没有重新编译，那么旧的使用方运行时就会抛出 MatchException，而不是在构建时失败，所以给一个导出的密封类型增加一个 case，实际上等同于一次 SemVer 主版本级别的破坏性变更。他的结论是：密封类型在组件内部非常出色，在公共 API 中则风险很高——他说，面向 PEM 编码密码学对象的预览 API 就犯了这样的错误，因为它建议客户端对一个密封接口做模式匹配。

**讨论**: 几乎没有人反驳文章的实际观点；整个讨论串演变成了一场 Java 对 Kotlin/Scala 的语言战争。Kotlin 支持者称密封类和模式匹配是「追赶」，随即在时间线上被纠正：Kotlin 的 `when` 自 1.0 起就是穷尽的，而 Java 的模式匹配要到 Java 21（2023 年）才出现，密封类则是在 Java 15（2020 年），而不是 17。一场旷日持久的交锋中，一方为 Java 刻意、极简、后发制人的设计辩护——他说团队有意没有采用任何 Kotlin 特性，约 90% 的 Java 平台开发者仍在使用 Java 语言，JDK 的 95% 是运行时和工具链——另一方则批评者列举了局部类型推断、switch 表达式、缺少 `with` 式方法/copy 的 record、被撤回的字符串模板以及被削弱的智能转换等特性，称它们都晚到 5 至 10 年。其他人则辩护说 Java 的一致性意味着少有尖锐的棱角，这一说法受到评论者质疑，他们指出泛型、类型擦除和型变恰恰就是这样的棱角，并更青睐 C# 的设计。支线讨论涉及：没有 JVM 的 Kotlin 是否存在（Kotlin/Native 是一个子集；JetBrains 仍在发布基于 JVM 的 IDE）、Java 缺失的可空性类型，以及在 LLM 写代码的时代字符串插值是否还重要。

**值得一读的评论**
- [Sharlin](https://news.ycombinator.com/item?id=50143419): 对前提的纠正：密封类早在 2020 年的 Java 15 中就已发布——是后来才出现的模式匹配让它们变得有用。
- [pron](https://news.ycombinator.com/item?id=50142728): 一位 Java 阵营的内部人士认为这种极简主义是有意为之：没有任何 Kotlin 特性被整体照搬，特性会被搁置多年，直到其价值足以证明复杂度的合理性，而 Java 在平台开发者中约 90% 的份额已保持 15 年以上。
- [dtech](https://news.ycombinator.com/item?id=50143624): 一位用户给出的犀利反例清单：局部类型推断、switch 表达式、缺少 copy()/with 式方法的 record、被放弃的字符串模板以及被削弱的智能转换，都比 Kotlin 晚了 5 至 10 年以上，他称之为「weaksauce」。

## 5. Sigsaly：丘吉尔通往总统的绝密热线 {#story-5}
*HN 第 6 名 · [iwm.org.uk](https://www.iwm.org.uk/history/iwm/cwr/telephone) · 62 分 · 6 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50096110)*
*原标题: Sigsaly: Churchill's top secret hotline to the President*

Imperial War Museums 的一篇历史页面，介绍 SIGSALY——连接伦敦与华盛顿的加密跨大西洋语音线路。Bell Telephone Laboratories 于1940年10月启动该项目（当时名为“Project X”），把语音数字化，再与两端同步播放的同一批12分钟唱片所产生的随机噪声混合，然后用声码器还原语音；每台终端机按1943年币值计造价100万美元，重逾50吨。

## 13. 解析器组合子 {#story-13}

## 17. Teal —— Lua 的静态类型方言 {#story-17}
*HN 第 24 名 · [teal-language.org](https://teal-language.org/) · 131 分 · 56 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50124730)*
*原标题: Teal – A statically-typed dialect of Lua*

Teal 是 Lua 的一个静态类型方言，由 Hisham Muhammad 发起，编译器名为 tl，把 .tl 源码编译成 .lua 文件。它给 Lua 加上数组、映射、记录的类型注解，以及接口、联合类型和泛型，定位类似 JavaScript 世界里的 TypeScript，但坚持 Lua 的极简、可移植和可嵌入精神。项目用 Teal 自己写成，MIT 许可，配套有构建工具 Cyan、teal-language-server 和 vscode-teal 扩展。

**讨论**: 讨论很快分成两条线。第一条是同类项目辨析：有人指出这与 Terra 不是一回事，更接近「给 Lua 加类型的 TypeScript」；有人问与 Luau 的比较，回答是 Luau 是另一门语言和运行时，而 Teal、Fennel、MoonScript 属于 Lua 语法三大流派；还有人纠正 Fennel 由其创建者 Calvin Rose 所写、现在的维护者是 technomancy。第二条线几乎占了一半篇幅，是「LLM 时代还需要新语言吗」的争论：有人质疑这类实验除艺术价值外还有什么用，反驳者则说 Teal 早于 LLM 且静态类型检查器对 AI 生成的代码恰恰有帮助，因为编译期错误是廉价而明确的反馈。此外还有老生常谈的 1-based 索引之争，以及 Lua 是否适合独立写大型程序的分歧——有人称自己用 LuaJIT 交付并维护多年、反驳「Lua 写非平凡程序是徒劳」的说法。

**值得一读的评论**
- [ufo](https://news.ycombinator.com/item?id=50140999): 给出一个大规模生产用例：Lua 包管理器 Luarocks 的 src/luarocks 目录本身就是用 Teal 写的。
- [saghm](https://news.ycombinator.com/item?id=50139788): 第一手经验：作者为给一个 mod 加功能而把代码移植到 Teal，并观察到 LLM 写的 Lua 质量很差（滥用 pcall 当控制流），而 Teal 能静态约束类型。
- [veqq](https://news.ycombinator.com/item?id=50142918): 纠正 Fennel 的归属：Calvin Rose 创建了 Fennel 和 Janet，technomancy 只是现在的维护者。

## 19. Hatching（纹章学） {#story-19}
*HN 第 27 名 · [en.wikipedia.org](https://en.wikipedia.org/wiki/Hatching_(heraldry)) · 61 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50093081)*
*原标题: Hatching (Heraldry)*

这是 Wikipedia 上关于 hatching（影线）的条目：纹章学中用点和线来表示 tincture（颜色）的体系，以便在木刻版画、铜版画、印章和硬币上以单色呈现纹章。条目把今天的这套体系追溯到 17 世纪 30 年代，追溯到 Silvester Petra Sancta 和 Marcus Vulson de la Colombière，但主张首创权其实属于鲁汶（Leuven）的雕版师 Jan Baptist Zangrius，他们只是改动了其 1600 年体系中 Sable（黑色）的影线画法。条目还把低地国家的铜版雕刻师——Franquart（1623）、Butkens（1626）、de Rouck（1645）——列为共同开发者，因为影线所需的线距比木刻版画能做出的更细。

**讨论**: 讨论基本没有围绕这个 3D 演示本身，而是迅速演变成一场正则表达式到底难在哪里的辩论。一派（ogogmad、atoav）认为正则的核心其实极小——量词 . | ? * +、捕获组 () 和懒惰变体 ?? *? +?，其余都是语法糖，难的是教学材料一上来就展示全部复杂度；另一派（StilesCrisis、nick__m、crazygringo）反驳说这远不是全部，还有反向引用、前后向断言、递归、内联标志等，PCRE2 兼容的正则可能极其复杂。围绕反向引用出现了最有技术含量的一轮交锋：有人称其为有争议的特性，随后被纠正为它并非「有争议」，而是超出了正则语言的表达力（对应有限自动机无法表达），支持它会让最坏匹配时间从 O(n) 升到指数级、问题变成 NP 完全，因此多数引擎用回慢速算法。另一个分支是 crazygringo 对正则语法的控诉（全是标点、没有注释和换行、转义地狱），多人指出大多数引擎的扩展/verbose 模式（如 x 标志）本就允许空白和注释，还有人推荐 pomsky-lang.org 和 Raku grammar 作为可读替代方案，也有人主张直接为复杂正则写单元测试。此外有零星实测反馈：输入框似乎限制在 301 个字符，有人表示希望加上音效和跟随镜头。
