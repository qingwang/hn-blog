## 1. Local Wikipedia：只收录距你半小时步行范围内的内容的维基百科 {#story-1}
*HN 第 1 名 · [edjefferson.com](https://edjefferson.com/localwiki/) · 87 分 · 20 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50202285)*
*原标题: Local Wikipedia: Wikipedia, but only for things a half hour walk from you*

这是 edjefferson.com/localwiki/ 上的一个副业项目，它把维基百科的范围缩小到所选地点附近带有地理坐标标记的条目，地点似乎是以邮政编码输入的，这样用户就能看到大约半小时步行范围内的本地历史和地标。所链接的页面在未启用 JavaScript 的情况下几乎没有可读文本，因此仅凭文章本身无法确认它具体如何处理距离，以及支持哪些语言。

*未能读取原文：page had almost no readable text (probably needs JavaScript or a login)*

**讨论**: 评论者大多觉得这个想法很有趣，并立刻上手试用：一位在俄勒冈州波特兰的人三次点击「随机条目」，得到了三个此前不知道的本地故事；其他人则发现了帕洛阿尔托一家旧书店咖啡馆，以及巴伐利亚西部一座从未听说过的修道院。最集中的诉求是提供语言选择器，因为在许多地区英文维基百科的内容很稀疏，而当地语言版本往往条目多得多；可调节的距离和公制单位也被反复要求，此外还有按教堂、桥梁和博物馆等类别筛选的功能。一位评论者提出了技术性批评：该网站似乎会漏掉附近没有地理坐标标记的条目，而且图片不可点击。其他人则指出维基百科自带的 Special:Nearby 以及 wiki-map.com 可作为替代方案，不过有一条回复指出，Special:Nearby 依赖浏览器定位，而在台式机 ISP 环境下定位往往极不准确。

**值得一读的评论**
- [dllu](https://news.ycombinator.com/item?id=50205142): 指出该工具会漏掉附近缺少地理坐标标记的条目，并且它的图片没有可用的链接来放大查看。
- [slymax](https://news.ycombinator.com/item?id=50205289): 指出维基百科已经有一个多语言的 Special:Nearby 功能。
- [edwcross](https://news.ycombinator.com/item?id=50205305): 解释了 Special:Nearby 为何常常无法使用：它需要位置权限，而台式机 ISP 的定位可能离用户实际住所很远。

## 2. Docker 很奇怪 {#story-2}
*HN 第 2 名 · [codeandcake.dev](https://codeandcake.dev/posts/2026-10-22-docker-is-weird) · 366 分 · 180 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50202681)*
*原标题: Docker is weird*

一位自行开发业余容器运行时的开发者写下了 Docker 令其惊讶之处：容器并非虚拟机，而是能在 /proc 中看到的普通进程，「container」实际上是一个由命名空间、cgroups、网络技巧以及在镜像目录上执行 chroot/pivot_root 组成的捆绑体。他们认为 Go 并不适合 runc——Go 的多线程运行时迫使在运行时之前插入一个 C shim 来处理单线程系统调用，Go 也没有真正的 fork，所以 runc 只能重新执行 /proc/self/exe——并指出该守护进程历史上需要 root 权限，而无 root 方案仍不得不在用户空间重新实现网络。

**讨论**: 这个讨论帖很大程度上被 Docker 的创造者 Solomon Hykes 占据，他回答了关于 Docker 在 2013 年之前 dotCloud 时期的历史、从 openvz 转到 lxc 再转到自研 Go libcontainer 的过程、有意选择 Go 以便交付一个所有语言社区都能采用的编译后单一二进制文件、失败的 Moby 重组，以及他当前的项目 Dagger；他承认文章说得对，Go 与内核接口确实相互冲突，但表示在当时那是正确的决定。评论者对细节提出了反驳：一位前 Docker 工程师指出运行时最重要的部分是用 C 写的，还有几个人坚称 Docker 大约七年来都不再需要 root，无 root 运行主要受限于网络——多个人指出 slirp 式用户空间协议栈、Podman 和 nspawn 是替代方案。一个反复出现的反驳论点是，文章漏掉了真正古怪的设计决定，即客户端/服务器守护进程架构，而另一些人则为它辩护，称这是让非特权用户启动容器、并让 Mac 和 Windows 用户获得相同 CLI 的唯一可行方式。语言之争围绕 Rust 是否会比 Go 更好而爆发（多数人同意 2013 年时 Rust 还太不成熟，支持者则援引 Go 的安全性以及对贡献者友好这一点优于 C），而一个较小的阵营表示，了解历史之后，清单上的东西其实都不奇怪。整体情绪主要是怀旧与感激，人们回忆早期的演示、Vagrant/LXC 带来的痛苦，以及 Docker 在终结「works on my machine」方面所起的作用。

**值得一读的评论**
- [shykes](https://news.ycombinator.com/item?id=50203555): Hykes 纠正了 Docker 是 LXC 商业化的说法：它最初基于 OpenVZ（早于 LXC），后来改用 LXC 用户态工具，再之后用自研的 Go libcontainer 取而代之——他还反驳了 Docker 把任何事情商业化得很好的说法。
- [shykes](https://news.ycombinator.com/item?id=50204886): Hykes 讲述了 2013 年 PyCon 闪电演讲的经历，Docker 实际上正是在那次演讲上爆发：他本以为会来 10-20 人，结果被安排到主舞台，演讲超时，回到 dotCloud 展台时发现一群人围在那里询问一个营销团队从未听说过的「副项目」。
- [stingraycharles](https://news.ycombinator.com/item?id=50203300): 对文章所列清单的一个有力反驳：真正古怪的决定是客户端/服务器守护进程架构，下面的评论者对此争论不休，有人认为它是权限管理的噩梦，也有人认为正是它让 Docker 在 Mac、Windows 和 Linux 上表现完全一致。

## 3. 大语言模型正让形式化软件验证在远大于以往的规模上变得可行 {#story-3}
*HN 第 3 名 · [anthropic.com](https://www.anthropic.com/research/formal-verification) · 286 分 · 157 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50202217)*
*原标题: LLMs are making formal software verification feasible at a much larger scale*

这是 Anthropic 的一篇研究文章，与创业公司 Theorem 合作完成。文章称 Claude 自主写出了 Rocq 证明，证明 123 个 OSS-Fuzz 开源库中的 239 个模糊测试入口点，在任何小于 64 MB 的输入下都不会崩溃。这些证明针对编译后的 RISC-V 汇编，总计约 1.8 亿行 Rocq；对于指令数中位数为 18,000 的二进制文件，典型证明约为 600,000 行。假设范围很窄：仅限单线程静态二进制文件、固定内存预算、Linux 上的 RISC-V；可信基仅限于 RISC-V/Linux 的进程语义、定理陈述本身以及 Rocq 检查器。在证明过程中，Claude 发现并修复了模糊测试器此前漏掉的缺陷，包括：一个解压器的计数器下溢，需要约 20 MB 且布局罕见的输入才能触发；一个图像解码器的越界读取，需要 64 MB 输入和超过 2 GB 内存；以及重新发现了 libexpat 中的 CVE-2026-56132。Theorem 将发布这条流水线和一项 Claude skill；Anthropic 还提到 Opus 5.5 完成了 36 个小型验证任务中的一半，所用 token 比 Opus 5 少约 40%。

**讨论**: 最主要的讨论线是信任：这些证明究竟覆盖了什么，你又如何知道规格说明与代码是一致的。多位评论者对定理陈述以及 RISC-V/Linux 模型提出质疑；论文作者之一回复时给出了 rocq-linux-process-semantics 仓库、riscv-coq 以及 oss-verify 证明仓库的直接链接。第二组讨论认为，这算不上真正的形式化验证，因为规格说明不过是「这个模糊测试永远不会崩溃」；支持者反驳说，许多模糊测试本身就编码了真实的性质（往返、幂等、差分测试），而且对 64 MB 以下的所有输入做全称量化，严格强于任何模糊测试器；怀疑者则指出，这不涉及意图、并发或多线程。最尖锐的批评帖引用了论文自己的附录，其中承认智能体生成的证明很冗长，而且如果抽象不够好，可能会撞上复杂度之墙；该评论把这与「大语言模型无法泛化到人类数学的凸包之外」的说法联系起来。论文合著者则辩称，软件验证与数学不同，因为瓶颈在于规模，而非分布外泛化。实践者也给出了正面评价：一位正在把 C 和 Rust 翻译成 Lean，以验证一次 Postgres 重写（按他自己的说法，约占代码的 12%、约 7 万行 C，且仅限单线程）；另一位在工作中合并 SIMD/CUDA 优化时很有信心，因为每个优化都附带了在 LLVM IR 层面证明与原始代码行为等价的 Rocq 证明；还有人提到基于 Alloy 和 ESBMC 的工作流。少数声音较大的人称这是一场营销活动，援引停机问题（很快被纠正——该主张针对的是特定程序，而非任意程序），并认为业界只会把省下的精力拿去发布更多未经验证的代码。

**值得一读的评论**
- [jaykru](https://news.ycombinator.com/item?id=50202573): 引用论文附录，其中承认智能体生成的证明冗长，并可能撞上复杂度之墙（如 MachCSL 那样），并将其与「凸包」假说联系起来——大语言模型的能力在人类数学边界之外就会停滞。
- [malisper](https://news.ycombinator.com/item?id=50203167): 一位实践者报告称，用大语言模型为 Rust Postgres 重写中约 12% 的代码（约 7 万行 C）写出了行为等价性的 Lean 证明，并且已经借此发现了跨平台浮点差异。
- [sestep](https://news.ycombinator.com/item?id=50203196): 第一手生产使用经验：一位工程师能放心合并 SIMD/CUDA 性能优化 PR，因为每个 PR 都附带了与原始代码行为等价的 Rocq 证明，而且证明读取的是实际代码，并用模糊测试将语义模型与真实硬件对照。

## 4. 这就是我的信念（1952） {#story-4}
*HN 第 4 名 · [awakin.org](https://www.awakin.org/v2/read/view.php?tid=468) · 56 分 · 14 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50203759)*
*原标题: This I Believe (1952)*

Robert A. Heinlein 于 1952 年发表的一篇短文，发布在冥想网站 Awakin.org 上。文中他宣称自己信仰的不是宗教，而是普通人：神父 Father Mike、半夜起床照顾流浪猫的兽医 Doc、会招待任何敲门说饿了的人的镇上居民、诚实的手艺人，以及——更具争议的一点——「几乎所有的政客」。他认为善良并不算新闻，每有一个罪犯，就有一万个诚实的人，并以一个宏大的论断收尾：人类将会「存活、延续」，比自己的母星存在得更久，并扩散到群星之间。该页面还配有读者感想和 Awakin Circle 的讨论记录，其中一份对这篇文章的创作年代提出了质疑。

**讨论**: 该讨论帖不大（14 条评论），意见分为赞赏和反驳两派。最尖锐的分歧在于 Heinlein 本人：一位评论者称他「一方面极其进步，另一方面又极其倒退，有时在同一段话里就能看到」，这引来了一些回复，认为「倒退」是一个带有倾向性的反义词，他其实只是保守主义者，而保守主义是一种保留行之有效之物的连贯策略——但有人反驳说，保守主义建立在内群体与外群体的区分之上，不应被当作普世伦理来推销。几位读者质疑的是文章的内容而非作者：有人说在 2026 年还相信几乎所有政客都诚实是不明智的；另一位指出，许多地方与 Heinlein 的家乡截然不同，所以文中的图景并不具有普遍性。一位对太空乐观主义持怀疑态度的评论者指出，到了 2026 年，我们仍然只能把发射质量的一小部分送入真正的太空，而燃料的能量密度和吞吐量也仍远未达到文章所描绘的星际航行愿景所需。最实际的警告是：Awakin 页面上的文本似乎经过编辑，一些段落被删除，可能还有部分是机器生成的——所以网站上的版本可能并非 Heinlein 本人的原文。两条评论点出了情感内核：一则关于 Philip K. Dick 的轶事——Heinlein 曾悄悄借钱给他缴 IRS 的税；以及这样一种观察：当文明不再相信这一点时，它就会消亡。

**值得一读的评论**
- [jankovicsandras](https://news.ycombinator.com/item?id=50205068): 引述 Philip K. Dick 对 Heinlein 的评价——他是「这个世界上为数不多的真正绅士之一」：Heinlein 给生病的 Dick 打电话，提出给他买一台打字机，还借钱给他缴 IRS 的税，尽管他并不认同 Heinlein 写下的任何观点。
- [u1hcw9nx](https://news.ycombinator.com/item?id=50205283): 警告说 Awakin 页面上的文本已被网站所有者编辑过——段落被删除——而且可能是机器生成的劣质内容，所以它可能未能忠实呈现 1952 年的原文。
- [rf15](https://news.ycombinator.com/item?id=50205182): 认为结尾处的太空乐观主义站不住脚：我们只能把发射质量的一小部分送入真正的太空，而燃料的能量密度和吞吐量仍远未达到星际旅行所需。

## 5. “自然语言编程”的愚蠢之处（1978） {#story-5}
*HN 第 7 名 · [cs.utexas.edu](https://www.cs.utexas.edu/~EWD/transcriptions/EWD06xx/EWD667.html) · 113 分 · 70 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50203161)*
*原标题: The foolishness of "natural language programming" (1978)*

EWD667 是 Edsger W. Dijkstra 于 1978 年写的一篇短文，由 UT Austin 计算机科学档案馆转录，主张让人们用母语指挥机器并不会让生活更轻松。他的论点是：接口的改变并不是一种固定的劳动分工——围栏两侧所增加的工作都可能增多，这正是窄接口胜出的原因——而形式符号之所以有价值，恰恰在于对它们进行操作只需满足少数几条简单规则，从而排除了自然语言轻易容许的胡言乱语。他最后猜想：能用荷兰语、英语或斯瓦希里语编程的机器，造起来会和使用起来一样难如登天。

*原标题: Speeding up code review with `small-change`*

Will Larson 讲述了 Imprint 的工程组织如何从平均合并 PR 数量达到两年前的 4 倍（两个团队达到 10 倍，其中一位工程师达到 25 倍），走到一个新的瓶颈：PR 审查时间中位数从 33 分钟升至 77 分钟。他们的解决办法是「small-change」：一项 CI 检查（而非由人手动添加的标签），只有在 PR 少于 1,000 行、其 AI 代码审查机器人没有给出 p1/p2 级别问题、根据 monorepo 不同只触及少于 1 个或 3 个服务、不包含共享库，且作者在这些目录中已有 10 个以上此前合并的 PR 时，才会将 PR 标记为可自动批准，并支持按仓库配置 .small_change 覆盖规则。一个名为 review-small-change 的 harness 技能只能批准或忽略这类 PR——绝不能发表评论——目前约有 10% 的变更符合条件；Larson 表示构建它大约花了两天，并承认质量提升（事故减少 42%，严重事故减少 78%）才是真正的赌注，而不是审查捷径。

**讨论**: 最强烈的反应是，1,000 行算不上小改动——几位评论者认为真正的阈值是一屏（36–48 行）、一千个字符，或者你能在脑中完整记住的连续代码块——不过有人为该上限辩护，称其刻意设得宽松，以免有用的测试把改动推过线；另一位指出，它是一个 AND 条件，需与作者经验和文件路径规则同时满足。另一派则否定整个设计：一位评论者称其为面向受信任开发者的「YOLO bro allowlist」，另一位则认为真正低风险的改动无论如何也只需 1–5 分钟就能审查完，第三位说标题误导了他们——他们期待的是关于编写更小 diff 的建议，而不是取消人工审查。其他人则报告说构建过类似系统并且很喜欢它们：一种反向的 needs-human-review 标签方案，约有一半 PR 自行合并；一个可按路径配置的 review-bar 机器人，让约 30% 的 PR 无需审查即可合并；以及一套基于 Terraform 的 PR 拆分设置，其中 80% 的 PR 符合条件。最有力的反证来自实证：故障注入数据（归因于 McConnell）显示，每行代码的缺陷数在 1–5 行的改动中最高；一位实践者表示，过去六个月里每一个糟糕的改动都与 PR 创建后 30 秒内点击的批准相关，即使确定性和 AI CI 检查都已到位。

**值得一读的评论**
- [0xbadcafebee](https://news.ycombinator.com/item?id=50202303): 详细的第一手反向设计：Claude 规则将 Terraform 变更拆分为堆叠的、可分别合并的 PR，使 small-change 比例达到 80% 而非 10%，因为 Terraform 资源提供了可部署工作的天然最小单元——并附有 Fowler《Continuous Integration》文章的链接。
- [fishtoaster](https://news.ycombinator.com/item?id=50202079): 描述了他们在生产环境中运行的反向方案——确定性检查会添加 needs-human-review 标签，而不是给予豁免——比例大约各占一半，规则大多基于文件路径，仍会产生误报。
- [beart](https://news.ycombinator.com/item?id=50202849): 第一手说法：过去六个月里每一个被合并的糟糕改动，都与 PR 创建后 30 秒内的橡皮图章式批准相关，尽管确定性和 AI 审查检查都已到位。

**讨论**: 评论者大体上怀疑这套因果解释：有人表示，寿命统计数据并不能说明营销更重要，而 LLM 生成的功能往往是有 bug 的，而不是免费的。一条统计学上的反对意见指出，中位数下降与更多产品成功并不矛盾，只要失败的增长更快即可；另一人则认为，如果几乎没有人成功，那么 fail-fast 就是不健康的。多位开发者描述了低成本构建的好处——其中一位让 Claude 生成了一个 RISC-V 模拟器，不到一小时就能跑起 Debian 的 bash 和 sqlite，不过他对代码的正确性表示怀疑；另一位说，如今小巧的个人工具已经胜过它们所取代的商业应用。还有人把软件比作靠爆款驱动的电影或音乐，强调许可证和内容这类无法复制的资产，并指出一致性和手艺仍然需要数千小时；一人警告说，SaaSHub 自己的列表看起来就像 vibe-coded 的产物，还含有幻觉内容。大家普遍认同开发软件变便宜了，但对于这是否能解释墓地数据，并未达成共识。

## 20. 女子因诈骗用 CashApp 账户挂在其名下而被控计算机欺诈 {#story-20}
*HN 第 44 名 · [404media.co](https://www.404media.co/amanda-smith-opened-a-cashapp-in-her-name-she-faces-years-in-prison-cashapp-fraud/) · 622 分 · 620 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50194833)*
*原标题: Woman charged with computer fraud due to scam CashApp account being in her name*

404 Media 的一篇报道（部分内容需付费）讲述了宾夕法尼亚州北部的 Amanda Smith：一名骗子用她的社会安全号码和出生日期开通了一个 Cash App 账户，从一位 Facebook Marketplace 受害者那里骗走 1,000 美元；她因此于四月依据阿肯色州的一份计算机欺诈逮捕令被捕。她在监狱里待了三个晚上——一位评论者引用了 50,000 美元的保释金数字——她从未去过阿肯色州，也从未使用过 Cash App，并说 Cash App 拒绝向她提供账户详情，因为她无法证明自己拥有该账户；她最终通过刑事证据开示程序拿到了这些信息。据报道，当局提出了一份认罪协议：1,000 美元罚款、1,000 美元赔偿以及三年缓刑，她已拒绝。

**讨论**: 讨论几乎完全围绕认罪协商展开：评论者认为，检察官的考核依据是定罪率和选举中的「严厉打击犯罪」数字，因此给出廉价的认罪协议就能结案，而无人承认错误；有几人称这种协议具有胁迫性，因为替代方案是一场风险很高的审判和长得多的刑期。少数人对这种愤怒提出反驳：一位评论者指出，文章从未说明那些相互矛盾的证据确实被呈交给了检察官；另一位认为，任何痴迷于胜诉率的地区检察官都不会仅凭社会安全号码和地址就起诉，并认为报道中缺少了某些东西；还有两人称这是一起成为新闻的极端个案，正因为它不正常才成为新闻。第二组讨论则针对 Cash App/Block 薄弱的 KYC 以及对真正账户持有人的推诿，并将其与银行级验证、欧盟/德国的芯片加 PIN 国民身份证，以及巴西的 Registrato 退出机制相比较；一个子讨论指出，美国和英国一样是普通法系（纠正了一种大陆法系理论），而且警察不会签发传票。实用建议很少——信用冻结很可能没有帮助，因为 Cash App 可能根本不查询信用记录；而自己开设一个账户也是软弱的防护，因为允许开设多个账户。

**值得一读的评论**
