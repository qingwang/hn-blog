## 1. sshole {#story-1}
*#1 on HN · [sshhole.com](https://sshhole.com) · 1,843 points · 482 comments · [HN discussion](https://news.ycombinator.com/item?id=50378228)*

sshole.com 是一个关于 musl libc 和 OpenSSH 组合漏洞的单页漏洞披露。musl 的 SHA-512 crypt 对超过 256 字节的密码返回错误，但 musl 为了让不检查 NULL 的旧程序不崩溃，把错误返回值定为单个字符 「*」，而 /etc/shadow 里「禁止登录」的账号哈希正好也是 「*」。OpenSSH 为了防 CVE-2016-6210 的计时攻击，遇到 「*」或 「!」账号时会拿另一个真实账号的 salt 去哈希密码，然后和原来的 「*」比较，于是 257 到 1024 字符的密码让 crypt() 返回 「*」并与存储值相等，登录被接受。利用条件为：musl + 不用 PAM（或 UsePAM no）+ 开启密码登录 + 存在一个 「*」账号 + 另有一个真实密码账号；Alpine 官方云镜像里的 alpine 用户带免密 doas，等于直接拿到 root。作者称用 AI agent swarm 对多种构建（glibc/musl、PAM/无 PAM）跑了约 17,600 次异常登录才发现，并且需要先失败一次、第二次才成功。

**Discussion**: 讨论一开始就分成两派：一派认为这是严重的现实漏洞，指出几乎每台 Linux 都有 「*」和 「!」账号、默认配置就开密码登录、Alpine 容器基数巨大，而且 Alpine 云镜像的默认 alpine 用户直接通向 root；另一派认为条件全是 AND、实际可利用面很窄，并质疑文章夸大了严重性。多人尝试复现但失败，随后有人指出 Alpine 已经把各版本（含 EOL）的 openssh-server 打了补丁，回退 aports 提交后即可复现，也有 lab 和 Docker 复现仓库被贴出。大量评论批评 musl 用 「*」表示错误是荒谬的带内信号设计，甚至怀疑是故意留的后门，同时称赞用错误值掩盖 NULL 崩溃的做法让坏程序活得更久；也有人反驳说 glibc 后来用 「*0」也是同类做法。关于受影响面，OpenWrt/AsusWRT 默认用 dropbear 因此不受影响（但 2019.77 之前的 dropbear 没有 100 字符上限），而 Alpine 官方 openssh 包已在 10.6p2 修复。另一条主线是对页面本身的抱怨：滚动劫持、动画和 AI 腔调导致很难读完，不少人说评论区某条解释比原文清楚。

**Worth reading**
- [amluto](https://news.ycombinator.com/item?id=50380581): 指出 musl 的 crypt_des.c 早就为同类失败做了 「*」的变通，只是 SHA-512 路径忘了做；同时说明 sshd 在哈希过短时不会转发 salt，所以只在 SHA 路径打补丁也堵不住这个洞。
- [evgpbfhnr](https://news.ycombinator.com/item?id=50379454): 总结出实际复现的关键细节：目标账号的 shadow 必须是单个 「*」（不是 「!」），且要先失败一次、第二次用超长密码才会被接受；并指出默认容器镜像里的 alpine 用户让影响变大。
- [mari_dtfy](https://news.ycombinator.com/item?id=50380097): 来自 Detectify 从业者的可操作清单：Alpine 3.16 到 3.24 及 edge 的 openssh-server 均受影响，修复包已回滚发布，给出 apk info、sshd -T 检查命令，以及补丁后按 「Accepted password for」 日志排查的方法。

## 2. Alpine Linux Security Advisory: OpenSSH-server password authentication bypass {#story-2}
*#2 on HN · [alpinelinux.org](https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/) · 425 points · 76 comments · [HN discussion](https://news.ycombinator.com/item?id=50379704)*

这是一份 Alpine Linux 安全公告：在未启用 PAM 构建的 openssh-server（以及 openssh-server-pam 配 UsePAM no）上，攻击者无需密码即可登录。成因是 musl 的 crypt() 对超过 256 字节的密钥返回字符串 *，而 * 正是无密码账户在 shadow 中的存储值，于是 sshd 借用的 salt 哈希与之「匹配」，一次连接即可成功。前提是机器上存在至少一个 $5$/$6$ 哈希账户；Alpine 3.16 至 3.24 及 edge 均受影响，修复版本为 OpenSSH 10.6p2 及 Alpine 3.21.10 / 3.22.8 / 3.23.8 / 3.24.4 的包，升级后必须重启 sshd，撰写时尚无 CVE 编号。

**Discussion**: 讨论很快从漏洞本身转向语言与 libc 设计之争。多人追问 musl 为何在错误时返回 * 这种哨兵值，指出这直接违反 POSIX 关于失败应返回 NULL 并设置 errno 的规定，并认为 musl 以「严格遵循规范」著称，此处尤为讽刺；也有人辩护说这是为了替不检查 NULL 的调用方兜底，且能避免通过时序侧信道泄露账户是否存在。另一大分支是 C 与 Rust 的老争论：一方称 Result/Option 强制处理错误就能从源头阻止此类 bug，另一方（包括数位工程师）反驳这是纯逻辑 bug，任何语言里库作者都可以选择用字符串哨兵，而且 C 里返回 NULL 被解引用通常也会安全地 trap。实务层面有人表示自己在硬件上跑 Alpine 但因为没有无密码账户而未受影响，也有人担心 Docker 生态里基础镜像更新缓慢会拖累修复；还有人认为大多数容器并不对外暴露 sshd。另有一条高赞支线指责公告部分段落像是 AI 写的，随后被其他人温和反驳，认为读安全公告时不必逐句做文体审查。

**Worth reading**
- [NewJazz](https://news.ycombinator.com/item?id=50380253): 引用 POSIX crypt() 规范原文，质问 musl 为何在错误时返回 * 而非 NULL，并问是否为唯一这样做的 libc。
- [cyphar](https://news.ycombinator.com/item?id=50381179): 指出返回哨兵值其实是为了伪装一次哈希校验、避免时序侧信道暴露用户是否存在，但同时质疑示例代码未用常数时间比较。
- [pheggs](https://news.ycombinator.com/item?id=50382995): 反驳「musl 不安全」的论调：一次漏洞不算统计证据，且可以说 musl 已记录该行为，是 OpenSSH 忽略文档所致。

## 5. The Lisp curse, now coming to your ecosystem {#story-5}
*#5 on HN · [javahippie.net](https://javahippie.net/programming/llm/2026/03/05/the-lisp-curse-coming-to-your-ecosystem.html) · 142 points · 86 comments · [HN discussion](https://news.ycombinator.com/item?id=50349667)*

A blog post from javahippie.net arguing that the 「Lisp curse」 — a language so flexible that everyone builds their own bespoke solution and nobody shares libraries — is about to hit mainstream ecosystems like Java, this time driven by LLM-assisted coding. The author predicts two compounding effects: fewer people using open source libraries (so maintainers lose feedback and contributors), and fewer new libraries being created, since maintenance and project management cost far more than generating a module tailored to your own stack. He concedes the premise that generating code is cheaper than learning library APIs but rejects it as a good idea, calling 「Not generated here」 a rebadged 「Not invented here」, and expects the decline to arrive gradually and by accident rather than by proclamation.

**Discussion**: The thread splits three ways. Several commenters attack the Lisp framing itself: Common Lisp is alive (SBCL, Quicklisp/Ultralisp, Lem), Clojure is the real modern success because it piggybacks on the JVM, and one 20-year Lisp veteran argues the curse is partly an artifact of 「Lisp」 being ambiguous across Common Lisp, Scheme, Emacs Lisp and Clojure — within any single dialect reuse is normal. Others report the predicted behaviour already happening: multiple people describe having an agent patch a local fork of an OSS project (fixing bugs, debugging an obscure Qt/OFX import failure) and never submitting the patch because they never read the generated diff and lack the time or domain knowledge to defend it. The sharpest disagreement is about security: one camp says supply-chain risk and transitive dependencies make reimplementation the safer trade, while others counter that vendored code never gets patched, LLMs can trip license terms, and some domains (crypto, numerics) must not be hand-rolled. A recurring counter-argument to the whole thesis is that the same agent can just as easily integrate the mature library, and that the author's parenthetical concedes the point. Pessimists see AI-generated slop flooding GitHub and devaluing contribution; a few note open source's career-building incentives were always a bit broken anyway.

**Worth reading**
- [jedberg](https://news.ycombinator.com/item?id=50383555): A concrete instance of the predicted decay: he has an agent patch a local fork of an open source project to fix bugs, rebases it occasionally, and never upstreams the patches because he hasn't reviewed the agent's code and has no time to.
- [AnimalMuppet](https://news.ycombinator.com/item?id=50381985): Draws a hard line against the 「roll your own」 camp — never write your own crypto or numeric libraries, since decades of corner-case hardening can't be reproduced in a lifetime, so library reuse genuinely does improve quality in some domains.
- [drob518](https://news.ycombinator.com/item?id=50381933): After 20+ years across Lisp dialects, argues the curse is only 「sorta true」: the real issue is that 「Lisp」 conflates Common Lisp, Scheme, Emacs Lisp and Clojure, while within a given dialect — Racket's package set, Clojure mixing with Java libs — reuse is substantial.

## 6. Launch HN: Rivet (YC W23) – Scale and Orchestrate Agents on S3 {#story-6}
*#6 on HN · [github.com](https://github.com/rivet-dev/rivet) · 36 points · 20 comments · [HN discussion](https://news.ycombinator.com/item?id=50381687)*

Rivet is an open-source (Apache 2.0) orchestrator for agentic workloads built on the virtual actor model: each agent gets a long-lived process with in-memory state, a per-actor SQLite database, WebSockets and cron, rather than a dedicated sandbox. The pitch is density and speed — 72 KB RAM per actor versus 512 MB for a minimal sandbox, 4.99 ms p99 cold starts versus 1.70 s — with SQLite writes acknowledged once SSDs in 2 of 3 availability zones have them and then batched to S3 in the background, yielding 1.07 ms p99 durable writes, 1.36 ms p99 reads, 138 ms p99 fallback reads from object storage, and roughly 10.4× cheaper storage than three EBS gp3 replicas. It replaces Postgres/FoundationDB/NATS with a single S3 bucket as the only dependency, self-hosts as one Rust binary, and is marketed as a self-hostable alternative to Cloudflare Durable Objects without the 128 MB memory cap, 10 GB SQLite limit or random evictions; the benchmark numbers are Rivet's own, run on Rivet 3.0.3, with sandbox figures from documented defaults and a third-party cold-start benchmark.

**Discussion**: Commenters were broadly positive — one reports moving a piece of Cloudflare Durable Object infrastructure out of its 「fairy tale land」 and into their own VPC with a pleasant experience, and others compare the design to celld. The real argument is whether orchestration speed matters: a top commenter says agentic workloads spend most of their time waiting on the model and that Rivet should have led with durability, with others countering that the latency matters for products running dozens or hundreds of concurrent agents and for time-to-interactive realtime use cases. Nathan Flurry answers the sandbox question with three patterns — agents that only need tools, a V8/WebAssembly sandbox (agentOS) for JS/Python with a POSIX filesystem, and agents run outside the sandbox with the sandbox exposed as tools — and says cold starts, not sandbox state recovery, are the bottleneck. He also says Rivet got Claude Code and Codex running inside agentOS but prefers the 「harness outside the sandbox」 architecture for blast radius and because per-instance memory overhead is 「nuts」, and that an object-per-actor S3 design does not scale, hence their SSD-tiered storage engine. The one sour note is usability: a commenter says their coding agent was as confused as they were about how to use it, and Nathan asked for details; others confused the project with Apache's mod_rivet and Ironclad's unrelated Rivet.

**Worth reading**
- [NathanFlurry](https://news.ycombinator.com/item?id=50382982): Nathan Flurry says Rivet did get Claude Code and Codex running inside agentOS, but deliberately runs the agent loop outside the sandbox as tools for blast-radius and memory reasons, and explains why they built an SSD tier rather than one object per actor.
- [esafak](https://news.ycombinator.com/item?id=50382786): A skeptical first reaction that orchestration speed is not the bottleneck in agentic workloads — most time is spent waiting on the model — and that durability would have been the stronger lead.
- [minraws](https://news.ycombinator.com/item?id=50382233): First-hand UX complaint: the commenter's Codex/Claude agent was as confused as they were about what to do with Rivet and its edge cases.

## 18. Show HN: Stroq – a local audit of what your coding agent did and why {#story-18}
*#19 on HN · [github.com](https://github.com/AGGIB/Stroq) · 37 points · 8 comments · [HN discussion](https://news.ycombinator.com/item?id=50380704)*

Stroq 是一个采用 Apache-2.0 许可证的开源本地安全工具，它通过 `npx @stroq/cli` 调用，需要 Node.js 22 或更高版本；它会读取你最近 30 天的 Claude Code、Codex CLI 和 Cursor 会话，将它们与这台机器上的凭据进行比对，并报告每个密钥的去向（发给了另一家公司、也许已经发送、被 AI 看到、用于它自己的服务，或者在运行前被拦截）。它只打印密钥名称和来源，绝不打印密钥值；它把内容写入 `~/.stroq` 下的小型缓存，只在 127.0.0.1 上监听，没有账户，也没有遥测。它的钩子横跨 Claude Code、Cursor、Codex、Copilot CLI、Windsurf、Antigravity，另外还有一个 OpenClaw 插件和一个 stdio MCP 代理；它们会拒绝 `curl | sh`，以及携带已知密钥的外连请求；在 0.30.0 版本上，内置的 36 次攻击测试套件得到的结果是 15 次被拒绝、21 次被询问、0 次通过。作者自己把它描述为一个过滤器，而非沙箱：它的匹配是文本层面的，而且钩子只能看到宿主传过来的内容。

**Discussion**: 排名最高的评论反驳了它的核心前提：审计数小时后才知道发生了什么，这已经太迟了；如果仅仅一次误敲的 `rm` 就能清空你的机器，那就说明你的 harness 用错了——应该让智能体使用自己的用户，并限制它可以访问的路径和网络。作者坦率地同意，用来生成报告的那条命令完全没有阻止任何操作，`stroq init` 只是增加了确认钩子，而这“一个过滤器，不是沙箱”。又有一个人反驳说，事后检查是必要的，因为 upfront 就写出好的访问控制策略非常困难，而权限会随时间只增不减，所以你只会在出了大问题时才发现缺口。另一位评论者建议增加一个后台守护进程，它会持续扫描，并在菜单栏应用里提醒匹配项，同时提供一键删改、修复或标记为误报，作者对此表示感谢。还有一名评论者提出，用 Linux 上的 eBPF 后端（eunomia 的 AgentSight）会覆盖更多对抗性场景——他们的理由是，反正你应该在 VM 里做开发。

## 19. Nyquist Limit:The frequency of changes in tech is invalidating our understanding {#story-19}
*#20 on HN · [ryanprior.com](https://www.ryanprior.com/posts/nyquist-limit-frequency-of-changes-in-tech-invalidates-understanding/) · 19 points · 9 comments · [HN discussion](https://news.ycombinator.com/item?id=50370793)*

A blog post by Ryan Prior applying the Nyquist–Shannon sampling theorem to software organisations: if the rate at which a system changes outpaces twice the rate at which humans can sample and model it, you stop measuring signal and start measuring noise. He argues LLM-driven development and continuous delivery are pushing teams past that limit, producing outages with no pre-warning, and that better prompting or clever engineering cannot fix a mathematical constraint — the answer is to pick a target change frequency and sample it well above 2x. His evidence is largely anecdotal, including a paraphrased message from a colleague at a tech unicorn describing teams 「YOLOing in prod」 at hyperscalers.

**Discussion**: The thread splits cleanly between people who accept the diagnosis and people who reject the metaphor. Several commenters attack the physics: the sampling theorem only applies to bandlimited periodic signals, a straight line needs just two samples, and prior knowledge reduces the required rate — with compressive sensing cited as a real technique for going below Nyquist — so codebase understanding is not a signal at all. Others grant the analogy is loose but insist the underlying problem is real: LLM-accelerated generation already exceeds human capacity to review, test and model systems, and the fix requires either AGI or a different form of work and review. One practitioner reports concrete first-hand evidence, saying bugs are now creeping above their team's baseline, which they attribute to a once-coherent large codebase becoming less coherent as more generated code lands — and that they are only seeing what they detect. A darker thread argues the industry simply no longer values human understanding, with AI advocates calling for abolishing code review, leaving humans as ritual-keepers around technology they cannot read.

**Worth reading**
- [nemo44x](https://news.ycombinator.com/item?id=50383610): A practitioner says bugs have recently risen above their baseline in a large mature codebase, blames growing volumes of generated code diluting coherence, and notes they are keeping strict human review in critical areas.
- [somethingsome](https://news.ycombinator.com/item?id=50383125): Raises compressive sensing as a genuine method for sampling below the Nyquist limit, and argues the analogy wrongly assumes auto-generated code is always badly organised underneath.
- [science4sail](https://news.ycombinator.com/item?id=50383010): Strong counter-argument: the industry is abandoning the premise entirely, moving from read-often-write-rarely to read-never-write-often, with humans reduced to managing rituals around opaque technology.
