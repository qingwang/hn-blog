## 1. Codex CLI installs a persistent, self-updating background daemon by default {#story-1}
*#1 on HN · [github.com](https://github.com/openai/codex/issues/48195) · 55 points · 18 comments · [HN discussion](https://news.ycombinator.com/item?id=50060694)*

这是一份发在 openai/codex 仓库的 GitHub issue（#48195），要求把 CLI 的 daemon_auto_start 改为可选、默认关闭。报告者称自 0.157.0（npm 全局安装、Linux/WSL2）起，仅打开一次交互式会话就会启动 codex app-server --managed-daemon，把约 374 MB 的平台包复制进 ~/.codex/packages/app-server-daemon/releases/<version>/，并拉起一个启动后 5 分钟、之后每小时的分离式更新器（会以 60 秒 drain 预算强杀进行中的回合）。问题还提到守护进程会锁定首个会话的环境变量（如 HTTPS_PROXY）、hooks 拿到错误的 cwd；关闭时 daemon stop 不会终止 pid-update-loop。临时解法是 codex features disable daemon_auto_start，issue 中已出现提交「codex: disable daemon auto-start by default」。

**Discussion**: 评论区基本站在报告者一边，并补充了更多实害：有人称旧版本累积占了约 12 GB 磁盘，还有人说自己每天用一个 LLM 扫描磁盘删除各 harness 留下的垃圾。争议集中在自动更新是否有必要：一方认为浏览器等软件都会自动更新，2026 年这是常态；另一方反驳自己的浏览器更新需要用户确认，并且讨厌自动更新软件，还有人讽刺这等于让厂商往自己机器上装 rootkit，而对方回应自己是在容器里跑。有评论澄清 Codex 其实是 Rust 写的，但并未否认体积膨胀的抱怨；也有人问 brew 安装是否同样受影响，thread 中未见回答。总体共识是默认开启常驻守护进程与自更新不合理，至少应改为 opt-in。

**Worth reading**
- [icantevenhold](https://news.ycombinator.com/item?id=50060934): 实测旧版本累积占用约 12 GB 磁盘，并认为 Codex 在这方面比 Claude Code 更糟。
- [InsideOutSanta](https://news.ycombinator.com/item?id=50061105): 指出所有 harness 都不清理自身残留，自己已每天让一个 LLM 扫描磁盘删垃圾——「像雇个纵火犯来救火」。
- [icantevenhold](https://news.ycombinator.com/item?id=50060975): 反驳「自动更新是行业常态」：自己的浏览器更新需人工确认，且出于多种原因厌恶自动更新软件。

## 2. GLM-Legal {#story-2}

## 3. A Modern Web App in C {#story-3}
*#3 on HN · [prophitt.me](https://prophitt.me/writing/a-modern-web-app-in-c) · 172 points · 70 comments · [HN discussion](https://news.ycombinator.com/item?id=50058528)*

Corey Prophitt describes marketyour.games, a commercial web product (user accounts, a creator-search dashboard, folders, Stripe payments, Postmark transactional email, progressive enhancement with no required JavaScript) built entirely in C and served via CGI. The stack is BCHS — OpenBSD, C, httpd and SQLite — with no framework, no templating language, no database server and no container: one statically linked binary plus a SQLite file, with assets compiled into the executable and served from memory, and OpenBSD's pledge/unveil plus httpd's default chroot for sandboxing. Dependencies are libcurl and libsodium (build) plus libcjson and the SQLite amalgamation (vendored); the author argues CGI's 2004-era criticisms no longer apply, since forking is cheap, deploys are a file swap with no restart, and the supply chain is tiny.

**Discussion**: The thread splits between appreciation and pushback on CGI's fork-per-request model. Several commenters argue a single Go binary (CGO_ENABLED=0, embedded templates, scratch container) delivers the same simplicity with memory safety, and one calls CGI a half-measure that still depends on a separate web server and pays massive per-request overhead; the author counters that it fits his head and that FastCGI is a simple upgrade path. A practical thread about SQLite concurrency is answered by the author (WAL mode makes reads non-blocking but writes remain synchronous, and you must set the busy timeout), while others cite SQLite's own docs that only one writer exists at a time. Commenters correct the opening claim that 1994 CGI meant C, noting Perl dominated cgi-bin, and share older CGI war stories (FORTRAN 77 on HP-UX, busybox's built-in CGI support, lighttpd, nginx-cgi, Caddy via community plugins, TurboLua). Two people ask for source code and conclude the project is not open source, and there's a side argument about whether the post and the product's low-contrast monochrome styling are AI-generated — one commenter reports Pangram flagged the first half as AI, and the author says the design was intended to meet AAA contrast and was 100% human-written.

**Worth reading**
- [prophittcorey](https://news.ycombinator.com/item?id=50059377): The author answers the concurrency question directly: SQLite in WAL mode allows non-blocking concurrent reads, but writes stay synchronous, so you must set a busy timeout or blocked writes fail immediately.
- [EGreg](https://news.ycombinator.com/item?id=50059179): EGreg gives first-hand detail on the CGI-vs-FastCGI tradeoff from building a PHP webserver, noting forking a process costs roughly 8ms and that he defaulted to long-lived FastCGI-style processes with an opt-in to fork-per-request.
- [xd1936](https://news.ycombinator.com/item?id=50059511): Adds a concrete data point to the AI-authorship argument: the detector Pangram reportedly classified exactly the first 50% of the post as AI and the second half as human.

## 5. AI coding agents generate more code, but not more software {#story-5}
*#5 on HN · [arstechnica.com](https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/) · 101 points · 79 comments · [HN discussion](https://news.ycombinator.com/item?id=50059523)*

An Ars Technica write-up (Kyle Orland) of a Harvard study by Fiona Chen and James Stratton using Jellyfish engineering analytics — 300 million work events from over 700,000 employees at 700-plus firms, 2021 through March 2026 — to test whether AI coding tools raise firm-level output. Introducing agents produced +30% lines of code, +20% commits and +23% pull requests, but Jira issue and epic resolution rates did not shift significantly; pull-request review time rose 49%, the share of PRs needing changes nearly doubled, comments per PR rose 35%, and 14% more workers ended up doing reviews. The authors find no statistically significant employment effect, and AI review is still marginal: by March 2026, 80% of firms used some AI code review, yet agents wrote only 23.3% of review comments and 10.8% of PRs.

**Discussion**: The dominant thread is that the study describes 2025, not 2026: jefftk points out the agent results rest mostly on Claude 3.5 through Sonnet 4.5, GPT-4.1 through GPT-5 and Gemini 2.5, capturing only the first months of deployment, and hajile notes the paper was revised in August 2026. hyperpape, who read the paper, supplies the baselines — 5,017 lines of code per worker-month (+1,494), 5.34 PRs per month (+1.22), 7.03 days mean review time — and argues a mean 7-day review shows the engineering culture was already broken. There is real disagreement over whether line-by-line review is a quality gate at all: datsci_est_2015 says its purpose is shared understanding of the codebase, while keybrd-intrrpt, 0x20cowboy and sroerick counter that tests, benchmarks and documentation should catch the bugs that matter and most diffs do not deserve human eyes. Several practitioners report better results from hybrid workflows — humans review requirements, specs and test scenarios while agents do first-pass correctness checks — and rbehrends prefers agent-assisted review inside an IDE over either extreme. Recurring complaints include agents spewing huge volumes of over-mocked or whiteboxed tests, and criticism that the study's GitHub/Jira footprint methodology misses software built by solo developers, which many commenters say has exploded. The rough consensus: writing code got much cheaper, but shipping software did not speed up proportionally, because the bottleneck moved to review, requirements and organizational process.

**Worth reading**
- [hyperpape](https://news.ycombinator.com/item?id=50060454): A commenter who read the paper gives the concrete baselines (5,017 LoC per worker-month, +1,494; 5.34 PRs/month, +1.22; 7.03-day mean review time) and argues those numbers prove the data is old.
- [svachalek](https://news.ycombinator.com/item?id=50060207): First-hand account of auditing ~100k lines of tests with an LLM, finding about 60k near-useless (largely from excessive mocking) and replacing them with scenario tests in roughly two hours — concluding humans should review requirements and test scenarios, not lines.
- [jefftk](https://news.ycombinator.com/item?id=50060168): Names the specific model generations behind the study's agent results (Claude 3.5–Sonnet 4.5, GPT-4.1–GPT-5, Gemini 2.5) and explains the academic write-up lag that makes 2025 data look like current events.

## 6. Citroen revives the 2CV for an electric age {#story-6}
*#6 on HN · [bbc.com](https://www.bbc.com/news/articles/c620r33plgppo) · 154 points · 177 comments · [HN discussion](https://news.ycombinator.com/item?id=50055220)*

A BBC piece by Theo Leggett about Citroën's 2CV-inspired electric concept, unveiled at the Paris Motor Show: a small, retro-styled city runabout that Citroën aims to put in showrooms by 2028 for around £13,000, with sub-tonne weight and deliberately simple styling cues (flared arches, tall roof, eye-like headlights). The framing is heritage-as-marketing against aggressive Chinese EV competition, with Citroën CEO Xavier Chardon calling it a modern, ingenious response, Autocar's Rachel Burgess calling retro a brilliant differentiator, and analyst David Leggett warning it must still be credible on price simplicity and modern EV functionality. It is explicitly a concept car, not a product.

**Discussion**: Commenters largely ignored the nostalgia framing and argued about specs: several praise the sub-tonne weight and the £13k target as real engineering, while others note the original weighed only ~600 kg and that in practice lighter EVs simply get smaller batteries and shorter range — and this one is a concept two years out while Dacia Spring, Renault 5 and Leapmotor T03 are already on sale. A long argument runs over whether retro design sells: one side says working-class buyers want bang-for-buck tools rather than fashion and that the new Beetle's fad wore off, the other points to the Renault 5, Fiat 500 and Mustang as proof that heritage styling works, and to Dutch and Belgian roads full of R5s. Several owners and industry veterans are sharply critical of Stellantis EVs as afterthought retrofits onto combustion platforms, and one commenter who worked for a German OEM says the Chinese win on execution rather than magic. There is concrete price data: nothing new under €17,800 in the Netherlands, BYD from about €20k, only the Dacia Spring and Leapmotor T03 below that — with a correction that Spain's €10k Seagull figure includes roughly €5k of government subsidy. Side threads dispute whether the 2CV was ever a style icon (German speakers split over whether it was just die Ente or hässliches Entlein), lament the disappearance of the A-segment, and note that much modern car cruft — backup cameras, driver assistance — is legally mandated or NCAP-driven, with Dacia cited as having sold well on one star.

**Worth reading**
- [muvlon](https://news.ycombinator.com/item?id=50056355): An owner of a modern Stellantis EV describes it as an EV afterthought retrofitted onto an ICE/hybrid platform: small battery, severely limited charging speed, no vehicle-to-load, no trip planning, no frunk, and a driver display mostly wasted on showing which energy source is active.
- [Swizec](https://news.ycombinator.com/item?id=50060787): Corrects the nostalgia about 2CV comfort: the floating ride came from non-independent linked suspension (pushing one wheel up pushed the other down), which was abandoned because it hurts handling and road feel in modern fast, heavy cars.
- [ekr](https://news.ycombinator.com/item?id=50055826): Concrete price reality check: no new electric car under €17,800 in the Netherlands, BYD starting around €20k, with only the Dacia Spring and Leapmotor T03 below, so a highway-capable €15k car would sell well.

**Worth reading**

## 8. Just say no to OpenAI and Anthropic {#story-8}

## 20. (Post-Quantum) Cryptographic Right Answers {#story-20}
*#26 on HN · [words.filippo.io](https://words.filippo.io/right-answers/) · 47 points · 5 comments · [HN discussion](https://news.ycombinator.com/item?id=50055409)*

Filippo Valsorda's post updates the long-running 「Cryptographic Right Answers」 tradition — Colin Percival (2009), Thomas Ptacek (2015), Latacora (2018 and 2024) — for a post-quantum world. His key claim: the PQ transition timeline shifted hard in early 2026, with consensus it must complete by 2029, so all asymmetric recommendations have changed, while symmetric crypto is fine because 「Grover does not matter」. The cheat sheet recommends KMS in the cloud, otherwise XAES-256-GCM or XChaCha20Poly1305 with random nonces and Cobblestone-128 for anything over a few MB; X25519+ML-KEM-768 key exchange; ML-DSA-44 signatures; HPKE with X-Wing (MLKEM768-X25519); Argon2id or passkeys; and restic with a long random password for online backups — plus two new entries, a memory-safe language and 「get a review from the best model you can afford」, since LLMs are now good at finding bugs.

**Discussion**: The thread is tiny and mostly low-stakes. One commenter simply celebrates that the post is mostly non-controversial. The main dissent comes from a commenter who says they don't care about the PQ specifics at all, arguing post-quantum work is a waste of time and resources, citing a Peter Gutmann talk as backup — no one in the thread rebuts this, and no practitioner weighs in with deployment experience. A separate sub-thread asks why rclone isn't the backup answer, and the reply notes that rclone is not a cryptographic right answer because its encryption is not always on, implicitly contrasting it with the recommended restic. There is no real consensus or disagreement beyond that; with only five comments, nobody engages the actual technical recommendations.

**Worth reading**
