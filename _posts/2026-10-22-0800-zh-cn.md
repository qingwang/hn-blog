## 1. 最近提出的 o(n log n) 整数乘法算法 [pdf] {#story-1}
*HN 第 1 名 · [web.maths.unsw.edu.au](https://web.maths.unsw.edu.au/~davidharvey/research/subnlogn.pdf) · 145 分 · 84 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50190455)*
*原标题: The recently proposed o(n log n) integer multiplication algorithm [pdf]*

这是 David Harvey（UNSW）撰写的一篇 PDF，评估一个新近宣称的 o(n log n) 时间整数乘法算法——显然出自 OpenAI 最近的数学发布，Harvey 称其「看似合理」，尽管他承认自己并未真正读过背后的论文，也觉得那些论文的阐述难以消化。这篇文章把该宣称放在既有成果的脉络里（基于 FFT 的 O(n log n)、Schönhage–Strassen 的 O(n log n log log n)，以及 Harvey–van der Hoeven 2019 年的结果），并反思一个从事研究的自动化系统对该领域意味着什么。文章本身无法作为网页抓取，因此本摘要依据的是标题与讨论串中的引用。

*未能读取原文：not a web page (application/pdf)*

**讨论**: 讨论串分成两路：技术细节上的挑刺，以及关于 AI 在数学中的更大争论。几位评论者纠正了标题的表述框架：big-O 早已通过 FFT 达到，真正的新闻是 little-o——增长率严格低于 n log n 的任意常数倍——这一区别被长篇解释，随后本身又被纠正（极限与常数）。在 AI 问题上，一方认为，如果专家读不懂论文而模型能解释它，用模型就是新的现实，而 Lean 验证加上形式化证明检查才是真正的保障；另一方由几位恼火的发帖者带头，坚持认为一个没人理解但已被验证的证明只是某个东西的证明，并援引望月新一/IUT 的僵局、Lean 可能存在健全性 bug 的可能性，以及 LLM 的错误率。一位有第一手知识的评论者反驳文章所称不存在形式化的说法，报告说已有一个用 Mathlib 的 TM2 机器完成的 Lean 开发。实践层面的粗略共识：该结果纯属理论，与任何能装进真实硬件的整数都无关。

**值得一读的评论**
- [jdb1729](https://news.ycombinator.com/item?id=50191011): 报告称 o(n log n) 结果已在 Lean 中完全形式化（由 platypii 完成，基于 Mathlib 的 TM2 机器），目前指数为 1-2^-14.38，这与文章所称不存在此类证明相矛盾。
- [krackers](https://news.ycombinator.com/item?id=50191565): 最清楚地梳理了该算法的谱系——FFT 卷积、Schönhage–Strassen 廉价的单位根环、2019 年 O(n log n) 结果中的高斯重采样，以及 OpenAI 同时计算多层蝶形运算的技巧。
- [DannyBee](https://news.ycombinator.com/item?id=50192000): 认为 Harvey 说自己跟不上的那一步——为什么 g < m 不可能——并不难：每次 slice 调用最多只能让非零项翻倍，而需要的是 2^m，并链接了一个由 Astra 生成的该论证的变体。

## 2. 这个 PHP 漏洞并没有轻易可用的利用方式 {#story-2}
*HN 第 2 名 · [eliastaylor.com](https://eliastaylor.com/noexploit/) · 445 分 · 220 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50188948)*
*原标题: There isn't an easy exploit for this PHP vulnerability*

这是 Elias Taylor（论坛用户名 zkldi）发布的一篇博客文章，其中论证：近期被广泛报道的 PHP 核心内存破坏漏洞「php2shell」（CVE-2026-109618 / CVE-2026-109619，CVSS 10）确实存在，但并不像 Log4Shell、Heartbleed、Shellshock 或 RoR YAML 反序列化那样容易利用。作者称，GitHub 上有数千个「PoC」，但没有一个能针对未修改的 PHP 实例运行；许多 PoC 依赖预先存在的本地文件包含（LFI），或者干脆修改服务器，使其变得脆弱，而这通常是 LLM 生成的。他认为，恐慌部分源于一位 PHP 核心开发者的「补丁发布 15 分钟后就会出现漏洞利用」的评论、人们对 PHP 安全性的既有印象，以及一段带有动漫女孩的漏洞利用视频。

**讨论**: 评论者严重分歧。怀疑者首先攻击文章本身：一位评论者指出 eliastaylor.com 三天前才注册，没有联系方式，并认为一位匿名博主无权做出这种绝对断言；另有评论者反驳说论点本身成立与否才是关键，并指出该域名/作者已通过另一篇博客文章和 zkldi 的 HN 账号得到验证。另一些人则反驳文章的核心主张：letmevoteplease 引用了 Wiz、Calif 和 PHP 基金会的说法，即该漏洞在默认配置下可被利用（包括 Apache mod_php 上的远程代码执行，以及 WordPress、Drupal、Joomla 上的预认证 RCE），而 Trail of Bits 的 CEO dguido 表示，他的两名员工分别在约 4 小时内针对未修改的 MediaWiki 写出了可用的漏洞利用程序。多位从业者报告了自己测试的结果：一人运行了两个 GitHub PoC，其中一个实际上只是借助 LFI 的间接利用，另一个需要修改才能触发过期的写入（stale write），但没有实现 RCE；另一人只有在把易受攻击的脚本放进 webroot 之后才复现出该行为。一场平行的、往往更激烈的争论则认为时间线才是真正的丑闻：管理员抱怨有 12 小时几乎没有人了解任何细节，而 Cloudflare 的 CTO 发帖称发生了漏洞利用尝试，这迫使一些人因风险而主动下线，而不是因为恐慌；还有一些人反驳说，在没有补丁的情况下为政府或医疗系统承担风险是不合理的，而且缺少公开 PoC 并不能证明不存在私有的、已被武器化的漏洞利用程序。相当一部分人同意打补丁是正确的，但认为 CVSS 10 的评分和营销式披露（php2shell.com、patchtheplanet.org）被夸大了。

**值得一读的评论**
- [dguido](https://news.ycombinator.com/item?id=50191174): Trail of Bits 的 CEO 表示，他的两名员工分别用约 4 小时各自写出了可用的漏洞利用程序，并针对未修改的 MediaWiki 验证通过——这直接反驳了「这是不可利用的」这一说法，不过他也同意编写漏洞利用程序仍然需要专业知识。
- [letmevoteplease](https://news.ycombinator.com/item?id=50190765): 直接引用 Wiz、Calif 和 PHP 基金会的话说，该漏洞在默认配置下可被利用，这表明该漏洞能在普通的 PHP 安装与 Hello World 脚本上生效，而不只是在预先被攻陷的服务器上。
- [Tadpole9181](https://news.ycombinator.com/item?id=50189461): 一名从业者指出，文章中「大家为什么害怕」这一节没有抓住重点：真正的失败在于 12 小时的几乎完全沉默、含糊的警告，以及一条关于漏洞利用流量的推文，这让管理员在毫无信息的情况下不得不决定是否让站点下线。

## 3. OpenAI CLI {#story-3}
*HN 第 3 名 · [github.com](https://github.com/openai/openai-cli) · 30 分 · 8 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50191507)*

OpenAI 在 GitHub 上发布了 openai-cli，一个用 Go 编写的官方 REST API 命令行工具（要求 Go 1.26+，也可 brew install openai/tools/openai）。它围绕资源组织命令（openai files upload、openai images generate、openai admin organization usage 等），支持 JSON/JSONL/YAML/raw 输出，可借助 GJSON 的 --transform 做数据提取，并自带更新检查（最多每七天显示一次提示，可用 OPENAI_CLI_NO_UPDATE_CHECK=1 关闭）、命令补全、@file 文件读取和 OPENAI_UNTRUSTED_STDIN 安全模式；mTLS 认证仍处于 beta，图片生成默认使用名为 gpt-image-2.5-sunburst 的模型，并把结果保存到 ~/Downloads/gpt-images/。

**讨论**: 讨论几乎没有落在工具本身的功能上，人们主要怀疑的是 OpenAI 长期维护自家工具的能力：一条高赞评论警告说，OpenAI 的几乎所有东西都在不到两年内被弃用，有时甚至没有正式通知，还称这些工具看起来像「vibecoded」，缺乏审查，并声称报告 bug 的用户曾被 GitHub 拉黑。有人反驳，认为有 bug 的软件并不能带来收入，公司成功也不代表不会犯错；另一位评论者则更悲观地认为，所有新软件现在都在走向由 agent 生成代码，而可读的代码库终将被这种潮流取代。几位评论者则试图搞清这款 CLI 的定位：Codex 是 agent harness，而这个 CLI 只是对 API 的一层包装，有人对此不以为然，说这基本上就是「curl？」。还有人猜测，真正的动机是让模型学会使用自家工具，以便进行强化学习训练。

**值得一读的评论**
- [throw20261022](https://news.ycombinator.com/item?id=50191829): 这位评论者警告说，OpenAI 过去会弃用大部分工具，MathJax 有时甚至没有通知；而且对于 GitHub 上的问题报告，它往往会拉黑报告者，而不是去修复问题。
- [imdsm](https://news.ycombinator.com/item?id=50191803): 用一句话说清了定位：Codex 是 agent harness，而 OpenAI CLI 只是对 API 的封装。
- [theanonymousone](https://news.ycombinator.com/item?id=50191924): 质疑这个 CLI 的实际作用：「包装 API」听起来不过是 curl，暗示它没有解决开发者真正遇到的问题。

## 4. WorldTUI：我训练了一个 360M 模型来假装自己是个终端 {#story-4}
*HN 第 4 名 · [simedw.com](https://simedw.com/2026/10/21/world-model-terminal/) · 71 分 · 33 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50190363)*
*原标题: WorldTUI: I trained a 360M model to pretend to be a terminal*

这是 simedw 的一个业余项目，它对 Qwen2.5-Coder-0.5B 进行微调，使其充当一个完整的终端：其中没有 shell，也没有文件系统，只有一个模型，负责预测每次按键后字符网格会如何变化，覆盖 vim、tmux、man 手册页以及一局贪吃蛇。训练数据是从 Docker 中的真实程序录制的 336k 个合成会话（约 2B 个 token），外加 DAgger 式的自我纠错轮次；记忆回读在提示基线中为 2/13 和 3/13，提升到了 9/13，而 PresetBench 在 int4 下从 24/47 提升到 38/47。并行解码各行并做推测性验证，把大帧的 p95 延迟从 6.7s 降到了 0.87s；把 151,936 个 token 的词表裁剪到 333 个，并量化到 int4，使模型缩小到 208 MB，可通过 WGSL 编写的 WebGPU 着色器在浏览器本地运行。总成本：在 RTX 4090 上约 75 GPU 小时。

**讨论**: 讨论分成两派：一派认为这预示着「学习得来的 UI」（一位评论者遗憾地称之为未来，只需快速的本地模型即可）；怀疑者则问，既然真实程序在 CPU 上几毫秒就能完成，为什么要为一个非确定性的过程烧掉一块 GPU —— 对此的反驳是，我们早已为了开发者便利、而非性能，接受了数 GB 的 Chromium 和 JavaScript。几位评论者把它对应到已有工作上：微软的 WHAM Quake II 世界模型、DeepMind 的 Genie、一个 GPT-3 时代幻想的操作系统演示，以及一个更早的 HN 讨论帖。实际问题得到了作者的解答：sleep/时间的行为来自在无按键时输入的一个 WAIT 或 sleep token（普通帧只由按键触发），他还说更大的模型在记忆方面也更好，尽管他还没做大量测试。一个反复出现的主题是，这是一项出于好奇心驱动的练习，而非产品 —— 好几个人用「因为它就在那里」来回应那句直白的「如果我有终端，这有什么意义？」，还有人指出，这可能是无需真实加速器就能研究系统轨迹的一种廉价方式。一个关于模型是否感知窗口宽度的问题没有得到回答。

**值得一读的评论**
- [simedw](https://news.ycombinator.com/item?id=50191986): 作者澄清了 `sleep` 背后的机制：通常只有按键才会推进一帧，而一个单独的 sleep token 会告诉运行器时间正在流逝。
- [skohan](https://news.ycombinator.com/item?id=50191968): 对「世界模型即 UI」论点最尖锐的反驳：为什么要为一个 CPU 程序几毫秒就能完成的事情，运行一个占用数 GB 显存的非确定性 GPU 进程。
- [psandor](https://news.ycombinator.com/item?id=50191555): 指向微软研究院的 WHAM —— 一个整个游戏都由模型生成的 Quake II 世界模型，也是本项目最接近的大规模先例。

## 5. 安全披露 {#story-5}
*HN 第 5 名 · [blog.railway.com](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) · 416 分 · 237 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50188228)*
*原标题: Security Disclosure*

Railway 的事件说明称，2026 年 10 月 21 日星期三上午，它在存储客户环境变量的系统中检测到异常活动，一个未经授权的第三方可能读取了加密变量，并获取了其中部分变量的解密内容——API 密钥、数据库和 registry 凭据。Railway 表示，它认为这次攻击是针对平台公司的一系列攻击的一部分，目的是攻陷 AI 推理服务提供商；它已通知上游提供商主动吊销密钥，建议所有客户轮换每一个环境变量和 registry 凭据，并已暂停所有部署以便调查，这意味着轮换后的凭据目前还无法重新部署。

**讨论**: 整个讨论串的焦点是满腹怒火地质问这次的处理顺序：客户在凌晨 5 点轮换密钥，结果立刻搞坏了自己正在运行的服务，因为修改环境变量需要重新部署，而部署已被冻结。Railway 的 Angelo（ndneighbor）出面为延迟辩护，称这是「aviate, navigate, then communicate」（先飞行、再导航、后沟通）——不想在入侵尚未控制住之前就让大家轮换密钥——结果几乎遭到一致反驳：披露应当立即进行，范围不确定就意味着要警告所有人；有几个人说，在密钥泄露和产品宕机之间做选择根本算不上选择。再往下，讨论串变成对极糟糕一周的盘点：PHP RCE、eMudhra 证书泄露、GitLab 补丁、LiteLLM，尤其是 PingCAP/TiDB Cloud 泄露，人们说这是其中最糟的一起。关于环境变量是否不适合存放机密，还引出一场旁支争论，tptacek 纠正说：启动时注入的环境变量没有问题，问题在于 .env 文件而不是环境变量；而且这里很可能的目标是 Railway 的机密数据库，而不是任何人的 shell 环境。其余大部分是杂谈：有人宣布要迁移到 Render、Cloud Run 或裸 VPS，还有一段很长的跑题，讲一位评论者休了他今年的第一次假。

## 7. Rust Style Guide {#story-7}
*HN 第 8 名 · [google.github.io](https://google.github.io/styleguide/rustguide.html) · 275 分 · 158 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50186010)*

Google 公开发布的 Rust 风格指南，适用范围覆盖 Android、Chromium、ChromeOS 和 Fuchsia。它的“style”不只指格式化，还包括 API 与实现设计：禁止 glob 导入、公共 enum 与含公共字段的 struct 一律加 #[non_exhaustive]、优先借用而非深拷贝、Chromium 内禁止 async/.await 与 std 线程（改用 fuchsia_sync::Mutex）、use 语句按 imports_granularity = Module 拆成单模块导入、顶层函数需带模块名调用、Chromium 的 rust_library 用扁平单目录布局并倾向拆成小 crate。文档明确区分库代码（规则有约束力）与应用代码（强建议），并把方便大规模自动化改动（LSC）列为核心目标之一。

**讨论**: 最大争议是公共 enum 强制 #[non_exhaustive]：多位评论者认为这废掉了 Rust 枚举最大的价值——新增变体时编译器强制逐处检查，把编译期错误变成运行期漏判；反方（包括为 Google 辩护者）指出不加则新增变体就是 semver 破坏性变更，在 google3 这种巨型 monorepo 里会造成下游大面积编译失败和无谓 churn，且与 protobuf 枚举语义一致。Chromium 的“小 crate、不嵌套目录”规则也遭质疑像 2010 年“函数越小越好”的教条，有 Chromium 相关经验的人解释这在内部构建系统下是成本很低的：crate 是并行编译与缓存的单位，且能强制依赖声明、杜绝模块循环依赖。另有关于类型是否该不加限定导入的往返争论（io::Error 这类歧义名称反而应保留限定），以及一条支线在吵“有了 LLM 还要不要风格指南”。整体没有共识，但多数人认可这份文档把散落各处的惯例集中成文很有价值。

**值得一读的评论**
- [Thom2000](https://news.ycombinator.com/item?id=50191811): 指出 Rust 未来的 non_exhaustive_omitted_patterns lint 能在保留 #[non_exhaustive] 的同时恢复对新增变体的编译期提醒，缓解了整场争论的核心痛点。

- [afdbcreid](https://news.ycombinator.com/item?id=50189221): 实用技巧：在扩展 trait 上加 #[rust_analyzer::prefer_underscore_import]，rust-analyzer 就会默认以 as _ 形式导入该 trait，正好对应指南里“局部作用域 trait 导入”的诉求。

## 19. Claude Duet {#story-19}
*HN 第 40 名 · [claude.com](https://claude.com/resources/articles/claude-duet) · 72 分 · 8 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50186455)*

Anthropic 为 Claude Duet 发布的启动公告。这是一款主动式 agent 应用的研究预览版，以独立应用形式登陆 iOS 和 Android，另有 claude.ai 版本，基于 Claude Opus 5.5 构建，初期通过候补名单仅面向美国的 Pro 和 Max 用户开放。Duet 会跨已连接的各个应用发送晨间简报，只在有事需要你处理时才发消息，并在自带浏览器的独立虚拟机上运行长时间任务，这样你的设备可以关机；它使用 Claude Marketplace 中的 6,000 多个连接器（Gmail、Slack、QuickBooks、Stripe、Gusto、HubSpot、Docusign、Shopify、Canva），可通过 Stripe 的 Link 或 Shop Pay 付款，之后还会支持 1Password 登录。Anthropic 表示，发送、支付、签名和删除都需要明确批准；即使在批准的情况下，证券交易和账户间转账也已被禁止；新增的分类器加上安全提示会阻止分享信用卡号和政府身份证件；后台检查会计入常规套餐的使用额度。

## 20. 通往智能体规模 Git 基础设施的桥梁 {#story-20}
*HN 第 44 名 · [github.blog](https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/) · 60 分 · 17 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50183344)*
*原标题: The bridge to agent-scale Git infrastructure*

GitHub 工程博客详细介绍了 Git 存储迁移的下一阶段：目前 99.99999% 的仓库已同时存在于自有数据中心和 Azure 中；第一个 Azure（美国中部）副本于 2025 年 8 月上线，如今大多数仓库的五个副本中有两个位于 Azure，Azure 承载约一半的 Git 流量。文章解释了一项变更，即把 Spokes 的写入法定人数（quorum）范围从整个仓库缩小到单个引用，这就消除了每次写入都要等待约 25ms 跨区域往返、而且写入还要经过仓库级锁的串行化瓶颈；GitHub 报告称，在内部测试中，不同引用的写入吞吐量提升了 3–4 倍。文章随后介绍了由 Azure Blob Storage 支持的「虚拟写副本」和瞬态虚拟读副本，作为最终状态的桥梁，用来与读取量解耦，也就是与写竞争的读操作约为每次写入的 100–1,000 倍。

**讨论**: 最直接的反对意见是架构层面的：若干评论者认为，GitHub 从自有数据中心迁往 Azure 属于降级，有人甚至把近期稳定性问题与微软收购 GitHub 的时间线联系起来，尽管其他人指出，一些不稳定投诉早在微软收购之前就已经存在。相当一部分讨论集中在 GitHub Actions 的可靠性和计时上，人们开玩笑说故障是常态，这与存储文章几乎无关。几位评论者称赞该文章对内部架构的深度披露，认为它在技术上很有价值；另有一位评论者批评关于 PR 策略的评论质量低下。一个反复出现的主题是发布时间：评论者指出，这篇文章看起来是对 Anthropic 声称 GitHub 无法处理其合并量这一说法先发制人的回应，并且有评论者链接了该系列的前几篇以及其他系列文章。争点最尖锐的争论在于，Anthropic 所说的每日 30k 次合并是否是个真正的问题：有评论者认为，那是一个选择了单体仓库、而非拆分项目所造成的问题。

**值得一读的评论**
- [locknitpicker](https://news.ycombinator.com/item?id=50191732): 认为 Anthropic 所报告的合并限制是它自己造成的，因为它的单体仓库布局使得它成立；它没有把项目拆分成独立仓库，反而推行自建版本控制系统。
