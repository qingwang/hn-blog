## 1. REA Reverse – Engineer Anything {#story-1}
*HN 第 1 名 · [rea.tools](https://rea.tools/) · 307 分 · 97 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50028275)*

REA 是一个把逆向工程能力接入编程 Agent 的工具（rea.tools），通过 `npx rea-agents@latest setup` 安装，让 Claude Code 等 Agent 调用 Ghidra/反汇编能力去检查程序并解释其行为。落地页给了两个完整示例：逆向 Chrome 恐龙游戏的 speed update 函数（4,000 次更新后速度为 10.0，10,000 次后为 13.0，上限 13），以及 Windows Calculator 11.2508.4.0（x64，REA 4.1.0）的 % 按钮，恢复出「200 + 10% = 220」是因为加乘两分支规则不同（乘法等于 current×previous/100）。主张是让 Agent 生成可读的函数摘要、重命名与调用关系，实现从可执行文件重建逻辑。

**讨论**: 讨论很快从工具本身转向 AI 大规糢逆向对社区和法律的冲击。多位老手认可 AI 反编译质量已经不错（有人点名 Touhou 4 的 LLM decomp 变量命名合理、Ghidra 残留很少，一个月就做完），但担心这会毁掉反编译作为爱好：有人反驳说爱好到底是「让老游戏能跑」还是「亲手用 Ghidra」，并以钢琴/drum VST 类比——工具再强也不妨碍人享受过程。另一条主线是法律风险：做 Adobe 系替代品（Storytold/ArtCraft）的开发者明确表示 100% clean room、不碰 Ghidra 和反编译，并警告 REA 用在高知名度专有软件上可能招来诉讼；由此引出一长串关于「LLM 是否等于洗白 IP」「模型是否训练过专有源码」的争论。多位使用者报告实际体验：CVP 类安全限制经常误拦逆向甚至引用 DMCA 条文，Anthropic 的 Opus 5.5 会拒绝，OpenAI 与国产模型更宽松；也有人质疑既然能让 Agent 自己装 Ghidra，REA 究竟多了什么。此外有人批评 `npx … setup` 是新一代 curl | bash，也有人认为 sha256/签名安装包更可验证。

**值得一读的评论**
- [InvisibleUp](https://news.ycombinator.com/item?id=50029703): 实测了 AI 生成的 Touhou 4 反编译：质量比多数 AI decomp 好得多（matching、变量命名合理），但文件结构更像为 AI 优化而非还原原开发者意图，并担忧逆向社区会被「半成品 decomp + PC 移植」淹没。
- [echelon](https://news.ycombinator.com/item?id=50029110): 正在做 Adobe 替代品的开发者 echelon 明确表示他们完全不用逆向、不看任何专有源码、禁用 Ghidra，是干净的 clean room，并警告 REA 用在高知名度软件上可能在诉讼取证时被查出用了反编译源码。
- [mgaldys4](https://news.ycombinator.com/item?id=50029899): 逆向工程师 mgaldys4 指出 REA 的 Android 支持仍基于 jadx MCP，预处理大型 APK 要几十分钟、无法规模化，于是他自建 droidasc，300MB APK 全局交叉引用只需 1.5 秒，已借此发现 2 个 RCE 和 5 个 root 漏洞。

## 2. Telegram Desktop 漏洞可导致任意用户文件被窃取 {#story-2}
*HN 第 2 名 · [beaksec.github.io](https://beaksec.github.io/posts/telegram-desktop-one-click-account-takeover/) · 76 分 · 26 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50029123)*
*原标题: Telegram Desktop vulnerability allowed any user's file to be stolen*

一篇由 beaksec 撰写的安全分析（由 g-b-r 发布），描述了一条攻击链：在 Telegram Desktop 直至 7.2.8 版本（在 Windows 6.9.3 上确认）上，点击一个链接即可演变为完整的账号接管；该问题在 7.2.9（commit db3405699f）中修复，CVSS 评分为 8.1 高危。两个漏洞串联在一起：应用会将点击的链接 URL 序列化为以分号分隔的命令字符串，通过其本地 socket 发送时不转义分号，因此一个精心构造的 tg:// URL 会注入一条额外的 OPEN: 命令；而内部的 interpret: URI scheme —— 最初是为让 Telegram 发布自家版本而构建 —— 会读取指令文件中指定的任意文件，并将其发送到某个聊天，全程无需授权或确认。作者展示了攻击者可以将指令文件放入 Downloads（Telegram 会自动从群组下载最大 8 MiB 的文件），并通过相对路径访问它，进而窃取 tdata/key_datas、账号文件夹和 maps 索引 —— 足以克隆会话，因为 Telegram 默认不设置本地密码。

**讨论**: 讨论分成了两派：一派将其视为一个直截了当的 Telegram 漏洞，另一派则主张根本原因在于桌面操作系统允许任意用户进程读取任意用户文件：g-b-r（提交者）和其他几人力主这是 Telegram 的漏洞，并指出当应用本身就是在把文件外泄、并自行访问 ../../../Downloads 时，不能把责任推给操作系统；而 Panzerschrek 认为这实际上是操作系统层面的弱点，并反驳说只有经过审计、处于沙箱中的应用才应被信任。反驳者列举了已经存在的缓解措施 —— OpenBSD 的 unveil、沙箱化的 Mac App Store 版本、firejail/FreeBSD jail —— 不过 g-b-r 指出沙箱化本不会阻止账号接管这条路径，因为它依赖的是 Telegram 自己的数据文件。评论者还重温了对 Telegram 更广泛的质疑：链接到一篇十年前的「insecure by design」文章，以及 Filippo Valsorda 关于 ECDH 的「Most Backdoor-Looking Bug」分析，此外还有对基于电话号码的账号以及默认关闭的 2FA 的抱怨。在技术层面，usr1106 和 iririririr 一般性地讨论了单实例 socket 设计，其中 iririririr 指出 Firefox 一直在移除其 --noremote 选项。g-b-r 解释了这次重发（更早的提交 id 50019667 标题没那么吓人），并强调 Telegram 为了发布自家版本而添加一个能上传任意文件的内部工具是多么奇怪；arjie 称其为「JiaTan grade」。

**值得一读的评论**
- [g-b-r](https://news.ycombinator.com/item?id=50029124): 提交者说明这是一次标题更尖锐的重发，并认为文章淡化了通用的任意文件窃取这一角度，指出危险的 interpret: scheme 之所以存在，仅仅是为了让 Telegram 发布自家版本。
- [Panzerschrek](https://news.ycombinator.com/item?id=50029822): Panzerschrek 认为真正的缺陷在于允许任意用户进程读取任意用户文件的操作系统设计，引发了本贴关于应用与操作系统责任归属的主要分歧。
- [penskymaterial](https://news.ycombinator.com/item?id=50030094): 指出 OpenBSD 的 unveil 是一种已存在的操作系统层面缓解措施，削弱了所有现代桌面操作系统都同样暴露这一说法。

## 3. 索伦之眼：远距离隐藏间谍摄像头检测 {#story-3}
*HN 第 5 名 · [usenix.org](https://www.usenix.org/conference/usenixsecurity24/presentation/zhang-qibo) · 102 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49997481)*
*原标题: Eye of Sauron: Long-Range Hidden Spy Camera Detection*

链接是 USENIX Security 2024 的论文页面，论文作者为 Qibo Zhang、Daibo Liu 及其同事（湖南大学、UC San Diego、密歇根州立大学），提出了 ESauron，被称为首个能够检测并定位无线、有线及离线间谍摄像头的概念验证系统。其核心思路是：任何摄像头都必须先在其内置的读写内存中对拍摄到的原始图像进行处理（编码、压缩），而这些内存操作会在内存时钟频率上发出电磁辐射；改变视觉场景会触发一阵视频处理，从而产生可检测的电磁辐射（EMR）激增。作者对 50 款摄像头产品进行了测试，报告称仅需 4 次刺激即可实现 100% 检测，即使隔着遮挡物，检测距离也超过 20 米，并能准确定位每一台摄像头。

**讨论**: 评论者普遍对这一构想印象深刻，有人称其为应对即将到来的隐私猫鼠游戏的天才方法，并将其与对环境中收听设备进行音频投毒等思路相提并论。最有力的技术反驳来自一条讨论串，认为这一效应可能很容易被破解：一位评论者提出，使用一个「极其糟糕的编解码器」，直接输出未压缩的原始像素，就不会产生场景变化带来的波动；不过有回复指出，原始 1080p60 视频每小时约占用 1 TB，并建议借鉴密码学采用恒定时间的编解码器，作为更好的缓解方案。一些人指出可以通过屏蔽或更大的内存缓冲区来延迟并摊薄处理时的突发，其中一人认为检测到的 EMR 主要是屏蔽不良的表现，厂商很容易修复。一位评论者给出了苏联被动窃听设备 The Thing 以及一篇相关 IEEE 论文的链接，并指出作者承认他们的方法在面对这类被动硬件时很可能失效；其他人则把这些问题的利害上升到国家安全和企业间谍活动层面，还有一个打趣的子讨论串围绕 Eye of Sauron 与 Palantir 展开。一位读者说演讲者的发言非常难以听懂。

**值得一读的评论**
- [sholladay](https://news.ycombinator.com/item?id=50030140): 将其与苏联被动的 The Thing 窃听设备及一篇相关 IEEE 论文作类比，并指出作者承认对完全被动的硬件进行这类定位攻击很可能行不通。
- [akoboldfrying](https://news.ycombinator.com/item?id=50029390): 推测 EMR 的波动取决于编解码器对相似帧的压缩，因此一个直接输出原始像素的编解码器或许无法被检测到——由此引出一条回复（C12），指出原始视频不切实际，恒定时间的编解码器是更好的防御手段。
- [ranger_danger](https://news.ycombinator.com/item?id=50029261): 对如此微小的电磁波动竟能在数米之外被利用表示惊讶，并认为根本原因是屏蔽不当或缺失，而大多数产品本可以修复。

## 4. 你能用自回归扩散来生成市场数据吗？ {#story-4}
*HN 第 9 名 · [blog.janestreet.com](https://blog.janestreet.com/can-you-use-autoregressive-diffusion-to-generate-market-data/) · 60 分 · 22 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50021410)*
*原标题: Can you use autoregressive diffusion to generate market data?*

这是 Jane Street 博客关于 2026 年暑期实习生项目的一篇文章。实习生 Kavish 基于 Li 等人的「Autoregressive Image Generation without Vector Quantization」思路，用编码器加扩散头的架构对美国股票四年的订单簿事件流（时间戳、价格、事件类型等）建模，目标是自回归地合成下一个市场事件。核心发现是 DDPM 在 1000 步余弦噪声表下不稳定，超过 88-95% 的值偏离均值 8 个标准差以上，改用时序无关的 rectified flow / flow matching 后开箱即用；而市场数据既非纯连续也非纯离散（价格、时间有尖峰点质量），他用直接的类别头拆分或用「atom smoothing」把尖峰平滑后再回嵌。模型目前还不够准确，但澄清了该把多少离散性烘焙进模型、以及如何表示与平滑特征分布这两个关键旋钮。

**讨论**: 评论区分成了明显几派。一派真正读了文章并对技术内容赞赏，称这是把扩散模型应用到既非离散也非连续时间序列上的精彩范例，并半开玩笑地说只有少数人读了原文。另一大派转向有效市场假说：有人断言任何准确模型都会因被市场吸收而失效，有人反驳说这假设了模型一定会大到被其他参与者察觉，也有人指出边取决于数据而非模型（如用卫星图像数停车场车辆作为内幕信息的代理）。还有一条支线围绕指数基金展开，争论「过去的业绩不代表未来」与指数投资逻辑，有人引用 Sharpe 1991 的《The Arithmetic of Active Management》说明主动投资者整体扣费后必然落后市场，也有人认为自动定投和指数基金已成为西方养老金，实际上是在押注政治体系维持股市上涨。此外有评论认为真正的护城河是数据量而非模型，量化机构能给出真实赔率而散户只能靠直觉，另一人则讽刺这是试图择时。

**值得一读的评论**
- [pottertheotter](https://news.ycombinator.com/item?id=50029400): 用 Sharpe (1991)《The Arithmetic of Active Management》的算术论证说明为何指数基金是有逻辑依据的选择。
- [arjie](https://news.ycombinator.com/item?id=50030152): 一位读者称赞这篇实习报告信息密度极高，并质疑为何会预期订单到达时间服从正态分布，认为它更可能是 Hawkes 式的自激过程。
- [asdff](https://news.ycombinator.com/item?id=50029468): 提出量化机构真正的优势是可获取的数据量和实时赔率，而非模型本身，散户只能靠直觉判断形态。

## 5. 用 Eurydice 把 Rust 编译成可读的 C {#story-5}
*HN 第 10 名 · [lwn.net](https://lwn.net/Articles/1055211/) · 59 分 · 7 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50027853)*
*原标题: Compiling Rust to readable C with Eurydice*

这是一篇 LWN 文章，介绍 Eurydice —— 一个把 Rust 代码转换成可读、结构保持的 C 代码的工具，面向高保障软件，因为现有的形式化验证与合规工具只认 C。它由 Inria 与 Microsoft 维护，2023 年启动，采用 MIT 与 Apache-2.0 双许可，基于把 F* 编译成 C 的 KaRaMeL；它借助 Charon 从 rustc 提取 MIR 的 JSON，再转成 KaRaMeL 中间表示并生成 C，曾用于把后量子密码例程从 Rust 迁到 C。文章说明它保留求值顺序和代码结构（与 rustc 生成的位运算循环相反），但尚不能扩展到小型示例之外 —— 泛型需要单态化、动态大小类型只能生成两个版本，作者建议用 -fno-strict-aliasing 编译产出代码；同类的多样化编译器还有 mrustc、GCC Rust 和 Cranelift。

**讨论**: 讨论很简短，焦点之一是 Eurydice 是否保留了 Rust 的运行时安全特性。一位评论者希望看到边界检查这类运行时安全机制的转换，另一位则反驳说这些检查会随 Rust 语义进入 IR，也应当出现在输出的 C 里，因为该工具的目标正是保持与 Rust 完全相同的语义和安全保证。另有一串玩笑围绕项目名字 Eurydice 的读音展开：把它念成「You're da C」和「You read da C」（后者据 Hadestown 而来），并打趣更贴近「you're rid of C」—— 还顺势问为何不做反方向的编译器。最后有人提出，D 和 C++ 也会受益于同类工具。

**值得一读的评论**
- [Lvl999Noob](https://news.ycombinator.com/item?id=50028527): 反驳「Eurydice 没覆盖运行时安全」的说法：Rust 的检查会随语义进入 IR 并出现在 C 输出中，保持相同语义与安全性本就是该工具的核心目标。
- [fithisux](https://news.ycombinator.com/item?id=50029868): 指出这种「抽象语言编译成结构保持的 C」的思路对 D 和 C++ 同样有价值。

## 6. 朊病毒病候选药物的临床试验开始招募受试者 {#story-6}
