## 1. MiniMax M3.1 Flash {#story-1}
*HN 第 1 名 · [minimax.io](https://www.minimax.io/blog/minimax-m31f) · 153 分 · 42 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50154540)*

MiniMax 的博客文章发布了 M3.1 Flash，它是 M3 的继任者，面向 agentic 工作、编程、computer use 和安全，推理速度约为原来的三倍（输出 200+ TPS，中位数 170+ TPS），agentic 使用成本比上一代低 70%。宣称的分数包括 DeepSWE v1.1 上的 73.7%、BankerToolBench 上的 76.2、OSWorld V2 上的 61.7、Agents' Last Exam 上的 29.6 以及 CyberGym 上的 82%。定价为每百万输入 token 0.15 美元、输出 0.60 美元、缓存输入 0.015 美元；可通过 MiniMax API、M Plan 和 MiniMax Code 使用，权重承诺稍后发布。文章还透露，匿名模型「Space Bunny」是 M3.1 Flash 的早期 checkpoint，训练使用了超过 200 万亿 token。

**讨论**: 这个讨论串中最有价值的内容是计算：一位评论者根据 M3 的 0.30/1.20/0.06 美元定价重新推算了 70% 成本说法，并得出结论认为它站得住脚（输入价格减半，缓存读取从输入的 20% 降至 10%），同时指出 DeepSeek V4.1 的 token 价格与之相同，但在缓存读取上仍以 0.003 美元更低。一个子讨论串认为，由于 Claude 订阅有大量 API 补贴且模型更强，它仍然是更划算的选择；但有人反驳说，他们优化的是价格而不是能力。评论者深入探讨了「Flash」如今意味着什么：有人引用 MiniMax 自己的 FAQ，指出其总参数为 428B、激活参数为 23B，与 DeepSeek 4.1 Flash 接近；还有几人指出，当基础模型达到 1T+ 时，Flash 不再意味着小或轻。主要的怀疑集中在基准可信度上：有人报告说，「Space Bunny」在 opencode 测试中犯下严重错误，用户于是转回 Qwen 3.8 Flash Next 或 DeepSeek V4 Flash；其他人指出，许多模型在 DeepSWE 上的得分可疑地集中在 74% 左右；还有人问，为什么这些发布从不显示每任务的 wall-clock 时间。讨论串管理员还指出，minimax.io 域名被 shadowban，这就是为什么会出现重复提交。

**值得一读的评论**
- [minimaxir](https://news.ycombinator.com/item?id=50156178): 拆解了 70% 成本说法与 M3 的 0.30/1.20/0.06 美元定价之间的关系，表明该说法可信，同时指出 DeepSeek V4.1 仍以每百万 0.003 美元在缓存读取上胜出。
- [penagwin](https://news.ycombinator.com/item?id=50155897): 引用 MiniMax 自己的 FAQ 说明真实规格，即总参数 428B、激活参数 23B，并认为「Flash」不再意味着小、轻或特别快。
- [walrus01](https://news.ycombinator.com/item?id=50156022): 表示 DeepSWE 和 TerminalBench 4.0 的分数与 opencode 用户从「Space Bunny」身上看到的表现不符；据称，其中许多人在遇到严重错误后转回了 Qwen 3.8 Flash Next 或 DeepSeek V4 Flash。

## 2. Wine 移植到 OpenBSD {#story-2}
*HN 第 2 名 · [marc.info](https://marc.info/?l=openbsd-ports&m=179236125692175) · 364 分 · 102 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50152307)*
*原标题: Wine ported to OpenBSD*

这是一封发到 openbsd-ports 邮件列表的帖子，宣布 OpenBSD 有了一个 Wine 移植草案，作者把它称为今年最出人意料的移植提案。主要工作由 Andrii 和 Fabien 完成；关键的障碍是 %gs/gsbase 寄存器，Andrii 通过模拟 %gs 前缀绕过了它，而不是设置 gsbase。数十个 64 位 Windows 程序都能正常运行，包括上个月刚发布的《巫师3》重制版；由于 WoW64 无法工作，32 位程序仍然完全跑不了；内置测试暂时禁用，并且上游 Wine 一直不愿意接受 OpenBSD 补丁。

**讨论**: 讨论从惊叹转向了对 AI 使用的追问。OpenBSD 最近公开拒绝作者无法证明来源的 LLM 生成代码，这引出一种猜测，认为这个移植也是 AI 写的；但移植作者 NethIafin 解释说，他只是用 AI 做原型、学习 %gs 编码，然后自己重写了代码，帮助他测试的 asveikau 也为他说话。版权方面的怀疑者反驳说，OpenBSD 的规则针对的是版权来源，而不是 AI 辅助本身；而长期贡献者则担心，一个拒绝 LLM 工具的小众系统会进一步落后，另一些人则反驳说，Linux 已经在接受 AI 代码，BSD 保持干净是有价值的。技术层面上，brynet 和 bentley 纠正了认为 OpenBSD 没有 3D 驱动的误解：即将发布的 8.0 版本会带上从 Linux 6.18.y 移植来的 inteldrm/radeondrm/amdgpu 驱动；Wine 开发者 coldpie 读了补丁，认为这些改动写得不错，只有 gs 寄存器相关工作确实困难。另一个反复出现的主题是英伟达完全不支持，以及该移植可能不得不继续留在源码树外维护。

**值得一读的评论**
- [NethIafin](https://news.ycombinator.com/item?id=50156224): 移植作者 NethIafin 详细解释了工作流程：用 AI 试探 %gs 方案是否可行，并生成解码表，然后自己写代码；他说自己现在理解了 REX/SIB/ModRM、前缀和信号桩的来龙去脉。
- [t-3](https://news.ycombinator.com/item?id=50153536): 引用 Andrii 在列表上更早的发言：Wine 维护者不愿意接受哪怕是让 Wine 在 OpenBSD 上编译通过的补丁，而且 %gs 桩绝不能上游化，因为这会改变模拟的应用程序代码。
- [coldpie](https://news.ycombinator.com/item?id=50153584): Wine 开发者 coldpie 读了实际补丁，说它们写得不错；gs 寄存器处理是最难的部分，因为 Windows 用它做线程本地存储；他建议上游化，同时提醒有些地方看起来有点 hacky。

## 3. 在 macOS 上原生运行的 Android 应用 {#story-3}
*HN 第 3 名 · [github.com](https://github.com/kksimp/Mac.apk) · 87 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50154624)*
*原标题: Android apps running native on macOS*

Mac.apk 是 Voltare 的 Kaleb 发布的开源（AGPL v3，另有商业授权）项目，目标是在 Apple Silicon Mac 上直接运行 Android 应用：没有模拟器、没有虚拟机，也没有底层 Linux 内核；应用作为普通 macOS 进程启动，使用 Mac 的 GPU 绘制图形，具备 Dock 图标、原生窗口、深色模式；窗口标题栏左上角有一个返回按钮。技术栈包括重新实现的 Android framework、原生运行时、arm64 loader 与 Bionic shim、ARM32 重编译器，图形依赖 ANGLE 和 MoltenVK，并捆绑了基于 OpenJDK 构建的 JRE。项目自述为 alpha 阶段软件，需要 macOS 27 起（从 v1.0.1702 版本开始），安装包约 280 MB，每个应用占用 1.5 到 3 倍 APK 体积，支持 .apk/.apkm/.xapk 等格式；作者特别警告应用没有手机式沙箱，会以用户账户权限读写文件。

**讨论**: 评论整体认可技术上有趣，但多数人强调其实用性受限于 Google Play Services 和 SafetyNet 依赖：有人指出自定义 ROM 式方案（如 Aurora Store，项目文档已列出）能补上部分 Google 服务，但银行应用、甚至火车时刻表、超市目录、打车软件都因 SafetyNet DRM 而无法运行，有人呼吁欧盟立法禁止这种状况。也有人质疑代码质量，认为命名（Mac.apk 会变成 Mac.apk.app）和数据结构带有明显 LLM 生成痕迹，并指出它似乎依赖 JVM 而不支持原生 ARM 二进制、且把应用数据存在 .app 包内。一位游戏行业从业者反驳「开发者会转向 Steam 设备」的乐观论调，称大厂通常只测 Windows 版能否在 Steam Deck 上跑，像 BG3 那样的完整 Linux 移植极为罕见。另有分支讨论 Minecraft Bedrock 在 Mac 上的需求与既有兼容层项目，以及 Windows 上已被微软砍掉的 WSA 和 BlueStacks 替代方案。

**值得一读的评论**
- [gambiting](https://news.ycombinator.com/item?id=50156368): 一位在多家大型发行商工作过的游戏从业者表示，Steam Deck 测试通常只是确认 Windows 版能否运行，完整的 Linux 移植极其罕见且难以立项。
- [LoganDark](https://news.ycombinator.com/item?id=50156053): 指出两个具体问题：似乎靠 JVM 执行而非支持原生 ARM 二进制，以及应用数据存放在 .app 内部。
- [franga2000](https://news.ycombinator.com/item?id=50156348): 指出 SafetyNet DRM 已蔓延到火车时刻表、超市目录、打车等日常应用，而不只是银行 App，并批评 Google Play 开发者后台还在鼓励加装这类保护。

## 5. 享受编程依然没问题 {#story-5}
*HN 第 5 名 · [chriskiehl.com](https://chriskiehl.com/article/it-is-still-ok-to-enjoy-programming) · 215 分 · 202 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50134472)*
*原标题: It's still ok to enjoy programming*

Chris Kiehl 的博文认为，尽管 AI 已经改变了工作中手写代码的经济账，但作为爱好的编程并不需要任何经济上的理由。他描述了周末折腾一个碰撞检测很糟糕、满是 bug 的 Breakout 克隆，在 Java 里试验从 Agda 借鉴来的依赖类型想法，以及跟递归方案较劲却还没看出其价值。一条脚注也承认，他同样享受自己一行都没读过的 vibe-coding 应用。

**讨论**: 讨论串在文章究竟回答了什么这个问题上分成两派。最高赞评论者 ryandvm 说，没人说过享受是被禁止的——他真正的不满在于，AI 夺走了他热爱的部分（写代码），只留下管理工作，让他的工作满意度在 18 个月里从很高跌到惨不忍睹；有几个人回复说，敲代码本来是他们的放松时间，现在他们开始担心过劳。对立阵营（prmph、tjeerdnet、f055、searls）报告的则相反：AI 消除了框架和文档方面的苦差事，他们更享受工作，能更快地做出更大的东西。另一些人则对「工作不是生活」这一说法强烈反驳——thayne、esafak 和 0c3ca83 认为工作占据了我们清醒生活的大部分，告诉别人去把编程当爱好，是回避了真正的不满。实践者们在交换战术：有人收回了 agent 的 git 权限，这样他就会批判性地审查变更集，并且可以随意回滚；另一些人坚持认为，审查 LLM 代码比写代码更难、更枯燥，或者工具的使用体验很糟糕，尽管产出更高，却让他们更累。支线讨论把编程比作编织和缝纫，争论 HN 是否被 AI 鼓吹者用马甲操纵（也有人说是相反的偏见占主导），还问这是不是湾区泡沫。

**值得一读的评论**

## 19. 我已无心再做任何 Ruby gem，因此归档了所有仓库 {#story-19}
*HN 第 26 名 · [po-ru.com](https://po-ru.com/2026/10/18/why-im-no-longer-updating-this-repository) · 210 分 · 188 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50154518)*
*原标题: I no longer care to work on any Ruby gems so I've archived all my repositories*

这是一篇 Ruby gem 维护者（po-ru.com）的个人博客文章，宣布他已归档自己所有 gem 的源码，并解释了原因。他的论点是：Ruby 当初是为人类的快乐而生的（文中引用了 Matz 在 2000 年和 2019 年的表述），但那个时代已经结束——Rails 由 DHH 掌控，而他称 DHH 的观点令人反感；Ruby 本身如今在很大程度上是用 LLM agent 开发的；Matz 正在把它推介为一种由 AI 生成的语言，理由是模型需要更多人类编写的 Ruby 来训练。他反对大型企业把公共资源当作矿场一样开采，用来喂养那些机器，而这些机器的产出随后又污染了这片公共资源；他在结尾写道：手写代码已经不可持续，就像一张床一旦有人在上面拉了屎，就没法再睡了一样。

**讨论**: 这条讨论串的分歧与其说在于归档这件事本身，不如说在于这种失落感意味着什么。一大批资深工程师认为损失是真实的、而且普遍存在：协作式、手艺层面的编码乐趣已经消失，有些人说同事因失去成就感而请假，还有一位评论者明确把它描述为一个 grieving process（哀伤过程），认为团队应当正视并为之命名。对此，几位自称老兵的评论者说这个前提就是错的——他们比以往更热爱这份工作，从指挥 agent 中获得心流般的满足感，主要感觉是从依赖地狱和晦涩难懂的调试中解放了出来；少数人认为抱怨者眷恋的是地位和社交认可，而不是这门手艺。另一些人则对双方都提出反驳：他们指出，被大肆宣传的生产力爆发并没有催生出什么值得注意的新开源软件，并预测随着维护者退出，生态稳定性会下降，还担心会出现一整代人只会提示、不读代码。反复出现的分支话题包括：Ruby 社区对「编码即快乐」的特殊情结、对 Matz 和 DHH 拥抱 AI 的敌意，以及用 LLM 自行 fork 并维护是否已成为替代向上游贡献的可行方案——对此的反驳是，维护者本来就无偿且不被感激，如今还要面对 slop PR 和 bug report。讨论没有共识；最接近共识的一点是，大家都认为这位维护者有权离开，以及对结尾那句话的语气几乎一致地反感。

**值得一读的评论**
- [bioneuralnet](https://news.ycombinator.com/item?id=50155287): 一位一个月前还处于否认状态的评论者，描述自己已接受 LLM 的产出只是「还行」，但对大多数有偿企业工作来说已经够用；他正在把身份认同与工作分开，同时学着做一个 LLM 编排者，以继续挣到钱。
- [micromacrofoot](https://news.ycombinator.com/item?id=50154734): 声称有一手了解：在 DHH 那场宣称 Rails 已死的演讲之后，至少有三个重要的 Rails 项目或出资方正在积极讨论由 AI 主导的重构，并预测该生态会在一两年内变得一团糟。
- [tempest_](https://news.ycombinator.com/item?id=50154721): 讲述自己提交了一个带签署 CLA 的 pull request，几个月无人回应，随后 fork 并用 LLM 私下维护这处改动——这正是小型 OSS 库可能逐渐枯萎的一个具体机制。

## 20. Show HN：我构建了一个任务系统来处理繁琐事务，好让我能专注于任务本身 {#story-20}
*HN 第 27 名 · [3anddoneapp.com](https://3anddoneapp.com/try) · 27 分 · 27 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50151980)*
*原标题: Show HN: I built a task system to handle the drudgery so I could focus on tasks*

该页面是 3 & Done 的落地页/演示，这是一款由拥有 44 年经验的软件工程老手（dmyle，曾任职于 YouTube/Google 和 Meta）打造的任务系统。他说自己在决定真正的症结在于维护工作而非任务清单之前，已经用废了大约 25 个任务系统。其卖点是：通过语音或文字把任务丢进去（音频只存储在浏览器/设备本地，绝不上传），每天早上会有一封邮件对所有事项排序，并点名三件最重要的事及理由——截止日期、紧迫性、搁置过久的条目——背后用的是 Anthropic 模型、跑在 Vercel 上的 Next.js，以及 Neon Postgres。定价为 14 天试用、需绑卡，之后每年 $99 或每月 $9.99，支持 JSON/纯文本导出，且不会用用户数据做训练。

**讨论**: 最主要的反应是价格震惊：多位评论者认为，一款待办应用每月收 $10 说不过去，因为每月 $20 的 ChatGPT 订阅就能被调教成每天发邮件；还有几个人说，他们宁愿花一个下午凭感觉（vibe-code）自己糊一个工具——其中一位表示自己正是这么做的，而且完全贴合需求。作者（dmayle）回应说，这不是一个一次性生成的 app（有调研、UI 流程、schema 重写、带保存预期排名的 prompt 评测），他拒绝广告是因为广告会打断思考时刻，而且任何人都可以注册、立刻在账单里取消，仍能用满两周。隐私是第二条讨论主线：批评者说他们不会付钱把任务数据交给第三方，作者则回复说任务会按禁止训练的商用条款发给 Anthropic，客服访问需要用户明确给予临时授权，音频永远不离开设备，而端到端加密与「由服务器为你的清单排序」在结构上不相容——所以没有自托管版本。少数人为作者辩护，称这篇帖子里最值钱的部分正是那段漫长的个人经历；也有人推荐更便宜或可自托管的替代品（一款叫 Grask 的一次性 $2 iOS 应用、aventasks.dev）。讨论没有形成共识：分歧在于，一方认为对这么薄的一层封装收这个价荒谬，另一方则认为一个有人维护、零维护负担的服务值得付费。

**值得一读的评论**
- [dmayle](https://news.ycombinator.com/item?id=50155621): 作者解释说，端到端加密会直接让服务端排序无法实现，这正是该设计转而依赖合同性的禁止训练条款的原因；他还表示，自托管版本不是他能维护得起的。

- [nater5000](https://news.ycombinator.com/item?id=50156205): 最尖锐的反驳：ChatGPT 已经可以接到 Gmail 上每天发邮件，所以目标用户不会为一款待办应用每月付 $10——「我是不是漏掉了什么？」
