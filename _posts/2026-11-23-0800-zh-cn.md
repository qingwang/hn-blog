## 2. XNU Linux：在 Linux 上运行完整的 OS X GUI 用户空间 {#story-2}
*HN 第 2 名 · [github.com](https://github.com/AFK-surf/xnulinux) · 202 分 · 90 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50607261)*
*原标题: XNU Linux: Full OS X GUI Userspace on Linux*

这是一个 GitHub 项目（由 Heyang Zhou 开发），它从公开源码构建 Apple 的开源 XNU 内核（xnu-12377.121.6），并把它作为内核模块 xnu.ko 加载进未经修改的 arm64 Linux 内核，同时配有一个姊妹模块 fki.ko，为它提供 CPU、内存、定时器、文件、网络和 GPU。XNU 直接掌管 CPU 和 MMU，不借助 hypervisor，因此 macOS 进程与 Linux 进程共享同一批核心；在 Ubuntu 官方内核上，insmod xnu.ko 就能把 Apple 自家安装器生成的 macOS 27.2.1 系统盘一路启动到 loginwindow、WindowServer、Dock、Finder、Safari 和 Chrome，耗时 31–48 秒。它目前要求一台运行 arm64 Linux 虚拟机（krunkit 或 tart）的 Apple Silicon Mac、4K 页、16 GB 内存，并且在若干处只是权宜之计：cryptex 被合并进系统卷，AMFI 被打补丁，SIP 被放宽，而且由于 4K 与 16K 页的差异，内存访问比原生虚拟机更慢。Metal 通过 metal2vulkan 插件经 Mesa Venus 转发到宿主 GPU 上运行，lavapipe 作为 CPU 回退方案。

**讨论**: 讨论串在赞叹与担心 Apple 反应之间分裂。几位评论者预测会被下架，援引 Stela 从 GitHub 被撤下以及 Nintendo 针对主机密钥的 DMCA 投诉，而另一些人则主张 Apple 一向只追究转售商、不追究爱好者，指出大部分代码是 XNU（开源）加上社区项目，而且该项目无论如何都需要真正的 Apple 硬件。一个反复出现的纠正是，「仅限 Apple Silicon」的说法比看上去要宽松：有人指出 PAC 是标准的 Armv8.3 扩展，其使用范围远超 Apple，而 XNU 的 vmapple 内核只需很少东西即可启动，所以移植到其他 arm64 甚至 x86 机器主要是驱动问题——不过也有人提到 Apple 专有扩展和页大小约束。关于动机，怀疑者问「为什么不干脆买台 Mac」，而辩护者举出为 macOS 和 iOS 搭建跨平台构建/测试农场的需求、现代 Mac 缺乏 eGPU、Vulkan 和 CUDA 支持，以及单纯的好奇心；少数人警告说在非 Apple 硬件上运行 Xcode 或 macOS 应用可能违反 EULA。一个支线话题转向对未来的猜测：操作系统以加密形式发布、密钥与硬件绑定，评论者还就「Mac 里的 Linux 里的 Mac」这种套娃以及 Brad Fitzpatrick 的两台虚拟机上限互相开玩笑。

**值得一读的评论**
- [m132](https://news.ycombinator.com/item?id=50608144): 纠正了「PAC 就等于仅限 Apple」的假设：它是标准的 Armv8.3 扩展，被广泛实现，大多编码在 HINT 空间（不支持处即为 NOP），而且许多 AArch64 发行版已经在发布用 PAC 编译的二进制，能在 Raspberry Pi 级别的 SoC 上运行。
- [bartvk](https://news.ycombinator.com/item?id=50608121): 指出被埋没的重点：该项目明确说明只能在通过 krunkit 运行 arm64 Linux 虚拟机的 Apple Silicon Mac 上工作，这削弱了「任何 PC 都能跑 macOS」的解读。
- [sneak](https://news.ycombinator.com/item?id=50607690): 主张 Apple 历来不理会人们对自己买来的硬件做了什么，而且初看之下这甚至可能并未违反 EULA——被打补丁的 AMFI 文件可以作为自行应用的 diff 来分发。

## 3. 用 Inkling、Qwen 和 Unsloth 玩转本地 AI 的入门指南 {#story-3}
*HN 第 3 名 · [gpupartner.com](https://www.gpupartner.com/blog/beginners-guide-local-ai-inkling-qwen-unsloth) · 450 分 · 181 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50603845)*
*原标题: A Beginner's Guide to Local AI with Inkling, Qwen, and Unsloth*

这是一篇 gpupartner.com 的教程，讲解如何在 Windows PC 上搭建一个本地 ChatGPT/Claude 替代品：安装 Unsloth Desktop，下载一个按你显存大小选择的 4-bit 量化 Qwen3.8-27B（UD-Q4_K_XL，约 18GB），设置 128K 上下文，并开启局域网共享，让全家人都能用。文章声称安装大约需要 10-15 分钟（不含下载），给出了一张从 8GB 显卡到 96GB 的 RTX PRO 6000 的显存-模型对照表，还加了一节讨论 Thinking Machines Lab 的 Inkling 2 Mini（26.4B 参数，Apache 2.0，1M 上下文，2026 年 11 月 17 日发布，量化后 17.6GB）和 Inkling 2 Small（594B 参数，最小文件 171.7GB，仅限统一内存）的对比。作者自己的机器是 32GB 显存的 RTX 5090。

**讨论**: 评论区就本地 AI 现在是否实用、还是只是昂贵的爱好分成了两派。一方称之为「等离子电视阶段」——笨重、昂贵，距日常可用还有五年——并算了一笔账：5000-10000 美元的 GPU 对 20 美元/月的订阅，或者 Newegg 上 6500 美元对 16 年的 Claude Pro。另一方则认为「苦涩的教训」和不断缩小的模型意味着本地模型对大多数任务已经足够好；好几个人报告说，通过把 MoE 专家卸载到系统内存，他们在 12-16GB 显卡上以 30-60 tok/s 跑 Qwen3.8-27B 或 Qwen3.8-Flash-Next，硬件便宜到二手 300 美元的 Tesla P40 或约 2200 美元的 AMD R9700 都行。最有力的反驳来自一线实践者：他们说低比特量化会悄悄退化——Opus 5.5 用十分之一的 token 和二十分之一的时间就能完成的任务，本地模型要折腾几个小时，所以如果是要干活，「免费」并不更便宜。还有人纠正文章的表述——Unsloth Desktop 也能在 Linux 和 macOS 上运行（提供 AppImage/.deb 下载和 Docker 镜像），评论者说指南中关于 35B MoE 需要 32GB 显存、以及从 16K 上下文起步的假设过于保守。Unsloth 的维护者也出现在帖子里，直接回答安装问题。

**值得一读的评论**
- [tacoman](https://news.ycombinator.com/item?id=50606063): 建议把二手 Nvidia P40（24GB，eBay 上约 300 美元）作为入门选择，报告称在 Ubuntu 上用 llama.cpp 跑 Qwen 3.8 27B UD-Q4_K_M 达到 14 tok/s——「非常有用，不只是玩具」。
- [Aurornis](https://news.ycombinator.com/item?id=50607197): 一线实测提醒：便宜的 2-3 bit 量化会引入细微错误，模型随后又浪费 token 去修正；即便是 5-6 bit 的 Qwen3.8-Flash-Next，也可能在一个 Opus 5.5 只需极少时间和 token 就能完成的任务上烧掉数百万 token。
- [hypfer](https://news.ycombinator.com/item?id=50608410): 直截了当地批评指南的建议，认为 24GB 显存足以舒服地容纳 q4 量化的 Qwen3.8-27B 外加 170K+ 的 q8 上下文，而从 16K 上下文起步并不是一个有意义的配置。

## 4. Masullo 谈黎曼猜想 {#story-4}
*HN 第 5 名 · [johncarlosbaez.wordpress.com](https://johncarlosbaez.wordpress.com/2026/11/22/masullo-on-the-riemann-hypothesis/) · 190 分 · 121 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50598441)*
*原标题: Masullo on the Riemann Hypothesis*

John Baez 的博客文章用通俗语言概述了 Alessandro Masullo 那份长达 940 页的广义黎曼猜想证明草稿；该草稿由 Ravi Vakil 于 2026 年 11 月 20 日发布，而就在同一天，Levent Alpöge 和 Claude 发布了一份 1700 万行的 Lean 形式化证明。Baez 将 Masullo 的策略解释为在 idèle 类群上采用 Connes 风格的迹公式：谱侧对 Hecke L-函数的零点求和；几何侧则逐素数计算，其中 Poisson 求和使除有限多个素数外的所有素数项都消失；并且用一个由光滑紧支撑截断函数逼近的测试函数，使 Montel 定理能够过渡到全纯极限——值得注意的是，这一过程中没有使用 Weil 的正性判别法。Baez 还列出了早期的反对意见：由 Eric Naslund 组织的一次 AI 辅助评审发现，当测试函数集中在素数 2 附近时，该定理给出的结果是 0 而不是 log 2；第 444 页似乎错误地将一个 Schauder 基的事实套用到 Markushevich 基上；而本应推出 GRH 的第 13 章仍然只是占位内容；Brian Conrad 表示手稿正在进行大幅修订，之所以提前发布，只是因为 Alpöge 的声明迫使如此。

**讨论**: 这个讨论帖几乎没有讨论数学内容，主导话题是一场关于 AI 功劳的争论。一方认为，Anthropic 抛出一份无法阅读的 1700 万行 Lean 证明，却不发布模型或论文，这是反人类的，并且抢走了一个人 12 年的工作成果；另一方则回应说，这份 Lean 证明在一两天内就通过了机器验证，其篇幅之所以很长，是因为它形式化了那些尚未进入 Lean 的标准数学内容。一个反复出现的争论是，这类 AI 成果是否只是「蛮力」，不会产生新理论——对此有人反驳，指出 Grothendieck 对构建理论的坚持；另一些人则表示，AI 证明是大型工程项目，其洞见之后会由智能体和数学家发掘出来。若干评论者完全反对这种同情叙事，指出 Masullo 的草稿是一份仓促、不完整的工作，报告了数百个问题，如果没有 Alpöge 的争议，它根本不会引起关注。技术性纠正讨论集中在验证上：Lean 构建通过并不能表明形式化陈述与 GRH 相符，因为规范本身可能是错的，而这种不匹配才是真正的延迟原因。

**值得一读的评论**
- [nl](https://news.ycombinator.com/item?id=50607641): 解释说，这 1700 万行主要是对已知数学内容的形式化，这些内容此前从未被放进 Lean，而不是 1700 万行的新论证。
- [hasyimibhar](https://news.ycombinator.com/item?id=50608719): 指出了实践者关心的形式验证区别：一个正确的 Lean 文件只能证明其形式化陈述，仍然需要有人证明该陈述就是 GRH——这与在 TLA+ 中看到的规范不匹配问题相同。
- [xamuel](https://news.ycombinator.com/item?id=50607004): 对同情叙事的有力反驳：这份草稿之所以受到关注，只是因为 AMS 主席传播了它，并且据称 Brian Conrad 为其背书；还有很多人在 RH 上花了 12 年以上，却没有得到同情。

## 5. 《GTA 6》的鸟类：罪恶都市与雷奥尼达野生动物野外指南 {#story-5}
*HN 第 6 名 · [audubon.org](https://www.audubon.org/magazine/birds-of-gta-6-field-guide-vice-city-wildlife) · 465 分 · 233 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50602843)*
*原标题: The Birds of GTA 6: A Field Guide to Vice City and Leonida's Wildlife*

## 19. 运营 1000 个 API 的鉴权，我们学到了什么 {#story-19}
*HN 第 25 名 · [nango.dev](https://nango.dev/blog/lessons-from-operating-api-auth-for-900-apis/) · 38 分 · 5 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50606072)*
*原标题: What we learned operating auth for 1k APIs*

这是 Nango 的一篇工程博客，讲述在为第三方 API 集成运行 OAuth 过程中积累的运维经验，其规模从约 400 个 API 增长到 1000 多个 API。起因是 2025 年 5 月的一个 bug：一个 if 条件从未触发，导致刷新后的 token 从未被持久化；在回滚前的两小时里，数百个连接丢失了 token，而由于 Airtable、Atlassian 等提供商在新 refresh token 签发的瞬间就作废旧 token（Salesforce 和 Slack 在启用轮换时也是如此），这些客户不得不重新授权。得到的教训包括：把刷新操作串行化在一个分布式锁之后；处理各提供商不同的过期缓冲（Exact Online 会拒绝在过期前 30 秒以上发起的刷新）；不要相信 expires_in（Zendesk 只在请求时才返回它，Salesforce 需要一个 introspection 端点，而该端点从 2024 年 6 月起间歇性返回 unsupported_token_type）；refresh token 的有效期差异极大（NetSuite 为 7 天，Google 则是无限期，除非处于 Testing 状态、闲置 6 个月或存在 100 个活跃 token）；鉴权失败常常返回 HTTP 200（Zoho、Workday、Dayforce、LastPass）。文章结尾向 API 提供商提出了十项请求，并指出其提供商配置的提交中有 16% 是修复，约 935 个提供商中只有 276 个暴露了可检查的已鉴权端点。

**讨论**: 这个讨论帖规模不大，且大多是元层面的讨论，而非围绕文章实质内容的辩论。一位评论者完善了文章的第一条建议，指出 expires_in 本身也很凶险，因为它是相对于签发时刻而非客户端收到响应的时刻，并且 token 可能被加密，导致你无法读取 exp——所以必须在发送请求之前先记录时间戳。另一位评论者认为标题用词不当：这篇文章讲的是凭据与 token 生命周期管理，而非授权（authorization），并呼吁人们区分身份/登录与权限，这样能更好地描述主题。第三位评论者指出 HN 上早先关于 Nango 在 900 个和 100 个 API 规模下的讨论，由此引出一个玩笑：这中间到底有没有学到新东西。一位 Elixir 开发者推荐 Nango，同时指出社区库 `tango` 是一个兼容的、可直接替换的 OAuth 管理方案。技术内容上并没有真正的分歧；大致共识是，文中描述的这些提供商特有的怪癖是真实存在且被低估的。
