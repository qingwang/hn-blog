## 2. Cuis：现代的 Smalltalk-80 {#story-2}
*HN 第 3 名 · [cuis.st](https://cuis.st/) · 86 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50255343)*
*原标题: Cuis: The Modern Smalltalk-80*

Cuis 是 Smalltalk-80 的一个免费、可移植的实现，其网站明确表示目标是简约、强大、快速且高效。Cuis 是从 Squeak 派生的环境，删掉了多余的“杂物”，最近发布了 7.8 稳定版。Cuis 社区还深度参与了 Smalltalks 2026 大会（10 月 14 日至 16 日，阿根廷罗萨里奥 UTN 的 Facultad Regional Rosario），大会有 8 个演讲来自 Cuis 社区或展示用 Cuis 完成的工作，内容包括 Milan Lajtos 用编码代理构建 Blueprint 桌面实验、新的 Stream Deck 控制插件以及 Dybo 的改进。页面上还展示了 2007 年的一句赞美“又好看、又干净、又简单、又漂亮”，评论区对此乐不可支。

**讨论**: 最受欢迎的回答解释了 Cuis 的定位：它和 Pharo 差不多在同一时期从 Squeak 分叉出来，但 Cuis 做了更严格的精简，给出的类比是 Squeak = Debian、Pharo = Arch、Cuis = Alpine，因此系统内容更少、更容易探索和理解。一位用户报告说，自己在 Cuis 中比在 Squeak、Pharo、VA 或 Dolphin 中更快完成了工作，并正在用 Cuis 搭配 Pocketbase 和 lighttpd 构建一个基本静态的网站；另一个人称赞共享的 Squeak VM 意味着性能相当。另一个人称赞 Cuis 对 Morphic 的重构：所有内容都是硬件加速的矢量图形，连字体都是这样绘制，并且在缩放和旋转时仍然清晰。讨论随后转向两个方向：一个人问编码代理是否让它适合现代 AI 辅助工作流（没有直接回答），另一个话题则从 Smalltalk 的教育起源延伸到早期版本缺乏继承，以及继承是否真的是面向对象编程的核心——几位评论者说自己刻意避免继承。几位新来者说，相比其他 Smalltalk，他们觉得 Cuis 令人望而生畏的感觉更少、更受欢迎。

**值得一读的评论**
- [isr](https://news.ycombinator.com/item?id=50299839): 用一个简洁的类比和具体技术细节说明各个 Smalltalk 的关系：Squeak=Debian、Pharo=Arch、Cuis=Alpine，并解释了 Cuis 的 Morphic 如何将一切都包括字体做成硬件加速的矢量图形。
- [edfsadfer](https://news.ycombinator.com/item?id=50299704): 第一手经验：相比 Squeak、Pharo、VA 和 Dolphin，在删减过的“Squeak”中能更快更轻松地完成工作。
- [0xpgm](https://news.ycombinator.com/item?id=50300484): 指出早期 Smalltalk 虽然自称“纯面向对象”，却缺乏继承，并质疑继承对于面向对象编程是否真如今天所认为的那样核心。

## 3. Astroterm：你的终端里的星象馆 {#story-3}
*HN 第 4 名 · [github.com](https://github.com/da-luce/astroterm) · 102 分 · 9 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50270651)*
*原标题: Astroterm: A Planetarium for Your Terminal*

Astroterm 是一个在终端中运行的星图，用 C 编写，由 da-luce 发布在 GitHub 上。它以 ASCII、Unicode 或盲文字符实时渲染恒星、行星、星座连线图形和月相的位置，而且你可以把视图设成任意日期、时间、纬度或经度，或设成内置 GeoNames 列表中的某个城市。它通过 pacman（extra 仓库）、Fedora 40+、Homebrew、Nix、Guix 以及预编译的发布二进制文件（Linux x86_64、macOS aarch64、Windows）分发，数据来自 Yale Bright Star Catalog、Stellarium 星座图形和 NASA JPL 轨道参数；README 中的一个示例复现了 Apollo 11 发射当天早晨肯尼迪航天中心上空的星空，并对照 Stellarium 做过校验。

**讨论**: 讨论串规模不大，以称赞为主：提交者称无论实用价值如何，这份创作努力都令人印象深刻；一位评论者提出，这类项目是压力测试终端渲染性能的好办法。最有实质内容的交流围绕 README 本身——有人把它树为格外易读的范例，说「vibe coders」应该照抄；另一位则回复说它看起来相当普通，并追问究竟哪里突出，除了「ASCII 输出看上去还行」之外没有得到详细回答。真正的反对意见来自一位试过示例图像的评论者：Capella、Rigel 和 Sirius 都有标注，但 Orion 看不清楚，因此他的结论是这还不是他想要的那个终端版 Stellarium。另有两条评论是跑题的玩笑或推广——一个占星术 CPU 调度器，以及一个不相干的社交网络项目——讨论串里没有人表示自己大量使用过 astroterm。

**值得一读的评论**
- [dotancohen](https://news.ycombinator.com/item?id=50300527): 一位持怀疑态度的读者说，示例渲染图标注了 Capella、Rigel 和 Sirius，但让 Orion 难以辨认，因此它算不上终端版 Stellarium。
- [hnlmorg](https://news.ycombinator.com/item?id=50300905): 对 README 赞誉的反驳：这位评论者觉得它相当普通，并追问真正有特色的地方是什么——他自己写 README 就很吃力。
- [esperent](https://news.ycombinator.com/item?id=50299931): 提出 ASCII 星图是测试终端性能的有用压力测试，这个角度超出了天文学本身。

## 5. Herdr 发布了原生应用 {#story-5}
*HN 第 6 名 · [github.com](https://github.com/herdrdev/herdr-app) · 159 分 · 94 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50298436)*
*原标题: Herdr has released native app*

链接页面是 herdr-app 的 GitHub README，这是 Herdr 的原生桌面前端；Herdr 是一款围绕编码智能体（coding agents）构建的终端复用器。它把窗口与一个「core」守护进程分离，窗口关闭后终端仍继续运行；它还增加了一个智能体侧边栏，带有 Working/Blocked/Done/Idle 状态、SSH 机器，以及用户可编辑的 JavaScript「mods」和布局，其中包含一套 Windows 98 主题。安装包覆盖 Apple Silicon macOS、需带 Vulkan 驱动的 x86-64 与 ARM64 Linux，以及 Windows 10 1803+；构建使用 Rust 1.95.0 和 Zig 0.16.0，使用情况遥测默认开启。

**讨论**: 讨论串主要由长期使用 tmux 的用户占据，他们说改用 Herdr 后就留了下来，称赞其更合理的默认设置、鼠标支持、实时智能体状态列表，以及 Herdr 内嵌 libghostty 而不是在一个终端模拟器里再跑一个终端模拟器；有几个人让 LLM 把自己旧的 tmux 快捷键绑定移植了过来。最尖锐的分歧在于这家公司：一些人拒绝在一个由 Y Combinator 支持的工具上投入时间，他们预计它会被「enshittify」（劣化）或通过云/推理服务变现；另一些人则回应说它是开源的、可以 fork，并反问批评者若没有 VC 资金是否愿意为它付费。第二个分歧是到底需不需要桌面 GUI——有人说 Ghostty 加 TUI 就够了，而且旧应用存在 macOS 选中与复制方面的 bug；另一些人则欢迎原生应用，并要求一个尚不存在的移动客户端，转而提到 Moshi、Collie、Cosyra 或 termux+mosh。实践者描述了在几台 SSH 机器、EC2 实例和通过 Tailscale 互联的 Mac 上运行智能体；一位竞品的开发者则认为，与把智能体包装在通过 ACP 或 iroh 通信的原生 GUI 里相比，「通过 SSH 提供控制台」的模式在高延迟连接上体验会很差。也有一些具体抱怨（Agents 面板检测不到 Claude Code 实例、UI 里有「slop」、README 里没有截图），外加大量竞品名字的罗列——Rex、Tern、cmux、codealong、mjolnir、Paseo——以及一个关于 JS 可定制布局究竟是真有新颖之处还是只是换主题的子讨论串。

**值得一读的评论**
- [shepherdjerred](https://news.ycombinator.com/item?id=50299783): 称 Herdr 是这一类明显带有「vibe-coded」痕迹的智能体软件中最精致的一款，并指出整个 UI 由可定制的布局/recipe 驱动，而非固定的界面框架。
- [steve_adams_86](https://news.ycombinator.com/item?id=50299479): 报告了新应用中的一个具体 bug：无论启动多少个 Claude Code 实例，Agents 面板始终为空，尽管 TUI 仍能跟踪到它们。
- [rvz](https://news.ycombinator.com/item?id=50299620): 把 VC 融资的反对意见反转过来，反问那些现在回避 Herdr 的人，在融资之前是否愿意捐赠或为它付费。

## 10. Pico CSS 已不再维护 {#story-10}

## 14. 在 C 中倒序迭代 {#story-14}
*HN 第 29 名 · [davidpriver.com](https://www.davidpriver.com/Iterating-backwards-in-C.html) · 95 分 · 55 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50249598)*
*原标题: Iterating Backwards in C*

David Priver 的一篇短博文，抱怨人们（他说在 LLM 时代更甚）写倒序循环时的常见错误。不能用 `for(size_t i = count - 1; i >= 0; i--)`，因为无符号数的 `i >= 0` 恒为真，且 count 为 0 时 i 立刻变成 SIZE_MAX；改用 ssize_t 又会引入有符号/无符号转换问题，而且 ssize_t 是 POSIX 的东西。他推荐的写法是 `for(size_t i = count; i--; )`，靠后缀自减在条件里取值并让循环在 i 为 0 时终止，无符号回绕在 C 里是良定义的。

**讨论**: 争论集中在可读性上：一方（包括只偶尔写 C 的人）认为 `i--` 藏在条件里属于「过于巧妙」甚至像 IOCCC 参赛作品，另一方反驳说这恰恰是代码看起来就是它该做的事，而且不像 `i >= 0` 那样会写出死循环。签名派的老争论重新爆发：作者本人出面澄清原文表述不清，说他担心的是把索引拿去做非下标运算时的 usual arithmetic conversions，并主张计数/大小一律用无符号、这样只需考虑一边的边界；而资深评论者反驳说混用才是摩擦的来源，自己已经改用有符号类型几乎 everywhere，认为对转换规则的恐惧被夸大了。另外几个人贡献了变体：`while (i --> 0)`（其实只是 `i-- > 0` 的排版）、`for(size_t i = count; i > 0; --i)` 配合 `i - 1`、以及用指针 `pos-- != haystack`。关于「倒序更快」的老说法，多人反驳说这是过时的货物崇拜，有人引 Agner Fog 说明比较零在旧 CPU 上略优但反向访问数组对缓存不利，另有人补充比较零本身不省，省的是递减已经设好标志位。

**值得一读的评论**
- [david2ndaccount](https://news.ycombinator.com/item?id=50300590): 作者本人（david2ndaccount）现身说明文章写得匆忙、表述含糊，真正担心的是索引参与下标以外的运算时的类型转换，并解释为何偏爱无符号计数。
- [hujun236](https://news.ycombinator.com/item?id=50299331): 指出这个写法真正的价值在于从 count 而不是 count - 1 起步，从而彻底避开零长度缓冲区回绕到 SIZE_MAX 的那个实际会出错的情形。
- [nkurz](https://news.ycombinator.com/item?id=50300020): 对「倒序更快」给出细致的技术裁决：比较零本身不更快，真正的差别是递减已设置标志位可省掉一条 CMP，在现代多发射 CPU 上偶尔能带来约 20% 的收益，但通常被指令融合和充足端口吃掉。

## 20. Show HN：IRS 联邦税表的概念验证形式化 {#story-20}
*HN 第 49 名 · [github.com](https://github.com/emmilco/us-tax-model) · 71 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50278678)*
*原标题: Show HN: A proof-of-concept formalization of the IRS federal tax forms*

这是一个 GitHub 仓库（emmilco/us-tax-model），它把美国联邦个人所得税的表格和说明书编码成 YAML 数据：每一行都带有指向已归档 IRS 页面的引用，这些引用包含哈希和定位符，共 2,313 个锚点、1,252 条引文。它使用约 20 种固定原子运算来表述表达式，组合成 2,384 行计算；用 TypeScript 和 Lean 写了两套求值器，并在 1,648 个用例上得到 0 处不一致；还通过 PolicyEngine-US 2.49.4、Tax-Calculator 6.8.5 和 OpenTaxSolver 23.06 对 1,700 份生成申报表做外部引擎差异比对。作者明确说这是「100% vibe coded」的后台项目，绝对不能用于真实报税，也不会上传或提交任何申报表；项目自己的证据记分板只显示 1,515 行中有 198 行（13.1%）获得了 Claude 模型家族之外的断言支持。
