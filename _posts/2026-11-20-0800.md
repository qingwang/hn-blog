## 1. Jujutsu Primer {#story-1}
*#1 on HN · [ethanlowman.com](https://ethanlowman.com/posts/jj-primer/) · 54 points · 32 comments · [HN discussion](https://news.ycombinator.com/item?id=50570628)*

A tutorial-style post by Ethan Lowman introducing Jujutsu (jj) to people who already know Git: install via cargo or nixpkgs, run jj git init in an existing repository, and jj and Git stay synchronized. It walks through the core model — every edit to the working copy is automatically snapshotted as a commit (no staging area), commits carry both a Git commit ID and a stable change ID, empty commits can be described before work starts, and jj new / jj edit / jj commit move you around a branchless commit graph. It also demos revsets (borrowed from Mercurial) such as @-, k::, and author(...) & (k | q), and pitches automatic rebasing and native undo as removing Git's sharp edges.

**Discussion**: The strongest thread is about Jujutsu's Git compatibility: danpalmer, who has used jj for over two years on a large work monorepo, wants jj-native forges and backends that don't chase Git, while ezst argues that breaking from the Git repo format is exactly what drove Mercurial into obscurity despite better UX. Others push back that Git itself displaced CVS without format compatibility, and danpalmer adds that GitHub's pull has weakened and that Git's scaling problems (forges, big monorepos) are now widely felt. The missing staging area splits people: some are skeptical, while ozim argues hunk-level staging in GUI tools is what teaches people to curate commits and that 'just commit stuff' is the alternative. A large subthread covers AI agents: practitioners report jj's squash workflow is excellent with Claude and that stacked 20-plus-commit chains are now feasible, but several say agent tooling assumes Git, forcing them back until they wrote AGENTS.md/skill files or adopted colocated worktrees; one commenter notes Google's Antigravity stack has been adding jj support. A recurring complaint is that primers teach commands but not what a good commit history looks like.

**Worth reading**
- [danpalmer](https://news.ycombinator.com/item?id=50570993): A two-year daily jj user on a large monorepo says it works fantastically there, but runs it on a custom backend and wants forges built for jj rather than Git compatibility.
- [ezst](https://news.ycombinator.com/item?id=50571150): Argues Git-format compatibility is what saved jj from Mercurial's fate, since losing GitHub access is what made hg fade despite better UX and technical merit.
- [pdpi](https://news.ycombinator.com/item?id=50571352): Describes a concrete jj squash workflow with Claude: a named revision below, an unnamed revision on top where the agent's changes land, reviewing and squashing upward until it is empty.

## 3. OpenSSL: Buffer overflow in EVP_EncodeBlock() (CVE-2026-121481, CVSS 9.8) {#story-3}
*#3 on HN · [github.com](https://github.com/openssl/openssl/pull/33652) · 188 points · 135 comments · [HN discussion](https://news.ycombinator.com/item?id=50569226)*

A GitHub pull request against OpenSSL fixing CVE-2026-121481, a buffer overflow in EVP_EncodeBlock(), the API that base64-encodes a block with no output-length parameter. The overflow occurs when the input length is large enough (roughly over 1.5GB, i.e. when the encoded size no longer fits in a signed int) that the caller's own size calculation or the implementation writes past the buffer; the patch also guards EVP_DecodeBlock(), fixes a bad length check in base64encode() in http_client.c, and adds tests in test/base64_dec_avx2_test.c. The PR's first approach — returning -1 for NULL buffers, negative lengths and oversized lengths — was argued down by reviewers who noted that 0 is a legitimate success value and that third-party callers casting the result to size_t would mishandle a new error code; the final version uses OPENSSL_assert() for inputs that previously caused undefined behavior. The reporter notes it can be triggered from the command line with a huge -proxy_pass to openssl s_client (supplied via env:VAR), and the bug resembles CVE-2021-23840.

## 6. Postgres 19 Repack: Faster, Built-In Table Bloat Cleanup {#story-6}
*#6 on HN · [snowflake.com](https://www.snowflake.com/en/blog/engineering/postgres-19-repack-table-bloat/) · 69 points · 8 comments · [HN discussion](https://news.ycombinator.com/item?id=50569516)*

A Snowflake engineering blog post about the REPACK command landing in Postgres 19 core — a built-in replacement for the long-standing pg_repack extension for reclaiming space from dead tuples and table bloat. The article itself could not be fetched (HTTP 403), so details come from the title and the thread: commenters discuss a REPACK CONCURRENTLY variant, a caveat around MVCC consistency, and the fact that partitioned tables are not yet supported. Commenters treat it as a flagship Postgres 19 feature that survived to release rather than being reverted.

*Article not read: HTTP 403*

**Discussion**: The thread is broadly enthusiastic: several people who have run pg_repack in anger (multi-TB databases, clusters generating millions of dead tuples an hour) call a core implementation long overdue. The original poster, craigkerstiens, agrees that pg_repack, pg_squeeze and pg_reorg were powerful but sharp-edged tools, and says he is glad REPACK stayed in 19 rather than being pulled. jzelinskie likes the general direction of extending Postgres by tailing its own internals — as pg_squeeze does via logical decoding, versus pg_repack's triggers — and cites SpiceDB's own use of pg_xact to layer strict serializability on top of Postgres. The strongest caveats come from scale users: QuentinM notes partitions are unsupported, exactly where bloat management matters most, and argues the real pain is bloat in ctid and btree leaf linked lists rather than disk space; he says HOT updates largely solved it for his team. One commenter asks whether the design's apparent loss of MVCC consistency means queries can occasionally return nothing, and that question goes unanswered. Practical advice in the thread is mundane: use screen so a dropped connection doesn't kill a multi-hour rewrite.

**Worth reading**
- [QuentinM](https://news.ycombinator.com/item?id=50570978): First-hand report from a trading database generating millions of dead tuples an hour: REPACK lacks partition support, and the real cost of bloat is ctid/btree leaf linked-list degradation, not disk space — HOT updates fixed it for them.
- [jzelinskie](https://news.ycombinator.com/item?id=50570379): jzelinskie contrasts tailing Postgres internals (pg_squeeze) with trigger-based pg_repack, and describes SpiceDB hooking pg_xact to implement strict serializability without writing an extension — portable to locked-down managed Postgres.
- [inkysigma](https://news.ycombinator.com/item?id=50570913): An unanswered question worth flagging: does the design's apparent loss of MVCC consistency mean a query can occasionally return nothing for hard-to-diagnose reasons?

## 8. Vint Cerf on why TCP/IP was never patented {#story-8}
*#10 on HN · [seremot.com](https://seremot.com/p/vint-cerf-on-why-tcpip-was-never) · 90 points · 29 comments · [HN discussion](https://news.ycombinator.com/item?id=50568861)*

A launch post for 'Future Stories', a new tech podcast, whose first episode is a 56-minute interview with Vint Cerf recorded over Zoom on October 14 (transcript at ourfuturestories.eu/vint-cerf). Cerf, 83, left Google this year after more than twenty years and is helping start Tolero, a company building software for an interplanetary internet — his line: 'the speed of light is too slow'. The headline answer to the patent question is that in 1973-74 he and Bob Kahn reasoned they could not predict who America's allies would be 25 years out, so the only safe way to guarantee allied access was to publish the protocols openly and push interoperability. The rest is anecdote: Steve Crocker finding in 30 seconds a bug Cerf had chased for two weeks, the naming of CERFnet and a plastic bottle of glitter smashed over a Cisco router at its 1989 launch, Minitel refusing to connect to MCI Mail, and Cerf's worry that 'the 22nd century won't know what happened in the 21st because all of our records will have evaporated or will be uninterpretable'.

**Discussion**: The thread barely touches the article and instead argues about whether unpatented, long-horizon work still happens: one top commenter says VC-driven monetization has crowded it out, and is answered with a list of modern unencumbered work — Signal Protocol, RISC-V, WireGuard, UTF-8, JSON, HTTP, LLVM, AV1 — plus a sub-thread on libraries and Wikipedia as commons that capital would never build today. Others think the picture has improved: open standards win on network effects, though one commenter concedes interop can hamper innovation, citing enterprises moving off standards-based Cisco products to Slack and Zoom. Several people supply first-hand Cerf colour from UCLA in 1969 — he wore a three-piece suit and carried a briefcase while Jon Postel and others dressed like hippies — and one recalls a meeting with him 20+ years ago as 'an engineer's engineer'. A quoted transcript excerpt draws the deflating verdict that the actual answer is not very interesting, and a counterpoint notes that in the early 70s the government owned most DARPA-funded research, so a patent would have been pointless anyway; a side thread drifts to Jonas Salk's 'could you patent the sun?' and jabs at Cerf ending up at an adtech company.

**Worth reading**
- [commandersaki](https://news.ycombinator.com/item?id=50571059): Quotes the transcript passage where Cerf gives the actual reasoning — unknown future allies, so publish and encourage interoperability — and calls the answer uninteresting.
