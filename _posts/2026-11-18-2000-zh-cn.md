## 1. Nginx 中的未认证远程代码执行漏洞 {#story-1}
*HN 第 1 名 · [wiz.io](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities) · 667 分 · 265 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50547374)*
*原标题: Unauthenticated remote code execution in Nginx*

Wiz Research 与 Ikotas Labs、Metnir、Rapid7 和 Xint 合作，披露了 NGINX 中的两个严重 HTTP/2 内存安全漏洞——CVE-2026-123633（当一个被标记为可复用的连接在处理请求期间被排空时发生的释放后使用，影响 1.19.7 及更高版本）和 CVE-2026-123007（一个 send_window 整数下溢导致越界拷贝，自 2015 年的 1.9.5 起就已存在）——两者 CVSS 4.0 评分均为 9.2，且即使在仅提供纯静态文件的服务器上也能实现未认证的 RCE。Wiz 表示，他们用自家的 Atlas harness 发现了这些漏洞，并使用 Gemini 4 Carbon 和 ChatGPT 5.6 Sol 验证了影响，并主张 AI 正在消解那道一直让此类缺陷无法被利用的复杂度壁垒。修复已随 NGINX OSS 1.30.7 稳定版 / 1.31.9 主线版以及 NGINX Plus 37.0.7.1 / 37.3.0.1 发布；临时缓解措施是禁用 HTTP/2。

**讨论**: 讨论分成两个不断交错的论点。一方认为，用 C 写的对外网络守护进程已经不再站得住脚，并力推 Rust 服务器（xinproxy、Ferron）、Caddy 或 Envoy；另一方（其中包括几位在岗的系统管理员）反驳说，新服务器未经实战检验，Rust 仍有 unsafe 代码块和供应链风险，而且对现有代码做 Fil-C 或形式化验证胜过重写。一个大型子讨论在争论 AI 究竟是在「烧掉互联网」还是终于让互联网变得安全，其中最尖锐的观点是：同样的模型让攻击者开发漏洞利用变得廉价，而那些攻击者本来根本不需要有多聪明。在实务层面，评论者指出发行版软件包（Ubuntu、Debian）和 kubernetes ingress-nginx 控制器都落后于上游修复，Docker 镜像晚了数小时，而补丁提交在公开仓库里已经放了大约一周，提交信息里还写着「Reported by Xint.io」。有几个人则给恐慌降温，指出 HTTP/2 默认关闭，且只有约 12% 的 nginx 服务器启用了它；并援引 Rapid7 的发现：这个下溢需要在单条连接上推送约 128GB 数据，因此速率低于约 300 Mbit/s 的链路在漏洞利用完成之前就会先撞上 nginx 的一小时连接上限；另一些人回应说，实验室里才有的难度最终也没能救下 PHP2Shell。

**值得一读的评论**
- [smallerize](https://news.ycombinator.com/item?id=50550927): 引用了 Rapid7 的分析文章：利用该整数下溢需要在单条连接上传输约 128GB 数据，因此速率低于约 300 Mbit/s 的链路会先撞上一小时连接上限而失败——这是一个相当重要的实际限制。
- [black3r](https://news.ycombinator.com/item?id=50548510): 指出该修复在披露前一周就已存在于公开的 nginx 仓库中，提交信息里还写着「Reported by Xint.io」，并认为 F5 本应在这段时间内发布一份禁用 HTTP/2 的公告。
- [puszczyk](https://news.ycombinator.com/item?id=50549563): 警告说，广泛部署的 kubernetes ingress-nginx 控制器并不在这些补丁的覆盖范围内，仍在运行它的集群需要单独采取缓解措施。

## 3. 以可扩展的性价比推出七款新模型 {#story-3}
*HN 第 3 名 · [microsoft.ai](https://microsoft.ai/news/microsoft-ignite-2026/) · 296 分 · 187 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50548021)*
*原标题: Seven new models at scalable price-performance*

微软的 MAI 实验室借 Ignite 2026 发布了七款面向廉价、高吞吐量工作的模型：MAI Cyber 2 Flash、MAI Code 2 与 Code 2 Flash、MAI Image 2.7、MAI Realtime 1（每音频分钟 $0.01）、MAI Transcribe 2（每月支撑 1000 万次患者问诊的 Dragon Copilot）以及 Decision 1.1。其主打宣传是：MAI Code 2 的编码质量达到 GPT-6.1 Sol 的 98%，而价格约为其 40%；达到 Claude Opus 5.5 的 96%，而价格仅为其 5%；此外 Cyber 2 Flash 在 CyberGym-E2E 上以不到 2% 的每任务成本达到了「GPT-6 Astra」的质量。同时发布的还有 Maia 200——一款已投产、每瓦 token 数提升 1.7 倍的第二代加速器，以及「MAI Licensed Weights」——即在你自己的数据上定制、并在你自己的 Azure 环境中运行的前沿模型。

**讨论**: 讨论区最主要的反应是对基准测试的怀疑：评论者称与 Opus 5.5 和 Sol 的对比是精心挑选的，指出 5% 价格这一数字很可能是拿 Opus 在 Max 推理档位的价格作比较，而 MAI Code 2 还带有 50% 的促销折扣；他们还嘲讽「比 GPT-6.1 Sol 快 50 倍、便宜 79 倍」这句话，认为这是拿一个路由/决策模型去和通用模型做基准对比。一位来自微软 Decision 团队的工程师加入讨论，用第三方数据为其辩护——Decision 1.1 在 Artificial Analysis 的 Decision Index 上得分为 68（高于 Gemini Decision 1 和 Jev 1.14），在 JevBench 的 API 模型排名中位列第 9，每 100 万任务成本为 $140，而 Jev 为 $156、Gemini 为 $345——不过他承认其每 token 价格与 Jev 持平。两条旷日持久的争论把讨论区一分为二：开放权重支持者表示他们不会构建在自己无法拥有的模型之上，并预言会重演「Windows Phone」的结局；另一方则回应说，企业采购看的是性价比，微软已经拥有渠道分销和合规保障，而且手机类的类比并不成立，因为切换 AI 模型的成本几乎为零（有几位说他们公司之所以只提供 Copilot，是因为既有的微软合同）。第一手使用反馈好坏参半，但比基准测试之争要温和——一位测试 MAI Code 2 的评论者称其「相当不错」，大致与 Opus 或 Sol 相当；另一位称赞其转写模型是自己用过最好的之一；还有一位说 MAI Image 2.7 Flash 约每张 1 美分的价格便宜到足以作为默认选项。一个反复出现的实际抱怨是，人们不清楚到底如何才能用上这些模型：它们只存在于 GitHub Copilot 和一个受限的 Foundry 预览中，目前尚未出现在 OpenRouter 上，而且有几款模型在 Artificial Analysis 上完全找不到。讨论的总体共识是：这套东西面向的是企业买家，以及在其 IPO 前一天针对 Anthropic 的定价，而不是面向个人开发者。

**值得一读的评论**
- [jmoore15](https://news.ycombinator.com/item?id=50550940): 一位来自 Decision 1 和 1.1 团队的微软工程师给出了实际的第三方数据：在 Artificial Analysis Decision Index 上得分 68（高于 Gemini Decision 1 和 Jev 1.14），在 JevBench 的 API 模型排名中位列第 9，每 100 万任务成本 $140，而 Jev 为 $156、Gemini 为 $345——且每 token 价格与 Jev 相同。
- [user43928](https://news.ycombinator.com/item?id=50549559): 认为「价格为 Opus 5.5 的 5%」这一说法是拿 Opus 在 Max 推理档位（约为 Medium 的 4.5 倍）的价格作比较，并且还包含了 50% 的促销折扣，因此「质量在 Max 的 4% 以内」这一结果令人难以相信。
- [johnshahbazian](https://news.ycombinator.com/item?id=50549009): 一位一直在测试 MAI Code 2 的开发者说，对于自己日常的工作它「相当不错」，并且对于它与 Opus 或 Sol 水平相当的说法，他不会有多少异议。

## 4. Genie 4 现已可用 {#story-4}
*HN 第 4 名 · [blog.google](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/genie-4-now-available-project-genie/) · 68 分 · 43 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50550415)*
*原标题: Genie 4 is now available*

Google DeepMind 正在 Project Genie 中向符合条件的 Google AI Ultra 订阅用户推出 Genie 4。Project Genie 是 DeepMind 基于浏览器的交互式世界生成器。Genie 4 新增了在会话过程中用文本编辑已生成世界的功能，可修改天气、角色和动作；提供实时原生音频；加入了一个对话式的「Project Genie agent」，由它编排 Gemini 多模态模型来搭建世界；还提供了社区画廊，用于发布和混搭（remix）世界。Genie 3 也得到了增强：单次生成时长增加到 3 分钟（此前为 60 秒），并支持世界串联、360 度全景图作为生成基础，以及可通过提示触发的世界内事件。使用该功能需要 Google AI Ultra 20x 方案，覆盖 140 多个国家；Pro 会员可以加入等候名单；所有生成的视频和音频都带有 SynthID 水印。

**讨论**: 得票最高的讨论帖本身就是一场关于这场讨论的元争论：一位长期评论者说，他觉得自己与时代脱节，因为 HN 在争论价格和功能，却不讨论「可能造成毁灭性后果」的问题；回复分成两派，一派要求他说出具体的危害，另一派则回敬说「如果你还得问，那你就是问题的一部分」。最具体的抱怨集中在访问权限和价格上：一名英国用户无法确定自己的账户是否算「符合条件的」Ultra 订阅用户；其他人引用 20x Ultra 的要求（约每月 200 美元），称花钱使用测试版是一种侮辱；还有一位评论者预测 Google 会像对待其他项目一样放弃这款产品。几位人士认为它还不是真正的工具：它没有 Unity/Unreal/Godot 集成，游戏引擎能做的一切它都做不到，并且「前沿模型 + Blender + 游戏引擎已经足够好了」；另一些人则推测它可能自己变成游戏引擎，但立刻有人回应说，一个能写出游戏引擎的神经网络并不需要自己成为游戏引擎。还有一条贯穿讨论的分支话题，争论 DeepMind 这类由研究动机驱动的工作是值得钦佩还是浪费资源；支持方的论点是，这些世界模型最终能为机器人提供物理层面的预见能力，并生成合成训练数据。

**值得一读的评论**
- [kingrolo](https://news.ycombinator.com/item?id=50551015): 一位付费用户描述了实际的困惑：他的 Workspace 账户无法持有 Ultra 订阅，而在他常用 Gmail 上看到的营销页面称 Ultra 可用 Genie 3，他无法判断这是英国地区不可用，还是文案过时。
- [simonsarris](https://news.ycombinator.com/item?id=50550914): 他认为建筑师早已生活在类似 AI 的默认设定之下，并引用 Autodesk CEO 的话说，他看一眼建筑就能判断它是由哪个版本的 AutoCAD 设计的。
- [largbae](https://news.ycombinator.com/item?id=50551126): 他给出了整条研究路线被引用最多的理由：世界模型为机器人提供预见能力，让机器人在采取行动之前先在物理世界中模拟该行动（后来澄清，这主要是一种合成训练数据的玩法）。

## 16. x86 CPU：从 4004 到 486 {#story-16}
*HN 第 17 名 · [pikuma.com](https://pikuma.com/blog/history-of-x86-4004-to-486) · 99 分 · 25 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50546967)*
*原标题: The x86 CPU: From 4004 to 486*

这是一篇来自 pikuma.com 的历史文章，追溯了 x86 指令集是如何在偶然之中积累起各种怪癖的：从 Intel 4004（1971 年 11 月，2,300 个晶体管，约 740 kHz，4 KB ROM）开始，经过 8086（1978 年 6 月），一直到 486。文章的核心论点是：x86 的种种古怪之处都是兼容性遗留的产物——小端字节序和奇偶标志位来自 Datapoint 2200 终端，CTC 的工程师 Victor Poor 和 Harry Pyle 为该终端设计指令集，供 8008 使用；而 AX/BX/CX/DX 这些名称，则来自对 8080 寄存器的映射，目的是让逐行翻译器（CONV86，1978 年）能够移植 8080 汇编代码，并且其编码顺序 AX、CX、DX、BX 与 8080 的 BC、DE、HL 寄存器对相对应。

**讨论**: 这个讨论串大体上既充满欣赏，又带着最地道的 HN 式较真。有评论者反驳了文章中「Intel 并未设计 8008 指令集」的说法：Intel 的 Stan Mazor 表示递增/递减指令是后来加上的，还有人指出，该设计另外还删掉了一条按位分支指令，并因为封装引脚数量限制，把地址宽度从 16 位削减到 14 位——不过也有人回应说，Mazor 列出的改动未必详尽。另一条单独的纠正意见认为，4004 除了人员上有交集之外，与 8008 并无关系；对此有人反驳说，在 4004 上跑一个运行 Linux 的 MIPS 模拟器，这件事本身就说明「它不算微处理器」的论点只是语义之争。小端字节序则被辩护为串行执行多字节运算的芯片的合理选择；而关于 586/686 命名的讨论，纠正了一个常见的说法，即 Intel 无法为数字注册商标：这些名称从来都不是 Intel 的官方命名，并且在 AMD 诉讼之前，Intel 确实注册了直到 i986 的商标，而 Cyrix 和 AMD 则推出过 5x86/6x86。大致共识是：这段历史是扎实可信的，只是 8085「12 条未公开指令」这则轶事被指出缺乏引用来源。

**值得一读的评论**
- [petercooper](https://news.ycombinator.com/item?id=50547785): 链接了一份 Intel 口述历史，以说明像 Stan Mazor 这样的 Intel 工程师确实修改过 8008 的 ISA，增加了递增和递减指令，这与文章所大胆声称的 Intel 并未设计该指令集相矛盾。
- [epcoa](https://news.ycombinator.com/item?id=50548220): 纠正了讨论串中关于商标的解释：586 和 686 从来都不是 Intel 的官方名称，只是外界的用法（GCC、Linux、BSD），而且在 AMD 提起诉讼之前，Intel 已经主动为直到 i986 的名称注册了商标。
- [dmitrygr](https://news.ycombinator.com/item?id=50549720): 询问文章中的说法，即 Intel 为了让 8086 保持简单，只公开记载了 8085 新增 12 条指令中的 2 条，是否有任何真实的引用来源；并表示这一说法被广泛重复，却缺乏证据。
