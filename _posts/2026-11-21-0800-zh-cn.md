## 1. Inkling 2 Mini {#story-1}
*HN 第 3 名 · [thinkingmachines.ai](https://thinkingmachines.ai/news/inkling-2-mini/) · 915 分 · 172 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50581260)*

Thinking Machines 为 Inkling 2 Mini 发布的文章。这是一个混合专家（MoE）模型，总参数 26.4B、激活参数 3.4B（由于中间层对每个 token 要跑三次，每 token 的有效权重激活量为 5.4B）。它声称在智能体编程基准上取得 100B 以下开源权重模型中的最佳成绩——DeepSWE v1.1 48.2%、仅用 bash 的 SWE-bench Verified 79.2%、SWE-bench Pro v2 77.9%——但在知识与多轮任务上落后于 Qwen3.8-27B（MultiChallenge 50.0%、ComplexConstraints v1.1 33.4%）。大部分权重以 NVFP4 原生训练和部署，最后四层为 MXFP8，占用约 20GB；另有一个可变循环的研究变体（TML-d24-varloop-research）支撑了相关实验：不启用 CoT 时的时间跨度从单次运行的 16 秒升至三次运行的 37 秒，思维链更短但仍可读，且智能体破坏（agentic-sabotage）得分没有上升。

**讨论**: 讨论串整体气氛热烈：评论者认为小型 MoE、原生 4 位训练与循环三者的结合是本地推理的真正进步，有几人梳理了该架构的谱系（Universal Transformer、NVIDIA 的 Dory、TinyRecursiveModels，以及自制的「RYS」层重复实验），其中一位指出 3 倍也正是在 Qwen 系列中手工复制层奏效的深度。早期实测报告集中在：M1 Pro/Max Mac 上 10-20 tokens/s；7900XTX 上解码约 28 tok/s、预填充约 480 tok/s；RTX 5090 上约 52 tok/s。人们还在交换 llama.cpp 的 PR 编号，以及一个约带来 30-35% 提速的小补丁。怀疑者对基准成绩强烈质疑：多名测试者报告该模型耗掉 15-20k 思考 token，凭空发明了一个 WordPress hook 然后执拗地去搜索它，在 Artificial Analysis 的 token 用量图上「比 Qwen 还话多」；另一些人则主张它在编程上确实取代了 Qwen3.8-27B，因为循环提升的是推理能力而非记忆性知识。大家大致认同速度仍是悬而未决的问题——一位评论者算出 M1 Max 应能达到约 74 tok/s，实际却只有 18——此外还有关于循环是否损害可监控性、以及开源权重实验室如何赚钱的支线争论。

**值得一读的评论**
- [hedgehog](https://news.ycombinator.com/item?id=50584949): 报告在 Ryzen 395 上通过 llama.cpp Vulkan 达到 27 tok/s 解码，并贴出一个两行的 ggml_cont 补丁用于 SiTU 激活，自测约快 30%，得到一位 7900XTX 用户的确认。
- [dofm](https://news.ycombinator.com/item?id=50583503): 详尽的实测失败案例：Unsloth 的 Q4 版本在写一个单文件 WordPress 插件时耗尽了全部 19,200 个允许的思考 token 仍未完成，凭空发明了一个核心 hook，而且在启用工具使用之后仍然继续搜索这个并不存在的 hook。
- [meatmanek](https://news.ycombinator.com/item?id=50584615): 做了内存带宽估算：以 400GB/s 和约 5.4B 有效激活参数计算，M1 Max 的生成速度应接近 74 tok/s，但实际只有约 18，说明运行时远未优化（也有人质疑其激活参数的算法）。

## 2. ClawDOS——一个面向 DOS 的 AI 编程代理 {#story-2}
*HN 第 4 名 · [ricapar.net](http://ricapar.net/ClawDOS/) · 32 分 · 5 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50586292)*
*原标题: ClawDOS – An AI coding agent for DOS*

Ricapar 的一个业余项目，几乎完全由 Claude 编写，在一台原装 IBM PC XT 上运行完整的编程代理框架——8088 处理器、4.77 MHz、640K 内存、CGA 显卡——这台机器在 86Box 中模拟，也在一台真实的 5160 上做了演示。HARNESS.EXE 是一个 176 KB 的 DOS 二进制文件（13,000 行 C/C++ 代码，用 Open Watcom、FreeDOS 1.4 加 mTCP 构建），它自己直接与 Claude Messages API 通信，除了 TLS 之外什么都自己做，TLS 被外包到第二台机器上的 Python/socat/stunnel 隧道，API 密钥也可以存放在那台机器上。它提供 18 个工具（读取/写入/编辑文件、运行 DOS 程序并捕获输出、在 8088 上截取编码为 PNG 的 CGA 屏幕截图、读写内存和 I/O 端口、PC 扬声器音乐、在 C:\MEMORY 中记笔记），附带一套 Turbo C 2.0 / TINYASM / WASM / GW-BASIC 工具链，并报告一次示例的「编写并运行 PRIMES.C」回合在按下回车后 64 秒完成。

**讨论**: 这个讨论帖很短，主要是在赞赏而非技术讨论——32 分、五条评论，没有人质疑其说法或实用性。实质性的讨论围绕一个真实的空白：linzhangrun 认为，市场严重缺乏面向庞大的 WinXP/Win7 时代机器存量装机量的代理，并指出目前几乎所有代理都要求 Windows 10 1809 或更高版本，因此调试老旧设备通常意味着要费劲把 SSH 弄通。这一点得到了亲身经历的印证：unleaded 说他们这个月做了一个 win32 代理，看着 DeepSeek 的思维链在一次目录列表之后意识到自己运行在 NT 4.0 里，然后跑去找到 VS6 附带的 DirectX SDK，一次性完成了「写一个 3D 射击游戏」的提示词。其他人则把整个类型当作好玩而非实用——Tiberium 称在古怪环境（DOS、功能手机上的 Linux、Windows 95）里运行代理是「可爱又调皮」——而 sans_souse 只是说自己很喜欢。没有出现对 ClawDOS 的纠正或批评。

**值得一读的评论**
- [unleaded](https://news.ycombinator.com/item?id=50586895): 一位本月构建了 win32 代理的评论者描述道，DeepSeek 的思维链注意到自己运行在 NT 4.0 上，然后用 VS6 附带的 DirectX SDK 一次性做出了一个 3D 射击游戏。
- [linzhangrun](https://news.ycombinator.com/item?id=50586985): 「面向老机器的代理」这一想法背后的具体抱怨：几乎所有代理都要求 Windows 10 1809+，所以老设备的调试就退化成要把 SSH 弄通。

## 4. Clojure 会改变你对编程的思考方式（2017） {#story-4}
*HN 第 7 名 · [eli.thegreenplace.net](https://eli.thegreenplace.net/2017/clojure-the-perfect-language-to-expand-your-brain/) · 63 分 · 21 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50585376)*
*原标题: Clojure will affect the way you think about programming (2017)*

Eli Bendersky 在 2017 年的博文中主张，Clojure 是最值得学习的「下一门语言」，并引用 Alan Perlis 的话：一门不会影响你思考编程方式的语言，不值得去了解。他逐一说明 Clojure 为何符合这一标准：它是一门 Lisp，语法统一，拥有真正的宏（core.async 就是基于宏实现的）；它推崇持久化不可变数据结构，用 map/vector 和高阶函数取代对象；它支持 REPL 驱动的开发。他还介绍了作为 Go 式继承替代方案的协议（protocols）、通过 clojure.spec 和 core.typed 实现的可选检查、STM/atom/future、无缝的 Java 互操作以及 ClojureScript，并表示在断断续续尝试了 15 年之后，他会把 Clojure 视为自己第一门可用于生产环境的 Lisp。

**讨论**: 讨论分成两派，争论点在于 Clojure 的理念是否真的可以迁移。几位评论者认为 Clojure 永久改变了他们建模代码的方式——用 map 和函数来思考，把问题拆解为数据变换——但一位很早就学习 Clojure 的人说，它留下的持久影响是对动态类型以及盲目使用 map/list 的深深反感，而 ML 家族才给了他一套他保留至今的范式。另一些人反驳「高级语言」这一定位：一位认为 TypeScript 同时提供动态与静态类型、联合类型、热重载、最大的包生态，并且能在主流 IDE 中使用而不必碰 Emacs，因此他从未遇到必须学 Clojure 才能突破的天花板；一位 Clojure 使用者回应说，热重载并不是真正的 REPL，因为你无法在运行中的进程里重定义一个 var，也无法在不重新编译的情况下跑测试。最大的争论在于相关性：一位用了十年的 Clojure 老用户称这篇文章在 LLM 之后已经过时，并说软件「基本已被解决」，所以只有分发才重要——其他人称这种说法是胡扯，并指出 vibe coding 导致的宕机和大量低质量软件的泛滥，还argue 紧跟潮流并不等于正确。

**值得一读的评论**
- [zergrush](https://news.ycombinator.com/item?id=50586465): 一位自称用了十年 Clojure 的用户认为整个前提都已过时：LLM 意味着你不再需要了解一门语言的内部机制，Clojure 在开发者体验上的优势已经消失，而且「软件基本已被解决」，所以只有分发才重要。
- [bigstrat2003](https://news.ycombinator.com/item?id=50586819): 对「LLM 之后」论点的直接反驳：你仍然需要懂得如何编程，vibe coding 造成的宕机说明手写代码往往更胜一筹，而如果软件真的已被解决，我们得到的会是高质量软件的洪流，而不是垃圾的洪流。
- [vemv](https://news.ycombinator.com/item?id=50587055): 对 TypeScript 对比的一处具体纠正：TypeScript 没有真正的 REPL——你无法在运行中的程序里重定义单个 var，也无法在不触发重新编译的情况下跑测试。

## 5. Valkey 淘汰 skiplist，将有序集合开销最多削减 43% {#story-5}
*HN 第 9 名 · [valkey.io](https://valkey.io/blog/from-skiplist-to-b+tree/) · 114 分 · 40 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50534387)*
*原标题: Valkey kills the skiplist, cuts sorted set overhead by up to 43%*

Valkey 工程博客的一篇文章解释说，Valkey 9.2 将大型有序集合背后的 skiplist 换成了「fbtree」——一种 B+ 树变体，具有 61 路扇出、对 4 字节节点「features」做 SIMD 比较、叶子节点相连以及缓存边缘叶子。在一个 500 万元素的测试中，顺序插入时每个成员带来的索引开销从 50.3B 降到 28.5B（43%，约 109 MB），随机插入时降到 32.0B（36%，约 92 MB），而 ZADD 分数更新吞吐提升 105%，ZREM 提升 76%；ZSCORE、ZRANDMEMBER 和范围扫描几乎没变，因为它们要么走 hashtable，要么受限于结果生成。行为除了 OBJECT ENCODING 现在返回「btree」而不是「skiplist」之外没有变化；这些数字来自一个合并前的分支，在 Graviton3 c7g.metal 机器上测出，而 9.2 仍处于 release-candidate 测试阶段。

**讨论**: 讨论串分裂成两半：一边是实质性的数据结构辩论，另一边是围绕文章本身是否由 AI 撰写的激烈争吵——几位评论者称其为「slop」，没什么有用信号，而另一些人指出 PR #4206（及其给审阅者建议的阅读顺序）才是更好的产物，作者自己的总结评论也被指为生成内容。在实质层面，评论者指出 skiplist 对并发写入者仍然更友好，而 B+ 树在缓存行为上占优；一位认为 skiplist 其实不需要向后的指针（finger/stack 搜索就够了），另一位则观察到内存延迟已经让「重量级」的高扇出树反复获胜。最大的反驳来自 antirez，他说他用不同技术为 Redis 写过可比的、针对有序集合的内存优化，节省有时更大，并建议用户两边都做 benchmark。支线话题包括 Valkey 与 Redis 的采用情况对比（据称 AWS 上的 Valkey 便宜 20–35%），以及有人索要 benchmark 代码。

**值得一读的评论**

## 17. 真不敢相信它是 1 {#story-17}
*HN 第 28 名 · [aperiodical.com](https://aperiodical.com/2026/11/i-cant-believe-its-1/) · 61 分 · 61 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50521550)*
*原标题: I can’t believe it’s 1*

一篇整理稿，讲的是今年 MathsJam Gathering 上一个五分钟的演讲，主题是数字 1，由一段 0.999… = 1 的题外话展开。真正的主角是一种混合进制展开：小数点后第 n 位用 n+1 进制书写，于是这个数写作 0.12345… 且等于 1——作者把它想象成逐步填满一个圆，然后通过乘以 4 走完一个证明，并处理不同进制数位之间的进位（4×5 = 20，在 6 进制下写作 32，并向下一进位 3）。

**讨论**: 几乎整个讨论串都无视混合进制的构造，转而重打作者明确请求大家不要争的 0.999… = 1 之战；发帖人本人也抱怨没人读第一节之后的内容。给出的解释有：几何级数/极限定义（Sharlin、cbolton、anlsh 借助 Cauchy 序列），曾在五年级学生身上奏效的 ⅓ × 3 技巧（Wowfunhappy），以及「整件事只是 10 进制的产物，在 12 进制下就消失了」的说法（jorjordandan）。有位评论者 yubblegum 坚称无限位算术是未定义行为，从 9.999… 中减去 0.999… 就像用无穷大减无穷大一样没有意义，结果被全面驳倒——他的 d = 0.000…1 并不是 0.000001，而且他的论证预先假定了它要证明的结论。最尖锐的交锋是 dhosek 指出 0.012345… 同样满足「每一位递增」的描述，却显然不等于 1，这戳破了 noduerme 关于该结果是同义反复的说法。

**值得一读的评论**
- [dhosek](https://news.ycombinator.com/item?id=50574996): 对「它显然是 1」这一直觉的一行反例：在同一混合进制方案下，0.012345… 并不等于 1，所以这个论证需要真功夫。
- [bhattid](https://news.ycombinator.com/item?id=50585844): 联系到阶梯悖论（把正方形的角反复翻折到圆上，得到 pi = 4），说明一列曲线可以收敛而它们的长度不收敛——在出租车度量下 pi = 4。
- [ColinWright](https://news.ycombinator.com/item?id=50577116): 作者自己也指出了这份讽刺：所有人都在争论 0.999…，却忽略了真正新颖的内容——第 n 位为 n+1 进制的那套展开。

## 20. Show HN: OpenComputer——Devin 的开源替代方案 {#story-20}
*HN 第 32 名 · [github.com](https://github.com/diggerhq/opencomputer) · 103 分 · 28 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50581403)*
*原标题: Show HN: OpenComputer – an open source alternative to Devin*

OpenComputer 是来自 Digger 团队的 Apache 2.0 云编码代理：你在 Slack 话题中 @Computer，它就会在你自己 AWS/GCP/Azure 账号中托管的 VM 上的隔离 rootless Podman 容器里运行 Claude Code、Codex 或 OpenCode，然后开一个 PR。其卖点是速度和成本：一项基准测试声称首次推送耗时 24 秒，而四个热门云代理平均为 62 秒；全部 4 个 PR 在 56 秒内通过，而 Devin 为 185 秒（快 3.3 倍）。架构是每个团队一台 VM，会话隔离在 git worktree 中，每轮之后将状态备份到 git 仓库，以便会话可在别处恢复；创始人认为，每月超过约 640 会话小时后，一台常开的 4 vCPU VM 比按会话分配的 E2B 沙箱更划算。

**讨论**: 讨论分成三条线。第一，关于 Devin 的定价和质量说法：一位评论者称 Cognition 加价很重，并默认使用廉价低质量模型，还说他所在机构中优秀的工程师用 Claude Code，较弱的用 Devin。两位自称 Cognition 员工的人做了详细反驳——额外用量按 API 价格计费，Fusion/Normal 在 9 月便宜了 30–40%，Normal 路由到 Opus 5.5 或 GPT-6.2 Sol，Ultra 路由到 Fable 5.2 或 GPT-6.2 Astra，SWE-2 仅在 Lite 模式中使用（且目前免费）；他们列出 Nvidia、Ramp、Modal 等作为用户。第三位评论者称该回复谄媚，并要求披露隶属关系。第二，定位：被问及与 OpenHands（原 OpenDevin）有何不同时，创始人表示 OpenHands 自带代理执行框架，而 OpenComputer 刻意保持框架无关并销售基础设施——每个 Slack 话题都有自己的容器，且可以自带 Claude Code 或 Codex 订阅。第三，自托管：仓库是 Apache 2.0，但仍需一台 VM 加 Cloudflare Workers；目前没有 Ollama 或家用电脑的路径，不过在路线图上，Discord 集成也仅是计划中。还有几位评论者抱怨这个名字说明不了什么且已被占用（有人想到 OpenComputers Minecraft 模组），一位指出帖子假设所有人都知道 Devin 是什么。

**值得一读的评论**
- [jkelleyrtp](https://news.ycombinator.com/item?id=50585090): 一位自称 Cognition 员工的评论者反驳「默认使用廉价低质量模型」的说法，列出了实际的模型路由器：Normal 中为 Opus 5.5/GPT-6.2 Sol，Ultra 中为 Fable 5.2/GPT-6.2 Astra，Fusion 作为多模型框架最多可节省 30%。
- [iacguy](https://news.ycombinator.com/item?id=50584957): 一位创始人划清了与 OpenHands 的界线：他们对代理执行框架不持立场，而是在基础设施上竞争——每个话题使用 rootless Podman 容器，本地磁盘状态持久化到 git 支持的存储。
- [SilentM68](https://news.ycombinator.com/item?id=50584262): 提出了缺失的使用场景——完全在家用 Ollama 运行，不依赖 Claude Code/Codex；团队确认家用自托管只是未来工作，目前的「自托管」指的是你自己团队的云账号。
