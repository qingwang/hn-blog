## 1. 为什么没有更多开发者「使用平台」？ {#story-1}
*HN 第 1 名 · [nolanlawson.com](https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/) · 88 分 · 47 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49950554)*
*原标题: Why don't more developers "use the platform"?*

Nolan Lawson（PouchDB 的作者）的博客文章，从「使用平台」这一信条的反面展开论述。他列举了若干历史原因（浏览器落后于 jQuery 时代的库、IE6）、熟悉度（npm/React 的使用习惯）、npm 包把平台 API 包装成熟悉的工效学形态、npm 上的文档比平台自身文档更好，以及自己动手造东西很有趣、会催生宜家效应。他还用一段 ClickHouse 的轶事把讨论推广到 Web 之外——他和一位同事手写 JSON 压缩和一个键值存储，结果发现 ClickHouse 对列式数据的原生压缩效果更好——并针对 AI 编程将如何影响这一现象，给出了乐观与悲观两组配对的看法。

**讨论**: 该讨论串在很大程度上通过抨击 Web Components 来否定文章的框架：几位资深前端开发者表示，原生 Web Components 是一个设计糟糕、别扭的 API，现实中必须依赖 Lit，这削弱了「直接使用平台」的说服力。反方则辩护说，React 之所以流行并非只因炒作，而是因为文档完善、政治资源充足；Svelte/Solid 的支持者称其设计在技术上更差，而 React 拥护者回应说，这些取舍并非没有代价。平台的具体缺口占据了实用讨论的大头：评论者指出，原生 <dialog> 在 Firefox 中无法轻松淡出、用起来别扭；原生日期选择器只能通过 min/max 排除日期（因此要排除周末就必须完全自建选择器）；也不存在完全无障碍、可搜索的 combobox，而另一些人则说手写的日期选择器在各类设备上都会出问题。一个反复出现的主题是，平台在历史上交付不足，有位评论者还链接了 Ian Hickson 本人关于平台未兑现承诺的评论；此外还有关于 Tailwind/shadcn 是否胜过纯 CSS 的争论。

**值得一读的评论**
- [JimDabell](https://news.ycombinator.com/item?id=49951072): 一个具体的实例，说明为什么原生 <input type=date> 无法满足真实需求：排除非工作日会迫使你抛弃原生选择器、从零构建一个。
- [satvikpendem](https://news.ycombinator.com/item?id=49950984): 主张平台的把关者并不自己使用自家 API（dogfood），并链接了 Ian Hickson 在 HN 上的评论（item 34612696），谈到 HTML 规范未兑现的承诺如何把人们推向 JS、Flutter 和 WASM。
- [JimDabell](https://news.ycombinator.com/item?id=49950836): 一位拥有 25 年前端经验的老兵的亲身证词：只有 IE6 和 Web Components 让他痛苦到考虑转行，而 AI agent 也会踩到同样的坑。

## 2. Tell HN：Bob Cringely 去世了 {#story-2}
*HN 第 2 名 · 文字帖 · 364 分 · 71 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49949438)*
*原标题: Tell HN: Bob Cringely has died*

一篇纯文本的 HN 帖子，宣布 Bob Cringely——本名 Mark Stephens，苹果公司早期员工——于周六在睡梦中去世，享年 73 岁。他最广为人知的是 PBS 纪录片「Triumph of the Nerds」（1996）和「Nerds 2.0.1」、著作「Accidental Empires」，以及长期连载的「I, Cringely」专栏。帖子里没有链接文章；帖子本身只是这则讣告，其中说人们会怀念他。

**讨论**: 这个讨论串几乎完全是一场追思，数十位读者表示正是「Triumph of the Nerds」和「Accidental Empires」把他们引上了计算机行业的道路——有人说他之所以移民到美国、直奔硅谷，正是因为那部 PBS 系列片。评论者互相推荐作品：「Plane Crazy」、NerdTV 访谈系列（尤其是 Dan Drake/Autodesk 那一集）、他关于刷 WRT54G 路由器装 OpenWRT 做 mesh 组网的「The Little Engine That Could」一文，以及他采访 Steve Jobs 的「Lost Interview」；有人给出了「Triumph of the Nerds」在 Internet Archive 上的副本。有几个人出来澄清事实，指出两个不同的「Robert X. Cringely」身份（一个是由 InfoWorld 拥有的集体笔名，另一个是 Mark Stephens），另有人拿他反复出现的「Not dead yet」博客文章开玩笑。还有一段更宽泛的离题讨论，谈 2000 年代之前硅谷文化的消逝；也有几个人提到一个令人悲伤的背景：他的儿子 Cole 已于四月去世，年仅 21 岁。还有几个人感叹，对科技专栏作家这批老将来说这是糟糕的一年，并提到 John Dvorak。

**值得一读的评论**
- [flowerlad](https://news.ycombinator.com/item?id=49950124): 澄清了长期以来的混淆：两个「Robert X. Cringely」身份——一个是 InfoWorld 拥有的集体笔名，另一个是 Mark Stephens——并引用了 1998 年 Wired 的一篇文章。
- [bcrescimanno](https://news.ycombinator.com/item?id=49950507): 补充了个人背景：Cringely 曾在四月宣布他 21 岁的儿子 Cole 去世，并表示这些纪录片把童年的计算机热情变成了一生的事业。
- [api](https://news.ycombinator.com/item?id=49949932): ZeroTier 的 api 回忆说，Cringely 大约在 2015 年顺道来过他那个位于南加州的狭小联合办公空间，并反思了那个充满创造力与乐观精神的旧硅谷，以及它在 2001 年互联网泡沫破裂之后显而易见的消亡。

## 3. 所以你以为你能当电工？ {#story-3}
*HN 第 3 名 · [asteriskmag.com](https://asteriskmag.com/issues/15/so-you-think-you-could-be-an-electrician) · 163 分 · 96 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49910462)*
*原标题: So you think you could be an electrician?*

《Asterisk Magazine》上一篇第一人称文章，作者是一位从业多年的技工，他反对流行的「放弃大学，去当电工」说法。他认为数字并不支持这一说法：大学毕业生收入仍高于非毕业生，大学工资溢价从1970年代到2000年代稳步上升，技工工资并没有暴涨（COVID期间只有一小部分细分工种的工资上涨），而2024年美国公立州内学费及杂费的净价平均不到2,500美元/年，且自2016年以来持续下降。更重要的论点关乎风险与层级：钢铁工人和屋顶工死于坠落，电力线路工死于触电，树艺师有多种死法；在蓝领工作中，工会电工更接近 McKinsey 合伙人，而不是银行柜员——那是一个需要培训、人脉、认证和真本事的顶级工作，而不是默认的退路。他还认为 AI 可能通过绕过灵巧度的工具（如气动钉枪和 AI 引导的智能眼镜）间接重塑技工行业。

**讨论**: 从业者大多认同文章关于风险和内部地位层级的说法是准确的，有几个人补充了具体细节：一位澳大利亚评论者指出电工并非同质群体（住宅、工业、船舶、高压和汽车电气工作彼此几乎没有重叠），而现职和前职电工描述工会的招录情况是从100–200名候选人中筛选出四到八人。在收入和流动性上存在尖锐分歧：一位评论者说他的汽车技师朋友收入比他高（他本人有 ECE 硕士学位），靠的是计件（flat-rate）工资；而一位修理工回应说计件工资非常残酷——保修工作和锈死的螺栓报酬一样，这正是经销商招不到人的原因。关于 AI，一些人认为人形硬件加上真正的 AGI 会在几个月内自动化体力劳动，另一些人认为拧扳手的工作50年内都安全，还有一个讨论串认为如果所有人都逃向技工行业，劳动力供给会激增，同时需求会崩塌，因为被裁掉的白领客户再也雇不起他们。几位评论者对文章的框架提出反驳：大学不只是关乎收入，鼓吹技工行业的人往往是持学位的精英在把别人的孩子往那边引，而且案头工作本身也有健康代价；一位工会技工反驳说，他认识的一位熟练木匠收入高于同等水平的软件开发，而且没有玻璃天花板。

**值得一读的评论**
- [huijzer](https://news.ycombinator.com/item?id=49950725): 一位曾获得计算机科学硕士和数据科学博士学位的电工讲述自己转行做造船电气工作：体力上很吃力，但同事友好，没有办公室政治，而且技能可以直接迁移，因为排查故障用的是同一种思维方式。
- [rpcope1](https://news.ycombinator.com/item?id=49950151): 一位修理工对那个美好的汽车技师工资故事给出第一手反驳，说计件/计时工时（flat-rate/flag-hour）工资意味着保修工作只算一半的工时，而噩梦般的拆解工作也不多给钱——这也是 Ford 招不到足够技师的部分原因。
- [mmooss](https://news.ycombinator.com/item?id=49951107): 引用 CDC 及其他数据指出建筑和体力劳动职业的自杀率位居最高之列，并认为鼓吹技工行业是在告诉孩子们留在自己的社会经济阶层里。

## 4. Valve 的 Timur Kristóf 在 Linux 上改进老旧 AMD GPU 的工作 {#story-4}
*HN 第 4 名 · [phoronix.com](https://www.phoronix.com/news/XDC-2026-Valve-Timur-AMDGPU) · 238 分 · 33 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49946895)*
*原标题: The work by Valve's Timur Kristóf on improving old AMD GPUs on Linux*

Phoronix 的 Michael Larabel 撰文介绍了 Valve Linux 图形驱动程序团队的 Timur Kristóf 在多伦多 XDC 2026 上做的一场演讲。Kristóf 花了一年多时间，把 GCN 1.0/1.1 时代的 AMD 显卡——2012 年左右的 Radeon HD 7800/7900 级别——从老旧的 Radeon 驱动迁移到现代的 AMDGPU 内核驱动，修复显示代码缺陷和电源管理问题，并添加软复位支持，由此解锁了 RADV Vulkan，并带来了诸如 Linux 6.19 为老旧 AMD Radeon GPU 带来约 30% 提升等已报告的收益。演讲还谈到了他如何进入 AMDGPU 内核开发领域。

**讨论**: 帖子中很大一部分是亲身经历的 Linux 游戏体验：一位 Ayaneo 2 掌机用户说，较老的 RDNA 2 硬件在 Linux 下比在 Windows 下运行得更流畅、更快；几位拥有 9070/9070 XT 显卡的评论者说他们转投后很满意，其中一人主张，最优解是有意购买较老的、中端硬件，因为其修复已经进入正式发布的内核。一个子分支在 Nvidia 与 AMD 之间产生分歧：一位评论者希望 AMD 自己做这项工作，并认为 Nvidia 对老显卡的长期驱动支持是一大真正的优势，而其他人反驳说，正是 AMD 开放的 Mesa 技术栈才使 Kristóf 这样的爱好者工作成为可能，并指出 Nvidia 现在正通过其 590 驱动终止对 RTX 2000 以下所有产品的功能支持（放弃 Maxwell、Pascal 和 Volta）。在光线追踪方面，关于 9070 XT 相对 Windows 的 RT 性能差距是否显著存在分歧，有一条回复指出更新的内核/Mesa 会缩小这一差距。最后一个分支问这些收益是否有助于本地 LLM 推理，但评论者持怀疑态度：这些显卡缺少 FP4/FP8 硬件，而显存是瓶颈，所以就连 16 GB 的 RX 6900 XT 也难以匹敌免费的托管模型。

**值得一读的评论**
- [gary_0](https://news.ycombinator.com/item?id=49949075): Gary_0 贴出了该演讲的 YouTube 直链，并且已经打好时间戳跳到开始处。
- [jeroenhd](https://news.ycombinator.com/item?id=49951517): jeroenhd 描述了 Nvidia 终止对 Pascal 时代 GPU 支持所带来的切实痛苦，指出专有二进制固件意味着社区无法修复，而 DKMS 每次内核更新都要折腾一番。
- [jeroenhd](https://news.ycombinator.com/item?id=49951478): jeroenhd 主张，AMD 推动开放、被普遍支持的 API（OpenCL/OpenGL/Vulkan）是正确的选择，却因为人们涌向 CUDA 而受到惩罚，为 AMD 辩护以回应帖子中的抱怨。

## 5. 我们将需要对几乎所有东西设置默认的硬性预算上限 {#story-5}
*HN 第 5 名 · [simonwillison.net](https://simonwillison.net/2026/Oct/3/default-hard-budget-caps/) · 382 分 · 191 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49949235)*
*原标题: We're going to need default hard budget caps on pretty much everything*

Simon Willison 在 2026 年 10 月 3 日的一篇博文中主张，按用量付费的 API 和服务应当默认自带*硬性*预算上限——在达到每月 X 美元后直接切断并返回错误——而不是软性的警告邮件，因为编码智能体和个人智能体会让失控的开销变得轻而易举。他指出 AWS 终于在 2026 年 9 月 16 日推出了每月项目支出限额（达到限额的项目会被暂停，数据保留 90 天宽限期），并提到 Google Cloud 的 7 月 Spend Caps，希望这能成为一种趋势。他还希望智能体能倾向于推荐带有硬性上限的服务商，并告诫缺乏经验的开发者不要使用没有上限的服务。

**讨论**: 讨论串在硬性上限究竟是有益还是有害的问题上分成两派。一派（twoodfin、kasey_junk、Anon1096、motionlessveloc）认为，企业绝大多数情况下宁愿收到超额账单，也不愿关键业务基础设施在凌晨两点被关停；大型组织运行着成千上万个预算，一封邮件毫无价值；而一旦涉及存储和数据删除，暂停访问在设计上就是一场噩梦。另一派（simonw、cogman10、handoflixue）则反驳说，意料之外的 1000 倍开销可能意味着小企业和个人破产，上限完全可以设在正常开销的 2–3 倍以撑过流量高峰，而一个「无消费限制」复选框则让它对企业成为可选项。几位评论者解释了技术上的滞后：云计费是异步的、分散在许多明细项上，而且在操作执行之前很难估算（simonw 举的例子是一次 BigTable 查询事后才发现要花 100 美元），由此催生了诸如基于预留／TTL 的持有额度、以及 nvader 的红绿灯（绿／橙／红）模型等设计方案。还有一些更正：Google 新的 Spend Caps 只对四个随机挑选的服务生效，只支持按月计费，并且不计入赠金和折扣，因此对许多项目来说几乎毫无用处。

**值得一读的评论**
- [motionlessveloc](https://news.ycombinator.com/item?id=49950196): 来自某家设有硬性上限的服务的支持团队的一手说法：他们被工单和诉讼威胁淹没，这些客户都是在最糟糕的时刻因自然增长或爆红事件而被切断；他认为在大多数情况下告警优于硬性限额。
- [jcims](https://news.ycombinator.com/item?id=49950525): 有人所在公司每月 AWS 账单达到八位数，他说雇主不会使用上限；但他个人曾因开发账户里一个意外的 CloudTrail+SQS 反馈循环而累积了 2.5 万美元，如今将会使用这一功能。

## 8. Agent 不需要记忆，它们需要文档 {#story-8}
*HN 第 8 名 · [liao.gg](https://liao.gg/blog/agents-dont-need-memory) · 139 分 · 74 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49945933)*
*原标题: Agents don't need memory, they need documentation*

一篇发表在 liao.gg 的博客文章认为，市面上每一个记忆插件都共享同一套有缺陷的架构——生成片段、把它们嵌入向量数据库、在每次提示时注入最相似的前 5 条——而这之所以行不通，是因为相似不等于正确、片段会丢失上下文、过去被当作真相，而且存储库无法审计。作者给出的替代方案是基于文档的记忆：一个纯 Markdown 的「brain」（大脑），由指令、规格、研究和索引组成，agent 在开始工作前阅读它、在完成工作后更新它，把这个循环包装成 prompt → consult → build → update。这篇帖子本质上是在推销作者自己的开源插件 Operator Memory（github.com/aerovato/operator-memory），它源自一套他声称已经使用超过一年的 internal/ 文件夹工作流；文中没有任何基准测试或评估。

**讨论**: 讨论区普遍同意向量数据库召回是错误的原语，但许多人反对文中隐含的「Markdown 文档可以替代记忆」这一主张。最强烈的反驳是，没有人证明过 agent 生成的文档确实能改善结果：一位评论者指出，如今仓库里堆积着数兆字节由 agent 编写的 Markdown，并要求拿出 A/B 评估，他认为 agent 真正需要的只是一个极简的 AGENTS.md、一种验证自身工作的方式，以及关于项目品味的指引——「其余都是噪音」。其他人纠正了文章的核心类比，指出记忆片段早已是会议之后记下的笔记，而非重看的录像；真正的问题在于 agent 为每一句话都写一条笔记，而不是识别出什么才重要，并且这种只追加、无结构的笔记无法扩展。几位实践者描述了混合方案——以原则驱动的文档，在代码注释中引用带版本号的 token；评估风格的 lint 规则，其消息会解释如何修复；重新提示 agent 的 GUI/hook 工具；或从 GitHub/Slack/Granola 派生文档以保持其时效——而怀疑者警告说，agent 编写的规格和 ADR 会带来不断回归的推测性膨胀，且 agent 无法区分一条通用原则与一条一次性的 PR 评论。一个反复出现的挑剔：作者自己的工具其实不过就是 AGENTS.md 里的指令或一个 hook（xkcd 927 的梗出现了），还有一条支线从 agent 通过共享的交接文件夹协作，一路滑向对多智能体系统的存在性恐惧，另一些人则将其斥为「不过是 token 跟着 token」。粗略的共识：今天所售卖的那种 RAG 记忆是坏的，但文档并未被证明是解药，而缺失的正是评估证据。

**值得一读的评论**
- [stbenjam](https://news.ycombinator.com/item?id=49950536): 怀疑者的反驳：数兆字节由 agent 生成的 Markdown 并无任何已证实的收益，且会随时间腐烂；他声称 agent 只需要一个极简的 AGENTS.md、一种验证正确性的方式，以及关于项目品味的指引——并说如果谁能拿出 A/B 评估，他就把自己的帽子吃掉。
- [zahrevsky](https://news.ycombinator.com/item?id=49949536): 对文章核心类比的反驳：记忆片段早已是会议之后记下的笔记，而非重看的录像；真正的失败在于 agent 每句话都记一条笔记，而且这些笔记不可变、无结构、只可追加。
- [bushido](https://news.ycombinator.com/item?id=49950101): 一种已在实践中的具体替代方案：原则驱动开发会在代码注释中引用带版本号的 token，如 PDD-3@v1，因此修改一条规则就会提升版本号，并迫使人们重新评估所有在旧版本下做出的决定。

**讨论**: 最主要的反应是标题有误导性：这篇文章只涉及 Mac 和 Windows 上的 Docker Desktop，而非 Linux 上的 Docker Engine——后者从不曾为每个容器使用单独的 VM，而且不少评论者指出，如今大多数生产容器仍共享同一个内核。另一些人认可其安全论点（VM 比共享内核更容易加固），但表示 Mac/Windows 采用 VM 的实际原因是当时 XNU/Darwin 和 Windows 都无法廉价地运行 Linux 二进制文件，而 WSL 要到很晚才出现。有反驳观点不认同把较早的 Linux VM 方案称作真正的「microVM」，并援引近期 Docker Sandboxes 的 CVE（CVE-2026-77179 和 CVE-2026-79994）作为安全模型已发生改变的证据；还有评论者提出数据留存方面的担忧，指 Sandboxes 会将进出数据保留 30 天，由此引出了改用 Podman 的建议。技术性回复强调，Docker 的 VM 是一个共享的轻量级 VM，而非每个容器一个新 VM，因此按工作负载隔离与密度之间的权衡仍然存在——动态内存热插拔在这方面仍弱于共享内核的密度——而一个很长的子讨论则把整件事斥为炒冷饭、属于既有技术（AIX WPARs/LPARs、Solaris zones、BSD jails），尽管共享内核设计并不能提供 microVM 所追求的那种隔离。

**值得一读的评论**
- [unsnap_biceps](https://news.ycombinator.com/item?id=49948985): 称这个标题是标题党，并澄清文章只涵盖 Mac/Windows 上的 Docker Desktop——Linux 上的 Docker 已经十年没用 microVM 了。
- [otterley](https://news.ycombinator.com/item?id=49950916): 区分 Docker Desktop 与 Docker Engine，并主张大多数正在运行的生产容器仍共享同一个内核。
- [rvz](https://news.ycombinator.com/item?id=49949011): 按操作系统逐一给出该技术栈的具体拆解：macOS 在 2025 年之前一直使用 QEMU + Virtualization.framework，之后转向 Apple 的原生虚拟化库；而 Linux 要运行 Firecracker 式 microVM 则需要 KVM。

## 18. 内存安全的 WebP 解码 {#story-18}
*HN 第 26 名 · [halide.cx](https://halide.cx/blog/wpd/) · 56 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49941641)*
*原标题: Memory-Safe WebP Decoding*

wpd 是来自 Halide 的一款新 WebP 解码器，用 Rust 编写，带有手写的 SIMD 汇编内核，定位为 libwebp 的直接替代品。文章认为 libwebp 在设计上并非内存安全（引用了 CVE-2023-4863，这个 2023 年的 Chrome/Firefox/Signal 零日漏洞已被加入 CISA 的 Known Exploited Vulnerabilities 目录），并给出了使用 image-webp 0.2.4 与 libwebp a1d89ff 对比的基准测试：单线程无损快 2.74 倍，多线程有损快 2.68 倍，多线程无损快 3.19 倍，另附一张与 libwebp 的功能对等表。项目采用 BSD 2-Clause 许可，可以在不编译汇编的情况下构建，这样只有 zerocopy crate 含有 unsafe 代码。

**讨论**: 讨论转向了 Rust wpd 与 Google 的 Wuffs WebP 解码器的比较。Wuffs 的作者解释说，主分支尚未进行 SIMD 优化（有一个 SIMD PR 存在，但由 AI 辅助完成，他正在手工重写）。Halide 的开发者对 Wuffs b2e6da3 做了基准测试，声称 wpd 在有损静态图上大约快 2-3 倍，即使在单线程下无损也快 7-8 倍，但 Wuffs 作者对「Wuffs 输出与 libwebp 并非逐像素一致」的说法提出异议，并索要示例文件。评论者就安全模型展开辩论：有几位认为独立的验证器（如 Signal 的 webpsan）弱于安全解析器，并指出 wpd 的汇编是一个逃生舱口，不过作者强调 unsafe 代码仅限于汇编绑定模块，配有带边界检查的封装、运行时 CPU 检测和守护页测试。其他人提出 fil-C 和 WebAssembly 作为替代的内存安全途径，还有一位评论者指出该项目在开发中大量使用了 Claude，并追问在禁用汇编的情况下性能如何。

**值得一读的评论**
- [nigeltao](https://news.ycombinator.com/item?id=49948927): Wuffs 作者纠正了「Wuffs 与 libwebp 并非逐像素一致」的说法，说明了主分支的 SIMD 现状，并索要具体的、存在差异的示例图像。
- [computerbuster](https://news.ycombinator.com/item?id=49949788): Halide 的开发者详细说明了 wpd 如何隔离 unsafe 代码：SIMD 内核位于安全的、带边界校验的封装之后，配有运行时特性检测和守护页测试；在关闭汇编时，该 crate 使用 forbid(unsafe_code)。
- [F3nd0](https://news.ycombinator.com/item?id=49950032): 指出该解码器在开发中大量使用了 Claude，并追问在不含手写汇编的情况下编译性能如何，而文章给出的基准测试并未展示这一点。

## 20. RSS Feed 最佳实践（2022） {#story-20}
*HN 第 29 名 · [kevincox.ca](https://kevincox.ca/2022/05/06/rss-feed-best-practices/) · 55 分 · 10 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49946845)*
*原标题: RSS Feed Best Practices (2022)*

Kevin Cox 于 2022 年撰写的一篇技术指南，讲的是如何发布博客 feed，且与内容质量无关。它的核心建议包括：使用 Atom 1.0（规范歧义更少）或 RSS 2；通过 HTTPS 提供服务并配上正确的 Content-Type（application/atom+xml、application/rss+xml、application/feed+json）；只使用绝对 URL；通过 HTML 的 <link rel=alternate> 声明 feed（并用 W3C Feed Validation Service 检查）；保持条目 ID 稳定且全局唯一；小心处理 published 与 updated 时间戳；并在 <content> 中提供完整的文章内容——还顺带提到用 auth-token 私有 feed 来承载付费内容。

**讨论**: 最详细的回复来自 tjansen，他正在开发 RSS 阅读器 downread.com，他说这篇文章除了 HTML/样式那一节之外都是对的，而那一节他称之为误导：包括 Feedly 在内的大多数阅读器完全忽略 CSS，<style> 块会被过滤掉，所以应当直接使用内联样式；而像样的阅读器确实支持 <video>、<audio> 以及常见的 iframe 嵌入（YouTube、X、Instagram、Facebook）——不过仅限于白名单中的主机。一个子讨论串指出，独立阅读器很少提供翻译功能，因此多语言 feed 实际上只能依赖基于浏览器的阅读器；有一位评论者开玩笑说，真正的最佳实践就是有一个 feed 并且不要把它关掉，并以 Twitter 和 Reddit 作为反面例子。关于 ID，talideon 推荐用 RFC 4151 tag URI 来生成全局唯一的条目 ID，cxr 则指出尽管 tag URI 没有权威解析机制，但技术上你仍然可以在 HTTP 中解析它们；另一位评论者也赞成使用 Atom 1.0。整个讨论串大体上同意文章的核心建议，争论主要集中在阅读器实际上会遵循多少样式和嵌入。

**值得一读的评论**
- [tjansen](https://news.ycombinator.com/item?id=49948062): 一位 RSS 阅读器（downread.com）的开发者说，文章关于 CSS/样式的建议具有误导性，并给出了具体的实际情况：大多数阅读器忽略 CSS，<style> 块会被剥离，而来自 YouTube/白名单提供方的 iframe 比文章所暗示的更好用。
- [talideon](https://news.ycombinator.com/item?id=49947840): 推荐把 RFC 4151 tag URI 作为一个实用的方案，用来生成全局唯一的条目 ID。
- [m2026](https://news.ycombinator.com/item?id=49951129): 指出文章忽略的一个缺口：独立 RSS 阅读器通常无法翻译，因此多语言 feed 会迫使用户改用基于浏览器的阅读器。
