## 1. sshole {#story-1}
*HN 第 1 名 · [sshhole.com](https://sshhole.com) · 1,843 分 · 482 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50378228)*

sshole.com 是一个关于 musl libc 和 OpenSSH 组合漏洞的单页漏洞披露。musl 的 SHA-512 crypt 对超过 256 字节的密码返回错误，但 musl 为了让不检查 NULL 的旧程序不崩溃，把错误返回值定为单个字符 「*」，而 /etc/shadow 里「禁止登录」的账号哈希正好也是 「*」。OpenSSH 为了防 CVE-2016-6210 的计时攻击，遇到 「*」或 「!」账号时会拿另一个真实账号的 salt 去哈希密码，然后和原来的 「*」比较，于是 257 到 1024 字符的密码让 crypt() 返回 「*」并与存储值相等，登录被接受。利用条件为：musl + 不用 PAM（或 UsePAM no）+ 开启密码登录 + 存在一个 「*」账号 + 另有一个真实密码账号；Alpine 官方云镜像里的 alpine 用户带免密 doas，等于直接拿到 root。作者称用 AI agent swarm 对多种构建（glibc/musl、PAM/无 PAM）跑了约 17,600 次异常登录才发现，并且需要先失败一次、第二次才成功。

**讨论**: 讨论一开始就分成两派：一派认为这是严重的现实漏洞，指出几乎每台 Linux 都有 「*」和 「!」账号、默认配置就开密码登录、Alpine 容器基数巨大，而且 Alpine 云镜像的默认 alpine 用户直接通向 root；另一派认为条件全是 AND、实际可利用面很窄，并质疑文章夸大了严重性。多人尝试复现但失败，随后有人指出 Alpine 已经把各版本（含 EOL）的 openssh-server 打了补丁，回退 aports 提交后即可复现，也有 lab 和 Docker 复现仓库被贴出。大量评论批评 musl 用 「*」表示错误是荒谬的带内信号设计，甚至怀疑是故意留的后门，同时称赞用错误值掩盖 NULL 崩溃的做法让坏程序活得更久；也有人反驳说 glibc 后来用 「*0」也是同类做法。关于受影响面，OpenWrt/AsusWRT 默认用 dropbear 因此不受影响（但 2019.77 之前的 dropbear 没有 100 字符上限），而 Alpine 官方 openssh 包已在 10.6p2 修复。另一条主线是对页面本身的抱怨：滚动劫持、动画和 AI 腔调导致很难读完，不少人说评论区某条解释比原文清楚。

**值得一读的评论**
- [amluto](https://news.ycombinator.com/item?id=50380581): 指出 musl 的 crypt_des.c 早就为同类失败做了 「*」的变通，只是 SHA-512 路径忘了做；同时说明 sshd 在哈希过短时不会转发 salt，所以只在 SHA 路径打补丁也堵不住这个洞。
- [evgpbfhnr](https://news.ycombinator.com/item?id=50379454): 总结出实际复现的关键细节：目标账号的 shadow 必须是单个 「*」（不是 「!」），且要先失败一次、第二次用超长密码才会被接受；并指出默认容器镜像里的 alpine 用户让影响变大。
- [mari_dtfy](https://news.ycombinator.com/item?id=50380097): 来自 Detectify 从业者的可操作清单：Alpine 3.16 到 3.24 及 edge 的 openssh-server 均受影响，修复包已回滚发布，给出 apk info、sshd -T 检查命令，以及补丁后按 「Accepted password for」 日志排查的方法。

## 2. Alpine Linux 安全公告：OpenSSH-server 密码认证绕过 {#story-2}
*HN 第 2 名 · [alpinelinux.org](https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/) · 425 分 · 76 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50379704)*
*原标题: Alpine Linux Security Advisory: OpenSSH-server password authentication bypass*

这是一份 Alpine Linux 安全公告：在未启用 PAM 构建的 openssh-server（以及 openssh-server-pam 配 UsePAM no）上，攻击者无需密码即可登录。成因是 musl 的 crypt() 对超过 256 字节的密钥返回字符串 *，而 * 正是无密码账户在 shadow 中的存储值，于是 sshd 借用的 salt 哈希与之「匹配」，一次连接即可成功。前提是机器上存在至少一个 $5$/$6$ 哈希账户；Alpine 3.16 至 3.24 及 edge 均受影响，修复版本为 OpenSSH 10.6p2 及 Alpine 3.21.10 / 3.22.8 / 3.23.8 / 3.24.4 的包，升级后必须重启 sshd，撰写时尚无 CVE 编号。

**讨论**: 讨论很快从漏洞本身转向语言与 libc 设计之争。多人追问 musl 为何在错误时返回 * 这种哨兵值，指出这直接违反 POSIX 关于失败应返回 NULL 并设置 errno 的规定，并认为 musl 以「严格遵循规范」著称，此处尤为讽刺；也有人辩护说这是为了替不检查 NULL 的调用方兜底，且能避免通过时序侧信道泄露账户是否存在。另一大分支是 C 与 Rust 的老争论：一方称 Result/Option 强制处理错误就能从源头阻止此类 bug，另一方（包括数位工程师）反驳这是纯逻辑 bug，任何语言里库作者都可以选择用字符串哨兵，而且 C 里返回 NULL 被解引用通常也会安全地 trap。实务层面有人表示自己在硬件上跑 Alpine 但因为没有无密码账户而未受影响，也有人担心 Docker 生态里基础镜像更新缓慢会拖累修复；还有人认为大多数容器并不对外暴露 sshd。另有一条高赞支线指责公告部分段落像是 AI 写的，随后被其他人温和反驳，认为读安全公告时不必逐句做文体审查。

**值得一读的评论**
- [NewJazz](https://news.ycombinator.com/item?id=50380253): 引用 POSIX crypt() 规范原文，质问 musl 为何在错误时返回 * 而非 NULL，并问是否为唯一这样做的 libc。
- [cyphar](https://news.ycombinator.com/item?id=50381179): 指出返回哨兵值其实是为了伪装一次哈希校验、避免时序侧信道暴露用户是否存在，但同时质疑示例代码未用常数时间比较。
- [pheggs](https://news.ycombinator.com/item?id=50382995): 反驳「musl 不安全」的论调：一次漏洞不算统计证据，且可以说 musl 已记录该行为，是 OpenSSH 忽略文档所致。

## 4. Window Sweaters {#story-4}

一个开源的 macOS 菜单栏小应用，用针织风格的彩色边框把窗口包起来，配色取自各个应用图标。内置 37 个应用的手工配色（Finder、Slack、VS Code、Claude、Figma、Photoshop 等），其余应用从图标中取色并套用锯齿、野餐等图案。基于 Felix Kratz 的 JankyBorders 构建，采用 GPL-3.0 许可，支持 macOS 13 及以上版本（Apple Silicon 与 Intel），使用私有 macOS 窗口 API，因此系统更新可能影响功能；尚未经 Apple 公证。可用 Homebrew cask 安装，或按 README 自行编译。

## 5. Lisp 诅咒，如今正降临到你的生态系统中 {#story-5}
*HN 第 5 名 · [javahippie.net](https://javahippie.net/programming/llm/2026/03/05/the-lisp-curse-coming-to-your-ecosystem.html) · 142 分 · 86 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50349667)*
*原标题: The Lisp curse, now coming to your ecosystem*

一篇来自 javahippie.net 的博客文章提出论点：所谓「Lisp 诅咒」——一种极其灵活、以至于每个人都自己造轮子、没人共享库的语言——即将降临到 Java 等主流生态系统，而这次的推手是 LLM 辅助编程。作者预测两种叠加效应：使用开源库的人变少（于是维护者失去反馈和贡献者），以及新建的库变少，因为维护和项目管理的成本远高于生成一个为自己技术栈量身定制的模块。他承认「生成代码比学习库 API 更便宜」这一前提，但拒绝认为这是好主意，称「Not generated here」不过是换了包装的「Not invented here」，并预计这种衰退会逐渐地、在不知不觉中到来，而不是靠谁宣布。

**讨论**: 讨论分为三派。一些评论者攻击 Lisp 这一框架本身：Common Lisp 活得好好的（SBCL、Quicklisp/Ultralisp、Lem），Clojure 才是真正的现代成功案例，因为它搭上了 JVM 的便车；一位有 20 年经验的 Lisp 老手认为，这个诅咒部分是因为「Lisp」一词在 Common Lisp、Scheme、Emacs Lisp 和 Clojure 之间含义模糊——在任何一个单一方言内部，复用是常态。另一些人则表示所预测的行为已经在发生：多人描述自己让 agent 给某个开源项目的本地 fork 打补丁（修 bug、调试某个冷门 Qt/OFX 导入失败），却从不提交补丁，因为他们从没读过生成的 diff，也没有时间或领域知识去为它辩护。分歧最尖锐的是安全方面：一方认为供应链风险和传递依赖使重新实现成为更安全的选择，另一方则反驳说 vendor 进来的代码永远得不到修补，LLM 可能违反许可证条款，而某些领域（密码学、数值计算）绝不能自己手写。对整个论点反复出现的反驳是：同一个 agent 同样可以轻松地集成成熟的库，而作者括号里的那句话已经承认了这一点。悲观者看到 AI 生成的垃圾代码淹没 GitHub、贬低贡献的价值；也有少数人指出，开源那套职业发展激励本来就有点问题。

**值得一读的评论**
- [jedberg](https://news.ycombinator.com/item?id=50383555): 一个关于所预测衰退的具体实例：他让 agent 给某个开源项目的本地 fork 打补丁修 bug，偶尔 rebase 一下，却从不把补丁上游化，因为他没有审查过 agent 的代码，也没时间。
- [AnimalMuppet](https://news.ycombinator.com/item?id=50381985): 对「自己造」阵营划出明确底线——绝不要自己写密码学或数值库，因为数十年积累的对边角情况的加固无法在一个人一生中复现，所以在某些领域，复用库确实能提升质量。
- [drob518](https://news.ycombinator.com/item?id=50381933): 在各类 Lisp 方言中摸爬滚打 20 多年后，他认为这个诅咒只是「大致属实」：真正的问题在于「Lisp」一词把 Common Lisp、Scheme、Emacs Lisp 和 Clojure 混为一谈，而在某个特定方言内部——Racket 的包集合、Clojure 与 Java 库的混用——复用是相当可观的。

## 6. Launch HN：Rivet（YC W23）——在 S3 上扩展并编排 Agent {#story-6}

*原标题: Launch HN: Rivet (YC W23) – Scale and Orchestrate Agents on S3*

Rivet 是一个开源（Apache 2.0）的 agent 工作负载编排器，基于虚拟 actor 模型构建：每个 agent 获得一个长生命周期进程，带内存状态、每 actor 一个 SQLite 数据库、WebSocket 和 cron，而不是一个专属沙箱。其卖点是密度与速度——每个 actor 72 KB 内存，而最小沙箱需 512 MB；p99 冷启动 4.99 ms，对比 1.70 s——SQLite 写入在 3 个可用区中的 2 个把数据落到 SSD 后即确认，随后在后台批量刷入 S3，从而做到 p99 持久化写入 1.07 ms、p99 读取 1.36 ms、从对象存储回退读取 p99 138 ms，存储成本约为三个 EBS gp3 副本的 1/10.4。它以单个 S3 bucket 作为唯一依赖，取代 Postgres/FoundationDB/NATS；自托管只需一个 Rust 二进制文件；并被宣传为 Cloudflare Durable Objects 的可自托管替代品，且没有 128 MB 内存上限、10 GB SQLite 限制或随机驱逐。这些基准数字来自 Rivet 自己，运行于 Rivet 3.0.3；沙箱数据取自其文档中的默认值，冷启动数据来自一个第三方基准测试。

## 18. Show HN: Stroq —— 一份本地审计：你的编码智能体做了什么，以及为什么 {#story-18}
*HN 第 19 名 · [github.com](https://github.com/AGGIB/Stroq) · 37 分 · 8 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50380704)*
*原标题: Show HN: Stroq – a local audit of what your coding agent did and why*

Stroq 是一个采用 Apache-2.0 许可证的开源本地安全工具，它通过 `npx @stroq/cli` 调用，需要 Node.js 22 或更高版本；它会读取你最近 30 天的 Claude Code、Codex CLI 和 Cursor 会话，将它们与这台机器上的凭据进行比对，并报告每个密钥的去向（发给了另一家公司、也许已经发送、被 AI 看到、用于它自己的服务，或者在运行前被拦截）。它只打印密钥名称和来源，绝不打印密钥值；它把内容写入 `~/.stroq` 下的小型缓存，只在 127.0.0.1 上监听，没有账户，也没有遥测。它的钩子横跨 Claude Code、Cursor、Codex、Copilot CLI、Windsurf、Antigravity，另外还有一个 OpenClaw 插件和一个 stdio MCP 代理；它们会拒绝 `curl | sh`，以及携带已知密钥的外连请求；在 0.30.0 版本上，内置的 36 次攻击测试套件得到的结果是 15 次被拒绝、21 次被询问、0 次通过。作者自己把它描述为一个过滤器，而非沙箱：它的匹配是文本层面的，而且钩子只能看到宿主传过来的内容。

**讨论**: 排名最高的评论反驳了它的核心前提：审计数小时后才知道发生了什么，这已经太迟了；如果仅仅一次误敲的 `rm` 就能清空你的机器，那就说明你的 harness 用错了——应该让智能体使用自己的用户，并限制它可以访问的路径和网络。作者坦率地同意，用来生成报告的那条命令完全没有阻止任何操作，`stroq init` 只是增加了确认钩子，而这“一个过滤器，不是沙箱”。又有一个人反驳说，事后检查是必要的，因为 upfront 就写出好的访问控制策略非常困难，而权限会随时间只增不减，所以你只会在出了大问题时才发现缺口。另一位评论者建议增加一个后台守护进程，它会持续扫描，并在菜单栏应用里提醒匹配项，同时提供一键删改、修复或标记为误报，作者对此表示感谢。还有一名评论者提出，用 Linux 上的 eBPF 后端（eunomia 的 AgentSight）会覆盖更多对抗性场景——他们的理由是，反正你应该在 VM 里做开发。

**值得一读的评论**
- [embedding-shape](https://news.ycombinator.com/item?id=50382260): 称审计从根本上解决错了问题——预防应该来自隔离的用户，以及限制路径和网络，而不是事后的报告。
- [maven29](https://news.ycombinator.com/item?id=50383008): 指向一个基于 eBPF 的替代方案（eunomia 的 AgentSight），它可以覆盖更多对抗性场景，但代价是只支持 Linux。
- [arnarbi](https://news.ycombinator.com/item?id=50382550): 为审计辩护：提前设计访问控制极难，而且权限总是只增不减，所以审计是发现策略缺口的方式，而不是可有可无的附加功能。

## 19. Nyquist Limit:The frequency of changes in tech is invalidating our understanding {#story-19}
*HN 第 20 名 · [ryanprior.com](https://www.ryanprior.com/posts/nyquist-limit-frequency-of-changes-in-tech-invalidates-understanding/) · 19 分 · 9 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50370793)*

一篇 Ryan Prior 的博客文章，把 Nyquist–Shannon 采样定理套用到软件组织上：如果一个系统的变化速度超过人类对其采样与建模速度的两倍，你测到的就不再是信号，而是噪声。他认为 LLM 驱动的开发和持续交付正把团队推过这条界限，带来毫无预警的故障；而更好的提示词或更聪明的工程都无法修复一个数学约束——答案是选定一个目标变更频率，并远高于 2 倍地去采样它。他的证据基本是轶事性的，其中包括转述一位在某家科技独角兽公司工作的同事的话，描述超大规模云厂商里的团队「在 prod 环境里 YOLO」。

**讨论**: 整个讨论清晰地分成两派：接受这一诊断的人，和拒绝这个比喻的人。几位评论者从物理学角度发起攻击：采样定理只适用于带限的周期信号，一条直线只需要两个采样点，而先验知识会降低所需采样率——有人举出压缩感知作为一种真正能低于奈奎斯特极限的技术——因此对代码库的理解根本不是一种信号。另一些人承认这个类比并不严谨，但坚持底层问题真实存在：LLM 加速的生成已经超出人类审查、测试和建模系统的能力，而解决办法要么是 AGI，要么是换一种工作与审查的方式。一位实践者报告了具体的第一手证据，说 bug 如今已超出他们团队的基线水平，他将其归因于一个曾经连贯的大型代码库随着更多生成代码进入而变得不再连贯——而且他们看到的只是自己能检测到的部分。还有一条更阴暗的思路认为，业界已不再重视人类的理解，AI 鼓吹者呼吁废除代码审查，把人类留作围绕他们读不懂的技术的仪式守护者。

**值得一读的评论**
- [nemo44x](https://news.ycombinator.com/item?id=50383610): 一位实践者说，在一个大型成熟代码库中，bug 最近已升高到基线之上；他归咎于不断增长的生成代码量稀释了连贯性，并指出他们在关键领域仍坚持严格的人工审查。
- [somethingsome](https://news.ycombinator.com/item?id=50383125): 提出压缩感知是一种真正能在奈奎斯特极限以下采样的方法，并认为这个类比错误地假设自动生成的代码在底层总是组织得很糟。
- [science4sail](https://news.ycombinator.com/item?id=50383010): 有力的反方论点：业界正在彻底抛弃这个前提，从「常读少写」转向「不读常写」，人类被降格为围绕不透明技术打理仪式的人。
