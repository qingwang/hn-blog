## 1. 分享数学领域的 AI 进展 {#story-1}
*HN 第 1 名 · [openai.com](https://openai.com/index/sharing-ai-progress-in-mathematics/) · 769 分 · 698 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49984923)*
*原标题: Sharing AI progress in mathematics*

OpenAI 发布了一个 GitHub 仓库（github.com/openai/math），其中收录了其内部前沿模型产出的大批数学成果，涵盖预印本、部分证明的 Lean 形式化、推理摘要以及算力统计。它声称平均每个结果大约消耗相当于 3 小时 ChatGPT Pro 思考量的算力，并称这批结果中包括对 Unique Games Conjecture（现称 Unique Games Theorem）、Barnette 猜想、矩阵乘法指数 ω ≤ 2.25、低于 n log n 的整数乘法以及快于 O(n log n) 的 FFT 等的证明或改进。OpenAI 表示，在如何发布这些结果的问题上，它咨询了普林斯顿高等研究院（Institute for Advanced Study）的 Advisory Group on Mathematics and Artificial Intelligence（AGMAI），并称未来还会进一步优化论文质量、引用和表述方式。

**讨论**: 讨论被一种悲欣交集的情绪主导：一位长期研究 Barnette 猜想的评论者描述了自己数千小时的努力被机器超越后近乎哀悼的感受，另一些人则反驳说这不算个人损失，还拿 AI 在国际象棋上超越人类后人类棋艺反而提高作类比。主要的实质性批评集中在验证环节——部分结果缺少 Lean 形式化证明，而且整个模型并未公开，因此除了 OpenAI 和 Anthropic 内部之外无法复现；有人把这描述为一种前所未有的权力集中，甚至称之为「AI 论文倾倒（slop dump）」。质疑者还指出，AGMAI 曾公开表示并不认可这种做法、并呼吁停止在专有模型上测试高难度数学问题，而 OpenAI 仍然发布了这批成果，具体是否遵循了其指导方针，评论者意见不一。与此同时，复杂度理论和调度领域的从业者认为 Unique Games Theorem 才是这组结果中真正的重磅——它将改写近似算法的教科书——并特别留意到一些荒谬的常数，比如三机器调度算法中 O((L+2)^150020) 的指数。总体共识是这些结果确实令人瞩目，但验证、可复现性以及它们究竟算是新的洞见还是庞大算力与 Lean 验证循环的产物，仍悬而未决。

**值得一读的评论**
- [jboggan](https://news.ycombinator.com/item?id=49987367): 一位编译器/图论爱好者讲述了自己在 Barnette 猜想上断续投入 24 年、甚至去年夏天还一度以为解决了它，如今看到被列为问题 180 时感到一种奇异的失落。
- [nilkn](https://news.ycombinator.com/item?id=49988412): 认为这些突破完全不可复现，只存在于 OpenAI 和 Anthropic 内部一两个团队中，是史无前例的算力/能力集中，也是许多人焦虑的真正来源。
- [winfieldchen](https://news.ycombinator.com/item?id=49988578): 解释为何 Unique Games Theorem 意义重大：它决定了一整类多项式时间近似算法的极限，包括 Goemans–Williamson 的 0.87856 比在 UGC 下已是最优，教科书将因此重写。

## 2. Strands Decider 2B：一个小型、开源的决策模型 {#story-2}
*HN 第 2 名 · [strandsagents.com](https://strandsagents.com/blog/introducing-strands-decider/) · 127 分 · 25 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49987076)*
*原标题: Strands Decider 2B: a small, open-source, decision model*

Strands Labs 发布了 strands-decider-2b，一个 20 亿参数的「决策模型」或「系统一模型」，已在 GitHub 和 Hugging Face 上开源，附带训练数据与脚本。它取自 Qwen3.5-2B 的骨架，去掉 LM head、换成一个约 100 万参数的指针头，并用 rank-16 LoRA 微调。它只从候选选项中选择或给出数值分数（例如一个 0–1 的「noul」置信度），而不是生成文本；论文声称其准确率和校准度在 JevBench 的 2B 类别中排名 33 个模型里的第 3（排除略超 2B 的模型后为 30 个中的第 1），在 RTX 3090 上中位延迟约 115ms，在 M3 MacBook 上小任务约 153ms。作者将它在模型路由、工具选择、护栏、记忆和策略分类方面的应用，与 API 型 LLM 推理相比，定位为推理成本更低。

**讨论**: 几条开头的评论都是关于「Jerry」的玩笑：一个由真人驱动的决策模型，呼应 Rick and Morty 和 Chappelle 的桥段。关键的技术讨论集中在命名和部署上：一些人询问为什么二元选择被标为「noul」，有人将其追溯到 Bernoulli（「Bernoulli 映射」）。有几位评论者主要关心本地运行：指出 Cloudflare 的 clef 可在 llama.cpp 上运行，并报告在将 PEFT/LoRA 权重转换为 GGUF 时遇到困难（一个不熟悉的 linear_attn 张量无法映射），这阻碍了更广泛的采用。关于实际速度也有分歧——一位在 Docker 中的 M3 上运行，看到的是 1732ms，而不是宣传的约 153ms；另一位则报告，在六核 CPU 上大约是每次决策半秒。常见的反对意见是，JevBench 上的基准校准并不能证明其在陌生的生产环境输入上依然可靠。

**值得一读的评论**
- [hrpnk](https://news.ycombinator.com/item?id=49989024): 指出采用障碍：被锁定在 Strands CLI 中很可惜，因为 Cloudflare 的 clef 可在 llama.cpp 上运行，而将 LoRA 转换为 GGUF 仍留给用户——并展示了未能映射的 linear_attn 张量。
- [soltanov](https://news.ycombinator.com/item?id=49988410): 对标题所指的校准提出质疑：基准校准并不能确保在模型从未见过的生产环境输入上仍然可靠。
- [gopalv](https://news.ycombinator.com/item?id=49988538): 分享第一手 CPU 数据——在 M3 上的 Docker 中，每次决策耗时 1732ms——并附上 README 脚本，指出针对 MLX 的优化还有待开发。

## 3. Decisions API 进入公开测试阶段 {#story-3}
*HN 第 3 名 · [developers.openai.com](https://developers.openai.com/api/docs/guides/decisions) · 242 分 · 112 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49984025)*
*原标题: Decisions API is in public beta*

这是 OpenAI 开放平台文档中的新指南页面：一个专门用于分类与评分的 POST /v1/decisions 端点，目前处于公开测试阶段（预计数周内 GA）。它接收文本和/或 base64 内联图片，返回三种类型化答案——predicate（条件为真的概率 0–1）、choice（从给定选项中选择一个）和 score（按层级序号加权平均）——OpenAI 称其比 Responses API 快约 10 倍；目前唯一可用的模型是 gpt-6-luna。请求不计输出 token，图片不支持 HTTP URL 或 file_id，文档中还包含 Python 3.26.0、JavaScript 7.30.0、Go 3.73.0、Ruby 0.101.0、Java 4.78.0 的 SDK 示例。

**讨论**: 最主要的争论是：Simon Willison 演示了实际的 curl 调用并很快发布了 llm-openai-decisions 插件，随后许多人把这件事读作 OpenAI 在追赶 Typesafe 的 Jev，以及对“AI 是否已商品化、是否存在护城河”的又一次验证。持怀疑态度的开发者（如 Topfi）用 OpenRouter 跑了不到 600 次自建评测，结论是 gpt-6-luna 比 Jev 更慢、贵约 3.1 倍、更容易在模糊任务上失手（在简单标签判断上给出 0.21 和 0.56 而不是 Jev 的 0.69 和 0.91），而其他人反问本地小模型是否真的能替代云端；一位 OpenAI 员工复现了同一批样例并得到 0.99 和 1.0，表示愿意排查异常输出。价格方面被反复引用：输入约每百万 token $0.10（Jev 约 $0.042），双方都不收输出费，所以总体上只有速度和图片输入是明确优势。另一条主线是商业化：许多人认为企业客户会因现有采购、合规、零数据保留合同和厂商审批流程而选择 OpenAI，甚至不需要赢下评测；反对者则说切换模型只需两次按键、开源权重模型足够好，这是价格战而 OpenAI 无法靠“粘性”取胜。关于缓存未启用、校准是否可靠（0.9 是否真的代表 90% 正确）以及这类 API 是否会被合并回通用模型，讨论没有形成共识，但多数人承认图片输入是其相对 Jev 的第一个明显功能差距。

**值得一读的评论**
- [simonw](https://news.ycombinator.com/item?id=49985035): Simon Willison 贴出了可运行的 curl 调用和真实返回（complaint 0.91、compliment 0.06），指出这类端点往往会成为其他厂商的事实标准，并顺手发布了 llm-openai-decisions 插件。
- [Topfi](https://news.ycombinator.com/item?id=49985095): 一位开发者用不到 600 次自建评测对比 Jev 与 Mercury Decide：Luna 更慢（p50 346ms、p95 860ms）、贵约 3.1 倍、在模糊任务上置信度更低，但承认未测试图片输入。
- [brianyu8](https://news.ycombinator.com/item?id=49988427): OpenAI 员工 brianyu8 用同一批标签样例复现评测并得到 0.99/0.99 与 1.0/1.0，邀请作者邮件反馈异常输出，是对前述评测最直接的反驳。

## 4. 1993 年墨西哥的 La Cueva BBS（会话回放） {#story-4}
*HN 第 5 名 · [nanochess.org](https://nanochess.org/la_cueva_bbs.html) · 38 分 · 9 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49987675)*
*原标题: La Cueva BBS in Mexico in 1993 (session replay)*

Oscar Toledo Gutiérrez（nanochess）讲述了他在 1993 年如何从自己基于 Zilog Z280、配备 512 KB 内存和 Hayes 2400 波特率调制解调器的自制电脑，连接到墨西哥的 La Cueva BBS。他自己编写了串口终端，实现了 AT 命令和 ANSI 转义序列，并在 Z280 的 MMU 区域中设有一个 64 KB 的捕获缓冲区。他在一张旧软盘上找到了文件 CUEVA.TXT，其中包含 1993 年 2 月 11 日（晚上 9:30 至 9:47）的一次完整会话，并用改编自 Peter Nitsch 的 jsTerm 将其制作成 2400 波特率的 JavaScript 回放；之后他又添加了另一份捕获记录（Nopal BBS）以及一份 1993 年墨西哥 BBS 电话号码列表。

**讨论**: 这个帖子主要充满怀旧情绪：多位评论者回忆起自己曾在 RBBS-PC 和 WWIV 上运营 BBS，用 20 MB 的 Seagate ST-225 硬盘、19.2k 的 Telebit Trailblazer 调制解调器和 14.4k 的 SupraFAXModem，以及那些从这些 BBS 中结下的长久友谊。一位评论者质疑年份、CPU 与内存的组合，认为一个 8 位、采用 16 位寻址的 Z80 无法处理超过 64 KB 的内存，而且在 1993 年，即便在墨西哥这也已是过时的硬件；另一人作出回应，作者本人也澄清说，那是一台带有 MMU 的 Zilog Z280，可寻址 16 MB，具有 8 KB 页和内部缓存，比 Z80 快得多。其他人则分享了青少年时期使用调制解调器的经历，以及用图片交换 warez 的往事，还有第一次连接到别人电脑时的惊奇。总体基调是对这一发现的欣赏，以及对没能保存更多会话捕获记录和 ANSI 艺术作品的遗憾。

**值得一读的评论**
- [notorandit](https://news.ycombinator.com/item?id=49988679): 认为 1993 年的 Z80 对墨西哥而言是过于受限且过时的硬件，质疑文章的技术前提。
- [nanochess](https://news.ycombinator.com/item?id=49989155): 作者本人作出更正：那是 Zilog Z280，带有可寻址 16 MB 的 MMU、代码与数据分离的映射、8 KB 页和缓存，比 Z80 快得多。
- [noduerme](https://news.ycombinator.com/item?id=49988992): 一位评论者讲述自己 12 岁时如何用 57.6k 的调制解调器，用色情 GIF 交换 3D 建模的 warez，从而获得了 Strata、Renderman、Playmation、Infini-D 和 ElectricImage 的副本。

## 5. Penguin Mail – 面向 Linux 的开源 Rust 邮件客户端，内置 AI {#story-5}
*HN 第 7 名 · [penguin-mail.com](https://penguin-mail.com/) · 148 分 · 79 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49984716)*
*原标题: Penguin Mail – open-source Rust email client for Linux with AI*

Penguin Mail 是一款面向 Linux（x86_64）的桌面邮件客户端，版本 1.0.0，采用 GPL-3.0-or-later 许可。它支持 Gmail、Outlook.com/Hotmail/Microsoft 365 以及任意 IMAP、POP3 和 SMTP 账号（自动探测服务器设置），并集成 Google/Microsoft/CalDAV 日历与 CardDAV 联系人，通过本机 GnuPG 签名和加密（不保存密钥），支持 Gmail 过滤器、Outlook 收件箱规则和 Sieve 规则；其 AI 助手默认关闭，可通过 LM Studio 或 Ollama 在本地运行，发送邮件或更改设置前会先询问，并展示它调用的每个工具。宣称没有自建服务器、不做追踪、不放广告，Gmail 与 Outlook 流量直接发往 Google 或 Microsoft Graph。

**讨论**: 最高票的讨论完全偏离主题：多位评论者指出该项目的 YouTube 介绍视频前的广告是一条明显的诈骗广告（usbest1.com，满是 AI 生成内容，结账流程甚至问你要不要给「司机」小费），并借此呼吁 Google 等广告网络应被强制审核广告主，同时推荐使用 uBlock Origin。技术上最大的质疑来自一位评论者：这类「vibe-coded」邮件客户端如何处理 HTML 邮件的完整内容视图——Thunderbird 等会阻止内联 JavaScript、追踪像素和 CSS 引用，这些新客户端是否只是把 HTML 丢进 WebView？另一个反复出现的争论是 AI 的必要性，有人反感嵌入式聊天框，也有人认为本地 LLM 自动分类和翻译邮件才是唯一真正有价值的用途，还有评论者纠正说 README 里其实提供了 MCP 接口。此外有人指责项目仅开发约一个月就发布 1.0 是「bullshit」，立刻被反驳（发布到 GitHub 一个月不等于项目只有一个月，且未见不稳定证据），也有人为语义化版本从 1.0 起步辩护。关于 Thunderbird 的评价分歧明显：一方抱怨其 UI 令人分心、线程（会话分组）在 2026 年仍不稳定、搜索又慢又不准，另一方则表示自己用了十年觉得挺好，并反讽「凭直觉假定不稳定」的标准过高。

**值得一读的评论**

## 7. 什么是 Codemode {#story-7}
*HN 第 9 名 · [lucumr.pocoo.org](https://lucumr.pocoo.org/2026/10/6/codemode/) · 57 分 · 16 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49978333)*

Armin Ronacher 解释了 Codemode，这是 Pi 1.0 为支持 MCP 而加入的机制：它不把工具定义加载进模型的上下文，而是让 LLM 编写 JavaScript 直接发起工具调用。Codemode 运行在受信任的 harness 一侧（在 Pi 中，是 WASM 里的 QuickJS，没有网络、没有文件系统、没有定时器、内存有限），而不是运行在沙箱化执行环境中；这使 agent 能组合并发调用、把状态暂存在 transcript 中，并在不消耗上下文的情况下访问图像生成和 Jev 分类器等内部 API。示例包括生成图像、对 100 个 GitHub issue 做情感/挫败感批量分类、通过 30 步的 Jev 循环操控一个坦克游戏，以及对 Sentry 之类的 MCP 服务器做渐进式发现。

**讨论**: 整个讨论大体上是怀疑中带着好奇；最具体的反对意见来自一位曾原型实现 Codemode 又把它移除的人：搭配小型本地 LLM 时，它消耗的 token 比平时更多；而当嵌套的工具调用因参数校验失败时，整个父级代码执行调用都会失败，导致模型重写大段代码。其他人表示，这印证了他们的担忧：code mode 在低端场景下扩展性很差——在 Opus 这类强模型上效果很好，但在弱模型上未经检验。一个反复出现的问题是：为什么所有实现都选 JavaScript？作者（the_mitsuhiko）回答说，模型是在 JS 上训练过的，所以需要的指令少得多；它通过 Promise 自然地表达并发；而 bash 很别扭，因为 Codemode 运行在 harness 一侧。评论者还争论 bash 能否胜任同样的工作，以及 read/view_image 这类工具和 stdio MCP 服务器在 bash 中会如何运作。

**值得一读的评论**

- [aidiveyt](https://news.ycombinator.com/item?id=49988961): 来自 Claude Code 日志的一个具体缓存细节：每个 subagent 的缓存写入都走 5 分钟档，而主会话走 1 小时档。

**讨论**: 该帖仅有五条评论，讨论较为单薄，且大多围绕机制而非影响。一位评论者认为本可阻止此事的是 HPKP（HTTP Public Key Pinning，HTTP 公钥固定），而 CAA 记录则不能，但他指出 HPKP 已被废弃——另一位评论者持怀疑态度地回应，问他忽略了什么，以及问题是否归结为顶级域名缺乏对此类反制措施的支持。一位评论者逐字引用了 Google 自己的博客文章，强调被入侵的是整个顶级域名注册局，而非单个网站，并抱怨文中缺少任何一手来源；另一位评论者则通过链接 Google 的安全博客以及同一新闻的另外两条 HN 投稿来提供来源。一条高赞评论列出了三个受影响的 ccTLD，并将 .gh 描述为格陵兰——实际上 .gh 是加纳（.as 是美属萨摩亚，.sl 是塞拉利昂）。大致的共识是：值得关注之处在于注册局级别的入侵，而证书层面的防御并没有看上去那么可靠。

## 19. 当随机数实际上不够随机时 {#story-19}
*HN 第 28 名 · [ersc.io](https://ersc.io/blog/when-random-isnt-random-enough) · 51 分 · 16 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49983404)*
*原标题: When random is not actually random enough*

一篇发表在 ersc.io 上的关于取模偏差（modulo bias）的博客文章：取一个均匀随机的 u64 并用 % n 对它进行缩减，并不能让 n 个选项各自等概率。那个玩具示例是从 10 个整数中挑选并映射到 3 个对象上，结果得到 40%/30%/30%，而不是各 33%。作者认为 random_u64() 是一个过于底层的 API，并推荐 random_between(l, h)，以及一个带相对整数权重的加权 random_choice()（就像 Python 的 random.choices 那样），还描述了在 Antithesis 风格的确定性模糊测试（deterministic fuzzing）中使用它来引导代码覆盖率（例如约 7/8 走小文件上传路径、约 1/8 走大文件上传路径），并报告说他的团队已移除所有 Antithesis 的 random_u64() 调用，改用加权选择。

**讨论**: 评论者大多认同取模才是 bug，而不是 RNG（有人指出正是 % 运算符让分布变差了），但在修复方式以及 API 的定位是否正确上存在分歧。一派主张拒绝采样（rejection sampling）才是简单且显然正确的答案——对超出范围的值重新抽取，因为对于一个真正的 u64，像 [0, 10) 这样的范围其拒绝率约为 2^64 中的 6（约 3.2e-17%），是一个冷分支；一位持异议者指出，在属性测试（property-testing）框架中，生成大型随机数组会让拒绝的成本变得可测量，另一位则提出 Lemire 的近无除法方法（nearly divisionless method）作为标准替代方案。另一派认为 random_u64() 并不算过于底层（任何实值变量都是 Uniform(0,1) 的逆分位数变换），真正的诉求是一个 std.choice 原语；还有几人怀疑仅靠更好用的 UI 并不能防止误用，因为人们连二分查找这种更简单的东西都会手写，并建议模糊测试或确定性模拟测试才能真正让他们醒悟。一个值得注意的更正：关于 rand() 只有 32767 个取值的说法适用于 MinGW/MSVCRT，而 glibc 的 RAND_MAX 是 2147483647——另外还有人争论约 5×10^-20 的权重偏差究竟是否值得在意。

**值得一读的评论**
- [tialaramex](https://news.ycombinator.com/item?id=49985782): 拒绝采样是这里简单且可证明正确的修复方式：抽取足够的比特，若值在范围内就保留，否则重新抽取——并顺带揶揄一句：程序员把随机数当成一种珍贵资源。
- [deathanatos](https://news.ycombinator.com/item?id=49987819): 量化了文章自身示例中的拒绝成本：以 u64 作为来源时，[0, 10) 需要重新抽取的概率约为 2^64 中的 6（约 3.2e-17%），所以拒绝是一个非常冷的冷分支。
- [omoikane](https://news.ycombinator.com/item?id=49987640): 更正了讨论串中关于 RAND_MAX 的说法：32767 是 MinGW/MSVCRT 的取值，而 glibc 及大多数库使用 RAND_MAX = 2147483647。
