**讨论**: 讨论帖中，多数人把热情转向了 Beyond All Reason，好几位评论者称它是最好的开源 TA 精神续作——打磨精良、对新手友好，且能支撑规模巨大的战斗（有人贴出一场 150 名玩家的对局链接）。一个针锋相对的反驳观点认为，Forged Alliance 在结构上是更好的游戏，而 BAR 只是一个 TA 克隆，缺少 FA 的改进；由此引发了人们对为 Supreme Commander 做类似引擎替换项目的期待，也有人提到 SupCom 糟糕的多线程和寻路性能 bug（为已死亡 AI 单位寻路），并称 LOUD mod 可以修复。另一些人提到 Planetary Annihilation（由前 Cavedog 成员制作）和 Spring Engine。还有一组评论对网站本身抱有敌意，称其文案明显是 AI 生成的垃圾——短促、重复、有节奏感的措辞，比如「Same scene. ## 4. 你的 PATH 中的波浪号可能并不是你的 HOME {#story-4}
*HN 第 4 名 · [disconnect3d.pl](https://disconnect3d.pl//2026/10/02/dont-put-tilde-in-your-path/) · 165 分 · 97 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50042425)*
*原标题: The tilde in your PATH may not be your HOME*

一篇博客文章指出，在 ~/.bashrc 或 ~/.zshrc 中写 export PATH=“$PATH:~/.local/bin/” 并不会把 ~ 展开成家目录，因为双引号内的波浪号不做展开，结果 PATH 里多出一个字面量 ~ 目录（相对路径 ./~/.local/bin/），作者还演示了把自己编译的 kek 二进制放进那个目录并被 shell 找到执行。触发他发现这个问题的是 nono 沙箱工具发出的警告「PATH entries the sandbox can write to」。修复办法是改用 $HOME，或者把冒号放在引号外：export PATH=“$PATH”:~/.local/bin，作者并给出用 echo “$PATH” | tr ':' '\n' | grep '~' 自查的方法。

**讨论**: 讨论大体分几派。一派认为这是常识级陷阱、脚本里根本不该用波浪号，一律用 $HOME 或其他环境变量；另一派（如 paulddraper）给出更细致的引用规则：只给 $ 表达式加双引号，并指出作者那个引号版本其实无法只靠改引号修好，因为波浪号只在词首展开。chasil 起初主张 export PATH=“$PATH:”~/.local/bin 是 POSIX 合规写法，被 yencabulator 指出那只是把字面量 ~ 留在路径里，随后他查阅 POSIX 2.6.1「波浪号可跟在未加引号的冒号之后」，改口认定把冒号移出引号才是正确写法。另有一大支讨论转向更换 shell：fish、zsh、nushell、murex 各有拥趸，反方强调 bash/sh 的不可替代优势是到处都已安装。安全方面有人提醒把用户可写目录放在系统目录之前有风险，也有人反驳说既然能写入你的 PATH，通常也能写入你的 shell 配置。

**值得一读的评论**
- [paulddraper](https://news.ycombinator.com/item?id=50043582): 给出一套实用的 Bash 引用规则（只给 $ 表达式加双引号、只给含特殊字符的字面量加单引号），并指出光换引号并不能修正原文例子，因为波浪号只在词首展开。
- [chasil](https://news.ycombinator.com/item?id=50046172): 在被指出错误后查阅 POSIX 2.6.1，确认波浪号可跟在未加引号的冒号之后，因此 export PATH=“$PATH”:~/.local/bin 才是既简洁又符合标准的写法。
- [quotemstr](https://news.ycombinator.com/item?id=50044504): 指出文章漏掉的话题：$HOME 与 getpwent(3)/etc/passwd 给出的家目录可能不一致，~ 会用 $HOME，而 ~user 会走用户数据库，各语言运行时的「用户家目录」API 又各不相同。

## 5. LineageOS 24.0 {#story-5}
*HN 第 5 名 · [lineageos.org](https://lineageos.org/Changelog-32/) · 345 分 · 132 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50040276)*

LineageOS 24.0（官方 Changelog 32，「Slick Seventeen」）是该项目基于 Android 17 的新版本，团队称这次 rebase 比预期更快，官方自评 24.0 在功能与稳定性上已与 23.2 持平；安全补丁已合并到 18.1 至 24.0 各分支，覆盖 2025 年 8 月至 2026 年 10 月的公告。核心应用全面转向 Material Design 3 Expressive：新增 Canvas 图片编辑器，Updater 默认流式更新（A/B 设备安装时间大幅缩短）、Catapult 增加电池指示、Etar/Seedvault/SetupWizard 更新，WebView 升至 155.0.8059.30；同时上线基于 WebUSB 的浏览器刷机工具 flash.lineageos.org。政策变化：只接受 4.4/4.9 内核设备提交 22.2，23.2/24.0 仅收具备 1:1 eBPF backport 且可完全不用 GCC 构建的内核；文中还提到一个实验性的通用 target 已在 x86_64 PC、Apple Silicon Mac、NVIDIA DGX Spark、Snapdragon X 笔记本上启动成功。2026 年 12 月 24 日 LineageOS 将满十周年。

**讨论**: 讨论主线是设备寿命：不少人感谢 Lineage 让 Pixel 4a、Pixel 3、OnePlus 6T 等老机继续可用，也有人指出 4a 的 modem/baseband 存在 Android 更新无法修补的漏洞，且换电池虽然只要约 90 欧元（德国第三方件约 13 欧，iFixit 原厂约 45 欧）仍有拆坏屏幕的风险。银行类 App 是第二大话题：有人称没遇到能拦住的银行 App，随即被指出 Revolut 会检查 build string 直接封杀 LineageOS，只能自编译改名字绕过，N26、DKB、UBS、ABN AMRO 也被点名；反方观点是这类 root/自定义 ROM 检测对攻击者毫无作用、只惩罚普通用户，有人归因于银行法务的保守要求。围绕 GrapheneOS 与 LineageOS 的比较争论激烈，有人问为何 Lineage 支持 Android 17 如此慢，支持者解释 GrapheneOS 有全职付费开发者、与某 OEM 有提前拿到 embargo 补丁的合作、且只覆盖 Pixel（约 Lineage 设备数的十分之一），而 Lineage 覆盖约十倍的设备类型。实际使用问题包括：Lineage 相机画质差（建议手动装 BSG 版 GCam）、Pixel 上 RCS 群聊失灵、build 列表并未全部上线（Pixel 9 Pro 有 24.0 而 Pixel 9 仍是 23.2），以及严格内核要求让 OnePlus 6/6T 失去官方新构建（其内核为 4.9，并非「接近 mainline」）。此外一条关于 WebUSB 通用 target 的帖子里跑偏出很长的远程度量（remote attestation）与相机取证辩论。

**值得一读的评论**
- [deng](https://news.ycombinator.com/item?id=50042901): 解释 LineageOS 追版本比 GrapheneOS 慢的原因：GrapheneOS 有全职付费开发者、与 OEM 有提前获取安全补丁的合作，而 Lineage 由业余时间开发并支持约十倍的设备数量。
- [platinum95](https://news.ycombinator.com/item?id=50041334): 指出 Revolut 会专门检测 LineageOS 的 build string 并封禁 App，当时的绕法是自己编译 ROM 并改名。
- [haunter](https://news.ycombinator.com/item?id=50041320): 强调文章里最令人兴奋的点：实验性通用 target 已在 x86_64 PC、Apple Silicon Mac、NVIDIA DGX Spark 和 Snapdragon X 笔记本上成功启动，可用于给旧笔记本刷 Android。

## 6. 纽约市的「Click to Cancel」规则现已生效 {#story-6}
*HN 第 6 名 · [nyc.gov](https://www.nyc.gov/main/click-to-cancel) · 38 分 · 8 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50045946)*
*原标题: NYC's "Click to Cancel" rule is now in effect*

这是纽约市消费者与工人保护局（DCWP）的一则说明页面：该市首创的市政级「Click to Cancel」规则已于 2026 年 10 月 1 日生效，要求商家用清晰语言披露订阅条款，并提供与注册方式相同媒介、同样简便的取消渠道，且不得要求消费者自付运费退回免费寄来的商品。违规者面临从 525 美元起的民事罚款，并可能被要求退款；消费者可提交投诉，但页面给出的提交方式是邮寄纸质表格或传真至 (212) 487-4482。

**讨论**: 讨论的焦点是「和注册一样容易」这条标准如何落地。有评论者提出，如果一个创业公司用 Stripe 一键注册，是否意味着取消也必须同样一键，而现实中许多公司虽然支持线上取消，却要求登录、进入设置、再层层拒绝挽留优惠——他呼吁官方给出具体示例来划清界线。另一位评论者反驳说，这种「规则难以遵守」的印象是有意制造的人为复杂性，原则其实很简单：网页注册就该网页取消，电话注册就该电话取消，企业故意让取消更难是出于自身利益，这项法律应当在各地推广。还有人指出一个讽刺之处：规则本身要求取消便捷，但投诉渠道却只能寄信或传真。另有评论者贴出此前关于该规则的讨论链接。

## 20. 一次 Git 提交有多大？ {#story-20}
*HN 第 29 名 · [ratfactor.com](https://ratfactor.com/cards/git-commit-size) · 75 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50017548)*
*原标题: How big is a Git commit?*

这是一篇由 ratfactor（Dave）撰写的短卡片文章，测量每次提交时 .git 目录增长了多少。一个空仓库约为 64 KB；提交 250 个极小的文件会增加 47,640 字节；在一个单文件仓库中做 3 字节的改动仍会增加 8,709 字节（四个松散对象：一个 commit、两个 tree、一个 blob）；一个 583,840 字节的二进制文件会增加 297,873 字节，而一个 16.4 MB 的 Linux 源码文件只增加 1.6 MB。要点在于：git 的 zlib 压缩加上最终形成的包文件（packfile）使存储极其高效，但极小的提交仍然带有千字节量级的 tree/object 开销——对于较大的提交，这一开销占未压缩内容的比例从 50% 到 10%。

**讨论**: 最大的一个分支讨论是一场风格之争：几位评论者希望文章中的 shell 片段使用长选项（--summarize、--bytes），好让代码自解释；而另一位指出短选项其实并不更具可移植性——一个 CI bug 就被追溯到 GNU 与 BSD 的 `base64 -d` 与 `-D` 之别，而长形式 `--decode` 在两者上都能用。关于压缩，一位评论者问 git 能否使用 zstd 或 brotli；给出的答案是不能，只能用 deflate 并配置级别（core.compression / pack.compression），而且因为用的是原始 zlib，包文件不携带标识算法的头部，所以更换算法会破坏网络交换；一位实践者把图片单独放进未压缩的 .keep 包，以免在已压缩的 JPEG/PNG 上浪费 CPU。对文章数字最高票的纠正意见是：松散对象的测量高估了长期成本——一次极小的改动会重新存储整个文件，直到 `git gc` 将其打包，而带增量压缩的包文件大小才是真正重要的，尽管 git 仍须找到一个好的增量。其他人报告了相邻的工程实践：一位评论者把 git 仓库存放到基于 S3 的分布式文件系统（HopsFS）中并使用远程 NVMe 写入，发现写穿透式 NVMe 缓存不可行，因为 S3 延迟太高；另一位提到用感知 AST 的路径做压缩，结论是 git 自带的压缩更好。

**值得一读的评论**
- [masklinn](https://news.ycombinator.com/item?id=50041462): 详述 git 的压缩现实：只用 deflate，松散对象和包可分别调节，包上不带标识算法的头部，外加一个生产技巧——把预压缩的图片放进它们自己的未打包 .keep 包中。
- [gblargg](https://news.ycombinator.com/item?id=50041133): 主张文章的松散对象数字是错误的度量——一次极小的编辑在短期会重新加入整个文件，而在包文件中它本应几乎不花代价，所以包文件大小才是关键。
- [jamesblonde](https://news.ycombinator.com/item?id=50041590): 来自构建 HopsFS 的第一手叙述：由 S3 支撑的 FUSE 文件系统中的 git 需要让写入落到远程 NVMe 并异步同步，而写穿透式 NVMe 缓存会失败，因为 S3 延迟太高。
