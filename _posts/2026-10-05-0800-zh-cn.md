## 2. 一次由 swap 引发的 40ms Go 垃圾回收暂停 {#story-2}
*HN 第 4 名 · [frn.sh](https://frn.sh/go-gc/) · 63 分 · 28 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49959654)*
*原标题: A 40ms Go garbage collector pause caused by swap*

frn.sh 的一篇博客文章描述了一次生产环境实验：为吸收内存峰值而启用 swap，结果导致 Go 的 stop-the-world GC 暂停时间暴涨。在一台 Hetzner 机器的 cgroup 中（内核 6.8，启用了 MGLRU），GC 暂停时间中位数约为 51us，但当 GC 元数据页被换出到 NVMe 后，最差暂停时间达到了 40ms——其中 39ms 花在了 runtime 记账代码（如 spanSet.reset、finishsweep_m 和 nextMarkBitArenaEpoch）内部的 228 次缺页中断上，这是在 30 分钟内 312 次 STW 暂停中发生的。正常构建一条 511 KiB 的消息需要 3-5ms，在 NVMe 上跃升至 105ms，在 Hetzner 的网络卷上则达到 903ms；文章的一则更新指出，Go 1.26 的 Green Tea GC 在此场景下几乎没有变化。

**讨论**: 讨论串总体认同 swap 与 GC 不能混用，但在解决方案上存在分歧。几位评论者（jacobgold、xxs）认为答案是：对延迟敏感的工作负载应禁用 swap，或者说对于带 GC 的语言而言 swap「普遍有害」；而 delamon 反驳说这并不全面：代码页仍可能被换出，mlock()/mlockall()（或按 quotemstr 所说，有选择地对 STW 会触及的页面调用 mlock）才是真正的保护措施。nasretdinov 称这是意料之中的，因为任何追踪式 GC 都必须遍历整个堆，每一个周期都会破坏 swap 的 LRU——pjmlp 对此提出异议，指出引用计数本身也是一种 GC 算法，具体行为取决于实现，不过其他人则反驳说引用计数有每次分配的开销和无界的释放链。讨论中提到了 on-the-fly GC（DLG、Fil-C 的 FUGC）以及 Go 现有的并发标记清除设计，klodolph 指出 Go 的 STW 已经只有几十微秒，而暂停时间与吞吐量之间的取舍是固有的；反复出现的结论是：GC 的延迟 SLO 应该把操作系统内存压力考虑在内，而不应被当作收集器的 bug 来诊断。

**值得一读的评论**
- [delamon](https://news.ycombinator.com/item?id=49961142): 反驳「直接禁用 swap」的建议：代码页仍可能被换出，因此 mlock() 才是正确的保护手段，而 swap 实际上让内核能在数据页和代码页之间做出更均衡的选择。
- [pizlonator](https://news.ycombinator.com/item?id=49960828): 来自一线 GC 专业知识的分享：讲解了经典的 on-the-fly DLG 算法，给出了 POPL'94 论文和 Fil-C 的 FUGC 源码链接，并将 permagrey 栈与 Go 的协程扫描开销做了对比。
- [xavdid](https://news.ycombinator.com/item?id=49961326): 指向 Discord 2020 年关于他们为何从 Go 迁移到 Rust 的文章，这是 Go GC 延迟问题的一个著名先例。

## 3. Anthropic 将日记内容报告给警方，女子面临重罪指控 {#story-3}

*原标题: Anthropic reported diary entry to police, woman faces felony charge*

TechSpot 的一篇报道讲述了佛罗里达州 Bonita Springs 的 Carli Michelle Heller，她据称把 Claude 当作日记使用，并在 9 月 26 日写道她要去「shoot up」警长办公室。Anthropic 的安全系统标记了该条内容，一名人工审核员判定其构成可信威胁并报告给了执法部门；Heller 在未发生冲突的情况下被拘留，并被控以书面暴力威胁罪——根据佛罗里达州法规 836.10，这属于二级重罪。文章提到 Anthropic 在有限紧急情况下共享用户数据的政策，并将此案与 OpenAI 在不列颠哥伦比亚省以及 6 月佛罗里达州诉讼中的做法作对比——在那些案件中，OpenAI 未能就其安全团队标记出的一名枪手向警方预警。

**值得一读的评论**
- [foolfoolz](https://news.ycombinator.com/item?id=49961323): 有力的反驳论点：此案并非 Claude 特有——书写并分享威胁在任何地方都会被起诉，并附有三个学生因书面威胁被捕的链接作为佐证。

## 4. Infidel 失控了 {#story-4}
*HN 第 7 名 · [blog.zarfhome.com](https://blog.zarfhome.com/2026/10/infidel-goes-wild) · 122 分 · 19 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=49943637)*
*原标题: Infidel goes wild*

Andrew Plotkin（Zarf）用他开发的 Visible Zorker 工具分析了 Infocom 1983/1984 年的冒险游戏 Infidel，发现了一个会破坏 Z-machine 内存的野指针 bug。ZIL 编译器把 DESERT-TO-TABLE 例程的 TBL 参数默认值初始化为全局变量的索引号（30），而不是数组地址（11129），于是丢弃物品的记账写入会覆盖地址 30 及以上的内存。在 Endless Desert 中丢弃九个物品后，这次覆盖会到达地址 64 处的缩写表，导致打印文本乱码（把「the」替换成「You」）或让解释器崩溃——这个 bug 就这样随游戏发布而无人察觉，因为没人会在一片毫无特征的沙漠里丢掉许多物品。

**讨论**: 评论者大多很开心：kwertyoowiyop 开玩笑说，1980 年代的游戏程序员没人敢说自己没有过破坏内存的 bug，还有几个人讲了自己的 C 语言内存破坏血泪史（一位资深工程师被实习生的 bug 搞得一头雾水、一个文本编辑器让 Windows 95 要求重装系统）。saghm 安慰 morkalork 说，写现实世界的 C 代码和写内存破坏 bug 实际上就是一个圈。kqr 热情洋溢地写了一篇长篇入门介绍，讲依旧活跃的互动小说圈子——IntFiction.org 论坛、免费竞赛作品，以及推荐的 IFDB 现代 parser 游戏搜索——同时提醒说 parser 的使用惯例必须专门学习，而老经典作品是不好的起点。另有一条并行的讨论串，jdw64 问如何写出技术上有趣的帖子，引来了一些实用建议：写你自己的经历（ajkjk）；追随随机灵感，不要每篇帖子都同样的分量，像 Julia Evans 那样（zem）；把现有的日志整理成一篇公开文章（embedding-shape）。

**值得一读的评论**
- [kqr](https://news.ycombinator.com/item?id=49961436): 一份关于当前互动小说社区的详细指南，说明为什么 parser 游戏的惯例必须专门学习，以及一个精选的 IFDB 现代游戏搜索可供入门。
- [Waterluvian](https://news.ycombinator.com/item?id=49959592): 对文章把内存损坏说成万恶之罪的论调进行调侃式反驳，引用其中一句为「自我鞭笞有害。」
- [zem](https://news.ycombinator.com/item?id=49959347): 实用的写博客建议：先把随机的职业灵感写成简短的回复，并以 Julia Evans 的 jvns.ca 做法为范例——深度和分量要有变化。

## 6. 失去动力的 F1 车手对巴林 F1 软件故障感到沮丧 {#story-6}

*原标题: Homa: The end of TCP for AI clusters [video]*

这是一个讲座视频（由 AI Engineer 的 swyx 策划），主讲人 John Ousterhout 推介 Homa——一种面向数据中心内部、旨在取代 TCP 的传输协议。Homa 最早发表于 2018 年 SIGCOMM 论文，并有 2021 年 USENIX ATC 版本：它把消息拆成「非调度部分」（第一个 RTT 字节，立即发送）和「调度部分」（仅在接收方用 GRANT 包明确请求后才发送），目标是最小化尾延迟而非提升吞吐量。其核心论点是 TCP 由发送方驱动的拥塞控制和队头阻塞正成为 AI 集群流量（权重梯度、模型权重、KV cache、checkpoint）的瓶颈。

**讨论**: 讨论分歧明显。评论者 Veserv 长篇批评 Homa 设计糟糕：没有外连接状态，若一个 RPC 的所有发送端包全部丢失则无从检测（对小消息影响尤甚）；不内建加密；性能差——ATC21 论文 Table 4 中 60 kB 平均消息场景用 5 个超线程才跑到约 20 Gbit/s，即每个超线程仅约 4 Gbit/s；并认为 QUIC 用更干净的设计（stream ID 对应 RPC ID、Stream Max 对应 Grant、内建加密、更精确的 RTT）解决了 Homa 想解决的所有问题。评论者 wmf 则反驳：Gbit/s 不是重点，Homa 追求的是延迟；TCP 同样依赖超时、同样没有加密；并指出不能空口断言 QUIC 更快。另有一组讨论集中在 RoCE/InfiniBand 与以太网流控（PFC/ECN）上，有人认为 AI 集群实际部署靠的是 InfiniBand（唯一供应商 Nvidia）或带 PFC/ECN 的 RoCE，本就很少用 TCP，而以太网 pause frame 只会把瓶颈转移并产生拥塞扩散。还有人以电路交换让位于分组交换作类比，指出 AI 集群流量模式远比公网可预测，因此定制协议更高效。策划者 swyx 现身提供了讲座转录与摘要链接，版主 dang 将其加入 toptext；也有评论抱怨不该把视频作为主要链接。

- [Veserv](https://news.ycombinator.com/item?id=49959116): 逐条列出 Homa 的设计缺陷：无法检测整条 RPC 丢失、无内建加密、实测每超线程仅约 4 Gbit/s，并论证 QUIC 以更干净的机制覆盖了 Homa 的诉求。
- [Animats](https://news.ycombinator.com/item?id=49958720): 解释 Homa 的核心机制（非调度部分 + GRANT 调度部分），梳理其 2018 年起源，并指出硬件交换机的每包开销已低到让小编包不再低效。
- [stingraycharles](https://news.ycombinator.com/item?id=49959760): 指出 AI 集群实际上靠 PFC/ECN 的 RoCE 或 InfiniBand 部署（Nvidia 十年前收购 Mellanox），本来就基本不用 TCP，以太网流控本身并不充分。
