## 2. 93% 的颜料泼溅图案都是合法的 Perl 程序（2019） {#story-2}
*HN 第 2 名 · [mcmillen.dev](https://www.mcmillen.dev/sigbovik/) · 383 分 · 50 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50459745)*
*原标题: 93% of paint splatters are valid Perl programs (2019)*

Colin McMillen 写的一篇简短的愚人节风格论文，发表于 SIGBOVIK 2019（匹兹堡，4 月 1 日），探讨的问题是：能不能把颜料抹在墙上却不产生一个合法的 Perl 程序？作者对一个包含 100 张颜料泼溅图像的数据集做 OCR，发现其中只有 93% 能被解析为合法的 Perl，并给出了七个不能解析的泼溅图案，还附了一个画廊，把每张图片与 OCR 从中提取出的 Perl 源码一一配对。这篇论文获得了 SIGBOVIK 的「Unwitting Participation Ribbon」奖；作者还提到了一些事后发现的趣例，比如一张泼溅图被 OCR 成 lerzfijglpFiji-j，另一张被识别为 -*?，这两个在 Perl 中求值都为 0，而 ;E,'__' 求值为 E__。

**讨论**: 讨论串分为两派：一派享受这个玩笑，另一派反对其方法。主要的批评来自 SoraTakai：结果完全取决于所用的 OCR，而论文没有给出任何基线——既没有测量随机字符串或随机 OCR 输出中有多大比例能被解析为 Perl——所以 93% 这个数字毫无意义；charcircuit 和 notorandit 也同意，这其实是一个关于糟糕 OCR 和精心挑选参数的故事。辩护者则回应说，这没有抓住重点：这是一个关于 Perl 的玩笑，而如果要说它严肃，那也是关于 Perl 如何接受荒谬输入，OCR 不过是一个有趣的任意字符串生成器；他们还指出，作者确实尝试了多种 OCR 设置，并在出现多个合法程序时挑出了最「有趣」的那个。有几位评论者跑题谈到其他几乎能接受任何内容的格式——Java properties 文件（只有在 \u 转义格式错误时才会失效）和 CSV，其中有人现身说法，讲了一个 XML 错误页面被悄悄当作 CSV 摄入、进而级联成填满 null 的数据库记录的故事。还有人指出，这篇论文至少是第四或第五次登上首页了（附有 2019、2021、2024 年的讨论链接），另有一个怀旧子串既哀悼也庆祝 Perl，其中包括有人提到一套 2003–2004 年、约 20 万行的 Perl 监控系统，据说至今仍在运行。

**值得一读的评论**
- [0xbadcafebee](https://news.ycombinator.com/item?id=50460966): 引用了论文的解释：大多数合法程序之所以成立，是因为 Perl 的「未加引号字符串」特性——裸的字母数字会被解析为带引号的字符串——并指出 perl -w 会警告该裸词可能与未来的保留字冲突。
- [omoikane](https://news.ycombinator.com/item?id=50462491): 点出一个脚注里的彩蛋：一个 Perl 错误 quine，即把「Illegal division by zero at /tmp/quine.pl line 1.」这一行写进文件，Perl 就会把它原样复现出来；已在 perl 5.42.0 上用任意绝对路径验证。
- [SoraTakai](https://news.ycombinator.com/item?id=50462724): 最有力的方法论反对意见：结果取决于所选用的 OCR，而论文没有为随机输入建立任何基线通过率，使得 93% 这个数字毫无意义。

## 3. Apache HTTP Server 中的严重 RCE 漏洞 {#story-3}
*HN 第 4 名 · [wiz.io](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) · 149 分 · 68 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50462177)*
*原标题: Critical RCE Vulnerability in Apache HTTP Server*

一篇 Wiz Research 的博客文章，讨论 CVE-2026-119618：这是 Apache 的 mod_http2 中 assign_headers() 函数里的一处竞态条件，可让未认证的远程攻击者破坏堆内存，并有可能以 Web 服务器进程的身份执行代码。该漏洞影响 httpd 2.4.55 至 2.4.70（已在 2.4.71 中修复）以及独立构建的 mod_h2，由 Anthropic 和 Google Cloud 的漏洞研究团队各自独立发现。Wiz 声称 64% 的云环境中存在受影响的资源，51% 有公开暴露的实例，但同时表示目前没有可用的漏洞利用程序，也未曾报告过在野利用；缓解措施是打补丁或禁用 h2/h2c，并继续使用 HTTP/1.1。

**讨论**: 最有价值的贡献来自一位评论者，他说自己借助 DeepSeek 花了约 0.02 美元、用了 7 分钟，就在一个有漏洞的构建版本上复现了 h2 竞态条件，并确认打过补丁的版本能够抵御同样的尝试。讨论区的很大一部分在争论「RCE」这个标签：几位评论者认为，在没有可用的 exploit 的情况下，内存破坏并不等于 RCE；另一些人则指出 Apache 的公告和 Red Hat 的说法——公开研究已证明存在针对默认配置的 mod_http2 服务器的可靠 exploit——再加上 Anthropic 和 Google 各自独立的发现时间，认为有理由相信它。评论者还挑出了这篇文章的质量问题：一处从 Brotli 文章中遗留的 CVE-2026-111497 标识符、把 GitHub 列为 mod_h2 的供应商，以及一个已修补的独立版本（2.0.24）与文中声称的受影响范围（最高到 2.0.42）相矛盾——有几个人称其为 LLM 生成的垃圾，并建议改看官方 httpd 安全页面。系统管理员指出 Apache 的部署仍然非常广泛（约占网站的五分之一，常常位于 nginx 之后，是 WordPress 官方 Docker 镜像的默认配置，也是需要 mod_shib 或 mod_md 时的选择），抱怨当时还没有打好补丁的发行版软件包或容器镜像，并质疑为何在修复到位之前就公开披露。一个分支讨论议题是 AI 发现的漏洞，多数人认为用 AI 找 bug 与 fuzzing 或静态分析并无不同，而一位评论者希望拒绝 AI 的项目也拒绝 AI 发现的修复，另一些人则嘲笑了这一立场。

**值得一读的评论**
- [jerrythegerbil](https://news.ycombinator.com/item?id=50463365): 声称做过一次快速复现：针对有漏洞版本的一次定向提示在 7 分钟内找到了 h2 竞态条件，DeepSeek 用量花费约 0.02 美元，同样的尝试在打过补丁的构建上失败，而禁用 h2 是有效的缓解措施。
- [woodruffw](https://news.ycombinator.com/item?id=50462662): 认为业内有一个很强的惯例：在没有演示过 exploit、或至少没有一条干净的 write-what-where 路径的情况下，不应把某个问题称为 RCE，因此「RCE」的说法言过其实——并指出如果 RCE 真的存在，LLM 应该很容易证明。
- [perching_aix](https://news.ycombinator.com/item?id=50462841): 引用 Red Hat 的公告，其中描述了一个针对默认配置的 mod_http2 服务器的可靠公开 exploit，并引用 Apache 的时间线，显示该漏洞由 Anthropic（10 月 26 日）和 Google（11 月 3 日）各自独立发现。

## 4. Jane Street：苏格拉底式导师 {#story-4}
*HN 第 6 名 · [github.com](https://github.com/janestreet/agent_skills/blob/master/socratic-tutor/SKILL.md) · 48 分 · 12 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50438261)*
*原标题: Jane Street: Socratic Tutor*

这是 Jane Street 的 agent_skills 仓库中的一份 SKILL.md 提示词规范，用户明确说出「教我」「考我」「练我到熟练」等触发语时才会启动，一次性的「解释 X」问题不会触发。流程是：先做 3-5 道题的诊断性摸底，把话题拆成 4-10 个子技能并各自评为 0-5 级（0 完全没听过，5 能教别人、能处理边界情况），此后一次只问一个问题、答错不直接给答案而是追问更窄的问题、按 2 次以上独立检验才升级，并穿插无预警的间隔复习，全部子技能达标后做一次综合终考；还支持「show progress」「harder/easier」「just tell me」「save state / resume from」等命令。

**讨论**: 评论分成两派。一派认为这种把结构化思维固化成提示词的做法有价值，有人观察到职场邮件质量整体提升，认为 AI 正把「结构、精简、次序」这些表达习惯传导给人类。质疑方的火力集中在两处：一是这种文件是否真的有用——有人直言这像一年前的「AI 顾问式垃圾」，说自己客户刚开除过一个往代码库里塞这类文件的人，并好奇 Jane Street 的 AI 负责人是谁；二是原创性——有人怀疑 Jane Street 抄了 bevibing/socrates-skill，但立刻被反驳说两者复杂度完全不同，GitHub 上「socratic tutor skill」能搜出 92 个仓库，苏格拉底式提问本是公开技术，多人各自独立想到很正常，也有人晒出自己 2024 年 12 月就做过类似的。另有实践派表示根本不需要 skill：直接让 AI 生成 Lean 教程加练习，一次成型效果就很好，关键是可以随时说「我卡住了，给个提示」。共识大致是：技巧本身没问题，但把它包装成仓库文件是否比一句提示更有用，仍无定论。

**值得一读的评论**
- [beans6543](https://news.ycombinator.com/item?id=50463915): 用 GitHub 搜索反驳抄袭指控：苏格拉底式提问是公开的经典教学法，「socratic tutor skill」能搜到 92 个仓库，Jane Street 的版本只是更复杂，属平行发明而非抄袭。
- [bob1029](https://news.ycombinator.com/item?id=50463980): 最强反方观点：认为这类文件就是「AI 顾问式垃圾」，自己的客户刚因为有人往代码库里堆这种东西而将其解雇，并调侃 AI 革命在不同地方推进速度差异巨大。
- [IshKebab](https://news.ycombinator.com/item?id=50464115): 第一手经验：不用任何 skill，直接让 AI 生成带练习的 Lean 教程，第四次学 Lean 终于有进展，最大价值是能随时要求「我卡住了，给个提示」。

## 5. 我给了一个 agent 一座湖仓，以及我花园的控制权 {#story-5}
*HN 第 7 名 · [jatorre.github.io](https://jatorre.github.io/garden/) · 33 分 · 10 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50415162)*
*原标题: I gave an agent a lakehouse and control of my garden*

正在开发名为 LakehouseBox 的数据产品的 Jatorre，用约 300 欧元的 Ecowitt 设备把一块 2 平方米的高架菜床武装了起来——八个土壤探头、一个气象站，以及叶片湿度、降雨、风速和太阳能传感器，外加一台 Reolink 摄像头——并通过一个设备 sink 把所有这些数据接入 Apache Iceberg 表（Ecowitt 网关每次直接 POST 62 行，没有中间件）。从 9 月 18 日至今，这座花园已记录下略超过四百万条读数，agent 查询的是这些数据，而不是仪表盘：例如一次前后对比的 SQL 检查显示，浇水后草坪探头的湿度从 29% 跳到 72%，而 soil-ch5 仍然干燥。核心论点是：真正有意思的工作是给 agent 更好的感官和指令，而不是更多的应用——FTPS 上传把摄像头 JPEG 送进了目录，而当广角镜头漏掉了毛虫造成的损害（叶片背面的虫粪）时，他修改了 agent 的提示词，让它检查全分辨率的裁切图以寻找孔洞、啃咬痕迹和害虫，并与前几天对比，因为损害是一个速率，而不是一种状态。

**讨论**: 得票最高的评论指责作者把园艺中人的因素剥离了出去——把妻子和孩子排除在外，让 agent 侵入一个自然领域，还说给一块 2 平方米的菜床插满传感器、称之为「粗俗」，理由只是「能做就做了」；回复要么不以为意（「Zeurpiet」），要么开玩笑说孩子们另有兴趣。一种中间观点认为，把浇水自动化「把乐趣优化掉了」——你会失去培养「每株植物需要什么」这种直觉的过程——但另一些人反驳说，鼓捣本身带来的乐趣就是正当的，人们不必对意义何在达成一致。作者本人现身说明了 agent 真正的动机：一个用于浇水的固定规则引擎总是出错，而这些错误需要上下文（天气预报、上周的反应、叶片外观），所以现在 agent 每天早上运行，读取全部历史，在硬性限制内调整浇水，并记录自己的预测，以便第二天核对；他披露数据层就是 LakehouseBox，他自己的产品，代码在 github.com/jatorre/garden-lake。最有实际价值的讨论串是关于安全的：给 agent 命名的动作并配上硬性上限（「给 2 号区浇水，最多 10 分钟」），再加上过去动作的日志和每日速率限制，因为模型会误读传感器或重复动作——「一株植物能扛过一次糟糕的猜测，但扛不住一个卡住的阀门。」

**值得一读的评论**

## 7. Gemini Decisions API {#story-7}
*HN 第 10 名 · [blog.google](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/) · 398 分 · 122 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50456791)*

这是 Google DeepMind 的产品博客，宣布 Gemini Decisions API 与配套模型 gemini-decision-1：不再逐 token 生成文本，而是在一次前向传播中对候选选项打分，返回 0 到 1 的置信度。单次请求可输入最多 256K token 的多模态内容（文本、图像、音频、视频、PDF），并最多附带 1,000 个问题，支持是/否（noul）、2 到 255 选一（choice）和有序评分标准（score）三种题型。官方称端到端延迟 150-250 毫秒、每百万输入 token 收费 0.10 美元且输出 token 不计费，比 Gemini 3.5 Flash-Lite 搭配 Interactions API 便宜近 5 倍，并称在路由、排序、多模态理解等基准上校准误差最低；文中还列举了 Gemini Notebook 用它做模型路由（日常查询延迟降低最多 40%）、Stitch 快速画布、Google Labs 的 CC 表情选择以及 Search 的 MCP 工具安全层等内部用例。

**值得一读的评论**
- [Topfi](https://news.ycombinator.com/item?id=50461867): 做过快速评测的用户称该模型在多数场景下 Brier 分数比 Jev 低约 4 倍（2-6 倍视任务而定），p50 延迟也低 100 毫秒以上，但端到端成本约为两倍，并认为这是 Gemini 团队相当出色的一次发布。

**值得一读的评论**
- [woodruffw](https://news.ycombinator.com/item?id=50459919): zizmor 的维护者列举了当前的缺口：可复用工作流、复合操作和 Docker 镜像引用都未被锁定，而且该工具的默认行为会剥掉复合操作上的哈希固定，危及外部调用方。

- [Already__Taken](https://news.ycombinator.com/item?id=50459589): 提出哈希固定可能意味着要信任某个仓库任意 fork 中的任意提交，并建议 GitHub 让市场标签变为不可变。

## 13. 面向 x86-64 PC 的通用 Apple Silicon 层 {#story-13}
*HN 第 20 名 · [github.com](https://github.com/tylertms/Stela) · 97 分 · 39 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50460154)*
*原标题: A general purpose Apple Silicon layer for x86-64 PCs*

Stela 是 tylertms 在 GitHub 上发布的开源项目（v0.1.0，GPL-2.0-or-later），一个 UEFI 引导程序，用 AOT+JIT 编译器把 arm64e 代码翻译成 x86-64，覆盖 3000 多种 AArch64 指令编码，并附带一个面向 NVIDIA GTX 16 / RTX 20 及更新显卡的 Metal 驱动（把 Metal 着色器 IR「AIR」直接编译成 Mesa 的「NIR」）。它模拟 Mac mini (M2) 硬件并运行 macOS 27，从而在普通 x86-64-v2 机器上启动 Apple Silicon 版 macOS 和大部分应用。作者强调仍极不成熟：启动成功率低、速度慢、需关闭 Secure Boot、需要 8GB 内存和至少 60GB 的 GPT 分区，且不含任何 Apple 软件，用户需自行遵守 Apple 的许可协议。

**讨论**: 讨论大部分时间花在术语之争上：一方认为这就是「模拟器」，另一方坚持它是把 arm64 指令翻译成本机代码的翻译层（类比反向 Rosetta），而不是模拟一台完整的机器。有人拿 WINE 举例说「模拟」该按效果而非实现来定义，随即被纠正——WINE 不翻译指令，只是 PE 加载器加一套用 Linux API 实现 Windows API 的库；还有人补充 Windows 程序不直接发系统调用而是走 kernel32.dll，而 macOS 一律走 libSystem，只有 Linux 才有直接调用系统调用的惯例。最有信息量的一条是有人在自己的 Mac 上发现 macOS 27.2.1（代号 Golden Gate，xnu-13432.41.4）里仍带着一个完整的 x86_64 内核文件，众人猜测是 Rosetta 2 的 ABI 需求或内部构建测试的残留，但没人给出定论。此外有人质疑项目必要性，称已能在 macOS 上跑起 nxnative；也有人看好用它延长 Intel Mac 的寿命，反方则主张装 Linux 才是正解。

**值得一读的评论**
- [jamesy0ung](https://news.ycombinator.com/item?id=50461286): 第一手发现：macOS 27.2.1 的 /System/Library/Kernels/kernel 仍是 x86_64 Mach-O，附有 sw_vers 与 strings 输出，引发对 Apple 为何保留 x64 内核的猜测。
- [pcwalton](https://news.ycombinator.com/item?id=50463180): pcwalton 指出 Windows 程序从不直接发系统调用而是调用 kernel32.dll，微软还会在系统更新时打乱系统调用号，这正是 WINE 可行的原因。
- [zbentley](https://news.ycombinator.com/item?id=50462505): 对「WINE 也是模拟器」的有力反驳：WINE 不翻译指令，只做二进制格式转换加库层，用「polyfill」形容更贴切。

James Stanley（incoherency.co.uk）描述了如何把一套 CNC 运动系统装到一台 Parkside PPS 30 B2 等离子切割机上——这台机器是他偶然在 eBay 上以 80 英镑拍下的，它采用高频（HF）引导弧引弧，而非更理想的吹回式（blowback）引弧。HF 引弧产生的 EMI 会打断他与 Grbl 控制器之间的 USB 串口连接，而 Grbl 仍在继续执行 g-code，于是他把控制器换成了运行在 Arduino Nano ESP32 上的 FluidNC，并通过 WiFi 与之通信——副作用是任何输入（限位开关、急停、伺服报警）在起弧时全都失效。机架用方钢管焊接，配 3D 打印的 ABS-GF 零件，用 608 轴承当直线导轨，Leadshine easy servo 虽标称 18V 却以 12V 运行；它能切 3mm 钢板，但 4mm 就无能为力，切割在某一轴上带斜度，他怀疑这台二手机器本身可能有故障。

## 19. Sierra Online 简史（2017） {#story-19}
