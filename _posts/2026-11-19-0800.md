## 3. Multiple vulnerabilities in Regexp and String case conversion {#story-3}
*#4 on HN · [ruby-lang.org](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/) · 213 points · 69 comments · [HN discussion](https://news.ycombinator.com/item?id=50554038)*

Ruby's official security advisory for seven memory-safety flaws in CRuby's regex engine and string case conversion, fixed in Ruby 4.0.10, 3.4.13 and 3.3.14. Four advisories credit Stephan Lipp (Ada Logics) and Anthropic for reporting, and the Ruby team says it has proof-of-concept exploits for RCE in several cases; 3.2 and earlier get no fixes. Bugs range from a one-byte heap overflow in case conversion and a double free during regex compilation to out-of-bounds reads in case-insensitive matching and a heap overflow in Regexp#to_s.

**Discussion**: The thread is dominated by Thomas Ptacek's reverse-engineering of the case-conversion bug: he argues Windows-1252 lacks an uppercase form of ß, so upcasing it produces 'SS' and grows the string by a byte, overflowing the buffer if ß is the last character — and Rails multipart POSTs let attackers choose the encoding. That splits into a long sidebar on whether 'SS' or 'ẞ' is 'correct' German (introduced as an option 2017, preferred since 2024, but Unicode stability rules fix the mapping at SS) and repeated calls to reject non-UTF-8 input, with one commenter noting Excel still exports Windows-1252 CSVs in France. A second strand is memory safety: several say this proves C extensions leave even a 'memory-safe' language exposed and demand Rust, while others counter that rewriting CRuby with its JIT and C-extension ABI is a multi-year non-starter and that the snark is unhelpful. A commenter posts a working 4GB Shift_JIS reproducer showing downcase collapsing bytesize to 6 on an unfixed build, plus a related Rails CVE (GHSA-4fqr-96q8-xrfx) to review.

**Worth reading**
- [tptacek](https://news.ycombinator.com/item?id=50554822): Ptacek's detailed theory of the Windows-1252 ß → 'SS' one-byte overflow, including how attacker-chosen encodings reach Rails through multipart POSTs.
- [pentestercrab](https://news.ycombinator.com/item?id=50555722): A concrete reproducer: a crafted Shift_JIS string reports bytesize 4294967302 and, after downcase on an unfixed version, collapses to 6 bytes — proof the bug is real and severe.
- [tptacek](https://news.ycombinator.com/item?id=50556367): Argues no Rails app has a good reason to accept Windows-1252 at all, comparing it to the YAML deserialization surprise where many endpoints silently accepted YAML.

## 5. LLM assisted reverse engineering {#story-5}
*#9 on HN · [slowchronicle.com](https://www.slowchronicle.com/posts/llm-assisted-reverse-engineering) · 176 points · 44 comments · [HN discussion](https://news.ycombinator.com/item?id=50553225)*

A practitioner blog post by ioma8 describing how they now reverse engineer binaries, firmware and websites by pointing an agent at the target instead of reading assembly by hand. Their stack is DeepSeek Harness with DeepSeek v4.1 Flash (with occasional Codex/Luna/Terra), Ghidra via an MCP bridge plus CLI disassemblers, Python with UV for quick probes and Rust for the actual implementations. The core tricks are forcing the agent to write every finding to Markdown files so it survives context compaction, and a public 'hypothesis-debugging' skill that makes a stuck agent log one testable hypothesis to a CSV, design a probe that definitively proves or disproves it, and record the result. They credit this with recent projects that would each have taken years by hand: hacking an Alphasmart NEO, mapping protocols for an EmWave biofeedback device and Sony Alpha cameras (including turning an A7III into a wireless webcam), custom firmware for the Xteink X4 e-reader, an HP printer driver fix for macOS, and a custom Evernote client.

**Discussion**: The thread is broadly enthusiastic and full of matching anecdotes: one commenter reverse engineered their CCTV camera's cloud plugin in about two hours with Gemini (netns + tcpdump, then Ghidra, then letting the model brute-force the auth strings), and another with a DevOps/SRE background and no RE experience cloned an abandoned audio plugin to near 1:1 sound. The sharpest disagreement is over process: Retr0id argues hypothesis-testing is right only for true black-box work, that on most targets the answer is deterministically available and 'guessing loops' are the main annoyance requiring constant babysitting, and that having the model write Unicorn emulation harnesses for bootroms and firmware is a bigger win. Tooling splits between IDA Pro (said to work better with LLMs) and Ghidra, with a reply that the stock Ghidra MCP is 'exceptionally bad' but headless scripting or a custom MCP matches IDA and Ghidra's emulation is stronger. A recurring practical complaint is model guardrails: Anthropic and OpenAI refuse disassembly and APK pulls or flag 'reverse shell' phrasing, prompting several people to use DeepSeek, which refuses far less (one notes its thinking cites Chinese-language restrictions but concludes English requests are fine); others chainsaw around it by clearing context or letting a permissive model start the work. On ethics and law, one camp says unlocking paid Android apps is theft dressed up as privacy advocacy, while another says the joy and skill of RE are lost when an agent does it — countered by people who have the agent document its work so they still learn.

**Worth reading**
- [Retr0id](https://news.ycombinator.com/item?id=50554878): Retr0id, an experienced RE practitioner, says the LLM's guessing loops are the main annoyance and that meticulous deterministic tracing plus LLM-written Unicorn bootrom emulation harnesses is the better pattern.
- [bri3d](https://news.ycombinator.com/item?id=50554454): bri3d reports the stock Ghidra MCP is 'exceptionally bad', but headless scripting or a custom MCP matches IDA, and Ghidra's emulation is notably more robust.
- [georgemcbay](https://news.ycombinator.com/item?id=50556537): Explains why Android apps fall so easily: they are Dalvik/JVM bytecode in a zip, the easiest format to decompile, usually protected only by name obfuscation that barely slows an LLM.

## 7. DaisyRose-27B {#story-7}
*#12 on HN · [radixark.com](https://www.radixark.com/blog/daisyrose-27b) · 191 points · 62 comments · [HN discussion](https://news.ycombinator.com/item?id=50551046)*

RadixArk's first model is a reinforcement-learning post-train of Qwen3.8-27B, trained on 1,200 hand-curated long-horizon agent tasks (built with Eigent AI) in 18 days on 144 H200s, using its open-source Miles RL framework and an in-house async setup with 128 GPUs on rollout and 16 on the trainer. The headline claim is Terminal-Bench 4.1 pass@1 rising from 5.6% to 12.0%, with no regressions on DeepSWE, SWE-Bench Pro, HLE, IFBench or GPQA, plus 37% MFU versus 16% for a Megatron-based open trainer (57% less GPU time, 2x end-to-end throughput, 63,000 GPU-hours total). It ships BF16, FP8 and NVFP4 checkpoints on Hugging Face, and the post also brags about ~944,000 sandboxes run on an AgentENV-based service at 80% lower cost than commercial sandbox providers.

**Discussion**: The dominant thread is benchmaxxing suspicion: several commenters argue that a jump on one target benchmark, trained on only 1,200 curated tasks, is likely to cost general capability, and one commenter who actually ran an 86-task private eval reports DaisyRose scoring 0.898 versus 0.87 for another Qwen3.8 finetune (Qwen 3.8 Swift 1.5) while using twice the VRAM, 1.9M output tokens and more wall-clock time — concluding 'benchmaxxing imo'. Others push back that cross-task generalization from RL is real and that the no-regression table is exactly the answer, with the release author (nblintao) stating no benchmark tasks were in the training data and that regressions were controlled through data and infra design; the skeptics reply that all benchmarks moving up is itself suspicious. Practitioners found the infrastructure side more interesting: the author confirmed dedicated rollout and trainer nodes with RDMA between them, and commenters costed the run at roughly $331,000 on cheap clouds like vast.ai, with a side argument about whether alternative accelerators such as Trainium would help. A separate subthread about frontier labs paying for eval and human-grading data (recruiting emails at $150/hour) turns into a broader fight over whether labs train on customer logs and whether opt-out settings can be trusted. Another commenter lists other post-trained open models (Ember-1, Particle-1, Nex-N2.6) and notes mixed results.

**Worth reading**
- [robertkarl](https://news.ycombinator.com/item?id=50556784): Runs his own 86-task private benchmark: DaisyRose scores 0.898 vs 0.87 for another Qwen3.8 finetune, but at 2x the VRAM, 1.92M vs 1.04M output tokens and 7.8 vs 5.5 hours — his verdict is 'benchmaxxing'.
- [nblintao](https://news.ycombinator.com/item?id=50554933): The author answers the topology question directly: dedicated rollout and trainer nodes with RDMA transfers between them.
- [reissbaker](https://news.ycombinator.com/item?id=50552785): A counter-argument to the 'all benchmarks going up is implausible' camp: imperfect cross-task generalization from more RL environments is exactly how labs expect to hill-climb.

## 8. Dumping an AES key from a MyQ garage opener to stop rebooting when offline {#story-8}
*#13 on HN · [kusha.me](https://kusha.me/blog/stop_myq_homebridge_819lmb_rebooting/) · 112 points · 37 comments · [HN discussion](https://news.ycombinator.com/item?id=50525260)*

A blog post by kusha about the Chamberlain/LiftMaster 819LMB (MYQ-G0303) MyQ Home Bridge, which crash-loops every 5–10 minutes and hard-reboots every 30 minutes when it cannot reach connect.myqdevice.com and connect1.myqdevice.com — even though it is a HomeKit device meant to work locally. DNS sinkholing and TCP RST to a local service only downgrade the failure to a 30-minute watchdog reboot, so the author dumps the device's TLS-PSK AES-128 key: two 560Ω resistors from the Cortex-M4 SWD debug pads (SWDIO to Arduino D8, SWCLK to D9) plus ground, a sketch that halts the CPU, scans flash 0x1F000000–0x1F070000 and reads nvm_rd_myq_serial and nvm_rd_myq_aes_key at 0x1F02F7A8 / 0x1F02F84C. The key and serial then feed a local Mosquitto container from ghcr.io/kushagharahi/myq-homebridge-jailbreak that impersonates the cloud broker (log shows PSK-AES128-CBC-SHA), so /jabout reports internet_connected: Yes and powered_time climbs past 30 minutes without reboots.

**Discussion**: The thread is overwhelmingly hostile to Chamberlain, with commenters saying the company actively fights third-party control to sell subscriptions and blaming a private-equity buyout for the change. The standard advice is to skip MyQ and use a RatGDO (or the free ratgdo firmware on a homemade ESP32 board) against a dumb opener, though several people point out that newer Chamberlain/LiftMaster units ship with Security+ 3.0 and a white learn button, which locks out RatGDO and Tailwind alike — so anyone buying today is stuck. A sideline argument has one commenter preferring cheap Shelly 1 modules, rebutted by a RatGDO user who says only RatGDO reports actual door state rather than blind toggling, which matters for remote 'did I leave it open' checks. Others note the device carries HomeKit certification despite failing local operation, and that the debug pads being left open raises questions about whether secure boot or signed images are used at all. A separate subthread drifts into garage-door spring failures and safety cables.

**Worth reading**
- [kusha](https://news.ycombinator.com/item?id=50525261): The author adds context left out of the writeup: the 819LMB is a HomeKit device that by spec should work fully on the LAN, yet Chamberlain's firmware watchdog forces a hard reboot every 30 minutes without cloud access — and every 10 minutes if the internet is blocked the wrong way.
- [Namidairo](https://news.ycombinator.com/item?id=50554730): Notes that Chamberlain did not flip the OTP security flag to disable JTAG, which suggests secure boot and signed images may also be absent, opening the door to repacking firmware with a custom certificate chain or patching out the reboot.
- [dalyons](https://news.ycombinator.com/item?id=50556608): A concrete correction for buyers: Tailwind, recommended elsewhere in the thread as a non-corporate alternative, explicitly does not work with Chamberlain/LiftMaster openers that have a white learn button (Security+ 3.0).

## 19. The Magic of Partial Evaluation {#story-19}
*#41 on HN · [jimmyhmiller.com](https://jimmyhmiller.com/magic-of-partial-evaluation) · 108 points · 30 comments · [HN discussion](https://news.ycombinator.com/item?id=50550096)*

Jimmy Miller's essay explains partial evaluation as evaluating the statically known parts of a program at build time and leaving only the dynamic parts, then walks through increasingly ambitious examples: a recursive power function, an arithmetic interpreter, and a Brainfuck interpreter whose specialization produces what amounts to a compiled program. That last step is the first Futamura projection: partially evaluating an interpreter with a program yields a compiled program, with the second projection yielding a compiler by specializing the partial evaluator itself. Miller also shows schema validation specialized to a fixed schema for roughly a 5x speedup, mentions James Long's revival of Meta's prepack, and releases his own library for exploring the idea, while admitting prepack was built for practicality rather than beauty.

**Discussion**: The thread starts with a broader claim that understanding recursion, lazy evaluation or unification, and the encoding of imperative state as pure functions are the key shifts in how programmers see languages; several replies ask what that buys you, and others answer with SSA in compilers, easier debugging of value evolution, and the usefulness of multiple equivalent representations. Practitioners point to production systems built on the same idea: NebulaStream's Nautilus compiles C++ operator traces to LLVM or Wasm, Cheerp used exhaustive execution exploration to shrink WebAssembly, Hazel partially evaluates programs with holes, and GraalVM Truffle is repeatedly cited as the mature example. The main pushback is that aggressive specialization can cause code-size explosions, longer builds, and slower code because the result no longer fits in cache, plus binary-compatibility problems when callers are not recompiled. On Zig, the author notes that comptime is not equivalent because a runtime condition cannot be stored to a comptime variable, while another commenter says a comptime code argument to an interpreter works well for this kind of Futamura trick.

**Worth reading**
- [artrax](https://news.ycombinator.com/item?id=50552243): Describes NebulaStream's Nautilus C++ library, which traces generic operator code and compiles the trace to LLVM IR or Wasm for query compilation.
- [fjfaase](https://news.ycombinator.com/item?id=50553770): Reports a concrete failure: specializing an interpreting parser produced a much larger program that compiled more slowly and ran slower, probably because it no longer fit in processor caches.
- [jimmyhmiller](https://news.ycombinator.com/item?id=50552150): The author corrects the Zig comparison: comptime rejects code that stores to a comptime variable based on a runtime condition, so it is not the same as general partial evaluation.
