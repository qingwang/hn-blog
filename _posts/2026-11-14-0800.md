## 1. Ggml v1.0.0 {#story-1}
*#1 on HN · [github.com](https://github.com/ggml-org/ggml/releases/tag/v1.0.0) · 205 points · 33 comments · [HN discussion](https://news.ycombinator.com/item?id=50493062)*

这是 ggml-org 在 GitHub 上发布的 ggml v1.0.0 release notes（发布页部分内容加载失败，但变更日志可读），该库是 llama.cpp 以及一大批本地推理工具底层的 C 张量/算子库。它清理了废弃的公共 API，移除了旧的 DIAG_MASK_INF/DIAG_MASK_ZERO 算子，把 RPC 协议升到 v9（加载更快，并能在连接不可达或握手失败时优雅退出），新增 OCP FP8 与 FP8 KV-cache 支持、可配置的 YaRN truncation，并在后端做了大量优化：CUDA/Metal 的少行量化 matmul 与 MoE 融合、Vulkan 的 Intel prefill FlashAttention、SYCL 设备端 MoE 调度器、OpenCL 上 Adreno 的分解式 FlashAttention、新的 WebGPU kernel、Hexagon/Qualcomm 覆盖，以及 ARM NEON 4x4 simd_gemm 与 SpacemiT RVV kernel。变更条目几乎逐条引用 llama.cpp 的 PR 编号。

**Discussion**: 讨论以赞赏为主：多位长期用户说每次月度升级通常能白捡 5%–10% 的速度提升，并称 ggml/llama.cpp 是「AI 界的 Linux」，在只能跑 Vulkan 的老 AMD 卡和 RISC-V 上都可用。也有人泼冷水，说针对特定硬件手写 kernel 的专用推理引擎会快得多，但若不打算逐个评估引擎，llama.cpp 依然是最稳的通用选择。话题随后偏离到 ggml.ai 官网的极简设计上，一方嫌它毫无设计感、连项目做什么都不说，另一方认为极简正是其哲学、比又一个「Claude 味」的落地页清爽得多。还有人调侃「以自己名字命名库」（GG 即 Georgi Gerganov），评论区搬出 Linux、djgpp、MZ 文件头等先例；另有一条指控把 CLI 到 server 的 HTTP 路由说成「遥测/监视用户」，基本无人接茬。

**Worth reading**
- [jacquesm](https://news.ycombinator.com/item?id=50494080): 实测一次月度升级：5 万 token 的提示跑完从 4:22 降到 3:59，prefill 是主要受益部分。
- [dust42](https://news.ycombinator.com/item?id=50494982): 给出反面视角——针对自己硬件定制 kernel 的专用推理引擎要快得多，llama.cpp 的价值在于「一个引擎通吃且稳定」。
- [nvme0n1p1](https://news.ycombinator.com/item?id=50494518): 引述项目「保持代码库尽可能小和简单」的原则，认为官网的极简风格正是这种哲学的延伸，难得地让人耳目一新。

## 3. Terminal borders that don't cost a cell {#story-3}
*#3 on HN · [joshka.net](https://www.joshka.net/cell-borders/) · 213 points · 88 comments · [HN discussion](https://news.ycombinator.com/item?id=50491423)*

Josh McKinney (joshka), a Ratatui maintainer, proposes a terminal protocol that draws thin lines on the edges of cells instead of using Unicode box-drawing glyphs, so panes, tab labels, underlined text fields and chart gridlines no longer consume a row or column. Borders become a per-cell attribute (up to twelve line segments with their own color, width and style), carried in a single DCS command namespace, with a capability query plus DA1 so apps fall back to box characters on unsupporting terminals. He has it working as a roughly 1,650-line patch to Ghostty (built with Zig 0.17, macOS only so far) plus a Ratatui demo branch; each cell uses a 16-bit border ID stored in existing padding, pointing into a shared table of border sets of about 100 bytes each, with a worst case around 10-25 MB if all 65,535 IDs were used. He lists prior art including DECterm ruled lines, SGR 51-65, Win32 console grid flags and IBM 3270 field outlines, and notes none of them offer per-edge color and width.

**Discussion**: The most-repeated alternative is overstrike mode (DECSET 20), letting an app draw border glyphs over existing text cells; commenters note mintty is essentially the only emulator that supports it, and the author replies that overstrike cannot give rounded corners with a correctly filled interior or per-edge colored lines. A larger argument broke out over ambition: one prominent commenter asks why, if you are changing both protocol and terminal, not build a full information-dense UI framework designed for interfaces, while others counter that the terminal's constraints are exactly why people use TUIs, and that the high cost of extending the protocol is what keeps cheap multiple implementations feasible. tmux was the biggest technical objection, with one commenter insisting per-cell attributes should survive multiplexers as other CSI sequences do; the author answers that tmux drops unknown DCS and that real support means storing and redrawing extra per-cell state, perhaps a thousand lines, and that a multiplexer without support should answer DA1 itself so apps fall back. An ex-Alacritty maintainer says he would likely disable the feature rather than ship a UI that renders differently per terminal; the author stresses the Ratatui work is an isolated proof-of-concept that would never ship as a default, expects adoption in Ghostty, Rio and Kitty but never Terminal.app, and jokes that he mostly wants the capability, not this particular spec. A few readers simply prefer the fallback screenshots, saying the native borders remove the breathing room they like, and one raises Unicode width problems for CJK users and asks whether a border attaches to a cell or a grapheme cluster.

**Worth reading**
- [favori995749721](https://news.ycombinator.com/item?id=50493340): Points out that box-drawing characters are East Asian 「Ambiguous」 width, so CJK-configured terminals already misalign frames, and asks the spec to define whether borders attach to cells or grapheme clusters given continuation cells and ZWJ emoji.
- [joshka](https://news.ycombinator.com/item?id=50492475): Directly answers the tmux objection: tmux drops DCS sequences it does not recognize, and full support means tracking, rendering and redrawing per-cell border state across all the edge cases.
- [nixpulvis](https://news.ycombinator.com/item?id=50494092): A former Alacritty maintainer predicts uphill resistance to adopting this there and explains why, as an app author, he might rather disable it than accept per-terminal rendering differences.

## 4. FAA issues national ground stop – lifted 4.5 hours later {#story-4}
*#4 on HN · [nbcnews.com](https://www.nbcnews.com/news/us-news/faa-orders-nationwide-ground-stop-departing-flights-reasons-safety-rcna609247) · 1,506 points · 1,154 comments · [HN discussion](https://news.ycombinator.com/item?id=50489641)*

NBC News report on the FAA's nationwide ground stop of all departing flights, issued at 3:54 p.m. ET on Friday Nov 13, 2026 and lifted at 8:15 p.m. ET, after more than 7,000 flights were canceled and Reagan National and O'Hare ran out of gate space. Transportation Secretary Sean Duffy said routers in the decades-old air traffic control system 「got overloaded with data」, causing instability in radar and communications data at en route centers and TRACONs; DHS's Markwayne Mullin said there was no evidence of a cyberattack. Duffy used the incident to push for $50 billion to overhaul ATC, against $12.5 billion Congress approved over five years, and the article notes this is only the third nationwide grounding since 9/11 (the others being 2001 and the January 2023 NOTAM failure).

**Discussion**: The thread is dominated by early speculation, then sharpens once commenters surface reporting that a software update to the L3Harris-run private communications network made the system reboot and crash. Several engineers seized on the timing — a Friday, roughly 3 p.m. — as evidence of a botched production deploy, and one commenter quoted Mullin saying new equipment 「was overwhelming the older system」 while others noted Duffy spent the press conference blaming Congress and asking for money rather than explaining the fault. A competing theory blamed the FAA's newly expanded AI tool, SMART, from contractor Air Space Intelligence (up to $875.9 million contract, rolled out to all 22 centers days earlier), though commenters flag both FAA and ASI statements that SMART only suggests routes and is 「completely disconnected」 from the failed equipment. Aviation-knowledgeable commenters pushed back on the panic: one linked the 2009 DOT inspector-general report on an FTI network outage, another described being airborne during a 2004 Southwest US ATC radar/radio failure, and others argued the 40-year-old legacy system is battle-tested while upgrades are what break things. There is no consensus on root cause, but the dominant view is a careless upgrade rather than an attack, amid a loud minority trading conspiracy theories tying it to the Microsoft outage the previous day, NOAA radar outages and Friday the 13th; scattered commenters posted live flight-tracking observations and the actual ATCSCC advisory text as the stop was lifted.

**Worth reading**
- [fooey](https://news.ycombinator.com/item?id=50491855): Cites Wall Street Journal and CBS reporting that the outage hit an L3Harris-operated telecom network carrying controller radio frequencies, and that an update caused the system to reboot and crash — the most concrete cause offered in the thread.
- [amluto](https://news.ycombinator.com/item?id=50490420): First-hand account from a passenger airborne during the September 2004 Southwest US ATC outage, with the detail that the failure was an application error rather than the famous Windows GetTickCount() overflow.
- [hysan](https://news.ycombinator.com/item?id=50492744): Live reaction from someone stranded: the White House press conference started ten minutes late and spent its first fifteen minutes blaming Congress instead of giving travelers actionable updates.

## 5. Unsloth Qwen3.8-27B Quantizations – Dynamic v3.1 Update {#story-5}
*#5 on HN · [unsloth.ai](https://unsloth.ai/docs/models/qwen3.8) · 108 points · 21 comments · [HN discussion](https://news.ycombinator.com/item?id=50491980)*

Unsloth's documentation page for its Qwen3.8-27B GGUF and NVFP4 quants, updated November 11 2026 with a new Dynamic V3.1 (preview) algorithm that the team says gains 5-10% accuracy at the same file size across Terminal Bench 2.1, DeepSWE v1.1, LiveCodeBench v6, GPQA Diamond, MMLU-Pro and AIME25. Quants from 2-bit to 6-bit are rebuilt; 3-bit UD3 is left alone because it already matched UD3.1. The post also rebuts a competing GSQ-RCO/ISTA benchmark, arguing ISTA ran a single trial (and a likely 96K context budget) versus Unsloth's 14 trials at 128K, which put average accuracy recovery at 93-96% rather than the claimed 100%. Separately, NVFP4 quants are ~1.5x faster than BF16 with 92-97% top-1 recovery, but need Blackwell GPUs and currently only run in vLLM (SGLang v0.5.19 for the FP8 lm_head).

**Discussion**: The thread is mostly comparison shopping rather than benchmarking: people ask how these quants stack up against TensorFold's 27B builds, against Bonsai 2, and against the older Dynamic v3.0, with no definitive answers posted. Several commenters describe the low-end workflow the model enables — running a Q4/Q5 quant CPU-only in llama.cpp overnight for a document review or web-research report, accepting minutes of prompt processing and single-digit tokens per second in exchange for not paying per token. Bonsai 2 (also built on Qwen3.8-27B) draws fire: two users say it fails basic multi-needle retrieval despite its benchmarks, while another notes Bonsai packs more into fewer GB via extra fp16 block-weight tuning but is a one-off release, whereas Unsloth's method applies to any off-the-shelf open model. A side argument questions whether local inference makes economic sense at ~25c/kWh versus cheap cloud APIs, with privacy, dedicated-server rental and very low-wattage boxes like the GB10 offered as counterweights. The strongest open technical question — why every parameter is quantized at the same rate rather than weighting by importance — went unanswered.

**Worth reading**
- [3eb7988a1663](https://news.ycombinator.com/item?id=50494245): First-hand report running a Qwen3.8-27B quant CPU-only in llama.cpp: a 6,000-word markdown file took ~10 minutes before any output, then ran fine overnight — usable for batch review, not vibe coding.
- [sroussey](https://news.ycombinator.com/item?id=50494887): Asks the pointed methodological question the post never addresses: how do you know which parameters matter, and why quantize every parameter identically instead of more aggressively where it hurts least?
- [jedbrooke](https://news.ycombinator.com/item?id=50494211): Explains the Bonsai 2 vs Unsloth tradeoff — Bonsai adds fp16 block-weight tuning per 32 parameters to pack more into few GB, but you wait for its next release, while Unsloth's recipe generalizes to any open model.

## 6. What happened to 3Com? {#story-6}

**Worth reading**

## 7. Show HN: Live map of U.S. flights during tonight's FAA nationwide ground stop {#story-7}
