## 2. XNU Linux: Full OS X GUI Userspace on Linux {#story-2}
*#2 on HN · [github.com](https://github.com/AFK-surf/xnulinux) · 202 points · 90 comments · [HN discussion](https://news.ycombinator.com/item?id=50607261)*

A GitHub project (by Heyang Zhou) that builds Apple's open-source XNU kernel (xnu-12377.121.6) from published sources and loads it as a kernel module, xnu.ko, inside an unmodified arm64 Linux kernel, with a companion fki.ko module lending it CPUs, memory, timers, files, network and GPU. XNU runs the CPU and MMU directly with no hypervisor, so macOS processes sit alongside Linux processes on the same cores; with a stock Ubuntu kernel, insmod xnu.ko boots a macOS 27.2.1 system disk made by Apple's own installer to loginwindow, WindowServer, Dock, Finder, Safari and Chrome, in 31–48 s. It currently requires an Apple Silicon Mac running an arm64 Linux VM (krunkit or tart), 4K pages, 16 GB RAM, and is a stopgap in places: the cryptex is merged into the system volume, AMFI is patched, SIP relaxed, and memory access is slower than a native VM because of 4K vs 16K pages. Metal runs on a metal2vulkan plugin over Mesa Venus to the host GPU, with lavapipe as CPU fallback.

**Discussion**: The thread splits between admiration and worry about Apple's reaction. Several commenters predict a takedown, citing Stela being pulled from GitHub and Nintendo's DMCA over console keys, while others argue Apple only ever chased resellers, not hobbyists, that most of the code is XNU (open source) plus community projects, and that the project needs genuine Apple hardware anyway. A recurring correction is that the 'Apple Silicon only' framing is softer than it looks: people point out PAC is a standard Armv8.3 extension used well beyond Apple and that XNU's vmapple kernel needs little to boot, so porting to other arm64 or even x86 machines is mostly a drivers problem — though others note Apple-specific extensions and page-size constraints. On motivation, skeptics ask 'why not just buy a Mac', while defenders cite cross-platform build/test farms for macOS and iOS, the lack of eGPU, Vulkan and CUDA support on modern Macs, and plain curiosity; a few warn that running Xcode or macOS apps on non-Apple hardware could violate the EULA. A side thread drifts into speculation about a future where the OS is shipped encrypted with hardware-bound keys, and commenters trade jokes about the Mac-inside-Linux-inside-Mac stack and Brad Fitzpatrick's two-VM limit.

**Worth reading**
- [m132](https://news.ycombinator.com/item?id=50608144): Corrects the assumption that PAC means Apple-only: it is a standard Armv8.3 extension, widely implemented, mostly encoded in HINT space (NOPs where unsupported), and many AArch64 distros already ship PAC-built binaries that run on Raspberry Pi-class SoCs.
- [bartvk](https://news.ycombinator.com/item?id=50608121): Notes the buried lede: the project explicitly works only on an Apple Silicon Mac running an arm64 Linux VM via krunkit, which undercuts the 'macOS on any PC' reading.
- [sneak](https://news.ycombinator.com/item?id=50607690): Argues Apple has historically ignored what people do with hardware they bought, and that this may not even breach the EULA on a first pass — the patched AMFI files could be distributed as self-applied diffs.

## 3. A Beginner's Guide to Local AI with Inkling, Qwen, and Unsloth {#story-3}
*#3 on HN · [gpupartner.com](https://www.gpupartner.com/blog/beginners-guide-local-ai-inkling-qwen-unsloth) · 450 points · 181 comments · [HN discussion](https://news.ycombinator.com/item?id=50603845)*

A gpupartner.com walkthrough for setting up a local ChatGPT/Claude substitute on a Windows PC: install Unsloth Desktop, download a 4-bit quantized Qwen3.8-27B (UD-Q4_K_XL, ~18GB) sized to your VRAM, set a 128K context, and enable LAN sharing so the whole household can use it. It claims ~10-15 minutes of setup (minus downloads), gives a VRAM-to-model table from 8GB cards up to the 96GB RTX PRO 6000, and adds a section on Thinking Machines Lab's Inkling 2 Mini (26.4B params, Apache 2.0, 1M context, released Nov 17 2026, 17.6GB quantized) versus Inkling 2 Small (594B params, smallest file 171.7GB, unified-memory only). The author's own machine is an RTX 5090 with 32GB VRAM.

**Discussion**: The thread splits over whether local AI is practical now or a premium hobby. One camp calls this the 'plasma TV phase' — heavy, expensive, five years from everyday usefulness — and does the arithmetic: a $5-10k GPU versus a $20/month subscription, or $6,500 on Newegg versus 16 years of Claude Pro. The other side argues the bitter lesson and shrinking models mean local is already good enough for most tasks; several people report running Qwen3.8-27B or Qwen3.8-Flash-Next at 30-60 tok/s on 12-16GB cards by offloading MoE experts to system RAM, on hardware as cheap as a $300 used Tesla P40 or a ~$2,200 AMD R9700. The strongest pushback comes from practitioners who say low-bit quants quietly degrade: a task that Opus 5.5 finishes in a tenth the tokens and a twentieth of the time leaves the local model flailing for hours, so 'free' isn't cheaper if you're getting work done. Others correct the article's framing — Unsloth Desktop also runs on Linux and macOS (with AppImage/.deb downloads and a Docker image), and commenters say the guide's assumptions about needing 32GB VRAM for a 35B MoE or 16K starting context are overly conservative. Unsloth's maintainer shows up in the thread answering setup questions directly.

**Worth reading**
- [tacoman](https://news.ycombinator.com/item?id=50606063): Suggests a used Nvidia P40 (24GB, ~$300 on eBay) as the budget entry point, reporting Qwen 3.8 27B UD-Q4_K_M at 14 tok/s via llama.cpp on Ubuntu — 'very useful, not just a toy'.
- [Aurornis](https://news.ycombinator.com/item?id=50607197): First-hand reality check that cheap 2-3 bit quants introduce subtle errors the model then wastes tokens fixing, and that even 5-6 bit Qwen3.8-Flash-Next can burn millions of tokens on a task Opus 5.5 finishes in a fraction of the time and tokens.
- [hypfer](https://news.ycombinator.com/item?id=50608410): Blunt critique of the guide's advice, arguing that 24GB VRAM comfortably fits Qwen3.8-27B at q4 plus 170K+ of q8 context, and that starting at 16K context is not a useful configuration.

## 4. Masullo on the Riemann Hypothesis {#story-4}
*#5 on HN · [johncarlosbaez.wordpress.com](https://johncarlosbaez.wordpress.com/2026/11/22/masullo-on-the-riemann-hypothesis/) · 190 points · 121 comments · [HN discussion](https://news.ycombinator.com/item?id=50598441)*

John Baez's blog post is a plain-language sketch of Alessandro Masullo's 940-page draft proof of the generalized Riemann Hypothesis, posted by Ravi Vakil on November 20, 2026 — the same day Levent Alpöge and Claude released a 17-million-line Lean formalization. Baez explains Masullo's strategy as a Connes-style trace formula on the idele class group: a spectral side summing over zeros of Hecke L-functions, a geometric side computed prime-by-prime where Poisson summation kills all but finitely many primes, and a test function approximated by smooth compactly supported cutoffs so Montel's theorem can pass to a holomorphic limit — notably without Weil's positivity criterion. Baez also lists early objections: an AI-assisted review organized by Eric Naslund finds the theorem gives 0 instead of log 2 at a test function concentrated near the prime 2, page 444 appears to wrongly transfer a Schauder-basis fact to Markushevich bases, and Chapter 13, where GRH should be deduced, is still placeholders; Brian Conrad says the manuscript is under major revision and was released early only because Alpöge's claim forced it.

**Discussion**: The thread barely discusses the mathematics; it is dominated by a fight over AI credit. One camp argues Anthropic dumping an unreadable 17M-line Lean proof with no released model or paper is anti-human and scooped a man's 12 years of work, while the other replies that the Lean proof was machine-verified within a day or two and that its length reflects formalizing standard mathematics that simply was not in Lean yet. A recurring dispute is whether such AI results are 'brute force' that produces no new theory — countered by people pointing to Grothendieck's insistence on theory-building, and by others who say AI proofs are large engineering projects whose insight will be mined afterward by agents and mathematicians. Several commenters push back on the sympathy framing entirely, noting Masullo's draft is a hasty, incomplete work with hundreds of reported issues that would have drawn no attention without the Alpöge controversy. Technical correction threads focus on verification: a passing Lean build does not show the formal statement matches GRH, since the specification itself can be wrong, and that mismatch is the real delay.

**Worth reading**
- [nl](https://news.ycombinator.com/item?id=50607641): Explains the 17M lines are largely formalizations of already-known mathematics that had never been put into Lean, not 17M lines of novel argument.
- [hasyimibhar](https://news.ycombinator.com/item?id=50608719): Draws the formal-verification distinction practitioners care about: a correct Lean file only proves the formal statement, and someone still has to show that statement is GRH — the same spec-mismatch problem seen with TLA+.
- [xamuel](https://news.ycombinator.com/item?id=50607004): Strong counter-argument to the sympathy narrative: the draft got attention only because the AMS president broadcast it and Brian Conrad reportedly endorsed it, and plenty of others have spent 12+ years on RH without tears.

## 7. Yes, 17M lines of Lean is a lot {#story-7}
*#10 on HN · [micjm.com](https://micjm.com/blog/yes-17m-lines-of-lean-is-a-lot/) · 30 points · 32 comments · [HN discussion](https://news.ycombinator.com/item?id=50607668)*

A short blog post by micjm testing whether the 17 million lines of Lean behind a recently announced Riemann hypothesis proof is really as huge as it sounds. Using Mathlib's collection of famous proofs (259 of over 1k have Lean formalizations) and Reservoir's index of 938 Lean packages on GitHub, it finds the extreme cases are almost all AI or script-generated: an 88m-line work-in-progress CFSG proof, a 36m-line LeanBridge project that is ~98% database-checking scripts (about 500k handwritten lines), and Anthropic's 27m-line Fermat's Last Theorem proof built on Kevin Buzzard's human FLT project of roughly 60k lines — about 450x longer. Verdict: yes, 17m lines is a lot.

**Discussion**: The dominant thread is verbosity versus elegance: several commenters argue LLMs can produce correct proofs but do not compress information, duplicating material everywhere, while others reply that elegance is exactly information compression or has an artistic component that has nothing to do with correctness. A second argument asks whether length even matters, since Lean checks down to primitives and a machine-verified proof is verified regardless — countered by the point that the Lean proof restates dozens of established mathematical theories a human like Masullo can simply cite, and by the worry that nobody will understand why the result holds. Line counts are treated as a live scoreboard: one commenter notes a 'shrink' effort taking the proof from 17m to 13m lines (rh-shrink.github.io, possibly 11m soon), while others report it rebounding to 18m and that GitHub cannot render a commit that large. Elsewhere the thread drifts into AI-and-labour politics, with one camp saying the industry's pitch was displacing mathematicians and another calling that framing villainous and insisting the real promise is power tools for experts; a few joke about brute force, Perl, and God creating the universe in 22 billion lines of Lean.

**Worth reading**
- [markasoftware](https://news.ycombinator.com/item?id=50608699): Argues that Anthropic's 27m-line FLT proof — longer than the 17m Riemann one despite resting on Wiles' 129-page proof — implies an informal Riemann proof could be far shorter than Masullo's.
- [adgjlsfhk1](https://news.ycombinator.com/item?id=50608462): Reports the proof is being actively shrunk, down to 13m lines at rh-shrink.github.io with a decent chance of 11m the next day.
- [Incipient](https://news.ycombinator.com/item?id=50608535): Raises the key correctness question: since Lean expands to base primitives, the proof's length may not affect the validity of the result, only our ability to understand why it is true.

## 8. GL.iNet Security Notice 2026-11-20 {#story-8}
*#11 on HN · [gl-inet.com](https://www.gl-inet.com/en-us/blogs/blog/glinet-security-notice-2026-11-20) · 174 points · 85 comments · [HN discussion](https://news.ycombinator.com/item?id=50604988)*

GL.iNet published a customer advisory saying it found a vulnerability in its cloud remote-management service on November 20, 2026, which an unauthorized party exploited to access and install malicious software on some routers and KVM devices. The cloud hole is now patched and that infection path blocked, but the fix does not clean already-infected units — users must install new stable firmware (e.g. 4.11.1+ for GL-MT3000/MT6000, 4.8.4+ for GL-AX1800/GL-SFT1200, 1.10.3+ for Comet RM1/RM10/RM4PE) without a factory reset. The indicator of compromise is a running process matching 'crond -i /tmp/.log'; GL.iNet also links an unofficial community scanning tool, says it is emailing affected cloud-account holders, and that the scope — including whether attached computers of KVM users were hit — is still under investigation.

**Discussion**: The dominant reaction is 'flash upstream OpenWrt', with several GL-MT6000/Flint 2 owners saying they did so on day one and are glad now; others caution that many GL.iNet models run vendor forks with proprietary Qualcomm/MediaTek blobs upstream won't take, that stock images ship badly outdated OpenWrt, and that at least one owner's GL-BE9300 has no official OpenWrt release at all. Commenters split on how exposed non-cloud users were: several insist the cloud client is off unless you bind an account and that disabling it via '/etc/init.d/gl-cloud disable' or the web UI is enough, while others report it enabled by default out of the box, and one poster links a GL.iNet forum thread arguing devices have been compromised since around December 2025. A sub-thread pushes back on the OpenWrt cure-all: one commenter lists concrete upstream defaults he considers weak (plaintext-HTTP LuCI, persistent DHCP DUID, FORTIFY_SOURCE=1, BusyBox without PIE) and says he moved to a NixOS gateway plus separate APs, drawing the rebuttal that a LAN admin UI doesn't need HTTPS and that many OpenWrt defaults are tunable. The KVM line is treated as the real worry, since there is no OpenWrt replacement and some suspect a PiKVM derivative; the thread drifts into router-shopping (UniFi, pfSense/OPNsense, MikroTik, eero) and a disputed claim that the Flint 4 is FCC-banned.

**Worth reading**
- [iceboundrock](https://news.ycombinator.com/item?id=50606741): An owner of the GL-BE9300, which has no official OpenWrt build yet, says the cloud service was on by default even without a bound account and gives the SSH command '/etc/init.d/gl-cloud disable' as the workaround.
- [dsissitka](https://news.ycombinator.com/item?id=50605891): Links a GL.iNet forum thread titled 'Found other malware while looking for 11-20 evidence', suggesting compromise dating back well before this incident (a reply pins it to December 2025).
- [jgil](https://news.ycombinator.com/item?id=50607985): A detailed counter-argument that vanilla OpenWrt is not automatically safer, citing plaintext-HTTP LuCI with no HTTPS redirect, a persistent DUID sent to the ISP, and binaries built without PIE/ASLR, with source links.

On the constructive side, people propose additions (local vs cloud models as the currently most important distinction, finer-grained labels for which parts of a product used AI) and the author himself suggests using it in READMEs, e.g. declaring a project 'AI:R level' or capping contributions at AI:R for new contributors and AI:W for trusted ones; one commenter links his own AC4A project, an agent access-control system likewise borrowed from Unix file permissions.
