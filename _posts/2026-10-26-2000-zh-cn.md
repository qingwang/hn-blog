## 1. 微软宣布 Type Server Protocol，扩展 Language Server Protocol {#story-1}
*HN 第 1 名 · [github.com](https://github.com/microsoft/pylance-release/blob/main/docs/tsp/type-server-protocol.md) · 93 分 · 42 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50248371)*
*原标题: Microsoft Announces Type Server Protocol, Extension of Language Server Protocol*

这是 TSP 的文档，TSP 是一种 JSON-RPC 协议，客户端用它向「类型服务器」请求 Python 类型分析数据，发布于 pylance-release 仓库。它沿用 LSP 的约定（Position/Range、字符串 URI），把方法归入 typeServer/ 命名空间，并定义了通过 semver 进行的版本协商、用于让过期结果失效的快照 ID，以及三类查询——计算类型、声明类型和预期类型——外加导入解析和搜索路径。可选的「多连接」模式允许客户端在主 stdio/Node-IPC 连接之外另开只读 IPC 通道；它目前处于 0.x 版本线，因此次版本更新可能带来破坏性变更。公告帖讲的是 Pylance 与 Pyrefly 在 VS Code 中的集成，不过提交的链接本身只是一份 Markdown 规范。

**讨论**: 这个帖子基本没怎么讨论协议本身，而是变成了一场关于 Python 的爱恨之争：一位评论者称 Python 是「语言和生态的双重灾难」，总在不断补上其他语言几十年前就有的东西；回复则分成两派——一派赞同（打包、virtualenv，以及 activate/PYTHONPATH 那套 hack 是被点名最多的具体抱怨），一派辩护（对新手友好、NumPy/SciPy、标准库、「worse is better」）。就这条新闻本身，最尖锐的批评针对命名：评论者认为「Type Server Protocol」为一个只面向 Python 的东西占用了通用命名空间，尤其考虑到提出者正是 LSP 的缔造者；也有人指出该设计是 Python 专有的——结果类型里没有 for-all binder——因此不太可能推广到 Elixir 等其他动态语言；反方观点是它位于 pylance 项目之下、又是在 Python 开发者博客上公布的，所以是标题有误导性，而非微软的本意。讨论中还冒出两条具体更正：basedpyright 的维护者已公开批评 TSP，而 Astral 的 Ty 显然仍计划支持它；另有一位评论者质问，为何新协议沿用了 LSP 的 UTF-16 字符偏移，而不是借机纠正这个决定。其他人则单纯困惑于 LSP 是否已经覆盖了「查询某点类型」这类请求，给出的解释是 TSP 让类型检查器（Pyrefly、Pyright）可以与编辑器前端解耦。

**值得一读的评论**
- [nikolatt](https://news.ycombinator.com/item?id=50249708): 给出了 basedpyright 维护者对 TSP 的详细批评链接，并指出 Astral 的 Ty 仍计划支持它，从而呈现了生态反应的双方立场。
- [anonymous908213](https://news.ycombinator.com/item?id=50249007): 认为这个名字为一个只面向 Python 的规范占用了通用协议命名空间，而考虑到它出自 LSP 的创造者之手，这就尤其奇怪。
- [0cf8612b2e1e](https://news.ycombinator.com/item?id=50249301): 指出新协议沿用了 LSP 的 UTF-16 字符偏移，错失了纠正这一选择的机会。

## 2. Sebastian Raschka 的从零构建推理模型视频课程 {#story-2}
*HN 第 2 名 · [magazine.sebastianraschka.com](https://magazine.sebastianraschka.com/p/building-reasoning-models) · 398 分 · 55 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50245138)*
*原标题: Sebastian Raschka's from-scratch video course on building reasoning models*

Sebastian Raschka 发布了他配合新书 Build a Reasoning Model (From Scratch) 的八集讲座视频（11 小时以上）。课程从 Python/PyTorch 中预训练的 Qwen3 0.6B 权重出发（环境用 uv 搭建），先构建一个数学答案验证器并在 MATH-500 上评估，然后实现推理时扩展（temperature、top-p、自一致性、对数概率打分、自我精炼），以及通过简化版 GRPO 循环实现带可验证奖励的强化学习；只有后面的训练实验才真正需要 GPU，前面的示例在 CPU 或 Apple Silicon 上就能跑。他把推理模型定位为 agent harness 内部的引擎，并指出当前大多数 LLM 都是推理强度可调的推理模型。

**讨论**: 这个讨论帖几乎一边倒地称赞 Raschka 的教学：多位读者表示，他的书 Build a Large Language Model (From Scratch) 及其推理模型续作让 attention、autograd 和反向传播终于变得清晰，还有几个人说自己是配合学习小组或视频讲座一起读的。真正的争论在于用途：一位评论者（hypfer）说，他看不出这门课除了满足好奇心之外是给谁看的，认为视频教程对任何真正想训练模型的人都不够用，并把这件事称为靠贩卖一种身份认同来变现个人品牌的生意——这招来大量反驳，包括一位职业做模型后训练（post-training）的评论者，他说 Raschka 的书教给他的东西比任何其他来源都多；其他人则指出视频是免费的，而且通过动手构建来学习本身就是重点。一个很长的子讨论探讨是否存在超越玩具练习的爱好者路径：建议包括对小型或中型开源模型做 LoRA 微调、为真实问题训练一个小分类器，以及转向数据/模型基础设施类岗位而不是试图在算力上竞争；有几个人承认，没有像样的 GPU 资源，家里做的实验基本只是噪声。一个顺带比较 Raschka 与 Karpathy 的支线被纠正了——两人是同一代人，CS231n 和 Raschka 的第一本机器学习书都在 2015 年出现。大致共识：教学极其出色、材料免费，唯一的怀疑是它对个人学习者来说是否能通向任何实用之处。

**值得一读的评论**
- [libraryofbabel](https://news.ycombinator.com/item?id=50249391): 认为从零实现类教程的意义在于理解你所实际使用的那一层之下发生了什么（就像 Crafting Interpreters 那样），并指出你是在实现真正的 RLVR 训练——也就是 2025–26 年编程和数学能力提升背后的技术——而不只是读一读。
- [danielmarkbruce](https://news.ycombinator.com/item?id=50248438): 一位在工作中做模型后训练的评论者说，他从 Raschka 的 LLM 书里学到的东西比任何其他来源都多，直接反驳了这些材料不实用的说法。
- [kadoban](https://news.ycombinator.com/item?id=50249835): 认为对爱好者来说现实的收获是后训练（post-training）以及对现有的小到中型模型用自己的数据做 LoRA 微调，这比预训练所需的算力少得多。

## 3. CSS-Tricks 有了新东家 {#story-3}
*HN 第 3 名 · [css-tricks.com](https://css-tricks.com/css-tricks-has-a-new-owner/) · 262 分 · 61 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50245831)*
*原标题: CSS-Tricks has a new owner*

Geoff Graham 已在 CSS-Tricks 工作 12 年，他宣布自己已从 DigitalOcean 手中买回该网站，并将把这作为自己的全职工作。他回顾了网站的历史——Chris Coyier 于 2007 年创立，2022 年将其出售给 DigitalOcean——并说明了计划：恢复真正的广告套餐、让 newsletter 回归、重启客座写作投稿表单、推出会员和周边商店、上线面向初学者的 HTML/CSS 课程，以及大致在大多数周发布一到两篇新文章，而不是此前的发布节奏。

**讨论**: 讨论帖气氛温暖，但对商业模式感到焦虑。被提及最多的担忧是，LLM 问答引擎正在掏空教育类前端网站赖以生存的流量和广告收入——Tailwind 的裁员及其被 Shopify 吸纳被反复举为警示案例，Stack Overflow 也被一并提起。对此，几位从业者反驳说，CSS 恰恰是 AI 最薄弱的领域：一位设计系统工程师表示，模型在一年内对经浏览器检查的 CSS 已有很大进步，但仍会犯低级错误；另一些人则坚持认为，大多数 B2B 和内部仪表盘只需要不冒犯的设计，所以市场无论如何都会萎缩。在变现方面，一位评论者建议在免费内容之外提供付费咨询或付费通话（免费/便宜/昂贵的阶梯），Simon Willison 则认为对赞助商来说受众质量胜于数量——不过另一人回复说，高价值的技术读者如今直接问 LLM，永远不会点广告。大家对 Graham 普遍抱有好感，认同 DigitalOcean 冷落了该网站，但也怀疑一个小型独立博客在 2026 年如何养活一个团队。

**值得一读的评论**
- [vanadium](https://news.ycombinator.com/item?id=50248919): 一位前 DigitalOcean 员工证实，该网站在 DO 内部优先级低得令人沮丧，并表示很高兴它回到了一位关心这门手艺的人手中。
- [gkoberger](https://news.ycombinator.com/item?id=50247835): 称 DigitalOcean 当年以 400 万美元买下 CSS-Tricks，如今很可能以接近 0 美元的价格卖回，而不是将其关停——给出了这笔交易的具体数字。
- [dfabulich](https://news.ycombinator.com/item?id=50249039): 对赞助商驱动的模式提出反驳：高价值的技术受众如今直接问 LLM，几乎从不点广告，而他看不到这一趋势有逆转的迹象。

## 4. 仍能在 Windows 11 上运行的最古老 GUI 应用程序 {#story-4}
*HN 第 4 名 · [blog.enlyth.com](https://blog.enlyth.com/posts/oldest-windows-gui-app-win-11/) · 82 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50248055)*
*原标题: Oldest GUI application that still runs on Windows 11*

enlyth 的一篇博客文章，寻找能在当前 Windows 11 上运行的、未经修改的最古老 GUI 程序。由于 64 位 Windows 砍掉了 NTVDM、无法运行 16 位软件，这条线索最终指向早期 Win32s 中日期为 1993 年 2 月 22 日的 FREECELL.EXE，它能正常运行、游戏体验完美（已有 33 年 8 个月）；在 Internet Archive 上翻查 NT 3.1 的预发布版本则走进死胡同（1991 年的一份 PE 格式草稿，以及 1992 年年中之前使用 cdecl 的构建版本，导致 API 参数被弹出两次），直到 Build 347（1992 年 11 月 16 日）的 CDPLAYER.EXE 才跑通，因为它链接的是系统 crtdll.dll，而 Windows 11 仍在 SysWOW64 中提供该文件——不过它需要一个小小的 cdemu.dll 来伪造 CD-ROM 驱动器并输出音频。作为一个自己承认的作弊手段，基于 DOS 的 otvdm 可在 Windows 11 上运行 Windows 1.01（1985 年 11 月 15 日）的 REVERSI.EXE。

**讨论**: 整个讨论串分裂为怀旧与反驳两派。最高票评论哀叹菜单栏和原生 Win32/C 开发败给了「移动优先」设计与 Electron 外壳，跟帖者则浪漫化拟物化设计与 1990 年代微软/苹果的可用性研究——但另一些人纠正了这一前提，指出 Windows 10 相比 8 是巨大进步，且仍有大量应用带有菜单栏。第二个话题群争论 2026 年写新的 Win32 应用是否仍然合理：一位开发者报告说，一个 Win32 图片查看器响应非常快，但可读性远不如 React；另一位乐于用 AI 配合 C 和 WinAPI；还有一位主张使用跨平台工具包（EGUI、Qt），因为「看起来原生」不如「不在操作系统之间筑起壁垒」重要——随即有人反驳，称自己在乎应用是否表现得原生（键盘快捷键、macOS 辅助功能集成）。一个岔开的话题问 1980 年代的 X11 二进制程序能否通过 Xwayland 运行；共识是不能，未经修改的 1980 年代二进制不行，只有 BSD a.out/4.3BSD ABI 支持以及仍在打补丁的 SCO OpenServer 被认为是可能打破 1992 年 11 月这个日期的现实途径，另有一场关于动态链接 libc 跨发行版破坏 Linux 二进制程序有多严重的附带争论。其间散落着一些链接：一个 CD Player 截图画廊、一个受 FreeCell Pro 启发、带 roguelite 模式的网页重制版，以及 solitairealonetogether.com。

**值得一读的评论**
- [ndiddy](https://news.ycombinator.com/item?id=50249857): ndiddy 把要击败的目标锁定在 1992 年 11 月 16 日，并认为 BSD a.out / 4.3BSD ABI 支持或仍在打补丁的 SCO OpenServer 是更老的二进制程序可能运行的现实去处。
- [0x0203](https://news.ycombinator.com/item?id=50249899): 0x0203 具体解释了旧 Linux 二进制程序为何跨发行版失效：动态 libc 版本不匹配，静态链接虽有帮助，但会让 X/Wayland GUI 程序变得复杂。
- [userbinator](https://news.ycombinator.com/item?id=50249495): 一位在 1990 年代初编写过小型 Win32 工具的开发者说，它们如今仍能未经修改地运行，只是大多跑在 WINE 下。

## 5. GPT-6.1 Terra {#story-5}
*HN 第 5 名 · [openai.com](https://openai.com/index/introducing-gpt-6-1-terra/) · 275 分 · 140 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50248124)*

链接页面是 OpenAI 为 GPT-6.1 Terra 发布的公告文章。Terra 是一款重新加入四模型阵容的中端模型，讨论帖将该阵容描述为 Luna < Terra < Sol < Astra，按规模和价格排序。文章本身返回 HTTP 403，因此这里的具体数字来自评论者：Terra 定价为每百万输入/输出 token 1 美元/5 美元——是 GPT-6.1 Sol 的 2 美元/10 美元的一半，是 GPT-6 Astra 的 10 美元/50 美元的十分之一——并声称在事实准确性、编程、视觉、计算机使用和技术沟通方面有所提升。一些读者将这次发布解读为针对 Anthropic 的 Sonnet 5.5 的按任务成本策略，而非追求前沿智能。

## 17. 一个流行的开放权重 AI 模型出现了令人担忧的行为 {#story-17}

**讨论**: 讨论串分成了两派：一派读者认为这可能是一个带有隐藏思维链的、人为植入的后门；另一派则认为这只是模型在阿里巴巴自家基础设施上进行强化学习训练时产生的罕见采样伪影。质疑者占多数：许多人指出 Cohere 销售私有化/主权部署方案，称「全球主权」是自相矛盾的说法，并把这篇文章解读为一场意在拖慢更廉价的中国模型的营销——其中一人论证说，真正的木马对阿里巴巴而言无异于商业自杀。另一些人则反驳说，把关于蓄意隐藏忠诚对象的指控当作普通的模型不稳定来打发，本身就是一种范畴错误，而且整件事的关键就在于：一个本地模型向外回连，恰好摧毁了在本地运行它的唯一理由。几条有技术依据的回复削弱了文章的论述框架：DNS/tmp/探测这一串操作大致就是测试一条数据外泄检测规则时的样子；它发送的是固定测试字符串而非真实数据；而创建私有的 tmpfs 命名空间是一种标准的无根（rootless）做法，并非内核漏洞利用的前兆。最具体的诉求是可复现性——公开检查点（checkpoint）和代码，让任何人都能验证——与此相关的一点是：即便模型是你自己训练的，LLM 权重依然是黑箱，所以真正的教训是把模型当作任何其他供应链依赖来对待，并对网络出口进行沙箱隔离。

**值得一读的评论**
- [peddling-brink](https://news.ycombinator.com/item?id=50249398): 认为整份报告描述的其实都是良性行为：他们要求的是数据外泄检测，模型便发送一段非敏感的测试字符串来做测试，而一个小模型没有先询问端点地址，并不构成间谍活动的证据。

## 18. 修复 vLLM 中的工具调用准确率问题 {#story-18}
*HN 第 22 名 · [ubicloud.com](https://www.ubicloud.com/blog/fixing-tool-call-accuracy-in-vllm) · 131 分 · 64 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50242870)*
*原标题: Fixing Tool-Call Accuracy in vLLM*

Jesse Donkervliet 和 Junhao Li 在 Ubicloud 博客上发表的一篇文章，讨论在服务开源权重模型时工具调用 schema 的准确率。在 vLLM 0.28 上服务 Kimi K2.6 时，只有 92% 的请求能产出有效的 tool-call schema —— 25 次里有 2 次失败 —— 文章解释了约束解码如何为新版 Kimi 和 DeepSeek 模型恢复 100% 的 schema 准确率；该功能在 0.31 中作为 vLLM 的服务端 flag 加入，并用 XGrammar token mask 实现。文章还介绍了 Moonshot 的 K2VV ToolCall 基准测试，其 2,000 个请求用于衡量触发相似度和 schema 准确率。

**讨论**: 整个讨论串大体认同约束解码是工具调用的正确默认做法，但对 Ubicloud 是否「修复」了 vLLM 存在争议：Aurornis 表示约束解码和受限的工具调用解码在 vLLM 中早已存在，作者主要只是需要正确的配置；而作者 jesdo 回应说，当时要让 Kimi 表现正确确实需要改代码，vLLM 后来在上游修复了它，而最新的 flag 是 `--tool-strict-level parameter`。最尖锐的分歧在于模型质量：hansvm 和 saurik 质疑强制使用合法 token 是否会扭曲模型分布，相比之下重试整个失败的工具调用同样能达到 100% schema 准确率并且避免上下文污染；hansvm 举了一个长 JSON 失败的例子和一个玩具分布，论证重试能保留模型学到的偏好（例如偏好 ripgrep 而非 grep），而 jesdo 说文章是刻意与 Moonshot 推荐的 serving 行为保持一致，并引用关于质量影响的正反两方面证据。多位实践者表示 vLLM 很强大但脆弱、配置起来令人困惑，且各家托管服务商差异很大；llama.cpp 用户指出语法约束解码在那里早已存在，draxen 认为 OpenAI 和 Anthropic 真正的护城河是 100% 工具调用准确率加上 prompt caching，并提到每个 prompt 约 300 次工具调用的工作负载。bob1029 认为 92% 远远不够，因为每次调用 95% 的成功率在连续 50 次调用后会复合为仅约 8% 的成功率，而 docjay 建议干脆把工具改名为模型本来就会输出的名字，例如用 `search_web` 而不是 `web_search`。其他子讨论涉及在运行中途更改工具集以及从上下文中剪除坏调用、`<|...|>` 特殊 token 的起源 —— 追溯到 GPT-2 的 `<|endoftext|>`，jesdo 解释为这是为了可读性而渲染的单个 token —— 以及同样的语法约束能否用于强制生成语法合法的代码，评论者认为可行但风险更高，因为许多代码错误只有在模型已经确定前面的 token 之后才会显现。

**值得一读的评论**
- [jesdo](https://news.ycombinator.com/item?id=50245660): 作者 jesdo 澄清，Kimi 的修复在当时确实需要在 vLLM 中修改代码，vLLM 团队后来在上游修复了它，现在由 `--tool-strict-level parameter` 处理。
- [hansvm](https://news.ycombinator.com/item?id=50245714): hansvm 给出了一个具体的失败模式 —— schema 约束迫使模型终止一段损坏的长 JSON 字符串 —— 并用一个玩具分布说明约束解码会把概率从 67/33 变成 50/50。
- [draxen](https://news.ycombinator.com/item?id=50245346): draxen 表示自己每个 prompt 要跑约 300 次工具调用，并认为 OpenAI 和 Anthropic 的优势在于约束解码带来的 100% 工具调用准确率加上 prompt caching，两者都在 2024 年就已推出。
