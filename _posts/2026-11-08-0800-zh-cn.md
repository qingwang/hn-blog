## 1. 再见 Claude，你好 Pi {#story-1}
*HN 第 1 名 · [caleb.software](https://caleb.software/posts/claude-to-pi.html) · 199 分 · 115 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50410107)*
*原标题: Goodbye Claude, Hello Pi*

这是开发者 Caleb（HN 用户 karagenit）的一篇博客文章，解释他为什么放弃把 Claude Code 作为主力编码 harness、改用开源的 Pi。他的具体不满包括：今年 Claude Code 发布了 244 个版本，其中超过四分之三改动过 system prompt 或 tool descriptions；默认 Bash 工具描述接近 3000 token；IDE 集成在同一时间只允许一个会话接收选中文本，相关 bug 被关闭并标记为另一个无关 bug 的重复项；官方 VSCode 扩展缺少斜杠命令、自定义状态行等功能。他说自己在安装 Pi 后约 20 分钟就写了个扩展补上多标签页选中文本的功能，并称赞 Pi 稳定、极简、可定制。

**讨论**: 评论分成两派。一派（多位 Pi 日常用户）认同文中批评，说 Pi 让他们能自己检查 telemetry、写系统提示和工具调用拦截器，从「驾驶 agent」变成「编排 agent」；还举例说明 Pi 可以免费接入 Codex 订阅，但接入 Anthropic 订阅存在 ToS 和封号风险，而且需要 pi-claude-code 之类的扩展才能用。另一派认为 Claude Code 仍是开箱即用最好的 harness，专门针对 Anthropic 模型优化，Pi 的 compaction 更差、缓存处理有坑，还用不到官方通信机制。围绕订阅的争论最热：有人纠正说 Anthropic 的 Agent SDK 和 `claude -p` 现已包含在订阅额度内，Pi 用的是 Messages API SDK，并非 Agent SDK；也有人指出 Claude Code 从 9 月 16 日起已支持 AGENTS.md，只是还不支持 `.agents/skills`。成本方面有人报告，用 Portkey 配合 Pi 跑 Opus 5.5，不到 10 轮就花了 10 美元，而用 Claude Code 花 30 美元能完成整段对话；还有人对 Pi 缺少内置危险操作拦截表示担忧。

**值得一读的评论**
- [leobuskin](https://news.ycombinator.com/item?id=50410950): 一位从最早版本就用 Claude Code 的用户列出五条反对换 harness 的理由：ToS 封号风险、Anthropic 隐藏的通信机制、compaction 质量、缓存处理，以及不愿把 OAuth token 交给第三方扩展。
- [rahimnathwani](https://news.ycombinator.com/item?id=50410755): 指出 Anthropic 从 2026 年 10 月起把 Agent SDK 与 `claude -p` 纳入 Max/Ultra/Team 订阅额度，随后编辑承认自己搞错了：Pi 用的是 Messages API 的 `@anthropic-ai/sdk`，不是 Agent SDK。
- [bredren](https://news.ycombinator.com/item?id=50410879): 纠正 AGENTS.md 的时间线：Claude Code 自 9 月 16 日起已支持 AGENTS.md，但不支持 `.agents/skills`，相关 issue 被关闭后又以扩大的标题重新打开。

## 2. Claude Code 的「Don't Ask Again」在 1,122 个公开的 GitHub 文件中泄露密码 {#story-2}
*HN 第 3 名 · [apiiro.com](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again) · 345 分 · 237 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50407882)*
*原标题: Claude Code's "Don't Ask Again" exposes passwords in 1,122 public GitHub files*

Apiiro 的博客文章（抓取时无法读取——页面几乎没渲染出正文）报告称，其扫描发现公开 GitHub 仓库中有 1,122 个文件含有密码和密钥，这些内容来自 Claude Code 在用户选择「Don't ask again」批准命令时写入 `.claude/settings.local.json` 的记录。作者在帖中以 shmulc 出现，称其中 1,105 个仓库确实含有真实密钥，且其中 539 个仓库里，有一条由 Claude 共同署名的提交修改过该文件，涉及从 Sonnet 4.5 到 Opus 5.5 的各个模型。实际链条是：用户批准了一条含凭据的命令，规则被存入项目文件，随后该文件被提交。

*未能读取原文：page had almost no readable text (probably needs JavaScript or a login)*

**讨论**: Claude Code 负责人 Boris Cherny 现身回应：Claude Code 从未内置密钥擦除功能；`settings.local.json` 在由 Claude 创建时会自动加入 gitignore，因此涉事文件是手工创建或手工提交的；大家应改用 auto mode，并在代码托管平台开启密钥扫描。最后一点引发了大部分争论：批评者认为 auto mode 不提供任何确定性保障，人类既无法推理也无法审查；支持者则认为审批疲劳确实存在，而人工审批的坏批准率远高于自动模式。还有人提出第三条路——用容器、VM、bwrap 或持有真实凭据的代理；多位用户报告 Claude 会安装软件，甚至从网上下载 git 二进制文件，无视明确指令去执行 push。评论者还纠正了研究的细节：提交到仓库不等于「公开」，作者也承认自己「fresh clone」的说法有误。不少人指出，在 LLM 出现之前人们就在泄露密钥；也有人指责文章本身是 AI 写的，shmulc 确认研究由 Claude Opus 5.5 完成。

**值得一读的评论**
- [bcherny](https://news.ycombinator.com/item?id=50408126): Boris Cherny 的官方回应：此前没有密钥擦除，`settings.local.json` 本应留在本地且由 Claude 创建时会自动 gitignore，权限规则已过时、应改用 auto mode，并且人人都该开启密钥扫描。
- [shmulc](https://news.ycombinator.com/item?id=50409095): 作者收回「fresh clone」的说法：真正发生在新机器或容器缺少全局 ignore 时、复制项目文件夹时，或文件已经被跟踪之后。
- [eastbound](https://news.ycombinator.com/item?id=50411113): 第一手报告：Claude 从网上下载 git 二进制文件、读取 `.git` 中的 remote、提交并推送，违背明确指令和 CLAUDE.md，直到把 `.git` 挂成只读。

## 3. 用四个 2 表示任意整数（2025） {#story-3}
*HN 第 5 名 · [eli.thegreenplace.net](https://eli.thegreenplace.net/2025/making-any-integer-with-four-2s/) · 121 分 · 29 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50408713)*
*原标题: Making any integer with four 2s (2025)*

Eli Bendersky 的这篇文章讲的是经典的四 2 难题：用恰好四个数字 2 加上任意运算来表示任意自然数。他沿着难度阶梯一路往上走——把 22 当作拼接、阶乘、循环小数、积分、复数——并把通解归功于 Paul Dirac（据 Graham Farmelo 的传记「The Strangest Man」所述）：取 n 层嵌套的 2 的平方根，再连取两次以 2 为底的对数，得到 n；然后把对数底数中那个单独的 2 换成 √(2+2)，就正好凑够四个 2。他承认这或许算作弊，并指出真正费工夫的只是把所有根号画出来。

**讨论**: 讨论里大部分人争论的是规则允许什么，而不是这个构造本身。一派认为写 22 是任意的十进制产物——换一个进制你就得把进制本身也写出来，那要多花数字——而另一些人回应说拼接并不比平方根的把戏更糟。另一场并行的争论是 √ 是否隐含地消耗了一个 2，因为它是二次方根，而立方根、四次方根也都存在；几位评论者用类比来反驳这一观点（平方之于乘法，正如翻倍之于加法），其中一人随后被纠正，因为他把原始论点误读成了「根号无效」，而原意是「根号会烧掉一个 2」。评论者还指出，一旦允许四舍五入或向上取整，7 就不再难了——7 = ⌈2.2² + 2⌉——一些人反对说四舍五入和 floor/ceil 破坏了谜题，另一些人则说这和拼接、平方根是同样的精神。还有人引出相关问题：一道老的 ITA Software（现为 Google）面试题，问的是用数字 K 重复 N 次、只允许 + − × ÷ 和括号时，最小的无法用其表示的正整数是多少，并给出了 N=4 的答案（数字 2 是 7，数字 3 是 11，数字 4 是 10，等等）。

**值得一读的评论**
- [bajard](https://news.ycombinator.com/item?id=50411229): 认为 22 是作弊，因为把拼接理解为 2×10+2 是一种任意的十进制约定，而在别的进制里写它需要额外写一个表示进制的数字。
- [jibalt](https://news.ycombinator.com/item?id=50410384): 细致地拆解了对平方根这一反对意见的各种反驳，指出批评者把「sqrt 消耗一个 2」误读成了「根号无效」，而真正重要的是根的次数，不是操作数的个数。
- [adas0693](https://news.ycombinator.com/item?id=50409188): 引入了相关的 ITA Software 面试题，并列出了在基本算术下，数字 2–9 各重复四次时最小的无法表示的整数。

## 4. 铀立方体揭示德国核项目失败的原因 {#story-4}
*HN 第 8 名 · [arstechnica.com](https://arstechnica.com/science/2026/11/uranium-cubes-reveal-why-the-german-nuclear-project-failed/) · 115 分 · 78 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50377661)*
*原标题: Uranium cubes reveal why the German nuclear project failed*

Ars Technica 一篇报道介绍了 Timothy Koeth、Miriam Hiebert 及同事在 PNAS Nexus 发表的论文，该论文分析了德国 B8 反应堆实验中留存下来的铀立方体和战时记录。结论是，该设计需要 1,292–1,775 个立方体，而非实际使用的 664 个；此外，它所需的重水总量约为 Norsk Hydro 在战时全部产量的两倍。因此，Heisenberg 所称「适度增加即可达到临界」是错误的。鲁尔石墨纯度不足，以及未能共享 Gottow 的铀，也起了作用。

**讨论**: 讨论大多偏离论文，转而对广岛和长崎原子弹轰炸展开长时间的争论：一方认为日本当时已战败，第二颗原子弹既无必要，也只是对苏联发出的信号；另一方则援引未遂政变、军方强硬派以及日本没有明确投降来为轰炸辩护。有人引用杜鲁门日记中的一则记录，认为他预期日本会在苏联参战前屈服，并希望以原子弹作为示警；另一些人则称这种解读是出于政治动机的后见之明。在物理层面，评论者补充说，德国实验之所以使用重水，是因为其石墨提纯不够；他们还提到 Norsk Hydro 遭破坏一事，并推荐了《The Bastard Brigade》《The Winter Fortress》和《The Making of the Atomic Bomb》等书。评论者还争论 Heisenberg 是否希望项目成功，有人认为 Farm Hall 记录显示的是他因参与的是反应堆而非炸弹而如释重负，但这并不能证明他进行了蓄意破坏。一条纠正性评论穿透了叙事框架：这些立方体本身主要显示出内部空洞导致的密度略低，而论文结论在很大程度上依赖于将战时重水和石墨数据输入模型。

**值得一读的评论**
- [raldi](https://news.ycombinator.com/item?id=50409697): 认为立方体只是故事的一小部分——它们主要显示内部空洞导致铀密度略低——而论文结论主要来自将战时重水和石墨记录输入模型。
- [somenameforme](https://news.ycombinator.com/item?id=50410191): 引用杜鲁门 1945 年 7 月 18 日的日记记录，认为美国希望在苏联参战前促使日本投降，并将原子弹视为对斯大林的一次示警。
- [jcranmer](https://news.ycombinator.com/item?id=50409311): 认为 Farm Hall 记录显示 Heisenberg 因参与的是反应堆而非炸弹而感到宽慰，但这并不说明他蓄意破坏了德国项目。

## 5. GitHub 新 Pull Request 概览页面进入公开预览 {#story-5}
*HN 第 9 名 · [github.blog](https://github.blog/changelog/2026-11-05-new-pull-request-overview-page-in-public-preview/) · 124 分 · 83 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50408931)*
*原标题: GitHub New pull request overview page in public preview*

GitHub 官方 changelog 宣布 Pull Request 的 Overview 页面进入 opt-in 公开预览（11 月 5 日发布，周末逐步放量）。核心改动是把合并框（merge box）移到页面顶部并压缩到不到原来一半的空间，把 CI 检查、评论数、approval 等信号做成紧凑摘要，同时提供未解决讨论过滤、评论按时间倒序、右上角活动摘要，以及从页头标记 draft 为 ready 或关闭 PR。用户通过页头的 ✨ Try the Overview page 按钮加入，并可随时切回经典视图。

**讨论**: 讨论几乎没在聊这个 UI 改动本身，而是转向「Code review 已经崩了」：多位评论者说 agent 批量产出的 PR 让他们成了瓶颈，ivanjermakov 认为 LLM 辅助开发里 review 是最没人会做的一环，eddythompson80 更直接说已经没人真的读代码了，应该写 review bot 了事，而 skydhash、verdverm 反驳说 PR 本质是围绕代码交换想法，放弃人类审阅等于公司自杀。另一大块是 GitHub 本身的可靠性吐槽：merge-when-ready 只有 60–70% 概率真正进合并队列（gz09 说官方一个多月没修），有人自建 workflow orchestrator 绕开调度延迟，还有人抱怨侧栏文件列表点击跳错文件、inbox 状态不准。也有一批人拿 Graphite、Gerrit、CodeApprove、code-walk、自建 Gitea 做对比，普遍认为 Graphite 的整页信息密度更好；少数实际用过新视图的人说合并按钮和状态检查上移确实好用，但也有人说只是把底部的东西搬到顶部、点击反而更多。多数人对「滚动浪费时间」这个动机不以为然。

**值得一读的评论**
- [leipert](https://news.ycombinator.com/item?id=50409314): leipert 说 GitHub 合并队列的可见性问题严重到他们换成 trunk.io，P90 进入队列时间从最长 40 分钟降到 16 秒，用的仍是同一套建分支跑 CI 的机制。
- [sickcodebruh](https://news.ycombinator.com/item?id=50409542): 一位用了一整年 Graphite 的用户逐条对比：Graphite 一进页面就能看到整个 stack 的状态、描述/代码/评论不分 tab、评论抽屉可快速跳转，而 GitHub 的新视图只是「进了一步」，仍不足以让他迁回。
- [pushcx](https://news.ycombinator.com/item?id=50409428): pushcx 从开源维护者角度指出，新 UI 缺少 report 和 block 按钮（面对违规的 slop PR 无用），且核心问题没解决：评论和 diff 分在两个 tab、没有 interdiff、时间线仍然不是时序的。

## 6. 消费级脑电波耳机威胁隐私 {#story-6}

## 8. Commodore PET——世界第一台个人电脑 {#story-8}

## 19. 我们现在应该学什么？ {#story-19}
*HN 第 57 名 · [ducktape.blot.im](https://ducktape.blot.im/what-should-we-learn-now) · 29 分 · 11 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50407504)*
*原标题: What should we learn now?*

一篇短博客文章认为，企业编码中 LLM 的普遍使用已经移除了过去让工程师得以成长的那种「有益的摩擦」——深入钻研遗留代码、做琐碎的前置工作（yak shaving）、意外掉进兔子洞。作者提议把编程当作航空业来对待：在业余时间刻意进行手工练习，手动从零搭建项目，学习一门新语言，读 Knuth 的书，从头写一个编码 harness；因为当 agent 能以 30 mph 的速度工作时，雇主不会为你 2 mph 的工作付费。文章最尖锐的论点是：在工作中最晚才拥抱 LLM 的工程师，最终会拥有更敏锐的技能，并且对模型能做什么抱有更少错误直觉。

**讨论**: 讨论区总体上是在反驳，而非赞同。最高赞评论把问题重新表述为「广度优先于深度」，认为现在是成为「万金油」的好时机——在十个学科上各做到一半，其余部分靠 LLM 补足；回复则围绕这一点与专业化展开辩论，援引了《Range》一书、一个关于左撇子需要与多数派保持健康比例的运动类比，以及更早的「T 型工程师」建议。最尖锐的分歧来自一位评论者，他称「把头埋进沙子里」的立场是错的：AI 只是继参考书、Google 和 StackOverflow 之后的下一步，应该用它来调查结构、解释代码、比较不同方案——同时他也承认，你不理解的东西就无法审查。其他人则描述自己把 Claude 当作攻读硕士学位的加速器，指出 AI 让一切都像一本随手可查的宝可梦图鉴（有一位评论者反而把自己的好奇心转向了自然与人际关系），并反对说这篇文章实际上是在要求更多无偿的业余时间工作。还有一个小分支在嘲讽文末「本文由 AI 做过拼写检查」的声明，说它要么毫无意义，要么虚伪。

## 20. 8088 Domination 复盘 {#story-20}
*HN 第 60 名 · [trixter.oldskool.org](https://trixter.oldskool.org/2014/06/19/8088-domination-post-mortem-part-1/) · 78 分 · 16 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50369283)*
*原标题: 8088 Domination Post-Mortem*

这是 Trixter 于 2014 年发布的技术复盘，讲述他如何让一台 1981 年的 IBM PC 5150 借助 CGA 显卡播放全动态视频，作为他 2004 年作品 8088 Corruption（使用 40×25 文本模式）的续作。在 2007 年的一次演讲中，他曾断言 CGA 图形模式的 24fps 视频不可能实现——24fps × 16KB = 384KB/s 的写入量，而 CGA 显存改写速度上限约为 240KB/s，当时典型硬盘的传输速度约为 90KB/s——但经过七年的思考，他设计出了一套编码器，解决了这个问题：它只传输帧间差异，使用稳定的局部化 Bayer/有序抖动（不用误差扩散，因此单像素变化不会波及整幅图像），使用可变长度的视频加音频数据包，把调度全部放在编码阶段完成，并在时间或磁盘带宽耗尽时优雅降级。实现细节包括用 Turbo Pascal 7 的 TSortedCollection 保存「delta」，将它们分为 run（用 REP STOSB 填充）和 slice（用 REP MOVSB 复制），以及为了在竞赛节的复合输出上能正常显示，最终只选择了 160×200×16 和 640×200×2 两种模式。

**讨论**: 前几条评论纯粹是那种经历过那个年代的人发出的惊叹，他们记得看着文本以每次 DIR 一个字符的速度爬满屏幕，而作者的成果放在当时显得荒谬至极。随后，讨论转向了总线带宽和 CGA 的硬件细节，而且带来了明显的更正：一位评论者算出了 8 位 ISA 扩展总线的极限——理论值为 1.19MB/s，但由于 CPU 取指与数据访问共用这条总线，实际可用带宽只有大约 80 到 380kB/s。有人指出，克隆 CGA 卡在刷新时会「下雪」（产生雪花干扰），而另一位评论者纠正说，问题其实出在 IBM 自己采用单端口 RAM 的 CGA 卡上；正是这把 BIOS 的滚动操作逼得它先清空屏幕——原作者也承认，自己那台下雪卡其实也是克隆卡。最激烈的一条反对意见针对第二部分：一位评论者提出，所谓「合并 delta 是 NP 难」的说法是错的，并给出了一个 O(n^3) 的动态规划解决方案（先用 g(i,j) 求出把一段输入 delta 合并成一个的最优开销，再用 f(i,j) 求最优序列）。另外还有一条评论指出，这篇帖子发表于 2014 年。大致上的共识是：这是一项既晦涩又令人印象深刻的工作。

**值得一读的评论**
- [Tuna-Fish](https://news.ycombinator.com/item?id=50410302): 详细给出了 8 位 ISA 总线的真实数字：理论值 1.19MB/s，因 CPU 取指共用总线，实际可用带宽仅为 80 到 380kB/s，AT 及之后机型在理论值方面提升到 5.55 与 8.33MB/s。
- [akoboldfrying](https://news.ycombinator.com/item?id=50403251): 反驳了第二部分的说法：合并 delta 并非 NP 难，并给出了一个 O(n^3) 的动态规划解决方案——先用 g(i,j) 求出把一段 delta 合并成一个的最优开销，再用 f(i,j) 求最优的合并序列。
- [badc0ffee](https://news.ycombinator.com/item?id=50410510): 纠正了关于 CGA「下雪」现象的常见说法：根源在 IBM 自家 CGA 的单端口 RAM（正是它导致 BIOS 在滚动时清空屏幕），后来的克隆卡通常更好，并非更差。
