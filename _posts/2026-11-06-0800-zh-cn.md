## 1. Claude Code 会把你的邮箱地址发送给网站 {#story-1}
*HN 第 1 名 · [github.com](https://github.com/anthropics/claude-code/issues/107757) · 978 分 · 318 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50385272)*
*原标题: Claude Code sends your email address to websites*

一份针对 anthropics/claude-code 的 GitHub bug 报告（#107757）指称，Claude Code 会把已登录用户的账号邮箱插入到对外 HTTP 请求的 User-Agent 头中——例如 my-session-slug/1 <my.name@example.com>——而报告者如今每天收到几十封诈骗和钓鱼邮件。报告者主张应当把它从 harness 中彻底移除，而不是做成可选的开启或关闭设置，称这是诈骗者的金矿，并表示正把公司迁移到配合 OpenRouter 使用的 Pi。随后整个讨论串变成一场争论：这是怎么发生的、有多严重、Anthropic 做了什么。

**讨论**: 得票最高的纠正重新框定了这件事：泄露多半是 Claude 在遵从那些要求爬虫在 User-Agent 中提供联系方式的网站——SEC EDGAR 的数据 API 对默认的 curl agent 返回 403，一旦附上邮箱就返回 200，Wikipedia 和 EVE Online 的 API 也有类似政策——所以这是模型为满足网站要求而自行生成的遵从行为，而不是网络层给每个请求都盖了章。Anthropic 员工（先是 mpoteat，之后是 lydia_hallie）确认了根因：账号邮箱是被有意放进模型上下文的，目的是让 Claude 不再为 @author 标签编造名字，而 Claude 在编写 curl 命令时有时会主动把它当作联系地址写出来；他们在 2.1.317 中发布了一个默认内置的 mod——cc-plugin-privacy，在包含该邮箱的 web/curl 调用前弹出提示，并承诺下个版本将把邮箱从上下文中彻底移除，同时承认这仍然无法阻止 Claude 写出一个悄悄泄露它的脚本。许多评论者十分愤怒——怒的是 vibe-coded 出来的软件夹带 PII 泄露、怒的是修法竟然是一个插件、怒的是 GDPR 角度——另一些人则反驳说暴露面很窄、垃圾邮件的轶事只是巧合；少数使用按服务划分的邮箱别名的用户报告零垃圾邮件，这支持了「范围很窄」的解读。有实践者补充说这种行为范围比账号邮箱更广：子 agent 会把姓名、公司名和 repo URL 塞进 User-Agent 字符串，只要私有数据出现在 agent 能触及的上下文里，泄露就会出现，因此有几个人认为唯一真正的修法是沙箱化，并把私有数据挡在上下文之外。

**值得一读的评论**
- [varenc](https://news.ycombinator.com/item?id=50387577): 用一个可复现的 curl 演示说明 SEC EDGAR 的 API 会以 403 拒绝默认的 User-Agent，却接受含邮箱的 User-Agent，因此 Claude 的行为更像是在尝试遵从要求，而不是硬编码的泄露（不过 SEC 也接受大多数非 curl 的 agent）。
- [lydia_hallie](https://news.ycombinator.com/item?id=50388176): Anthropic 的 lydia_hallie 说明了根因——账号邮箱被加入模型上下文，以阻止 @author 名字被幻觉编造——以及时间线：2.1.317 中的 mod、下一版本从上下文中移除邮箱、stable 渠道仍停留在 2.1.311。
- [sunaookami](https://news.ycombinator.com/item?id=50385931): 引用了注入用户邮箱、并附有「绝不要把它发送给无关服务」指示的那段隐藏 system-prompt 块，说明这种 prompt 层面的防护如何败给 curl 生成的请求头。

## 2. MS Paint 远程代码执行漏洞 {#story-2}
*HN 第 3 名 · [cve.org](https://www.cve.org/CVERecord?id=CVE-2026-83844) · 488 分 · 178 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50384233)*
*原标题: MS Paint Remote Code Execution Vulnerability*

这个链接指向 CVE.org 上 CVE-2026-83844 的记录页，但该页面在没有 JavaScript 的情况下无法渲染，因此以下细节来自评论者引用的 MSRC 公告原文。该公告描述的是 Windows Paint 中的一处越界读取漏洞：未认证的攻击者可以通过网络向受影响的服务发送特制数据包来执行代码，无需身份认证，也不需要用户交互，CVSS 评分为 8.1（AV:N/AC:H/PR:N/UI:N）。评论者称修复版本为 Paint 11.2609.401.0，受影响的是 11.0.0.0 到 11.2605.91.0 之间的版本，并指出该更新通过 Microsoft Store 而非 Windows Update 推送。

**讨论**: 整个讨论串几乎都围绕一个问题：一个位图编辑器怎么可能会被网络访问到。一大群持怀疑态度的评论者认为，MSRC 那句关于「向受影响的服务发送特制数据包」的话，是塞进每一条 RCE 常见问题条目里的模板话术——他们指出微软 10 月那批补丁中有 59 个「可蠕虫传播」的 CVE 用了完全相同的措辞——真正的攻击向量几乎肯定是打开一个恶意图片文件，或者来自新增 Copilot 集成的、被劫持的出站连接；若如此，那么「无需用户交互」和「网络」这两项评分就是错的，或者至少是被误抄了。另一方则反驳说，Windows 11 上的 Paint 是重写过的 Store 应用，具备图层、背景移除和 AI 功能，因此确实含有真正的网络代码；还有人报告说，在一台保持最新、未做改动的机器上并没有看到任何监听端口，这削弱了「它是个服务器」的字面解读。两派都认同的实际抱怨是：Windows Update 没有提供任何更新，人们必须打开 Microsoft Store 的 Paint 页面才能拿到修补后的版本；而且版本号（11.2605.91 与 11.2609.401.0）让人困惑，用户根本分不清自己是否已经修好。外围则是一些玩笑，说下一个该轮到 Calc、Minesweeper 和 Solitaire 的 CVE 了，还有 Zawinski's Law，以及一条贯穿始终的怀旧线：怀念 XP 时代那个离线的老 mspaint.exe。

**值得一读的评论**
- [6thbit](https://news.ycombinator.com/item?id=50386446): 指出 10 月的 59 个 CVE 都用了完全相同的「特制数据包／无需用户交互」模板措辞，因此 Paint 的公告可能只是抄错了，并附上 Zero Day Initiative 的 2026 年 10 月回顾链接。
- [akerl_](https://news.ycombinator.com/item?id=50387237): 认为那句关于网络访问的话看起来像是微软给所有标为 RCE 的问题自动填入的占位式常见问题文本，在有人说明 Paint 究竟如何暴露于网络之前，他保持怀疑。
- [greyhound1](https://news.ycombinator.com/item?id=50385483): 第一手报告：Windows Update 没有显示任何修复，修补后的 Paint 必须手动从 Microsoft Store 获取。

## 3. Pwn.college {#story-3}
*HN 第 4 名 · [pwn.college](https://pwn.college/) · 121 分 · 12 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50387796)*

这是 pwn.college 的落地页。pwn.college 是一个免费的动手实践网络安全教育平台，由 Arizona State University 的黑客们维护，同时也支撑着 ASU 的许多安全课程。学习者从「白带」开始，逐个完成道场（dojo）——即关于计算、利用与网络基础的模块——并一路赢得腰带；平台上有社区制作的道场，也有教育者可以导入的道场，此外还提供道场之后的 CTF 和 wargame 指引。该页面请用户不要发布挑战题解的 writeup、walkthrough 或直播，以便这些材料仍能用于大学评分；页面还说明其基础设施是开源的，而部分模块内容（含题解）则是闭源的。

**讨论**: 这条讨论帖很小，几乎是一致好评，多数评论者都在交换对早期 wargame 的怀旧之情：hackthissite.org、OverTheWire、SmashTheStack 和 OWASP WebGoat 都被提到。一位评论者指出该网站因 HN 的流量而被「挤到瘫痪」，另一位则说通过更深的链接（例如 /welcome/welcome/）仍可访问。唯一真正的分歧在于排行榜：一位读者指出，页面上显示的最高分只有 10 分，而这正是完成教程所得的分；有人纠正说每个模块都有自己的排行榜，所以教程排行榜的上限自然就是教程的总分——对此还有人开玩笑说，接受这个解释可不是很有黑客精神的思维方式。一位看起来是该项目幕后成员之一的评论者表示，OverTheWire（他曾用作课堂作业）是 pwn.college 的一大灵感来源；另一个人则强调，完成所有关卡会得到一条真正的实体腰带。

**值得一读的评论**
- [adamdoupe](https://news.ycombinator.com/item?id=50388915): 一位参与该项目的人说，OverTheWire（他曾用作课堂作业）是 pwn.college 的主要灵感来源之一。
- [unsnap_biceps](https://news.ycombinator.com/item?id=50388431): 解释说每个模块都有自己的排行榜，所以看起来很低的第一名 10 分只是反映了教程模块的最高分。

## 4. Nvidia Kubernetes Engine (NVKE) {#story-4}
*HN 第 5 名 · [github.com](https://github.com/dsx-ai-factory/nvke) · 67 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50387738)*

这是 NVIDIA 旗下 dsx-ai-factory 组织在 GitHub 上的一个仓库，介绍 NVKE——一个处于预览阶段的管理平面，平台团队安装它之后，可以在自己拥有的 NVIDIA GPU 裸机上创建 Kubernetes 集群并对其做生命周期管理。先用一个用完即弃的 seed 集群搭起管理集群，这个管理平面再通过 NVIDIA Infra Controller（NICo，预览阶段唯一支持的基础设施 provider）、Cluster API 和一个节点 agent 创建 workload 集群，节点则用自身的 TPM 经由 SPIFFE/SPIRE 完成 attestation。README 明确说明它不是发行版，也不是 Cluster API 的一个 flavor；并说明预览构建默认关闭 API 认证、使用明文 HTTP，没有管理平面升级路径，也没有备份／恢复路径，而其 FDE 节点镜像并不能提供真正的静态数据机密性。

**讨论**: 最主要的反应是 README 没把产品讲清楚：评论者称它是一堆 AI 生成的内容倾倒，读完之后比读之前更困惑，不过也有人回复说开头那段其实已经说明了它是什么。一条有技术分量的批评认为 NVKE 把本应分开的关注点混在了一起——Cluster API、Kamaji 式的托管控制平面以及 gpu-operator——真正有意思的只剩下基于 kind 的管理集群引导器和 SPIFFE/TPM 身份相关的工作。其他人指出普通 Kubernetes 本来就能调度 GPU，并追问一个已经在用 k8s 或 k3s 的平台团队为什么需要它；一种解释是它面向 NVIDIA DSX 参考栈上租户隔离的集群，用 NICo/BlueField 做隔离网络，并在租户切换时擦除主机并重新 attestation——这主要在你想要 NVIDIA Cloud Partner 资格或端到端 NVIDIA 支持时才有意义。一条篇幅不小的支线是 OpenStack 怀旧，有人提到在 Broadcom 的 VMware 价格推动下用 Kolla-Ansible 加 Ceph 做部署，帖子末尾则跑偏成关于把事物以「AI 之前」（BAI）来纪年的玩笑。

**值得一读的评论**
- [QuentinM](https://news.ycombinator.com/item?id=50388910): 解释了实际用例：NVIDIA DSX 参考栈上租户隔离的集群，用 NICo/BlueField 做网络隔离，并在租户之间擦除主机并重新 attestation；主要在你想要 NVIDIA Cloud Partner 资格或全栈 NVIDIA 支持时才值得。
- [Yasuraka](https://news.ycombinator.com/item?id=50388976): 认为该项目把 Cluster API、Kamaji 和 gpu-operator 混为一谈，真正值得借鉴的只有基于 kind 的引导器和 SPIFFE/TPM 集成。
- [hedora](https://news.ycombinator.com/item?id=50388171): 困惑的一种犀利版本：如果你已经有一个平台团队在交付 k8s 或 k3s，NVKE 还能增加什么——另外有没有 Stripe 集成可以用来转售集群？

**讨论**: 匈牙利评论者立即对报道的定性提出异议：这里的「agent」（ügynök）指的是线人，而非秘密警察官员；许多人表示，公开的文件只能说明某人曾被接触并登记，并不能说明其是否真的写过报告——有人举 Katalin Karikó 为例，她 2023 年获得诺贝尔奖，而早在自己的回忆录中她就描述过自己被招募、但未报告任何内容。另一些人则认为这一区分在道德上无关紧要，因为线人往往是因失业、流放或更糟的后果而被胁迫，有时还会以职业机会或免于被捕作为补偿；一位评论者的祖父就因一出戏被判定为不同情而被流放到乡村学校。还有几个人讲述了家族中关于告密的故事，结果发现那些告密只是建立在审讯中逼取签名的基础上，这印证了历史学家的告诫：仅凭名单说明不了什么。随后讨论转向一场长时间的争论：这些专制政权究竟该由苏联还是本地负责（以波兰、东德——91,015 名 Stasi 工作人员、189,000 名 IM——以及雅尔塔为参照），并抱怨西方和美国的学校几乎不教这段历史；这一方面没有形成共识，但几乎所有人都同意，这些档案几十年前就该公开了。

## 19. TextEdit vs. Pages {#story-19}
*HN 第 36 名 · [leancrew.com](https://leancrew.com/all-this/2026/10/textedit-vs-pages/) · 93 分 · 71 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50352846)*

Dr. Drang（leancrew.com）回应了 Allison Sheridan 那篇把 TextEdit 称为「macOS 无名英雄」、可以当简易文字处理器用的文章。他试用后表示仍然留在 Pages：TextEdit 的工具栏无法隐藏、不能自定义，缩放只有「放大一倍／缩小一半」两档，也没有可保存的模板；Pages 的工具栏收在标题栏里、可自定义，有模板（他的「Big Note」用 16pt Helvetica Neue 正文、18pt 粗体标题），侧边栏也能折叠。他承认 TextEdit 内存占用小得多，但自己用的是 48 GB 的 MacBook Pro，且 Pages 免费版够用；如果 Apple 哪天强制 Pages 用户订阅 Creator Studio，他会重新考虑 TextEdit。

**讨论**: 评论区分歧最大的不是两个应用本身，而是作者挑刺的正当性：一批人认为「谁需要加粗、斜体、对齐按钮」这个抱怨站不住脚，普通用户恰恰需要这些随手可点的按钮，而且 MacWrite 时代屏幕只有 512×342，如今屏幕空间没那么紧张；另一派则觉得这只是一篇个人偏好文章，作者本就没有假装客观评测。技术派补充了历史：TextEdit 源自 OPENSTEP 的文本视图示例程序，源码一直公开到 OS X 10.9，有人报告在 Xcode 27.2 / Tahoe 26.7.2 上稍作修改就能编译，并纠正了「Cocoa 被移除」的说法（被移除的是 Carbon）；Chess 的源码也仍在 apple-oss-distributions 上。针对文中「TextEdit 无法保存模板」的论断，有人指出系统内置的 Stationery Pad（文具簿）功能正是干这个的。此外还有人夸 Pages 被低估、Preview.app 功能强大，抱怨 Notes.app 没有版本控制、iCloud 会把误删同步到所有设备，以及 Pages 不支持 Zotero 插件。

**值得一读的评论**
- [phil-pickering](https://news.ycombinator.com/item?id=50377996): 直接反驳文中观点：macOS 内置的 Stationery Pad 功能可以用来为 TextEdit 创建并使用模板。
- [wpm](https://news.ycombinator.com/item?id=50380453): 第一手经验：把 .strings 文件编码设置改一改、构建目标设为 macOS 14，旧版 TextEdit 源码在 Xcode 27.2 / Tahoe 26.7.2 上除了一些弃用警告外可以正常编译，并指出被移除的是 Carbon 而非 Cocoa。
- [MBCook](https://news.ycombinator.com/item?id=50381229): 温和但明确的反驳：排版按钮对不熟快捷键的用户是救星，MacWrite 时代 512×342 的屏幕才容不下工具栏，如今取舍已经不同，因此把这当成普遍性批评很奇怪。

## 20. 从零构建多智能体系统：架构模式 {#story-20}
*HN 第 37 名 · [kadhar.dev](https://kadhar.dev/blog/multi-agent-systems-from-scratch) · 87 分 · 35 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50380658)*
*原标题: Building a Multi-Agent System from Scratch: Architecture Patterns*

kadhar.dev 的一篇博客文章，列出了把工作拆分给多个 LLM 智能体的三种模式：编排者-工作者（由一个规划者把任务分派给彼此从不交流的专家智能体）、黑板模式（各个智能体读写共享状态，没有人拥有整体计划的归属权）以及流水线模式（一条固定的检索 → 抽取 → 校验 → 格式化的链条），另外还给出一条在它们之间做选择的决策规则。其核心论点是，多智能体设计买到的是任务分解，而不是正确性：文章列举了一批只有在过了演示阶段之后才会出现的失效模式——智能体之间来回推诿（delegation ping-pong）、因反复重新调用而失控的 token 成本、两个智能体写共享状态时的竞态条件，以及下游不断累积放大的幻觉，因为接收方智能体无法区分一个猜测与一个已核实的事实。文章给出的解法是代码层面的护栏，而不是提示词层面的：把重新委派的硬性上限设在约 3-5 跳、集中追踪每个任务的 token 或美金上限，以及一条真正可用的升级到人的通道。

**讨论**: 讨论串中很大一部分谈的是这篇东西的包装而非内容：好几位读者说这个页面读起来明显是 Claude 生成的——默认主题、没删掉的「The Honest Summary」标题——并说他们一看到这类页面就直接关掉；作者承认有 AI 协助，并表示自己已经换掉了主题。另一些人反驳说，信息本身比写作投入更重要，认为应当按有用性和信息源的过往记录来评判产出，而不是试图检测模型生成；有一条回复则反驳说，在没有人类把关的信号的况下，读者无法区分精编与垃圾。真正的工程争论在于并发是否真的有必要：一位评论者认为嵌套子智能体——把子智能体建模成又一次工具调用——胜过多智能体系统，并给出一个基准挑战（让一个多智能体系统以比单个分层智能体更快的速度单调递增一个共享计数器），讨论串里没有人回应；一条回复指出 Claude Code 和 Codex 目前都不允许子智能体再派发自己的子智能体，所以多层结构需要自建调度框架。一位实践者在一个分支上并行跑 4-5 个 Claude 会话，报告说这主要是在审查环节有回报——自九月以来对 4,471 个提交给出了 4,454 条结论，其中约五分之四的首轮审查都发现了问题，一半要求修改——另有人贴出 Stanford CS146S 和 CMU 的 11-768 智能体课程，有人索要具体的生产环境案例（被点名的一个是 Claude 的研究功能），还有人指出黑板模式的想法已有 25 年以上的历史。

**值得一读的评论**
- [brkomir](https://news.ycombinator.com/item?id=50383531): 来自真实使用的数字：在一个分支上并行跑 4-5 个 Claude 会话，用共享消息队列和提交锁来协调，跨会话代码审查在约 80% 的首轮审查中都抓到了问题。
- [bob1029](https://news.ycombinator.com/item?id=50381328): 一个有力的反面论证：嵌套子智能体（把提示词包成一次工具调用，可任意分层）胜过并发智能体，并给出一个具体的证伪测试——让一个多智能体系统以比单个分层智能体更快的速度单调递增一个全局计数器。
- [scubbo](https://news.ycombinator.com/item?id=50382685): 主张读者应当评判从技术写作中获得的价值，而不是写作所投入的功夫，并引用 Stephen Fry 关于一本书作为艺术品与作为沟通媒介之区别的论述。
