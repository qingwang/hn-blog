## 2. 在太阳能阵列田间放牧绵羊 {#story-2}
*HN 第 2 名 · [news.cornell.edu](https://news.cornell.edu/stories/2026/10/sheep-grazing-solar-fields-offers-farmers-economic-ecological-gains) · 117 分 · 101 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50520182)*
*原标题: Grazing sheep in fields with solar arrays*

一篇 Cornell（康奈尔大学）的新闻稿，介绍两篇新论文。第一篇《Low solar-grazing densities support beneficial insects in agrivoltaic systems》（发表于 Environmental Research Letters，10 月 7 日，第一作者 Leana Zoller，资深作者 Steve Grodsky），在纽约州 Dryden 的 Cascadilla Community Solar Farm 进行了为期三年的试验：每公顷两只羊时，野蜂、蜜蜂和瓢虫的丰度比割草的对照地块高 38%，这一效应主要来自蜜蜂数量上升 83%；每公顷四只羊时，昆虫数量与割草持平，而植被控制有所改善；每公顷八只羊时，植被控制达到峰值、羊群健康状况保持良好，但蜜蜂丰度下降了 45%。第二篇《Flock Management for Solar Grazing》（发表于 Manufacturing & Service Operations Management，9 月 28 日）是康奈尔大学商科与工程研究人员（Vincent Slaugh、Linwei Xin、Shane Henderson）开发的基于电子表格的模型，帮助农场主根据合同收入和场地植被情况来确定羊群规模，Ithaca 的 United Agrivoltaics 已在其客户接入流程中使用该模型。

**讨论**: 讨论串大多偏离了论文本身：最大的一簇讨论在争论为什么 Permian Basin 的作业者宁可把搁浅的天然气火炬烧掉也不出售（管道运力、Waha Hub 价格接近零、Oklahoma 的反浪费法规），以及加密矿工或数据中心能否消纳这些天然气。第二个大分支在争论为什么太阳能建在草地上而不是沙漠里——给出的答案是输电成本和审批拖延（SunZia 线路从规划到投运用了 20 年），另外还有人指出所谓「贫瘠」土地往往是放牧导致退化的土地。回到正题，实践者一致认为绵羊是破坏性最小的选择：山羊会爬上光伏板并啃咬电缆，而牛——体重 1,000–1,500 磅的动物——会蹭撞并弄坏支架，这正是某位养牛者所说的碰到的障碍。有几位评论者对研究的框架提出质疑，指出对照的是割草，而在数百根支撑立柱周围割草本身就是一件代价高昂的麻烦事，所以这个基准很低。一位评论者针对绵羊给出更正：绵羊会把草从基部啃到裸土，因此可能需要补播三叶草或本地开花植物——而这实际上会有助于论文关于生物多样性的论断。

**值得一读的评论**
- [_heimdall](https://news.ycombinator.com/item?id=50521557): 一位养了约 20 头牛的牛主说，他想给自家田地提供遮荫，但受阻于两点：缺少能承受 1,000 磅阉牛蹭撞且价格可负担的支架；以及当地电力公司让向电网反送电变得毫无意义。
- [fred69](https://news.ycombinator.com/item?id=50521875): 指出绵羊会把草啃到土面处的基部，而不是留茬较高地采食，因此三叶草／本地花卉混播可能需要定期补播——这对生物多样性有利，但确实是一项成本。
- [scblock](https://news.ycombinator.com/item?id=50521882): 一条行业细节，更正另一位评论者的说法：公用事业规模的阵列按 1500 VDC 设计（每串 20–25 块组件，而不是 12–18 块），电缆常常不加保护地直接接入汇流箱并埋入地下，架空吊挂的情况很少见。

## 3. Jiff 1.0：Rust 的日期时间库 {#story-3}
*HN 第 3 名 · [burntsushi.net](https://burntsushi.net/jiff/) · 185 分 · 43 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50519744)*
*原标题: Jiff 1.0: A datetime library for Rust*

Andrew Gallant（burntsushi）宣布发布 Jiff 1.0，这是一个 Rust 日期时间库，核心设计是让 DST 与时区处理成为 API 的中心，而不是事后补丁，并通过 ICU4X 提供对区域设置敏感的格式化。文章逐层介绍了类型体系——civil::Date、civil::Time、civil::DateTime、Timestamp、TimeZone、ZonedDateTime，以及 Span 和 SignedDuration——并展示了在 DST 折叠（fold）和空档（gap）中出现的歧义民用时间如何用「compatible」（默认）、「earlier」、「later」以及遇到歧义即报错的策略来消解。Gallant 指出 Jiff 已在生产环境中使用于 uv、Cargo、Starship、fd、Nushell、mise、Jujutsu、uutils/coreutils 以及一个 AWS LLRT 的 Temporal 实现，并承诺 1.0 之后 API 永久稳定，因为 Jiff 的定位就是出现在其他库的公开 API 中。Jiff 有意只支持 Unix 时间尺度（不支持 TAI 或闰秒）。

**讨论**: 整个讨论串基本是对 burntsushi 的库设计与性格的致敬，好几个人提到他的其他项目，一位贡献者称他很好合作。最有分量的证词来自 chrono 的前维护者：他说自己接下这份工作本是希望能修好 chrono 的 API，结果每一项改进都遭到抵制，最后心力交瘁，如今称 chrono 稳定但处于半弃用状态——其他人则贴出确认这一状态的 chrono issue，并表示迁移到 Jiff 很容易。一位模拟小行星轨道的科学家询问 UT1 之类的非 Unix 时间尺度；burntsushi 把他引向 hifitime，这位科学家回复说 hifitime 的整数表示会给他的长基线模拟引入数值噪声。另有一场篇幅不小的附带争论，讨论一门语言是否应该在标准库里自带日期时间处理：一方举出供应链安全和生态整合得当的理由，并以 java.time 为例；另一方则认为一个糟糕的内置 API 会挤掉更好的库、教坏用户，并把 Go 的 time 包当作反面教材。还有一个小分支纠正了一种说法，指出 Temporal 模型并非新近才有，而是源自 Joda/java.time；其余内容则是关于把 Jiff 念成软 g 的「gif」的玩笑。

**值得一读的评论**
- [quodlibetor](https://news.ycombinator.com/item?id=50521423): 维护 chrono 约五年的维护者解释，他曾试图修好 chrono 的 API 但未能成功，因遭遇抵制而心力交瘁，如今称 chrono 稳定但半弃用，同时赞扬 Jiff。
- [burntsushi](https://news.ycombinator.com/item?id=50520811): burntsushi 明确表示 Jiff 只支持 Unix 时间尺度，并推荐 TAI/UT1 这类天文工作使用 hifitime——而提问者在 C10 中回复说 hifitime 的内部表示不利于他的长期轨道模拟。
- [masklinn](https://news.ycombinator.com/item?id=50520954): 纠正了「Temporal 发明了这套好模型」的想法：它沿袭 Joda 和 java.time，并链接了 Colebourne 对 Temporal 将非 ISO 日历列为一等公民的反对意见。

## 4. 软件正在系统性层面崩溃 {#story-4}
*HN 第 4 名 · [breck-mckye.com](https://www.breck-mckye.com/blog/2026/11/software-is-breaking-down-at-a-systemic-level/) · 132 分 · 95 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50520866)*
*原标题: Software is breaking down at a systemic level*

一篇由 Breck McKye 撰写的博客文章，主张 2026 年接连发生的可靠性与安全灾难——持续两天的全球性 Microsoft 故障、FAA 停飞、影响约 70% 网站的运行时中的 PHP2Shell 远程代码执行漏洞，以及 eMudhra 因一把弱私钥而导致数千张 SSL 证书被攻破——其直接原因各不相同，却有着共同的形态：由无人能端到端理解的低质量部件拼装而成的高度复杂系统。他将此追溯到云服务整合、2010 年代中期以来依赖繁重的开源生态，以及专家知识的流失；随后论证 AI 的真正危险不是糟糕的模型输出，而是「脱相干」（decoherence）——引用 Kristen Maevyn 的文章「The Decoherence Trap」，谈局部有效但彼此不相容的模型不断累积，直至变革变得难以负担——并加上前 Microsoft 工程师 Axel Rischin 对 Azure 那种「快速修补」式可靠性文化的批评。（抓取到的文章在脱相干一节中途被截断。）

**讨论**: 最主要的反应是：这篇文章的历史讲错了，情绪是怀旧的。评论者指出 AWS 已有约 20 年历史，Maven Central 25 年，CPAN 31 年，left-pad 已是十年前的往事，并一口气举出 log4j、Heartbleed、CrowdStrike 和 Okta 作为佐证，说明软件从来没有什么黄金时代——故障数量上升，主要是因为软件总量庞大了许多，而且如今的检测几乎不花成本。仍有数人认同核心论点：复杂性与集中化使故障变得相互关联、波及整个行业；一个很大的子话题则认为解决之道是文档：把规则、规范和测试写下来，让 agent 有可遵循的约束框架。对立阵营称这种想法天真，认为真正的难题是：当你再也无法把整个系统装进脑子里时，如何评估输出，而且 AI 不会从自己的错误中学习。第一手经验报告则分成两派——一边是发布更快、单个任务的失败更少，另一边是对 500 行 diff 的橡皮图章式评审和每月更多的事故——双方大致只在一件事上达成一致：AI 压缩了时间尺度，而不是发明了新的故障模式。

**值得一读的评论**
- [tflinton](https://news.ycombinator.com/item?id=50521220): 一位负责自动化基础设施升级的从业者报告称，AI agent 的失败率只有人类的一半（1/20 对 1/10），但每月产生的事故却是 5 倍，因为它们以 10 倍的速度运行——单次操作更安全，但按单位人类时间衡量则更不可靠。
- [dotdi](https://news.ycombinator.com/item?id=50521329): 描述了这样的情况：70 人被裁，剩下 20 人吸收全部工作；对 500 行 diff 的评审 30 秒就给出 LGTM；一位 DevOps 负责人正准备按照 Opus 5.5 的建议在所有地方关掉 JVM JIT，而真正的修复只是改动一行库代码。
- [titzer](https://news.ycombinator.com/item?id=50521192): 来自 Virgil 编译器维护者的反例：Claude 在约 3 天内产出了一个可用的 arm64 后端，并在 3 小时内产出了一个完整的 RISC-V 后端，两者都通过了完整测试套件——这说明 AI 可以加固核心基础设施，而不只是生成垃圾。

**值得一读的评论**
