## 2. A 40ms Go garbage collector pause caused by swap {#story-2}
*#4 on HN · [frn.sh](https://frn.sh/go-gc/) · 63 points · 28 comments · [HN discussion](https://news.ycombinator.com/item?id=49959654)*

A blog post by frn.sh describing a production experiment where enabling swap to absorb memory spikes caused Go's stop-the-world GC pauses to balloon. In a cgroup on a Hetzner box (kernel 6.8, MGLRU enabled), median GC pause was ~51us, but when GC metadata pages had been evicted to NVMe the worst pause hit 40ms — 39 of those milliseconds spent on 228 page faults inside runtime bookkeeping like spanSet.reset, finishsweep_m and nextMarkBitArenaEpoch, across 312 STW pauses in 30 minutes. Building one 511 KiB message normally 3-5ms jumped to 105ms on NVMe and 903ms on Hetzner's network volume; an update notes Go 1.26's Green Tea GC shows negligible change here.

**Discussion**: The thread largely agrees that swap and GC don't mix, but disagrees on the fix. Several commenters (jacobgold, xxs) say the answer is to disable swap for latency-sensitive workloads or that swap is 'universally bad' for GC languages, while delamon argues that's incomplete: code pages can still be paged out, and mlock()/mlockall() (or selectively mlocking STW-touched pages, per quotemstr) is the real protection. nasretdinov says this is expected because any tracing GC must walk the whole heap, destroying the swap LRU every cycle — a claim pjmlp pushes back on, noting reference counting is itself a GC algorithm and behavior depends on implementation, though others counter that refcounting has per-allocation overhead and unbounded deallocation chains. On-the-fly GC (DLG, Fil-C's FUGC) and Go's existing concurrent mark-sweep design come up, with klodolph noting Go's STW is already tens of microseconds and that pause-vs-throughput is an inherent tradeoff; the recurring takeaway is that GC latency SLOs should account for OS memory pressure, not be diagnosed as a collector bug.

**Worth reading**
- [delamon](https://news.ycombinator.com/item?id=49961142): Counters the 'just disable swap' advice: code pages can still be evicted, so mlock() is the right protection and swap actually gives the kernel an even choice between data and code pages.
- [pizlonator](https://news.ycombinator.com/item?id=49960828): First-hand GC expertise: explains the classic on-the-fly DLG algorithm, links the POPL'94 paper and Fil-C's FUGC source, and contrasts permagrey stacks with Go's coroutine scan overheads.
- [xavdid](https://news.ycombinator.com/item?id=49961326): Points to Discord's 2020 write-up on why they moved from Go to Rust, a well-known precedent for Go GC latency trouble.

## 4. Infidel goes wild {#story-4}
*#7 on HN · [blog.zarfhome.com](https://blog.zarfhome.com/2026/10/infidel-goes-wild) · 122 points · 19 comments · [HN discussion](https://news.ycombinator.com/item?id=49943637)*

Andrew Plotkin (Zarf) analyzes Infocom's 1983/1984 adventure game Infidel using his Visible Zorker tool and finds a wild-pointer bug that corrupts Z-machine memory. The ZIL compiler initializes the DESERT-TO-TABLE routine's TBL argument default to the global variable's index number (30) instead of the array address (11129), so dropped-object bookkeeping writes over addresses 30 and up. After dropping nine objects in the Endless Desert, the overwrite reaches the abbreviations table at address 64, garbling printed text (replacing 「the」 with 「You」) or crashing the interpreter — a bug that shipped unnoticed because nobody drops many items in a featureless desert.

**Discussion**: Commenters are mostly delighted: kwertyoowiyop jokes that no 1980s game programmer can claim a clean record on memory-trashing bugs, and several tell their own C corruption war stories (a staff engineer baffled by an intern's bug, a text editor that made Windows 95 demand reinstallation). saghm reassures morkalork that writing real-world C and writing memory corruption bugs is effectively a circle. kqr gives a long, enthusiastic primer on the still-thriving interactive fiction scene — IntFiction.org forums, free competition releases, and a recommended IFDB search for modern parser games — while warning that the parser convention must be learned and old classics are a bad starting point. A parallel thread has jdw64 asking how to write technically interesting posts, drawing practical advice: write up your own experience (ajkjk), follow random inspirations and don't make every post the same weight, as Julia Evans does (zem), and compile existing journals into a public piece (embedding-shape).

**Worth reading**
- [kqr](https://news.ycombinator.com/item?id=49961436): A detailed guide to the current interactive fiction community, why parser-game conventions must be learned, and a curated IFDB search for modern games to start with.
- [Waterluvian](https://news.ycombinator.com/item?id=49959592): Wry pushback on the article's framing that memory corruption is the worst of all sins, quoting the line as 「Self-flagellation considered harmful.」
- [zem](https://news.ycombinator.com/item?id=49959347): Practical blogging advice: write up random career inspirations as short replies first, and model posts on Julia Evans' jvns.ca approach of varying depth and weight.

## 7. The Tao of Backup {#story-7}
*#10 on HN · [taobackup.com](http://www.taobackup.com/index.html) · 105 points · 25 comments · [HN discussion](https://news.ycombinator.com/item?id=49932236)*

The linked page, taobackup.com, is an old, multi-page, plain-HTML humor essay that teaches backup strategy through Zen koans — a novice who backs up only working files loses three days reinstalling software after a crash, and the punchline has the master confirming the whole thing exists to sell more copies of “Veracity.” The article text could not be fetched (the page is effectively unreadable to the scraper), so this summary rests on the title, the post and the koans quoted in the thread. Commenters note the site is still up decades later and that even in 1997 its multi-page layout was a pain to read.

**Discussion**: The thread splits into nostalgia, jokes and a long, genuinely technical tangent on backup media. One top comment points out that the koan's lesson is now largely moot because NixOS lets you back up a single declarative config file and rebuild a byte-identical system in minutes. A detailed storage-cost survey argues that an 8TB HDD is still the best JBOD option, that 25GB BD-R is the cheapest media for dozens of sub-25GB projects (about 35% cheaper than large HDDs above 12TiB, with 50/100GB discs a worse deal), and that HPE LTO9 tape is 5–15x cheaper per byte than HDD/SSD but carries high drive/autoloader fixed costs and single-point-of-failure risk — prompting the classic “fast, cheap or good, choose two.” Others push back that Blu-ray makes no sense at any level: writers are getting rare and the 25GB capacity limit wastes space, so a plain hard drive wins on utility even if $/GB is slightly worse. On cloud, one commenter calls S3 Glacier “tape-as-a-service” and another counters that S3 restore is too expensive and must be tested to be trusted. Minor notes flag that the site is HTTP with no valid cert, and that total personal data minus media is tiny (~1.57GB over 40 years).

**Worth reading**
- [dbdr](https://news.ycombinator.com/item?id=49961123): Argues the koan's reinstall-your-system lesson is obsolete: NixOS lets you back up one text file describing the system and rebuild it bit-for-bit identical in minutes.

- [Terr_](https://news.ycombinator.com/item?id=49961236): Counters the Blu-ray-immutability argument: encryption and signed checksums are the right defense against external tampering, with read-only date-bounded copies mainly useful against a compromised backup process.

## 8. Turn off Apple Intelligence on macOS 27 and get its disk space back {#story-8}
*#11 on HN · [github.com](https://github.com/omlahore/RemoveMacAI) · 515 points · 323 comments · [HN discussion](https://news.ycombinator.com/item?id=49957116)*

RemoveMacAI is an open-source macOS 27 tool (omlahore/RemoveMacAI on GitHub, also on a Homebrew tap) whose README argues Apple no longer provides a single switch for Apple Intelligence and that its downloaded models stay on disk after the features are turned off. It disables Siri (including 「Hey Siri」 and the menu-bar icon), Writing Tools, Genmoji, Image Playground, the ChatGPT extension, Mail/Messages/Safari/Notes/notification summaries, smart replies, inline predictions, Spatial Photos, Photos Clean Up and Xcode predictive completion, then deletes the foundation and image/Genmoji/Spatial Photos/Clean Up/Xcode models. It installs via curl|bash or Homebrew, uses an Apple-approved configuration profile plus Apple's asset service (SIP stays enabled, changes are reversible), and redirects model re-downloads to a closed local port; releases carry a GitHub Actions build provenance attestation.

**Discussion**: The thread splits between people who read this as Apple following Windows into debloat territory — the top comment calls it the same pattern as Windows de-crufting — and people who push back that Apple Intelligence required an explicit opt-in, that the new Spotlight and Siri are genuinely better for them, and that calling local-first on-device models 「crapware」 is unfair. The sharpest concrete complaint is storage: the models are put at about 12 GB (roughly 10% of a 256 GB machine, said to be non-functional on a 256 GB Mac mini), and several note the auto-download happens with no user-facing off switch even after the features are disabled, with some saying they will now stay on macOS 26 or move to Linux (KDE/CachyOS, Fedora). A recurring correction is that 「consent」 is a fuzzy line — commenters point out years of shipped ML features (handwriting recognition, face detection, Core ML) and ask why this one is different — while others counter that a disabled feature should not consume disk. A large sub-thread attacks the curl|bash installer: defenders cite the SHA-256 checksum and build attestation, while critics note the attestation is never verified inside a pipe, that it covers only the payload and not the mutable main-branch shell script, and that the suggested Homebrew route just points to a random third-party tap; iOS users separately report there is no simple toggle there either and call the language-swap workaround user-hostile.

**Worth reading**
- [woodruffw](https://news.ycombinator.com/item?id=49958044): Security engineer points out the build provenance attestation is worthless in a curl|bash install because nothing verifies it, and it covers only the payload — not the shell script, which is fetched from mutable main.
- [macintux](https://news.ycombinator.com/item?id=49959301): First-hand report that the new Siri on an iPhone 15 Pro is slower and now forgets reminders (「Remind me in 2 hours」 asks what to do in 2 hours), an argument for reverting.
- [m463](https://news.ycombinator.com/item?id=49960137): Lists 693 running processes on their Mac and names 60+ they consider unnecessary telemetry/ads/AI daemons (adprivacyd, mediaanalysisd, siriknowledged, spotlightknowledged), a concrete inventory of the bloat being discussed.

**Discussion**: 评论区迅速变成一封推荐信合集，多数人质疑作者为何没考虑 iCloud+ 自定义域名（尤其因为他要 Apple Mail 集成）、Fastmail、Protonmail、Migadu、MXRoute、Zoho、StartMail 或 Google Workspace，有人指出 MXRoute 黑五终身套餐 $99 是好买卖，Protonmail 需付费的 Bridge 才能用第三方客户端。self-hosting 之争最激烈：一派说 Gmail/Outlook 的垃圾邮件过滤让自托管信封基本发不出去（有人配置了 SPF/DKIM/DMARC 仍无效，最终转向 AWS SES），另一派（以自托管者自居）称这是被科技巨头渲染的夸大说法，配好 SPF/DMARC 且 IP 不在黑名单就基本一劳永逸；作者本人回应说不信任自己服务的稳定性。一个反复出现的反驳是针对 iCloud 的：多位用户（含一手经历）称 iCloud Mail 会静默丢弃含特定词句的邮件，不通知收发双方、也不进垃圾箱。此外 FounderMail 创始人 adospace 亲自现身解释人工审批是为防垃圾邮件（几乎 4 周零投诉、退信率低于 0.1%），但也承认体验烦人、正在改进；有人吐槽该服务官网疑似 AI 生成。

**Worth reading**
- [lucb1e](https://news.ycombinator.com/item?id=49958893): 自托管邮箱的用户反驳「不可能」论：只要设好 SPF/DMARC、IP 不在封禁段、域名不是已知发信人，基本无需操心，并举例 Apple 曾封掉一个荷兰议会文件通知服务。
- [sherry-sherry](https://news.ycombinator.com/item?id=49958660): 一手经历：iCloud Mail 会静默过滤含特定词句的邮件（连附件内容也算），既不进垃圾箱也不通知收发双方，直接删除、无从申诉，作者最近一次发生在 2026 年 6 月，@mac.com、@me.com、@icloud.com 和自定义域名都受影响。
