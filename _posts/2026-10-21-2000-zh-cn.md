## 1. PHP 8.2.35 {#story-1}
*HN 第 1 名 · [github.com](https://github.com/php/php-src/releases/tag/php-8.2.35) · 848 分 · 476 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50180873)*

PHP 8.2.35 的 GitHub 发布页面。这是一个安全版本，修复了两个漏洞（CVE-2026-109618 和 CVE-2026-109619），PHP 团队称这两个漏洞可被用于未授权的远程代码执行，并直言「不存在完整的缓解措施，升级是唯一安全的选择」。它属于一次多版本协同补丁发布的一部分（8.3.36、8.4.27、8.5.12），同时提醒用户 PHP 8.2 将于 2026 年 12 月 31 日停止支持。

**讨论**: 讨论串的大部分内容不是关于补丁本身，而是关于漏洞披露的处理方式：批评者称 OpenAI、Wiz 和 Calif 把这个漏洞压了两个月，做了 php2shell.com 之类的造势网站，弄丢了禁发令（embargo），迫使官方仓促发版，而各发行版和容器镜像的软件包却迟迟跟不上。另一些人则强烈反驳，指出 Wiz 是在 8 月 24 日上报的，PHP 安全团队直到 9 月 21 日才确认，而且发布修复等同于发布细节——延误是 PHP 方面的，不是报告者的。第二类讨论纯粹是运维层面的痛苦：官方 php Docker 镜像花了大约三个小时（期间出现的占位 tag 实际根本拉不下来），Ubuntu、Amazon Linux 2023 和 Linode 的镜像源落后于 Debian，PECL 返回 504，还有人发现刚构建出来的镜像里仍然是未修复的 8.4.26 和 8.3.35。Ondřej Surý 的 deb.sury.org PPA 和 Remi 的 RPM 收获了大量感谢，也有人呼吁公司出钱资助它们，Debian 则因在几分钟内就发布更新而被反复称赞。技术层面的质疑也出现了：一份流传的、声称可 RCE 的 PoC 已被撤回；而修复本身是在一个基于 longjmp 的 C 代码库里散布数千处 ZEND_HAS_OOM() 检查，有人怀疑这些检查并不完备。没有人认为 PHP 会消失；共识是打补丁、做隔离，并接受这样一个现实：借助 agent 的补丁差分分析已经让旧的禁发令模式失效。

**值得一读的评论**
- [tetraodonpuffer](https://news.ycombinator.com/item?id=50181334): 给出了重新界定责任归属的时间线：Wiz 于 2026 年 8 月 24 日上报，而 PHP 直到 9 月 21 日才确认并开始修复。
- [benibela](https://news.ycombinator.com/item?id=50184174): 指出一份 PoC 已被撤回，并称 CVE-2026-109618 其实并不是 RCE，因为一次 addref 调用阻止了 use-after-free；而 CVE-2026-109619 属于内存不安全，但不构成 RCE。
- [bombcar](https://news.ycombinator.com/item?id=50180939): 一份针对 WordPress 机器的详细临时缓解清单——禁用 session.upload_progress、在 Web 服务器层拦截 multipart 请求体、设置 pm.max_requests=1、调低 post_max_size——不过另一位评论者立刻指责这是未经核实的 LLM 输出。

## 3. PyPI 上被污染的 LiteLLM 1.107.0 会安装凭据窃取程序和后门 {#story-3}
*HN 第 3 名 · [safedep.io](https://safedep.io/litellm-pypi-compromise-credential-stealer-backdoor/) · 254 分 · 98 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50181114)*
*原标题: Compromised LiteLLM 1.107.0 on PyPI Installs a Credential Stealer and Backdoor*

SafeDep 对 PyPI 上 LiteLLM 1.107.0 版本的拆解分析：所有 wheel 包都在 site-packages 中携带了三个文件——cook.pth、cook.py 和 sitecustomize.py——它们会在主机上的每一个 Python 进程中运行，即使该进程从未 import litellm。该窃取程序会收集 SSH 密钥、云凭据、CI/CD 机密、浏览器密码、AI 工具令牌（Claude Code、Cursor、Codex、opencode……）以及 LiteLLM 代理数据库中的各家提供商密钥，用内置的 RSA-4096 公钥加密后 POST 到 www.litellm[.]dev；sitecustomize.py 会启动一个每小时运行一次的守护进程，该进程从一个已被删除的 GitHub 仓库（letters9813）读取服务器地址，并 exec() 下载来的代码。1.106.2、rc1 和 rc2 是干净的，该发布与它的 tag 不匹配（pyproject 中的版本号从 1.108.0 被回退），没有任何公开的 GitHub Actions 运行构建过它，PyPI 上也没有来源证明（provenance attestation）。

**讨论**: 最主要的反应是愤怒：这是 LiteLLM 今年第二次供应链被攻陷，多位评论者认为重复发生这种事属于失职，而非运气不好。一个反复出现的观点主张在 uv、npm 和 pip 中默认设置 24–48 小时的依赖冷却期，但其他人反驳说，真实攻击往往潜伏数月才被发现，冷却期只是推迟发现、会挡住安全更新，而且知道有冷却期的攻击者只要等过去就行。在防御手段上，一条被广泛阅读的评论指出，来源证明在这里帮不上忙，因为它只能证明是哪个 workflow 发布了 wheel，而不能证明它构建的是哪份源码——只有从公开 tag 重新构建并做 diff 才能发现。官方的事件响应遭到批评，因为它一边告诉用户锁定 1.106.2，一边把企业客户引向一个私有 registry，那里存有另一个漏洞的禁发期修复，该漏洞定于 10 月 27 日披露；为其辩护的人把它比作 Red Hat 和 OpenSSL 的禁发期做法，而一个子讨论串则认为这个类比有误导性，因为厂商只是提前准备好软件包，并不会提前把禁发期漏洞的修复交付给付费客户。另一个并行的讨论串关于迁移：从未信任过 LiteLLM 的人在问该换用什么，答案从用 Go 重写（GoModel、sturnus、自制的密钥注入代理）到 Pydantic AI 都有，而持怀疑态度的人指出，网关仍然能提供故障转移、预算控制和集中配置。

**值得一读的评论**
- [aakashpawar](https://news.ycombinator.com/item?id=50183906): 来源证明在这里救不了任何人——它只能证明是哪个 workflow 发布了 wheel，而不能证明它检出的是哪份源码；只有从公开 tag 独立重新构建才能发现这个问题，而几乎没有人会对 Python wheel 这么做。
- [hmokiguess](https://news.ycombinator.com/item?id=50183423): 引用了 BerriAI 的 issue #47826：开源用户应锁定 1.106.2，而企业客户会得到一个禁发期版本，用于修复另一个定于 10 月 27 日披露的漏洞。
- [petesergeant](https://news.ycombinator.com/item?id=50183637): 纠正了与 Red Hat 的类比：厂商会收到禁发期通知，以便在禁发期解除时软件包已经就绪，但他们并不会提前把禁发期漏洞的修复交付给付费客户。

## 4. 当年编译器也曾被认为会终结编程 {#story-4}
*HN 第 4 名 · [hrih.si](https://hrih.si/articles/the-compiler-was-supposed-to-end-programming/) · 30 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50185045)*
*原标题: The compiler was supposed to end programming too*

一篇文章认为，AI 编程代理只是 70 年自动化历程中的最新一步，而不是编程的终结：IBM 在 1954 年的 FORTRAN 报告中承诺「几乎消除编码与调试」，1981 年的 BASIC 代码生成器 The Last One 则宣称自己是任何人需要购买的最后一个程序。文章引用了 Stack Overflow 2025 年的调查（采用率 84%，但正面态度从 77% 降至 60%，66% 的人对「几乎正确，但不完全对」的输出感到沮丧）、METR 的随机试验（16 名经验丰富的开发者在有 AI 辅助时慢了 19%，却自认为快了 20%），以及 Faros AI 的数据（拉取请求更多，但评审时间中位数变为五倍，未经评审就合并的 PR 增加了 31%）。文章随后警告初级人才通道正被切断：Stanford/ADP 的数据显示，22 至 25 岁开发者的就业人数较 2022 年末的峰值下降了近 20%，这引出了一个问题：如果代理接手了常规工单，未来的资深工程师要在哪里学会判断代码。

**讨论**: 讨论帖基本是在反驳文章的编译器类比，而不是回应其中的 METR、Faros 或初级招聘数据。gonzalohm 认为编译器处理的是形式化定义的语言，因此 float x = 3.1 这样的语句含义是确定的，而「创建一个变量 x 并赋值为 3.1」这样的请求则在类型、精度和意图上留有开放空间；coldtea 直言这个比较很糟糕。cwoolfe 等人则反驳说，LLM 编程只是下一个抽象层，并指出 COBOL、SQL、4GL 和 BASIC 都是更早尝试用更接近自然语言的方式来编程的例子。一个旁支讨论把 AI 比作终端带来的转变：dvh 称终端终结了计算机机房里的社交文化，并把女性推离了这个领域，而 david-gpu 则将这一变化归因于人们更看重薪水。整体情绪是怀疑的——misano 问这篇文章是不是「自我安慰」，mbil 则开玩笑说文中 2031 年的某个周二已经描述了他今年的早晨，只不过他 7:40 并不在上班。

**值得一读的评论**
- [gonzalohm](https://news.ycombinator.com/item?id=50185781): gonzalohm 从形式化角度否定编译器类比：编译器翻译的是具有确定语义的既定语言，而自然语言指令在类型、精度和意图上都是模糊的。
- [cwoolfe](https://news.ycombinator.com/item?id=50185667): cwoolfe 认为，LLM 辅助编程只是人们在长期寻找自然语言编程的过程中出现的下一个抽象层。

## 5. 八比特的信任；eMudhra 的 CA 密钥在毫秒内被破解 {#story-5}
*HN 第 5 名 · [scotthelme.co.uk](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/) · 693 分 · 329 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50177916)*
*原标题: Eight Bits of Trust; eMudhra's CA keys cracked in milliseconds*

Scott Helme 的一篇博文，内容是 eMudhra 八个中间 CA 私钥的恢复过程。这些密钥本应是 384 位的 P-384 椭圆曲线标量，结果却成了单字节整数（4、56、115……），任何人都可以通过逐一尝试最多 255 次点乘法，在不到一秒内找回来。被攻破的八个中间证书是 2025 年 4 月签发的六个 TLS 签发 CA（DV/OV/EV，两代）和两个代码签名 CA，2025 年 5 月又由 Sectigo 的 AAA Certificate Services 根证书交叉签名。Helme 只用本地服务器和一张伪造的 api.stripe.com 证书做测试，系统默认配置下的 curl、Python 和 Node 都接受了它；原因是大多数非浏览器客户端使用磁盘上自带的 CA 包，既不做证书吊销检查也不检查 CT。于是，无法更新的路由器、电视和 IoT 设备要到证书 2039 年 7 月过期之前，一直信任这些密钥。

**讨论**: 讨论很快分成三类。第一类是影响范围：有人指出，大量工具会自己捆绑 CA 包，例如 pip、Node、bun、Java keystore.jks、Flatpak 运行时和容器基础镜像，因此只更新系统 ca-certificates 包并不能解决全部问题。Scott Helme 确认了这个“长尾问题”，并说这类固定包只包含根证书，不会检查证书吊销。第二类是出路：有人用泄露的密钥对 Google Home 音箱做中间人攻击，还有人成功提取了两台难以破解的 ESP32 设备的固件；也有人提出在自己的网络上架设反向代理，以保护无法更新的设备，Helme 认可这一做法。第三类是动机：几位评论者坚称只可能是蓄意或国家级行为，另一些人反驳说，CA 本来就持有可用于中间人攻击的密钥，没有必要故意制造容易被猜到的密钥；Mozilla 的 bug 报告显示，是密钥生成仪式脚本的一个缺陷在 HSM 上产生了第二对弱密钥，它和正常密钥的标签相似，被人误用来生成 CSR。有人发现，这些密钥中有两个连续数字，而且八个数写出来在键盘上都是自左向右的笔画，这支持“序列号或手工挑选”的推测。另外，多位评论者质疑文章是 AI 写的，因为某些段落读起来像大模型润色；Helme 回应说，全文由他本人撰写，只在最后让 Claude 做了一次微调。

**值得一读的评论**
- [mminer237](https://news.ycombinator.com/item?id=50180736): 引用 Mozilla bug 2083449 中 eMudhra 的解释：当日密钥生成脚本的一个偏差先创建了原本该有的 ECC 密钥，代码缺陷又生成了第二对弱密钥，由于标签相似，人误用了后者生成 CSR 并送去 Sectigo 交叉签名。
- [muvlon](https://news.ycombinator.com/item?id=50178723): 推测成因是序列号被当作私钥，或私钥被截断成 8 位；并用蒙特卡洛模拟指出，从 0..255 均匀抽 8 个数出现两个连续值的情况只有约 18% 的概率。
- [cromka](https://news.ycombinator.com/item?id=50180981): 第一手经验：评论者自称用 DeepSeek 快速复现了信任链攻击，发现 Google Home 音箱仍未更新证书链，正在做中间人抓包，尝试借此取得 root 权限，或做 Home Assistant 的模拟端点。

## 6. DuckDB 2.0.0 LTS “Cinnamon Teal” {#story-6}

## 17. C++ futures 第一部分：心智模型 {#story-17}
*HN 第 23 名 · [devblogs.microsoft.com](https://devblogs.microsoft.com/oldnewthing/20261012-00/?p=112767/) · 51 分 · 10 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50155751)*

Raymond Chen 在 The Old New Thing 上的一篇文章，把标准库的 futures 机制——std::promise、std::packaged_task、std::async、std::future、std::shared_future——拆解为其共同的构建块，他将其重新命名为「source」（标准称之为 shared state）。他勾勒了它的实现：一个 union，存放空、值或异常三者之一，由互斥锁保护，并用条件变量支持定时等待；其语义是只能设置一次，重复设置会抛出 future_error(promise_already_satisfied)，而值被取走后再次取用会抛出 future_already_retrieved。这是系列文章的第一篇——后续部分将涵盖 promise/packaged_task 和 std::async——他提到自己写这篇文章的部分原因是总记不住它是怎么运作的。

**值得一读的评论**
- [jandrewrogers](https://news.ycombinator.com/item?id=50183700): 纠正了「协程/async 的状态必须分配在堆上」这一常见说法：堆分配只是默认做法，只要不怕麻烦，静态分配是可行的。
- [lukaslalinsky](https://news.ycombinator.com/item?id=50185664): 解释说 std::atomic::wait/notify_all 就是标准中的 futex 抽象，因此真正的局限只在于没有 std::atomic::wait_for。

## 20. Show HN: Sumi.css – CSS 框架 {#story-20}
*HN 第 29 名 · [github.com](https://github.com/vladocar/Sumi.css) · 57 分 · 13 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50180039)*
*原标题: Show HN: Sumi.css – CSS Framework*

Sumi.css 是 vladocar 打造的一个单文件、无依赖的 CSS 框架，为纯语义 HTML 添加样式而无需任何 class：标题、表单、表格、卡片、折叠面板、模态框和导航都仅靠标签即可工作。它压缩并 gzip 后仅 6.7 KB，遵循系统的浅色/深色设置，并可通过任意元素上的 data-theme 覆盖；它将所有颜色、字体、圆角与间距值暴露为 --s-* 自定义属性，并把元素样式包裹进 :where() 中，因而特异性为零、覆盖起来毫不费力。它依赖 :where()、:has() 和 color-mix()，也就是说需要 Chrome/Edge 111、Firefox 121 和 Safari 16.2 或更新版本；压缩后的构建产物由 lightningcss-cli 生成。

**讨论**: 讨论串以赞赏为主，很快变成了贴链接大会：有人惋惜 PicoCSS 如今已被弃用，并推荐各种替代品，包括 Sakura、classless-css 的 GitHub 清单、dropin-minimal-css 以及 Neat CSS：其作者指出它只有 3 KB。最尖锐的批评针对的是语义而非代码：Harry Roberts（csswizardry）反对文档中把带真实跳转目标的 anchor 标上 role=button 的示例，称这会制造虚假可供性。被提议作为 Pico 继任者的 Blades CSS 受到质疑：一位评论者说该网站完全没有向新用户解释自己，另一位则抱怨其新增组件是基于 class 的，与 Pico 的前提相矛盾；在原作者要求 fork 改名的情况下，其 fork 路径中仍保留着 Pico 之名；还有人质疑标题中首字母被 em 包裹的奇怪做法。另有一位评论者报告了一个被登记为 issue #1 的小 bug，还有一位开发者举出具体收益：把一份 HTML 文件和一份无 class 样式表交给非技术的同事，让他每周编辑并上传到 S3。关于框架本身没有真正的分歧：共识是它看起来不错，而且这个品类正在悄然繁荣。

**值得一读的评论**
- [csswizardry](https://news.ycombinator.com/item?id=50185022): Harry Roberts 认为，给一个带有真实跳转目标的链接加上 role=button 是错误的，因为这等于宣称该元素拥有它并不具备的按钮可供性。
- [xd1936](https://news.ycombinator.com/item?id=50185228): 对作为 Pico 继任者的 Blades CSS 的一番细致批驳：基于 class 的组件、在原作者已要求改名的情况下仍名为 anyblades/pico 的 fork，以及令人困惑的网站设计。
- [elicash](https://news.ycombinator.com/item?id=50182400): 一个亲身用例：无 class 框架让一位非技术同事能够每周安全地编辑单个 HTML 文件并重新上传到 S3。
