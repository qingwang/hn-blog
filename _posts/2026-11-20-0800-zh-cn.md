## 1. Jujutsu 入门指南 {#story-1}
*HN 第 1 名 · [ethanlowman.com](https://ethanlowman.com/posts/jj-primer/) · 54 分 · 32 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50570628)*
*原标题: Jujutsu Primer*

Ethan Lowman 的一篇教程式文章，写给已经会用 Git 的人，介绍 Jujutsu（jj）：通过 cargo 或 nixpkgs 安装，在已有仓库里运行 jj git init，此后 jj 与 Git 保持同步。文章走了一遍核心模型——对工作副本的每一次编辑都会自动快照成一个提交（没有暂存区），提交同时带有一个 Git commit ID 和一个稳定的 change ID，空提交可以在动手之前就写好描述，而 jj new / jj edit / jj commit 让你在一个无分支的提交图上移动。文章还演示了 revsets（借自 Mercurial），例如 @-、k:: 和 author(...) & (k | q)，并宣传自动 rebase 和原生 undo 能磨平 Git 的棱角。

**讨论**: 最热的讨论串围绕 Jujutsu 的 Git 兼容性：danpalmer 在一个大型工作 monorepo 上用了 jj 两年多，认为它在那种场景下表现出色，但他跑在自定义后端上，并且希望有专为 jj 打造的 forge，而不是去追 Git 兼容。ezst 则反驳说，正是脱离 Git 仓库格式这一点把 Mercurial 推向了默默无闻，尽管它 UX 更好。其他人回击说，Git 自己当年也是在格式不兼容的情况下取代了 CVS；danpalmer 补充说 GitHub 的吸引力已经减弱，而 Git 的扩展性问题（forge、大型 monorepo）如今已被广泛感受到。缺失的暂存区让人分成两派：一些人持怀疑态度，而 ozim 认为 GUI 工具里按 hunk 暂存才是教会人们精心整理提交的东西，「直接把东西提交上去」是另一种做法。一个很大的子讨论串关于 AI agent：实践者报告说 jj 的 squash 工作流与 Claude 配合极佳，20 多个提交的堆叠链现在可行，但好几个人说 agent 工具默认假设使用 Git，迫使他们退回去，直到他们写了 AGENTS.md/skill 文件或改用 colocated worktree；一位评论者指出 Google 的 Antigravity 技术栈一直在增加 jj 支持。一个反复出现的抱怨是：入门文章只教命令，却不教一个好的提交历史长什么样。

**值得一读的评论**
- [danpalmer](https://news.ycombinator.com/item?id=50570993): 一位在大型 monorepo 上每天用 jj 已有两年的用户说，jj 在那里表现出色，但他跑在自定义后端上，并且想要为 jj 本身打造的 forge，而不是 Git 兼容。
- [ezst](https://news.ycombinator.com/item?id=50571150): 认为正是 Git 格式兼容性让 jj 免于重蹈 Mercurial 的覆辙，因为失去 GitHub 访问权正是 hg 尽管 UX 和技术都更优却逐渐消失的原因。

## 3. OpenSSL：EVP_EncodeBlock() 中的缓冲区溢出（CVE-2026-121481，CVSS 9.8） {#story-3}
*HN 第 3 名 · [github.com](https://github.com/openssl/openssl/pull/33652) · 188 分 · 135 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50569226)*
*原标题: OpenSSL: Buffer overflow in EVP_EncodeBlock() (CVE-2026-121481, CVSS 9.8)*

一个针对 OpenSSL 的 GitHub 拉取请求，用于修复 CVE-2026-121481，即 EVP_EncodeBlock() 中的缓冲区溢出。EVP_EncodeBlock() 是执行 base64 编码的 API，对一块数据编码且没有输出长度参数。当输入长度足够大（约超过 1.5GB，即编码后的长度无法再放入有符号 int 时），调用方自己的长度计算或实现本身会写出缓冲区边界之外，从而触发溢出；该补丁还加固了 EVP_DecodeBlock()，修复了 http_client.c 中 base64encode() 里一处错误的长度检查，并在 test/base64_dec_avx2_test.c 中补充了测试。该 PR 最初的方案是对 NULL 缓冲区、负长度和超长长度返回 -1，但评审者反驳了这一做法，他们指出 0 是合法的成功返回值，而第三方调用方若把返回值转换为 size_t，就会错误处理这个新的错误码；最终版本对以往会导致未定义行为的输入改用 OPENSSL_assert()。报告者指出，可以从命令行用带巨大 -proxy_pass 参数的 openssl s_client 触发该问题（通过 env:VAR 提供），并且这个缺陷与 CVE-2021-23840 相似。

## 4. FFmpeg 9.1 'Gauss' {#story-4}
*HN 第 4 名 · [ffmpeg.org](https://ffmpeg.org/download.html#release_9.1) · 82 分 · 16 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50569998)*

这是 FFmpeg 官方为版本 9.1「Gauss」提供的下载与发布页面，该版本于 2026-11-20 发布，其发布分支于 2026-10-24 从 master 切出。页面本身主要是打包、PGP 校验和旧版本说明的套话；实质性的功能清单来自维护者 gyan 在评论中的发言。其中的要点包括大幅改进的 AAC 编码器、APV Vulkan 编码器、通过 libfdk-xhe-aac 实现的 xHE-AAC 编码、新增的 libcurl 与 Windows handle 协议、NVDEC CUARRAY 硬件加速，以及基于图的比特流过滤 API。

**讨论**: 评论者总体上表示赞赏，维护者 gyan 贴出的完整变更日志构成了讨论的主线。两条新增条目引发了疑问：一是 Windows handle 协议，回答中附上了 pull request 链接；二是 libcurl 协议，有评论者以为它是用于网络流的。一位用户抱怨默认构建被 strip 过且缺少 vidstabtransform；gyan 纠正说 vidstabdetect 和 vidstabtransform 都存在于 FFmpeg 中，也存在于他的所有构建中，包括 essentials 构建。其他人感谢 gyan 提供 Windows 构建，并询问为什么 winget 的 shared 构建有时无法注册 DLL，他将其归因于权限问题。主要批评集中在发布沟通过于单薄：一位评论者称那份原始的 RELEASE_NOTES 文件就是所谓的发布说明，gyan 表示新闻稿应会在一两天内出现，但另一位指出 9.0 的新闻稿至今仍不见踪影。

**值得一读的评论**

## 5. 「我能看出来这是你自己写的」 {#story-5}

这是一篇博文，作者是一名澳大利亚工程专业学生。他在做一个关于扑翼微型飞行器控制的荣誉项目期间，导师对他说：「我能看出来这是你自己写的」——因为导师已经收到过许多由 AI 撰写的报告。作者此前因为把日历上的截止日期设错了，在紧张的 48 小时冲刺中写了大约 10 页、约 5,000 字。他认为自己的学位项目实际上在积极推动学生使用 AI（作业要求的措辞从「强烈鼓励」变成了事实上必须使用，而他最难的一门课，是每天在无窗的机房实验室里花八个小时写提示词），并在结尾恳请不要把自己的思考自动化：去读书，去写论文，去问问朋友。

**讨论**: 这个讨论帖规模不大，整体上持同情态度，大家一致认为一个学生应当能独立写出一份 10 页的报告。主要的反对意见来自 sambejk：他认同文章的前提，但认为用 AI 做语法和拼写检查、以及把 AI 当作可以碰撞想法的审阅者是没问题的——他还指出，这篇文章本身就有一处把「write」写成了「right」。对此的回复出现了分歧：一位评论者讽刺地回答说，用 AI 加读垃圾内容反而更好；而 paganel 的观点相反——真实的人类语法错误令人耳目一新，并且「完美主义是扼杀人类创造力的敌人」。pascahousut 说自己希望存在一个健康的折中方案，bongofizzbuzz 则打了一个《I, Robot》的比方：在那里面，自己开车会被人皱眉头，因为 AI 在高速行驶时更安全；他预测类似的要求最终也可能被强制推行。

**值得一读的评论**
- [sambejk](https://news.ycombinator.com/item?id=50571274): 认同文章观点，但为用 AI 做语法、拼写检查和想法审阅辩护——还在阐述理由的过程中抓住了文章里一处真实的笔误（把「write」写成了「right」）。
- [paganel](https://news.ycombinator.com/item?id=50571507): 对此的直接反驳：打磨得完美无瑕的文字是一种损失，看到诚实的人类语法错误反而令人耳目一新——「完美主义是扼杀人类创造力的敌人」。
- [bongofizzbuzz](https://news.ycombinator.com/item?id=50571506): 一个带有推测性但令人印象深刻的《I, Robot》类比：一旦 AI 在某项任务上比人类更安全，自己亲手去做这件事可能就会在社交或法律层面遭到非议。

Zerodha 工程团队介绍了 Blobasaur：这是一个开源的 Rust 服务器，它使用 Redis 协议，在普通商用硬件上的众多 SQLite 分片上存储用户界面和工作区偏好等 blob（大多是 JSON，大小在 2 KB 到 5 MB 之间）。它取代了无人维护且只支持单节点的 SSDB；在测试之后，他们放弃了 ScyllaDB、Postgres BYTEA、SeaweedFS、S3/MinIO 和直接使用文件系统。他们在 tmpfs 上对 64 KiB 的 zstd 压缩 blob 做的基准测试显示，16 个分片优于 1 个分片：HSET 从 7,740 ops/s 提升到 25,324 ops/s（p99 从 10.7 ms 降到 8.3 ms），混合读写从 14,227 ops/s 提升到 29,538 ops/s，读性能基本持平，约为 70k ops/s；生产环境中 HSET 负载平均为 63.6 KiB，压缩约 11 倍后降至 5.5 KiB。持久性被有意放宽（synchronous=NORMAL，另有一个在提交前就返回确认的 async_write 模式），理由是这些数据属于非关键的 UI 状态。

**讨论**: 讨论的主线是质疑：anacrolix 写过类似的系统（possum），他说 SQLite 从来就不是为这种用途设计的，提交开销仍是瓶颈；也有人认为 RocksDB 或 LMDB 会是更合适的带事务的 KV 基础。第二场争论围绕文章承认删除行不会缩小 SQLite 文件这一点展开——一位评论者说，在发现这些有文档记载、可从第一性原理推出的常识之后仍然照此发布产品，会让人对项目失去信心；另一些人（包括 Simon Willison）则反驳说，惩罚这种「这是我学到的东西」式的文章会扼杀有价值的讨论，而且如今大多数人从不自己运行数据库服务器，这类知识已经淡漠了。那位批评者随后把攻击面扩大，链接到 Zerodha 自己关于 Postgres 的文章，引用 600 MB 的 work_mem、每个查询一张表、每天创建和删除数百万张表，作为其问题出在运维而非工具上的证据。评论者认为最大的实质性缺口是韧性：文章从未提到复制、一致性模型、故障转移或备份（仓库似乎用的是 cp，有人猜测是 Litestream），而且分片是静态的，所以节点宕机时无人处理——有几个人总结说，它解决了 Zerodha 那个范围狭窄、风险很低的具体场景，但不是一个可复用的数据库。被提到的替代方案包括存储 diff 并做压缩合并、把 JSON 规范化成 SQLite 列、ClickHouse，以及 Cassandra/ScyllaDB；rqlite 的作者也来插话说 rqlite 同样不合适，因为所有写入都要经过 Raft leader。

**值得一读的评论**
- [anacrolix](https://news.ycombinator.com/item?id=50559043): anacrolix 多年来一直试图把 SQLite 用在这个场景上，称它对多进程工作负载是死路一条，并贴出了自己的 possum 项目；即使在只用来存元数据和 TTL 时，SQLite 的提交/事务层仍然是瓶颈。
- [sgarland](https://news.ycombinator.com/item?id=50566492): 认为抽象并不能成为不理解所用工具的借口，并附上 Zerodha 自己那篇 Postgres 文章作为佐证——600 MB 的 work_mem、每个活跃查询一张临时表，以及每天创建和删除数百万张按查询生成的表。
- [gkamal](https://news.ycombinator.com/item?id=50562314): 具体拆解了「重复造轮子」的指责：Blobasaur 缺少真正的分布式方案（静态分片、没有容错、没有一致性模型），也缺少备份和恢复这类运维基本功，而这些在有状态基础设施上线后是很难补上的。

链接指向 Models Engineering Index（MEI），这是一个排行榜页面，按编程与智能体基准的综合评分对模型进行排名，目前将 Gemini 4 Neon 列为第一。可见表格显示：Fable 5.2（Anthropic）为 66.3，成本与 token 倍数为 5.9x/2.1x；Sonnet 5.5 为 57.9；K3.1 Pro（Moonshot）为 47.6；6.1 Terra（OpenAI）为 44.7；V4.1 Flash（DeepSeek）为 44.5；Haiku 5.5 为 43.4。页面本身几乎没有方法说明文字，只有条形图和逐模型的成本/token 对比。

**讨论**: 最实质性的批评针对这个指数本身：深入查看仓库的评论者发现，它是 TerminalBench、CursorBench、vals.ai 等的综合，而 Neon 只在 8 个基准中的 3 个上有评分，Fable 则有 6 个，且对缺失数据没有任何扣分——有几个人称其为凭感觉、自行提交的排名，而非真正的指数。与之相对，大量人报告第一手经验称该模型确实很强：在 monorepo 移植工作中比 Opus 5.5 更快、更便宜且质量相近，文笔更好、沟通更简洁，一位用户说花 $30 的 Neon 一天替代了花 $70 的 Opus 一天。怀疑者反驳说，每次 Gemini 的强势发布在基准上都好看，然后在实际日常使用中站不住脚；一份详细的负面报告描述 Neon 引入了四个 P1 回归、使五个现有测试失败，并且在它声称发现的 bug 中误诊了约一半，这些 bug 出现在一个 OpenGL 到 Metal 的桥接项目中。另一个子讨论串认为 Google 真正的问题在分发而非能力：混乱的模型命名（Hydrogen、Argon、Carbon、Neon）、Antigravity 的权限提示和缺少可用的自动模式，以及 $5、$20、$100 和 $200 各档位之间访问权限不一致。

## 20. 为 LLDB 添加 Fortran 支持（GSoC 2026） {#story-20}
*HN 第 50 名 · [blog.llvm.org](https://blog.llvm.org/posts/2026-09-07-gsoc-add-fortran-support-to-lldb/) · 40 分 · 15 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50521083)*
*原标题: Adding Fortran Support to LLDB (GSoC 2026)*

这是一篇发表在 LLVM 博客上的 Google Summer of Code 2026 博文，作者是一位贡献者，他在 LLDB 中实现了原生 Fortran 支持——此前 LLDB 只能基于原始行表设置断点。这项工作新增了 Fortran 语言插件、TypeSystemFortran 类型系统以及 DWARFASTParserFortran 解析器，覆盖基本类型（INTEGER、REAL、LOGICAL、COMPLEX）、函数与子程序、指针和数组——包括列主序布局、自定义上下界与步长、针对 A[2] 这类查询的中间子数组切片，以及带无界索引的假定大小数组。作者指出，该 RFC 花了约两个月才达成共识；补丁正在逐步合入（例如针对基本类型的 PR #218269），并配有 C++ 单元测试和 Python SB API 测试，以及 x86_64/AArch64 构建机器人；通过 Flang 进行表达式求值的工作被推迟，且 LLDB 目前尚未链接 Flang。
