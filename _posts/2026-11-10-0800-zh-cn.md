## 1. Amazon 用 Strands Decider 替代 Sonnet 4.6，节省数百万美元 {#story-1}
*HN 第 1 名 · [strandsagents.com](https://strandsagents.com/blog/amazon-saves-millions-replacing-sonnet-with-strands-decider/) · 147 分 · 41 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50436640)*
*原标题: Amazon saves millions by replacing Sonnet 4.6 with Strands Decider*

这是一篇由两位 Amazon 工程师 Carr 和 Mehul 撰写的 AWS 博客文章，描述他们如何用 Strands Decider 替代 Claude Sonnet 4.6。Strands Decider 是一个小型开源决策模型，采用 Gemma 4 的 E4B 构建版本，用于在 Amazon 内部工单系统中把工单归类到 20 个类别之一。他们声称在 token 成本降低 98% 的情况下，标签质量达到持平或更好：每百万张工单的成本从约 22,200 美元降至约 500 美元，平均调用延迟从 4,215 毫秒降至 897 毫秒，每张工单消耗的 token 从 6,724 降至 2,010；模型部署在 SageMaker ml.g5.xlarge 实例上，该实例配有一块 A10G，模型权重约 19 GiB。他们把这项成果归功于一个由 AppConfig 控制的三路开关，该开关可在 BEDROCK、DUAL、DECIDER 三种模式之间切换，让两个模型同时处理线上流量，并只需改一次配置就能回滚。他们还提醒说，JSON 键的顺序变化会使输出概率偏移最多 0.19，而且这种方案只适用于封闭选项、高流量、短上下文的场景。文章有些地方读起来像是为 AWS 一个月前推出的模型所做的产品案例研究。

**讨论**: 讨论基本上把这件事看作向经典机器学习的回归：有几位评论者质问，既然 SVM、scikit-learn 或 BERT 能更快更便宜地完成这件事，为什么当初要用 LLM 把工单分进 20 个桶？其中一位评论者附上了一篇 2021 年 ICSE 论文的链接，讲的是他自己搭建的基于 SVM 的日志分类流水线。最有力的反驳论点是：经典分类器需要带标注的领域数据和一名数据科学家，而 LLM 让人几分钟内就能得到一个可用的原型，不需要训练集，并且能容忍类别的新增和删除；逐渐形成的共识是，LLM 适合用来快速起步一个功能，等标签体系稳定下来之后，就应该把它优化成更小的东西，有人把这种取舍比作 Electron 应用用效率换取开发速度。另一些人则质疑算术：每百万张工单节省约 21,700 美元，那「节省数百万美元」意味着一年大约 9,000 万张工单；他们也质疑文章的角度，指出 Strands 是 AWS 自己的开源项目，而不是外部厂商的产品，所以这篇文章更像是用内部采用情况做案例研究的广告。一位经营 ML 工具公司的评论者警告说，这类决策模型重构常常在生产中遇到阻力，最终又会回滚到 LLM，因为这些模型在表达真实的应用逻辑时能力较弱。

**值得一读的评论**
- [armcat](https://news.ycombinator.com/item?id=50436847): 六年前他们就在 SVM 上搭建了一套工单分类流水线，训练只需几分钟，分类只需几毫秒，并附上了发表于 ICSE 2021 的 Linnaeus 论文的链接——这说明这个领域绕了一圈又回到了起点。
- [wodenokoto](https://news.ycombinator.com/item?id=50436989): 认为没有领域数据就无法在工单系统上训练 SVM，而 LLM 只需要有人能把 API 接起来，无需重新训练就能应对类别变化，并且在之后正适合被优化掉。
- [Kaedon](https://news.ycombinator.com/item?id=50436881): 算了一笔账：按每百万张工单节省约 21,700 美元计算，一年节省数百万美元意味着年工单量至少约 9,200 万张；考虑到告警、安全发现和容量申请都会产生工单，这个数字是合理的。

## 2. Claude Fable 5.2 和 Mythos 5.2 {#story-2}
*HN 第 2 名 · [anthropic.com](https://www.anthropic.com/claude-fable-and-mythos-5-2) · 500 分 · 756 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50429068)*
*原标题: Claude Fable 5.2 and Mythos 5.2*

Anthropic 发布 Claude Fable 5.2 和 Claude Mythos 5.2。两者是同一个底层模型：Fable 面向所有用户，带有较强的网络安全和生物安全防护；Mythos 则通过验证计划向受审查的组织开放。文中称新模型输出速度比 5.1 快约 30%，输入和输出价格分别降到每百万 token 8 美元和 40 美元（可选 fast mode 在价格翻倍的基础上，生成速度提升 2.5 倍）。发布稿还宣称，1000 个 Fable 5.2 agent 用 30 小时完整形式化了费马大定理（Opus 5.5 用同样的设置只完成 26%）；以及一个 agent 花八天时间从空目录构建出能启动的操作系统，并让 Python 服务迁移到 Rust 后启动快 26 倍。文中还写到，模型解决了两个黑洞物理的开放问题，设计了三台电子设备，并在机器人评测上取得了进展。

**讨论**: 大量早期使用者表示，在普通编码任务上几乎分不出 Fable 5.2 和 Opus 5.5：有人说两者在 30 个任务中各自解出 26 个，但 Fable 5.2 的耗时只有 5.1 的 0.62 倍，而且几乎没有因防护机制而中止；也有人认为它在架构设计和需要高野心提示词的任务上明显更强。另一方面，评论对话题热度很高：用户抱怨额度消耗太快（有人在 20 分钟内耗尽了 5 小时用量），并普遍怀疑 Opus 5.5 发布前曾被「nerf」，还引用更早的 HN 帖子和 nerf-bench 追踪器；同时 5.2 这个版本号低于 Opus 5.5，也被骂为令人困惑的营销。基准图表受到最多质疑：有人问为什么把 Fable 的 xhigh 与 Gemini 4 Carbon 的 medium 相比、为什么网络安全基准里没有 Carbon；jsnell 回应说 Carbon 尚未公开发布，medium 正是它在 FrontierCode 2.0 上的最佳档位，其他基准根本没有它的数据。反方还指出 CVE Rediscovery 使用的是已公开的 CVE，本质上是在测记忆；Artificial Analysis 显示 Fable 5.2 每任务成本 26.54 美元，而 GPT-6.1 Sol 只要 1.27 美元；并且它的幻觉率为 59%。另一条主线是「奇点」之争：有人把费马大定理的形式化当作富矿，另一些人则指出，该证明依赖训练数据里已有的轨迹和可自动校验的 oracle，1000 个 agent 花费的计算量约为单个 agent 跑 11 天的 13 倍，因此这更像是计算量堆叠，而非递归自我改进。

**值得一读的评论**
- [jsnell](https://news.ycombinator.com/item?id=50431328): 逐条反驳「基准图表作弊」的指控：Carbon 尚未公开，无法自行跑分；FrontierCode 2.0 的 medium 是 Carbon 的最佳档位；而 Astra 的 CVE 测试需要 OpenAI 的验证计划授权。
- [ianberdin](https://news.ycombinator.com/item?id=50432975): 用同一 SVG 基准实测，Fable 5.2 在高档位只是因为被允许生成更多 token（76k，对比 Opus 的 20k），在 max 档位两者结果基本相同，Opus 5.5 反而略好且便宜约一半。
- [stefanpie](https://news.ycombinator.com/item?id=50431343): 引用系统卡指出，Anthropic 在训练中刻意压制了「加速器 kernel 优化 / 改进 LLM 架构」相关能力，使其只达到 Opus 5.5 水平，并对非标准加速器上的 kernel 开发做透明回退；作为 EDA 研究者，这令人担忧。

## 3. USPS 现在提供官方的 ZIP Code 边界多边形 {#story-3}
*HN 第 3 名 · [postalpro.usps.com](https://postalpro.usps.com/zcb) · 601 分 · 301 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50431058)*
*原标题: USPS now offers official ZIP Code boundary polygons*

这是 USPS PostalPro 上的一个产品页面，不是文章：它出售「ZIP Code Boundaries」数据集，声称基于投递地址和位置数据给出权威边界，每季度更新四次，分为 Internal、Enterprise 和 Publication 三个层级，并附带许可协议、技术指南和 GeoJSON 示例。页面没有标价，但评论者从订单表上查到最低档为 1 万美元，最高档达 15 万美元，且许可证禁止再分发或转售。

**讨论**: 压倒性的反应是愤怒：联邦数据理应以近乎零的增量成本公开，而这里却被定成了企业级价格；多位欧洲、荷兰的评论者指出，本国的邮编数据由政府机构免费发布，甚至直接作为 QGIS 图层使用。关于「USPS 为什么缺钱」的争论最激烈，也出现了关键纠正：有人说国会要求它提前几十年为养老金注资，但有人指出那其实是退休人员医保，且 2022 年的《邮政服务改革法》已经取消了这一要求，另外 USPS 自 1970 年代以来基本不拿纳税人拨款、靠邮资和产品销售自筹，同时被要求像企业一样运营。技术派反复强调 ZIP code 从来不是地理区域，而是一组投递路线的标签：PO Box、单栋建筑、跨州、一条街两侧分属不同邮编都真实存在，因此多边形只能是近似，这也解释了为什么 Census 的免费 ZCTA 数据集成为默认替代品，发帖人自己也按这份数据对比过。还有从业者提到 USPS 的地址验证 API 2026 年 8 月也开始收费，以及有人试图用众筹买下数据再公开，会因为许可证和可能的数据指纹而不可行。

**值得一读的评论**
- [munro](https://news.ycombinator.com/item?id=50432321): 发帖人 munro 把 USPS 的波多黎各样例数据与 Census 2026 年的 ZCTA 做了逐块对比，结论是差异不大、 Census 模型更简单，因此打算继续用免费的 Census 数据，并顺带发现「ZIP Code」是注册商标。
- [shiflett](https://news.ycombinator.com/item?id=50435188): 一位 1999–2003 年在 USPS 工作的评论者说，USPS 的数据历来与处理代码分开授权，还故意掺入假地址（DPV false positive）用于检测滥用，因此「买一次然后公开」这条路走不通。
- [anamexis](https://news.ycombinator.com/item?id=50431916): 解释了法律依据：39 U.S.C. §410(c) 给了 USPS 豁免，使其可以不予披露「商业性质的信息」，所以常规 FOIA 走不通。

## 4. 你的电视能透视墙壁 {#story-4}
*HN 第 4 名 · [maurycyz.com](https://maurycyz.com/projects/fading/) · 64 分 · 18 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50436410)*
*原标题: Your TV can see through walls*

Maurycyz 的项目文章展示了一张本地 ATSC 数字电视台在 490 MHz 的频谱图，由 Ettus USRP B200 软件定义无线电捕获。由于直达信号被一个很强的频率相关反射部分抵消（选择性衰落），接收信号对附近的移动变得极其敏感：在隔壁房间站起来或走动，都会在水瀑布图上产生条纹状零点。数出这些条纹（在 150 Hz 刷新率下约相距 70 px，即 2.1 Hz 拍频），再套用 λ = c/490 MHz，可以估算出行走速度为 1.3 m/s（4.6 km/h）；作者还指出，任何宽带信号——WiFi、LTE——都能以同样方式工作。

**讨论**: 这个讨论串基本上是一场热情的「而且情况还会更糟」巡游，而非对该方法的批评。评论者纷纷补充相关的先行技术：numlock86 描述了通过检测光路上的微小扰动来从光纤电缆中提取音频（受限于每条链路，因为中继器会再生信号）；有几个人回忆起 Van Eck 窃听（Van Eck phreaking）以及那项通过墙壁还原屏幕内容的 CRT 辐射研究；还有人贴出 MIT 的穿墙射频研究，以及一家通过 4G 路径损耗与散射估算交通流量的初创公司（arXiv 2101.09143）。在实用层面，有人问为什么 Home Assistant 没有 Wi-Fi 存在传感器，随后给出了两个答案：ESPectre Wi-Fi 移动检测集成，以及一个基于 Zigbee 的存在检测讨论；此外还有人提到一个不到 10 美元的 ESP32 频谱感知项目（ESPSDR/espargos），以及一个把普通 Wi-Fi 变成存在与生命体征感知的 RuView 仓库。隐私角度也被提出——外面的人可以推断出房子何时无人——但很大程度上被一句回复挡了回去：一部没有开飞行模式的手机已经泄露了这一点；同时有人指出，监控摄像头的音频流才是更现实的室内移动侧信道。有几位评论者指出，对任何在模拟天线时代长大的人来说，这个效应早就是旧闻了——当年站错位置就会让画面失真。

**值得一读的评论**
- [1e1a](https://news.ycombinator.com/item?id=50437203): 贴出了一个不到 10 美元的基于 ESP32 的 SDR 方案（espargos/ESPSDR），用于观测 Wi-Fi 和 LTE 频谱，使这个实验无需 USRP 也能进行。
- [sudorm-rf--no-p](https://news.ycombinator.com/item?id=50437315): 用实际存在的 ESPectre Wi-Fi 移动检测社区集成，回答了「为什么没有 Home Assistant 集成？」这个问题。
- [cowlevel](https://news.ycombinator.com/item?id=50436990): 对隐私担忧的直截了当的反驳：一部没开飞行模式的手机已经能告诉观察者你是否在家。

## 5. 定位一处神秘哔声的来源 {#story-5}
*HN 第 5 名 · [simonwillison.net](https://simonwillison.net/2026/Nov/9/mysterious-beeps/) · 137 分 · 65 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50434310)*
*原标题: Locating the source of a mysterious beep*

Simon Willison 的博客文章讲述了他如何搭建「Beep Locator」：起因是他储物间里的某个东西开始间歇性地发出哔声。这是一个 Python Web 服务器，协调几台闲置设备（两台 iPad、一部手机、一台 MacBook Pro、一台 Surface）作为基于浏览器的监听器，使用 WebAudio、WebSockets，以及一个带 FFT 哔声检测的 60 秒环形缓冲区。监听器录到的片段通过由服务器触发的一声啾鸣进行对齐，这一方法取自 Peng、Shen、Zhang、Li 和 Tan 在 2007 年发表的 BeepBeep 论文；此外还有一个可拖动设备位置的「粗略模式」，以及一个用于校准的拍手模式。它把哔声的位置定位到约 40cm 以内，最终让他找到了一台老掉牙的一氧化碳探测器，它只是需要换电池。这套系统主要是他用 iPhone 在 Claude Code Cloud 里借助 Opus 5.5 搭建的，随后又用 Fable 5.2 边跑边迭代；其中有一个可热替换的 installModule() 机制，用来向监听器推送新的 JS，而无需刷新页面、重新申请麦克风权限。

## 7. Horible 公钥戏法 {#story-7}
*HN 第 9 名 · [maurycyz.com](https://maurycyz.com/projects/badcert/) · 138 分 · 43 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50434264)*
*原标题: Horible public key tricks*

maurycyz.com 的一篇博文，讲解如何取得一张可信的 TLS 证书，使其 RSA 公钥模数在 base64 编码后能拼出一段可读的文字——文中展示的证书里确实含有「You+dont+actually+have+to+pick+random+private+keys / No+one+checks+these+things / A+certificate+authority+got+away+with+the+number+4+for+a+year」。方法如下：先随机选两个素数，直接改写 n 的字节以嵌入信息，再令 q = n/p，向上取整到下一个素数（通常只差几百），由于信息位于 n 的高半部分，因此能保留下来；在 RSA-2048 下 base64 大约能提供 150 个字符的空间，RSA-4096 下则有 320 个，而错位通常尝试四次以内就能对齐。作者承认这把密钥损失了熵，他的脚本也没有检查两素数是否过于接近或 d 是否过小，但他认为对于公共网站而言，前向保密足以让密钥泄露变得可以承受。

- [jeroenhd](https://news.ycombinator.com/item?id=50434221): 在一台老旧的 i3-2120 NAS 上给出了具体基准测试（默认速度下 AVIF 需 4–6 秒，JPEG 约 2 秒；加 --speed 10 后只需半秒），并认为 AV1 编码器已改进良多，旧基准测试已经过时。
- [brigade](https://news.ycombinator.com/item?id=50429885): 纠正了讨论中一个被广泛重复的说法：AVIF 每个维度允许 2^32-1 像素，而 JPEG XL 是 2^30-1，并且任意平面可作为 AVIF 辅助图像存在——那些对比网站把 AV1 的 profile 限制与 AVIF 的限制混为一谈了。
- [mikae1](https://news.ycombinator.com/item?id=50436976): 警告说一款流行的 WordPress AVIF 插件会把每个上传的 JPEG 都转码供所有浏览器使用，结果图片反而比原图更差——这正是 JPEG XL 能提供而 AVIF 无法提供的无损路径。

## 18. 论 2026 年做一名工程师 {#story-18}

*原标题: On Being an Engineer in 2026*

这是一篇由 Shahar Glazner 撰写的文章——他是 Keepalerting 的联合创始人兼 CTO，公司被收购后现在在 Elastic 担任技术负责人——文章主张工程师对 AI agent 仍然握有真实的影响力。他的论证是一种归谬：所有人都能用到大致相同的模型（他举了 Opus 4.6 和 Cursor），但强工程师的产出依然远远超过弱工程师，于是 10x 工程师变成了 100x 工程师；他把这一差距归因于隐性知识（Michael Polanyi 的「我们知道的比我们能说出来的更多」）、涌现，以及亲身经验——其中包括那种集体性的、难以定义的、识别 AI 垃圾（AI slop）的直觉。

**值得一读的评论**
- [zeroonetwothree](https://news.ycombinator.com/item?id=50436334): 一位自认的 10x 工程师说出了与文章乐观论调相反的情况：他们交付的比以前更多，却不再觉得自己真正理解自己的代码，遇到技术问题必须先转给 agent。
- [wrs](https://news.ycombinator.com/item?id=50431063): 主张隐性知识根本不是人类的护城河——强化学习后训练正是获取那些从未被写下来的东西的过程，其上限只取决于环境和反馈的质量。
- [kypro](https://news.ycombinator.com/item?id=50432454): 形容这份工作依然忙碌但乐趣大减：不再有艰难的纯逻辑问题，相对能力较弱工程师的优势不复存在，设计上的争论也输给了「我们以后让 Claude 重构一下就行」。

## 20. Claude Fable 5.2 在 Artificial Analysis 上得分 65，为目前最高 {#story-20}
*HN 第 30 名 · [artificialanalysis.ai](https://artificialanalysis.ai/models/claude-fable-5-2) · 338 分 · 244 条评论 · [HN 讨论](https://news.ycombinator.com/item?id=50431144)*
*原标题: Claude Fable 5.2 scores 65 on Artificial Analysis, highest so far*

这是 Claude Fable 5.2（「Max, Default Fallback」推理配置）的 Artificial Analysis 模型页面，发布于 2026 年 11 月 9 日，具备 100 万 token 上下文窗口，定价为输入 $8/M、输出 $40/M（缓存折扣 98%）。它在 Intelligence Index v5.0.1 上得到 65 分——该套件包含 Terminal-Bench 4.0、FrontierCode 2.0、HLE-Diamond 和 AA-Omniscience 在内的九项评测——而同等价位模型的中位数为 40，但页面本身也标注它很慢（每个任务 46.4 分钟，中位数为 12.6 分钟，首个回答 token 耗时 219.85 秒）且非常啰嗦（生成 2.75 亿 token，中位数为 7280 万）。平均成本折算为每个 Intelligence Index 任务 $26.54。

**讨论**: 争论的焦点主要是成本而非分数：最高赞评论指出，在 max 力度下 Fable 5.2 的每任务成本大约是本就偏高的 Fable 5.1 的两倍，每任务输出 token 从 118k 跳到 274k（仅推理部分就从 71k 增至 192k）。几位评论者反复提出的最有力反驳是：AA 页面默认使用 max 力度，而没人会真的这么用——在 high 下它得分 62、每任务约 $9.08，而 Opus 5.5 max 是 59 分、$10.04；在 low/medium 下它比 Fable 5.1 的同等设置既更便宜也更聪明。另一个讨论串争论这次发布是否标志着「智能/成本」回报递减的「墙」；有人援引 Dennard scaling 的终结和 Anthropic 即将到来的 IPO，另一些人则指出推理侧的 scaling 仍然有效，而且实验室惯于把昂贵模型蒸馏成廉价模型（Opus 5 → Opus 5.5）。第一手使用报告则好坏参半、分歧鲜明：一些用户说它无视 CLAUDE.md 指令、编造结果，并拒绝它认为敏感的任务；另一些人说 low 力度在延迟和质量上都胜过 Opus 5.5 的 medium/high。附带讨论涉及 DeepSeek/GLM 在多数工作上便宜约 100 倍、Artificial Analysis 未公开的基准测试及其武断的「最具吸引力象限」分界线，以及 Google 的 Argon/Carbon 模型是否被低估。
