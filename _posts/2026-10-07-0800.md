## 1. Sharing AI progress in mathematics {#story-1}
*#1 on HN · [openai.com](https://openai.com/index/sharing-ai-progress-in-mathematics/) · 769 points · 698 comments · [HN discussion](https://news.ycombinator.com/item?id=49984923)*

OpenAI 发布了一个 GitHub 仓库（github.com/openai/math），其中收录了其内部前沿模型产出的大批数学成果，涵盖预印本、部分证明的 Lean 形式化、推理摘要以及算力统计。它声称平均每个结果大约消耗相当于 3 小时 ChatGPT Pro 思考量的算力，并称这批结果中包括对 Unique Games Conjecture（现称 Unique Games Theorem）、Barnette 猜想、矩阵乘法指数 ω ≤ 2.25、低于 n log n 的整数乘法以及快于 O(n log n) 的 FFT 等的证明或改进。OpenAI 表示，在如何发布这些结果的问题上，它咨询了普林斯顿高等研究院（Institute for Advanced Study）的 Advisory Group on Mathematics and Artificial Intelligence（AGMAI），并称未来还会进一步优化论文质量、引用和表述方式。

**Discussion**: 讨论被一种悲欣交集的情绪主导：一位长期研究 Barnette 猜想的评论者描述了自己数千小时的努力被机器超越后近乎哀悼的感受，另一些人则反驳说这不算个人损失，还拿 AI 在国际象棋上超越人类后人类棋艺反而提高作类比。主要的实质性批评集中在验证环节——部分结果缺少 Lean 形式化证明，而且整个模型并未公开，因此除了 OpenAI 和 Anthropic 内部之外无法复现；有人把这描述为一种前所未有的权力集中，甚至称之为「AI 论文倾倒（slop dump）」。质疑者还指出，AGMAI 曾公开表示并不认可这种做法、并呼吁停止在专有模型上测试高难度数学问题，而 OpenAI 仍然发布了这批成果，具体是否遵循了其指导方针，评论者意见不一。与此同时，复杂度理论和调度领域的从业者认为 Unique Games Theorem 才是这组结果中真正的重磅——它将改写近似算法的教科书——并特别留意到一些荒谬的常数，比如三机器调度算法中 O((L+2)^150020) 的指数。总体共识是这些结果确实令人瞩目，但验证、可复现性以及它们究竟算是新的洞见还是庞大算力与 Lean 验证循环的产物，仍悬而未决。

**Worth reading**
- [jboggan](https://news.ycombinator.com/item?id=49987367): 一位编译器/图论爱好者讲述了自己在 Barnette 猜想上断续投入 24 年、甚至去年夏天还一度以为解决了它，如今看到被列为问题 180 时感到一种奇异的失落。
- [nilkn](https://news.ycombinator.com/item?id=49988412): 认为这些突破完全不可复现，只存在于 OpenAI 和 Anthropic 内部一两个团队中，是史无前例的算力/能力集中，也是许多人焦虑的真正来源。
- [winfieldchen](https://news.ycombinator.com/item?id=49988578): 解释为何 Unique Games Theorem 意义重大：它决定了一整类多项式时间近似算法的极限，包括 Goemans–Williamson 的 0.87856 比在 UGC 下已是最优，教科书将因此重写。

## 2. Strands Decider 2B: a small, open-source, decision model {#story-2}
*#2 on HN · [strandsagents.com](https://strandsagents.com/blog/introducing-strands-decider/) · 127 points · 25 comments · [HN discussion](https://news.ycombinator.com/item?id=49987076)*

Strands Labs 发布了 strands-decider-2b，一个 20 亿参数的「决策模型」或「系统一模型」，已在 GitHub 和 Hugging Face 上开源，附带训练数据与脚本。它取自 Qwen3.5-2B 的骨架，去掉 LM head、换成一个约 100 万参数的指针头，并用 rank-16 LoRA 微调。它只从候选选项中选择或给出数值分数（例如一个 0–1 的「noul」置信度），而不是生成文本；论文声称其准确率和校准度在 JevBench 的 2B 类别中排名 33 个模型里的第 3（排除略超 2B 的模型后为 30 个中的第 1），在 RTX 3090 上中位延迟约 115ms，在 M3 MacBook 上小任务约 153ms。作者将它在模型路由、工具选择、护栏、记忆和策略分类方面的应用，与 API 型 LLM 推理相比，定位为推理成本更低。

**Discussion**: 几条开头的评论都是关于「Jerry」的玩笑：一个由真人驱动的决策模型，呼应 Rick and Morty 和 Chappelle 的桥段。关键的技术讨论集中在命名和部署上：一些人询问为什么二元选择被标为「noul」，有人将其追溯到 Bernoulli（「Bernoulli 映射」）。有几位评论者主要关心本地运行：指出 Cloudflare 的 clef 可在 llama.cpp 上运行，并报告在将 PEFT/LoRA 权重转换为 GGUF 时遇到困难（一个不熟悉的 linear_attn 张量无法映射），这阻碍了更广泛的采用。关于实际速度也有分歧——一位在 Docker 中的 M3 上运行，看到的是 1732ms，而不是宣传的约 153ms；另一位则报告，在六核 CPU 上大约是每次决策半秒。常见的反对意见是，JevBench 上的基准校准并不能证明其在陌生的生产环境输入上依然可靠。

**Worth reading**
- [hrpnk](https://news.ycombinator.com/item?id=49989024): 指出采用障碍：被锁定在 Strands CLI 中很可惜，因为 Cloudflare 的 clef 可在 llama.cpp 上运行，而将 LoRA 转换为 GGUF 仍留给用户——并展示了未能映射的 linear_attn 张量。
- [soltanov](https://news.ycombinator.com/item?id=49988410): 对标题所指的校准提出质疑：基准校准并不能确保在模型从未见过的生产环境输入上仍然可靠。
- [gopalv](https://news.ycombinator.com/item?id=49988538): 分享第一手 CPU 数据——在 M3 上的 Docker 中，每次决策耗时 1732ms——并附上 README 脚本，指出针对 MLX 的优化还有待开发。

## 3. Decisions API is in public beta {#story-3}
*#3 on HN · [developers.openai.com](https://developers.openai.com/api/docs/guides/decisions) · 242 points · 112 comments · [HN discussion](https://news.ycombinator.com/item?id=49984025)*

这是 OpenAI 开放平台文档中的新指南页面：一个专门用于分类与评分的 POST /v1/decisions 端点，目前处于公开测试阶段（预计数周内 GA）。它接收文本和/或 base64 内联图片，返回三种类型化答案——predicate（条件为真的概率 0–1）、choice（从给定选项中选择一个）和 score（按层级序号加权平均）——OpenAI 称其比 Responses API 快约 10 倍；目前唯一可用的模型是 gpt-6-luna。请求不计输出 token，图片不支持 HTTP URL 或 file_id，文档中还包含 Python 3.26.0、JavaScript 7.30.0、Go 3.73.0、Ruby 0.101.0、Java 4.78.0 的 SDK 示例。

**Discussion**: 最主要的争论是：Simon Willison 演示了实际的 curl 调用并很快发布了 llm-openai-decisions 插件，随后许多人把这件事读作 OpenAI 在追赶 Typesafe 的 Jev，以及对“AI 是否已商品化、是否存在护城河”的又一次验证。持怀疑态度的开发者（如 Topfi）用 OpenRouter 跑了不到 600 次自建评测，结论是 gpt-6-luna 比 Jev 更慢、贵约 3.1 倍、更容易在模糊任务上失手（在简单标签判断上给出 0.21 和 0.56 而不是 Jev 的 0.69 和 0.91），而其他人反问本地小模型是否真的能替代云端；一位 OpenAI 员工复现了同一批样例并得到 0.99 和 1.0，表示愿意排查异常输出。价格方面被反复引用：输入约每百万 token $0.10（Jev 约 $0.042），双方都不收输出费，所以总体上只有速度和图片输入是明确优势。另一条主线是商业化：许多人认为企业客户会因现有采购、合规、零数据保留合同和厂商审批流程而选择 OpenAI，甚至不需要赢下评测；反对者则说切换模型只需两次按键、开源权重模型足够好，这是价格战而 OpenAI 无法靠“粘性”取胜。关于缓存未启用、校准是否可靠（0.9 是否真的代表 90% 正确）以及这类 API 是否会被合并回通用模型，讨论没有形成共识，但多数人承认图片输入是其相对 Jev 的第一个明显功能差距。

**Worth reading**
- [simonw](https://news.ycombinator.com/item?id=49985035): Simon Willison 贴出了可运行的 curl 调用和真实返回（complaint 0.91、compliment 0.06），指出这类端点往往会成为其他厂商的事实标准，并顺手发布了 llm-openai-decisions 插件。
- [Topfi](https://news.ycombinator.com/item?id=49985095): 一位开发者用不到 600 次自建评测对比 Jev 与 Mercury Decide：Luna 更慢（p50 346ms、p95 860ms）、贵约 3.1 倍、在模糊任务上置信度更低，但承认未测试图片输入。
- [brianyu8](https://news.ycombinator.com/item?id=49988427): OpenAI 员工 brianyu8 用同一批标签样例复现评测并得到 0.99/0.99 与 1.0/1.0，邀请作者邮件反馈异常输出，是对前述评测最直接的反驳。

## 4. La Cueva BBS in Mexico in 1993 (session replay) {#story-4}
*#5 on HN · [nanochess.org](https://nanochess.org/la_cueva_bbs.html) · 38 points · 9 comments · [HN discussion](https://news.ycombinator.com/item?id=49987675)*

Oscar Toledo Gutiérrez (nanochess) describe cómo se conectaba en 1993, desde su computadora casera basada en un Zilog Z280 con 512 KB de RAM y un módem Hayes de 2400 baudios, al BBS La Cueva en México. Escribió su propio terminal serie implementando comandos AT y secuencias de escape ANSI, con un búfer de captura de 64 KB en el área MMU del Z280. Encontró en un disquete antiguo el archivo CUEVA.TXT con una sesión completa del 11 de febrero de 1993 (de 9:30 a 9:47 pm) y la convirtió en un replay en JavaScript usando un jsTerm adaptado de Peter Nitsch a 2400 baudios; luego añadió otra captura (Nopal BBS) y una lista de números telefónicos de BBS mexicanos de 1993.

**Discussion**: El hilo es mayormente nostálgico: varios comentaristas recuerdan haber administrado BBS sobre RBBS-PC y WWIV, con discos Seagate ST-225 de 20 MB, módems Telebit Trailblazer a 19.2k y SupraFAXModem a 14.4k, y las amistades duraderas que salieron de esos tableros. Un comentarista cuestiona la combinación de año, CPU y memoria, argumentando que un Z80 de 8 bits con direccionamiento de 16 bits no podía manejar más de 64 KB y que en 1993 eso era hardware obsoleto incluso en México; otro responde y el propio autor aclara que se trata de un Zilog Z280 con MMU capaz de direccionar 16 MB, páginas de 8 KB y caché interna. Otros comparten experiencias de adolescencia con módems y el intercambio de warez por imágenes, además del asombro de conectarse por primera vez a la computadora de otra persona. El tono general es de aprecio por el hallazgo y lamento por no haber conservado más capturas de sesiones y arte ANSI.

**Worth reading**
- [notorandit](https://news.ycombinator.com/item?id=49988679): Sostiene que un Z80 en 1993 era hardware demasiado limitado y obsoleto para México, cuestionando la premisa técnica del artículo.
- [nanochess](https://news.ycombinator.com/item?id=49989155): El propio autor corrige: es un Zilog Z280, con MMU que direcciona 16 MB, mapeo separado de código y datos, páginas de 8 KB y caché, mucho más rápido que un Z80.
- [noduerme](https://news.ycombinator.com/item?id=49988992): Un comentarista relata cómo a los 12 años, con un módem de 57.6k, intercambiaba GIFs pornográficos por warez de modelado 3D, obteniendo copias de Strata, Renderman, Playmation, Infini-D y ElectricImage.

## 5. Penguin Mail – open-source Rust email client for Linux with AI {#story-5}
*#7 on HN · [penguin-mail.com](https://penguin-mail.com/) · 148 points · 79 comments · [HN discussion](https://news.ycombinator.com/item?id=49984716)*

Penguin Mail 是一款面向 Linux（x86_64）的桌面邮件客户端，版本 1.0.0，采用 GPL-3.0-or-later 许可。它支持 Gmail、Outlook.com/Hotmail/Microsoft 365 以及任意 IMAP、POP3 和 SMTP 账号（自动探测服务器设置），并集成 Google/Microsoft/CalDAV 日历与 CardDAV 联系人，通过本机 GnuPG 签名和加密（不保存密钥），支持 Gmail 过滤器、Outlook 收件箱规则和 Sieve 规则；其 AI 助手默认关闭，可通过 LM Studio 或 Ollama 在本地运行，发送邮件或更改设置前会先询问，并展示它调用的每个工具。宣称没有自建服务器、不做追踪、不放广告，Gmail 与 Outlook 流量直接发往 Google 或 Microsoft Graph。

**Discussion**: 最高票的讨论完全偏离主题：多位评论者指出该项目的 YouTube 介绍视频前的广告是一条明显的诈骗广告（usbest1.com，满是 AI 生成内容，结账流程甚至问你要不要给「司机」小费），并借此呼吁 Google 等广告网络应被强制审核广告主，同时推荐使用 uBlock Origin。技术上最大的质疑来自一位评论者：这类「vibe-coded」邮件客户端如何处理 HTML 邮件的完整内容视图——Thunderbird 等会阻止内联 JavaScript、追踪像素和 CSS 引用，这些新客户端是否只是把 HTML 丢进 WebView？另一个反复出现的争论是 AI 的必要性，有人反感嵌入式聊天框，也有人认为本地 LLM 自动分类和翻译邮件才是唯一真正有价值的用途，还有评论者纠正说 README 里其实提供了 MCP 接口。此外有人指责项目仅开发约一个月就发布 1.0 是「bullshit」，立刻被反驳（发布到 GitHub 一个月不等于项目只有一个月，且未见不稳定证据），也有人为语义化版本从 1.0 起步辩护。关于 Thunderbird 的评价分歧明显：一方抱怨其 UI 令人分心、线程（会话分组）在 2026 年仍不稳定、搜索又慢又不准，另一方则表示自己用了十年觉得挺好，并反讽「凭直觉假定不稳定」的标准过高。

**Worth reading**
- [jttnr](https://news.ycombinator.com/item?id=49989222): 指出所有 vibe-coded 邮件客户端都面临的同一个安全问题：它们如何清理 HTML 邮件的全内容视图，是否像 Thunderbird 那样阻断内联 JavaScript、追踪像素和 CSS 引用，还是直接交给 WebView 渲染。
- [tamimio](https://news.ycombinator.com/item?id=49986660): 在 Fastmail 上实测十分钟后的具体短板清单：无法选择发件人地址（多别名用户直接出局）、没有 favicon、文件夹排序混乱、给文件夹上色提示服务器不支持，并认为整体 UI 仍需打磨。
- [mal10c](https://news.ycombinator.com/item?id=49986600): 给出在 FreeBSD 上编译的可行步骤：安装 gtk4、libadwaita、webkit2-gtk_60、pkgconf，并把 webkit6 crate 的 v2_50 特性改为 v2_46 以匹配系统的 WebKitGTK 2.46.6。

## 6. EmbeddingGemma 2: An open, lightweight multimodal embedding model {#story-6}
*#8 on HN · [blog.google](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/) · 294 points · 31 comments · [HN discussion](https://news.ycombinator.com/item?id=49980487)*

Google DeepMind announced EmbeddingGemma 2, an Apache 2.0-licensed embedding model built on the Gemma 4 architecture that maps text, code, images, audio and video into one shared embedding space. It has 740M parameters total, split into a 270M text model plus optional 170M vision and 300M audio encoders, runs in as little as ~191MB active RAM for text-only quantized weights (~567MB multimodal) on a Pixel 11 Pro, and supports an 8K token context (4x the first model). Google claims a 9.92-point MTEB Code gain over EmbeddingGemma (68.76 to 78.68), best-in-class sub-1B results, and Matryoshka truncation from 768 down to 128 dimensions for up to 6x storage savings. The original EmbeddingGemma passed 20 million downloads.

**Discussion**: The dominant thread is praise for the Apache 2.0 license: simonw argues embedding models especially shouldn't be closed and hosted-only, because a vendor sunsetting a model forces re-embedding millions of stored vectors, though he'd still rather pay a host than run it himself. Practitioners quibble over specifics — one notes the text benchmarks are unchanged from EmbeddingGemma 1 and the real win is selective enabling of modality encoders, another points out EG2 lacks a decoder/encoder for OCR so it isn't a SigLIP2 replacement, and another flags that it uses MRL rather than MatFormers, so lower-dimensional vectors don't shrink the model weights. A hands-on report says the marketed MediaPipe Decision Task example failed: classifying 「Cancel my flight and refund my credit card immediately.」 returned p(true)=0.22 for financial, with Laya doing better and nearly as fast. minimaxir posted local M3 Pro throughput — 78 text embeddings/sec, 4 image/sec, 6 audio/sec (30s chunks), 0.2 video/sec per minute — and commenters broadly see the model as filling a real gap for on-device multimodal search and RAG.

**Worth reading**
- [simonw](https://news.ycombinator.com/item?id=49983751): simonw explains why permissive licensing matters specifically for embeddings: proprietary vendors sunset models and leave you paying to re-embed millions of stored vectors — and Google's GPT-4 re-embedding offer in 2024 isn't something to rely on.
- [Zambyte](https://news.ycombinator.com/item?id=49984951): A first-hand test says the MediaPipe Decision Task example shipping with the release fails on the refund/credit-card classification, returning p(true)=0.22, with Laya more accurate and almost as fast.
- [minimaxir](https://news.ycombinator.com/item?id=49985694): minimaxir's measured throughput on an M3 Pro: 78 text embeddings/sec, 4 image/sec, 6 audio/sec in 30-second chunks, and 0.2 video/sec per minute of footage (encoder runs at 1fps).

## 7. What Is Codemode {#story-7}
*#9 on HN · [lucumr.pocoo.org](https://lucumr.pocoo.org/2026/10/6/codemode/) · 57 points · 16 comments · [HN discussion](https://news.ycombinator.com/item?id=49978333)*

Armin Ronacher explains Codemode, the mechanism Pi 1.0 added to support MCP: instead of loading tool definitions into the model's context, the LLM writes JavaScript that issues tool calls directly. Codemode runs on the trusted harness side (in Pi, QuickJS inside WASM with no network, no filesystem, no timers, limited RAM) rather than in the sandboxed execution environment, letting agents compose concurrent calls, stash state in the transcript, and reach internal APIs like image generation and the Jev classifier without burning context. Examples include generating images, batch-classifying 100 GitHub issues for sentiment/frustration, driving a tank game via a 30-step Jev loop, and progressive discovery of MCP servers like Sentry.

这是博主 Signore Galilei 写的一篇科普文章，按生物量（biomass）给地球单一物种排名：人类约 3.5 亿公吨，南极磷虾 2009 年估算约 3.79 亿公吨，而动物类冠军是家牛（约 6.5 亿公吨，猪以约 1.4 亿公吨居后）。按 Bar-On 等人 2018 年的碳质量统计，动物总共只有 20 亿吨碳，远少于原生生物、真菌、细菌，尤其远少于植物的 4500 亿吨碳。作者据此推断植物冠军在驯化作物里是甘蔗（2023 年产量超 20 亿公吨），在野生植物里则是北方针叶林树种——加拿大黑云杉（超过 110 亿公吨）和俄罗斯的达乌里落叶松（至少 84 亿公吨，可能更多）。

## 17. Hackers obtain counterfeit TLS certificates for Google and other large services {#story-17}

An Ars Technica security piece by Dan Goodin reporting Google's disclosure that attackers hijacked three country-code top-level domains — .gh, .sl and .as — and used that control to alter authoritative DNS records and nameserver delegations for selected domains, passing domain-control validation checks and obtaining unauthorized TLS certificates for 「several Google domains」 plus domains of other large brands. Google says Chrome was updated to block the identified certificates and that issuing CAs revoked them, that no Google infrastructure was compromised and the CAs followed all requirements. Google warns domain owners not to rely on browser-side blocking, urging certificate-transparency monitoring and restrictive CAA records, and concedes it cannot guarantee it found every affected domain.

**Discussion**: With only five comments, the thread is thin and mostly about mechanism rather than impact. One commenter argues HPKP (HTTP Public Key Pinning) could have prevented this while CAA records could not, but notes HPKP is deprecated — another replies skeptically asking what he is missing and whether it comes down to TLDs lacking support for such countermeasures. A commenter quotes Google's own blog post verbatim to stress that whole TLD registries, not individual sites, were compromised, and complains about the lack of any primary source, which another commenter supplies by linking Google's security blog and two other HN submissions of the same story. A top comment lists the three affected ccTLDs, describing .gh as Greenland — it is actually Ghana (.as is American Samoa and .sl Sierra Leone). Rough consensus: the notable part is registry-level compromise, and certificate-side defenses are weaker than they look.

**Worth reading**
- [Borealid](https://news.ycombinator.com/item?id=49988998): Argues HPKP, not CAA records, is the defense that would have blocked this — and that HPKP is deprecated, so that option is gone.
- [fulafel](https://news.ycombinator.com/item?id=49988517): Quotes Google's blog directly confirming entire ccTLD registries were hijacked, and questions why no primary source is cited in the article.

## 19. When random is not actually random enough {#story-19}
*#28 on HN · [ersc.io](https://ersc.io/blog/when-random-isnt-random-enough) · 51 points · 16 comments · [HN discussion](https://news.ycombinator.com/item?id=49983404)*

A blog post on ersc.io about modulo bias: taking a uniform random u64 and reducing it with % n does not give each of n choices equal probability. The toy example is picking from 10 integers and mapping them onto 3 objects, which yields 40%/30%/30% instead of 33% each. The author argues random_u64() is too low-level an API and recommends random_between(l, h) plus a weighted random_choice() with relative integer weights (as Python's random.choices does), and describes using it in Antithesis-style deterministic fuzzing to steer code coverage (e.g. ~7/8 small vs ~1/8 large upload paths), reporting that his team removed all its Antithesis random_u64() calls in favor of weighted choice.

**Discussion**: Commenters mostly agree modulo is the bug, not the RNG (one notes the operator % is what worsens the distribution), but split on the fix and whether the API framing is right. One camp pushes rejection sampling as the simple, obviously-correct answer — reroll out-of-range values, since for a real u64 the rejection rate for something like [0, 10) is about 6 in 2^64 (~3.2e-17%), a cold branch; a dissenter notes in a property-testing framework, generating large random arrays made rejection cost measurable, and another raises Lemire's nearly divisionless method as the standard alternative. Another camp argues random_u64() is not too low-level (any real-valued variable is an inverse quantile transform of Uniform(0,1)) and that the real ask is a std.choice primitive; several doubt a nicer UI alone prevents footguns, since people hand-roll even simpler things like bisection search, and suggest fuzz or deterministic simulation testing is what actually disabuses them. A notable correction: the claim that rand() has only 32767 values applies to MinGW/MSVCRT, while glibc's RAND_MAX is 2147483647 — and others debate whether an overweighting of ~5×10^-20 is worth caring about at all.

**Worth reading**
- [tialaramex](https://news.ycombinator.com/item?id=49985782): Rejection sampling is the simple, provably correct fix here: draw enough bits, keep the value if in range, otherwise reroll — with the jab that programmers treat random numbers as a precious resource.
- [deathanatos](https://news.ycombinator.com/item?id=49987819): Quantifies the rejection cost for the article's own example: with a u64 source, needing a redraw for [0, 10) has probability about 6 in 2^64 (~3.2e-17%), so rejection is a very cold branch.
- [omoikane](https://news.ycombinator.com/item?id=49987640): Corrects the thread's RAND_MAX claim: 32767 is the MinGW/MSVCRT value, while glibc and most libraries use RAND_MAX = 2147483647.
