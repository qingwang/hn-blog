## 1. AI is forcing us to pay off 40 years of technical debt {#story-1}
*#1 on HN · [spectrum.ieee.org](https://spectrum.ieee.org/ai-in-cybersecurity-php2shell-vulnerability) · 859 points · 507 comments · [HN discussion](https://news.ycombinator.com/item?id=50364336)*

An IEEE Spectrum piece by Dina Genkina on the PHP2Shell vulnerability, which put WordPress- and Drupal-based sites — NASA, Wikipedia, the White House among them — at risk of remote code execution. The underlying out-of-memory bug was reported to the PHP Foundation in 2024 and dismissed as a mere crash; this year a researcher at the security firm Calif, working under an OpenAI-sponsored audit with AI tooling, turned it into arbitrary code execution within two weeks, and a team of four engineers spent two months building the patch before disclosure. Columbia's Suman Jana argues AI excels at the tedious, highly specific reasoning exploitation requires and is improving fast on patching via formal verification (citing an Anthropic release on 22 October), while Johns Hopkins' Matthew Green predicts nothing serious gets funded until a genuinely bad incident, maybe in early 2027.

**Discussion**: The thread splits between seeing AI as the accelerant and seeing it as the remedy: several commenters call the headline AI-glazing, noting the vulnerability class is 40 years old and asking why machines that find bugs are celebrated for also fixing the ones only they could find. A long subthread reopens Linus's Law, with the sharpest point being that it was coined by ESR, not Linus, and that whose eyeballs matters more than how many — maintainers of an open-source healthcare project confirm they had routine audits yet were swamped with legitimate findings in the last six months. A recurring counter-argument blames incentives rather than engineering culture: managers and customers wanted cheap, fast shipping, so compatibility and refactoring never got budget, and several practitioners report AI has now dumped years of deferred fixes on them at once (one says Opus 5.5's September upgrade triggered two to three frantic weeks of cleanup). Others push back on the article's framing of PHP as a legacy language, pointing out 7.x/8.x improvements and that ubiquity, not age, made it the target, and a widely-read reply argues the real worse case was the Brotli/HTTP2Shell bug, which humans sat on for months.

**Worth reading**
- [adunsulag](https://news.ycombinator.com/item?id=50366063): A maintainer of an open-source healthcare project describes how routine third-party audits created a false sense of security and how the recent flood of AI-assisted reports has been humbling and taxing, even after filtering false positives.
- [vanschelven](https://news.ycombinator.com/item?id=50364661): Argues HTTP2Shell/Brotli2Shell was arguably worse than PHP2Shell, and links a timeline showing 8 years in the code, 8 months unreleased after the fix, and four independent researchers finding it — i.e. humans, not AI, sat on it.
- [0xfedcafe](https://news.ycombinator.com/item?id=50365317): Lays out the policy angle with links: Amazon reportedly lobbying for limits on model capabilities while OpenAI ($1B in subsidized Daybreak access) and Anthropic ($100M in Mythos credits, $4M in donations) offer frontier security models to defenders.

## 2. A New Go API for JSON {#story-2}
*#2 on HN · [go.dev](https://go.dev/blog/jsonv2) · 88 points · 22 comments · [HN discussion](https://news.ycombinator.com/item?id=50369106)*

The Go team's go.dev blog post announcing a new JSON API — from the thread, the `encoding/json/v2` package with a companion `encoding/json/jsontext` layer for low-level token/value handling. The article text itself could not be retrieved (the page returned almost no readable content), so details here come from the title and what commenters describe. The headline reaction is that the design took roughly six years to land.

*Article not read: page had almost no readable text (probably needs JavaScript or a login)*

**Discussion**: Commenters are broadly positive about `encoding/json/v2` but fixate on migration costs and API ergonomics. The loudest complaint is that `MarshalIndent` is gone, making quick pretty-printing awkward and migration non-obvious — until others point out the replacement is just `json.Marshal(v, jsontext.WithIndent("  "))` or `jsontext.Value.Indent()`, which the original complainer had missed. A separate argument breaks out over why `json.Marshal` returns an error at all: one camp says unmarshalable types are a code bug that a stronger type system or a panic should catch, while others note `Marshal` takes `any`, that `MarshalJSON` methods can fail at runtime (e.g. lazy loading), and that non-finite floats make even statically known types partly unmarshalable. The suggested idiom is a `MustMarshal`/generic `Must[T]` wrapper. Several people also note they now mostly have LLMs write their Go, which makes a nicer API matter mainly for what models emit.

**Worth reading**
- [CamouflagedKiwi](https://news.ycombinator.com/item?id=50369853): Likes v2 overall but argues dropping `MarshalIndent` makes both migration and quick readable-JSON dumps needlessly painful.
- [arccy](https://news.ycombinator.com/item?id=50370310): Correction: pretty-printing is still a one-liner via `json.Marshal(v, jsontext.WithIndent("  "))` (with a sibling pointer to `jsontext.Value.Indent`).
- [duskwuff](https://news.ycombinator.com/item?id=50370539): Rebuts the claim that marshaling only fails for unmarshalable types: `MarshalJSON` implementations can fail at runtime, e.g. lazily loaded data that won't load, and `any` can appear anywhere in the object tree.

## 3. Progress on provable inference for large language models {#story-3}
*#3 on HN · [anthropic.com](https://www.anthropic.com/research/provable-inference) · 118 points · 51 comments · [HN discussion](https://news.ycombinator.com/item?id=50368626)*

Anthropic research post presenting FlashProve, an open-source (Apache 2.0) prototype that uses zkSNARKs to prove a response came from a committed set of model weights without revealing them. For Llama 4 Maverick (400B-parameter MoE, 4-bit quantized), one H100 generates proofs at ~110 tokens/sec with ~19 MB proofs per 1,024-token request — roughly 70-95x the GPU time vLLM needs to just run the model; clients verify a proof in 17 seconds on 24 threads (21 on one), after downloading a ~6.5 MB weight commitment good for about 16 million requests. The release includes a technical report, a Claude-written protocol spec, a C++ and a Lean verifier, and Lean proofs of the top-level security statements; the stated motivations are evaluators, routing services, tamper detection, and regulators pacing AI development.

**Discussion**: The loudest thread is an attribution fight: neuwirth says the work is built on VerInf, a prototype he wrote as a MARS fellow, and that Anthropic took everything down to the choice of Llama 4 Maverick with little credit — others note the post does cite VerInf, at ~0.02 tok/s, and the subthread turns into a fatalistic argument about MIT-vs-GPL licensing and whether AI rewriting makes software copyright moot. A second camp argues the cryptography is overkill: for open-weight models you can just re-run the computation deterministically (cheaper than a 70-95x proof overhead), while for closed models signed responses, comparing several independent providers, or TEEs are cheaper — though attestation today only spans a single 8-GPU node, with rack-scale encryption not yet broadly deployed. Several commenters stress the current scope limits: integer-only weights, greedy decoding, ~1k context, so a host silently serving a quantized or sampled-decoding variant could depart from the proof at some token — which is exactly the fraud people suspected of BaseTen, Fireworks and Together. On usefulness the thread splits between 「who cares, you already have to trust your provider」 and concrete cases: Chinese resellers passing off other models as Claude, OpenRouter-style routing, independent pre-release evaluators, and black-box audits (a PhD student working on ZKPs for AI auditing says this confirms their results). Cynics read it as protecting Anthropic's pricing from cheaper routing and as a PR move given past silent rerouting to weaker models; a final thread questions whether the regulatory 「only run inference」 scenario is a real problem at all.

**Worth reading**
- [neuwirth](https://news.ycombinator.com/item?id=50370121): A researcher claims Anthropic's system is derived from his own VerInf prototype and that the attribution is minimal — the origin of the thread's biggest argument.
- [gopalv](https://news.ycombinator.com/item?id=50368978): Notes the proof/commitment mechanics look like expensive proof-of-work, and links an investigation into why BaseTen, Fireworks and Together serve the same weights differently, possibly via quantization for long contexts.
- [FrasiertheLion](https://news.ycombinator.com/item?id=50370668): Explains why confidential computing is not an easy substitute: attestation requires secure hardware, is limited to a single 8-GPU node on Blackwell, and rack-scale encryption on Vera Rubin is not widely deployed.

## 5. Ripple-65B Preview: U.S. Open-Weight SOTA on Agentic Coding {#story-5}
*#5 on HN · [ricursive.com](https://www.ricursive.com/ripple) · 30 points · 15 comments · [HN discussion](https://news.ycombinator.com/item?id=50369925)*

Ricursive Intelligence（一家同时做 AI 芯片设计的实验室）发布了 Ripple-65B Preview——一个从头训练的稠密 Transformer（d_model 5120、80 层、12T token 预训练、最高 1M 上下文），它声称这是美国开放权重模型在 agentic coding 上的 SOTA。它的核心数字是 TerminalBench 2.1 上 80.52，超过体积大得多的美国开放权重模型：Reflection Beam 501B（80.1）、Meta Muse Spark Open 816B（76.4）、Thinking Machines Inkling 975B（63.8）和 NVIDIA Nemotron 3 Ultra 550B（56.4）。Ricursive 表示，这个模型的完整 R&D 成本只有 3200 万美元，预训练中 MFU 保持在 40%，RL 阶段只用了 140 万次 rollout（比 Beam 少约 70 倍）；模型已在 Hugging Face、Together AI、GMI Cloud 和 OpenRouter 上线。

**Discussion**: 评论者对「美国开放权重 SOTA」这个限定词很不满：他们认为，在国家和模型规模上不断收窄类别，已经让 SOTA 这个词失去意义（有评论者讽刺说，只剩「美国制造的、某个规模段的、能在本地跑的开放模型」这一层限定）。最实质的反驳是一个横向对比：Qwen 3.8 Flash Next 在 TerminalBench 2.1 上得 84.3，Qwen 3.8-27B 得 73.0，都超过或接近 Ripple 的成绩，所以有人断言「不拿 Qwen 做对比，说明性能不行」。还有人指出，对比图表只选了美国模型，对读者没有参考价值；另有人猜测，这可能是为了迎合 Palantir 这类买家。旁支讨论集中在命名混乱上——Ricursive 与另一家叫 Recursive 的 LLM 实验室很容易混淆，有回复打趣说「希望他们永远不用互相打电话，否则谁都搞不清谁是 base case」。没有人自称在生产或本地运行过这个模型，所以讨论里没有一手使用经验的反馈。

**Worth reading**
- [2001zhaozhao](https://news.ycombinator.com/item?id=50370626): 列出了 Qwen 3.8 Flash Next 的 84.3 分和 Qwen 3.8-27B 的 73.0 分，指出这篇文章所谓的 SOTA 取决于它在多大程度上针对基准做了优化（benchmaxx），并认为 MoE 架构的 Qwen 可能更便宜。
- [advael](https://news.ycombinator.com/item?id=50370633): 批评在「美国 / 开放权重 / 特定规模」这一层层限定下，SOTA 的说法已被稀释成自我定义的类别冠军。

## 6. Nvidia RTX Spark encrypted firmware slows inference speed to 35% on Linux {#story-6}
*#7 on HN · [mindstudio.ai](https://www.mindstudio.ai/blog/linux-nvidia-rtx-spark-laptop) · 518 points · 230 comments · [HN discussion](https://news.ycombinator.com/item?id=50362905)*

A hands-on MindStudio blog post tests Linux on an MSI Prestige N16 Flip AI Plus based on Nvidia's RTX Spark platform, the laptop counterpart to the DGX Spark. Native Linux works with Nvidia's open kernel driver and CUDA, but on wall power the GPU stays near 780 MHz instead of roughly 2.2 GHz, dropping GPT-OSS-120B from 65.4 tokens/s on Windows and 65.1 under WSL to 13.9 on native Linux; on battery Linux recovers to 61–67 tokens/s. The stated cause is the Windows-only Nvidia Platform Controllers and Framework plus an encrypted firmware power table Linux cannot decrypt, with the 96 GB default GPU memory reservation also adjustable only from Windows.

**Discussion**: The thread splits between outrage and a technical correction. The top comment reads the episode as another step toward cloud-dependent AI and DRM-locked hardware, and many replies tie it to Nvidia's history of limiting consumer features — the two-stream NVENC cap and capped tensor-core throughput — and to encrypted model weights generally. Several commenters push back hard, saying this is missing Linux support on a new Windows-first laptop platform, not a deliberate plot, and cite Nvidia's precedent of adding power-sharing support such as Dynamic Boost years after launch; others reply that a Windows-only encrypted power table is still artificial lock-in. First-hand reports add context: a DGX Spark owner says the Linux-native desktop unit is unaffected, while a Surface Laptop Ultra buyer calls the Nvidia-Microsoft ARM laptop effort rushed and describes the fixed GPU memory split and WSL2 compounding it. The submission also originally confused DGX Spark with RTX Spark and the title was corrected; practically, WSL is treated as the current workaround, with a real fix dependent on Nvidia implementing the platform controller for Linux.

**Worth reading**
- [nonethewiser](https://news.ycombinator.com/item?id=50367331): Argues the article is being misread: the problem is missing Linux driver support for a Windows-first RTX Spark laptop platform, not an Nvidia plot to centralize inference, and notes Dynamic Boost took about two years to reach Linux.
- [jasomill](https://news.ycombinator.com/item?id=50366368): Counter-argues that an anti-abuse motive makes little sense when buyers could use DGX Sparks or WSL, and that Linux running full speed on battery but downclocking on AC power points to a bug rather than a deliberate feature.
- [dagmx](https://news.ycombinator.com/item?id=50369846): A Surface Laptop Ultra owner reports the Nvidia-Microsoft ARM laptop is rushed: the fixed 32 GB GPU memory reservation needs a reboot to change, WSL2 splits memory further, and performance trails a comparably specced Mac.

## 19. Adding Window Functions to a Spreadsheet {#story-19}
*#23 on HN · [getgrist.com](https://www.getgrist.com/blog/running-totals-you-dont-have-to-chase/) · 35 points · 22 comments · [HN discussion](https://news.ycombinator.com/item?id=50366860)*

这是 Grist 的一篇博客文章，作者是该公司的联合创始人兼产品负责人 Dmitry Sagalovskiy。文章说明传统电子表格的 running balance 会在插入或删除行时悄无声息地算错：因为单元格里的公式会把「上一行」调整成指的是原来那个单元格，而不是现在它上面的那一行。文章提出的做法是在电子表格里使用有序查找，具体包括 Grist 的 PREVIOUS()、NEXT() 和 RANK()，以及 lookupRecords(...).find.le()，把排序写进公式本身。文章称，在一张 2 万行的测试表上，用 PREVIOUS() 算完整列 running balance 只需几秒，而用 Python 逐行扫描的写法运行五分钟仍未结束。

**Discussion**: 评论者从几个方向提出了意见。有几个人抱怨文章读起来像 AI 写的；一位评论者认为这种语法很别扭：UPPER_CASE 的函数名和 Python 的 dot 属性访问混在一起；而维护者的回复澄清说，这其实都是纯 Python，PREVIOUS() 返回的是一条完整的记录，.Running_Balance 只是取出其中一个字段，$A 也只是 rec.A 的语法糖，经典 Excel 函数本身就是用 Python 实现的，代码可在 GitHub 上找到。另一位评论者反驳说，返回记录并用点号访问是「clunky」的做法，主张返回一张表，再用列名做一次 index lookup，就像 Google Sheets 里 GOOGLEFINANCE 的工作方式。也有评论者认为，电子表格变得越来越像数据库是好事，但它有使简单任务复杂化的缺陷，而且很难避开近五十年的电子表格语法历史。旁支的讨论则提到了其他替代产品（IronCalc、treesum、omasheet、pyspread），并半开玩笑地说这等于在重新发明 BusinessObjects，或者幻想从小学开始教 SQL——其中有人设想，以后 SQL 对 LLM 来说会像中古英语一样显得过时。

**Worth reading**
- [dsagal](https://news.ycombinator.com/item?id=50369002): Grist 的开发者 dsagal 解释了实际实现：大小写敏感的 Excel 风格函数是 Python 的简单封装，链接到了 grist-core 的 sandbox 源码，并说明 PREVIOUS() 之所以特殊，只是因为它会自动创建索引，以便提升效率。
- [shevy-java](https://news.ycombinator.com/item?id=50367204): 提出了最犀利的语法批评：为什么函数是大写的，而字段访问又用点号？为什么需要同时写 $Person 和 $Date？以及人们是否必须把这些都记在脑子里？
- [whizzter](https://news.ycombinator.com/item?id=50367357): 主张这种数据库化方向是一种误导：它想解决电子表格结果任意的问题，代价却是把「简单操作」变复杂，而且还要面对近五十年的电子表格语法；评论者说，这种语法和 Python 混用，是最大的设计约束。
