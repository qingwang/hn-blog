## 1. REA Reverse – Engineer Anything {#story-1}
*#1 on HN · [rea.tools](https://rea.tools/) · 307 points · 97 comments · [HN discussion](https://news.ycombinator.com/item?id=50028275)*

REA 是一个把逆向工程能力接入编程 Agent 的工具（rea.tools），通过 `npx rea-agents@latest setup` 安装，让 Claude Code 等 Agent 调用 Ghidra/反汇编能力去检查程序并解释其行为。落地页给了两个完整示例：逆向 Chrome 恐龙游戏的 speed update 函数（4,000 次更新后速度为 10.0，10,000 次后为 13.0，上限 13），以及 Windows Calculator 11.2508.4.0（x64，REA 4.1.0）的 % 按钮，恢复出「200 + 10% = 220」是因为加乘两分支规则不同（乘法等于 current×previous/100）。主张是让 Agent 生成可读的函数摘要、重命名与调用关系，实现从可执行文件重建逻辑。

**Discussion**: 讨论很快从工具本身转向 AI 大规糢逆向对社区和法律的冲击。多位老手认可 AI 反编译质量已经不错（有人点名 Touhou 4 的 LLM decomp 变量命名合理、Ghidra 残留很少，一个月就做完），但担心这会毁掉反编译作为爱好：有人反驳说爱好到底是「让老游戏能跑」还是「亲手用 Ghidra」，并以钢琴/drum VST 类比——工具再强也不妨碍人享受过程。另一条主线是法律风险：做 Adobe 系替代品（Storytold/ArtCraft）的开发者明确表示 100% clean room、不碰 Ghidra 和反编译，并警告 REA 用在高知名度专有软件上可能招来诉讼；由此引出一长串关于「LLM 是否等于洗白 IP」「模型是否训练过专有源码」的争论。多位使用者报告实际体验：CVP 类安全限制经常误拦逆向甚至引用 DMCA 条文，Anthropic 的 Opus 5.5 会拒绝，OpenAI 与国产模型更宽松；也有人质疑既然能让 Agent 自己装 Ghidra，REA 究竟多了什么。此外有人批评 `npx … setup` 是新一代 curl | bash，也有人认为 sha256/签名安装包更可验证。

**Worth reading**
- [InvisibleUp](https://news.ycombinator.com/item?id=50029703): 实测了 AI 生成的 Touhou 4 反编译：质量比多数 AI decomp 好得多（matching、变量命名合理），但文件结构更像为 AI 优化而非还原原开发者意图，并担忧逆向社区会被「半成品 decomp + PC 移植」淹没。
- [echelon](https://news.ycombinator.com/item?id=50029110): 正在做 Adobe 替代品的开发者 echelon 明确表示他们完全不用逆向、不看任何专有源码、禁用 Ghidra，是干净的 clean room，并警告 REA 用在高知名度软件上可能在诉讼取证时被查出用了反编译源码。
- [mgaldys4](https://news.ycombinator.com/item?id=50029899): 逆向工程师 mgaldys4 指出 REA 的 Android 支持仍基于 jadx MCP，预处理大型 APK 要几十分钟、无法规模化，于是他自建 droidasc，300MB APK 全局交叉引用只需 1.5 秒，已借此发现 2 个 RCE 和 5 个 root 漏洞。

## 2. Telegram Desktop vulnerability allowed any user's file to be stolen {#story-2}
*#2 on HN · [beaksec.github.io](https://beaksec.github.io/posts/telegram-desktop-one-click-account-takeover/) · 76 points · 26 comments · [HN discussion](https://news.ycombinator.com/item?id=50029123)*

A security write-up by beaksec (posted by g-b-r) describing a chain that turns a clicked link into full account takeover on Telegram Desktop through version 7.2.8 (confirmed on Windows 6.9.3), fixed in 7.2.9 (commit db3405699f), rated CVSS 8.1 High. Two bugs chain together: the app serializes clicked link URLs into a semicolon-separated command string sent over its local socket without escaping semicolons, so a crafted tg:// URL injects an extra OPEN: command; and the internal interpret: URI scheme, originally built to let Telegram publish its own releases, reads any file named in an instruction file and sends it to a chat with no authorization or confirmation. The author shows an attacker can drop the instruction file into Downloads (which Telegram auto-downloads from groups up to 8 MiB) and reach it via relative path, then steal tdata/key_datas, the account folder and the maps index — enough to clone the session since Telegram sets no local passcode by default.

**Discussion**: The thread splits between treating this as a straightforward Telegram bug and arguing the root cause is that desktop OSes let any user process read any user file: g-b-r (submitter) and several others insist it is Telegram's vulnerability and note the OS can't be blamed when the app is what exfiltrates files and reaches ../../../Downloads on its own, while Panzerschrek argues it's really an OS-level weakness and pushes back that only audited, sandboxed apps should be trusted. Counterpoints cite mitigations that already exist — OpenBSD's unveil, the sandboxed Mac App Store build, firejail/FreeBSD jails — though g-b-r notes sandboxing wouldn't have blocked the account-takeover path because it relies on Telegram's own data files. Commenters also rehash broader Telegram skepticism: links to a decade-old 「insecure by design」 piece and Filippo Valsorda's 「Most Backdoor-Looking Bug」 ECDH writeup, plus complaints about phone-number-based accounts and disabled-by-default 2FA. On the technical side, usr1106 and iririririr discuss the single-instance socket design generally, with iririririr noting Firefox has been removing its --noremote option. g-b-r explains the repost (earlier submission id 50019667 had a less alarming title) and highlights how odd it is that Telegram added an internal tool that uploads any file just to publish its own releases; arjie calls it 「JiaTan grade」.

**Worth reading**
- [g-b-r](https://news.ycombinator.com/item?id=50029124): The submitter explains this is a repost with a sharper title and argues the article underplays the general arbitrary-file-theft angle, calling out that the dangerous interpret: scheme existed only to let Telegram publish its own releases.
- [Panzerschrek](https://news.ycombinator.com/item?id=50029822): Panzerschrek argues the real flaw is the OS design that lets any user process read any user file, sparking the thread's main disagreement about app versus OS responsibility.
- [penskymaterial](https://news.ycombinator.com/item?id=50030094): Points to OpenBSD's unveil as an existing OS-level mitigation, undercutting the claim that all modern desktop OSes are equally exposed.

## 3. Eye of Sauron: Long-Range Hidden Spy Camera Detection {#story-3}
*#5 on HN · [usenix.org](https://www.usenix.org/conference/usenixsecurity24/presentation/zhang-qibo) · 102 points · 18 comments · [HN discussion](https://news.ycombinator.com/item?id=49997481)*

The link is the USENIX Security 2024 page for a paper by Qibo Zhang, Daibo Liu and colleagues (Hunan University, UC San Diego, Michigan State) presenting ESauron, described as the first proof-of-concept system to detect and locate wireless, wired and offline spy cameras. The key idea: every camera must first digest captured raw images (encoding, compression) in an inbuilt read-write memory, and those memory operations emit electromagnetic radiation at the memory clock frequency; changing the visual scene triggers a burst of video processing and a detectable EMR surge. Testing 50 camera products, the authors report 100% detection after only 4 stimuli, a detection range exceeding 20 metres even through blockages, and accurate location of every camera.

**Discussion**: Commenters are broadly impressed by the concept, with one calling it a genius approach to the coming privacy cat-and-mouse game alongside ideas like audio poisoning of ambient listening devices. The strongest technical pushback comes from a thread arguing the effect may be easy to defeat: one commenter suggests an 「extremely bad codec」 that dumps raw pixels without compression would produce no scene-change variation, though a reply notes raw 1080p60 fills about a terabyte per hour and proposes a constant-time codec borrowed from cryptography as a better mitigation. Several people point to shielding or larger memory buffers that delay and spread out the processing bursts, with one suggesting the detected EMR is mostly a symptom of poor shielding that vendors could easily fix. A commenter links the Soviet passive listening device The Thing and a related IEEE paper, noting the authors acknowledge their method would likely fail against such passive hardware; others frame the stakes as national security and corporate espionage, and a joking subthread runs on Eye of Sauron versus Palantir. One reader says the talk's speaker was very hard to understand.

**Worth reading**
- [sholladay](https://news.ycombinator.com/item?id=50030140): Draws the parallel to the Soviets' passive The Thing listening device and a related IEEE paper, and notes the authors acknowledge this kind of targeting would probably not work on fully passive hardware.
- [akoboldfrying](https://news.ycombinator.com/item?id=50029390): Speculates that the EMR variation depends on codecs compressing similar frames, so a raw-pixel-dumping codec might be undetectable — prompting a reply (C12) that raw video is impractical and a constant-time codec is a better defence.
- [ranger_danger](https://news.ycombinator.com/item?id=50029261): Expresses surprise that such small EM fluctuations are usable from several metres away, and argues the root cause is improper or absent shielding that most products could fix.

## 4. Can you use autoregressive diffusion to generate market data? {#story-4}
*#9 on HN · [blog.janestreet.com](https://blog.janestreet.com/can-you-use-autoregressive-diffusion-to-generate-market-data/) · 60 points · 22 comments · [HN discussion](https://news.ycombinator.com/item?id=50021410)*

这是 Jane Street 博客关于 2026 年暑期实习生项目的一篇文章。实习生 Kavish 基于 Li 等人的「Autoregressive Image Generation without Vector Quantization」思路，用编码器加扩散头的架构对美国股票四年的订单簿事件流（时间戳、价格、事件类型等）建模，目标是自回归地合成下一个市场事件。核心发现是 DDPM 在 1000 步余弦噪声表下不稳定，超过 88-95% 的值偏离均值 8 个标准差以上，改用时序无关的 rectified flow / flow matching 后开箱即用；而市场数据既非纯连续也非纯离散（价格、时间有尖峰点质量），他用直接的类别头拆分或用「atom smoothing」把尖峰平滑后再回嵌。模型目前还不够准确，但澄清了该把多少离散性烘焙进模型、以及如何表示与平滑特征分布这两个关键旋钮。

**Discussion**: 评论区分成了明显几派。一派真正读了文章并对技术内容赞赏，称这是把扩散模型应用到既非离散也非连续时间序列上的精彩范例，并半开玩笑地说只有少数人读了原文。另一大派转向有效市场假说：有人断言任何准确模型都会因被市场吸收而失效，有人反驳说这假设了模型一定会大到被其他参与者察觉，也有人指出边取决于数据而非模型（如用卫星图像数停车场车辆作为内幕信息的代理）。还有一条支线围绕指数基金展开，争论「过去的业绩不代表未来」与指数投资逻辑，有人引用 Sharpe 1991 的《The Arithmetic of Active Management》说明主动投资者整体扣费后必然落后市场，也有人认为自动定投和指数基金已成为西方养老金，实际上是在押注政治体系维持股市上涨。此外有评论认为真正的护城河是数据量而非模型，量化机构能给出真实赔率而散户只能靠直觉，另一人则讽刺这是试图择时。

**Worth reading**
- [pottertheotter](https://news.ycombinator.com/item?id=50029400): 用 Sharpe (1991)《The Arithmetic of Active Management》的算术论证说明为何指数基金是有逻辑依据的选择。
- [arjie](https://news.ycombinator.com/item?id=50030152): 一位读者称赞这篇实习报告信息密度极高，并质疑为何会预期订单到达时间服从正态分布，认为它更可能是 Hawkes 式的自激过程。
- [asdff](https://news.ycombinator.com/item?id=50029468): 提出量化机构真正的优势是可获取的数据量和实时赔率，而非模型本身，散户只能靠直觉判断形态。

## 5. Compiling Rust to readable C with Eurydice {#story-5}
*#10 on HN · [lwn.net](https://lwn.net/Articles/1055211/) · 59 points · 7 comments · [HN discussion](https://news.ycombinator.com/item?id=50027853)*

这是一篇 LWN 文章，介绍 Eurydice —— 一个把 Rust 代码转换成可读、结构保持的 C 代码的工具，面向高保障软件，因为现有的形式化验证与合规工具只认 C。它由 Inria 与 Microsoft 维护，2023 年启动，采用 MIT 与 Apache-2.0 双许可，基于把 F* 编译成 C 的 KaRaMeL；它借助 Charon 从 rustc 提取 MIR 的 JSON，再转成 KaRaMeL 中间表示并生成 C，曾用于把后量子密码例程从 Rust 迁到 C。文章说明它保留求值顺序和代码结构（与 rustc 生成的位运算循环相反），但尚不能扩展到小型示例之外 —— 泛型需要单态化、动态大小类型只能生成两个版本，作者建议用 -fno-strict-aliasing 编译产出代码；同类的多样化编译器还有 mrustc、GCC Rust 和 Cranelift。

**Discussion**: 讨论很简短，焦点之一是 Eurydice 是否保留了 Rust 的运行时安全特性。一位评论者希望看到边界检查这类运行时安全机制的转换，另一位则反驳说这些检查会随 Rust 语义进入 IR，也应当出现在输出的 C 里，因为该工具的目标正是保持与 Rust 完全相同的语义和安全保证。另有一串玩笑围绕项目名字 Eurydice 的读音展开：把它念成「You're da C」和「You read da C」（后者据 Hadestown 而来），并打趣更贴近「you're rid of C」—— 还顺势问为何不做反方向的编译器。最后有人提出，D 和 C++ 也会受益于同类工具。

**Worth reading**
- [Lvl999Noob](https://news.ycombinator.com/item?id=50028527): 反驳「Eurydice 没覆盖运行时安全」的说法：Rust 的检查会随语义进入 IR 并出现在 C 输出中，保持相同语义与安全性本就是该工具的核心目标。
- [fithisux](https://news.ycombinator.com/item?id=50029868): 指出这种「抽象语言编译成结构保持的 C」的思路对 D 和 C++ 同样有价值。

## 8. Next.js 16.4 {#story-8}
*#15 on HN · [nextjs.org](https://nextjs.org/blog/next-16-4) · 18 points · 17 comments · [HN discussion](https://news.ycombinator.com/item?id=50028855)*

The official release post for Next.js 16.4, which promotes “Cache Components” — a programming model built on 'use cache' annotations that make caching opt-in, declarative and composable — as the recommended choice for every app. It is now enabled by default in new create-next-app projects and is slated to become the default in Next.js 17. The release adds ensureStatic (build-time guard against dynamic content sneaking into a route), new navigation() and prefetch() APIs to defer cached content out of prefetches, an agentic next upgrade --agent workflow with experimental.agentUpgrade reminders and agent feedback, plus out-of-the-box wins: less dev memory and disk use, faster compiles, smaller production bundles, and React 19.3.

**Discussion**: The thread is overwhelmingly critical of Next.js rather than of the 16.4 features specifically: several long-time users say they have lost any coherent mental model of what the framework does, blaming implicit and ever-shifting caching behavior and arcane route-type differences. Alternatives argued for include Vite + React SPA with TanStack Router/Query and a Node/FastAPI backend, which people call simpler, easier to reason about and deployable anywhere; the older Pages Router for its simpler caching; and SvelteKit. A few push back on calling Next a “unified platform” when much of the developer base still runs Pages Router, while one commenter notes 'use cache' also works at the function level and is handy for scaling bottlenecks in a pinch. An adjacent subthread shifts to LLM-era tooling, with developers praising Phoenix and Gleam for giving agents deterministic guardrails (credo, dialyzer, warnings-as-errors) and easier codebases; a counter-argument is that sloppy AI-generated Next apps are a competitive gift to their betters. There is no consensus favoring the release — sentiment toward Next.js itself is broadly negative.

**Worth reading**
- [zoul](https://news.ycombinator.com/item?id=50030062): A long-time user describes how Next's abstraction initially felt like a sane unified platform but that caching quirks and obscure code differences eventually destroyed their mental model of the framework.
- [sergiotapia](https://news.ycombinator.com/item?id=50030041): First-hand account of building a production project on Phoenix for executives and ops staff to vibe-code in, with deterministic guardrails via a mix precommit task chaining compile --warnings-as-errors, format, credo --strict, dialyzer and tests.
- [Imustaskforhelp](https://news.ycombinator.com/item?id=50030230): Reports porting a Go htmx + templ codebase to Gleam with an open-weights model (glm 5.3) in about two small prompts, calling Gleam underrated for such ports.
