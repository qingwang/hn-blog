## 1. Residential proxies detected on White House network {#story-1}

The article's stated signal is timing: roughly half the activity falls between 5 p.m. and midnight Eastern, with almost none in the early morning, which the authors read as a person on the network late into the evening whose device carries an infected proxy SDK rather than an open guest Wi-Fi network. **Discussion**: The dominant response is methodological skepticism: the data ties traffic to IP ownership only, not to a building, and could just as easily be a segmented guest network, a night-shift worker's infected phone, press Wi-Fi, or an isolated IoT VLAN — with one commenter noting the site is new and effectively advertising its own lookup service. ## 3. Images 2.6 {#story-3}
*#3 on HN · [openai.com](https://openai.com/index/introducing-images-2-6/) · 248 points · 160 comments · [HN discussion](https://news.ycombinator.com/item?id=50372945)*

这是 OpenAI 为 Images 2.6 发布的官方公告，该模型已在 ChatGPT、Codex 和 API 上线。它声称生成速度比上一代快 50%，新增 GIF 动画输出、API 端图像标记（image markup）和 SVG 导出，还引入了一个复杂度参数；模型被拆成 GPT‑Image‑2.6 Flare（低质量下最快约 6 秒出图）和 GPT‑Image‑2.6 Sunburst（质量更高、编辑一致性更强两个版本，低质量下的最快约 6 秒出图）。OpenAI 称 ChatGPT、Codex 和 API 每周合计生成 40 亿张图片，即每天超过 5 亿张。

**Discussion**: 讨论从审美问题展开：许多评论者认为输出看起来仍像 「AI slop」，并追问模型为什么摆脱不了这种风格。反驳意见认为，AI 图像那种光泽感、有美感的观感正是普通用户和 RLHF 奖励所偏向的，可以用提示词绕开，只是一般人不会这么做；也有人否认这是标注者的问题，指出食物图像的失败，以及 Z 世代对人类偏好评估的排斥，表明奖励信号在跨领域时应用不当。还有一大串评论指责定价误导：输入输出 token 单价没变，但按 OpenAI 自己的价格计算器，低、中质量档的 token 用量约为 2.5 的 3–4 倍，所以实际每张图的价格大约翻了三倍。有几位实际测试者（包括一位运营 prompt-to-design 网站的开发者）报告称 2.6-flare 比 2.5-flare 更差，并称 arena.ai 排行榜上 2.5 得分更高，而 2.6-sunburst 则被认为更稳。技术评论聚焦在新功能上：一位长期做图像基准测试的评论者指出，基于网格的帧技巧早已存在，GIF 帧间一致性仍然有噪点，而且 SVG 实际上是一次光栅转矢量流程（接到 API 后他还发现需要单独传一个 svg.model 参数，否则返回 400 error）。有几个评论者抱怨他们找不到质量提升，认为图像生成已经趋于平台期，还有人开玩笑说，把每周 40 亿张图的数字看作大量浪费。

**Worth reading**
- [minimaxir](https://news.ycombinator.com/item?id=50373156): 长期做图像基准测试的评论者指出，GIF 生成依赖老式的网格/精灵帧技巧，帧一致性脆弱；SVG 文档证实是光栅转矢量流程，并指出 OpenAI 声称的 50% 加速伴随着与 2.5 相同的标价。

## 4. A thousand fewer paths to root {#story-4}
*#4 on HN · [openai.com](https://openai.com/index/a-thousand-fewer-paths-to-root/) · 291 points · 187 comments · [HN discussion](https://news.ycombinator.com/item?id=50372929)*

OpenAI's cyber team describes a five-stage autonomous pipeline — scout agents pick ~2.8M lines (7% of the kernel, 5,034 audit targets), analyst agents produce 2,308 candidate findings in 12 hours, triage agents reproduce them under KASAN, then exploit and patch generation — run against the Linux kernel master branch in mid-October 2026. It reproduced 1,724 findings (74.7%), yielded 291 information-leak PoCs and 948 working local privilege escalation exploits for $1,213,430 in API credits ($1,279 per LPE), versus 166 LPEs for $513,690 in a July run with GPT‑5.6 Sol; only 3.1% of candidates were pure model error. On an adapted kernelCTF target it got 25 leak PoCs and 21 LPEs for ~$32,936, and it claims at least 10 novel exploitation techniques whose details are withheld; the author frames $1.2M as an upper bound that harness engineering could cut.

**Discussion**: The dominant reaction is that this is unsurprising rather than alarming: LPEs have long been assumed to be one bug away, the kernel is 40M lines of memory-unsafe C, and security people have said for decades that any model relying on the absence of LPEs is not a security model. The main argument is about OpenBSD — one camp says its far lower bug count proves Linux's design and culture are the problem, while others reply that OpenBSD supports a fraction of the hardware, has far fewer eyes and dollars pointed at it, and still ships use-after-free and out-of-bounds CVEs; someone cites Anthropic's Mythos run reporting a single OpenBSD vulnerability. Skeptics question the headline number, likening it to counting every SQL injection path as a separate bug, and the pipeline's author answers that these are distinct issues counted by patches and are all kernel-only, with userspace root daemons out of scope. Several commenters push on what is missing: a breakdown by subsystem and code age, how many findings Sashiko already catches, whether scanning will be continuous with each new model, and whether a human team given the same $1.2M could do comparable work.

**Worth reading**
- [ky1ebot1337](https://news.ycombinator.com/item?id=50373607): The pipeline's author explains the 948 figure counts distinct vulnerabilities by patch (with variant analysis collapsing related exploits) and that all findings are kernel code, with root-running userspace explicitly out of scope.
- [amluto](https://news.ycombinator.com/item?id=50375361): A former handler of non-public Linux kernel security reports asks for a sample of the reports and notes that his own juiciest kernel LPEs were almost never memory-safety bugs, urging the team not to stop at LPEs and infoleaks.
- [tiffanyh](https://news.ycombinator.com/item?id=50374692): Points to Anthropic's Mythos/Glasswing run against OpenBSD, which reportedly surfaced only one vulnerability — the strongest concrete counter-data point in the OpenBSD subthread.

## 6. Spreading Liquid with Three.js {#story-6}
*#9 on HN · [mofu-dev.com](https://mofu-dev.com/en/blog/fluid-foundation/) · 63 points · 11 comments · [HN discussion](https://news.ycombinator.com/item?id=50341576)*

A technical blog post by Misaki Nakano (mofu-dev) about how he built a liquid-foundation spreading effect in Three.js, first implemented in January 2021 for a Japanese cosmetics brand's foundation-simulation promo site and later presented at Vue Fes Japan 2026. The method runs a fluid simulation for velocity, writes liquid thickness into a separate height-map FBO that is advected by backtracing the velocity map, adds an alpha map that keeps the historical maximum thickness so traces linger, and derives surface normals in the fragment shader for Matcap shading instead of deforming geometry. Nakano is explicit that it is not volume-conserving — drawing circles accumulates liquid — and shows that 8-bit height textures produce visible banding in shading versus 32-bit floats; a bonus demo mixes three colored liquids via a simplified Kubelka–Munk model.

**Discussion**: The thread is mostly praise plus one sharp observation: the simulation does not conserve volume, which andai notes by spreading a blob inward until the fluid vanishes, and Tadpole9181 exploits by spinning a small circle to make infinite paint and cycling circle sizes until colors converge toward secondary colors — both points the author already documents in the article. A separate debate opens over Nakano's closing admission that publishing this makes the technique 「no longer something special」 in an era of more spatially capable AI: etatester and xpct find the melancholy understandable, with xpct framing it as future LLMs knowing the trick without anyone learning who invented it, while augment_me tells him to step outside ego and view it from connectedness, and nomel says he would be happy if something he gave away for free became common, noting he public-domains his personal code. Practical asides: brandonpelfrey sees a base for a calligraphy app, and others just register surprise at how smooth the effect looks.

**Worth reading**
- [Tadpole9181](https://news.ycombinator.com/item?id=50375701): Demonstrates a concrete exploit of the volume bug: spinning a small circle generates endless paint, and cycling between large and small circles drifts the mix toward secondary colors.
- [xpct](https://news.ycombinator.com/item?id=50376033): Articulates the counter-argument to the 「don't be sad」 reply — a future LLM will reproduce the effect without anyone reading the write-up or learning who made it.
- [brandonpelfrey](https://news.ycombinator.com/item?id=50375531): Suggests a real application beyond makeup: a calligraphy tool, with some modification to the spreading behavior.

## 7. Insects don't swarm at LED lights {#story-7}
*#10 on HN · [birdsoutsidemywindow.org](https://www.birdsoutsidemywindow.org/2026/11/03/insects-dont-swarm-at-led-lights/) · 233 points · 125 comments · [HN discussion](https://news.ycombinator.com/item?id=50370610)*

A blog post on birdsoutsidemywindow.org arguing that the familiar cloud of bugs around an outdoor lamp is largely a thing of the incandescent past. It claims insects navigate by orienting their backs to moonlight, which carries UV, so any lamp emitting UV looks like the moon and draws them in; LEDs emit almost entirely within the visible 400–700nm band, so they attract far fewer. The backing evidence is a 2016 University of Bristol field experiment comparing incandescent, compact fluorescent, cool-white LED and warm-white LED, which found LEDs attracted significantly fewer insects (including fewer Culicoides midges) and no significant difference between cool and warm white. The post also flags that white LEDs still spike in blue at 450–465nm, which disrupts circadian rhythms in humans and nocturnal animals, and links insect-decline literature.

**Discussion**: The thread is dominated by first-hand contradiction: people with LED headlights, tractor light bars, Fenix flashlights, porch lights, crop grow lights and even LIFX tile arrays report bugs swarming them as badly as ever, and several say the headline should have been 「swarm less」 rather than 「don't swarm」. The most common reconciliation offered is that brightness and spectrum matter more than the LED/incandescent binary — cool-white and blue-pumped LEDs, and grow lights that leak a little UV, are the culprits. legitronics points out the Bristol paper lists both UV and IR as candidate explanations while the blog post credits only UV. piskov calls the entire moon/UV premise wrong and links a 2024 Nature paper on how artificial light disrupts insect flight, arguing insects orient to whichever side is brighter (sky over ground) rather than to the moon specifically; others push back on his phrasing that 「the sky is always brighter than the land」 and on his logic, noting a true conclusion can survive a bad argument. A long side-thread covers LED flicker and PWM drivers — claims insects perceive sub-kilohertz flicker, rebuttals that eyes have no 「refresh rate」 (only a flicker-fusion threshold), plus a factory anecdote about ~1% failure rates on unfiltered PWM fixtures versus decade-old constant-current ones. A second large branch debates the 「windshield test」 of insect decline, splitting between pesticides, urbanization and modern car aerodynamics.

**Worth reading**
- [tw04](https://news.ycombinator.com/item?id=50372236): A commenter says his LED tractor light bar swarms so badly he must wear glasses to keep bugs out of his eyes within 30 seconds, and suspects the post is confusing the overall insect decline with a behavior change.
- [piskov](https://news.ycombinator.com/item?id=50372534): Argues the article's moon-and-UV premise is simply wrong, citing a 2024 Nature paper that artificial light disorients insects via dorsal orientation to a brighter sky rather than to moonlight — so the stated reasoning fails even if the conclusion holds.
- [legitronics](https://news.ycombinator.com/item?id=50372214): Notes that the Bristol paper's own conclusion names both UV and IR as candidate mechanisms, while the blog post reports only UV, and suggests the chart could equally be sorted by power draw.

## 8. So my ISP was hijacking my DNS {#story-8}
*#12 on HN · [karthihegde.dev](https://www.karthihegde.dev/posts/dns_tampering) · 49 points · 25 comments · [HN discussion](https://news.ycombinator.com/item?id=50364860)*

A homelab write-up: a Podman container couldn't reach an external site, and plaintext lookups through Google and Cloudflare DNS all returned the same address — which turned out to be registered to the author's own ISP — while Cloudflare's DoH endpoint returned a different one, revealing in-path tampering. The post then explains why DNSSEC doesn't solve it (it verifies with signatures, it doesn't encrypt, and per an October 2026 Defaults.Exposed census only 7.03% of graded domains have a valid, fully validating chain), why DoT/DoH merely move trust to the resolver, and why the ISP can still see hostnames via SNI or infer them from destination IPs. The author's setup is AdGuard Home fed by dnscrypt-proxy over DNSCrypt, Cloudflare as a fallback for critical containers, and Mullvad through a Tailscale exit node.

**Discussion**: The thread splits between technical fixes and blame. The owner of a UK ISP points out the article never discusses why ISPs do this — many are legally compelled into age-gating, censorship or monitoring regimes, and he doubts any ISP wants to (while stressing that's not an endorsement); others reply that trust is routinely abused. Commenters press for the ISP's name and get it: most Indian ISPs, and in this case ACT Fibernet. One commenter draws a distinction the article blurs — an ISP's own default resolver returning filtered answers is common, but actively rewriting responses from third-party resolvers was previously unheard of to him. On the technical side, a correction notes that SNI is no longer always visible thanks to Encrypted Client Hello, though a linked tally shows very few of the top 10k sites support ECH; a separate argument over DNSSEC produces first-hand reports of obscure breakage (Jira plugins, Sweden's SJ railway site) and the counter-argument that validation failures should be loud rather than quietly optional. Practical anecdotes include Telecom Italia locking the router's DNS setting, worked around by moving DHCP onto a Pi-hole, and a workplace resolver whose 1–2 second latency spikes vanished once Firefox DoH was enabled.

**Worth reading**
- [simonjgreen](https://news.ycombinator.com/item?id=50376284): An ISP owner explains that many carriers tamper under legal compulsion for age gating, censorship or monitoring, not by choice — context the article omits.
- [AceJohnny2](https://news.ycombinator.com/item?id=50375847): Draws the key distinction: an ISP filtering its own default resolver is routine, but rewriting responses from outside resolvers is a different and previously unheard-of act.
- [usr1106](https://news.ycombinator.com/item?id=50376021): A developer who enabled DNSSEC validation for a year reports it broke Jira plugins and Sweden's SJ site, requiring hard-to-diagnose per-domain exemptions.

An essay by psychoanalyst Adam Phillips in the London Review of Books (Vol. 48 No. 20, 5 November 2026) arguing that curiosity is one of the best things about us and that the Freudian superego — the internalised voice of guilt and shame — is essentially the part of us with no curiosity about ourselves, a 「saboteur」 that kills our pleasure in being alive. Phillips traces the idea through Freud, Ferenczi (who wanted analysis to dissolve the superego) and Klein's Roger Money-Kyrle, and frames curiosity as risk: direction without a destination, an admission of dependence and of not being omniscient, easily delegated to others and often envied in them. The piece is largely abstract and ends in a review-style discussion; the fetched text is truncated.

**Discussion**: The thread splits between jokes (Dumbledore's 「curiosity must be handled with care」, 「it killed the cat」, a Blindsight reference to Rorschach and the Big Ben ship) and two substantive disputes. The loudest is about Freud: one commenter calls him 「completely and entirely objectively wrong about everything」 and says 25 mentions of Freud discredit the essay, with others agreeing they stop reading when Freud is cited as an authority; the pushback is that dismissing the intellectual past guarantees repeating its mistakes, and that what feels 「intuitive」 only became so through earlier inquiry. A second critique argues the essay is too long and misses the real worry — that curiosity has a healthy-to-unhealthy spectrum (morbid self-experimentation, say) and that, at societal scale, truth-seeking could in principle conflict with any values at all, so curiosity can undermine what we care about. One practitioner-ish note: a commenter in a technical job says curiosity is a professional obligation, not a luxury — without it you are negligent. Rough consensus: curiosity is broadly good, but nobody defended the essay's prose style, which several found 「slop」-like or unreadable.

**Worth reading**
- [nomel](https://news.ycombinator.com/item?id=50375013): Argues Freud was 「completely and entirely objectively wrong about everything」 and that heavy reliance on him discredits the whole essay, comparing it to physicists citing Aristotelian mechanics.
- [sublinear](https://news.ycombinator.com/item?id=50375363): Direct rebuttal: dismissing Freud assumes someone else already established how wrong he was, and notes that what counts as 「intuitive」 shifts over time precisely because of past inquiry.
- [roenxi](https://news.ycombinator.com/item?id=50374177): Substantive counter-argument that the essay misses the unhealthy end of the spectrum and the deeper question of whether truth-seeking is always compatible with human values.

## 20. Show HN: The DNA of DOOM – How code structure survives across 44 ports {#story-20}
*#33 on HN · [squid-protocol.github.io](https://squid-protocol.github.io/gitgalaxy/museum-of-code/doom-dna/) · 43 points · 23 comments · [HN discussion](https://news.ycombinator.com/item?id=50339183)*

Joe Esquibel scanned the 1997 linuxdoom release plus 43 descendants (faithful copies, source ports, and translations into roughly 20 languages including Go, Scheme, Fortran, COBOL and SQL) with his GitGalaxy engine, which measures function length, branching, inputs and call graphs while ignoring names and text. The post claims structure works like a fingerprint: Chocolate Doom keeps 87% of the original's function names but only 35% of the code inside them, Doom Retro 69% and 0.2%, GZDoom 32% and 0.2%; shape-based look-alike detection was 93% precise and caught about two-thirds of text-verified copies. As controls, Quake, Quake II and Lua share 0–0.6% of DOOM's shape versus Chocolate Doom's 31%, and hiding all names still lets the engine sort 60% of a Go port's functions into the correct one of 16 subsystems (20% by chance, 99% among its most confident quarter).

**Discussion**: The thread is dominated by pushback on the writing rather than the analysis: the top comment asserts flatly that the copy was written by Claude, and several others call it AI slop, complain about vague rhetorical labels like 「the hard case」 and 「the wiring carries the signal」, and say the page reads like a DevOps dashboard instead of an article. The author, joe-esquibel, conceded that it was heavily LLM-written and said he worked hard on the methodology, offering the GitHub repo and JSON dataset for scrutiny; he also took the feedback seriously, saying he could see the AI voice now. Counterpoint came from a few who genuinely enjoyed the experiment, notably the DOOM modding/dehacked nostalgia angle, and gave constructive advice — write the first draft yourself, cut the interactive clutter, and fix the passage that implies Lua descends from the id Tech family. One commenter noted a real genealogy nugget in reply: id shared a tile map editor and file format from Keen through to Doom. There is no consensus on the artifact, but broad agreement that the underlying idea is interesting and the presentation hurt it.

**Worth reading**
- [boomlinde](https://news.ycombinator.com/item?id=50375516): Long, specific critique: the repeated 「the hard case / the fun part / the real test」 framing wears out the reader, and terms like 「wiring」 and 「signal」 are never defined, so the cross-language claims are incomprehensible.
- [rhet0rica](https://news.ycombinator.com/item?id=50374813): Concrete editorial correction: the line about DOOM's shape showing up in Quake, Quake II and Lua reads as if Lua were derived from id Tech, and should be reframed explicitly as a negative control.
- [mjdiloreto](https://news.ycombinator.com/item?id=50372483): Writers' advice with examples — don't let AI write even the first draft, citing 「How code keeps its family resemblance」 and other Claude-typical sentence constructions, because the voice is hard to remove later.
