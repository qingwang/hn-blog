## 4. The tilde in your PATH may not be your HOME {#story-4}
*#4 on HN · [disconnect3d.pl](https://disconnect3d.pl//2026/10/02/dont-put-tilde-in-your-path/) · 165 points · 97 comments · [HN discussion](https://news.ycombinator.com/item?id=50042425)*

一篇博客文章指出，在 ~/.bashrc 或 ~/.zshrc 中写 export PATH="$PATH:~/.local/bin/" 并不会把 ~ 展开成家目录，因为双引号内的波浪号不做展开，结果 PATH 里多出一个字面量 ~ 目录（相对路径 ./~/.local/bin/），作者还演示了把自己编译的 kek 二进制放进那个目录并被 shell 找到执行。触发他发现这个问题的是 nono 沙箱工具发出的警告「PATH entries the sandbox can write to」。修复办法是改用 $HOME，或者把冒号放在引号外：export PATH="$PATH":~/.local/bin，作者并给出用 echo "$PATH" | tr ':' '\n' | grep '~' 自查的方法。

**Discussion**: 讨论大体分几派。一派认为这是常识级陷阱、脚本里根本不该用波浪号，一律用 $HOME 或其他环境变量；另一派（如 paulddraper）给出更细致的引用规则：只给 $ 表达式加双引号，并指出作者那个引号版本其实无法只靠改引号修好，因为波浪号只在词首展开。chasil 起初主张 export PATH="$PATH:"~/.local/bin 是 POSIX 合规写法，被 yencabulator 指出那只是把字面量 ~ 留在路径里，随后他查阅 POSIX 2.6.1「波浪号可跟在未加引号的冒号之后」，改口认定把冒号移出引号才是正确写法。另有一大支讨论转向更换 shell：fish、zsh、nushell、murex 各有拥趸，反方强调 bash/sh 的不可替代优势是到处都已安装。安全方面有人提醒把用户可写目录放在系统目录之前有风险，也有人反驳说既然能写入你的 PATH，通常也能写入你的 shell 配置。

**Worth reading**
- [paulddraper](https://news.ycombinator.com/item?id=50043582): 给出一套实用的 Bash 引用规则（只给 $ 表达式加双引号、只给含特殊字符的字面量加单引号），并指出光换引号并不能修正原文例子，因为波浪号只在词首展开。
- [chasil](https://news.ycombinator.com/item?id=50046172): 在被指出错误后查阅 POSIX 2.6.1，确认波浪号可跟在未加引号的冒号之后，因此 export PATH="$PATH":~/.local/bin 才是既简洁又符合标准的写法。
- [quotemstr](https://news.ycombinator.com/item?id=50044504): 指出文章漏掉的话题：$HOME 与 getpwent(3)/etc/passwd 给出的家目录可能不一致，~ 会用 $HOME，而 ~user 会走用户数据库，各语言运行时的「用户家目录」API 又各不相同。

## 7. How I reverse engineered a commercial spatial audio effect {#story-7}
*#7 on HN · [epestr.com](http://epestr.com/blog/reverse-engineering-a-commercial-spatial-audio-effect/) · 41 points · 17 comments · [HN discussion](https://news.ycombinator.com/item?id=50044272)*

A blog post by epestr (who also posted it) describing how he built a Linux equivalent of a commercial real-time spatial-audio enhancer using PipeWire. After HRTF attempts with the MIT KEMAR database (which sounded 「cheap」 because it was recorded anechoically) and later SADIE II (which included room responses and sounded much closer), he switched to black-box measurement: he generated a probe file of impulses at varying amplitudes, sine sweeps, steady tones, multitone and noise, played it through the program on a friend's laptop, and recorded the output. The extracted 2x2 stereo impulse responses confirmed the surround mode is linear and time-invariant (reconstruction error comparable to run-to-run repeat variation), while a volume-reducing mode was level-dependent and another mode varied between repeats — both unreproducible with fixed convolution; he loaded the four filters into the Saq real-time enhancer and shipped a browser demo.

**Discussion**: The thread is dominated by pushback on the sound itself: the top commenter calls the effect 「Bose barf」 — bass-boosted, mid-scooped processing that cheap tiny drivers made ubiquitous — and says neutral-sounding devices are getting hard to find; others agree the default bass boost is excessive. The author replies that it is a matter of taste, points to the subwoofer slider (now defaulted to 20%), and notes that stacking the effect on already bass-heavy or already-wide material gets grating, asking one critic for the specific rock track that sounded 「squished」. A separate cluster is audiophile advice: buy Etymotic IEMs or planar magnetics and EQ to a reference (with AutoEq, a caveat that no target curve has consensus), and a pointer to ffmpeg's `earwax` filter — which the author says is very close to what he had been trying to build and which he had failed to find via search or an LLM. Skepticism remains that HRTF/spatial processing suits music at all, with one commenter preferring Atmos downmixing and another calling the Nothing Ear effect more realistic; several users also want an on/off A/B comparison of the same clip.

**Worth reading**
- [ryankrage77](https://news.ycombinator.com/item?id=50045975): A concrete counter-example: the effect made an already wide-stereo rock track sound squished and inside his head, with phase and distortion artifacts — and the author asks for the track to investigate.
- [epestr](https://news.ycombinator.com/item?id=50045355): The author says ffmpeg's earwax filter sounds very close to his target and much softer to hear, and that neither search engines nor an LLM had surfaced it for him.
- [mrob](https://news.ycombinator.com/item?id=50045487): Detailed first-hand EQ advice: any low-distortion headphone can be EQed neutral, planar magnetics beat dynamics in the bass, and no consensus exists on the best target curve so flat in a real room is not the reference.

## 8. Valen's Memory Safety: A New Kind of Borrow Checking {#story-8}
*#8 on HN · [verdagon.dev](https://verdagon.dev/blog/valen-group-borrowing) · 103 points · 45 comments · [HN discussion](https://news.ycombinator.com/item?id=50042362)*

这是 verdagon（Evan Ovadia）的一篇博文，介绍其语言 Valen 的新型借用检查器，它基于 Nick Smith 的 Group Borrowing（分组借用）提案：编译器记住每个引用指向哪个路径，从而可以捕获编译期的 use-after-free，并把「shared-xor-mutable」放宽为「无 use-after-free」。文中称该思路已被 Google 的 Carbon（完全转向 group borrowing）、Ante、Plecra 的 exclusion typing、Zeta、Fang 等采纳，而 Mojo 曾拒绝它；Valen 把 group borrowing 与 Vale 的 generational references/region borrowing 结合，并支持与 Rust 互操作。Valen 与 Vale 的区别包括：Valen 有 group borrowing 和普通 generational references、有 Rust 互操作/Rc/comptime，但没有 Vale 的完美重放与无畏 FFI。

**Discussion**: 评论区首先围绕 shared-xor-mutable 展开争论：zamalek 认为把它说成「问题」是误归因，该限制正是 Rust「无畏并发」的来源，而且与生命周期无关，移除它并不是更好的方案；verdagon 回复澄清 Valen 仍能表达 shared-xor-mutable，只是额外支持通过 `in` 关键字显式选择可变别名，因此这两种风格都能表达，且可变别名是 opt-in。命名上多人（kvark、_old_dude_、falconBrisk47）认为「Path Borrowing」比「Group Borrowing」更贴切，verdagon 也表示认同并征求意见，但有人指出 `foo in bar` 在 .NET 语境下更像迭代。amluto 追问多线程下如何保证不可变性，verdagon 回答不可变引用即「没有 mut effect 的引用」，可借该机制实现类似 std::thread::scope 的结构化并发。另有反对声音：octoberfranklin 认为「函数签名描述其修改的路径」会给抽象带来代价，与 C++/Rust 的零成本抽象原则冲突，并吐槽文章前半篇是废话；此外还有关于是否可能回移植到 Rust、给 D/Free Pascal/Java 做改造的讨论，以及作者透露 GPU 编译（可能降级到 Rust MIR、SPIR-V 或 MLIR）和下一篇文章将讲控制流的计划。

## 20. How big is a Git commit? {#story-20}
*#29 on HN · [ratfactor.com](https://ratfactor.com/cards/git-commit-size) · 75 points · 29 comments · [HN discussion](https://news.ycombinator.com/item?id=50017548)*

A short card post by ratfactor (Dave) measuring how much the .git directory grows per commit. An empty repo is ~64 KB; committing 250 tiny files adds 47,640 bytes; a 3-byte change to a single-file repo still adds 8,709 bytes (four loose objects: one commit, two trees, one blob); a 583,840-byte binary adds 297,873 bytes, and a 16.4 MB Linux source file adds only 1.6 MB. The point: git's zlib compression plus eventual packfiles make storage extremely efficient, but tiny commits still carry kilobyte-scale tree/object overhead — 50% to 10% of the uncompressed content for larger commits.

**Discussion**: The largest side-thread is a style argument: several commenters wish the post's shell snippets used long options (--summarize, --bytes) so the code is self-documenting, while another notes short options are not actually more portable — a CI bug traced back to GNU vs BSD `base64 -d` vs `-D`, where the long form `--decode` worked on both. On compression, one commenter asks whether git can use zstd or brotli; the answer given is no, only deflate with configurable levels (core.compression / pack.compression), and raw zlib means packs carry no identifying header, so changing the algorithm would break network exchange; one practitioner separates images into uncompressed .keep packs to avoid wasting CPU on already-compressed JPEGs/PNGs. The most upvoted correction to the article's numbers is that loose-object measurements overstate long-term cost: a tiny change re-stores the whole file until `git gc` packs it, and packfile size with delta compression is what actually matters, though git still has to find a good delta. Others report adjacent engineering: a commenter storing git repos in a distributed filesystem (HopsFS) over S3 with remote-NVMe writes, finding a write-through NVMe cache unworkable because S3 latency is too high, and another mentions compressing with AST-aware paths, concluding git's own compression was better.

**Worth reading**
- [masklinn](https://news.ycombinator.com/item?id=50041462): Details git's compression reality: only deflate, separately tunable for loose objects and packs, no algorithm-identifying header on packs, plus a production trick of keeping pre-compressed images in their own unpacked .keep packs.
- [gblargg](https://news.ycombinator.com/item?id=50041133): Argues the article's loose-object numbers are the wrong metric — a tiny edit re-adds the whole file short-term, while in a packfile it should cost almost nothing, so packfile size is what matters.
- [jamesblonde](https://news.ycombinator.com/item?id=50041590): First-hand account from building HopsFS: git in a FUSE filesystem backed by S3 needs writes to hit remote NVMe and sync asynchronously, and a write-through NVMe cache fails because S3 latency is too high.
